## 0. 먼저 읽을 것 — 기존 테스트 1건과의 의도적 충돌

`waves-event.md` 는 자기 서두에 **"minor: 필드 추가"** 라는 SemVer 규칙을 선언한다. 본 작업은 선택 필드를
추가하므로 **1.1.0 → 1.2.0 minor bump** 가 강제된다. 그런데 기존 테스트
`kiwi-event-contract-content.test.ts › FR-FLOW-046 › %s declares schema version 1.1.0` 가 버전 리터럴을
1.1.0 으로 **정확히 고정**하고 있다. 두 단언은 동시에 만족될 수 없다.

**구현자가 할 일** (단언 약화 아님 — 같은 강도로 새 버전에 재고정):

`test/skills/kiwi-event-contract-content.test.ts` 의 해당 `it` 블록만 아래로 교체한다.

```ts
  it.each(WAVES_COPIES)("%s declares schema version 1.2.0", (copy) => {
    const text = read(copy);
    expect(text, `${copy} must declare the minor-bumped contract version in its title`).toMatch(
      /^#\s*kiwi waves event v1\.2\.0/m
    );
    expect(text, `${copy} emit and schema examples must carry the bumped schema_version`).toMatch(
      /"schema_version"\s*:\s*"1\.2\.0"/
    );
    expect(text, `${copy} must not leave a stale pre-1.2.0 schema_version example behind`).not.toMatch(
      /"schema_version"\s*:\s*"1\.(?:0|1)\.0"/
    );
  });
```

**주의**: `§3` 본문의 산문 표현 `1.1.0 이상` / `1.1.0 미만` / `1.1.0 이벤트가 하나라도 있으면` 은 **그대로 둔다**.
그것들은 grandfather 경계를 가리키는 산문이고, 1.2.0 은 "1.1.0 이상"을 만족하므로 규칙이 그대로 유효하다.
바뀌는 것은 **JSON 예시의 `"schema_version"` 리터럴** 과 **제목**뿐이다.
FR-FLOW-046 의 다른 단언(status enum 4종 고정, 전이도, verdict enum, 카운터 영속 규칙)은 **손대지 않는다**.

## 2. `_shared/kiwi/waves-event.md` (4사본) — v1.2.0

### 2.1 제목 / 버전

- 1행 `# kiwi waves event v1.1.0` → `# kiwi waves event v1.2.0`
- §5 Emit 패턴의 모든 JSON 예시 `"schema_version":"1.1.0"` → `"1.2.0"`
- 그 밖에 `"schema_version":"1.0.0"` / `"1.1.0"` 리터럴이 남아 있으면 안 된다.

### 2.2 §2.2 선택 필드 — `phase` enum 확장 + 신규 3필드

`phase` 행의 **값 셀**을 아래 4종으로 확장한다(테스트는 그 셀만 읽는다).

```
| `phase` | string (enum) | `pipeline` / `srs-authoring` / `wave-verify` / `final-verify` — `in_progress` 이벤트가 어느 단계에 있는지 |
```

신규 선택 필드 3행을 **선택 필드 표에만** 추가한다. **필수 필드 표에 올리면 breaking change** 이며 테스트가 막는다.

```
| `design_baseline` | object | 그 wave 의 설계 기준선 포인터. 아래 §2.4 |
| `constraints_path` | string | 선언된 사용자 제약 아티팩트 경로 |
| `srs_authored` | bool | 그 wave 의 SRS 저작 완료 표식. `phase="srs-authoring"` 이벤트에만 싣는다 |
```

`srs_authored` 규칙 문장(같은 절 어딘가, 1줄):

> `srs_authored` 가 `true` 인 `phase="srs-authoring"` 기록이 그 wave 의 저작 완료 표식이며, 저작 **진행 중인 것과 구분된다** — `phase` 만으로는 저작 시작 시점의 줄과 구분되지 않는다.

### 2.3 §2.4 신설 — `design_baseline` object

새 h3 `### 2.4 \`design_baseline\` object (선택, v1.2.0 신설)` 를 만들고 아래 7행 표를 넣는다.
(기존 §2.3 `verification` object 절은 그대로 두고 그 **뒤**에 붙인다.)

| 키 | 타입 | 값 |
|---|---|---|
| `path` | string | 설계 기준선 아티팩트 경로 (`docs/analysis/kiwi-wave-master-{run_id}/design-baseline.json`) |
| `source_file` | string | 그 wave 를 고정한 입력 문서 경로 |
| `heading_path` | string | 그 wave 가 대응하는 헤딩 경로 |
| `line_start` | number | 소스 범위 시작 줄 |
| `line_end` | number | 소스 범위 끝 줄 |
| `out_of_scope` | array | 어느 wave 에도 배정되지 않고 명시적으로 범위 밖으로 기록한 최상위 섹션 `{ heading, reason }` **전량** |

### 2.4 §2.3 `verification` object 확장

기존 7행(`rounds`/`cap`/`verdict`/`axis_a`/`axis_b`/`residual`/`report_path`)은 **그대로 두고** 아래 3행을 추가한다.

| 키 | 타입 | 값 |
|---|---|---|
| `design_layer` | object | `{ expected: n, mapped: n, unmapped: [...] }` — 설계 기준선 범위의 설계 항목 분모 |
| `preservation_layer` | object | `{ expected: n, checked: n, rows: [{ item, verdict }] }` — `verdict` ∈ `intended-improvement` / `unapproved-damage` |
| `regression` | object | `{ command, exit_code, failing_tests: [...] }` — 그 wave 의 head 에서 실행한 전체 회귀 스위트 |

`residual` 행의 값 셀에 항목 스키마를 명시한다.

```
| `residual` | array | 종료 시점의 미해소 finding **전량**. 각 항목 `{ id, severity, summary, reason_class, cross_wave, carried_into }` |
```

이어서 아래 규칙 문장들을 **각각 한 줄로** 넣는다(테스트가 줄 단위로 앵커한다).

- `` `design_layer.unmapped` 이 **1건이라도** 있으면 `axis_a.roll_up` 을 `ALL_MATCH` 로 기록할 수 없다 — REQ·AC 계층이 완결하더라도 마찬가지다. ``
  - 문장 안에 `수 있다` / `권장` / `바람직` / `원칙적으로` / `가능하면` / `되도록` / `가급적` / `경우에 따라` / `해도 된다` 가 **하나도 없어야** 한다.
- `` `unmapped` 은 **전량**이어야 하며 잘라내지 않는다 — 상위 N 건만 남기면 설계 계층이 커버된 것으로 읽힌다. ``
- `` `regression.exit_code` 가 0 이 아니면 `verdict` 를 `pass` 로 기록하지 않는다 — 통과 `verdict` 는 그 wave head 의 전체 회귀 성공을 요구한다. `` (헤지 어휘 금지)
- `` 열거한 **행 수**가 고정 분모의 개수와 다른 라운드는 두 검증자 **모두**에 대해 **무효**이며, cap 은 소비하되 연속 clean 스트릭은 0 으로 되돌린다. ``
- `` `reason_class` ∈ `draft-stability-skip` / `task-failure-skip` / `scope-boundary-deferred` / `srs-level-unclosable` / `design-gap` / `cross-wave-carry-forward` ``
- `` `cross_wave` 가 `true` 인 항목은 이전 wave 가 만든 산출물을 건드리는 finding 이며, `carried_into` 에 그것을 이월한 wave id 를 적는다. ``

### 2.5 §3 status 전이 — run-scope 이벤트

기존 검증 게이트 문단은 그대로 두고, 아래 문장을 추가한다.

> 전체 wave 최종 검증 결과는 하나의 wave 가 아니라 **run 전체**에 붙는다: 그 이벤트는 `wave` 는 `"all"`, `order` 는 `0`, `phase` 는 `"final-verify"` 를 싣는다. wave 별 최신 상태를 계산할 때는 `wave="all"` 이벤트를 **제외**한다 — 포함하면 존재하지 않는 wave 하나가 영원히 미완료로 읽힌다.

### 2.6 §4 재개 규약 — 전체 완료 술어

기존 첫 불릿을 아래로 교체한다(한 줄, 헤지 금지).

> - 모든 wave 가 `complete` 이고 **그리고** 최신 `final-verify` 이벤트의 `verification.verdict` 가 `pass` → 전체 완료.

이어서 한 문장 추가.

> 최종 검증이 통과하지 않은 run 은 완료로 보고하지 않고 **최종 검증으로 재개한다**.

`run_id` 재사용·라운드 카운터 누적·통과 verdict 비영속 문단은 **그대로 둔다**(FR-FLOW-046 테스트가 고정).
