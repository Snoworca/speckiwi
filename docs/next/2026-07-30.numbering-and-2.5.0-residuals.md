## 1. Known gap, deliberately not claimed

**A numbered sidecar in `docs/spec` can share a number with a scope document, and nothing reports it.**

`SRS-W070` compares scope documents only. Round 3 showed a real path: a project with `01`–`04` plus the legacy `docs/spec/05.completed-work.md` gets `05.five.srs.md` from `scaffold-scope`, and `validate --fail-on-warning` stays clean. The same happens for a consumer's own `01.glossary.md`, and for a project whose highest scope document is `89` (the next is `90`, beside `90.appendix.md`).

An earlier fix attempt in this run *looked* correct — the validator unioned numbered sidecars into the set it checks — but the union was dead: `scopeDocumentsByLeadingNumber` filtered it back out one line later. That is why the union was reverted rather than kept: `parseWorkspace` discovers a **fixed** sidecar set (`05.completed-work.md`, `90.appendix.md`, `91.completed-work-log.md`, `steps/state.md`) rather than reading the directory, so the validator genuinely cannot see an arbitrary numbered file.

Closing it properly means having the parser record the `docs/spec` directory listing and passing it to the rule. That is a parser change, so it needs its own requirement.

### 2.0c Two contract tests that cannot catch what they exist to catch — MEDIUM

Both found on 2026-07-30 by the independent per-AC audit of `IR-CLI-076`–`078`, and both are pre-existing.

**A fabricated `mcpName` in the ToolSpec registry passes every parity test.** With `upgrade` temporarily declaring `mcpName: "upgrade_project"` — a tool the MCP server does not register — `test/release/tool-signature-parity.test.ts` still passed. Only the requirement's own AC-5 assertion caught it. So the registry is not a trustworthy proxy for the live MCP surface: a spec can claim a tool that does not exist and no contract test objects. The fix is a test that enumerates the instantiated server and compares it to the registry's `mcpName` set, rather than comparing the registry to itself.

**`edit_requirement_table_rows` silently ignores unrecognised column keys.** Passing `values: { Covers: …, Notes: … }` (the capitalisation the rendered table header uses) returned `ok: true`, `written: true` and a `replaceLine` operation whose replacement was byte-identical to the original — a reported write that changed nothing. Lowercase `covers` / `notes` works. An unknown key should be an error, not a silent no-op; a caller trusting the envelope would record an evidence correction that never happened.

## 3. Decisions made in this run — do not re-open

- **Sequential, not decades.** `{NN}` is highest + 1, first document `01`. An existing by-tens project is valid and is never renumbered; its next document is one above its highest, not the next ten. This is why this repository's own `10`–`60` layout stayed as it is.
- **The tool's sidecars do not drive allocation.** Counting `90.appendix.md` would push every project's second scope document to `91`.
- **Init does not scaffold a default scope document when the project already has one**, and it registers each existing document under the scope identity that document declares. Binding a pre-existing document to the default `ARCH` identity filed ARCH requirements into it with validation clean — that was measured, not theorised.
- **Line endings are not content.** The agent-block drift comparison normalises CRLF; comparing raw bytes rewrote every Windows checkout on every init.
- **`§30.1`'s successor slot reads incoming rows.** The v3.0.0 text said to scan the discarded requirement's own table, which is the opposite of what `trace-search.ts` does; the ported text was corrected rather than copied.
- **No diagnostic code is cited that the registry does not define.** The v3.0.0 `§23.5` cited `SRS-W042`/`SRS-W043`, which have never existed. `FR-NODE-087` AC-9 is enforced by a test that matches every code token in the document against the registry.
