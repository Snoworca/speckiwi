**Two things about this that were learned the expensive way on 2026-08-10.**

**Every vitest invocation, not just the full suite.** The guard is `setupFiles`, so it runs for a
single-file targeted run exactly as it runs for `npm test`. Wrapping only the long runs and calling
`npx vitest run <one file>` directly for the quick ones is what actually deleted all four sentinels
this session. Put the wrapper in front of every one of them.

**The guard's failure is easy to misattribute, and that is how it goes unnoticed.** It deletes the
sentinels and then fails *one* test — whichever test happened to be running — with a message about
repo pollution. So the symptom is "this file has one more failure than I expected", in a test that
has nothing to do with the sentinels. On 2026-08-10 `tool-signature-parity` showed 2 failures where
1 was expected, the extra one was explained away as pre-existing, and every later run showed 1
because the sentinels were already gone. **If a run shows an unexpected extra failure, check the
sentinels before explaining it.** Recovery cost nothing only because the backup existed.

### 4.1 The disposition — decided by a five-member committee, unanimous

**In-place revision. `supersede_requirement` zero times. No reliance on "in this target" self-release.**

Rules permit it explicitly: `docs/rule/SRS-MD-Rules-v2.5.0.md:1873` says a frozen target's AC change *requires Change Notes* — an obligation, not a prohibition; `:1002` "When the criterion has changed, record the reason in `Change Notes`"; `:607` "Keep the ID even when the wording of the same requirement is modified". Supersede is scoped to *merging* (`:612`, §29.2) and is block-level (`supersede-requirement.ts:215-222`), so revising ~50 boundary assertions would discard ~144 unrelated AC across the carriers.

Auto-release fails on facts: **no code reads "in this target"**, and the tests that guard those AC contain no target vocabulary at all. Relying on it leaves verified requirements holding evidence files that no longer assert their AC — undetectable, since release readiness checks only that the path exists and `Covers` is free text.

### 4.2 The window — T1 vs T2

`assertEditable` (`src/core/mutation/edit-requirement.ts:90-93`) refuses granular edits on a `verified` requirement and names the fix itself: change status first. `update_status` has **no guard** on `verified → implemented` (`update-status.ts:123-137` is `discarded`-only; `:139-156` is `verified`-entry-only).

```
update_status(id, "implemented", reason)     # opens the window
  → replace_acceptance_criteria / edit_requirement_fields / edit_requirement_table_rows
  → update_status(id, "verified", reason)    # re-fires the AC + resolvable-evidence gate
```

**Route every truth-value flip through this window.** `editAcceptanceCriteria` (`check-ac.ts:68-106`) does *not* call `assertEditable` and preserves the `- [x]` checkbox (`:88-94`), so it can silently invert an AC's meaning while the requirement stays verified and no gate ever re-runs. Reserve it for meaning-preserving edits.

**While the window is open, also update VE Notes** (`edit_requirement_table_rows`). VE Notes routinely quote counts and line numbers that the change falsifies, and nothing checks them. This is the one chance.

Two more mechanical facts: `add_requirement` defaults to `stability: "draft"` (`render-requirement.ts:4`) and `verified` + `draft` is **SRS-E033** (`rules.ts:507-508`) — always pass `stability: "evolving"` explicitly. And `trace_links` rows have no ID column; `edit_requirement_table_rows` needs `rowIndex`, not `rowId`.

### 4.3 The classifier — two axes, not one

For each landing, classify touched carriers by:

1. **Red** — the assertion failed. Obvious.
2. **Universe shrink** — an element left a quantifier array (`ORCHESTRATE_PHASE2_VERB_ROWS`, `PHASE2_VERBS`, `DEFERRED_TOOLS`, `GATE_IDS`, `PHASE2_GATE_IDS`). **Nothing goes red and the protection is silently gone.** Treat as touched; revise and Change-Note it anyway.

### 4.5 The pattern C2 established — reuse it for every remaining row

Separate **phase membership** (a fixed fact about the design) from **registration state** (what
changes as phase 2 lands). C2 did this in `src/cli/commands/orchestrate.ts`:

```
ORCHESTRATE_PHASE1_VERB_ROWS      21 rows, unchanged, historical
ORCHESTRATE_PHASE2_VERB_ROWS       5 rows, unchanged — membership, NOT registration
ORCHESTRATE_DEFERRED_VERB_ROWS     the phase-2 rows not yet registered; shrinks as they land
ORCHESTRATE_REGISTERED_VERB_ROWS   derived: PHASE1 ∪ (PHASE2 \ DEFERRED)
```

Why it is worth copying: **every count literal stays a literal and stays true.** `21` and `5` never
move, so they keep working as tripwires; only `4` moves, and moving it is the deliberate act of
landing a row. The derivation makes the two failure directions both loud — registering a leaf
without removing its row from DEFERRED leaves it unfoldable (`orchestrateVerbRow` → `null`, red),
and removing a row from DEFERRED without registering the leaf breaks the set equality (red).

Two things measured the hard way while doing it:

- **Assert the LEAF, not the container.** The first version derived containers from the deferred
  rows and asserted them absent. That works only while every row under a container is deferred: the
  day `lane audit` lands with its three siblings still deferred, it demands `lane` be registered and
  absent at once. The container clause is now conditioned on full deferral.
- **A derived constant cannot violate its own derivation.** A case asserting "no registered row
  belongs to neither phase" was written, passed, and was **vacuous** — the constant is built from
  those two sets. An independent audit caught it. Do not write guards against states the
  construction already excludes; they read as coverage and are not.

## 5. Lessons from this session that are worth keeping

These cost real rework. Two independent verification rounds caught defects that had already been marked verified.

- **A block heading repeats the rule's words.** An unscoped `line()` search matches the heading and leaves the rule sentence below it completely unchecked — a body weakened to `…권장한다` still passes. Strip the heading before asserting. The sibling suite names this trap at `test/skills/orchestrator-delegated-flags.fr-flow-113.test.ts:71-73`; it was re-introduced anyway.
- **Prose counts drift against their own heading.** Adding a sixth flag to a §1.5 heading while the sentence two lines below still says "5개 플래그" produced a self-contradiction in four renderings that no assertion caught. Assert the agreement.
- **Put the caveat where the reader is.** The "no replay consumer yet" warning was recorded only in the SRS Rationale. The SRS is not what an agent reads at runtime, and neither is a commit message. It belongs in the shipped skill text, pinned by an AC.
- **Mutation-check the load-bearing assertions, one variant at a time.** Green proves nothing about whether the assertion bites. Every claim of the form "this is load-bearing" in a VE should name the mutation that reddened it.
- **Section regexes need anchored numbers.** `/^###\s.*6\.2\s/` matched `### 5.2 까칠 리뷰 8축 (snoworca-coder §6.2 동일 …)` first. Use `/^###\s+6\.2\s/`.
- **Distinguish a test defect from an implementation defect in the record.** One of the two failures above would have failed even against a correct implementation; the other was caught by a correct test. Different lessons, different fixes.
- **Ask a workflow for rules and measurements, not for a step script.** A step-level directive authored against a moving tree goes stale — this session produced one that described already-completed work as future, and one of its instructions (`don't add **/`) was simply wrong about gitignore anchoring semantics. Rules do not go stale.
