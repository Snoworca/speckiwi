# `speckiwi upgrade -g` / `speckiwi remove` — 5인 결정위원회 기록

작성 2026-08-17. 5인 위원회(파괴성 · API 설계 · 아키텍처 중복 · 운영 시나리오 · 반대심문)가 독립 판단한 결과와 그 근거를 남긴다. 표결은 근거의 요약이지 근거의 대체가 아니다 — 소수 의견이 이긴 지점이 두 곳 있고 둘 다 아래에 이유를 적었다.

## 0. 착수 전에 확인된 CRITICAL — 홈 루트 오해석

`resolveProjectRoot`(`src/core/project-root.ts:21`)는 `.git` **또는** `docs/spec/00.index.md` 중 먼저 만나는 것에서 멈춘다. speckiwi 프로젝트인지는 검사하지 않는다.

이 개발 머신에서 측정한 사실:

- `C:\Users\beom\docs\spec\00.index.md` 가 **존재한다**
- `C:\Users\beom\.git` 은 **없다**
- 홈의 `CLAUDE.md` · `AGENTS.md` 첫 줄이 `# SpecKiwi SRS workflow v1.9` 다

따라서 홈 트리 아래 아무 디렉터리(다른 저장소 밖)에서 `speckiwi remove` 를 **`-g` 없이** 실행하면 root 가 `C:\Users\beom` 으로 해석되고, 프로젝트 스코프 claude 스킬 루트가 `C:\Users\beom\.claude\skills` — 즉 **전역 스킬 디렉터리**가 된다. 그 안에는 kiwi 스킬과 사용자 자신의 스킬이 함께 있다.

**귀결: 홈-루트 가드가 이 기능의 선행 조건이다.** 해석된 프로젝트 스킬 목적지가 그 에이전트의 전역 목적지와 같으면 `-g` 없이는 진행을 거부한다. 그리고 계획·실행 양쪽에서 해석된 절대 루트를 첫 줄에 출력한다.

### D1 — 지우는 것과 지우지 않는 것

판정 기준은 "경로가 목록에 있다"가 아니라 **"이 도구가 만들었음을 증명할 수 있다"** 이다.

**지운다** (각 항목마다 증명 수단이 다르다):

| 대상 | 증명 수단 |
|---|---|
| `kiwi-*` 스킬 디렉터리 | `.speckiwi-skill-install.json` 의 `installMode`+`agent`+`name` + 설치 checksum 일치 |
| `_shared/kiwi/**` | 남은 스킬이 참조하지 않는 파일만. **스킬 삭제 후** 계산 |
| `.mcp.json` 의 `mcpServers.speckiwi` | JSON 키 단위. **파일은 지우지 않는다** |
| `.git/hooks/pre-commit` | `renderGitPreCommitHook()` 출력과 바이트 동일할 때만 |
| `.claude/settings.json` · `.codex/hooks.json` | `trace.mjs` 를 부르는 **엔트리만** 외과 제거. 남은 내용이 없을 때만 파일 제거 |
| `AGENTS.md` · `CLAUDE.md` 관리 블록 | `hasEndMarker === true` 인 블록만 |
| `docs/.kiwi/hooks/*.mjs` | 번들 내용과 동일할 때만 |
| `.speckiwi-*-stage-*` · `-backup-*` | 이름 규칙이 코드에 고정된 도구 스크래치 |

**지우지 않는다** (전부 보고문에 이름과 이유를 적는다):

- `docs/spec/**` — 요구사항은 도구가 만든 것이 아니라 **사용자가 도구로 쓴 것**이다. `init --force` 가 `00.index.md` 를 덮어써 요구 인덱스를 파괴한 사고가 이 저장소에 CRITICAL 로 기록돼 있고 그 결함은 무증상이었다. **플래그로도 열지 않는다** — `--include-spec` 같은 옵션이 생기는 순간 그것을 켜라고 조언하는 문서나 에이전트가 반드시 생긴다. `init --force` 가 doctor 의 안내를 타고 요구사항을 지운 경로가 정확히 그것이었다.
- `docs/rule/**` — spec 을 남기고 rule 만 지우면 `docs/spec/00.index.md` 의 `| Rules |` 행이 dangling 이 된다. 그건 `upgrade` 가 존재하는 이유인 바로 그 결함을 도구가 스스로 제조하는 것이다.
- `docs/.kiwi/trace/**` — 훅이 누적한 작업 기록이고 다른 사본이 없다. init 은 소비자에게 `.gitignore` 규칙을 설치하지 않으므로 추적 중인지 무시 중인지 도구가 알 수 없다 — 복구 가능성이 소비자 설정에 달린 것은 지우지 않는다.

**두 파일이 특별한 이유.** `.claude/settings.json` 과 `.codex/hooks.json` 에는 소유 표식이 하나도 없다. init 이 `writeIfMissing` 으로만 쓰므로 **파일이 있다는 사실은 speckiwi 가 썼다는 증거가 아니다** — 이미 있었으면 speckiwi 는 한 글자도 쓰지 않았다. 파일 삭제는 사용자의 `permissions` 와 `Stop` 훅을 파괴하고, 방치는 제거 후에도 매 Edit/Write 마다 존재하지 않는 러너를 호출한다. 두 경우 모두 옳은 답은 엔트리 하나만 외과 제거하는 것뿐이다. `.mcp.json` 이 이미 쓰는 규율과 같다.

**소수 의견이 이긴 곳 (1).** 위원 4는 `docs/rule/` 포함을 주장했다 — "init 이 항상 덮어쓰는 것은 도구 소유"라는 규칙이 우아하고 외우기 쉽다. 그러나 그 규칙은 dangling 참조를 만든다. 우아한 규칙보다 만들지 않는 결함이 이겼다.

### D2 — `-g` 는 전역만

이 CLI 안에서 `-g` 는 **이미 두 가지 뜻으로 쓰이고 있다**:

- `init -g` = 가산적. "프로젝트에 더해 전역도"
- `skills install -g` = 선택자. 전역만, project 를 대체 (`scope = options.dest ? "custom" : options.global ? "global" : "project"`)

"뜻이 갈리면 함정"이라는 반대 논거는 아직 갈림이 없다는 전제 위에 있었는데 그 전제가 거짓이다. 어느 쪽을 골라도 절반이 놀란다면, **파괴적 명령에서는 오해했을 때 덜 지우는 쪽**을 고른다. 가산으로 정의하면 전역만 정리하려던 사용자가 프로젝트 배선까지 잃고, 선택자로 정의하면 반대로 오해한 사용자는 한 번 더 실행하면 된다. 덤으로 `npm uninstall -g` 관례, 그리고 같은 산출물을 설치하는 형제 명령 `skills install -g` 양쪽과 일치한다.

**규칙 한 문장: 생성 명령의 `-g` 는 가산, 파괴 명령의 `-g` 는 배타.** 두 명령의 `--help` 에 각각 한 문장으로 못박는다 — 이 비일관은 실재 비용이고, 감추는 대신 적는다.

**따라오는 의무.** 프로젝트 스코프 실행은 전역 잔여를 **탐지해 반드시 출력해야 한다**. 그러지 않으면 프로젝트 32개를 지워도 에이전트는 전역 것을 계속 로드하므로 스킬 목록이 하나도 줄지 않고, 사용자는 "remove 가 아무것도 안 했다"고 결론짓는다. 탐지는 쓰기 없이 가능하다.

**소수 의견이 이긴 곳 (2).** 위원 3·5는 `init -g` 와의 대칭을 주장했다. 대칭은 진짜 가치이지만, **설치의 대칭이 삭제의 대칭을 정당화하지 않는다** — 설치는 두 스코프 모두 되돌릴 수 있고 삭제는 한쪽만 되돌릴 수 없다.

### D3 — 모드 필수

두 선례가 반대를 가리켰다.

- `upgrade`(IR-CLI-088)는 "계획 기본"을 "수행 기본"으로 뒤집었다. 사유: 모든 항목을 나열한 계획이 수행된 실행처럼 읽혀 운영자가 마이그레이션이 끝났다고 오인했다.
- `skills mirror` 는 모드를 필수로 요구하고 맨 명령을 거부한다. 사유: "`--check` 를 기본으로 두면 오늘은 안전하지만 기본값이 바뀌는 날 플래그 하나 빠뜨림으로 `--write` 에 도달할 수 있다. 명시적 모드는 재생성을 의도의 행위로 유지한다."

세 선례를 모두 설명하는 규칙: **맨 명령이 재실행으로 되돌릴 수 없는 상태를 파괴할 수 있으면 기본값을 두지 않는다.** `mirror --write` 는 로컬 편집을 복원 불가하게 파괴한다 → 기본값 없음. `init`/`upgrade` 는 도구 소유만 쓰고 작성자 소유는 거부한다 → 기본값 있음. `remove` 는 정의상 파괴한다 → 기본값 없음.

계획 기본안이 진 지점: 그 안의 유일한 완화책("헤더 한 줄로 계획임을 못박는다")은 IR-CLI-088 이 이미 기각한 완화책의 재제안이다. 기록된 진단은 문구 부재가 아니라 **계획이 항목을 나열한다는 사실 자체**였고, 채택된 해법은 문구 강화가 아니라 기본값 반전이었다. 그리고 remove 의 오독은 upgrade 와 성질이 다르다 — 사용자의 *다음* 행동(`npm uninstall -g speckiwi`)의 전제가 되어, 제거했다고 믿는 환경에서 도구가 계속 도는 무증상 상태를 만든다.

**모드 쌍은 `--dry-run` / `--apply`.** `--check`/`--write` 를 쓰지 않는다 — remove 는 mirror 의 형제가 아니라 init/upgrade 의 형제이고, 이미 두 방언이 있는데 세 번째를 만들 이유가 없다.

**모드 게이트를 안전 근거로 계상하지 않는다.** 이 CLI 의 주 소비자는 사람이 아니라 에이전트이고, `REMOVE_MODE_REQUIRED` 를 받은 에이전트는 망설이지 않고 에러가 지목한 플래그를 붙여 재시도한다. 실제 안전은 홈-루트 가드 · 마커 검증 · drift skip 이 진다. 모드 게이트가 있으니 D1/D5 를 느슨하게 해도 된다고 생각하는 순간 이 결정은 순손실이 된다.

### D4 — `upgrade -g` = `init -g`, 전역 prune 없음 (만장일치)

`upgradeProject` 는 이미 `initProject` 를 호출해 도구 소유 산출물 갱신을 위임한다. `-g` 는 `installSkillsGlobal` 을 그 호출에 얹는 일이며, 에이전트별 홈 존재 게이트와 전역 무-prune 이 정의상 같은 코드에서 따라온다. 신규 로직 0.

upgrade 고유의 두 보수에는 전역 대응물이 **없다**. `insertMissingRulesRow` 는 `docs/spec/00.index.md` 대상이고 전역에는 인덱스가 없다. `repairRulesReferences` 의 전역 대응물은 `~/.claude/CLAUDE.md` — **사용자 개인 지시 파일**이고 `init -g` 조차 손대지 않는 경계 밖이다. 전역 스킬이 구 규칙 문서를 인용하는 경우는 재설치가 본문을 통째 교체하므로 이미 해소된다. 즉 전역에서의 마이그레이션 등가물은 스킬 갱신 그 자체다.

전역 prune 을 하지 않는 이유가 upgrade 에서 **더 강해진다**: `upgrade` 는 `npm i -g speckiwi@latest` 직후 치는 명령, 즉 번들 스킬 집합이 방금 바뀐 시점이다. 그 시점의 전역 prune 은 이번 릴리스에서 이름이 바뀐 스킬을 아직 구 버전에 고정된 다른 프로젝트의 홈에서 지운다.

**대가를 감추지 않는다.** 다음 릴리스가 어떤 스킬을 은퇴시키면 그 스킬은 전역에 영구히 남아 매 세션 로드되고, 에이전트는 존재하지 않는 워크플로를 호출한다. upgrade 로는 절대 정리되지 않는다. 이것이 오히려 `remove -g` 를 만들어야 할 가장 강한 논거다 — remove 는 prune 과 중복이 아니라, **prune 이 설계상 손대기를 거부한 잔여물을 처리하는 유일한 통로**다.

### D5 — checksum 게이트 유지 (만장일치)

`pruneOrphanKiwiSkills` 의 6조건 중 remove 에서 뜻이 달라지는 것은 **조건 2(orphan) 하나뿐**이고, 그것은 이미 파라미터다 (`const keep = new Set(options.sourceSkillNames)`). 빈 집합을 넘기면 나머지 5단계 판정이 한 줄도 안 고치고 그대로 발화한다. 두 번째 삭제기를 쓰는 것은 §10.2 가 중복 코드보다 나쁘다고 규정한 "같은 책임을 두 곳이 나눠 갖기"에 정확히 해당하며, 여기서 어긋남의 결과는 사용자 파일 삭제다.

함수 이름은 중립화한다 — `pruneOrphanKiwiSkills` 는 orphan 아닌 것도 지우게 되면 거짓 이름이 된다. 호출자가 늘어서 생긴 필연적 계약 변경이지 인접 코드 개선이 아니다.

checksum 불일치를 남기는 이유는 두 실패의 비대칭이다. "지웠다는데 남아있다"는 잃는 것이 0 이고 복구가 10초다. "사용자 수정본이 사라졌다"는 `~/.claude/skills` 가 대개 git 저장소가 아니라 복구 불가다. **다만 exit 0 으로 완료를 보고하면 그 순간 잔여는 거짓말이 된다** — skip 이 1건이라도 있으면 non-zero 종료 + 남은 경로 나열이 필수다.

**판정은 항목별이다.** drift 1건이 나머지 전부의 제거를 막으면 사용자는 즉시 탈출 플래그를 찾고, 그 플래그는 수정본까지 지운다. 깨끗한 것은 지우고, drift 된 것은 남기고, 종료 코드로 알린다.

**해제 플래그를 `--force` 로 이름 짓지 않는다.** 이 저장소에서 `--force` 는 이미 "작성자 소유 파일을 덮어쓴다"는 다른 뜻이고 요구 인덱스 파괴 사고가 붙은 단어다. `--include-modified` 를 쓴다.

## 2. 위원회가 지목한 필수 부수 조건

1. **홈-루트 가드** — §0. 없으면 이 머신에서 오늘 당장 전역이 날아간다.
2. **해석된 root 를 출력 첫 줄에 표시** — 계획·실행 양쪽.
3. **MCP 미노출, CLI 전용** — `upgrade` 의 선례와 사유가 그대로 적용된다: "init_project 가 MCP 에 노출된 것은 도구 소유 산출물만 건드리기 때문이고, 그 논리는 작성자 파일을 다시 쓰는 명령으로 확장되지 않는다. 어떤 에이전트도 이 마이그레이션을 무인으로 몰지 않는다."
4. **`resolveDestinationRoot` / `resolveGlobalSkillContext` 공유** — IR-CLI-086 이 "세 진입점이 전역 위치에 대해 서로 다른 답을 냈다"를 이미 기록했다. remove 가 `~/.codex/skills` 를 보는데 설치는 `$CODEX_HOME/skills` 였다면 **아무것도 못 지우고 성공을 보고한다**. 이 기능에서 재발 확률이 가장 높은 결함이다.
5. **`withSrsMutationLock` 취득** — 동시에 도는 init 과 경합하면 반쯤 설치된 디렉터리가 남고, 그건 영구 conflict 로 판정되는 상태다.
6. **npm 패키지는 지우지 않는다는 안내 한 줄** — `speckiwi remove -g` 는 `npm remove -g speckiwi` 와 한 글자 차이로 읽힌다.
7. **위치 인자 방어** — 최상위 이웃 명령이 전부 요구사항 동사(`restore`, `supersede`, `retarget`)다. 누군가 반드시 `speckiwi remove FR-CLI-001` 을 친다. 위치 인자를 받으면 즉시 실패하고 `supersede` 를 안내한다.
8. **doctor 에 폐기 전역 스킬 보고** — doctor 의 드리프트 루프는 소스 집합을 순회하므로 소스에 없는 폐기 이름은 검사 대상에 들어가지 않는다. 이걸 같이 넣지 않으면 `remove -g` 는 아무도 도달하지 못하는 명령이 된다.
9. **ToolSpec 레지스트리 등록** — `speckiwi commands` 카탈로그가 레지스트리에서 파생된다.
10. **`_shared/kiwi` 는 스킬 삭제 후에 계산** — 순서가 뒤집히면 전부 남거나 전부 지워진다.

## 2.1 독립 검증 2축이 잡은 것 (전부 반영)

두 축이 **독립적으로 같은 CRITICAL** 을 찾았다 — §0 의 홈-루트 가드가 실제로는 발화하지 않았다.

| 축 | 결과 |
|---|---|
| 구현↔요구 일치 | AC 판정 MATCH 대부분, **MISMATCH 1**(가드) + **HIGH 2** + MEDIUM 3 + LOW 5 |
| 안전 하한 | **FLOOR BREACHED** — **CRITICAL 1** + **HIGH 2** + MEDIUM 2 + LOW 4 |

### 가드는 있었는데 발화하지 않았다

`resolveProjectRoot` 는 루트를 `realpath` 로 정규화하는데 홈은 `HOME`/`USERPROFILE` 원문이다. 두 경로를 문자열로 비교하면 **같은 디렉터리가 두 문자열**이 되어 가드가 통과시킨다. junction 홈과 대소문자만 다른 홈, 두 경로 모두에서 재현됐고 **전역 관리 스킬이 실제로 삭제됐다** — `ok: true`, `complete: true`, exit 0 으로.

이 요구의 Rationale 이 정확히 그 시나리오를 적어두고 있었다는 점이 교훈이다. **위험을 알고 가드를 썼는데도 비교 한 줄에서 틀렸다.** 기존 테스트는 루트와 홈에 같은 문자열을 넘겨서 이 결함을 구조적으로 잡을 수 없었다 — 그런 테스트는 문자열 비교만 하는 구현에서도 통과한다.

수정: 양변을 같은 방식으로 정규화(존재하지 않는 목적지는 존재하는 최상위 조상까지 realpath 후 나머지 재부착). 두 스펠링을 쓰는 테스트를 추가하고 뮤테이션 red 확인.

### 공유 미러는 소유를 증명하지 않고 지웠다

`_shared/kiwi` 정리에는 스킬 디렉터리를 지키는 4중 판정이 **하나도** 적용되지 않았다. 참조되지 않으면 지웠고, 전역에서는 사용자가 그 디렉터리에 둔 파일까지 삭제됐다. **참조되지 않음은 소유되지 않음과 다른 사실이다.** 이제 번들 소스가 같은 상대경로에 같은 바이트를 갖고 있을 때만 지운다.

### 파괴 후 예외가 보고를 통째로 삼켰다

읽기 전용 `.claude/settings.json` 이 34개 디렉터리와 MCP 키가 이미 삭제된 뒤 실행을 중단시켰고, 호출자는 `removed` 도 `kept` 도 없는 에러 봉투를 받았다. **`kept` 는 손으로 처리할 목록을 알려주는 유일한 수단인데, 그것이 필요해지는 바로 그 순간 사라졌다.** 단계별로 격리해 실패를 kept+warning 으로 격하한다.

### 나머지

거짓 "removed" 보고(인식 못 하는 훅 형태), 중복 관리 블록 미제거, `-g` 가 프로젝트에 락 상태 파일 생성, CRLF 를 "편집했다"고 오인하는 안내, 빈 훅 이벤트 임의 삭제 — 전부 수정하고 각각 테스트를 붙였다.

### 하한이 유지된 것 (안전 축이 깨려다 실패한 경로)

`docs/spec`·`docs/rule`·`docs/.kiwi/trace` 보존, 편집된 스킬 보존, 메타데이터 없는 디렉터리 보존, 이름 바꾼 복사본 보존, symlink 미추종(스킬·`_shared` 양쪽), 맨 명령 거부, 위치 인자 거부, 두 모드 동시 거부, `--dry-run` 순수성, `-g` 배타성, `.mcp.json` 키 단위 편집, 같은 matcher 그룹의 사용자 훅 보존, 프로토타입 오염 무효, init 동시 실행 시 락 직렬화, MCP 미노출.

## 3. 범위 밖으로 남기는 것 (보고만)

- **`install --reinstall`** — "스킬이 깨져 다시 깔고 싶다"는 시나리오는 remove 로 풀 문제가 아니다. 도구가 이미 "remove that directory to reinstall" 이라고 안내하며 사용자를 2단계로 몰고 그 중간 상태가 *스킬 없음*이다. 올바른 해법은 install 이 자기가 쓴 디렉터리를 교체하는 것이지만, 이번 요청 범위 밖이다.
- **install/update 경로의 checksum 부재** — `classifyExistingDestination` 은 identity 필드만 대조하고 내용이 다르면 `update` 를 낸다. `executeOne` 은 디렉터리를 통째 교체하고 성공 시 백업을 삭제한다. 즉 **사용자가 수정한 kiwi 스킬은 다음 `speckiwi init` 한 번에 복구 불가능하게 사라진다.** remove 의 checksum 게이트는 이 배신을 고치지 못한다 — 그래서 remove 의 skip 보고문에 "이 디렉터리들은 다음 `speckiwi init` 이 번들 내용으로 덮어씁니다. 보존하려면 스킬 루트 밖으로 옮기세요"를 반드시 넣는다. 지키지 못할 보호를 약속하지 않기 위해서다.
- **전역 전용 정리의 자리** — D2 가 `-g` 를 배타로 고정했으므로 이 의도는 `remove -g` 가 받는다. `skills` 하위로 옮기자는 안은 진입점이 갈려 채택하지 않았다.
