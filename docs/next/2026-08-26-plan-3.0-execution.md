### 5.2 위 방식에 얹기로 확정된 것 셋

**(가) 요구 등록을 마지막으로 미루지 않는다.** 각 계획 문서의 「4. 작업 단계」 첫머리가 이미 "요구를 먼저 등록한다"이다. **다만 단계 번호는 문서마다 다르다** — 04·05·06 은 0단계, 01·02·03·07·08·09·10·11·13·14·15·16 은 1단계, 17 은 1단계(0단계는 "04 를 먼저 닫는다"), 12 는 선행 항목 확인 뒤 2단계다. 착수할 때마다 등록하면 마지막 `/kiwi-srs-sync` 는 누락분을 줍는 정도로 끝난다. 17개를 다 구현한 뒤 한꺼번에 동기화하면 그 시점에는 어느 변경이 어느 요구에 속하는지 판단할 근거가 코드 diff 밖에 남지 않는다.

**(나) 01번 하나로 파일럿을 먼저 한다.** 한 항목을 끝까지 가 보면 세 가지를 알 수 있다 — 이 루프가 수렴하는지, 한 항목에 얼마가 드는지, 계획의 완료 조건이 정말로 판정 가능한지. 17개를 벌여 놓고 세 번째에서 완료 조건이 판정 불가능함을 발견하면 앞의 둘도 다시 해야 한다.

**(다) 검증 결과를 못 받으면 체크하지 않는다.** 그 항목은 "구현됨, 미검증"으로 남기고 다음으로 간다. **메인 세션이 자기검증으로 대체하지 않는다.** 체크박스가 채워졌다는 것이 곧 검증되었다는 뜻이어야 그 표가 쓸모 있다.

이번 세션에서 검증 에이전트가 결과를 반환하지 않는 일이 반복됐다(§6.1). 다음 세션에서는 **검증 서브에이전트에게 결과를 파일로 쓰게 하는 것**을 함께 시도한다. 메시지 전달이 실패해도 산출물은 디스크에 남는다. 쓸 위치는 스크래치 디렉터리를 쓰고 저장소를 오염시키지 않는다.

## 6. 이번 세션에서 알게 된 것

코드나 git 이력에 남지 않는 것들이다.

### 6.1 서브에이전트 결과 전달이 반복 실패했다

**확인된 사실**: `plan-a2` 와 `plan-b` 두 건은 `failureReason: "You've hit your session limit · resets 3:50am (Asia/Seoul)"` 으로 종료되었고 리셋 후 복구되었다.

**그러나 나머지는 다르다**: `feas2` · `adv2` · `r2-adv` · `r2-consist` · `r3-adv` · `plan-verify-feasibility` 는 전부 `idleReason: "available"` 이었다. 한도 실패 신호 없이 정상 유휴로 돌아왔는데 결과만 오지 않았다. **⚠️ 미검증 —** 한도에 근접했을 때 다르게 동작했을 가능성은 배제할 수 없으나 그것을 확인할 근거가 없다.

같은 요청을 세 번까지 보냈으나 응답이 오지 않았다. 반복 요청은 효과가 없었고, 새 에이전트로 교체하는 것도 마찬가지였다.

**대응으로 한 것**: 판단이 개입하지 않는 검사는 메인 세션이 기계적으로 대체했다 — 인용 실존(223건 전수), 의존 표와 머리표 대조, 자기증명 후보 추출. 이것들은 오히려 더 확정적이다. 그러나 **"이 계획을 실행하면 무엇이 깨지는가"라는 적대적 판단은 대체되지 않았고, 1라운드 결과만 있다.**

### 6.2 계획 수립이 검수보다 정확할 수 있다

계획을 세우던 서브에이전트가 검수 문서의 주장 하나를 반증했고, 메인 세션이 소스로 확인해 검수를 정정했다. 검수는 한 번 훑고 판정하지만 계획은 그것을 실제로 고치려 하므로 더 깊이 판다.

이 사실이 §5.1 의 루프를 뒷받침한다 — **구현 서브에이전트가 계획의 오류를 발견할 수 있고, 그때는 계획을 고치는 것이 옳다.**

### 6.3 검수 문서를 두 번 정정했다

**첫째, 누락**: `update_status { status: "draft" }` 발견을 문서화에서 빠뜨렸다. 진입 축 에이전트가 보고했는데 §2 에 넣지 않았고, 적대 검토자가 다시 찾았다. §2.3.1 로 추가했다.

**둘째, 사실 오류**: "검증기를 아무도 부르지 않는다"는 §3.6 의 서술이 틀렸다. `orchestrate_journal_append` 가 부르는 `appendWavesLine`(`src/cli/commands/orchestrate.ts:949`)이 쓰기 전에 검증기를 부르고 진단이 나오면 거절한다. 다만 `:1046` 이 `engine: "kiwi-orchestrator"` 를 하드코딩해 **wave-master run 에는 그 검증이 미치지 않는다.** 검증이 있다고 믿어지는 자리의 구멍이라 원래 진단보다 무겁다. §3.6 에 정정 블록을 넣었다.

### 6.4 이 결함은 이미 한 번 일어났고 데이터만 수리되었다

### 8.1 한 항목을 수행하는 절차

계획 문서 하나를 열고 다음을 반복한다.

1. **요구를 먼저 등록한다.** 그 문서 「4. 작업 단계」의 첫머리가 이것이다(단계 번호는 문서마다 다르다 — §5.2 (가) 참조). MCP `add_requirement` 또는 CLI 를 쓴다. 요구 ID 를 기록한다.
2. **구현 서브에이전트를 띄운다.** 계획 문서 전문과 요구 ID 를 주고, 「4. 작업 단계」를 순서대로 수행하게 한다. TDD 순서(실패 테스트 → red 확인 → 최소 구현 → green)를 지키게 한다.
3. **검증 서브에이전트를 띄운다.** 계획 문서의 「5. 완료 조건」과 diff 만 준다. **작성자의 결론을 주지 않는다.** 결과를 파일로도 쓰게 한다(§5.3).
4. **개선 서브에이전트를 띄운다.** 검증이 낸 지적을 CRITICAL → HIGH → MEDIUM → LOW 순으로 반영하게 한다.
5. **3~4를 반복한다.** CRITICAL 과 HIGH 가 0이 될 때까지. MEDIUM 이 남으면 한 라운드 더 돌린다.
6. **요구를 `verified` 로 승격한다.** 검증 증거를 붙인다. 증거 없이 승격하지 않는다.
7. **색인의 체크박스를 채운다.** 요구가 `verified` 이고 증거가 있을 때만 채운다.

### 8.2 매 항목에 공통으로 적용되는 것

- **스킬을 고치면 세 렌더링을 함께 고친다.** `skills/claude` · `skills/codex` · `skills/etc`. 그다음 `speckiwi skills mirror --write` 로 `.agents/skills/` 를 재생성한다. **한 렌더링만 고친 변경이 이 저장소의 알려진 실패 형태다**(§6.7).
- **전체 스위트는 `npm test` 로 돌린다.**
- **`npm install` 을 맨손으로 돌리지 않는다.** 셸에 `NODE_ENV=production` 이 있어 devDependencies 가 잘린다. 빌드·pack 은 `NODE_ENV=development`, vitest 는 `NODE_ENV=test`.

### 8.3 절대 하면 안 되는 것

- **`speckiwi init`(특히 `--force`) · `skills install` · `upgrade` · `remove` 를 이 저장소에 실행하지 않는다.** `docs/spec/00.index.md` 를 템플릿으로 덮어쓴다. `skills mirror --write` 만 허용된다.
- **`git checkout` · `git restore` · `git stash` · `git clean` · `git reset --hard` 를 실행하지 않는다.**
- **커밋 메시지에 어떤 시그니처도 넣지 않는다.** `Co-Authored-By` · `Generated with` · `🤖` · `[bot]` 전부 금지. 커밋 후 `git log -1 --format="%B"` 로 확인한다.
- **커밋 제목에 `Phase {n}` · `Step {n}` · `TASK-XXX` 를 넣지 않는다.**
- **`.claude/` · `.codex/` · `.mcp.json` · `docs/spec/steps/` 를 커밋하지 않는다.**
- **서브에이전트가 `C:\Users\beom\.claude` 와 `C:\Users\beom\.codex` 에 쓰지 않게 한다.**
- **`AskUserQuestion` 을 쓰지 않는다.** 사용자 결정이 필요하면 5인 결정 위원회로 자동 결정한다.
