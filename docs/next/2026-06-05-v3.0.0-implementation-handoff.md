## 2. 반드시 지킬 정책·워크플로 (사용자 지시)

1. **SRS 결정 = 3명 위원회 → Claude 타당성 검증 → 자동 진행.** SRS 관련 결정(스코프·버전·AC 정합성·도구 갭 등)이 필요하면 `Workflow` 로 3명 서브에이전트 위원회(각자 다른 lens: 거버넌스 정합성 / 스펙 충실성·변경관리 / 구현·전방호환)를 돌려 심사숙고 결정 → Claude(main)가 타당성 최종 검증 → 타당하면 사용자 확인 없이 자동 진행. (메모리 `decision-committee-auto-decide.md` 참조. SRS 외 일반/사용자 부재 결정은 5-에이전트.) **단 사용자가 직접 결정을 내리면 그게 최우선 — 위원회 불요.**
2. **Cadence = stage 체크포인트 없이 TDD 까지 쭉 진행** (사용자: "쭉 진행"). 매 stage 마다 "계속할까요?" 묻지 말 것. 진짜 결정/모순/blocker 에서만 멈춤.
3. **TDD test-first 강제** (CLAUDE.md §4): 동작 변경은 **실패 테스트 먼저 → red 확인 → 최소 구현 → green → typecheck/lint/회귀 → evidence 부착 → status=implemented**. 실수로 test-after 한 경우 구현 제거 후 재진행. (선언적 *문서* REQ 는 콘텐츠 회귀 테스트로 대체 가능 — FR-FLOW-013 선례 참고.)
4. **§5 검증은 서브에이전트로**: `implemented` → `verified` 전이는 **독립 서브에이전트 리뷰**(편향 없는 입력: 원본 REQ+diff)를 거친 뒤에만. 효율상 **stage 단위 배치 리뷰** 권장. 현재 implemented 4건은 아직 verified 전이 안 됨 — 배치 리뷰 대상.
5. **코드 주석 trace 태그**: sdd 모드(현재)는 변경 코드에 REQ-ID 주석을 남긴다 — 예: `// FR-MCP-020: ...`. (vibe 모드의 `step: {작업이름}` 은 Part 3 구현 후.)
6. **커밋 메시지 시그니처 금지** (CLAUDE.md §6): Co-Authored-By / Generated by 등 일절 금지. 커밋은 **사용자 요청 시에만**.
7. **장시간 백그라운드 작업의 결정·중단·완료** 시 doculight 알림 (메모리 참조, 남용 금지).

## 3. speckiwi CLI 운용 가이드 & 함정 (중요)

- **add-requirement** (이미 등록 완료라 거의 불필요하지만, D3 같은 신규 시):
  `speckiwi add-requirement --type functional --scope <PARSE|NODE|MCP|CLI|FLOW> --target v3.0.0 --title "<t>" --requirement "<stmt>" --ac "<ac1>" --ac "<ac2>" --status planned --stability evolving --priority high --tags "feasibility:high" --trace "Code|src/x.ts:1|addition_site" --json` → 반환 `value.requirementId`.
- **유효 priority enum = `high|medium|low`** (P2 같은 값은 **SRS-E006 Invalid priority**). status enum 에 **`proposed` 없음** → 신규는 `planned`.
- **메타 편집 도구 부재 (2.2.4)**: priority / AC 텍스트 / requirement statement 를 고치는 mutation 도구가 **없다** (이것들이 바로 v3 에서 만들 `edit_acceptance_criteria`=FR-NODE-026, `update_requirement_statement`=FR-NODE-025 — 부트스트랩). 부득이한 경우 **SRS 마크다운 직접 편집**으로 처리하되 **반드시 사용자 명시 사인오프**가 있을 때만 (거버넌스 — 위원회 결론).
- **인덱스 카운트 수동 갱신**: `add_requirement`/`update_status` 는 `00.index.md` §5 Status Summary / §6 Type Summary 를 **자동 갱신하지 않음** → 변경 후 수동 Edit 필요(안 하면 W019/W020 drift). **현재 인덱스(product-wide)**: §5 planned 60 / implemented 4 / verified 115, §6 functional 126 / interface 33. (v3 만 보면 planned 56 / implemented 4.)
- **depends_on 연결**: `speckiwi add-trace <id> --type Requirement --reference <depId> --relation depends_on`.
- **status 전이**: `speckiwi update-status <id> <status>`. `verified` 는 evidence/가드 필요. evidence: `speckiwi add-evidence <id> --type test --reference <testfile> --covers all --notes "..."`.
- **대량 등록 스크립트 패턴**: `docs/analysis/register-part3.mjs` (Node `execSync`, 각 인자 큰따옴표 래핑, **텍스트에 큰따옴표 미포함**, 기존 json 읽을 때 BOM strip). 일회성 도구 — 새 등록 거의 없으니 참고만.
- **MCP vs CLI**: 새 세션에서 MCP 도구가 보이면 MCP 우선(CLAUDE.md 황금률). 안 보이면 CLI.
