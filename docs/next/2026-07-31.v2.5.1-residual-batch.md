**Decide per code: emit it, or stop advertising it.** Default to retracting — a claim the tool does not honour is worse than a missing feature — and emit only where the check is cheap and clearly wanted.

**Load-bearing constraint discovered this session:** the registry and the rules-document table are pinned to each other **in both directions**, by `test/core/diagnostic-registry.test.ts` ("keeps the rules document diagnostic table aligned to the registry") and `test/core/bootstrap/agent-instruction-english.fr-node-086.test.ts` AC-2. So retracting a code means removing it from the registry **and** the document table, and adding one means adding it to both. Adding `SRS-W071` failed both tests until the document row was added; that is how the constraint was found.

Also check whether any retracted code is referenced in prose elsewhere in the rules document (`grep -n 'SRS-E009' docs/rule/`), because `FR-NODE-087` AC-9 fails on a cited code the registry does not define.

## E.1 `FR-MCP-056` supersedes a clause of the verified `IR-CLI-074`

`IR-CLI-074`'s requirement text said the former host rows are "CLI-only", which directly contradicted exposing `scaffold_scope`. Granular edits are refused on a verified requirement, so the sanctioned path was: demote to `implemented` → amend AC-4 to state what remains true plus the supersession → update the test assertion to "hosts no *step* tool" → re-verify. The demotion is recorded in its Change Notes. `set-supersede` stays CLI-only.

Note the asymmetry with the `Related Docs` links, which were **not** fixed by demoting five verified requirements: there the fix was a new tool (`FR-NODE-092`), because the defect was a stale path, not a wrong rule. Here the clause itself was wrong going forward.

## E.2 `repair rules-references` is a repair, not an edit, and is CLI-only

It rewrites a `Related Docs` reference at any status, because `add_related_doc` already writes that row at any status — the verified gate never protected it. What the verified case demands is an audit trail, so every repair appends a Change Note. No MCP tool drives it: it writes inside requirement blocks, the same reasoning `IR-CLI-076` used for `upgrade`.

## E.3 The `repair` subtree is outside the registry-derived catalog

`renderCliCommandNames()` is compared against a program built from **read + mutation trees only**; `registerRepairCommands` is not walked. An AC claiming the catalog lists a repair leaf is false — `IR-CLI-079` AC-3 was corrected to say the opposite before implementation.

## E.4 A `Stability=draft` requirement carries the marker however it got there

The marker states state, not provenance. `add_requirement` still defaults to `draft`; the default is now documented in the rules document rather than changed, so no existing caller's behaviour shifts.

# Part F — Traps

- **A background subagent's final turn text does not reach the main session.** Only idle notifications arrive. Always instruct: *deliver the report by calling SendMessage with `to: "main"`*. Three idles with no report = treat the audit as not performed and say so; never infer a result.
- **Split file ownership between concurrent auditors**, and tell each which files another agent owns. Two auditors probing the same file produced 1–3 different failures per run and made the suite unreadable for twenty minutes.
- **Never `git checkout` / `git restore` / `git stash`.** Everything here is uncommitted. Revert a probe by restoring exact bytes with Edit.
- **Always `npx vitest run --no-file-parallelism`.**
- **`add_requirement` acceptance criteria must not carry an `AC-N:` prefix** — the tool adds it, and you get `AC-1: AC-1: …`. Fix with `replace_acceptance_criteria`.
- **`edit_requirement_table_rows` needs lowercase column keys** (`covers`, not `Covers`). It used to ignore unknown keys and report `written: true` with a byte-identical replacement; `FR-NODE-093` now rejects them.
- **Adding an MCP tool touches four places**: `src/mcp/schemas.ts` (registry `mcpName` + kind), `src/mcp/server.ts` (`toolSchemas` zod entry), `src/mcp/tools/mutation-tools.ts` (handler), and `docs/spec/90.appendix.md` (the tool table — `test/release/tool-signature-parity.test.ts` requires every registered tool to be documented). `test/mcp/mutation-kind-contract.test.ts` also holds a hand-written `EXPECTED_KINDS` map.
- **`AGENTS.md` and `agents.md` are both tracked**; on Windows they are one file and `git add` can keep a stale blob.
