**The `status` field is the hardest part of this item. The writer's side is forced; the reader's side
is the real work.**

Two reviewers converged on this independently, each by measurement:

1. **A round line cannot be written status-free.** `status` is the **only** member of
   `WAVES_EVENT_FIELDS.required` the validator actually enforces: dropping each of the eight in turn,
   seven are accepted silently and only `status` is refused, with `verification-without-status`
   (`waves-validate.ts:147`). And the only status-free line that validates is one carrying **no
   `verification`** — which is not a round record. So "omit the status on loop F" is not an option; it
   is an instruction that cannot be followed.
2. **Therefore both laundering paths must be closed on the READER, not avoided by the writer.**

| path | reader | what it does today |
|---|---|---|
| loop F discharges the run's final verification | `latestFinalVerify`, `waves-validate.ts:500-504` | filters on `phase === "final-verify" ∧ assertsStatus`, which a status-bearing round record now satisfies. Measured: `needsFinalVerify` false, `runComplete` true, **zero diagnostics**. |
| loop P reopens a completed wave | `computeRunProgress`, `waves-validate.ts:483-487` | walks `latestPerWave` and calls `waveStatuses.set(wave, status)` **unconditionally**. Loop P runs at 3.l, `complete` lands at 3.o, so a resumed verification writes after the completion and — with `-post` stripped — regresses the real wave. |

`FR-NODE-159` AC-2 and AC-4 (both `verified`) make status-bearing lines honoured **by design**, so
neither is a bug to route around; the discriminator has to get sharper. For loop F, two candidates are
already visible in `final-verify-witness.fr-node-161.test.ts`: the genuine run-scope line (`:29`)
carries `status: "complete"` and no `event`, while a round record carries `status: "in_progress"` and
`event: "result"`. `waves-event.md:219`'s own emit example writes `status: "complete"`, and
`FR-NODE-161`'s code comment already names `event` as the intended discriminator even though the code
does not use it.

**Write a new red test for each path.** Do **not** rely on the existing criteria to catch these:
`FR-NODE-161`'s fixture is a hard-coded literal without `status`, so it does not track the product —
measured, the suite stays at 16 passed while the behaviour AC-1 asserts is violated. That is §4.6's
own failure class, and an implementer who trusts the suite here will ship the laundering.

**The verdict map**, with the row the earlier document left open now decided:

| round verdict | journal verdict |
|---|---|
| `pass` | `pass` |
| `pass-with-residual` | `pass`, residual carried in full |
| `fail-cap` | `fail-cap` |
| `invalid` | `in-progress` when `outcome.unreachable === false`; **`fail-cap` when it is `true`** |
| `fail-residual` | **`in-progress`** unless the caller supplies an explicit terminality signal |

**The `invalid` row is not one case.** `evaluateRound` short-circuits on the denominator mismatch
*before* the cap check (`verification-gate.ts:77-86`), so an arithmetically unpassable round returns
`invalid` rather than `fail-cap` — an asymmetry that does not exist for valid rounds. Mapping every
`invalid` to `in-progress` therefore writes "the loop is still running" onto a round the tool's own
arithmetic has just declared unpassable, with zero diagnostics. Measured, it is reachable in ordinary
mid-loop positions, not only at the boundary: `mode=max, cap=5, roundIndex=4` returns `invalid` with
`unreachable: true`. `RoundOutcome.unreachable` is already on the return value.

The last row was measured over **55,296 input points**: kernel `fail-residual` is terminal in **0 of
13,304** cases, and carries an empty residual list in 6,652 of them — it means "did not pass yet", not
"left findings unresolved". The journal's `fail-residual` is terminal by definition
(`waves-event.md:105`). The terminal value's real producer is the oscillation stop
(`verify-loop.md:104`), which is **unimplemented** — do not reach back for this mapping to supply it.

**State these costs in the requirement rather than discovering them later.**
`waves-validate.ts:237` reads `const terminal = verdict !== null && verdict !== "in-progress";` — note
the full clause: a `verification` object with no `verdict` key is also non-terminal. `terminal` gates
`truncated-residual`, so mapping to `in-progress` switches that completeness check off. (The
`residual` **and** `axis_b.open` requirement in the line-shape table above is therefore load-bearing
only on `pass` and `fail-cap` lines; do not test it as a universal invariant.)

**One blocker must land with it, and its exemption is wider than it looks.** An honestly recorded
`invalid` round carries the very `frozen_denominator` mismatch that `denominator-mismatch` refuses as
an **error**, so the only honest record of a void round is unwritable. Scope that rule to terminal
verdicts — `truncated-residual` at `:237` is the precedent, in the same function. **But** the map
sends both `invalid` and `fail-residual` to `in-progress`, so a terminal-only exemption exempts every
non-terminating round line, and the journal can no longer tell a void round from a still-running one —
which is the exact fact the exemption exists to preserve. Either accept that and say so, or add a
discriminator (`verification.invalid_round: true` costs one `WAVES_EVENT_FIELDS` row plus four skill
copies — budget it).

**Also carry forward two defects the line shape must not drop.** The out-of-vocabulary `scope`
rejection that `05:1142` requires and `08-03` §1.5 lists as defect 4 has no home in the table above —
restate it as an explicit acceptance criterion. And the `verb` row omits loop L while the `phase` row
includes it; `verify-lane` is in the closed enum, so either add `L → verify-lane` or drop L from both
rows and say that phase 2 owns it.

## 4. Constraints that bind the next session

These are not advice. Each one has a recorded incident behind it.

1. **TDD, test-first.** Write the failing test, observe it fail, then implement. Work written
   implementation-first is discarded and redone.
2. **Verification goes to a subagent.** Never verify your own judgment calls. Objective counts
   (build PASS/FAIL, test totals) are exempt; "does this evidence carry this criterion" is not.
   This session's most valuable finding — that `FR-NODE-164`'s own gate was uncarried — came from a
   verifier, not the author.
3. **Subagent spawn cap is 200 per session and this session exhausted it.** Budget for it. Prefer
   fewer, better-briefed agents; reuse an idle agent with `SendMessage` rather than spawning a fresh
   one. If the cap is hit, say so in the report rather than silently self-verifying.
4. **`grep -a`, never plain `grep`, for any source census.** Four files under `src/` carry literal NUL
   bytes (`conflict.ts` 1, `handoff.ts` 2, `resume.ts` 2, `parser/workspace-parser.ts` 1); plain grep
   prints `Binary file … matches` and the census both under-reports and counts that notice as a hit.
5. **Every probe must assert its own guard held.** `assert old in s` before writing, `assert new != old`
   after. Two probes in a previous session replaced zero occurrences and were read as passes.
6. **A non-vacuity guard must not depend on incidental state.** A guard that passes because of the
   environment rather than because of the property is not a guard.
7. **No signature of any kind in commit messages** — no `Co-Authored-By`, no "Generated with", no
   `[bot]`, no 🤖. Verify with `git log -1 --format="%B"` after every commit. No `Phase {n}` /
   `Step {n}` / `TASK-XXX` in commit **titles**.
8. **Never run `speckiwi init`, `speckiwi skills install` or `speckiwi upgrade --apply` against this
   repository as the target root.**
