Two pieces of work, both in `2.6.0-phase1-kiwi-orchestrator`:

## 2. The `--auto` change

**New behaviour.**

- When a user-decision gate offers options and one is **marked recommended**, `--auto` adopts that
  option immediately. No committee is convened.
- When no option is marked recommended, a **3-member committee decides by simple majority**.
- The unanimity requirement and the 3 → 5 escalation ladder are **removed**.

**Explicitly out of scope for 2.6.0-phase1-kiwi-orchestrator.** The user's original framing also proposed a gate that
judges *why* an option carries a recommendation — adopting it when the recommendation serves
completeness, but sending it to the committee when the recommendation merely serves speed. The
user has **excluded that judgment gate from this version**. Do not design it, do not implement it,
and do not let it leak back in as a "small addition". It can be a later target.

**Unchanged.** Gates registered in a skill's `critical_gates[]` still halt for the user regardless
of `--auto`. The committee never overrides a critical halt.

## 3. What `kiwi-orchestrator` is

A skill that carries a piece of work from an unclear intent all the way to merged, verified code.

**Intake.** If the user's intent is thin, run a QnA to thicken it. If instead the user supplies a
research document, a design document, or a GitHub issue, read it, investigate the code and
architecture that already exist, and ask the user questions where the design is still weak. The
goal of intake is a design of high enough quality to implement from.

**Wave design.** Split the work into waves. Write the wave design out as a document before
implementing anything. For each stage, write a handoff document.

**Handoff documents are for coding agents, not for people. They must be written in English.**
This is a hard requirement, not a preference. The handoff documents themselves go through a
feedback loop of verification and improvement, like any other artifact.

**Parallelism.** For each wave, determine which of its tasks can run in parallel. Tasks that can
run in parallel each get their own worktree. When they finish, subagent feedback loops verify and
improve them until quality is sufficient, and only then do they merge. Some tasks genuinely cannot
be parallelised, so **dividing the tasks correctly at the start is the most important step**.

**Routing by scale and scope.** The orchestrator must judge the **scale and scope** of the work and
decide which execution route to take: `kiwi-wave-master`, TDD mode, or `kiwi-pm`. This is the
orchestrator's own judgment about the work, not a mode read from configuration. Added by the user on
2026-07-31; in scope for `2.6.0-phase1-kiwi-orchestrator`, since it is intake and dispatch rather
than concurrent execution.

Three things this collides with, all of which the design must settle rather than assume:

- A persisted work-mode already exists (`get_work_mode`, or `speckiwi mode`), and `kiwi-pipeline`
  §2.8 already routes on it: `tdd` plus step-scoped work goes to `kiwi-tdd`, everything else takes
  the five-stage sdd chain. When the orchestrator's judgment and the persisted mode disagree, one of
  them has to win, and the design must say which and why.
- The three routes are not siblings. `kiwi-wave-master` delegates each wave to `kiwi-pipeline`, which
  delegates implementation to `kiwi-pm`. Choosing "wave-master" is choosing the outermost shell, not
  an alternative to `kiwi-pm`. The design must describe the ladder, not a flat menu.
- The orchestrator performs its own wave decomposition, which overlaps `kiwi-wave-master` directly.
  Decision D1 already requires extracting the shared engine, so the honest form of "route to
  wave-master" may be "drive the shared wave engine directly" rather than invoking the sibling skill.

A misjudgement must also be recoverable: the design must say what happens when work routed as small
turns out to be large after implementation has started.

**New issues discovered at a stage boundary.** When a stage finishes completely, new issues
sometimes surface. These must not be carried silently into the next stage. Plan how to resolve
them, write the plan to a document, and resolve it under the existing rules. Only then may the
next stage begin.

**Surviving compaction.** Long runs will be compacted repeatedly. The defence is front-loaded:
author the SRS carefully at the start and write enough guardrails that a resumed session cannot
wander off course.

**Debt.** Do not introduce code duplication or architectural technical debt.

## 4. Settled decisions

| # | Decision | Consequence |
|---|---|---|
| D1 | **Extract a shared engine, then coexist with `kiwi-wave-master`.** | The overlapping parts — wave splitting, verification loops, merging — move into `_shared` modules. `kiwi-wave-master` becomes a thin caller over that engine. `kiwi-orchestrator` adds design involvement, parallelism, and handoffs on top. `kiwi-wave-master` will have to be modified; that is accepted. |
| D2 | **Compose first; build only what is missing.** | SRS authoring goes to `/kiwi-srs`, planning to `/kiwi-planner`, implementation to `/kiwi-coder` and `/kiwi-pm`, verification to `/kiwi-review-fix-loop`. `kiwi-orchestrator` owns only wave design, handoff authoring, parallel dispatch, and merging. |
| D3 | **All artifacts live under `docs/research/{work-or-target-name}/`.** | Research, design, wave design documents, and handoff documents share one numbered directory, so a single unit of work has a single context to recover after compaction. This is a separate lineage from the existing `docs/plans/` convention. |
| D4 | **Both work items ship in `2.6.0-phase1-kiwi-orchestrator`.** | The `--auto` change lands alongside the new skill, since the orchestrator will exercise `--auto` gates heavily. |

## 6. The parallelism verdict — binding constraints

Report `02` settled empirically, by running real worktree agents and real merges, that per-task
worktree parallelism **is** feasible here. It is feasible only under the constraints below, and
every one of them was reproduced rather than reasoned about. A design that violates any of them is
wrong, not merely risky.

**C1 — A parallel task's write set may contain only code and tests.** No parallel task may perform
an SRS mutation. Two branches that added requirements to *different* scope documents merged
`00.index.md` cleanly and silently produced wrong rollup counts. `validate` catches it
(`SRS-W019` / `SRS-W020`) and `sync-index` repairs it, which is why C4 exists — but the merge
itself gives no signal.

**C2 — Every requirement id is allocated on the host before fan-out.** Two worktrees independently
allocated `FR-ARCH-001`. Id allocation is not parallelisable, and this is the same mechanism behind
the four real collisions recorded in `docs/research/12`.

**C3 — A worktree's *default* HEAD is stale; the worktree itself is not cut off.** A worktree is
created at the **session-start HEAD**, and that default HEAD sees neither uncommitted work nor commits
made later in the session. It **can** be moved to any *committed* sha by an explicit checkout, because
worktrees share the object database. What is broken is a design that relies on the **default HEAD** to
carry a predecessor's output, or that tries to pass **uncommitted** work between agents.

Measured 2026-07-31 in `.claude/worktrees/agent-a64238f13448420a3`, which sits at `86a090d` while the
host had advanced to `031c4ec`: inside that worktree `git cat-file -t 031c4ec` returns `commit`,
`git rev-parse 031c4ec^{tree}` resolves, and `git merge-base --is-ancestor HEAD 031c4ec` succeeds.

This constraint was previously written as "worktree agents cannot be chained — any design that feeds
one worktree agent's output to another is broken." That over-stated the evidence. Report `02` measured
the default-HEAD staleness and drew the chaining conclusion from it; the chaining conclusion does not
follow, and `02:185` in fact contains the counter-evidence, having computed an ancestry relation
against a later host commit **from inside** a worktree. Correcting this reopens multi-stage parallel
execution, which the over-stated form had ruled out.

**C4 — `validate` followed by `sync-index` is mandatory after every merge**, not advisory. It is
the only detector for the silent class in C1.

**C5 — Worktree agents are born in split-brain.** A worktree agent's MCP call returns
`workspaceRoot` pointing at the *main* repository while its git toplevel is the worktree, because
subagents share the parent's MCP connection and the server's root is fixed to its own process cwd
by design (`REL-MCP-004` / `IR-CLI-045`). This is not a bug to fix; it is the reason C1 exists.

**C6 — Merge classes.** Safe: disjoint code and tests. Loud, so at most one concurrent writer each:
`src/cli/index.ts`, the command modules, a single scope SRS document, `91.completed-work-log.md`,
`kiwi/pipeline.jsonl`, `package.json`. Silent: `00.index.md` rollups. Never parallel: id
allocation, `speckiwi init`.

**C7 — Windows costs are real.** Path budget measured at 188 of 260 characters with `core.longpaths`
unset, leaving roughly 70 characters of headroom. Roughly 119 MB and 4 s of warm-cache `npm ci` per
worktree. `core.autocrlf=true` with no `.gitattributes` means CRLF churn. And this shell carries
`NODE_ENV=production`, under which `npm ci` silently omits devDependencies and still exits 0 — any
per-worktree install must pin it.

Two things stayed undetermined and should not be assumed either way: identical empty
`speckiwi-cli-init-*` directories appear in all six pre-existing worktrees by an unknown mechanism,
and N concurrent `npm ci` runs sharing one cache on Windows was not tested.

### 7.1 The audit resolved it — the table above was wrong where it mattered

`06.deferred-multiroot-audit.md` is authoritative over this section. **Verdict: harvest five named
artifacts, do not adopt the branch as a foundation, do not merge it.** The table above was written
from file names before anyone read the code, and the two entries that most influenced the reading of
this charter were both wrong:

- `wave-file-allocation.ts` is **not** a task scheduler and does not avoid parallel write conflicts.
  It spawns a pinned PowerShell and exports `WaveSparseProofSession`. It never reads a planner sidecar.
- `wave-agent-instructions.ts` does **not** author handoff documents. It **pins** documents — sha256,
  git blob OID, size caps.

Three findings drive the verdict:

- **The branch is architecturally superseded, not merely stale.** It discards `FR-FLOW-029`, which is
  `verified` on mainline (`docs/spec/60.workflow-release.srs.md:2325`) and which **25 requirements
  authored since the fork now build on** (`FR-FLOW-042`..`FR-FLOW-066`), two recording
  `| FR-FLOW-029 | extends |` explicitly. Adopting it retracts a verified requirement out from under
  25 successors. The branch forked at `21e0f5e` (v2.3.1), so its 10,172 "deletions" are mainline
  additions that post-date it — adopting it reverts all of v2.4.0 through v2.5.1.
- **Mainline answered the same question in a different layer and shipped.** `src/core/workflow/` on
  `feat/2.3.0.1` contains no `wave*.ts` at all, and `kiwi-wave-master/SKILL.md` grew 169 → 573 lines
  on mainline while the branch took the same file to 218. Two answers, one filename.
- **The two most-recommended modules fail on inspection.** `event-schema.ts:199` hard-rejects any
  `schema_version != "1.0.0"` while mainline shipped `waves-event.md` v1.3.0, so porting it is a
  contract regression. `wave-spec-client.ts` answers C5 by spawning a per-root MCP server from Node —
  unavailable to a skill, moot under C1, and already recorded as prohibited at `02:402`.

**Harvest list**, under 1,000 lines in total: the pinning half of `wave-agent-instructions.ts`;
`lease-lock.ts` **re-keyed on the git common dir** (as written it keys per `ProjectRoot`, so N
worktrees over one `.git` get no mutual exclusion at all); `deriveCanonicalRequirementReadiness` and
`scopeRequirementDiagnostics` (`wave-spec-client.ts:456-557`, the best-reasoned code on the branch,
with 15 behavioural tests); the expected-parent CAS **technique only** from
`wave-product-committer.ts:759`; and the `safe-path.ts` TOCTOU fix, **which mainline lacks**.

`trusted-git.ts` is **excluded** until an unexplained defect is root-caused: a guard misjudges based
on the caller's cwd, reproduced outside vitest against `dist`, with `dynamicCommandOverrides`
spawning git with no `cwd` (`trusted-git.ts:402-406`). Harvested components must drop their
`runTrustedGit` dependency.

Merge cost, measured with `git merge-tree` rather than estimated: 25 conflicted files, 72 clean
auto-merges. The surprise is that `validate.ts`, `jsonl.ts`, `mutation.ts`, `srs-lock.ts` and
`safe-path.ts` have **zero** mainline commits since the fork and merge clean — the conflict is
entirely contracts and requirements, not code. Plus silent conflicts git will not report: four
duplicate requirement ids against released v2.4.0 requirements, the `FR-FLOW-029` retraction, and
`00.index.md` rollups, which is C1's named silent class.

### 7.2 Correction: a reason *was* recorded

This charter previously stated that no reason for the deferral was recorded anywhere. That was wrong,
and it was wrong because only `docs/next/` was checked. A reason exists in three places: the branch's
own `README.md:319` — **"Security hold."** — the SRS change notes, where the authors reopened their

The genuine process failure is narrower and sharper than "no record": no `docs/next/` entry among
thirteen, so the convention was skipped exactly where it mattered most; no requirement-id coordination
across worktrees, which is the empirical origin of constraint C2; and three rows in
`91.completed-work-log.md` claiming completion for requirements that are still `in_progress`.

Those three rows are **added by the branch and exist only there** — checked with

in what would be merged, not a live integrity problem in the repository — one more reason the harvest

## 6. Standing constraints that apply to this work

- `docs/spec/` is the only source of truth for requirements. No behaviour ships without a
  requirement, and no requirement is marked verified without evidence.
- Behaviour changes follow test-first TDD. Work written implementation-first is discarded and redone.
- Verification is delegated to subagents with unbiased inputs. Self-verification of judgment calls
  is not accepted; objective PASS/FAIL counts are.
- Commit messages carry no signature of any kind, and no phase or step markers in the title.
- Never run `speckiwi init`, `speckiwi skills install`, or `speckiwi upgrade` — which performs by
  default since IR-CLI-088 — against this repository as the target root.
- Run the test suite with `--no-file-parallelism`.
