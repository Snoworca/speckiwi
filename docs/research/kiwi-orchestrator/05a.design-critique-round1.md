## CRITICAL

**C1. The phase ordering makes it impossible to commit the handoffs, and `dispatch-base-dirty` is unevaluable where it is declared.**
`05.orchestrator-design.md:207` places `3.d commit the wave inputs` *before* `3.e freeze-lane-plan` and `3.f handoff authoring`. But `:971` and `:778` state the handoff "is committed to the dispatch base (Phase 3.d)", and load-bearing ordering rule #1 (`:248`) requires "the plan, the sidecar, **the handoff**, the wave design" to be committed before dispatch. At 3.d no handoff and no lane plan exist yet. The gate `dispatch-base-dirty` is declared at "Phase 3.d" (`:1986`) with the predicate "uncommitted content on a path **the handoff references**" — at 3.d that predicate has no input; at 3.g, if there is no second commit step, it fires unconditionally because every handoff is uncommitted. Charter C3 (worktree sees no uncommitted work) then bites for real: lanes read a handoff path that does not exist at `base_sha`.
*Closes it:* split into `3.d commit wave inputs` (plan/sidecar/wave design) and a new `3.f′ commit lane artifacts` after handoff freeze, with `dispatch-base-dirty` evaluated at 3.f′; and re-derive `base_sha` from the 3.f′ commit, not the 3.d one.

**C2. Multi-stage waves are structurally unrepresentable: `base_sha` is frozen per-lane at 3.f, but stages dispatch at different integration heads.**
`3.g` is explicitly "dispatch lanes (**per stage**)" (`:216`), `depends_on_lanes[]` is "never non-empty within a stage" (`:1002`) so cross-stage lane dependencies exist, and `:1290` runs a full-suite merge gate after *each* merge — so the integration head moves between stages. Yet all handoffs are authored and frozen at 3.f, and `base_sha` is a required, frozen front-matter field defined as "integration head at dispatch" (`:991`), sealed into `lane-{k}.lock.json` with a drift digest (`§4.7` rule 4). A stage-2 lane's `base_sha` is unknowable at 3.f. The lane's mandatory first act `git checkout -B … {base_sha}` would then pin stage-2 lanes to the pre-stage-1 base, silently discarding stage 1's merges from their view — and the resulting merge is still clean and still yields a valid `git-ancestor` proof, so nothing downstream detects it. This is exactly the failure class probe assertion 2 exists to prevent.
*Closes it:* make handoff authoring/freeze per **stage**, not per wave (3.e–3.f′ inside the stage loop), or add a `base_sha`-rebinding step with a re-verification of the handoff lock. Either way the phase flow needs an explicit stage iteration; today `§2` shows none.

**C3. The integration branch is never defined — no creation, name, base, resume field, or end-of-run disposition; and there is no rollback for a terminal halt after merges have landed.**
"integration branch" / "integration head" appear only incidentally (`:557`, `:706`, `:917`, `:1289`, `:1303`); `§5.6` writes `git switch {integration}` with `{integration}` undefined. The resume card (`§4.1`) has `open[].branch` for lanes and `run_root`, but **no integration-branch field** — so `computeResumeState` cannot know the merge target after compaction, which defeats the ledger's whole premise. There is no `--base-branch` option in `§14.1`. Worse: `wave-verify-fail-residual`, `post-merge-index-drift`, `srs-mutation-replay-failed`, `design-contradiction-at-stage-boundary` are all terminal halts that occur *after* real merges have landed; the design never says what repository state the user is left in, and there is no `abort` / `revert-run` verb in the closed enum (`§4.4` has only `halt`, "terminal"). `§9.1` mentions an "always-PR-under-`--auto` / never-direct-merge-to-base rule" exactly once, as the *contents of a shared module* — it contradicts `§5.5`/`§5.6`/`§5.9`, which merge directly, contradicts the lane contract's "no push, no PR", and contradicts `§14.2` ("commit/push is deliberately not auto-chained"). No PR-creation step exists anywhere in the phase flow.
*Closes it:* a named `integration_branch` in `frozen`, a `--base-branch` option, a creation step in Phase 0, an explicit merge-target contract for `--auto` vs attended, a `rollback-run` verb, and deletion of either the always-PR rule or the direct-merge steps.

**C4. `acquire()` cannot exist under Profile A, so C7's single most important mitigation has no carrier into the lane.**
`§5.4`'s interface orders `acquire(lane, base_sha)` → `dispatch(lane)`, and `acquire` is where the pinned `NODE_ENV=development npm ci --ignore-scripts` + `npx vitest --version` lives (`:783-788`). But `§5.5:762` states the orchestrator "does **not** issue `git worktree add` itself" — the runtime creates the workspace when the agent is spawned. Under Profile A the workspace does not exist until `dispatch`, so `acquire` has nothing to act on, `workspace_ref` cannot be recorded on the write-ahead `intent` line, and the install must be performed *by the lane agent*. Yet the handoff schema (`§6.1`) has no bootstrap/setup field, its seven required body headings contain no setup section, and the worked example (`§6.3`) never runs `npm ci`. Report `02` §7.3 measured that without the pin `npm ci` silently omits devDependencies and exits 0 — so every Profile A lane would run its `verification_cmd` with no vitest, or with a stale install from the worktree's session-start `package-lock.json`.
*Closes it:* make `acquire` a no-op stub for Profile A, add mandatory `bootstrap` front-matter (the pinned install + the `npx vitest --version` assertion + the `git checkout -B {base_sha}` pair) and a `## Setup` required heading, and add the install/checkout ordering (checkout **before** install, since `package-lock.json` differs between session-start HEAD and `base_sha`).

**C5. User interruption, abandoned child agents, and workspace reclamation are entirely absent.**
The word "timeout", "deadline", "heartbeat", "orphan", "reap", "cleanup" appear nowhere in the design. Consequences, all concrete here:
- Profile A dispatches up to 8 background agents. If the user interrupts, they keep running. This repository has a recorded, reproduced failure exactly here (`MEMORY.md` → `kiwi-bg-agent-session-scoped-unreachable.md`: background teammate names are runtime-session-scoped, so after a resume every previously spawned agent is unreachable while still holding its worktree). A resumed session that reads `dispatch-lane` intent-without-result and re-dispatches gets **two** agents on one branch; the recovery rule (`§4.4`) says only "a branch with commits means the lane ran", which cannot distinguish *running* from *finished*.
- `release(lane)` is declared (`:707`) but Profile A gives no mechanism (the orchestrator does not own the worktree) and no phase step ever calls it. Empirically: `git worktree list` shows **6 stale worktrees** on this checkout right now, at 3 different shas, from earlier sessions.
- A lane that never writes a manifest has no terminal state and no timer; `status ∈ complete | dead | lease-breach-requested` (`:369`) has no "no-response" value.
*Closes it:* a per-lane deadline with a `lane-timeout` gate, a liveness/heartbeat field in the manifest or journal, an explicit `release`/reap step in 3.j and at `halt`, and a stated policy for what a resumed session does when a lane may still be running (the safe answer is: never re-dispatch, always require user adjudication).

## HIGH

**H1. The lane manifest and the deferred-mutation queue contradict the convergence registry and mean two different things per profile — breaking the "profile-blind" claim.**
`manifest_path` is `docs/research/{work}/waves/wave-{n}/lanes/lane-{k}.manifest.json`, written by the lane agent (`:283`, `:1004`, `:1068`). But CP-07 declares `docs/research/{work}/**` and `.kiwi/**` `orchestrator-only` (`:897-900`), and the claim audit fails any lane whose delta touches an orchestrator-only glob (`:1276`). Under Profile A the path resolves inside the worktree and must be read by the host out of `.claude/worktrees/agent-*/…`, which nothing states. Under Profile B (shared tree) the same path *is* the host path, so the lane writes directly into the orchestrator-only region and, if uncommitted, dirties the tree for the next lane's dispatch-base check. `deferred_mutations_path` under gitignored `.kiwi/` compounds it.
*Closes it:* state that manifest and queue are workspace-local and uncommitted, define how `collect()` resolves them per profile, and carve them out of CP-07 explicitly.

**H2. The `.agents/skills/**` mirror has no permitted writer, yet four-copy parity is a shipping requirement.**
CP-05 marks `.agents/skills/**` `orchestrator-only` and notes regeneration "requires `speckiwi skills install`, forbidden against this repo by charter §6" (`:892-894`) — i.e. the only writer is the orchestrator, and the orchestrator is forbidden from writing it. Meanwhile `§9.4` mirrors `kiwi-orchestrator` normally, `§14.5` requires `waves-event.md` v1.4.0 "in all four copies … edited in one change", and E28 asserts set-equality "across all four shipped copies". I verified there is no mirror-sync script (`scripts/` holds only `release-check.mjs` and `version-check.mjs`); the mirror at `.agents/skills/_shared/kiwi/` is maintained out-of-band.
*Closes it:* name the sanctioned mechanism (hand-authored mirror edit, or a new `speckiwi skills mirror --check/--write` that is not `init`), and make it a step in the work order.

**H3. Profile A depends on `.claude/worktrees/` being ignored, and that is true only via a machine-local, untracked file.**
`git check-ignore -v .claude/worktrees` resolves to `.git/info/exclude:11`, **not** `.gitignore` (which I read in full — it does not mention `.claude/`). On any fresh clone, CI runner, or second developer machine, every lane worktree is untracked content inside the host tree: `git status --porcelain` becomes thousands of lines, `dispatch-base-dirty` becomes noise, and any broad `git add` at the dispatch-base commit stages another lane's source tree. Neither the preflight nor the six probe assertions check this.
*Closes it:* add a probe/preflight assertion that the isolation root is git-ignored at the host, and require `.claude/worktrees/` in tracked `.gitignore`.

**H4. "Three independent signals" are not independent.**
`:1279` requires manifest `finished_at` **and** branch commits **and** a `TASK_DONE` in the lane's `pipeline.jsonl`. The manifest and the pipeline line are both written by the same lane agent into the same workspace; only the branch is externally witnessed. The stated purpose — "the AND is what stops a half-dead lane presenting as complete" — is not achieved against an agent that writes both files. This matters because the whole authentication story rests on it.
*Closes it:* either drop the independence claim and rely on the integrator's own re-run of `acceptance[]` (which *is* independent), or add a genuinely external second signal (e.g. the host-side child-agent completion record).

**H5. There is no path for a design item discovered to be wrong *mid-wave*.**
`design-gap` and `design-contradiction` are stage-boundary-only (`§8`, gate at 3.l). Mid-wave, a lane that finds `[D-031]` unimplementable has three options, none correct: `lease-breach-requested` (a path-scope state), die into the serial epilogue (which discards the finding — loop L's denominator is `acceptance[]` rows, not design validity), or implement something wrong. Simultaneously `invariant_digest` over the frozen block makes any mid-wave design amendment a `run-invariant-drift` halt by construction. So the charter's *"wave design turns out wrong"* case resolves either as a silent wrong implementation or as a drift halt with no sanctioned amendment route.
*Closes it:* add a `design-refuted` lane terminal state that carries a `[D-nnn]` id and evidence, a `stage-issue` intake for it mid-wave, and an explicit legitimate-amendment path (new design lock + new journal line) that does not read as drift.

**H6. The charter's "do not introduce code duplication or architectural technical debt" has no phase, gate, artifact, or requirement.**
The only mention of a duplication detector is inside `§17.6` ("runs a duplication auditor over the union of lane diffs in the serial epilogue") — it appears in no phase (`§2`), no gate table (`§13`), no artifact inventory (`§3`), no CLI verb (`§10.6`), and no requirement (`§15`). A charter requirement that exists only in the self-criticism section is not covered. The risk is structurally elevated here precisely because lanes cannot see each other.
*Closes it:* promote the auditor into 3.j's serial epilogue as a named step with an artifact and a finding class, and give it a `T`-row in `§15.2`.

**H7. `06.deferred-multiroot-audit.md` is a hard precondition with no producer.**
Charter §7 makes it blocking; `§0.4` gates A1/A2/A3 on it; `§13` declares `deferred-branch-audit-pending` as a critical gate; `§10.5` step 4 says "`06` lands" as a passive event. No work item, owner, wave, or requirement produces it. The directory listing confirms `06` does not exist while `07` does. A blocking artifact nobody is assigned to write is a run that halts at Preflight P.6.
*Closes it:* make authoring `06` an explicit pre-wave-0 work item with a named scope (per-capability implemented-and-tested / implemented-untested / stubbed), or state that the design proceeds with the `§0.4` verdict and remove the gate.

**H8. The `--auto` contract in `§12` reinstates the escalation ladder the charter deleted, without recording a charter amendment.**
Charter §2: "The unanimity requirement and the 3 → 5 escalation ladder are **removed**", and charter §preamble: "If a later document in this directory contradicts this file, this file wins." `§12`/`07` reinstate "If no majority exists, add two members **once** and re-vote" — a 3→5 rung on a different trigger. A1 in `§15.4` states both halves in one sentence ("the 3→5 / 5→7 ladder are removed; a tie escalates once by two members"), which will be authored into a requirement as a self-contradiction. Separately, `07:184` notes the six stale worktrees carry the old ladder text — nothing in the design updates or invalidates them.
*Closes it:* get an explicit user amendment to charter §2 for the tie rung, or drop it (with 3 members and a binary option set a tie is impossible; the rung only exists for ≥3 options and degraded quorum, which could be handled by escalating to critical instead). Split A1 into two requirements so neither states a contradiction.

**H9. Under `--auto`, intake QnA — the one place the charter names the user — becomes committee-decidable with no gate.**
Charter §3: "ask the user questions where the design is still weak", and the goal of intake is "a design of high enough quality to implement from". `§7.2` routes a `needs-decision` row to `AskUserQuestion`, "subject to the standard read-time replacement … a recommended option is adopted immediately and otherwise a 3-member committee decides". `design-intake-insufficient` fires only on **cap exhaustion**, so an unattended run whose committee answers every design question converges without ever consulting the user. That is the one substitution the charter's intake section does not authorise.
*Closes it:* either declare intake QnA a `critical_gates[]` member (halts regardless of `--auto`), or state explicitly that `--auto` intake is a user-accepted degradation and record it in the run header and the journal.

## MEDIUM

**M1. No resource ceilings beyond lane count.** No per-lane or per-run wall-clock budget, no subagent/token spend ceiling (6 loops × up to 8 lanes × up to 8 waves with only per-loop round caps), no free-disk preflight against the stated ~950 MB at cap 8 plus already-resident stale worktrees, and no mitigation for the admitted-untested N-concurrent-`npm ci`-on-one-Windows-cache case (`§17.2`) — serialising `acquire()` is a one-line mitigation the design does not propose. *Closes it:* a `--budget`/deadline option, a disk assertion in the probe, and a stated install concurrency policy.

**M2. New code lands outside the enforced coverage set while modified code sits inside it.** `vitest.config.ts` coverage `include` is `src/cli/**`, `src/core/{mutation,parser,validator,workflow}/**`, `src/mcp/**` — `src/core/orchestrator/**` (where all ~18 new modules go, `§10.1`) is **not** included, so the design's largest executable surface carries no threshold. Meanwhile the design modifies `src/core/workflow/validate.ts` (`normalizeTasks`) and `jsonl.ts` (`eventKeying`), both under a 90% lines/statements threshold. The design never mentions coverage. *Closes it:* add `src/core/orchestrator/**` to `include` with a threshold, in the same change.

**M3. Integration order within a stage is unspecified, and the reconciliation predicate is undefined for a partially-dispatched multi-stage wave.** `§7.5` runs a gate "after every `integrate(lane)`" but never fixes the order; lane-id order is stated only for coupling *recovery* (`:1303`) and for `replay` (`:908`). `§4.6` compares `journal_lanes` / `git_lanes` / `lock_lanes` / `card_lanes` and classifies "anything else → divergent" — `lock_lanes` contains every lane of the wave including stage-3 lanes not yet dispatched, so the normal mid-wave state has no defined classification. The resume card's `stage` is a free string (`"wave-2/dispatch"`) with no stage index. *Closes it:* pin integration to lane-id order, add a stage coordinate to the card and to `lanes.lock.json`, and define "agree" per stage.

**M4. Probe assertion 2 does not test the case it is declared to decide.** `§5.5` calls assertion 2 "the decisive one" for C3, but it runs at Preflight P.5 against a pre-existing `{base_sha}`. The dangerous case is checking out a sha **created after the worktree existed** — report `02` §5.2 measured that worktrees sit at session-start HEAD while the host advances. Report `02` does show a later host commit is reachable from inside a worktree, so the mechanism is probably fine, but the probe as specified does not measure it. The probe also asserts nothing about ignore status (H3) or free disk (M1). *Closes it:* have the probe make a throwaway host commit after the probe worktree exists and check that sha out inside it.

**M5. The charter's stated compaction defence is dropped without being flagged.** Charter §3: "The defence is front-loaded: **author the SRS carefully at the start**". The design defers SRS to per-wave `3.b` and states "Targets are not registered up front" (`:244`), substituting a front-loaded *design* document. That may well be better, but it is a divergence from a binding document and is not recorded as one — and `§16` (rejected alternatives) does not carry it. *Closes it:* record it as an explicit deviation with the reason, or reinstate up-front SRS authoring.

**M6. `kiwi/waves.jsonl` tracked-vs-untracked is unspecified.** `git ls-files kiwi/` returns only `kiwi/pipeline.jsonl`; `waves.jsonl` is neither tracked nor gitignored. If it is committed, every dispatch-base commit carries mid-run journal state and CP-07's restore must handle it at every merge; if it is not, it is permanent `git status` noise at the host and absent from every lane worktree. The design assumes neither. *Closes it:* state the policy and, if untracked, add it to `.gitignore` alongside the other `kiwi/` runtime files.

**M7. The `writer` stamp authenticates the path, not the payload — the compensation in `§10.2` overstates.** "A run containing hand-appended journal lines fails its own audit" is true only for bash-appended lines. An agent calling `orchestrate journal append` with a fabricated `frozen_denominator`/row-count/residual payload gets a valid `writer` stamp and passes `orchestrate validate --strict`. `evaluateRound` checks internal consistency, which raises the cost of fabrication but is not authentication. *Closes it:* say so plainly in `§10.2` and `§17.9`, and require at least one externally-recomputable proof (`git-ancestor`, `mcp-state`) on every verdict-bearing line rather than allowing `journal` as a sole proof kind.

**M8. The four new `_shared` modules create a reference combination FR-NODE-090 has not seen.** They will be referenced by both a **mirrored** skill (`kiwi-orchestrator`) and a **mirror-excluded** one (`kiwi-wave-master`, per `.agents/skills/.speckiwi-mirror-exclusions.json`, which I read). `§9.4` cites FR-NODE-090 as closed but does not state that the prune test covers the both-referenced case. *Closes it:* extend `test/core/skills/shared-prune-exclusions.fr-node-090.test.ts` with that combination as part of this work.

**M9. Delegated-skill outputs at 3.b/3.c are trusted without audit, though C2 depends entirely on them.** The lane claim audit is thorough; `/kiwi-srs` (3.b) and `/kiwi-planner` (3.c) get only `child-srs-needs-user-or-failed`. Nothing asserts "every task in the sidecar carries a `req_id` from the 3.b allocation set" — which is the actual invariant C2 needs. Handoff resolvability catches unresolvable ids but not a task with empty `req_ids`. *Closes it:* a post-3.c gate comparing sidecar `req_ids` against the 3.b allocation set, with an `unallocated-req-id` refusal.

## CRITICAL

### C1 — `integrate(lane)`'s restore step cannot execute in this repository; it fails atomically and then commits lane-side journal and spec content

**Location:** §5.9, `05.orchestrator-design.md:912-919`.

The design states the mechanism "exactly":
```
git merge --no-commit --no-ff <lane_branch>
git checkout HEAD -- <every orchestrator-only path glob>
git commit -m "orch({run_id}): integrate wave-{n} lane-{k}"
```

`git checkout <tree-ish> -- <pathspecs>` is **all-or-nothing**: one pathspec that matches nothing in the tree aborts the command and restores *nothing*. At least two CP-07 globs can never match `HEAD` here:

- `kiwi/waves.jsonl` — untracked. `git ls-files kiwi/` returns only `kiwi/pipeline.jsonl`; `git check-ignore kiwi/waves.jsonl` exits 1 (not ignored either).
- `.kiwi/**` — ignored at `.gitignore:20`, therefore never in any tree.

I reproduced the full sequence in a scratch repo mirroring this layout:

```
### 2) the design's restore: ONE checkout with every orchestrator-only glob
error: pathspec 'kiwi/waves.jsonl' did not match any file(s) known to git
error: pathspec '.kiwi/**' did not match any file(s) known to git
checkout rc=1
-- kiwi/pipeline.jsonl content:      p1 / LANE-EVENT      <-- lane line NOT dropped
-- files in the integration commit:  docs/analysis/kiwi-review-fix-loop-r1/r.md, kiwi/pipeline.jsonl, ...
```

**Failure scenario.** Wave 2, lane 3. `/kiwi-pm` inside the lane emits its pipeline event; the merge stages it. The restore aborts on `.kiwi/**` before touching anything. `git commit` runs (the design specifies no error handling), so the lane's `kiwi/pipeline.jsonl` line lands on the integration branch. §5.9 then **replays** the same event through `workflow_pipeline_emit` at host root → duplicate pipeline events, and `kiwi-pipeline`'s `next_hint` routing reads a doubled history. The same abort leaves CP-02 (`docs/spec/**`, `orchestrator-only`) unrestored, so a lane that touched a scope SRS merges its edit — precisely charter C1's silent class, for which `validate`/`sync-index` (§5.9) is the *only* detector and which the design claims this step prevents.

Second, independent defect in the same three lines: even for globs that *do* match, `git checkout HEAD -- <glob>` cannot remove a file the merge newly **added** under that glob. Confirmed in the repro — `docs/analysis/kiwi-review-fix-loop-r1/r.md` survived into the integration commit. §7.3 routes lane remediation to `/kiwi-review-fix-loop` *inside the lane workspace*, which is exactly what creates `docs/analysis/kiwi-{skill}-{run_id}/` (§3.2). So "no shared-journal append that survives integration" (§5.4) is false for every new path.

### C2 — Nothing makes a lane commit, and the two skills that execute lanes decline to commit by contract
