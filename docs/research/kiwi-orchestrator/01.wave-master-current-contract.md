## 2. What wave-master actually does, stage by stage

The declared phase list (`:97-107`):

```
Preflight : Run-root preflight gate (§2.1)
Phase 0   : Input document resolution + waves.jsonl path resolution (resume detection)
Phase 1   : Wave decomposition (§3) + design baseline materialisation (§3.1) + coverage gate (§3.2)
Phase 2   : Per-wave target registration (§4) — /kiwi-srs authors wave-{n}
Phase 3   : Per-wave kiwi-pipeline (§5) — in registration order
Phase 3.5 : End-of-wave cross-verification (§5.5) — 2-verifier loop; must pass to mark complete
Phase 4   : waves.jsonl update (§6) — only successful waves marked complete
Phase 4.5 : All-wave final verification (§5.6) — against the whole design baseline
Phase 5   : Self pipeline event emit (§9)
```

Critically, **Phase 2 through Phase 3.5 repeat per wave** — targets are *not* registered up front (`:109`):

> "Phase 2~Phase 3.5 는 **wave 마다 반복**된다 — 모든 wave 의 target 을 앞에서 **일괄 등록하지 않는다**."

### 2.1 Preflight — run-root gate (FR-FLOW-042)

Before decomposition (`:115-150`):

1. Call `mcp_workspace_info`, read `workspaceRoot` (`:119`).
2. Read `git rev-parse --show-toplevel` (`:120`).
3. Normalise both before comparing: separators to `/`, drop trailing separator, case-insensitive including drive letter on Windows, resolve symlinks where possible (`:121-127`).

The ordering rule is explicit and load-bearing (`:129`): the check runs **before** wave decomposition, target registration, SRS mutation, child pipeline spawn, **and before `waves.jsonl` path resolution / resume reads** — to prevent pinning the journal root at a mismatched root.

On mismatch or lookup failure: immediate critical halt, not bypassable by `--auto`; failure to obtain `workspaceRoot` is treated identically to a mismatch; the `speckiwi` CLI is explicitly **not** a fallback because it resolves root from the caller's cwd, making the check vacuous (`:131`). At halt time there must be zero SRS mutations and zero spawned children (`:133`).

Halt output must carry four items (`:135-140`): two recovery paths (single-root `git switch`; a new agent session rooted at the intended worktree) and two warnings (a diverged-worktree session must not allocate new Requirement IDs; such a session cannot edit the host repo's `docs/spec/`).

Also in preflight:

- **`--wt` is refused** (`:144`) — see §4.
- **work-mode is read** via `get_work_mode` (MCP first, CLI `speckiwi mode` fallback), and the wave cycle is declared **body-scope**, so `tdd` mode's step-scoped routing to `kiwi-tdd` does **not** apply (`:146`).
- **`--skip-regression` / `--reviewer-off` are refused** (`:148`).
- **Regression baseline captured once and pinned for the whole run** (`:150`): the full suite runs once, failures become `baseline_failing_tests`, pinned run-wide — "wave 마다 다시 재면 앞 wave 가 만든 실패가 다음 wave 의 기준선으로 승격된다". Shares one SSOT with `kiwi-coder`'s `state.regression_baseline`. If capture itself fails, the field is left absent and that is reported.

### 2.2 Phase 1 — decomposition (§3)

Two-branch split heuristic (`:158-161`):

1. **Headers-first** — if the document has explicit wave structure (`## Phase 1`, `## 1단계`, top-level section titles), those boundaries become wave boundaries verbatim.
2. **Otherwise** — a **subagent** analyses the document's overall flow and splits into **3–8 coherent sub-goals**, one per wave.

The wave-split subagent additionally receives a structural summary of existing modules and their dependency direction (`:165`), because "기존 구조를 모르는 분해는 한 모듈을 여러 wave 가 동시에 건드리도록 잘라 교차 wave 회귀를 만든다". Each wave records `existing_modules`.

**§3.1 design baseline materialisation** (`:167-193`) — this is the heaviest artifact machinery in the skill:

- Per wave: `source_file` · `heading_path` · `line_start` · `line_end` (`:169`).
- Unassigned top-level sections go to `out_of_scope` as `{ heading, reason, exclusion_class }`, where `exclusion_class` is a **closed** five-value list — `already-implemented` / `superseded` / `external-ownership` / `user-excluded` / `non-normative` (`:171`).
- Persisted to `docs/analysis/kiwi-wave-master-{run_id}/design-baseline.json`, path carried on the wave's **first `in_progress`** event in `design_baseline` (`:173`).
- `design_items` fixed **in full** at the same moment: `{ id, heading_path, line_start, line_end, statement }` (`:175`). Granularity is pinned: **one normative sentence under the lowest heading = one item**; examples and rationale sentences are **not** items — "단위를 굵게 잡으면 `unmapped=0` 이 공짜가 된다" (`:177`).
- `integration_items` — design items belonging to no single wave's scope — fixed at the same moment, same shape; they are the denominator of the final pass (`:179`).
- Per-wave design **prose excerpt** materialised to `docs/analysis/kiwi-wave-master-{run_id}/design-baseline/wave-{n}.md`, path in `excerpt_path` (`:181`).
- **User constraints are collected, not just checked** (`:183-187`): extracted from the user prompt, conversation log, and `--constraint` args; one declared constraint sentence = one item with `{ id, statement, source }`. Written **even when empty** (empty array artifact), and `constraints_path` **always** recorded — "빈 배열은 반증 가능한 주장이고, 필드 부재는 침묵이다".
- **Late constraints** declared mid-run are written as a *new* artifact plus a new `in_progress` line, never edited in place; resolution always reads the **latest** `constraints_path` (`:189`).
- A **carry-forward-created wave** has no source range, so its design-layer denominator is the carried finding list, converted one-finding-to-one-`design_items`-entry (`heading_path` = `carried-forward`, line coords `0`) and materialised as markdown at `excerpt_path` (`:191`).
- The whole artifact set must be resolvable **from `waves.jsonl` alone**, never from conversation state (`:193`).

**§3.2 coverage gate** (`:195-205`): the mapping is compared against the input's section set; **every** unassigned item is reported, not the top N. The comparison unit is the **full `design_items` set, not one layer of top-level headings** (`:199`) — "하위 절에만 있는 미배정 설계는 최상위 대조를 그대로 통과한다". An unassigned item with no recorded out-of-scope reason blocks entry to §4 (`:201`). Out-of-scope is "기록이지 판단이 아니다" (`:203`), and any non-empty `out_of_scope` triggers user confirmation **even under `--auto`** (`:205`).

### 2.3 Phase 2 — per-wave target registration (§4, `:209-227`)

One dedicated SRS target per wave: wave-1 → target `wave-1`, etc. (`:211`). Scope is explicitly bounded to that wave so downstream feasibility / planning / review never look beyond it (`:213`).

The `/kiwi-srs` call carries:

- `--research-doc` = the wave's `excerpt_path`, plus the original `source_file` (`:219`). Passing the wave body **inline** is explicitly insufficient, and passing the coordinate JSON instead is also insufficient — the research verify-and-improve loop needs prose at a path. The path handed over must be the **same** path recorded in `waves.jsonl`.
- `--constraints-doc` = `constraints_path` (`:221`).
- The wave's `existing_modules` as **authoring** input, not merely verifier input (`:223`).
- Every residual whose `carried_into` is this wave, collected in full (`:217`).

Registering an unregistered wave target with a creation option is the **normal path**, not an exception (`:225`).

Idempotency: if any event for that wave carries `srs_authored = true`, §4 is skipped and the run goes straight to §5. The marker rides a `phase="srs-authoring"` event, and **only `srs-authoring` lines without the marker** read as authoring-in-progress — because wave-verify lines legitimately lack the marker, so judging by "latest line" alone would resurrect authoring after every verification record (`:227`).

### 2.4 Phase 3 — per-wave pipeline (§5, `:231-245`)

Waves run **in registration order**; the next wave's pipeline starts only after the previous one returns `TASK_DONE` (`:233`) — and, more strictly, only after the previous wave has passed §5.5 and been recorded `complete` (`:235`).

The entry is **skip-authoring**: `/kiwi-pipeline --cycle --from=feasibility --run` (`:237`). This entry point is provided by `kiwi-pipeline` (FR-FLOW-026 / T-PH003-04) and consumed by wave-master (FR-FLOW-029); both provider and consumer state it (`:239`).

Target is passed **explicitly** as `--target wave-{n}` (`:243`) — relying on `/kiwi-srs`'s `set_active_target` side effect breaks on the §6 resume path that skips §4. Residuals carried into this wave are included in the re-entry scope (`:245`).

### 2.5 Phase 3.5 — end-of-wave cross-verification (§5.5, `:249-425`)

Runs after `TASK_DONE`, **before** the `complete` record (`:251`). "complete first, audit later" is explicitly ruled out because `complete` is append-only, the transition graph has no `complete → failed` edge, and §0.6 resume skips completed waves forever (`:253`). Per-hunk code review is **out of scope** — owned by `kiwi-review-fix-loop` (`:255`).

**Evidence bundle (`:257-283`).** Exactly two verifier subagents, both given the **identical** bundle; splitting evidence between them is forbidden (`:259`). Bundle rows (`:261-275`): the wave's `pipeline.jsonl` window; its `waves.jsonl` rows; `.kiwi/sessions/{plan_run_id}/worklog.jsonl`; `docs/plans/{plan_run_id}.plan.md` + `.sidecar.json`; `{review_fix_loop_analysis_dir}/report.md`; speckiwi `list_requirements` / `summarize_target` for the wave target; the wave's git diff; the design baseline range; the declared constraints artifact; a full regression run at wave head with `baseline_failing_tests`; the wave's `diff_window` base/head SHAs; `existing_modules`; and **all** `pipeline_run_ids`.

The design-baseline and constraints rows are mandatory and cannot be omitted (`:277`). The window is bounded by **all** `pipeline_run_ids` plus the `in_progress` timestamp, because `pipeline.jsonl` is shared by all waves (`:279`). Two key-space distinctions are spelled out: `.kiwi/sessions/` and `docs/plans/` are keyed by **plan run-id** (different from `pipeline_run_id`, resolved from `artifacts.plan_file` / `artifacts.analysis_dir` in the window's planner/pm events) (`:281`), while `docs/analysis/` is keyed **per skill** and resolved from that skill's own event `artifacts.analysis_dir`; a `*` glob is forbidden, and an entirely absent `kiwi-review-fix-loop` event must be **raised as a verifier-2 finding**, not silently dropped from the bundle (`:283`).

**Two verifiers, separated by stance (`:285-325`).**

| | Verifier 1 | Verifier 2 |
| --- | --- | --- |
| stance | wave SRS **intent realisation** + **process conformance** | **artifact quality** + **cross-wave regression** risk |
| roll-up | `ALL_MATCH` / `GAPS` | `substantive_clean` |
| output | per REQ/AC row: `intent_match` + evidence pointer | per finding: `severity` + `severity_class` |

Verifier 1 carries **four** externally fixed denominators:

1. **REQ/AC** — from `list_requirements` for that target, not chosen by the verifier; every REQ and AC enumerated, `checked == expected` compared; samples/excerpts/top-N are not denominators. Because `list_requirements` defaults to a compact projection without ACs, an AC-bearing projection must be requested explicitly or `get_requirement` called per REQ (`:293`). Realised rows need a **resolvable** pointer (existing `file:line` or existing test id). Count mismatch or unresolvable pointer ⇒ round **invalid**: cap consumed, clean streak reset to 0.
2. **Design layer** — every design item in the wave's baseline enumerated, each mapped to a REQ id or marked `unmapped` (`:295`). **One** unmapped item forbids `ALL_MATCH` even if REQ/AC is complete (`:297`). `design_layer.expected` is the `design_items` length, not verifier-computed (`:299`).
3. **Constraint layer** — `expected` / `checked` / `violations`; one violation forbids `ALL_MATCH` (`:301`); `expected` is the item count of the latest `constraints_path` artifact (`:303`).
4. (Verifier 2's) **Preservation layer** — denominator derived **mechanically from the diff**, in four classes: deleted/moved existing files, deleted/changed existing public symbols, deleted/modified existing test files, and **assertion weakening** in existing tests (judged by `kiwi-coder §0.20.3`'s closed list) (`:305`). Each row's verdict is a two-value enum `intended-improvement` / `unapproved-damage`; free prose is not a verdict (`:307`). `intended-improvement` requires a REQ or plan Task backing it, recorded as REQ-ID/Task-ID in `evidence` (`:309`); this is the **same rule as the execution layer** `kiwi-coder §0.20.4` (`:311`); unbacked rows are `unapproved-damage` (`:313`); and **weakening is always `unapproved-damage`, even with a REQ/Task backing it** (`:315`).

Row count ≠ frozen denominator ⇒ round invalid for **both** verifiers (`:319`). Denominators are frozen at round entry and recorded in `frozen_denominator` (`:321`); they do **not** grow mid-round — items added by incremental authoring are re-frozen at the *next* round, and that re-freeze round is **not** invalid (`:323`).

**Round structure (`:327-339`).** One round is **all three** steps; step 1 alone is not a round, and `--loops 1` means one full three-step round (`:329`):

1. **Isolated** — the two verifiers run independently; neither the main session's conclusions nor the other verifier's output is passed (`:331`).
2. **Cross-refutation** — each receives the other's findings as **claims plus evidence pointers only** (rationale / verdict / confidence stripped). Only **add** and **confirm** are permitted — **`add-only`**; dismissal is impossible. A round that skips this step is **invalid** (`:332`).
3. **Merge** — **mechanical union**; neither verifiers nor main session have discretion (`:333`).

The rationale is stated (`:335`): granting dismissal power creates a collusion payoff, since both verifiers' local interest is "finish the wave", making mutual dismissal the shortest path. Verifiers are **re-spawned from round 2 onward** (`:337`) — reusing context would make a second clean round mean "the first verifier agreed with itself".

A finding closes by exactly three paths (`:339`), where "the raising side" means **stance, not instance**: (i) fix, then the raising *stance*'s new verifier re-verifies clean; (ii) the raising stance withdraws with counter-evidence; (iii) unanimous reclassification by both verifiers — but a round containing (iii) does **not** count toward the clean streak, and, **regardless of mode**, at least one further verification round must run before PASS, with the reclassification recorded in `verification.residual`.

**Termination (`:341-360`).**

| Mode | PASS |
| --- | --- |
| Normal | merged `CRITICAL=0` + `HIGH=0` + verifier-1 `ALL_MATCH`, **and no fix applied in that round**, and zero new regression failures (`failing_tests ⊆ baseline_failing_tests`; `exit_code`=0 if no baseline), and `unapproved-damage` = 0 |
| `--max` | the above + `MEDIUM=0` across **2 consecutive** rounds |

The "no fix applied" clause is what makes a low cap safe (`:348`). Round caps come from `loop-option.md v1.0`: default **5**, `--max` **8**, `--mini` **3**; `--loops` beats `--mini` with a non-fatal WARN (`:352`). If on resume `cap - rounds` is below the mode's streak requirement, PASS is arithmetically impossible — record `fail-cap` and get a user decision without running more rounds (`:354`). **Cap exhaustion is not a pass** (`:356`). Normal mode alone may terminate early once its gate is met, recording leftover MEDIUM/LOW as `pass` + `residual` **without** a user decision; anything else left unresolved before the cap is `fail-residual` and halts (`:358`). Streak requirements: Normal **1**, `--max` **2** (`:360`).

**Remediation routing (`:362-385`).** Wave-master introduces **no fixer of its own** (`:364`) — routing table (`:367-373`):

| Finding kind | Route |
| --- | --- |
| quality / regression / implementation defect | `kiwi-review-fix-loop` with an **explicit scope** (`--base`/`--head` or `--commits`) — a committed wave has an empty working-tree diff and would report a false clean |
| verifier-1 gap for which **no plan task ever existed** | **re-enter** that wave's `/kiwi-pipeline` — a code reviewer cannot invent plan items |
| SRS-level finding no code change can close | `residual` + user decision |
| requires touching a **previous** wave's completed target | `wave-verify-cross-wave-fix-required` critical HALT |
| present in the **design baseline** but absent from the wave SRS | incremental `/kiwi-srs` re-entry on that target, then pipeline re-entry from planning |
| REQ left `draft` by feasibility/planning | re-run `/kiwi-srs-feasibility` with `--req-filter <REQ-ID[,…]>`, then re-enter planning; on failure `reason_class="draft-stability-skip"` residual |

Prohibitions (`:375`): a fixer must not edit **AC text**, must not weaken or delete existing tests (`kiwi-coder §0.20` closed list), and must not author `severity_class` (only the raising verifier writes it). And `kiwi-review-fix-loop`'s **own PASS does not satisfy the wave gate** (`:377`) — wave-level findings close only through the two verifiers' re-verification.

Re-entry always carries scope: `--req-filter` (unaddressed REQs) and `--plan-run-id` (whether the existing plan run is reused) (`:379`). Design-layer gap remediation **is** allowed to proceed automatically under `--auto`, because its basis is a recorded design baseline rather than inference (`:383`). Sub-skill-skipped REQs surface in `verification.residual` with a `reason_class` (`:385`).

**Recording (`:387-413`).** A `status=in_progress` / `phase="wave-verify"` line is appended **every round** — not once at loop end — and always before `complete` (`:389`); recording once at the end would lose `rounds` on a crash, letting an unstable wave never reach `fail-cap`. The `verification` payload carries `design_layer`, `preservation_layer`, `constraint_layer`, `frozen_denominator`, and `regression` (`:391`). The last round's line is the "preceding pass record" §3 of waves-event requires; without it the following `complete` is invalid (`:393`).

Verdict semantics (`:399-404`): `in-progress` for non-terminal rounds (writing `pass` early collapses the journal gate; writing `fail-residual` makes resume read a running loop as failed); `pass` ⇒ append `complete` with the same `verification` duplicated so one line reconstructs the judgement; `fail-cap` and `fail-residual` ⇒ no `complete`, wave stays incomplete and §0.6 resume returns to it (`:406`).

Producer duties (`:409-413`): `base_sha` captured at **wave entry**; `head_sha` at **wave-verify round entry**; both ride `diff_window`; each pipeline spawn **appends** its run_id to `pipeline_run_ids`.

**Cross-wave carry-forward (§5.5.7, `:415-425`).** Cross-wave status is decided **mechanically by file set** — intersection with a previous wave's recorded REQ code-trace anchors or its diff file set (`:417`). Carry-forward is the **first** response, not HALT (`:425`): code-level findings carry into a remaining wave, or into a newly appended wave under the §0.5 exception if none remains (`:421`); even requirement-level findings try carry-forward first and HALT only when **both** paths are impossible (`:419`). Carry-forward is recorded as `cross_wave = true` + `carried_into` in `verification.residual`, and never edits or reverses a previous `complete` (`:423`).

### 2.6 Phase 4.5 — all-wave final verification (§5.6, FR-FLOW-049, `:429-461`)

Runs after the **last** wave's `complete`, before reporting orchestration complete. It is explicitly **not a re-check of the last wave** (`:431`) — per-wave verification only sees each wave's own scope, so anything in no wave's scope is never verified otherwise.

Denominator: the **union of all waves' `design_items` plus `integration_items`**, externally fixed, compared against the union of all wave requirements (`:433`). `out_of_scope` is carried in **full** as a separate layer, with both verifiers confirming per item that non-implementation was intended (`:435`) — exclusion is otherwise the only path never verified in the whole run.

The loop **reuses §5.5 wholesale** (`:437`): exactly two verifiers by stance, `add-only` cross-refutation, no-fix-in-that-round clean requirement, §5.5.4 caps and `--mini`/`--loops`, §5.5.5 routing, §5.5.7 carry-forward. The record attaches to the run, not a wave: `wave="all"` · `order=0` · `phase="final-verify"`, and wave-level status computation **excludes** it (`:439`). "wave head regression" reads as **run head** regression (`:441`); the preservation denominator reads over the **run window** `run_diff_window`, not the last wave's window (`:443-445`). `unapproved-damage = 0` also applies (`:447`).

Run-scope findings append a wave-N+1 rather than halting, then §5.6 **re-runs** after that wave completes (`:449`), capped at **3** wave appends per run (`:451`, gate `wave-append-cap-exhausted`). Round counters **accumulate across re-runs** (`:453`). A non-passing final verify writes `status=failed` (`:457`), and a run whose final pass has not passed is not complete — resume enters the final verification, not the first incomplete wave (`:459-461`).

### 2.7 Phase 4 / journal (§6, `:465-485`)

`complete` only after a successful pipeline run (`:467`); resume from the **first incomplete wave** (`:469`). `pipeline_run_id` is mandatory on `complete` and `phase=wave-verify` lines but omitted on the first `in_progress` (no cycle yet) — "생략되는 것은 필드이지 이벤트가 아니다" (`:471`).

**Wave-internal resume granularity is three stages** — target registration / pipeline / wave verification — and completed stages are not re-run (`:473`). Pipeline-stage resume must pass `--plan-run-id` **and** `--req-filter`, with `kiwi-pm` entered via `--resume` (`:475`); `plan_run_id` is journalled for exactly this (`:477`). A resume that skips §4 must pin the active target with `set_active_target` first (`:479`).

Run scoping (`:481-485`): the resume scan reads **only events matching the current `run_id`**, because `waves.jsonl` is one append-only file per repository and `wave-{n}` is not unique across runs. The resume target is the most recent run not ended in `complete`, overridden by `--run-id`. **Another run's `complete` is never read as this run's completion** — otherwise a new epic's `wave-1` reads the previous epic's completion and reports full completion with zero implementation.

### 2.8 Options and propagation (§7, `:489-528`)

`--auto` runs every wave to the end but per-wave safety gates stay in force (`:493-495`), including §5.5's residual CRITICAL/HIGH, verifier-1 `GAPS`, and `fail-cap`, and the same three conditions in §5.6 (`:497`). **`--auto` alone does not clear** the child `kiwi-coder` gates `--auto-integration` and `--auto-cost-warning` — each needs its own explicit option, or the run stops at the first coding wave (`:499`).

`--max` propagates to every wave's pipeline and its sub-skills (`kiwi-srs`, `kiwi-srs-feasibility`, `kiwi-planner`, `kiwi-pm`, `kiwi-review-fix-loop`) (`:505`), **and** to the `kiwi-srs` that §4 invokes directly — which the "sub-skills the cycle spawns" phrasing would otherwise miss, since the cycle enters at `--from=feasibility` (`:507`).

`--mini` / `--loops N` propagate to per-wave `kiwi-srs` and `kiwi-pipeline` (`:513`) **and are wired into §5.5's own round cap** (`:515`) — otherwise `--mini` would shrink children only.

Pass-through table (`:523-528`): `--auto-cost-warning` and `--auto-integration` (→ pipeline → pm → coder), `--force` (→ pipeline → pm, **explicit input only**), `--regression-baseline` (the §2.1-pinned value → coder / review-fix-loop). A child blocked by `pm.lock` does **not** get `--force` auto-granted; it halts via `child-pipeline-needs-user-or-failed` (`:521`).

### 2.9 Epic entry mode (§8, FR-FLOW-030, `:532-561`)

An epic issue number replaces the document as wave source; everything after extraction is identical to §3–§7 (`:534`). Waves come from three combined sources — epic body structure, task list, and linked sub-issues — in listed order (`:540`). **Only** the up-front wave-split research is skipped; each wave's pipeline still runs its own research (`:554-556`). Structure guard (`:560-561`): skip applies only with **extractable structure** (a task-list group or **≥2** linked sub-issues); free-form prose or <2 sub-issues **falls back** to the §3 wave-split subagent, with no new component.

### 2.10 Emit (§9, `:565-573`)

One `pipeline.jsonl` line at end of run, idempotent by run_id (`:567`). A preflight-halted run pins **no** wave-journal root and writes **nothing** to `waves.jsonl`, but still emits exactly one event with `status=FAILED`, `next_hint=null` (`:569`), resolving the path through the pipeline-event location chain evaluated **once against the run's own cwd**, never from the MCP-reported root (`:571`). A **resumed** run emits under `{run_id}#r{n}` (`:573`) — bare `run_id` would idempotently skip, so a resumed-to-completion run would never record its final `TASK_DONE`.

### 2.11 How a wave is decided done — the whole chain

1. Child `/kiwi-pipeline` returns `TASK_DONE` (`:233`).
2. §5.5 loop converges to `verdict = pass` — no-fix round, `CRITICAL=0`, `HIGH=0`, verifier-1 `ALL_MATCH` across four denominators, `unapproved-damage = 0`, no new regression failures (`:345`).
3. A `phase="wave-verify"` line carrying that `verification` is appended (`:389`).
4. Only then is `complete` appended, duplicating the same `verification` (`:402`).
5. `waves-event.md §3` independently invalidates any `complete` lacking a preceding passing wave-verify record in the same run, and resume treats such a wave as incomplete (`skills/claude/_shared/kiwi/waves-event.md:135`).
6. The **run** is done only when all waves are `complete` **and** the latest `final-verify` event's verdict is `pass` (`waves-event.md:149`).

## 3. How work is divided into waves

- **Unit**: a wave is an ordered, sequential bundle where each wave founds the next (`:156`): "각 wave 는 순차(sequential)적으로 실행되는, 서로 정렬된(ordered) 작업 묶음이며 앞 wave 가 뒤 wave 의 토대가 된다."
- **Source of boundaries**: document headers when present, else a subagent's 3–8 coherent sub-goals (`:160-161`); or epic structure in §8 mode.
- **Immutability**: `waves.jsonl`-confirmed order and scope are never re-split mid-run; re-decomposition means starting over (`:22`). The **single exception** is *appending* a wave to close a discovered coverage gap — explicitly declared not to be re-decomposition, and **already-registered wave order never changes** (`:22`).
- **Granularity of the SRS unit**: one wave = one SRS target `wave-{n}` (`:211`), bounded so downstream stages never look beyond it (`:213`).

## 4. Parallelism, worktrees, task-level independence — what it does about them

**Nothing, deliberately, and in two places it actively forbids them.** A grep for `병렬|parallel|worktree|워크트리|--wt|동시|fan-out` over the whole 573-line skill returns only: the description line, the "순차" (sequential) statements, the `--wt` refusal, the preflight recovery paths, and one "동시에 건드리도록" phrase about avoiding cross-wave regression.

The two explicit refusals:

1. **`--wt` delegation is refused** (`:144`):
   > "본 스킬은 워크트리 격리를 `kiwi-pipeline --wt` 로 위임하지 않는다. `--wt` 요청이 들어오면 명시적으로 거부한다 — per-wave worktree 생성은 앞 wave 가 뒤 wave 의 토대가 되는 wave 누적을 깨뜨리기 때문이다"

   Declared as gate `wt-delegation-refused` (`:39`).

2. **The whole flow is serial by contract** (`:235`):
   > "앞 wave 가 §5.5 **웨이브 종료 상호검증**까지 통과해 `complete` 로 기록된 뒤에야 다음 wave 의 pipeline 을 시작한다. wave 는 뒤 wave 의 토대이므로, 검증 중인 wave 위에 다음 wave 를 쌓으면 §0.G 의 halt 게이트가 무의미해진다."

Task-level independence is **not modelled at all**. The only nod toward it is defensive: the wave-split subagent gets the existing module/dependency structure so that one module is not cut across several waves (`:165`), and `existing_modules` feeds verifier 2's cross-wave regression judgement (`:317`). That is dependency-*avoidance*, not dependency-*exploitation*.

The only parallelism anywhere in the skill is the **two verifier subagents in §5.5**, and even that is downgraded to two sequential axes on the single-worker `etc` profile (FR-FLOW-044 requirement text, `docs/spec/60.workflow-release.srs.md:3220`+).

## 5. Where it stops — does it author requirements or design?

**It does not author requirements and does not implement code.** Stated in the second paragraph of the body (`:10`):

> "이 스킬은 *직접 요구사항을 저작하거나 코드를 구현하지 않는다* — wave 경계를 정하고, 각 wave 의 target 을 `/kiwi-srs` 로 등록하고, wave 별 `/kiwi-pipeline` 을 순서대로 spawn 하는 상위 오케스트레이터다."

Repeated when the remediation router is defined (`:364`):

> "본 스킬은 상위 오케스트레이터이므로 **전용 fixer 를 신설하지** 않는다 — 직접 요구사항을 저작하거나 코드를 구현하지 않는다는 본 문서 서두의 성격을 유지한다."

**But it is not purely a plan consumer either.** Precisely:

| Activity | Does wave-master do it? | Citation |
| --- | --- | --- |
| Produce the design / research / SDS document | **No** — it is a *required input*; if absent, halt at `decomposition-input-missing`, "입력 문서는 위원회가 추론으로 만들어내는 대상이 아니다" | `:69`, `:47` |
| Decompose that document into waves | **Yes** — this is its core act, via headers or a split subagent | `:156-163` |
| Materialise a design baseline (coordinates, `design_items`, `integration_items`, excerpts, constraints) | **Yes** — a substantial derived-artifact authoring step | `:167-193` |
| Author the SRS requirements for a wave | **No** — delegates to `/kiwi-srs`, feeding it the excerpt and constraints | `:215`, `:219-221` |
| Produce a task plan | **No** — the child pipeline's `kiwi-planner` does | `:237` |
| Write code | **No** — the child pipeline's `kiwi-pm`/`kiwi-coder` do | `:237` |
| Fix findings its own verification raises | **No** — routes to `kiwi-review-fix-loop`, pipeline re-entry, `kiwi-srs` incremental, or `kiwi-srs-feasibility` | `:364-373` |
| Verify the wave and the run | **Yes** — §5.5 and §5.6 are its own two-verifier loops | `:249`, `:429` |

So the boundary is: **it consumes a design document, derives an ordered, coordinate-pinned decomposition and its verification denominators, and owns verification — but delegates all authoring, planning, coding, and fixing.**

### 6.2 Reusable as patterns — mechanisms already designed, debugged, and text-pinned

These are the expensive parts. Each was arrived at through three documented evaluation rounds and each has an explicit stated failure mode it exists to prevent — copying the *reasoning* is far cheaper than rediscovering it.

1. **`critical_gates[]` declaration table** (`:30-57`) — 16 rows of `gate_id | reason | 발생 위치`, with the stated rule that partial declaration is worse than none because undeclared halts fall to committee judgement (`:34`). FR-FLOW-061 requires **identifier parity across variants**, and FR-FLOW-066 requires **a parent to inherit a child's critical gates by a general rule rather than per-gate transcription** — a new sibling that spawns the same children inherits that obligation.
2. **Two-verifier stance separation + `add-only` cross-refutation + mechanical union** (`:285-339`) — including the collusion argument (`:335`), verifier re-spawn per round (`:337`), and the three closing paths with the streak cost on reclassification (`:339`).
3. **Externally fixed, frozen denominators** (`:293-325`) — the four layers, the "verifier does not compute its own `expected`" rule, `frozen_denominator`, invalid-round-on-count-mismatch, and mid-round freeze immutability. This is the anti-"skim and PASS" machinery.
4. **"No fix applied in that round" as the pass precondition** (`:348`) — the single clause that makes a cheap cap safe.
5. **Cap exhaustion ≠ pass**, plus the `pass+residual` vs `fail-residual` distinction (`:356-358`) and unreachable-PASS arithmetic detection (`:354`).
6. **Preservation layer with a two-value verdict enum and REQ/Task-backed evidence** (`:305-315`), symmetric with `kiwi-coder §0.20.3/§0.20.4` — FR-FLOW-063 exists precisely to keep those two layers on the same rule.
7. **Delegation-only remediation routing** (`:362-379`) — the finding-kind → skill table, the explicit-scope requirement on every delegation, and "a sub-loop's own PASS does not close a wave-level finding" (`:377`).
8. **Design-baseline artifact convention** (`:167-193`) — `docs/analysis/kiwi-{skill}-{run_id}/` directory layout, coordinate JSON + prose excerpt pair, closed `exclusion_class` vocabulary, empty-array-over-absent-field rule, append-new-artifact-over-in-place-edit for late inputs.
9. **Journal-only resolvability** (`:193`, `:271`, `:273`, `:477`) — every value a later stage consumes has a declared producer and is reachable from the journal alone, because a resumed session has no conversation. FR-FLOW-062 is entirely about this.
10. **Run-root preflight with path normalisation and ordering-before-journal-read** (`:115-150`) — directly reusable by any skill that spans MCP + git.
11. **Run-scoped journal computation** (`:481-485`) + the `wave="all"` exclusion rule (`waves-event.md:139,147`).
12. **Pinned run-wide regression baseline** (`:150`) shared with `kiwi-coder`'s `state.regression_baseline`.
13. **Idempotent stage markers** (`:227` `srs_authored`, `:473` three-stage resume granularity).
14. **Skip-authoring pipeline entry** `--cycle --from=feasibility --run` with explicit `--target` (`:237`, `:243`) — a provider/consumer pair already implemented on the `kiwi-pipeline` side (FR-FLOW-026 / T-PH003-04).
15. **Pass-through option chain** (`:519-528`) — the rule that a middle skill dropping one option stalls the unattended run at the last hop.

### 6.3 Testing convention — reusable harness

All six test files use the same technique, stated in their headers: a SKILL.md is natural-language agent instruction, so behaviour cannot be unit-tested; instead they make **raw-text presence + proximity assertions over every packaged variant**. Reusable helpers, present in each file:

- `readWaveSkill(variant)` returning `""` on ENOENT so a missing file fails as a clean AssertionError (red driver) rather than throwing (`test/skills/kiwi-wave-master-content.test.ts:27-31`).
- `skillBody(text)` stripping YAML frontmatter so the `description` cannot false-green a check (`test/skills/kiwi-wave-verify-content.test.ts:33-35`).
- `windowsAround(text, re, radius)` for proximity assertions (`kiwi-wave-verify-content.test.ts:38`).
- **Section-scoped rather than body-wide assertions**, with the stated reason that neighbouring sections restate the same tokens and a body-wide check stays green when the sentence under test is deleted (`kiwi-wave-verify-content.test.ts:18-20`).
- Bilingual (English/Korean) regexes keyed on technical tokens, because claude/codex text is largely Korean and etc is mixed (`kiwi-wave-master-content.test.ts:17-20`).
- Hedge-vocabulary absence assertions on MUST sentences (per FR-FLOW-047 VE-1 notes, `docs/spec/60.workflow-release.srs.md:3441`).

### 6.4 What would have to be written new

- **Anything about parallel execution, worktree isolation, or task-level independence.** The existing contract has zero mechanism and two explicit refusals (§4 above). A design that wants parallelism cannot extend wave-master's rules; it must supply its own, and must reckon with the FR-FLOW-042 preflight gate and the worktree blocker in §7.1 below.
- **A different work-decomposition unit.** `wave-{n}` targets, the founds-the-next ordering assumption, and the immutability rule are pervasive — `:22`, `:156`, `:211`, `:235`, `:419`.
- **A `skill` enum entry in `pipeline-event.md §3` and a T1 `next_hint` row in §4.** Note `kiwi-wave-master` is present in the enum (`pipeline-event.md` §3) but **absent from the T1 table** — so even the existing skill has no declared routing hint.
- **A `loop-option.md §6` propagation row** for any new orchestrator.
- **A `_shared/kiwi/` module** if the new skill's own event stream is not `waves.jsonl` — and, per `.speckiwi-mirror-exclusions.json`, a decision about mirror inclusion, since the mirror-prune bug in §7.3 is triggered by exclusion.
- **New SRS requirements** — everything above is already claimed by FR-FLOW-029/030/042–066.

## 7. Known defects and open items

### 7.1 Worktree isolation is blocked — two independent hard blockers (do not re-investigate; another agent owns this)

Recorded in `docs/research/12.kiwi-wave-master-worktree-isolation-research.md` (Date 2026-07-27, Status "Research complete; SRS 작업 미착수"). Its §1 conclusion, verbatim:

> "**결론: 도구와 스킬 양쪽에 서로 독립적인 hard blocker 가 있다. 한쪽만 고쳐도 실행되지 않는다.**"

- **Tool layer**: SpecKiwi MCP resolves workspace root **only** from the server process cwd — an explicit designed prohibition under `REL-MCP-004` / `IR-CLI-045`. Claude Code starts the MCP server once per session and does **not** restart it when session cwd moves to a worktree (measured, §3 of that doc). A session started in the original directory writes SRS mutations to the original repository for its entire life. Not bypassable by prompting.
- **Skill layer**: `kiwi-coder §0.9` and `kiwi-planner §0.8` block edits to paths outside cwd as a critical gate. From the host session, every worktree file is outside cwd — so **even if the MCP problem were fixed**, per-Task implementation hard-stops.
- **Silent-misbehaviour factor**: the *deployed* `kiwi-wave-master v0.1` has "worktree·root 어휘가 **한 글자도 없고**, root 정합성 preflight 도 없다", so the tool constraint first appears as **writing to the wrong repository** rather than as an explicit failure.

Partial mitigations already shipped: **FR-FLOW-042** (preflight gate, v2.4.2, verified) and **FR-MCP-055** (`docs/spec/40.mcp-stdio-interface.srs.md:3845`, v2.4.2, verified) — the latter removes a recovery hint naming a non-existent `restart_mcp_server` tool and replaces it with the truthful statement that root comes solely from the MCP server process cwd. These make the failure loud; **they do not enable worktree operation.**

## 9. Said vs. tested — where the contract has no test

**Every test in this set is a text-contract test, not a behaviour test.** The test files state this explicitly (`test/skills/kiwi-wave-master-content.test.ts:15-17`):

> "A SKILL.md is natural-language agent instruction, not executable code, so the AC behavior cannot be run in a unit test. These raw-text presence + proximity assertions verify the authored orchestration text for every packaged variant."

Coverage map:

| Test file | `it` count | Covers |
| --- | --- | --- |
| `test/skills/kiwi-wave-master-content.test.ts` | 19 | FR-FLOW-029, FR-FLOW-030, FR-FLOW-042/043 |
| `test/skills/kiwi-wave-verify-content.test.ts` | 21 | FR-FLOW-044, 045, 046 (skill side) |
| `test/skills/kiwi-wave-continuity-content.test.ts` | 57 | FR-FLOW-047 … 055, plus a gate-table completeness check |
| `test/skills/kiwi-wave-continuity-r2-content.test.ts` | 73 | Round-2 findings R2-C1..C3, R2-H1..H10, R2-M1..M2 |
| `test/skills/kiwi-wave-continuity-r3-content.test.ts` | 77 | Round-3 findings R3-H1..H10, R3-M1..M5 |
| `test/skills/kiwi-event-contract-content.test.ts` | (6 describes) | `waves-event.md` and `pipeline-event.md` across all 4 copies |

**What this means precisely.** A green suite proves that the *sentence* mandating a rule is present in all three variants, in the right section, without hedge vocabulary. It does **not** prove that an agent executing the skill:

- actually spawns exactly two verifiers rather than one;
- actually freezes denominators, or that `checked == expected` is really compared;
- actually refuses to dismiss a finding in the cross-refutation step;
- actually appends a `wave-verify` line **every** round rather than once;
- actually captures `base_sha` at wave entry;
- actually resolves the analysis directory per skill rather than by glob;
- actually halts on any of the 16 `critical_gates[]` rows.

**Nothing in this repository executes the wave cycle.** There is no integration test, no fixture run, no simulated `waves.jsonl` consumer. The `waves.jsonl` schema itself is likewise only text-asserted (`kiwi-event-contract-content.test.ts`) — there is no parser or validator for it in `src/`. So the *entire* runtime behaviour of wave-master is untested in the executable sense; the tests are a regression net against **text deletion and cross-variant divergence**, which is a real and useful property (they caught variant drift), but it is not behavioural verification.

The one genuinely behavioural test that touches this area is `test/core/health/installed-skill-drift.ir-cli-080.test.ts`, which exercises `diagnoseHealth` against injected fixture homes — and it tests the *doctor*, not the skill.

This is also why FR-FLOW-047..066 sit at `implemented` rather than `verified` (§7.2): the evidence is text-contract tests plus three evaluation rounds, and the fourth clean round was never run.
