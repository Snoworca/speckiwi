## 0. Verdict

> **Harvest five named artifacts — H1–H4 into the orchestrator target and H5 as a standalone fix on
> `feat/2.3.0.1` (§3.1, §8). Do not adopt the branch as a foundation. Do not merge it, do not
> rebase it, and do not treat any of its requirements as live. Keep the branch on disk until the
> harvest lands, then archive it under a tag and delete the working branch.**

Three findings drive this, in order of weight.

**F1 — The branch is not merely stale; it is architecturally superseded.** It discards `FR-FLOW-029`
(`docs/spec/60.workflow-release.srs.md` on the branch — heading struck through, `[DISCARDED → see
FR-FLOW-036]`). On `feat/2.3.0.1`, `FR-FLOW-029` is `verified`
(`docs/spec/60.workflow-release.srs.md:2319`, Status at `:2325`) and **twenty-five requirements
authored after the branch was checkpointed now build on it** — `FR-FLOW-042` … `FR-FLOW-066`
(`docs/spec/60.workflow-release.srs.md:3076`–`4574`), of which two are `verified` and twenty-three
`implemented`. Two of them state the relationship explicitly in their Traceability tables:
`FR-FLOW-042` records `| Requirement | FR-FLOW-029 | extends | Adds a run-root preflight gate ahead
of the FR-FLOW-029 wave flow; none of its AC-1..AC-5 are replaced. |`
(`docs/spec/60.workflow-release.srs.md:3124`) and `FR-FLOW-043` records `extends` at `:3194`.
Adopting the branch would retract a verified requirement out from under twenty-five successors.

**F2 — Mainline answered the same question in a different layer, and shipped.** The branch solves
multi-root wave execution in the **runtime layer**: 15 new TypeScript modules under
`src/core/workflow/`. Mainline solved run-root integrity in the **skill layer**: `src/core/workflow/`
on `feat/2.3.0.1` contains *no* `wave*.ts` at all, while
`skills/claude/kiwi-wave-master/SKILL.md` grew from 169 lines at the fork point (`git show
21e0f5e:skills/claude/kiwi-wave-master/SKILL.md | wc -l`) to **573** today, against the branch's
**218**. Both rewrote the same file from the same base in incompatible directions. This is not a
merge conflict that careful resolution fixes; it is two answers to one question, and the mainline
answer is the one with 25 requirements and a shipped release behind it.

**F3 — The parts that look most reusable are the parts that transfer least.** The two modules the
surveys recommended most confidently — `wave-spec-client.ts` (the "C5 answer") and `event-schema.ts`
(the "journal validator") — both fail on inspection for this design's purposes. §3.2 and §3.3 give
the evidence. What survives the filter is small, pure, and genuinely worth taking.

Against that, the branch's engineering quality is high and its failure is not incompetence: 1,502
tests pass, `tsc` and `eslint --max-warnings=0` are both clean, and the adversarial security work is
better than what this design would otherwise produce. That is precisely why the harvest list in §3 is
non-empty and why the branch must not be deleted before the harvest lands.

### 3.2 Why `wave-spec-client.ts` is *not* the C5 answer for this design

Every survey named this module the answer to the split-brain in
`02.worktree-parallelism-feasibility.md` §5.3. It is a correct answer to a **different** problem.

The branch's mechanism is `createMcpCwdBoundSpecClient` spawning a fresh stdio MCP server via
`bin/speckiwi mcp` with `cwd: workspaceRoot` (`wave-spec-client.ts:800-805`). That is available only
to a **Node process**. `kiwi-orchestrator` is a skill: markdown instructions to an agent, which can
invoke CLI commands and MCP tools and nothing else. It cannot call a TypeScript factory.

Worse, the problem does not survive the charter's own constraints:

- **C1 removes it.** "No parallel task may perform an SRS mutation." If a worktree task never touches
  `docs/spec/`, the fact that its MCP calls resolve to the host root is irrelevant to it.
- **The CLI already binds root by cwd.** `FR-FLOW-042` states this as settled fact:
  *"the `speckiwi` CLI SHALL NOT serve as a fallback source for this comparison, because the CLI
  resolves its root from the caller's cwd and would make the check vacuous"*
  (`docs/spec/60.workflow-release.srs.md:3076` block, Requirement paragraph). What is a defect for
  a preflight comparison is exactly the property a worktree task needs.
- **`02` §3.1/§10 already recorded the disposition**: per-root server spawn "would require ... which
  `REL-MCP-004` / `IR-CLI-045` currently prohibit at the CLI surface; the unmerged
  `work/kiwi-wave-master-multiroot-g0` branch attempts exactly this and is under a security HOLD"
  (`02.worktree-parallelism-feasibility.md:402`; stated as a designed prohibition at `:65`).

Additionally the branch's own orchestrator would **reject** a worktree agent outright: readiness
discovery hard-compares `workspace.workspaceRoot` against `binding.specRoot` and fails with gate
`root-mismatch` (`wave-orchestrator.ts:266-271`, and again in preflight at `:906-907`). Under §5.3's
measured split-brain that is a hard no, not an accommodation.

**Ruling:** harvest H3 (the pure readiness functions). Discard the transport.

### 3.3 Why `event-schema.ts` must not be ported — `05` gate A2 resolved

`05.orchestrator-design.md:92` set the default action for A2 as *"port from the branch and extend to
v1.4.0, not write fresh"*. **That default is wrong and is hereby overridden.**

Two disqualifying facts, both in the code:

1. `validateWaveEvent` rejects any event whose `schema_version` is not exactly `"1.0.0"`
   (`event-schema.ts:199`, against `WORKFLOW_EVENT_SCHEMA_VERSION` at `:1`). Mainline shipped
   `waves-event.md` at **v1.3.0** (`skills/claude/_shared/kiwi/waves-event.md:1`). The branch's
   validator would reject every event any currently shipped skill writes. It is a **contract
   regression**, not a base to extend.
2. `manifest_hash` is required on every wave event (`:207-209`) and is a 64-hex SHA-256 of an
   immutable run manifest. There is no manifest in this design. The validator cannot be satisfied
   without adopting the whole manifest model — the very model §1.1 #11/#13 shows is incompatible.

The field sets diverge in the same way: branch `WaveEvent` is `{event_id, wave_id, manifest_hash,
input_sha, output_sha, readiness, blockers}` (`:60-81`); mainline v1.3.0 is `{wave, order, target,
...}` with `target = wave-{n}` (`skills/claude/_shared/kiwi/waves-event.md` §2.1). The branch
*deliberately* removed `target` because it discarded per-wave targets — F1 again.

**What is genuinely reusable is one idea, not the module:** the transition table
`pending → in_progress → {complete, failed}` with both terminal states closed
(`event-schema.ts:232-237`) and the cross-transition invariants (run_id/wave_id/order/hash constant,
`event_id` unique) at `:245-255`. That is ~20 lines. Write `waves-journal.ts` fresh against the
**mainline v1.3.0 shape**, extend to v1.4.0 there, and carry that transition table across.

## 5. Risks of adopting any of it

The repository's own history shows green suites hiding defects; this branch is not green. What
follows is what must be verified before any harvested line is trusted.

### 5.1 The trusted-git root binding is not proven — this is the blocking risk

Two distinct defects sit on the same guard, `assertCleanIntegrationWorktree`
(`wave-service.ts:289-296`), which rejects a clean fixture with
`MUTATION_DENIED: Integration worktree contains uncommitted changes ... M root-a/docs/spec/00.index.md`.

**Defect A — a fixture defect, fully explained, not the production code's fault.** Production
`sterileEnvironment` blanks global and system config (`trusted-git.ts:255-256`:
`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=NUL`), so the trusted invocation never sees this host's
`core.autocrlf=true`. The fixture's plain `git add` does see it and stores LF blobs for CRLF working
files; `git status` under the sterile environment then reads every such file as `M`. The proof is in
the branch's own tests: `wave-orchestrator.test.ts:109-113` sets `core.autocrlf=false` and
`core.eol=lf` **under a comment naming this exact hazard**, and `wave-terminal-sealer.test.ts:33`
does the same — both pass. `wave-service.test.ts:89-93` sets neither — and is 34/47 red. This is a
two-line fixture fix and it exonerates the production code.

**Defect B — unexplained, and the one that matters.** Independently of Defect A, the same rejection
was reproduced **outside vitest**, against compiled `dist`, with the fixture's `git status
--porcelain` empty in every case, and the outcome depending only on the calling process's working
directory: cwd outside any repository → accepted; cwd inside the branch worktree → rejected;
deterministic across repeats. `execGit` does pass `cwd: root.root` (`wave-service.ts:57-70`) and
`trustedGitInvocation` does pin `--git-dir`/`--work-tree` plus `GIT_DIR`/`GIT_WORK_TREE`
(`trusted-git.ts:460-480`) — but `dynamicCommandOverrides` spawns git with **no `cwd` option at all**
(`trusted-git.ts:402-406`), inheriting the caller's. The precise path was not isolated.

**Why this is disqualifying for `trusted-git.ts` adoption.** Ambient-cwd sensitivity is the exact
failure mode a multi-root, multi-worktree orchestrator cannot tolerate; it is the same class as the
`02` §5.3 split-brain. **H1 must therefore drop its `runTrustedGit` dependency and use plain
`git cat-file`/`ls-tree` with an explicit `cwd`.** `trusted-git.ts` may be reconsidered only after
Defect B is root-caused and covered by a test that runs the guard from three different cwds.

A third, smaller hazard from the same layer: the injected filter-disabling overrides at
`trusted-git.ts:410-412` make behaviour depend on the developer's *global* gitconfig — this machine
carries `filter.lfs.*` and `filter.obfuscate.clean`. Any harvested code must be tested under a
non-trivial global config.

### 5.2 The safety-critical halt path is red

`wave-orchestrator.test.ts` fails two tests, both on halt semantics: *"halts and journals a child
failure without mutating Active Target"* (`expected 'in_progress' to be 'failed'`) and *"keeps
NEEDS_USER in_progress and refuses automatic replay"*. Whether the engine or the test is wrong was
not isolated. Either way the branch's own specification of its halt behaviour is unproven — and halt
behaviour is precisely what the charter's "new issues at a stage boundary must not be carried
silently into the next stage" depends on.

Related: `wave-service.test.ts:973` expects the guard to fire with reason `/runtime|kiwi|ancestry/i`
and gets `"Manifest child with a different existing target is missing its ordered trusted
select/restore pair"`. The wrong guard wins the race, so **the security property that test exists to
prove is not proven**, even though the test's file was later fixed to pass.

### 5.3 Windows-only coverage reads as coverage but is not

Several of the strongest committer and allocation tests are `it.skipIf(process.platform !== "win32")`
(`manifest-child-runner.test.ts:415`, `:462`, `:483`, `:583`). On a Linux CI they silently pass by
not running. `wave-file-allocation.ts`'s entire guarantee is a no-op off Windows
(`NoopSparseProofSession`, `:362-365`). `lease-lock.ts`'s kernel fence is a stub on POSIX (`:70`),
leaving exclusion to `wx` + pid liveness — sound, but **no test spawns a second Node process**; the
64-way race is 64 promises in one process. If H2 is adopted, add a genuine cross-process test.

### 5.4 The C1 hazard ships with `wave-product-trust.ts`

`normalizedIndexBytes` masks Status Summary counts before comparison (`:240-247`) and `SRS-W019` is
never consulted (`:739` vs `src/core/validator/rules.ts:360-372`). `sync-index` is called **nowhere**
in the wave path — `git grep -n "syncIndexRollups" -- src/` on the branch returns only
`src/cli/commands/mutations.ts:119`, `src/core/mutation/add-requirement.ts:281,361`, and
`update-status.ts:162`. A worker can leave a corrupt index rollup and this machinery accepts it
silently. Charter constraint **C4** — `validate` then `sync-index` after every merge, mandatory — is
therefore not satisfied by anything on this branch and must be built.

### 5.5 Verification required before any harvested line is trusted

1. **H1** — reproduce the pinning test suite with `runTrustedGit` replaced by plain `git` with
   explicit `cwd`; re-run all 15 attack cases; add a case where the pinned document is the
   orchestrator's own handoff, not `AGENTS.md`.
2. **H2** — add a real cross-process test (two Node processes, not two promises); add a test proving
   the common-dir-keyed lock excludes two worktrees over one `.git`.
3. **H3** — re-run all 15 readiness cases against a snapshot obtained from `speckiwi list --json`
   rather than MCP, to prove transport independence.
4. **H4** — a test where a second writer moves the branch between build and publish, asserting the
   CAS rejects rather than overwrites.
5. **H5** — the missing pre-created-junction test.
6. **All** — run under a non-trivial global gitconfig (filters + autocrlf set) and from at least
   three different process working directories.

No harvested code enters the design without its own test, authored test-first, under a `v2.6.0`
requirement. Porting a passing test alongside ported code does **not** satisfy the TDD rule when the
port changes the code's dependencies, which H1 and H2 both do.

## 7. Why it was deferred — a reason exists, and a process failure exists alongside it

**A reason was recorded, in three places.** The charter's premise that this work was abandoned with
no explanation is only half right.

1. **On the branch, in `README.md`**, under a heading **"Security hold."**: *"Production
   manifest-child execution is fail-closed on every supported platform. There is currently no
   supported production invocation example. `executeProductionWaveRun` remains exported for contract
   and preflight compatibility, but its host-safety preflight stops before it creates an MCP client,
   starts Codex, acquires a Wave lease, or mutates project state."* (`README.md:319`, mirrored in
   Korean at `:800`.) The technical cause: on Windows, Codex's unelevated sandbox requires full-disk
   read access and cannot enforce the deny-read boundary protecting `auth.json`; non-Windows hosts
   lack a kernel-owned process-family boundary.
2. **In the branch's SRS change notes.** `FR-FLOW-036`, `FR-NODE-071` and `IR-FLOW-001` each carry
   `2026-07-15 | Status -> verified` immediately followed by `2026-07-15 | Status -> in_progress |
   Independent G0 seal audit HOLD: reopen for exact readiness, ancestry allowlist/status-cache,
   trusted Windows process-tree termination, and final HEAD TOCTOU hardening`. The authors reopened
   their own work.
3. **On `feat/2.3.0.1`, in `docs/research/12.kiwi-wave-master-worktree-isolation-research.md` §6–§8
   and §10.** This is a full post-mortem, written 2026-07-27: the security HOLD (`:203-207`), the
   absence of any `wave` surface in released `speckiwi 2.4.1` (`:209`), the four ID collisions
   (`:214-226`), the three `in_progress` requirements (`:186`), and — critically — the open question
   at `:302`: *"선행 브랜치 처분: ... (a) ID repair 후 마감·병합, (b) 설계만 취하고 재구현,
   (c) 폐기 — 어느 쪽인가?"*

**So the sequence is legible.** The work was checkpointed under a self-declared security HOLD on
2026-07-16. Mainline pivoted to TDD-mode work the next day (`94c3c32`, 2026-07-17) and, having no
coordination mechanism for requirement IDs across worktrees, reused four of the branch's IDs. The
disposition question was formally raised on 2026-07-27 and **was never answered**. This audit answers
it: **(b), take the design and a small harvest, reimplement** — with the correction that most of the
design does not transfer either.

**The process failure is real and worth reporting to the user, but it is narrower than "no record".**

- `docs/next/` — the repository's own handoff convention, 13 files — contains **no entry for this
  branch**. Every other significant piece of work has one. A reader following the documented
  convention would find nothing.
- The branch's `docs/` changes are **only** the seven `docs/spec/` files. It added no
  `docs/analysis/`, no `docs/plans/`, no run log.
- The branch added **three rows to `91.completed-work-log.md` dated 2026-07-15 claiming completion
  for requirements whose blocks are `in_progress`** — the source of 14 `SRS-W015` warnings recorded
  at `docs/research/12:186`. The Completed Work Log said done while the requirement blocks said not
  done.
- The audit that produced `docs/research/12` was itself triggered by unrelated worktree housekeeping,
  and the charter's discovery of the branch on 2026-07-31 was likewise incidental (`00.charter.md:152`).

**Three concrete process gaps, offered as findings, not as work:**

1. **No `docs/next/` entry is written when a branch is checkpointed under a hold.** The convention
   exists and was skipped exactly where it mattered most.
2. **Requirement ID allocation has no cross-worktree coordination.** This produced four real
   collisions and is the empirical origin of charter constraint **C2**. The collision-repair tooling
   exists, but it is a cure, not a prevention.
3. **Completed Work Log rows can be written for requirements that are not complete.** `SRS-W015`
   catches it as a warning; nothing blocks it.
