(provisionally `kiwi-orchestrator`) can be built by composition rather than duplication.

All line citations are against the **bundled source** in this repository unless stated otherwise.
Nothing in this repository was modified while producing this report.

## 3. The shared contract modules (`skills/claude/_shared/kiwi/`)

Seven files. All are read-time SSOTs: a skill references them from its `§0` table and inlines only
the skill-specific bits. `auto-option.md:285` states the rule explicitly — *"Do not make copies. The
skill body stays as-is; a `§0` reference plus an inlined `critical_gates[]` is enough."*

### 3.1 `pipeline-event.md` (179 lines) — the inter-skill event contract

Standardises the schema, file location, emit rules and the next-step decision table for
`kiwi/pipeline.jsonl`. Referenced by every skill that ends a run. Conformance requirement for an
author: add one line to the final Phase — `pipeline-event.md:165-171`. Detail in §4 below.

### 3.2 `pipeline-v1.md` (69 lines) — ownership + routing + cycle summary

- Responsibility matrix: which skill *may* update SRS `status` and which may update `stability`
  (`pipeline-v1.md:9-22`). Only `kiwi-srs-feasibility` may move stability; `kiwi-srs`, `kiwi-coder`,
  `kiwi-pm`, `kiwi-srs-sync`, `kiwi-review-fix-loop` may move status.
- Single-step routing summary (`:29-41`) and the `--cycle` chain definition (`:43-60`).
- Guardrails (`:62-69`): MCP required for normal target-scoped SRS mutation; event emission is
  best-effort; **Kiwi skills must not call Snoworca skills**.

### 3.3 `auto-option.md` (388 lines) — the `--auto` decision-committee contract

The largest and most load-bearing module. What it standardises:

- Activation channels and their priority (`auto-option.md:11-18`): tool args > exact prompt token >
  natural language (confirm once) > parent propagation.
- **Decision committee topology** (`:25-36`): `--auto` = 3 members; `--auto --max` = 5. Members are
  isolated subagents that research the gate independently and cast one vote; they inherit the
  current session model unless `--model` overrides.
- Unbiased input contract (`:38-49`) — the caller must not pass its own tentative conclusion.
- Standard spawn pseudocode with a fixed prompt (`:64-116`), and member-model resolution (`:109-116`).
- **Consensus ladder** (`:143-159`): unanimous → escalate 3→5 → plurality → `--max` escalates 5→7 →
  deterministic tie-break by senior member #1. Arbitrary decisions outside the ladder = immediate HALT.
- Member-failure fallback (`:161-168`) and decision normalisation (`:170-179`).
- Severity policy (`:181-190`): `clarification` (confidence ≥ 0.5), `business-decision` (≥ 0.7),
  `rollback-confirmation` (auto-approve), `critical` (HALT regardless of `--auto`).
- Confidence de-rating heuristics (`:192-222`) — thin rationale, high risk + high confidence, empty
  `side_effects` on a mutation gate all shrink confidence.
- **`critical_gates[]` interface** (`:224-252`): *a skill that does not declare `critical_gates[]` has
  `--auto` disabled* — the safe default. Declaration position is free-form; the requirement is the
  existence of a `gate_id` / `reason` / location table. A recommended catalogue is at `:254-274`.
- Read-time replace conventions (`:276-285`) and **child propagation** (`:287-309`).
- Audit artifact `docs/analysis/{skill-run-id}/auto_decisions.json` (`:329-360`).

**To conform:** reference the module in `§0.X`, declare `critical_gates[]`, and use the
`§2.3` spawn shape verbatim.

### 3.4 `loop-option.md` (59 lines) — `--mini` / `--loops N`

- `--mini` = round cap 3; `--loops N` = cap N (integer ≥ 1); both are **upper bounds**, severity gates
  may exit earlier (`loop-option.md:7-16`).
- Precedence: explicit `--loops` beats `--mini`, order-independent, non-fatal WARN (`:18-26`).
- Cap-reached behaviour: stop, **report residual findings in full**, never silently truncate, never
  bypass safety gates (`:28-32`).
- Orthogonal to `--max` and composes with it (`:34-38`).
- Loop-less skills (`kiwi-step`, `kiwi-srs-research`) accept both as documented no-ops (`:40-42`).
- Orchestrator propagation table (`:44-54`).

### 3.5 `workmode-policy.md` (36 lines) — work-mode → `tdd_policy` derivation

- `tdd` → `strict`; `sdd`/`wait`/`vibe` → `relaxed` (`workmode-policy.md:7-17`). Lookup order
  MCP `get_work_mode` → CLI `speckiwi mode` → default `wait` (**fail-open**).
- `disabled` is **never derived** — only an explicit `--tdd-policy=disabled` sets it (`:19-22`).
- Explicit flag beats derived default, with a non-fatal WARN (`:24-28`).
- Consumers: `kiwi-planner` records the derived value into plan frontmatter + sidecar; `kiwi-pm` WARNs
  on contradiction; `kiwi-pipeline`'s work-mode routing is declared **orthogonal** to this (`:30-36`).

### 3.6 `waves-event.md` (188 lines) — `kiwi/waves.jsonl` schema

Separate file from `pipeline.jsonl`; holds per-wave state of one wave-master run (`waves-event.md:1-7`).
Notable content: `verification` object with the four denominators
(`axis_a`, `axis_b`, `design_layer`, `constraint_layer`, `preservation_layer`, `regression`,
`frozen_denominator`, `residual`) at `:69-101`; `design_baseline` object at `:103-120`; status
transition rules and the "complete requires a prior passing wave-verify line" gate at `:124-141`;
resume predicate at `:145-164`.

### 3.7 `feasibility-policy-schema-v1.md` (58 lines)

Feasibility scoring/stability-policy schema shared by `kiwi-srs-feasibility` and reused inline by
`kiwi-srs`'s research A/B loop (`skills/claude/kiwi-srs/SKILL.md:577`).

## 4. The pipeline event contract (`pipeline.jsonl`)

### 4.1 Path resolution — `pipeline-event.md:9-21`

1. `git rev-parse --show-toplevel` succeeds → `{git_root}/kiwi/pipeline.jsonl`
2. else if `./kiwi/` exists → `{cwd}/kiwi/pipeline.jsonl`
3. else → `~/.kiwi/pipeline.jsonl`

The resolved absolute path is written to `{pipeline_dir}/.pipeline-path`. **Run-root pin**: resolution
happens once at run start and is not re-evaluated per emit (`:21`).

### 4.2 Schema — `pipeline-event.md:25-64`

Required: `ts`, `schema_version`, `skill`, `run_id`, `status`, `summary`, `next_hint`, `artifacts`,
`dry_run`. `status ∈ {TASK_DONE, NEEDS_USER, FAILED, DRY_RUN, CORRECTION}`.
`artifacts = { spec_files[], plan_file, sidecar_file, analysis_dir }` (`:43-54`).
Optional: `target`, `req_ids`, `duration_sec`, `notes`, `corrects_run_id` (`:56-64`).
The `skill` enum is closed (`:68-87`) and — importantly for a new skill — **does not contain
`kiwi-orchestrator`, `kiwi-step`, or `kiwi-tdd`**. Values outside the enum are WARN+skipped by the
meta skill.

### 4.3 Stage-transition table (T1) — `pipeline-event.md:91-110`, mirrored at `kiwi-pipeline/SKILL.md:245-265`

| Last skill | status | next_hint |
|---|---|---|
| `kiwi-srs` / `kiwi-srs-from-code` | TASK_DONE | `kiwi-srs-feasibility` |
| `kiwi-srs-sync` | TASK_DONE | `kiwi-pipeline` (re-evaluate) |
| `kiwi-srs-feasibility` | TASK_DONE | `kiwi-planner`, or `kiwi-srs-research` if blockers are ambiguous |
| `kiwi-srs-research` | TASK_DONE | `kiwi-srs-feasibility` |
| `kiwi-planner` | TASK_DONE | `kiwi-pm` |
| `kiwi-pm` / standalone `kiwi-coder` | TASK_DONE | `kiwi-review-fix-loop --close-reqs` |
| `kiwi-review-fix-loop` | TASK_DONE | `kiwi-commit-auto-push` (self mode) or `null` (PR mode) |
| `kiwi-hot-fix` | TASK_DONE | `kiwi-commit-auto-push` or `kiwi-pipeline` |
| commit skills | TASK_DONE | `kiwi-pipeline` |
| any | NEEDS_USER / FAILED | `null` |
| any | DRY_RUN | real run of the same skill |
| `kiwi-pipeline` | TASK_DONE | previous-previous event's `next_hint` (self-recursion guard) |

An explicit `next_hint` on the event **beats** the table (`kiwi-pipeline/SKILL.md:269-273`).

### 4.4 Emit rules — `pipeline-event.md:114-159`

- Exactly one append per run, immediately after the user report.
- **Idempotency by `run_id`** (`:133-141`): if a line with the same `run_id` exists, skip.
- **Re-entrancy key** (`:147-155`): a re-entrant run driven by `kiwi-wave-master` must emit under
  `{run_id}#r{n}`, because the idempotency skip applies to the exact key. `kiwi-pipeline`,
  `kiwi-planner` and `kiwi-pm` all follow this — if only one does, the others emit nothing.
- Emit is **best-effort**; a failed emit must not fail the primary task (`:157-159`).

## 5. Composition points

### 5.1 `kiwi-pipeline` — what it can and cannot do today

**Can:**

| Capability | Citation |
|---|---|
| Read the last N events, parse, schema-check, derive next candidate | `kiwi-pipeline/SKILL.md:98-107`, `:220-239` |
| Recommend a single next step, or gate a multi-candidate choice via `AskUserQuestion` | `:284-295` |
| Spawn the chosen skill with the `Skill` tool | `:321-336` |
| **`--cycle`**: chain `kiwi-srs → (conditional) kiwi-srs-feasibility → kiwi-planner → kiwi-pm → kiwi-review-fix-loop` | `:113-127` |
| `--cycle` implies `--run` without lowering any gate | `:123` |
| Conditional feasibility skip when new REQs are ≥ evolving and implementability is verified | `:129-131` |
| **skip-authoring entry** `--from=feasibility` / `--from=planner` | `:133-135` |
| **Worktree isolation** `--wt` with a dedicated branch, plus a merge-or-PR completion gate; under `--auto` always PR, never direct-merge to base | `:145-160` |
| **GitHub issue entry mode**, research-first: issue → `kiwi-srs-research` → `kiwi-srs` (with `--qna-force` escalation when research is insufficient; suppressed under `--auto`) → normal cycle | `:163-177` |
| Work-mode routing gate (see §5.3) | `:181-197` |
| Propagate `--max`, `--mini`/`--loops`, `--target`, `--req-filter`+`--plan-run-id`, and pass-through `--auto-integration` / `--auto-cost-warning` / `--force` / `--regression-baseline` | `:338-363` |
| Emit its own event; run_id `pipeline-{YYYYMMDDHHMMSS}`, never idempotent-skipped | `:399-420` |

**Cannot:**

| Gap | Citation |
|---|---|
| Mutate anything — no MCP, no filesystem, no git. Its only side effect is one jsonl line | `:25` |
| Auto-chain to commit/push: `kiwi-commit-auto-push` is deliberately **not** linked by the cycle, because commits are irreversible external side effects | `:127` |
| Decompose work into waves, or hold any notion of a design baseline | (absent — that is `kiwi-wave-master`) |
| Run stages in parallel — the chain is strictly sequential, each stage gated on the previous `TASK_DONE` | `:115` |
| Verify the cycle's output against the originating design — the last hop is `kiwi-review-fix-loop` and the cycle ends there | `:125` |

### 5.2 `kiwi-wave-master` — the closest existing thing to the proposed orchestrator

Explicitly *"does not author requirements or implement code itself"* — it sets wave boundaries,
registers each wave's target via `/kiwi-srs`, and spawns per-wave `/kiwi-pipeline`
(`kiwi-wave-master/SKILL.md:10`). Phase flow at `:97-107`:

```
Preflight  run-root preflight gate (§2.1)
Phase 0    input parse + waves.jsonl resolution (resume detection)
Phase 1    wave decomposition + design-baseline materialisation + coverage gate
Phase 2    per-wave target registration via /kiwi-srs
Phase 3    per-wave /kiwi-pipeline --cycle --from=feasibility --run
Phase 3.5  wave-end cross-verification (2 verifiers, add-only cross-rebuttal loop)
Phase 4    waves.jsonl update (complete only after success + verification pass)
Phase 4.5  whole-run final verification against the full design baseline
Phase 5    own pipeline event emit
```

Load-bearing behaviours a new orchestrator would otherwise re-invent:

- **Run-root preflight** — compares MCP `workspaceRoot` against `git rev-parse --show-toplevel` with a
  four-rule normalisation (separators, trailing slash, Windows case, realpath), and hard-stops on
  mismatch with two named recovery paths (`:115-144`). Refuses `--wt` delegation because per-wave
  worktrees break wave accumulation (`:144`). Refuses `--skip-regression` / `--reviewer-off` (`:148`).
  Pins a **regression baseline** once per run (`:150`).
- **Two-branch wave-split heuristic** — headers-first, else a subagent analyses overall flow into 3–8
  coherent sub-goals; the subagent is given existing modules and dependency direction so the split
  does not cut one module across waves (`:154-165`).
- **Design baseline materialisation** — per-wave `source_file`/`heading_path`/`line_start`/`line_end`,
  `design_items` enumerated in full at *one normative sentence per lowest heading = one item*,
  `integration_items` for cross-wave design, per-wave markdown **excerpt** files, `out_of_scope` with a
  closed `exclusion_class` enum, and a **user-constraint artifact that is always written even when
  empty** (`:167-193`).
- **Decomposition coverage gate** — the comparison unit is the full `design_items` set, not top-level
  sections; unassigned items with no recorded out-of-scope reason block target registration; recording
  an exclusion additionally requires user consent even under `--auto` (`:195-205`).
- **Per-wave scoped target registration** — `/kiwi-srs` per wave with the excerpt as `--research-doc`,
  the constraints artifact as `--constraints-doc`, `existing_modules` as authoring input, and
  carried-forward residuals folded into the authoring input (`:209-227`).
- **Wave-end cross-verification (§5.5, `:249-425`)** — the richest verification machinery in the suite:
  - A shared evidence bundle given identically to both verifiers; splitting evidence is forbidden (`:257-283`).
  - Two verifiers with separated stances: intent-realisation + process conformance vs output quality +
    cross-wave regression risk (`:285-325`). Denominators are **externally fixed** (`list_requirements`
    for REQ/AC, `design_items` for the design layer, the constraints artifact for the constraint layer,
    a mechanical four-class diff derivation for the preservation layer) and frozen per round.
  - Round structure: independent → **add-only cross-rebuttal** (rejection is impossible by construction,
    to remove the collusion incentive) → mechanical union; verifiers are re-spawned from round 2 (`:327-339`).
  - Exit conditions: Normal = CRITICAL 0 + HIGH 0 + `ALL_MATCH` + no fix applied in that round + zero
    new regression failures + zero `unapproved-damage`; `--max` adds MEDIUM 0 for two consecutive
    rounds. Cap 5 / `--max` 8 / `--mini` 3. Cap exhaustion is **not** a pass (`:341-360`).
  - **Fix delegation by finding class** (`:362-385`): quality/regression/implementation → `kiwi-review-fix-loop`
    with an explicit range; plan-absent gaps → pipeline re-entry; design-baseline-but-not-in-SRS →
    incremental `/kiwi-srs` then pipeline re-entry from planning; draft-stability REQs → `/kiwi-srs-feasibility --req-filter`;
    previous-wave requirement changes → critical HALT. The sub-loop's own PASS explicitly **does not**
    satisfy the wave gate (`:377`).
  - Cross-wave carry-forward decided **mechanically by file set** intersection with prior waves'
    trace anchors / diff sets (`:415-425`).
- **Whole-run final verification (§5.6, `:429-461`)** — denominator is the union of all waves'
  `design_items` plus `integration_items`, run-scope diff window, run-head regression; run-scope
  findings append a wave (capped at 3 per run) and re-run the final pass.
- **Resume** — three-granularity resume within a wave (target registration / pipeline / wave verification),
  run-scoped event scanning, `--plan-run-id` + `--req-filter` mandatory on pipeline resume (`:465-486`).
- **Epic issue entry mode** — extract ordered waves from epic body structure / task lists / linked
  sub-issues; only the up-front wave-split research is skipped, and only when extractable structure
  exists, else fall back to the subagent split (`:532-561`).

### 5.3 `kiwi-tdd` and the work-mode routing gate

- The routing gate lives in `kiwi-pipeline/SKILL.md:181-197`. Read work-mode MCP-first with CLI
  fallback and `wait` as a **fail-open** default (`:185-189`). If mode is `tdd` **and** the work is
  step-scoped, route to `kiwi-tdd` instead of the 5-stage sdd chain; otherwise keep the sdd chain (`:191-195`).
- **`--cycle` / `--from=` entries are excluded from this routing** (`:196`) with two stated reasons:
  `kiwi-tdd` declares no `critical_gates[]` so `--auto` is inactive for it under the shared contract,
  and its artifacts (design.md, step SRS, promoted block) do not satisfy the wave evidence bundle.

same shape — *design as a first-class artifact at body/wave scope*:

## 8. How one kiwi skill invokes another, and what propagates

### 8.1 The two sanctioned invocation mechanisms

| Mechanism | Used by | Citation |
|---|---|---|
| **`Skill` tool** — `Skill({ skill: "kiwi-<name>", args: "<inherited or empty>" })` | `kiwi-pipeline` spawning cycle stages; `kiwi-wave-master` spawning `/kiwi-srs` and `/kiwi-pipeline`; `kiwi-hot-fix` delegating `/kiwi-srs-sync` | `kiwi-pipeline/SKILL.md:321-327`, `kiwi-wave-master/SKILL.md:19` |
| **`Agent` tool** — isolated `general-purpose` subagent instructed to execute a named skill | `kiwi-pm` spawning each Task as `kiwi-coder`; `kiwi-srs-feasibility` calling `kiwi-srs-research --mode=subagent` | `kiwi-pm/SKILL.md:400-409`, `kiwi-srs-research/SKILL.md:13` |

Hard constraint on both: **`/snoworca-*` skills must never be called from a kiwi skill** — logic may
be borrowed, execution must stay inside the kiwi set (`pipeline-v1.md:69`, `kiwi-wave-master/SKILL.md:19`,
`kiwi-pipeline/SKILL.md:26`).

### 8.2 What propagates on invocation

**Flags consumed and re-emitted by the parent:**

| Flag | Propagation rule | Citation |
|---|---|---|
| `--auto` | Parent in `--auto` must explicitly pass `--auto` to every spawned kiwi child; `--auto --max` / `--auto --model <name>` propagate as a unit. Parent `--auto` never synthesises a child's safety-bypass flag (`--auto-apply`, `--yes-all`) | `auto-option.md:287-309` |
| `--max` | Propagated to every spawned sub-skill; `kiwi-wave-master` additionally propagates to the `/kiwi-srs` it calls directly, which the cycle would otherwise miss | `kiwi-pipeline/SKILL.md:338-340`, `kiwi-wave-master/SKILL.md:503-507` |
| `--mini` / `--loops N` | Propagated to all children; additive to the `--auto` table; wave-master also wires it into its own §5.5 verification loop cap | `loop-option.md:44-54`, `kiwi-wave-master/SKILL.md:511-515` |
| `--model <name>` | Overrides verification-subagent model, inherited otherwise; propagated when the user specified it | `kiwi-pipeline/SKILL.md:331` |
| `--target` | Passed explicitly to `kiwi-srs` / `kiwi-srs-feasibility` / `kiwi-planner`, because all three fall back to `get_active_target` otherwise | `kiwi-pipeline/SKILL.md:334` |
| `--req-filter` + `--plan-run-id` | Must travel **together** to `kiwi-planner` and `kiwi-pm`; passing one alone yields an unscoped re-entry that re-runs the whole plan | `kiwi-pipeline/SKILL.md:333` |
| `--close-reqs` | Auto-attached when the next hop is `kiwi-review-fix-loop` after `kiwi-pm` or standalone `kiwi-coder`; becomes `--close-reqs --auto` under `--auto` | `kiwi-pipeline/SKILL.md:272`, `:332` |

**Pure pass-through flags** (parent must not interpret, and must not drop — dropping stalls unattended
runs at the last hop): `--auto-cost-warning`, `--auto-integration`, `--force`, `--regression-baseline`,
along the chain `kiwi-wave-master → kiwi-pipeline → kiwi-pm → kiwi-coder`
(`kiwi-wave-master/SKILL.md:517-528`, `kiwi-pipeline/SKILL.md:352-363`). All three of the first three
flow **only when the user specified them explicitly**.

**Run identifiers — three distinct id spaces, easily conflated:**

| Id | Owner | Keys |
|---|---|---|
| `pipeline_run_id` | each `kiwi-pipeline` invocation | the `pipeline.jsonl` window for that cycle |
| `plan_run_id` | `kiwi-planner`, reused verbatim by `kiwi-pm` | `docs/plans/{plan_run_id}.plan.md`, `.sidecar.json`, `.kiwi/sessions/{plan_run_id}/worklog.jsonl` |
| per-skill run-id | each skill independently | `docs/analysis/kiwi-{skill}-{run-id}/` |

`kiwi-wave-master/SKILL.md:281-283` spells out the resolution chain: read `plan_run_id` from the
`kiwi-planner`/`kiwi-pm` events' `artifacts.plan_file` / `artifacts.analysis_dir`; resolve a review
report from **that skill's own** `artifacts.analysis_dir`, never by glob. `waves.jsonl` records
`plan_run_id` and the full `pipeline_run_ids[]` list precisely so a resumed session with no
conversation state can reconstruct them (`waves-event.md:56-64`).

**Events:** each skill appends exactly one `pipeline.jsonl` line at its own end — the parent does not
record on the child's behalf (`kiwi-pipeline/SKILL.md:336`). Re-entrant runs must use the
`{run_id}#r{n}` emit key or the chain never sees a fresh `TASK_DONE` (`pipeline-event.md:147-155`,
`kiwi-pipeline/SKILL.md:365-373`).

**Safety on invocation:** a child returning `NEEDS_USER` / `FAILED` halts the parent even under
`--auto` (`kiwi-pipeline/SKILL.md:27`, `kiwi-wave-master/SKILL.md:21`, `:40`).

## 9. Overlaps between skills — read this before designing

| Overlap | Detail |
|---|---|
| **`kiwi-pipeline --cycle` vs `kiwi-wave-master`** | Both are orchestrators that spawn other skills and emit journal events. The division is: wave-master owns decomposition, per-wave target registration, cross-verification and resume; pipeline owns the single five-stage chain. Wave-master consumes pipeline through the skip-authoring entry `--cycle --from=feasibility --run` (`kiwi-wave-master/SKILL.md:237-239`). A third orchestrator on top would sit above wave-master or replace it |
| **`kiwi-wave-master` §5.5 verification vs `kiwi-review-fix-loop`** | Deliberately disjoint: §5.5 declares hunk-level code review **out of its scope** because `kiwi-review-fix-loop` already owns it, and §5.5's value is wave-granularity evidence, not diffs (`kiwi-wave-master/SKILL.md:255`). It *delegates* quality findings to `kiwi-review-fix-loop`, but that skill's own PASS explicitly does not satisfy the wave gate (`:377`) |
| **`kiwi-review-fix-loop` vs `kiwi-coder` Phase 2.f/2.g** | Same 7-axis harsh-review logic; review-fix-loop borrows it (`kiwi-review-fix-loop/SKILL.md:23`). `kiwi-hot-fix` mandates the same harsh reviewer, described as "kiwi-coder Phase 2.f/2.g equivalent" |
| **Preservation rules duplicated in three places** | `kiwi-coder §0.20` is the SSOT closed list; `kiwi-review-fix-loop §0.17` restates it because it is a code-change path that bypasses kiwi-coder (`kiwi-review-fix-loop/SKILL.md:39`); `kiwi-wave-master §5.5.2` uses the same two-value enum and the same evidence requirement so plan-approved refactors do not pass verification and HALT execution (`kiwi-wave-master/SKILL.md:305-315`) |
| **`kiwi-srs` vs `kiwi-step`** | `kiwi-step` is described in its own text as the lightweight counterpart of `kiwi-srs` for step scope (`kiwi-step/SKILL.md:10`) |
| **`kiwi-step` vs `kiwi-tdd`** | `kiwi-tdd` is an extension of `kiwi-step`'s step-local authoring convention, adding SDS, red/green discipline and promotion (`kiwi-tdd/SKILL.md:8`). Both claim the step and both forbid body-scope writes |
| **`kiwi-srs-sync` vs `kiwi-hot-fix`** | `kiwi-hot-fix` delegates its SRS catch-up to `/kiwi-srs-sync` rather than doing it (`--no-sync` opts out) |
| **`kiwi-commit-auto-push` vs `kiwi-commit-auto-pr`** | Same commit machinery; the PR variant adds branch creation off protected branches and PR body/comment handling |
| **QnA logic** | `kiwi-srs` §5 reimplements the Agent-Dropout QnA pattern in-skill rather than calling out, because `/snoworca-*` invocation is banned (`kiwi-srs/SKILL.md:321`) |
| **Regression baseline** | `kiwi-wave-master` preflight pins one, and explicitly states it shares an SSOT with `kiwi-coder`'s `state.regression_baseline` — same suite, same command (`kiwi-wave-master/SKILL.md:150`). `kiwi-review-fix-loop §6.0` captures its own baseline too |
| **Pipeline emit** | Every skill hand-writes the same bash append block, while `workflow_pipeline_emit` exists as an MCP tool (see §6) |

## 10. Notes for the designer (facts, not design)

- A new skill that emits pipeline events will need its name added to the closed `skill` enum at
  `pipeline-event.md:68-87` and a row in T1, or `kiwi-pipeline` will WARN-and-skip its events
  (`kiwi-pipeline/SKILL.md:230-234`). `kiwi-step` and `kiwi-tdd` are currently in this position.
- A new skill with no `critical_gates[]` declaration has `--auto` **disabled** by the shared contract
  (`auto-option.md:23`, `:237`) — this is the stated reason `kiwi-tdd` is excluded from unattended
  cycle routing (`kiwi-pipeline/SKILL.md:196`).
- `kiwi-wave-master` refuses `--wt`, `--skip-regression`, `--reviewer-off` outright
  (`kiwi-wave-master/SKILL.md:144`, `:148`); those refusals are declared as critical gates, not
  preferences.
- Both journals resolve their root **once per run** and pin it; re-resolution mid-run is explicitly
  forbidden (`pipeline-event.md:21`, `waves-event.md:21`).
- Per CLAUDE.md §7, skills in this repo carry no changelog section; git history is the SSOT.
