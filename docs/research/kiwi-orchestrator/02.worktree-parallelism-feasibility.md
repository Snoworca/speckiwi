# Worktree Parallelism Feasibility

| Field | Value |
| --- | --- |
| Date | 2026-07-31 |
| Question | Is per-task, worktree-isolated parallel agent execution achievable in this environment? |
| Method | Runtime probes (2 `isolation: "worktree"` agents), throwaway git repos in the temp area, source tracing, MCP live call |
| Scope | Read-only against this repository. All measured mutations were performed in throwaway repos under the scratchpad. |
| Prior claims tested | `docs/research/12.kiwi-wave-master-worktree-isolation-research.md` |

---

## 1. Verdict

**Per-task worktree parallelism is feasible in this repository — but only for tasks whose write set is confined to code and tests, and only if the orchestrator refuses to let any parallel task perform an SRS mutation.**

Three findings drive that verdict, all measured, not inferred:

1. **The agent runtime already creates worktrees, and it hands each agent a guaranteed split-brain.** An `isolation: "worktree"` agent's git root is its worktree, but its SpecKiwi MCP connection resolves to the *host* repository — measured character-for-character (§4.3). Every worktree agent is born in the exact state that `FR-FLOW-042`'s preflight gate is designed to halt on.
2. **The historical hard blocker in the tool layer is real, is a designed contract, and is unchanged.** MCP workspace root is the server process cwd, per-call override is refused, and the server is started once per session (§3.1). It is not a bug to route around.
3. **The historical hard blocker in the tool layer does not apply to the git/file/CLI axis.** SpecKiwi's CLI works correctly from inside a worktree today, including `init` — the `.git`-is-a-file crash is fixed and now degrades to an explicit, correct warning (§4.1). Requirement-ID allocation, however, is per-root and uncoordinated, and two parallel roots deterministically allocate the same ID (§5.2).

**Conditions.** Parallelism works if the design accepts this split:

| Axis | Where it must happen | Why |
| --- | --- | --- |
| Code, tests, build, regression | Parallel worktrees | Isolated, mergeable, cheap (§6) |
| SRS authoring, ID allocation, status/evidence mutation, index rollups | Serialized, in the host root only | MCP is host-pinned; ID allocation has no cross-root coordination |

**Cost.** ~119 MB and ~4 s of `npm ci` per worktree with a warm npm cache (§6.3), plus one manual `speckiwi sync-index` after merging (§5.3). Path length has ~70 characters of headroom (§6.1). None of these is prohibitive.

**What is not feasible**, without new runtime work: running a *skill* that performs SRS mutations inside a worktree agent. Both `kiwi-coder` and `kiwi-wave-master` will correctly refuse (§3.2, §3.3), and their refusals are not misconfiguration — they are the only honest response to the split-brain.

## 3. Q1 — What exactly blocked worktree isolation before

The prior research (`docs/research/12`) named two independent hard blockers. Both claims hold. One stated side-defect has since been fixed.

### 3.1 Tool layer: MCP workspace root is the server process cwd (unchanged, by contract)

`src/mcp/adapter.ts:37`

```ts
const workspaceRoot = deps.root ? path.resolve(deps.root) : path.resolve(process.cwd());
```

`deps.root` is an internal DI seam, annotated at `src/mcp/adapter.ts:40` as test-only. Any caller-supplied `root` / `workspaceRoot` on a tool call is rejected at `src/mcp/adapter.ts:45-70` with `MCP_WORKSPACE_ROOT_UNSUPPORTED` / `SRS-E075`. Starting a server with an explicit root is likewise rejected at `src/cli/commands/mcp.ts:25-28`.

This is a designed prohibition (`REL-MCP-004`, `IR-CLI-045`), not an oversight. **Category: SpecKiwi tool constraint.**

Live confirmation from this session (§6 of the probe transcript; call made from the host):

```json
{"workspaceRoot":"C:\\Work\\git\\_Snoworca\\speckiwi","rootSource":"server-cwd-discovery",
 "indexPath":"docs/spec/00.index.md","activeTarget":"v2.5.1","packageVersion":"2.4.1"}
```

Note `packageVersion: 2.4.1` while the installed CLI is `2.5.1` (`speckiwi --version` → `2.5.1`). The MCP server process was started once, at session start, from an older install and has not been restarted since. That is direct evidence for the "one long-lived server per session, cwd fixed at start" mechanism — the process cannot follow a cwd change because it is not re-executed.

**Correction to the prior research.** `docs/research/12` §4 T3 recorded a side-defect: the rejection payload pointed at a non-existent `restart_mcp_server` tool. That is **fixed**. `src/mcp/adapter.ts:63-68` now carries a `@req FR-MCP-055` comment and a `recovery.message` naming the operator action instead of a tool. `FR-MCP-055` is `Status = verified`.

### 3.2 Skill layer: the `cwd`-external edit gate (unchanged)

`skills/claude/kiwi-coder/SKILL.md:26`

> §0.9 | **외부 모듈 수정 금지**. cwd 외부 path 가 sidecar files[] 또는 실제 변경에 진입 시 즉시 중단 + AskUserQuestion

and `skills/claude/kiwi-coder/SKILL.md:70`

> 시니어 코더가 cwd 외부 파일 편집 시도 | 즉시 차단 + CRITICAL

For a *host* session driving a worktree, every worktree file is cwd-external, so this gate fires on every task. **Category: skill-authoring constraint, deliberate.**

Important nuance the prior research did not draw out: this gate is **not** a blocker for the runtime's own worktree agents. An `isolation: "worktree"` agent's cwd *is* the worktree (measured: `pwd` = the worktree path, §4.2), so its edits are cwd-internal and the gate passes. The gate only blocks the "host session reaches into a worktree" topology — which is the topology the prior research was testing, and which `EnterWorktree` produces.

### 3.3 The gap has since been closed with a fail-closed gate, not a fix

`FR-FLOW-042`, `FR-FLOW-043`, `FR-MCP-055` are all `Status = verified`, `Stability = evolving`. The shipped skill now carries the preflight:

- `skills/claude/kiwi-wave-master/SKILL.md:115-131` — compare `mcp_workspace_info.workspaceRoot` against `git rev-parse --show-toplevel`; on mismatch **or lookup failure**, critical halt that `--auto` cannot bypass; the CLI is explicitly *not* a fallback for the comparison.
- `skills/claude/kiwi-wave-master/SKILL.md:144` — `--wt` delegation is refused outright, because per-wave worktree creation breaks wave accumulation.

So the current state is: the silent-wrong-repository failure mode is gone, replaced by a loud halt. **The underlying constraint is untouched.** A designer should read `FR-FLOW-042` as a detector, not a solution.

### 3.4 Not a git constraint

Nothing in git blocks this. `src/core/project-root.ts:21` walks up looking for `.git`, and `access()` succeeds on a `.git` *file*, so the CLI correctly resolves a worktree as its own root. That is why the CLI and MCP disagree — both are behaving as specified.

## 4. Q2 — Does SpecKiwi work from inside a git worktree?

**Yes.** Measured in a throwaway repo (`exp1/base` + `exp1/wt-a`, `exp1/wt-b`), never against this repository.

### 4.1 `speckiwi init` inside a worktree: works, exit 0, correct warning

`.git` in the worktree was a file:

```
gitdir: .../exp1/base/.git/worktrees/wt-b
```

`speckiwi init` exited 0 and emitted:

```
"Detected a git worktree or submodule (.git is a file, not a directory); skipped installing the
 pre-commit hook. Run speckiwi init in the main working tree to install the shared pre-commit hook."
```

The historical ENOTDIR crash is fixed. **The warning is also not a functional gap**, which I verified separately:

```
$ git rev-parse --git-path hooks        # run inside wt-b
.../exp1/base/.git/hooks
```

Worktrees share the main repository's `hooks` directory. So a worktree agent *does* get the SRS pre-commit gate, provided the main tree ran `init` once. Skipping the install is correct behaviour, not a degradation.

### 4.2 Read and mutation commands work from a worktree

```
$ cd wt-a && speckiwi validate --json
{"diagnostics":[],"errors":[],"warnings":[],"summary":{"errors":0,"warnings":0,"byCode":{}}, ...}

$ speckiwi active-target --json
{"activeTarget":"", ...}          # correct: this worktree's own spec state

$ speckiwi add-requirement --type functional --scope ARCH --target v1.0 ...
"ok": true,  "requirementId": "FR-ARCH-001"
```

Root resolution, validation, and mutation all target the worktree. No worktree-specific failure was observed in any command run.

Incidental usability notes from the same run, both minor: `--type FR` is rejected (`Invalid requirement type`) — the enum is `functional|non_functional|…` (`src/core/types.ts:10-22`), and `--scope "Product Architecture"` is rejected in favour of the prefix `ARCH`. Neither is worktree-related.

### 4.3 The lock is per-root — no cross-worktree mutual exclusion

`src/core/mutation/srs-lock.ts:9`

```ts
export const SRS_LOCK_PATH = "kiwi/.srs.lock";
```

Root-relative. Two worktrees therefore hold two independent locks that cannot see each other. Concurrent SRS mutation across roots is unguarded — confirming `docs/research/12` §4 T5. In practice this matters less than it sounds, because the two roots write to two different files on disk; the damage surfaces at merge (§5), not at write time.

## 5. Q3 — What the agent runtime actually gives you

All measured. `isolation: "worktree"` is real and it works.

### 5.1 Shape of the worktree

| Property | Measured value |
| --- | --- |
| Location | `<repo>/.claude/worktrees/agent-<id>` — **inside** the repository working tree |
| Branch | `worktree-agent-<id>`, created fresh |
| `.git` | a **file** containing `gitdir: <repo>/.git/worktrees/agent-<id>` |
| Lock | `git worktree list` shows the running agent's worktree as `locked` |
| `git status` | **EMPTY** at start |
| `node_modules` | **absent** |
| Toolchain | `node v24.16.0`, `npm 11.5.2` reachable |
| Ignored state (`.kiwi/`, `kiwi/.status.json`, `dist/`) | **absent** |

### 5.2 Which commit, and whether it sees uncommitted work

**Created at session-start HEAD. The recorded observation is confirmed.**

Both probe worktrees came up at `86a090ded574d14f0bf4e48de969e9dcece32279` — the HEAD recorded at this session's start. The host session's HEAD had since advanced to `031c4ec` (other agents committed during the session). `git merge-base --is-ancestor HEAD 031c4ec` from inside the worktree returned `HEAD_IS_ANCESTOR_OF_031c4ec`: the worktree is strictly *behind*.

This is stronger than the original claim. A worktree agent does not see uncommitted work **and does not see work committed during the session either**. Two agents spawned hours apart in the same session both land on the same stale commit. (The pre-existing worktrees on disk confirm this is per-session: worktrees from an earlier session sit at `af4e623`, that session's start HEAD.)

Practical consequence for an orchestrator: **you cannot chain worktree agents.** Task B spawned after Task A merged will not see A's work. Any sequential dependency must be handled by the orchestrator passing content explicitly, or by not using worktree isolation for dependent tasks.

> **Correction — the chaining conclusion above was withdrawn by charter C3 (`00.charter.md:145-160`).** The measurement stands: a worktree's *default* HEAD is the session-start commit and sees neither uncommitted work nor commits made later in the session. The conclusion drawn from it — "you cannot chain worktree agents" — does not follow, because a worktree shares the repository object database and **can** be moved to any *committed* sha by an explicit checkout. What is broken is a design that relies on the **default HEAD** to carry a predecessor's output, or that passes **uncommitted** work between agents. Read the paragraph above as scoped to the default HEAD.

### 5.3 MCP inside a worktree agent — the load-bearing measurement

A worktree agent called `mcp__speckiwi__mcp_workspace_info` and compared:

```
git rev-parse --show-toplevel : C:/Work/git/_Snoworca/speckiwi/.claude/worktrees/agent-a93b887a3e27e11a8
MCP workspaceRoot             : C:\Work\git\_Snoworca\speckiwi
rootSource                    : server-cwd-discovery
```

Different directories, not merely different separators. **Subagents share the parent session's MCP connection, so every worktree agent's SRS reads and writes land in the host repository while its files and git land in the worktree.** This is the §3.1 constraint, now automatic and unavoidable for the runtime's own isolation feature.

It also means a worktree agent that invokes `kiwi-wave-master` halts immediately at the `FR-FLOW-042` preflight — correctly.

### 5.4 How results get back, and lifecycle

- The agent's final text is returned to the caller. There is no automatic merge.
- The worktree and its branch **persist on disk** after the agent finishes if it changed anything: my first probe wrote `WT_PROBE_SENTINEL.txt`, and both worktree and branch were still present afterwards.
- If the agent changed nothing, the worktree is **auto-removed**: my second probe wrote nothing, and `agent-a93b887a3e27e11a8` was already gone when I went to clean it up (`fatal: … is not a working tree`). This confirms the documented "auto-cleaned if unchanged" behaviour.
- So the caller's integration path is: `git merge worktree-agent-<id>` (or cherry-pick / diff), then `git worktree remove` + `git branch -D`.
- `.claude/worktrees/` is kept out of `git status` by `.git/info/exclude` under a `# claude-code-runtime` marker — a **local, unshared** file maintained by the harness. Git does **not** auto-ignore nested worktrees; I verified this by adding one manually and getting `?? nested-wt/`. So the exclusion is load-bearing, and a `git add -A` in a checkout lacking that entry would try to stage other agents' worktrees.
- `vitest.config.ts:27-30` excludes `**/.claude/worktrees/**` for the same reason — otherwise a full test run picks up every agent worktree's copy of the suite and reports another agent's in-flight probe as a local failure.

### 5.5 Conflicting concurrent writes

There is no cross-agent write coordination at the runtime level. Each worktree is a separate checkout on a separate branch; concurrent writes to the same path in different worktrees simply produce divergent branches, and the conflict surfaces at merge. That is §6's subject.

### 5.6 One unexplained observation

Every worktree on disk — all six, created across two sessions — contains two identically named empty directories, `speckiwi-cli-init-XDYAmG/docs` and `speckiwi-cli-init-u7wHBZ/docs`. They are invisible to `git status` (git does not track empty directories) and absent from the main checkout. Identical random suffixes across independently created worktrees cannot be produced by independent `mkdtemp` calls (`test/cli/mutation-commands.test.ts:606`), and their mtimes precede their containing worktree's creation time. I could not determine the mechanism. **What would settle it:** create a worktree while watching the main checkout for those paths, or instrument worktree creation to log whether it copies untracked working-tree content. It is harmless as observed (empty directories), but it means a worktree is not provably a pristine checkout of its commit.

## 6. Q4 — Real constraints on merging N parallel branches

Measured against this repository's actual structure, and reproduced in the throwaway repo.

### 6.1 Class A — Safe to parallelize: disjoint code and tests

`src/core/**`, `src/cli/commands/*` bodies, individual `test/**` files, individual `docs/**` documents. Different files, ordinary three-way merge. No special handling.

### 6.2 Class B — Loud conflicts: shared registries and same-document appends

These conflict textually, so they are *safe* (nothing is silently lost) but they cost a manual resolution per task pair.

| Surface | Why it collides |
| --- | --- |
| `src/cli/index.ts:44-49` | Six `registerXCommands(command, { io })` calls; a new command group appends here |
| `src/cli/commands/{read,mutations,repair,skills,doctor}.ts` | Every new CLI command appends into one of five files |
| `src/mcp/tools/{read-tools,mutation-tools}.ts` | Same shape for MCP tools |
| A single `docs/spec/NN.*.srs.md` | Requirement blocks append at the document tail — **verified**: two branches adding to the same scope doc produced `CONFLICT (content) in docs/spec/01.product-architecture.srs.md` |
| `docs/spec/91.completed-work-log.md`, `kiwi/pipeline.jsonl` | Append-only journals; parallel appends collide at the tail |
| `package.json` version | Every release-shaped task edits the same line |

Mitigation is scheduling, not tooling: assign at most one parallel task per registry file and per scope document.

### 6.3 Class C — Silent semantic corruption: index rollups (detectable and repairable)

**Verified.** Two branches each added one requirement, to *different* scope documents. `docs/spec/00.index.md` **auto-merged cleanly** — and the result was wrong:

```
## 5. Status Summary          -> | planned | 2 |     (actual requirement count: 3)
## 6. Requirement Type Summary-> | functional | FR | 2 |
```

Git merged two independent `0 → 1` increments into `2`. No conflict, no warning from git.

This class is **not a blocker**, because SpecKiwi detects and repairs it:

```
$ speckiwi validate --json
SRS-W019  Status Summary count drift for planned          expectedCount:2 actualCount:3
SRS-W020  Requirement Type Summary count drift for functional  expectedCount:2 actualCount:3

$ speckiwi sync-index --dry-run --json
"| planned | 2 |"        -> "| planned | 3 |"
"| functional | FR | 2 |" -> "| functional | FR | 3 |"
```

**Required merge-time step:** run `speckiwi validate` then `speckiwi sync-index` after integrating parallel branches. Skipping it leaves a wrong-but-plausible index.

### 6.4 Class D — Genuinely non-parallelizable: Requirement ID allocation

**Verified, deterministically.** Two sibling worktrees off the same base, each running one `add-requirement` for the same scope:

```
wt-a: ### FR-ARCH-001 — Alpha feature
wt-b: ### FR-ARCH-001 — Beta feature
```

ID allocation reads the current root's documents and takes the next free number. There is no cross-root reservation. Two roots off one base always collide. This is the same mechanism that produced the four real ID collisions catalogued in `docs/research/12` §7 (`FR-NODE-071`, `FR-FLOW-036`, `IR-CLI-071`, `FR-MCP-052`).

When the colliding requirements live in the same scope document, git conflicts and you notice. When they are engineered into different documents they would not collide by ID at all (different prefixes). The dangerous middle case is a same-prefix collision reached through documents that merge cleanly — repairable only through the `speckiwi repair requirement-id-collisions` diagnose → plan → apply workflow.

**Design conclusion: never allocate Requirement IDs in a parallel worker.** Allocate all IDs up front in the host root, then hand each worker a fixed ID.

### 6.5 Class E — Whole-tree rewrites: `speckiwi init` / skill install

Re-running `speckiwi init` in a checkout that already has skills rewrote **32** `.speckiwi-skill-install.json` files (16 skills × `.agents/` + `.claude/`). This repository additionally maintains three skill mirrors (`skills/claude` 17 entries, `skills/codex`, `skills/etc`) plus `.agents/skills` (15 entries). Any task that touches one skill must touch its mirrors.

**Never run two of these in parallel.** They are whole-tree rewrites disguised as small edits.

### 6.6 Summary taxonomy

| Class | Example | Parallel-safe? | Merge cost |
| --- | --- | --- | --- |
| A. Disjoint code/tests | `src/core/parser/*.ts`, one test file | Yes | none |
| B. Shared registry / same SRS doc | `src/cli/index.ts`, one scope doc, `91.completed-work-log.md` | Yes, ≤1 task per file | manual conflict resolution |
| C. Index rollups | `docs/spec/00.index.md` §5/§6 | Yes | mandatory `validate` + `sync-index` |
| D. Requirement ID allocation | any `add-requirement` | **No** | `repair requirement-id-collisions` |
| E. `init` / skill mirrors | 32+ files per run | **No** | intractable; serialize |

## 7. Q5 — Windows-specific hazards and the real cost per worktree

### 7.1 Path length — safe, with ~70 characters of headroom

| Measurement | Value |
| --- | --- |
| Worktree path prefix `…\.claude\worktrees\agent-<17hex>\` | 72 chars |
| Longest tracked path in repo | 108 chars (`test/fixtures/workspaces/parser-hardening-forbidden-heading-content/docs/spec/10.product-architecture.srs.md`) |
| Longest `node_modules` path | 116 chars (`node_modules/@typescript-eslint/eslint-plugin/dist/rules/prefer-optional-chain-utils/…`) |
| Worst case in a worktree | **188 chars** |
| `core.longpaths` | **unset** (system and local) — the 260-char limit applies |

188 of 260. Safe today. The margin would be consumed by a deeper repository root, a nested fixture workspace one level deeper, or a dependency with a longer path. A designer relying on this should either set `core.longpaths=true` or treat 260 as a hard budget.

### 7.2 Line endings — a live trap

`core.autocrlf = true` and there is **no `.gitattributes`** in the repository. Every checkout, including every worktree, converts LF→CRLF on the working copy. Observed repeatedly during the experiments:

```
warning: in the working copy of 'docs/spec/00.index.md', LF will be replaced by CRLF the next time Git touches it
```

Consequence for parallel merging: content generated by a tool that writes LF and content round-tripped through the working tree can differ by line ending alone, producing spurious whole-file diffs. This repository already has CRLF-specific test fixtures (`test/fixtures/workspaces/crlf-basic/`), so the parsers handle it — but a merge driver or a naive diff-based orchestrator will not.

`core.symlinks = false` as well; anything relying on symlinks will silently get a regular file.

### 7.3 `npm` / `node_modules` per worktree — cheap, with one trap

Worktrees are created **without** `node_modules`. Measured cost of installing it (warm npm cache, `--ignore-scripts`):

```
NODE_ENV=development npm ci --ignore-scripts
elapsed = 4s
119M    node_modules
7507 files
```

**The trap:** this shell session has `NODE_ENV=production`. Under it, the same command silently omits devDependencies:

```
npm ci --ignore-scripts   (NODE_ENV=production)
elapsed = 2s
23M     node_modules      3508 files
node_modules/vitest       -> No such file or directory
node_modules/typescript   -> No such file or directory
```

Exit code 0, no error. An orchestrator that installs per worktree and then runs `npm test` would get a confusing failure. **Any per-worktree install must pin `NODE_ENV`.**

### 7.4 File locking and cleanup

Worktrees are `locked` in `git worktree list` while their agent runs, so `git worktree remove` on a live one fails — cleanup must be lifecycle-aware. Windows file locking on `node_modules` during concurrent installs was not exercised here; with N parallel installs into N separate directories there is no shared target, but the npm cache is shared and I did not test concurrent cache access. **What would settle it:** run N concurrent `npm ci` into N worktrees and check for `EPERM`/`EBUSY`.

### 7.5 Practical cost of one worktree per parallel task

- Disk: ~119 MB (`node_modules`) + the checkout, per worktree.
- Time: ~4 s install with a warm cache; worktree creation itself is fast.
- Housekeeping: `git worktree remove` + `git branch -D` per task (only for tasks that changed something; unchanged ones self-clean).
- Test-run hygiene: already handled by `vitest.config.ts:30`.

For a handful of parallel tasks this is negligible. For 20+, disk becomes the binding constraint at ~2.4 GB.

## 9. Design implications

1. **Do not put SRS mutations in parallel workers.** Not because a gate forbids it, but because the MCP root is the host regardless of where the worker runs (§5.3). Let workers produce code and tests; let the host serialize all `add_requirement` / `update_status` / `add_verification_evidence` calls.
2. **Allocate every Requirement ID before fan-out** and pass it to the worker as a fixed input (§6.4).
3. **Assume workers are blind to session progress** (§5.2). Worktrees are cut at session-start HEAD. Dependent tasks cannot be parallelized by worktree; either serialize them or pass content explicitly. **[Withdrawn in part — see the §5.2 correction and charter C3 (`00.charter.md:145-160`): the default-HEAD blindness stands; the "cannot be parallelized by worktree" generalisation does not.]**
4. **Budget one shared-file owner per registry** (§6.2). `src/cli/index.ts`, each `src/cli/commands/*.ts`, each scope SRS document, and `91.completed-work-log.md` each admit at most one concurrent writer if you want to avoid manual conflict resolution.
5. **Make `validate` + `sync-index` a mandatory post-merge step** (§6.3). It is the only thing standing between a clean auto-merge and a silently wrong index.
6. **Never parallelize `speckiwi init` or skill-mirror work** (§6.5).
7. **Pin `NODE_ENV` in any per-worktree install** (§7.3).
8. `FR-FLOW-042`'s preflight gate will halt any wave-master invocation inside a worktree agent. That is correct behaviour and should not be weakened; a new orchestrator should reuse the same comparison as its own admission check rather than route around it.
