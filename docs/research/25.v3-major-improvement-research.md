## 0. 한 장 요약

**SpecKiwi 의 문제는 기능이 모자란 것이 아니다.** 14주 만에 표면이 6배로 늘었다.

| | 2026-05-15 | 2026-08-22 |
|---|---|---|
| CLI leaf 명령 | 11 | **136** |

| 스킬 | 0 | **17** (× 3 변종 = 51 `SKILL.md`) |
| 요구 | — | **568** |

같은 기간 **검증 기계는 모양이 그대로다.** 그 격차에서 나오는 결함이 한 가족을 이룬다 — **존재하지만 아무것도 증명하지 않는 검사**.

**v3.0.0 의 주제는 하나다: 도구가 자기에 대해 하는 진술을 도구가 검사하게 만든다.**

지금 동시에 참인 것들 (전부 실행으로 확인):

1. `speckiwi explain SRS-E006` 은 도구가 **거부하는** Priority 값을 안내한다 — 실제 enum 과 겹치는 값 **0**.
2. `orchestrate run lock` 은 CLI 호출 사이에 **아무것도 배제하지 않는다**. 같은 코드가 MCP 에서는 배제한다.
3. `speckiwi validate` 는 `verified` 요구의 증거가 **없는 파일을 가리켜도** 오류 0을 보고한다 — 그리고 릴리스 게이트도 **활성 타깃 밖의 427개 요구는 검사하지 않는다**.
4. 테스트 456개 중 **354개가 어떤 타입체크 게이트에도 들어가지 않고**, 165개가 **673개 오류**를 품고 있다.
5. 닫힌 게이트 어휘 68개 중 도구가 실제로 올릴 수 있는 것은 **23개(33.8%)** 다.
6. `src` 4개 파일의 NUL 바이트 때문에 **`rg` 재귀 검색이 침묵으로 실패한다** — 경고가 아니라 exit 1 + 빈 출력.

## 1. 방법과 신뢰 수준

네 축을 독립 서브에이전트로 병렬 실행하고, 종합 뒤 **다섯 번째 에이전트에게 문서를 공격하게 했다.** 검토자에게는 "모든 숫자를 스스로 재측정하되 문서의 인용을 재사용하지 말 것", "괜찮다고 적힌 목록을 가장 세게 칠 것"을 지시했다.

### 1.1 실행으로 재현된 것 (신뢰도: 최고)

| 주장 | 재현 |
|---|---|
| CLI `run lock` 이 상호배제를 하지 않는다 | 팀리드·검토자 **각각 독립 재현**. 연속 두 호출 모두 `{"ok":true}` exit 0 |
| `explain` 이 도구가 거부하는 값을 안내 | 안내 `P0,P1,P2,P3` / 실제 `critical,high,medium,low,optional` — 겹침 **0** |

### 1.2 반려·정정한 것 (총 6회)

정확성을 위해 되돌린 판정들. 여섯 번 다 서브에이전트 보고를 그대로 옮겼다면 문서에 틀린 문장이 남았다.

1. **"~26개 AC 가 `verified` 요구에서 거짓"** → 실측 **25개 중 1개**. 23개는 삽입절만 만료했고 22개는 만료를 날짜와 함께 공시하고 있었다.
2. **"`verified` 요구가 배선 안 된 게이트를 주장"** → FR-NODE-121 의 9개 AC 는 전부 함수 입출력이다. 요구는 거짓말하지 않는다.
3. **"게이트 29개를 도구가 만든다"** → 23 도달가능 + 6 도달불가로 분리. 그 구분이 핵심이었다.
4. **"호출자가 성공했다고 듣는다"** → 코드를 읽으니 **묻지를 않는다**. 또 다른 맵이 블록 진입을 막고 있었다.
5. **"`_shared` 안전 게이트가 3 대 7"** → 재현 불가. 진짜 격차는 더 크다(§2.4).
6. **"증거 참조 해석은 릴리스 게이트가 강제한다"** → **거짓**. 타깃 스코프다(§3.1).

## 2. 네 주제

### 2.1 도구가 자기에 대해 하는 진술이 틀렸다

모든 사례가 한 원인을 공유한다: **문자열이 자기가 서술하는 대상에서 유도되지 않고 손으로 다시 쓰였다.**

**진단 remediation 이 거부되는 값을 안내한다.** 84개 진단 코드 전부가 remediation 을 갖는 것은 강점이다. 그런데 enum 을 나열하는 넷 중 셋이 틀렸다 — Priority 는 겹침 0, Status 는 `draft`(Stability 값)를 넣고 `planned` 를 빠뜨리며, Risk 는 `critical` 을 빠뜨린다. **가장 흔한 두 메타데이터 오류에서 안내를 따르면 같은 오류가 재현된다.**

그리고 유도할 대상이 이미 있다: `src/core/schema.ts` 의 `isPriority`·`isRisk`·`isStability` 는 **호출자가 아무 데도 없다.**

**명령 카탈로그가 MCP 레지스트리에서 렌더된다.** `speckiwi commands --json` 은 149행 = `toolSpecs.length` 로, **commander 트리(136 leaf)가 아니라 MCP 레지스트리**에서 나온다. 이 한 문장이 모든 증상을 설명한다 — 행에 경로가 없고(`plan` ×5, `validate` ×4, `check` ×4 중복), 일부 leaf 가 빠지고, **`kind:"read"` 인데 `readOnly:false` 인 행이 30개**(`explain`·`history`·`scopes`·`commands` 자신 포함). 경로가 없으니 정확한 대조 자체가 불가능하다 — 그 불가능성이 곧 발견이다.

**설계 계약이 6배 낡았다.** `test/mcp/schemas.fr-arch-006.test.ts` 는 아직 *"사용자 확인된 설계 계약: 전체 CLI 명령 집합(현재 23개), MCP 부분집합은 17개 유지"* 라고 적고 있다.

**복구 힌트가 실패한 명령과 무관하다.** 오케스트레이터 verb 에 `--lane` 을 빠뜨리면 *"유효한 필터로 requirements 를 나열한 뒤 read 명령을 재시도하라"* 는 답이 온다. `explain` 의 enum 오류보다 나쁘다 — **사람이 읽는 게 아니라 에이전트가 소비한다.**

**실패 봉투가 세 모양이다.** 맨 문자열, 구조체+복구, 구조체+**틀린** 복구.

**`--json` 이 exit code 를 바꾼다.** 미초기화 프로젝트에서 human=2 / json=4. README 는 2를 "사용법 오류"로 문서화하고 `--bogus-flag` 도 2다. 그리고 `classifyUnhandledError` 가 `if (jsonMode(...))` **안에** 있어 사람은 절대경로가 박힌 raw errno 를, 기계는 `"recovery":{"command":"init"}` 를 받는다. 신규 소비자가 처음 만나는 화면이고 하필 `doctor` 가 낸다.

**38개 AC 가 같은 인과 전제를 진술하는데 작성 시점부터 거짓이다.** *"charter 가 이 저장소에 대한 재설치를 금지하므로"* — 실제 금지는 **target root** 로 삼는 것에 한정이고, **source** 로 `--dest` 설치는 범위 밖이며 수행됐다. 저장소가 자기를 그 자리에서 반박한다: FR-FLOW-074 **AC-7 이 그 전제를 진술하고, 같은 요구의 VE-3 이 그것을 부정한다.**

> **원칙: 값 집합·개수·호출자·복구 경로를 지목하는 모든 문자열은 그 대상에서 유도되거나 기계적으로 대조되어야 한다.**

### 2.2 발화할 수 없는 가드

**게이트 68개 중 도구가 도달 가능한 경로에서 올리는 것은 23개(33.8%)다.**

| 계층 | 개수 | |
|---|---|---|
| 1. 도구가 도달 가능한 경로에서 만든다 | **23** | 33.8% |
| 2. 생성 함수는 있으나 `src/` 의 무엇도 도달하지 않는다 | 6 | 8.8% |
| 3. `src/` 에 코드 출현 없음 — 어휘 전용 | 39 | 57.4% |

계층 3 은 설계다(에이전트가 올리고 도구가 멤버십만 검증). **문제는 그 구분이 어디에도 없다는 것** — `refuse()` 가 맨 문자열을 거부하는 것은 *어휘* 강제이지 *배선* 강제가 아닌데 배선처럼 읽힌다.

**계층 2 의 여섯이 전부 같은 모양이고**, 그 뒤에 더 큰 사실이 있다. `export function` 440개 중 101개가 다른 `src` 파일에서 참조되지 않는데, 이 숫자를 쪼개면 훨씬 날카롭다:

- **60개는 테스트가 참조한다** — 단위 테스트는 있고 호출자는 없다. **이것이 위험한 계층이다.**
- 41개는 테스트도 참조하지 않는다. 진짜 죽은 표면. `assertVerifiedGuard` 가 여기 있다.

**그리고 이 결함은 모듈 단위 아래에 숨는다.** `src` 의 다른 모듈이 import 하지 않는 모듈은 13개, 재-export shim 둘과 패키지 진입점 `src/index.ts` 를 빼면 **10개**다. 그중 셋이 657줄을 차지한다 — `merge-journal.ts` 275, `unit-gate.ts` 243, `allocation.ts` 139, 심볼 단위 확인.

**그런데 `prose-gate.ts` 는 그 목록에 없다.** `handoff.ts:12` 가 `maskExcludedConstructs`·`maskFencedBlocks` 를 import 해 4곳에서 쓴다. 모듈은 살아 있고 **게이트 함수만 썩었다** — `scanProse` 호출자 0, `countNormativeTokens` 는 `scanProse` 만 부른다.

**모듈 단위 전수조사였다면 `prose-gate.ts` 를 건강하다고 채점하고, 이 문서에서 가장 많이 인용되는 미배선 게이트를 놓쳤을 것이다** — 자기 파일 첫 줄에 *"**Not wired.**"* 라고 적혀 있고 요구가 `verified` 인 바로 그것을. 심볼 단위 도달성이 필요하다는 논거를 주장이 아니라 데이터가 만든다.

**요구는 거짓말하지 않는다** — FR-NODE-121 의 9개 AC 는 전부 함수 입출력이다. 문제는:

> **요구 집합에 "게이트에는 호출자가 있어야 한다"고 말하는 요구가 없다.**

부분은 전부 verified 인데 전체가 발화 불가다. 커밋 `e118c030` 이 이미 그 수업료를 기록했다: *"순수 모듈의 단위 테스트는 함수가 계산한다는 것을 증명하지, 게이트가 존재한다는 것을 증명하지 못한다."*

**run lock 이 CLI 호출 사이에 아무것도 배제하지 않는다.** sentinel 에 `process.pid` 를 찍고 CLI 는 곧 종료하며, 다음 획득자는 pid 가 죽었으니 stale 로 회수한다.

MCP 에서는 배제된다. **기전은 한 줄로 확인된다** — `src/mcp/tools/read-tools.ts:156` 이 `await import("../../cli/index.js")` 로 CLI 를 **장수 서버 프로세스 안에서** 실행한다. 구현이 같은 정도가 아니라 **호출이 같고 프로세스 소유자만 다르다.** *"구현이 하나라 두 표면이 갈릴 수 없다"* 는 주장이 그래서 거짓이다.

스킬은 이 락을 critical 게이트로 의무화하면서 **명령도 도구도 지정하지 않는다**(세 변종 전부 검색 0건). 전송이 환경에 좌우되고 두 전송의 의미가 반대다. 스킬은 이걸 **lease** 라고 부르는데 구현은 pid 생존만 표현한다.

**해제가 프로세스를 넘으면 조용히 no-op 이 된다.** 모듈 맵에 capability 가 없으면 `{ok:true, released:false}` — **`ok: true`** 다. 다섯 곳이 같은 모양이고 이번에 `run-lock` 한 곳만 닫혔다.

가장 날카로운 형제는 **retained-cleanup 재시도**다. 그 테스트 이름이 스스로 `same-process` 라고 말하고, `:223` 이 `{ok:true, released:false, reason:"not_found"}` 를 **정답으로 고정**한다.

이 절의 초판 결론은 과했고, 끝까지 실행해서 정정했다. 기전은 맞다 — 관련 맵이 셋인데(`retainedCleanup`, `retainedJsonlCleanup`, `retainedReclassificationCleanup`) **하나도 export 되지 않고, 모든 쓰기가 방금 해제에 실패한 그 함수 안에 있으며, 디스크에서 되살리는 경로가 없다.** 새 프로세스에서 바깥 맵이 비어 `if (retained)` 블록에 **진입조차 하지 않는다.** 호출자가 성공했다고 *듣는* 게 아니라 *묻지 않는다*.

**그러나 결과는 초판이 말한 것과 다르다.** 시나리오 전체를 돌린 결과: 자식이 락을 잡고 해제 없이 종료 → sentinel 이 죽은 pid 를 달고 디스크에 남음 → 새 프로세스에서 재시도는 `not_found`, **그런데 그 뒤 `acquireArtifactLock` 이 성공한다.** 평범한 pid-liveness 회수 경로가 같은 사례를 이미 덮는다. 에이전트는 막히지 않고 mutation 도 막히지 않는다.

**살아남는 주장은 "복구가 프로세스를 넘어 실행될 수 없다"가 아니라 "retained-cleanup 기제가 무용하다"다.** 프로세스를 넘으면 돌 수 없고, 같은 프로세스 안에서는 stale 회수가 이미 같은 일을 한다. 죽은 분기 하나와, **코드가 택하지 않는 복구 경로를 서술하는 계약** — 즉 §2.1 계열(도구의 자기 서술이 틀림)이지 §2.2 계열(락이 잠김)이 아니다. 잠긴 락으로 서술하면 실제로 돌려보는 첫 구현자에게 무너진다. 연구 18·19 가 그렇게 틀렸다.

**그리고 이 계층에서 게이트보다 무거운 것이 하나 나왔다.** `src/core/patch/merge-journal.ts` — 275줄, import 되지 않는 모듈 중 최대 — 은 **다중 파일 커밋의 크래시 복구**를 구현한다. `readMergeJournal`·`recoverMerge` 는 다른 `src` 모듈에서 참조 0이고 테스트 두 개만 부른다. 요구 문서를 쓰는 엔진의 복구 경로가 "테스트는 있고 호출자는 없다" 계층에 있다. 그리고 겹친다 — `src/core/patch/**` 는 **커버리지 임계값 밖 46개 파일 중 하나**라, 호출자 검사도 커버리지 게이트도 이걸 보고 있지 않다.

발화하지 못하는 게이트는 아무것도 거절하지 않을 뿐이다. 아무도 부르지 않는 복구 저널은 다중 파일 커밋 중 크래시가 SRS 를 반쯤 쓴 채 남긴다는 뜻일 수 있다. **"일 수 있다"로 적는다** — 확인한 것은 *production 호출자가 없다*이고, 쓰기 경로가 다른 기전으로 원자적일 가능성은 배제하지 않았다.

> **원칙: 게이트는 함수가 아니라 호출자로 정의된다.**

### 2.3 아무것도 증명하지 않는 검사 — 그리고 잘못된 분모

568개 요구 중 36개가 자기 증거의 공허성을 기록하고 있다(정밀 계수는 검출기 의존적, 방향은 확실). **무엇이 잡았나**: 뮤테이션 탐침과 독립 감사. 리뷰 라운드나 스위트 실행이 잡은 사례는 사실상 없다.

**분모가 틀린 게이트가 최소 셋이다.** 이것이 이 주제의 핵심이고, 초판이 놓친 축이다.

- **증거 참조 해석**: 워크스페이스 전체를 도는 함수가 있지만, 유일한 production 호출자가 **활성 타깃으로 먼저 좁힌다**(`release-readiness.ts:668`). 활성 타깃은 568개 중 **2개**를 담는다. **타깃 밖 427개 `verified` 요구의 증거 경로는 아무도 검사하지 않는다** — `validate` 도, 릴리스 게이트도. 저장소가 이미 이걸 기록했다(FR-FLOW-025 VE-4): *"릴리스 준비 검사가 타깃 스코프이고 이 요구는 다른 타깃에 속해 첫 패스가 놓쳤다."*
- **스킬 mirror**: `.agents/skills` 를 `skills/codex` 와만 비교한다. claude 와 etc 는 **무엇과도 대조되지 않는다.**
- **citation parity**: 세 스킬 트리만 읽고 README·`AGENTS.md`·`CLAUDE.md` 는 열지 않는다.

**CI 는 `ubuntu-latest` 단일 잡이다.** `process.platform === "win32"` 분기가 **한 번도 실행되지 않는다** — Windows 커널 fence 포함. symlink 치환 **거부** 케이스 2개는 로컬에서 EPERM 으로 skip 된다. 보안 가드 셋이 어느 실행에서도 시험되지 않는다.

**조용한 커버리지 소실을 소실 순간에 보고한 자동 검사는 0건이다.** 이번 세션 실물 확인: candidate 파일명에 접미사를 붙이자 두 테스트의 리터럴 경로 단언이 **존재할 수 없는 경로**를 보게 되어 항진명제가 됐고, 정리 코드를 지워도 세 파일이 green 이었다.

**검증 도구 자체가 고장난 사례 8건**이 기록돼 있고, 이번 세션의 뮤테이션 하네스가 아홉 번째였다 — **무변경 통제군이 아니었으면 그대로 SRS 증거가 됐다.**

**NUL 바이트가 grep 전수조사를 눈멀게 한다.** 고의이고 의미상 대체 가능한 `join("\0")` 이지만, `rg` **재귀** 검색은 경고 없이 **exit 1 + 빈 출력**을 낸다. 감사자가 실제로 치는 형태가 그것이다.

> **원칙: 검사는 "존재하는가"가 아니라 "어떤 집합 위에서 도는가"로 평가한다.**

## 4. v3.0.0 제안

### V1. 유도된 진술 (§2.1)

- remediation 의 enum 나열을 상수에서 생성한다. **`isPriority`·`isRisk`·`isStability` 가 이미 있고 호출자가 없다.**
- **`commands --json` 을 commander 트리에서 렌더한다.** 지금은 MCP 레지스트리에서 나온다 — 이 한 줄이 경로 부재·중복·`readOnly` 오표시를 전부 설명한다.
- 복구 힌트를 실패한 명령에서 유도하고, 힌트가 지목한 명령이 거기서 도달 가능한지 테스트가 강제한다.
- 실패 봉투를 한 모양으로. exit code 를 `--json` 과 독립시키고 복구 힌트를 두 모드 모두에.
- AC 본문에 검증 불가능한 현재형 관찰을 금지한다. 관찰은 증거 노트로, 기준은 시간 불변으로.

### V2. 호출자로 정의되는 게이트 (§2.2)

- **어휘를 분할하고, 그 분할을 기계가 검사하게 한다.** 초판은 "게이트에는 호출자가 있어야 한다"는 요구를 추가하자고 했다. 그건 처방이 병의 사례가 되는 길이다 — §2.2 의 논지가 *부분은 전부 verified 인데 전체가 발화 못 한다*인데, 아무것도 실행하지 않는 산문을 하나 더 얹는 것이기 때문이다. 게다가 **소박하게 쓰면 거짓이다**: 68개 중 39개(57%)가 의도적으로 에이전트가 올리는 것이라 "모든 게이트는 호출자를 갖는다"는 다수에 대해 틀리고, 예외를 산문으로 달아야 한다. `_shared` 게이트 목록이 세 갈래로 갈린 경로가 정확히 그것이다.

  없는 것은 **분할이고, 분할은 데이터다.** `GATE_IDS` 를 `TOOL_RAISED` 와 `AGENT_RAISED` 로 나눠 export 하고, 전자는 도달 가능한 생성 지점이 있어야 하며 후자는 없어야 한다고 기계가 단언한다. 오늘 값은 이미 측정돼 있다 — 23 과 39, 그리고 **6이 green 이 되기 전에 해소해야 할 실패 집합**이다.

  둘 곳과 선례도 있다. `doc-lint.rel-flow-003` 과 `skill-citation-parity.fr-node-128` 은 실제 트리를 프로세스 안에서 만들어 대조하고, §3 이 이 저장소에서 가장 강한 기계 가드로 꼽은 것이 그 둘이다. 같은 기법을 `GATE_IDS` 로 겨눈다. **단 `release:check` 의 기존 진단이 타깃 스코프이므로, 도달성 검사는 워크스페이스 전체로 써야 §3.1 의 버그를 물려받지 않는다.**

  워크플로 규칙상 요구는 여전히 하나 필요하다. **요구를 게이트들에 대해 쓰지 말고 기제에 대해 쓴다** — 요구가 검사와 분할을 의무화하고, 검사가 속성을 강제한다. FR-NODE-128 과 REL-FLOW-003 이 정확히 그렇게 쓰여 있고, 이 저장소에서 무언가를 실제로 잡은 실적이 있는 가드는 그 둘뿐이다.

  **그리고 그 요구의 AC 는 뮤테이션 증명을 달아야 한다.** 도달성 검사는 자기 오탐 표면을 갖는다 — 검토자가 이 계수를 29/0 → 26/3 → 23/6 으로 세 번 만에 맞췄고, 모듈 상수 운반과 심볼 단위 도달성을 제대로 다룬 것은 세 번째뿐이었다. 살아 있는 게이트의 배선을 끊어 그 id 를 지목하는 red 를 보고, 어휘 전용 게이트에 호출자를 붙여 그 id 를 지목하는 red 를 보고, 복원해 green 을 본다. 그게 없으면 이 검사는 **테스트가 있고 아무것도 증명하지 않는 60개 함수**에 합류한다.
- **run lock 의 주어를 먼저 정한다 — run 인가 프로세스인가.** 초판은 "만료 기반 lease" 를 제안했는데 **두 가지가 틀렸다**:
  - **`verified` FR-NODE-131 AC-4 와 충돌한다** — *"pid 가 살아 있는 sentinel 은 회수 불가"*. 진짜 lease 는 기한이 지나면 살아 있는 보유자에게서도 회수하므로 이 기준이 거짓이 된다. supersede 가 필요하고 초판은 그걸 말하지 않았다.
  - **보고된 결함을 고치지도 못한다.** 결함은 보유자가 이미 죽은 순차 호출이다. TTL 을 더하면 "아무것도 배제 안 함"이 "TTL 동안 정당한 순차 호출을 전부 배제함"으로 바뀔 뿐이다.
  - 가용한 형태는 **run 정체성에 대한 파일 권위**다. `run unlock` 이 이미 외부 프로세스에서 파일 권위로 동작한다. 만료는 liveness 백스톱으로만.
- 프로세스 경계를 넘는 해제를 파일 권위로. **"내 것이 아님"은 `ok: true` 가 아니어야 한다.**
- `verified` 의 의미를 validator·쓰기 경로·릴리스 게이트에서 하나로.

### V3. 값을 증명하는 검사 — 그리고 올바른 분모 (§2.3)

- **증거 참조 해석을 워크스페이스 전체로 넓힌다.** 한 줄(좁힌 `records` 를 쓰지 않는다)이고 파급이 크다. 지금 427개가 무검사다.
- **모든 기계 가드의 분모를 감사한다.** mirror(3 중 1), citation parity(스킬만), 증거 해석(타깃만) — 셋이 나왔으니 더 있을 것이다.
- **타입체크 include 확대.** 단 **FR-NODE-164 AC-1 이 그 목록을 문자 그대로 고정하고, 같은 요구의 Implementation Notes 가 이 확대를 *가격 매겨 기각*했다** — *"`test/**` 는 153 파일 577건이고 이건 교정 물결이지 이 타깃의 일이 아니다."* supersede 와 범위 결정이 필요하지 설정 편집이 아니다. **더 나은 논거는 절대 수치가 아니라 추세다**: 2026-08-02 에 577/153 이던 것이 20일 만에 **673/165** 다. 그 요구 자신의 2/47 실결함 비율을 적용하면 대략 **29건**이 진짜다.
- **vitest `typecheck` 블록을 켠다.** 지금 `expectTypeOf` 13개가 no-op 이고, 두 파일 다 typecheck include 밖이라 **양쪽 어디서도 검사되지 않는다.**
- **CI 에 Windows 잡을 추가한다.**
- **뮤테이션 통제군을 하네스의 의무로.** 무변경 통제군이 SURVIVED 가 아니면 판정 대신 UNUSABLE.
- 수명 의존 가드에 **순차 시나리오**(획득 → 종료 없이 해제 → 재획득)를 의무화한다.

  > **프로세스를 띄우는 것은 시험 대상이 아니다. 프로세스보다 오래 사는 것이 시험 대상이다.**

  비율("6개 중 2개")은 무엇을 수명 의존으로 셀지에 좌우되므로 쓰지 않는다. 검증 가능한 형태는 이것이다 — **run lock 의 실패 순열을 조립하는 테스트가 어디에도 없다.** `run-lock.fr-node-102` 의 네 케이스는 전부 동시 시나리오(살아 있는 두 번째 프로세스, 또는 경쟁하는 두 워크트리)다. `run-lock.fr-node-131` AC-4 는 죽은 pid sentinel 을 심고 회수 가능함을 단언한다 — **CLI 결함을 만드는 바로 그 규칙**. AC-5 는 해제 → 획득을 시험하되 **깨끗한 해제**로 한다. 스위트는 양쪽 절반을 각각 증명하고, "획득 → 해제 없이 종료 → 재획득"으로 **조립하지 않는다.** CLI 가 가진 유일한 수명이 그것인데.

  이 한 문단이 왜 완전히 green 인 스위트와 아무것도 배제하지 않는 락이 공존하는지를 설명한다.
- NUL 리터럴을 이스케이프로. 5줄, 의미 동일, 저장소 전체 검색 신뢰도 회복.
- `no-unreachable` 을 켠다 — 단 **지금 위반은 0건**이다(초판의 "2건"은 틀렸다). 잠재 공백이지 현행 결함이 아니다. `off` 는 저장소 선택이 아니라 `@typescript-eslint/recommended` 상속이다. `noUnusedLocals` 는 lint 가 이미 `--max-warnings=0` 으로 덮으므로 **불필요하다.**

### V4. 기계가 강제하는 단일성 (§2.4)

## 5. 다섯 번째 축이라면 봤을 것

네 축의 브리프가 고정돼 있었으므로 사각지대는 구조적이다. 둘은 문서 안의 어떤 것보다 클 수 있다.

**a. 보안과 적대적 입력 — 아무도 안 봤고 가장 큰 구멍이다.** 도구는 `git` 과 Node 자식을 띄우고, 사용자가 준 `--root` 를 받고, symlink 를 해석하고, **신뢰할 수 없는 Markdown 과 JSONL 을 파싱한다.** `safe-path.ts`·`isUnderRoot`·`realPathIfExists` 가 있으니 누군가 한 번은 생각했다. 그러나 **적대적 SRS 문서, 적대적 `waves.jsonl`, symlink 된 `docs/spec` 이 패치 엔진에 무엇을 하는지** 아무 축도 묻지 않았다. mutation 경로의 traversal 이나 symlink 탈출은 §2 의 어떤 결함보다 나쁘다. 그리고 §2.3 이 지적했듯 **그걸 시험하는 두 케이스는 로컬에서 skip 되고 CI 에서는 실행조차 안 된다.**

**b. 커버리지 제외 목록의 내용.** 초판은 "46 파일 / 9,433줄"을 맨 숫자로 적었다. 그 46개에는 `src/core/patch/**`(요구 문서를 편집하는 엔진), `exclusive-lock.ts`(§2.2 전체의 주제), `init-project.ts`(`--force` 가 요구를 파괴할 때 쓰는 것), `install-skill.ts`, `doctor.ts` 가 들어 있다. **§2.2 와 §2.5 가 가장 위험하다고 지목한 하위 시스템이 정확히 커버리지 바닥이 없는 것들이다.** 이미 수집한 데이터 안에 있었고 질문 하나가 모자랐다.

**c. 가드의 *범위* — §3.1 이 속한 계층.** 모든 축이 "가드가 있는가"를 물었고 **"어떤 집합 위에서 도는가"** 는 아무도 묻지 않았다. 셋이 이미 나왔다. 싸고 더 나올 것이다.

**d. 소비자 업그레이드와 호환성.** 14주에 11→136인데 유일한 명시 계약이 23이다. 2.3.x 에 고정된 소비자가 `speckiwi upgrade` 에서 무엇을 겪는지, 번들 규칙 버전이 설치된 SRS 와 대조되는지, `MIG-*` 가 그 델타를 덮는지 아무도 안 물었다. **외부 가시 위험이 가장 큰 축이고, "실제 프로젝트 사용에서 발견된 도구 개선"이라는 헌장이 가장 직접적으로 함의하는 축이다.**

**e. 스킬이 실제로 작동하는가.** 네 축 전부 스킬을 **문서로** 읽었다 — 바이트, 인용, 분기, 게이트 목록. **아무도 하나를 끝까지 실행하지 않았다.** 27개 도구 중 5개만 인용하는 124,963 바이트 스킬은 어떤 정적 검사도 닿지 않는 방식으로 망가져 있을 수 있고, 세 변종이 **물질적으로 다른 안전 지시**를 준다는 것이 이미 확인됐다.

**f. 명령당 지연.** 에이전트는 과제당 수십 번 호출한다. `50.nodejs-implementation.srs.md` 하나가 1.0MB 이고 거의 모든 읽기에서 파싱된다. `perf:srs` 는 파서를 고립해 재고, **CLI 왕복은 아무것도 재지 않는다.**
