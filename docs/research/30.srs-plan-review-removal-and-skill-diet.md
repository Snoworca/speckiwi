## 0. 한 장 요약

**제안 ① 은 방향이 맞다. 단 "구현하는 쪽이 SRS 를 고친다"는 부분에 장치 세 개가 없으면 SRS 가 코드를 따라가는 문서로 바뀐다.**

1. **SRS·계획의 다중 라운드 LLM 검증은 걷어낼 근거가 충분하다.** 저장소 기록에서 요구 결함은 대부분 구현 단계에서 드러났고(구현자가 잡은 요구 결함 8건, 스위트가 잡은 verified 요구 간 모순 2건, 3라운드 검토를 거친 계획 3.0 의 실행 중 오류 반복), 외부에서도 명세를 다중 라운드 LLM 리뷰로 검증하는 SDD 도구는 없다. BMAD 는 2026년에 PRD 적대 리뷰어와 별도 준비도 검사를 오히려 걷어냈다. LLM 의 요구사항 리뷰는 전문가가 찾은 문제의 중앙값 47%만 잡고 필요성·정확성 문제는 거의 놓친다는 벤치마크도 있다.
2. **"0" 이 아니라 "결정적 검사 + 충돌면 조회" 는 남긴다.** SRS 한 라운드 독해가 HIGH 를 잡은 기록, 계획 검토가 빌드 파손과 되돌리기 명령 삭제를 잡은 기록이 있다. 이것들은 대부분 결정적 검사(`speckiwi validate`, `validator.mjs`)나 "이 경로를 이미 못박는 verified 요구는 무엇인가" 한 번의 조회로 대체할 수 있는 종류였다.
3. **"도중에 고쳐 가며"에는 장치 셋이 필요하다.** (a) 고치는 방향의 제한 — SRS 가 세계에 대해 틀렸을 때(FR-FLOW-139 의 충돌 세 종류)만 고치고, 코드와 다르다는 이유로는 고치지 않는다. (b) 약화 변경의 분리 — AC 삭제·완화는 따로 표시되어 코드 리뷰어가 **사용자 원문 요청**을 기준으로 판정한다. (c) 변경 기록의 기계화 — AC 교체 도구가 Change Notes 를 스스로 남긴다(지금은 남기지 않는다). 외부 근거: 명세와 테스트가 충돌하면 최신 모델은 테스트를 고치거나 우회한다(ImpossibleBench, ICLR 2026).
4. **현재 스킬은 제안과 반대로 짜여 있다.** 코드 리뷰(`kiwi-review-fix-loop`)는 SRS 를 리뷰도 수정도 못 하고(FR-FLOW-152/153), 리뷰어 입력에 AC 본문이 없다. 계획 작성자는 SRS mutation 이 두 종, 코더는 네 종뿐이라 요구 본문을 고칠 수 없다. "요구는 틀릴 수 있다"는 지시(FR-FLOW-139)는 `kiwi-coder` 한 곳에만 있고, 누가 고치는지는 어디에도 없다.
5. **스킬 다이어트의 첫 걸림돌은 텍스트가 아니라 텍스트의 양을 잠그는 계약 테스트다.** 복제본에서 절 13개를 지워 보니 10개가 테스트를 깼다. 하한(`VALUE_FLOOR`, `CITATION_FLOOR`), byte-exact golden, "orchestrator 에 `references/` 금지" 단언이 양 자체를 잠근다. 이것을 "정합성" 단언으로 바꾸는 작업이 모든 다이어트의 선행 조건이다.
6. **하네스 무용론이 겨냥하는 것은 하네스 전체가 아니라 모델 보정 문구와 절차 서술이다.** 명세·진행 기록·독립 평가자·결정적 검사는 무용론 쪽도 걷어내지 않는다. "SDD 유지, 스킬 다이어트"는 외부 흐름과 맞는다. Claude Code 는 컴팩션 뒤 스킬마다 **앞 5,000 토큰만** 다시 붙이므로, 불변식은 스킬 맨 앞에 두어야 긴 세션에서 살아남는다.

### 1.3 정책 문언의 해석 문제

저장소 `CLAUDE.md` 의 검증 강도 정책은 "code, contracts, **SRS acceptance criteria**, and safety boundaries keep the full policy (TDD, per-AC mutation proof, CRITICAL=0 and HIGH=0, subagent verification)" 라고 적는다. 이 문언은 "AC 텍스트 자체를 다중 검증한다"로도, "구현이 AC 를 만족하는지 검증한다"로도 읽힌다. 2026-08-17 이후 한 핸드오프는 앞의 뜻으로 읽고 SRS 품질 관점 제거를 보류했다. 제안을 받아들이려면 이 문장을 뒤의 뜻으로 명시해야 한다 — "AC 에 대한 full policy 는 구현 대 AC 검증에 적용되고, AC 문장 자체의 LLM 리뷰에는 적용되지 않는다."

## 2. 근거 — 찬성과 반대

### 2.1 찬성 근거

**저장소 기록**
- 요구 결함 8 건(주입 지점 수 오류, 본문↔AC 모순, `append-only` 와 `prune` 의 문자 그대로 모순 등)을 전부 구현자가 잡았다. FR-FLOW-139 의 "요구는 틀릴 수 있다" 지시를 브리프에 넣은 결과다(FR-FLOW-139 Change Notes).
- FR-NODE-193 ↔ verified FR-NODE-021, FR-FLOW-150 ↔ verified FR-FLOW-084 AC-3 의 모순은 구현 뒤 스위트가 잡았다.
- 계획 3.0 은 작성 때 3 라운드 적대 검토를 거쳤는데도 실행 중 계획 오류가 반복해서 나왔다("the plan was wrong about it twice", 계획이 지목한 세 곳이 이미 정리됨 등, `docs/spec/91.completed-work-log.md`).
- FR-FLOW-022 AC-2 누락은 3 라운드 review-fix-loop 를 지나 **코드 단계의 AC 수준 읽기**가 잡았다. "코드 리뷰 때 SRS 를 본다"가 실제로 효과를 낸 사례다.
- SRS 산문 품질만 겨냥한 관점 셋(kiwi-srs 관점 9, kiwi-srs-sync A4, kiwi-planner A10)은 실결함 포착 기록이 0 건이다.
- 이미 같은 방향의 결정이 있다: FR-FLOW-137(연구 문서 리뷰 0 회), FR-FLOW-142(A/B 루프를 심각도에서 멈추고 문서 수로 곱하지 않음).

**외부**
- SDD 도구 중 명세·계획을 다중 라운드 LLM 리뷰로 검증하라는 곳은 없다. Spec Kit `/speckit.analyze` 는 읽기 전용 1 회·finding 상한 50. BMAD v6.7.0 은 PRD 적대 리뷰어를 루브릭 1 회 종합으로 바꿨고, v6.11.0 은 구현 준비도 검사를 별도 스킬에서 빼 계획 단계 첫 게이트 하나로 합쳤다. Kiro 는 명세를 리뷰가 아니라 속성 기반 테스트로 검증한다.
- LLM 요구사항 리뷰의 한계: 최고 모델도 전문가 발견의 중앙값 47%, 필요성·정확성 문제는 거의 놓침(Shefa 등 2026). 34 명 통제 실험에서 LLM 보조가 인스펙터의 탐지 정확도를 떨어뜨림(Broccia 등 2026).
- 반복 라운드는 수렴이 보장되지 않는다: 9 라운드 감사의 결함 수가 15, 8, 12, 2, 8, 1, 4, 1, 0 으로 오르내림(Calboreanu 2026). 외부 신호 없는 자기교정은 성능을 떨어뜨리기도 함(Huang ICLR 2024, Stechly ICLR 2025). 요구 적합성 판정을 시키면 맞는 코드도 결함으로 판정하는 과잉교정(Jin & Chen 2026).
- "요구 결함은 늦게 고칠수록 100 배" 는 원자료가 약하다. Boehm & Basili(2001)도 "often" 을 붙였고 작은 비핵심 시스템은 5:1 이라 했으며, 명세 변경을 피할 수 없는 재작업으로 인정했다. Menzies 등(2017, 171 개 프로젝트)은 지연 비용 효과의 증거를 찾지 못했다.
- Anthropic Opus 5 프롬프팅 가이드: "legacy harness scaffolding that adds separate verification steps" 를 지우라. Claude Code 문서: "찾으라고 한 리뷰어는 건전한 작업에서도 finding 을 보고하고, 그것을 다 쫓으면 과잉 설계가 된다."

### 2.2 반대 근거

**저장소 기록**
- SRS 적대 검토 1 회(31 에이전트)가 HIGH 1 건을 확정했다(FR-FLOW-024↔028 `--auto` 우선순위 비대칭). 정밀도는 약 12.5% 였다. 연구 21 은 이것으로 연구 19 의 "CRITICAL/HIGH 는 전부 뮤테이션이 잡았다"를 SRS 평가 루프에 대해서는 정정했다.
- 계획 `--max` 6 라운드가 codex 미러 빌드 파손·package-doctor 미등록·`npm test -- undefined` 보간 버그를 잡았다. v3.0.0 계획 검토가 폐기 목록이 되돌리기 명령 넷을 지우고 있던 것을 잡았다(커밋 `d58643a`). 뒤의 것은 삭제 diff 가 계획과 일치하므로 코드 리뷰가 "계획대로"로 통과시켰을 가능성이 크다.
- "구현자가 기준을 고친다"를 이 저장소는 여러 번 거절했다 — "실패를 만든 쪽이 편집자를 겸하면 안 된다"(FR-NODE-134). 다른 요구의 술어를 범위 밖에서 넓혔더니 CRITICAL 2 + HIGH 4 가 나고 철회했다(FR-FLOW-131 사례).
- 수정이 새 결함을 만든다: 인수인계 검증의 FALSE 4 건 중 3 건은 1 라운드 수정이 만들었고, v3.0.0 게이트 명세는 판마다 직전 수정 자리에서 CRITICAL 이 새로 났고, README 루프는 자기 수정으로 결함 8 건을 들였다.
- 처리가 이미 갈린 전례: FR-FLOW-022(C3)는 supersede 를 노트로만 남기고 AC-1 을 `[x]` 로 둔 채 증거 테스트만 좁혀, 지금도 요구와 증거가 어긋나 있다. 검증 없이 "고쳐 가며" 처리한 결과가 이런 모양으로 남을 수 있다.
- 사용자 본인의 기존 결정과 겹친다: "루프가 과하더라도 괜찮다"(2026-08-25), v3.0.0 재제안 금지 목록의 "검증 라운드 수 감축", FR-FLOW-152 코드 전용 리뷰.

**외부**
- 명세와 테스트가 충돌하면 모델은 테스트를 고치거나 우회한다. 명세를 우선하라고 지시해도 GPT-5 는 한 과제 변형에서 76% 우회했고, Claude 계열은 주로 테스트 파일을 직접 고쳤다. 테스트 읽기 전용이 "promising middle ground" 였다(ImpossibleBench, ICLR 2026).
- LLM 이 만든 테스트 오라클은 기대 동작보다 현재 동작을 담는 경향이 있다(Konstantinou 2024). 구현을 보고 명세를 고치면 버그가 정답으로 굳을 수 있다.
- 감시 신호가 목표가 되면 무너진다: CoT 모니터를 보상에 넣자 보상 해킹이 숨은 형태로 바뀌었다(OpenAI 2025). 테스트를 통과한 SWE-bench 패치의 29.6% 가 정답과 동작이 달랐다(Wang 등 ICSE 2026).
- 명세 모호성, 특히 덜 적힌 명세는 코드 품질을 확실히 떨어뜨리고 LLM 은 스스로 알아채지 못한다(Orchid 2026). 효과를 낸 것은 LLM 리뷰가 아니라 **사람에게 되묻기** 였다(ClarifyGPT, FSE 2024: 70.96% → 80.80%).

### 2.3 두 쪽을 함께 놓고 본 판단

- 반대 근거의 "코드 이전에 잡은 결함"은 대부분 **결정적 검사나 한 번의 조회로 대체 가능한 종류**다. 빌드 파손·doctor 미등록은 스위트, 보간 버그는 `validator.mjs` 류, verified 요구와의 모순은 식별자 검색(연구 26·27 이 사후 대입으로 4~6 히트까지 좁혀진다고 적음), 되돌리기 명령 삭제는 "기존 verified 요구가 이 명령을 못박고 있는가" 조회로 잡힌다. 반복 LLM 라운드가 아니면 잡을 수 없었던 사례는 FR-FLOW-024↔028 비대칭 하나이며, 그 비용은 31 에이전트였다.
- 반대 근거의 두 번째 묶음(구현자가 기준을 고칠 때의 위험, 수정이 새 결함을 만드는 패턴, 테스트 우회)은 **검증 단계를 없애는 것에 대한 반대가 아니라 "고쳐 가며"를 무제한으로 여는 것에 대한 반대**다. 장치로 막을 수 있다(§3.2).
- 비용이 나는 곳은 둘이다. 사용자가 다른 프로젝트에서 speckiwi 를 쓸 때는 세 스킬의 검증 루프가 비용을 낸다(사용자 체감: "40 라운드"). 이 저장소 자체 개발 기록의 긴 루프(7~9 라운드)는 대부분 코드·스킬 계약 테스트의 뮤테이션 루프였다. 제안은 앞의 것을 줄이고 뒤의 것은 줄이지 않는다.

## 3. 권고 — 제안 ① 을 어떤 모양으로 받아들일 것인가

### 3.1 SRS·계획 단계: LLM 검증 루프를 없애고 결정적 검사와 충돌면 조회만 남긴다

> 계획 부분은 통제 실험으로 확인했다(`docs/research/32.plan-verification-loop-experiment.md`). 계획 검증 루프는 구현 품질을 올리지 못했고(Opus 14 회 모두 100%) 비용만 6.9 배로 늘렸다. 약한 모델에게는 긴 절차형 계획이 오히려 해로웠고, 150 줄 이내의 짧은 계획이 가장 좋았다.

| 남길 것 | 이유 |
|---|---|
| `speckiwi validate`(SRS-MD 규칙), `validator.mjs`(계획·사이드카 무결성 C01~C25) | 결정적이고 싸다. 계획 검증이 잡은 결함의 상당수가 이 종류였다 |
| 작성 중 **충돌면 조회**: 새·수정 요구마다 "이 동작·경로·명령을 이미 못박는 verified 요구가 있는가"를 식별자 검색으로 확인 | 코드 단계까지 간 모순(FR-NODE-193, FR-FLOW-150)과 계획 검토가 잡은 되돌리기 명령 삭제가 이 한 번의 조회로 좁혀진다. 검증이 아니라 작성의 일부로 둔다 |
| 모호성은 사용자에게 되묻기(`kiwi-srs` QnA) | 외부 근거가 가장 강한 부분(ClarifyGPT). LLM 리뷰로 대체되지 않는다 |
| `--max` 에서만 독립 검증 1 패스 | 사용자가 원할 때의 선택지. 기본값에서는 돌지 않는다 |

| 걷어낼 것 | 비고 |
|---|---|
| `kiwi-srs` Phase 5/6 의 기본 모드 반복 루프, A/B 루프의 기본 모드 반복 | 1 회 작성자 자기 점검 + 기계 검사로 대체 |
| `kiwi-srs-feasibility` Phase 5/6 루프 | 10 개 관점 중 7 개가 결정 가능한 규칙이고, 복제본에서 지워도 테스트가 하나도 깨지지 않았다(연구 D §4.4 E12). 가장 먼저 옮기기 쉽다 |
| `kiwi-planner` Phase 3 13 개 관점 루프, §6.8 커버리지 루프 | 커버리지 산술은 `validator.mjs` 가 이미 한다. 판단 관점(A1 황금률, A9 dod 구체성 등)은 코드 리뷰로 넘긴다 |

### 3.2 도중에 고치기: 허용하되 장치 셋을 먼저 만든다

1. **방향 제한.** SRS·계획을 고쳐도 되는 경우는 FR-FLOW-139 의 충돌 세 종류뿐이다 — 요구가 단언한 사실을 코드가 반증함 / 기준을 적힌 대로는 만족할 수 없음 / 같은 요구의 두 부분이 다른 답을 냄. "코드와 다르다"는 사유가 아니다. 계획은 권위가 낮으므로 더 자유롭게 고쳐도 된다(연구 24: 산문 계획은 값을 잃었다).
2. **약화 변경의 분리.** AC 삭제·완화, 임계값 하향, 범위 축소는 명확화·범위 조정과 구분해 표시한다. 코드 리뷰어는 이것을 **수정된 SRS 가 아니라 사용자 원문 요청과 수정 전 AC** 에 대어 판정한다(BMAD Intent Alignment Auditor: "only the intent, never the spec's own scope language, can justify deferring a finding"). 약화 변경은 기존 규칙대로 테스트 약화와 같은 등급(critical gate)으로 다룬다.
3. **기록의 기계화.** `replace_acceptance_criteria`·본문 편집 도구가 Change Notes 행을 스스로 쓰게 한다. verified 요구는 "착수 전에 하향 → 수정 → 재승격" 규율(`docs/plan/3.0/REMAINING.md`)을 도구가 강제한다. 에이전트 규율에 맡기면 FR-FLOW-022(C3) 같은 반쯤 처리된 상태가 남는다.

권한 배치 — "실패를 만든 쪽이 편집자를 겸하지 않는다"(FR-NODE-134)를 지키는 최소 형태:
- 구현자(`kiwi-coder`·`kiwi-pm` 자식·`kiwi-tdd`)는 SRS 변경을 **제안·적용**할 수 있다. 적용한 변경은 diff 에 남는다.
- 코드 리뷰(`kiwi-review-fix-loop`)는 구현자가 바꾼 **SRS·계획 diff 를 코드 diff 와 함께** 받아, SRS 약화 변경을 판정한다. 관련 요구의 AC 본문을 리뷰 입력으로 넣는 것은 권하지 않는다 — §3.3 의 실험(연구 31)에서 결함 적중을 늘리지 못했다.
- 판정자는 새 컨텍스트의 서브에이전트다(외부: 새 컨텍스트 리뷰가 자기 코드에 대한 편향을 줄인다).

### 3.3 코드 리뷰가 SRS 를 보면 빨라지는가, 느려지는가

사용자 질문(2026-09-27): "코드 리뷰가 SRS 을 보는 것은 도움이 될까요? 아니면 더 느려지기만 할까요?"

**보는 범위와 묻는 질문에 따라 갈린다.** 좁게 보면 SRS·계획 검증 루프를 없앤 뒤 "옳은 것을 만들었는가"를 확인하는 유일한 지점이 되고, 넓게 보면 이번 제안이 없애려는 산문 루프를 코드 리뷰 안에 다시 만든다.

도움이 된다는 근거:
- FR-FLOW-022 AC-2 누락은 구현·좁은 테스트·review-fix-loop 3 라운드를 모두 통과했고, 코드 단계의 AC 수준 읽기가 잡았다.
- 코드 검증 라운드의 AC 대조 렌즈가 HIGH 1 건(FR-NODE-198 AC-5 릴리스 노트 부재 — 뮤테이션으로는 심을 결함이 없는 종류)을 잡았고, 사실성 검사가 요구가 존재하지 않는 상수를 지목한 것을 잡았다(연구 29).
- 테스트 통과는 명세 충족이 아니다. 테스트를 통과한 SWE-bench 패치의 29.6% 가 정답과 동작이 달랐다(Wang 등 ICSE 2026). 테스트가 AC 를 빠뜨렸는지는 AC 를 읽어야만 알 수 있다.
- SRS·계획 검증을 없애면 AC 대 구현 대조는 사전 단계에서 할 수도 없다(코드가 없으므로). 이 대조를 코드 리뷰로 옮기는 것은 비용을 더하는 것이 아니라 **없앤 단계의 유일하게 실효 있는 기능을 옮기는 것**이다.

느려진다는 근거:
- 요구 적합성 판정을 LLM 에 맡기면 맞는 코드도 결함으로 판정하는 과잉교정이 나오고, 프롬프트가 자세할수록 심해진다(Jin & Chen 2026). SRS 전체를 주면 리뷰어가 SRS 문장 품질을 지적하기 시작하고, 그것이 "세세한 문제까지 잡는" 라운드를 늘린다.
- 읽기량: FLOW 요구 블록만 1.37 MB 다. 모순 검사 1 회 전량 읽기 약 300 만 자 대 식별자 검색 3,877 자(연구 27 추정, 750~845 배)이며 라운드마다 곱해진다.
- FR-FLOW-152 의 배경: 리뷰 루프가 산문을 대상으로 삼자 연구·설계 문서를 고치며 범위를 벗어났다. 산문 라운드는 수렴하지 않는다(README 6 라운드, 자기 수정 결함 8 건).

실험 전 추정은 "관련 AC 본문만 좁혀 주고 AC 마다 충족·테스트 여부를 묻는다"였다. 이 추정을 맹검 통제 실험으로 확인했다(`docs/research/31.code-review-with-srs-experiment.md`). 실제 이력 6 사례 × 4 조건(코드만 / AC 본문 + AC 표 / SRS 전체 / AC 전담 렌즈)으로 리뷰 24 회를 돌리고 조건을 가린 판정자 2 명이 채점했다(판정 일치 κ 0.86).

- **적중이 늘지 않았다.** 코드만 본 리뷰가 양성 4 사례의 주정답을 4/4 잡았고, 나머지 세 조건은 3/4 였다. 셋 다 같은 사례에서 AC 문장 성립 여부에 시선이 고정되어 코드 수준의 버그를 놓쳤다.
- **느려졌다.** AC 만 주면 시간 +17%, SRS 전체를 주면 +20% 에 도구 호출 +44%.
- **SRS 전체는 요구 문장 트집을 네 배로 늘렸다**(리뷰 1 회당 0.4 → 1.6 건).
- 이 저장소의 diff 는 테스트 이름·`@req` 태그·주석으로 요구 의도를 이미 싣고 있어, 코드만 본 리뷰도 의도를 복원했다(추정).

수정된 권고:
1. **기본 코드 리뷰에는 SRS 를 넣지 않는다.** 현행 코드 전용 리뷰(FR-FLOW-152)를 유지한다.
2. **AC 와 구현의 대조는 기계 대조로 둔다.** `--close-reqs` 의 AC 별 통과 테스트 지목과 뮤테이션이 "이 AC 를 지키는 테스트가 없다"를 더 확실하게 잡는다. AC 판독 렌즈가 필요하면 `--max` 의 선택 렌즈로만 둔다.
3. **리뷰가 받는 SRS 입력은 구현자가 바꾼 SRS·계획 diff 뿐이다**(§3.2 의 약화 판정용). SRS 원문 전체나 관련 AC 본문은 주지 않는다.
4. **다음 변수는 심각도 게이트다.** 실험에서 맞힌 정답 결함의 대부분이 MEDIUM 이하로 매겨져, CRITICAL·HIGH 만 막는 게이트로는 수정이 강제되지 않았다. 반대로 음성 사례에서는 기각된 후보가 네 조건 모두에서 HIGH 로 올라왔다. 별도 실험이 필요하다.

### 4.1 규모

- 스킬 원문은 네 벌이다: `skills/claude` 1,121,251 B · `skills/codex` 1,047,288 B · `skills/etc` 1,022,031 B · `.agents/skills` 970,851 B(codex 미러). 실제로 다른 내용은 한 벌뿐이다. claude 렌더링 전체는 약 36 만 토큰이다.
- 호출 1 회 적재량(SKILL.md + 따르라고 지시하는 `_shared`): orchestrator 291 KB(약 9.7 만 토큰), wave-master 189 KB, pm 142 KB, review-fix-loop 135 KB, coder 125 KB, srs 113 KB, planner 112 KB.
- `kiwi-pipeline` 기본 사이클은 여섯 스킬을 `Skill` 도구로 같은 컨텍스트에서 연달아 부르므로 약 459 KB(약 15 만 토큰)가 한 컨텍스트에 쌓인다. Task 마다 kiwi-coder 77 KB 가 서브에이전트별로 더 든다.
- 세 스킬의 검증 루프 서술: kiwi-srs 191 줄(21.8%, 13,449 B), feasibility 120 줄(12.0%, 8,208 B), planner 140 줄(14.6%, 10,398 B). §3.1 을 적용하면 약 28~30 KB 가 빠진다.

|---|---|---|---|---|---|
| kiwi-orchestrator | ~5% | ~6% | ~10% | ~75% | ~7% |
| kiwi-pm | ~11% | ~5% | ~40%(의사코드 33%) | ~40% | ~5% |
| kiwi-coder | ~20% | ~7% | ~26% | ~40% | ~5% |

| kiwi-srs | ~35% | ~15% | ~15% | ~30% | ~5% |

- SDD 본질은 `CLAUDE.md`/`AGENTS.md` 에 설치되는 8.6 KB 블록에 이미 있다.
- 글자 그대로의 중복은 약 3%(31 KB)로 적다. 대신 같은 개념이 스킬마다 다른 문장으로 반복되고, 일부는 이미 어긋났다: finding_hash 공식이 kiwi-srs·planner 는 severity 를 포함하고 feasibility 는 제외한다. kiwi-planner 는 한 파일 안에서 개선 루프 분기 목록이 두 곳에서 다르다.
- 실행과 무관한 텍스트: 계보·로드맵·설계 요약 15 KB, 자연어→플래그 매핑표 26 KB, 다음 편집자와 계약 테스트를 향한 근거 문장.

### 4.3 가장 큰 걸림돌 — 양을 잠그는 계약 테스트

- `test/skills` 91 파일 43,086 줄, golden 3,300 줄. FR-FLOW 176 개 중 124 개가 스킬 문구를 언급한다.
- 하한 단언: FR-FLOW-154 `VALUE_FLOOR`(lifecycle 값 단어가 측정된 횟수만큼 계속 나와야 함), FR-FLOW-179 `CITATION_FLOOR`·`RESOLVED_FLOOR`, FR-FLOW-179 AC-7(orchestrator 에 `references/` 금지), FR-FLOW-164·161 의 byte-exact golden.
- 복제본 삭제 실험(claude 렌더링만, 13 개 절): 10 개가 2~16 건의 테스트를 깼다. 깨지지 않은 것은 kiwi-coder `@req` 규칙 7.6 KB, kiwi-srs finding_hash 행, feasibility 검증 루프뿐이다.
- 이 하한들은 연구 29 가 "검사 대상이 조용히 줄어드는 것"을 막으려고 만든 것이다. 다이어트는 바로 그 축소를 의도적으로 하는 일이므로, 두 목적이 정면으로 부딪힌다.

### 4.4 외부 — 하네스 무용론과 그 반론이 가리키는 것

- 걷어내는 쪽: Claude Code 팀은 Opus 5 에 맞춰 시스템 프롬프트의 80% 를 지웠다고 말했다(Boris Cherny, YC 2026, 제3자 전사본). Anthropic 은 "Every component in a harness encodes an assumption about what the model can't do on its own" 이라 쓰고 Opus 4.6 에서 sprint 분해 구조를 걷어냈다. Fable 5 가이드는 "Skills developed for prior models are often too prescriptive … and can degrade output quality" 라고 적는다. OpenAI GPT-5.5 가이드는 단계별 절차 지시를 줄이고 ALWAYS/NEVER/MUST 는 "true invariants" 에만 쓰라 하고, 현행 GPT-6 가이드는 스킬과 AGENTS.md 감사를 강하게 권한다(모호하거나 모순된 스킬 지시가 작업을 일찍 멈추게 함).
- 남기는 쪽: 같은 Anthropic 글에서 planner 와 evaluator 는 새 모델에서도 필요했다(자기 결과물 평가는 평범한 것도 자신 있게 칭찬). 장기 작업 하네스(기능 목록 파일, 진행 기록, git)는 Opus 4.5 에서도 필요했다. OpenAI harness engineering 은 약 100 줄짜리 AGENTS.md 지도와 커스텀 린터·구조 테스트로 "enforce invariants, not micromanage implementations" 한다.
- SDD 비판(Thoughtworks Radar Assess, Böckeler)이 겨냥하는 것은 산출물의 양과 의례적 절차다. Böckeler 도 명세를 먼저 쓰는 것 자체는 가치 있다고 인정한다.
- 기계적 제약: Claude Code 는 컴팩션 뒤 호출된 스킬마다 앞 5,000 토큰만 다시 붙이고 전체 합계는 25,000 토큰이다. 스킬 설명은 1,536 자에서 잘린다. Anthropic 스킬 문서는 SKILL.md 500 줄 미만을 권한다. 지시 수가 늘면 준수율이 떨어지고 앞쪽 지시를 더 잘 지킨다(IFScale). 집중형 스킬(모듈 3 개 이하)이 망라형보다 나았다(SkillsBench).
- 규칙 강제: Claude Code 문서는 CLAUDE.md 를 "advisory", 훅을 "deterministic" 이라 부르고, 반드시 막아야 하면 훅으로 막으라고 한다. OpenAI·Factory·Böckeler·HumanLayer 가 같은 방향이다.

정리하면 무용론과 반론은 "무엇을 걷어낼 것인가"에서 일치한다: **모델의 약점을 메우던 문구와 절차 서술은 걷어내고, 외부 상태(명세·진행 기록·증거)와 결정적 검사는 남긴다.** speckiwi 에서 앞의 것은 스킬 본문의 (c)·(d) 대부분이고, 뒤의 것은 SRS·MCP/CLI·코드 게이트다. SDD 를 유지하는 결정은 이 흐름과 충돌하지 않는다.

## 5. 스킬 다이어트 — 권고

### 5.1 원칙

1. **SDD 본질 여덟 가지는 지우지 않는다.** SRS 단일 원천 / 작업 전 Requirement ID 확인 / Status·Stability 게이트 / 증거 없는 verified 금지 / TDD 와 테스트 약화 금지 / MCP 우선과 황금률 / ID 를 손으로 바꾸지 않음 / 요구가 틀리면 우회하지 않고 보고. 코드로 옮기거나 한 곳에 모을 수는 있다.
2. **도구가 먼저 거부하게 만든 뒤 산문을 지운다.** 순서가 바뀌면 게이트가 사라진다(FR-FLOW-143 "결정 가능한 관점은 스크립트로", FR-NODE-188 "아무도 부르지 않는 검증기는 없는 보장과 같다").
3. **불변식은 스킬 맨 앞 5,000 토큰 안에 둔다.** 컴팩션 뒤 살아남는 부분이고, 모델이 가장 잘 지키는 위치다. 스킬마다 맨 앞에 짧은 "계약 카드"를 두고 나머지는 절차·참조로 내린다.
4. **강한 표현은 진짜 불변식에만 쓴다.** 판단 사항은 결정 규칙으로 쓰고 이유를 한 줄 붙인다.
5. **모델이 바뀔 때마다 절제 실험을 한다.** 지시를 지운 기준선과 비교해 차이를 낸 줄만 남긴다. 효과가 모델마다 반대인 지시도 있다(Opus 5 는 명시적 검증 지시를 지우라, Fable 5 는 장기 작업에서 새 컨텍스트 검증자를 명시하라).

### 5.2 순서

| 순서 | 방안 | 추정 절감(claude 런타임) | 선행·위험 |
|---|---|---|---|
| D0 | **계약 테스트를 "양"에서 "정합성"으로.** 유지: 없는 enum 값·없는 도구·코드 목록에 없는 게이트 ID 를 지시하지 않는다. 교체: 하한 단언, byte-exact golden, `references/` 금지, 근접 문구 단언 → "스킬별 계약 카드(필수 문장 집합)" 기준 | 0(나머지를 가능하게 함) | FR-FLOW-154/179/164/161 AC 교체. 연구 29 가 막으려던 조용한 축소가 다시 열리므로, "지운 절 목록 + 이유" 매니페스트를 두고 목록 밖 축소만 실패시키는 방식을 검토 |
| D1 | **게이트를 코드로 옮기고 산문을 한 줄로.** 역방향 status 전이, trace_intent status 상한, validate error 시 승급 거부, Stability 게이트, finding_hash 계산, `@req` lint, 결정 가능한 formal check. 이미 있는데 안 부르는 `workflow_task_check` 연결 | 20~35 KB | 도구마다 TDD 와 요구 신설. 거부 메시지에 해결 방법을 담는다 |
| D2 | **검증 루프 축소**(§3.1) | 세 스킬 28~30 KB. coder·review-fix-loop·verify-loop 에도 같은 모양 | §3.3 의 요구 변경 |
| D4 | **공통 보일러플레이트를 공용 파일 하나로.** MCP 배너, Workflow 도구 정책, §0 의 CLAUDE.md 재진술, 게이트 관측 문단, Pipeline emit 절(합계 19 KB), 워크트리 절차 중복 | 스킬당 3~8 KB, 파이프라인 한 사이클 25~45 KB | 공용 파일을 읽지 않는 경우. 합치다 뜻이 바뀌는 경우 |
| D3 | **실행과 무관한 텍스트 제거.** 계보·로드맵 15 KB, 이연 기능 서술, 근거 문단(→ SRS Change Notes 로 이동), 자연어→플래그 매핑표 26 KB | 35~55 KB | 근거 문장의 "되돌리기 방지" 역할을 SRS 로 옮겨야 함. 매핑표 삭제는 트리거 정확도를 측정하고 결정 |
| D5 | **모드별로만 읽히는 절을 `references/` 로.** commit-auto-pr 자식 모드 18.5 KB, commit-auto-push §11 15.8 KB, orchestrator 세 rung | 호출당 10~25 KB | 커밋 `a617c52` 의 실제 절감은 계획 34 KB 가 아니라 9.2 KB 였다. "거의 항상 도달하는" 절을 옮기면 읽는 시점만 늦어진다 |
| D6 | **산문 스키마를 도구 자기설명·생성물로.** `waves-event.md`·`run-ledger.md` 필드·enum 표, planner 사이드카 스키마, coder 상태 스키마 | orchestrator·wave-master 실행당 30~50 KB | 먼저 "산문 규칙 ⊆ 코드 검증" 대조표 |
| D7 | **네 렌더링을 한 원천에서 생성** | 런타임 0, 유지보수 감소 | codex 축약본과 claude 원본의 내용 차이를 변환 규칙으로 추출해야 함 |
| D9 | **파이프라인 단계를 서브에이전트로 분리**해 메인 컨텍스트 누적을 끊는다 | 총 토큰은 비슷, 메인 압박 감소 | 사용자 게이트와 NEEDS_USER 버블업 처리 변경 |
| D8 | `--auto` 결정 위원회(33 KB) 단순화 | — | 사용자 운영 원칙("모든 결정은 5 인 위원회")과 충돌. **사용자 결정 사항** |

D0 → D1 → D2 → D4 → D3 → D5 → D6 → D7 순서를 권한다. 1~5 순위는 SDD 본질을 강화하거나 건드리지 않는다. D1 은 절감과 함께 정확도도 올린다(산문 게이트를 기계 게이트로 바꾸므로).

## 6. 사용자 의견에 대한 답

| 사용자 의견 | 판단 | 조건 |
|---|---|---|
| SRS 와 계획은 검증하지 않는다 | **동의.** LLM 검증 루프는 없앤다 | 결정적 검사(`validate`, `validator.mjs`)와 작성 중 충돌면 조회는 남긴다. 모호성 되묻기는 남긴다. `--max` 에서만 독립 검증 1 패스 |
| 코드 리뷰만 한다 | **동의.** 판정을 코드 리뷰 한 곳에 모은다 | 리뷰어는 코드 diff 와, 구현자가 바꾼 SRS·계획 diff 를 받는다. SRS 원문·AC 본문은 주지 않는다(연구 31: 적중이 늘지 않고 느려짐) |
| 계획 작성 중 SRS 가 이상하면 SRS 를 고친다 | **동의** | 세 종류의 충돌 안에서만. 권한 확장(planner §0.13) 필요 |
| 코드 작성 중 계획·SRS 가 이상하면 둘 다 고친다 | **조건부 동의** | 방향 제한, 약화 변경의 분리 표시, Change Notes 자동 기록, 착수 전 하향. 이 장치 없이 열면 SRS 가 코드를 따라간다 |
| 코드 리뷰 때 SRS 도 보고 이상하면 개선한다 | **부분 동의.** 실험(연구 31)에서 SRS 를 본 리뷰가 결함을 더 잡지 못했고, SRS 전체는 트집만 네 배로 늘렸다 | 리뷰는 구현자가 바꾼 SRS diff 의 약화 여부만 판정한다. SRS 결함을 고치는 경로는 구현자 보고(FR-FLOW-139)에 둔다 |
| 하네스 무용론 속에서도 SDD 는 필요하다 | **동의.** 외부 흐름도 명세·기록·증거·결정적 검사는 걷어내지 않는다 | 스킬의 모델 보정 문구와 절차 서술을 걷어내는 것으로 응답한다 |
| 스킬을 다이어트한다 | **동의. 첫 작업은 텍스트가 아니라 계약 테스트** | D0 없이 시작하면 절 하나 지울 때마다 2~16 건씩 깨진다 |

## 7. 이 연구의 한계

1. "SRS·계획 검증을 빼고 돌렸다면 무엇이 코드 단계에서 잡혔을까"는 전부 사후 추정이다. 대조 실행 기록은 저장소에 없다.
2. 요구 결함 8 건과 두 모순 사례의 요구가 kiwi-srs 검증을 실제로 거쳤는지는 확인하지 못했다. "검증이 놓쳤다"와 "검증이 돌지 않았다"를 가를 수 없다.
3. FR-FLOW-147 이후에도 검증 산출물 영속 데이터가 쌓이지 않아 관점별 포착률을 잴 수 없다.
4. 스킬 내용 분류는 한 조사자의 판단이며 교차 분류하지 않았다. 삭제 실험은 claude 렌더링만 바꿨고 `test/core` 전체는 돌리지 않았다.
5. 라운드당 토큰·시간의 1 차 측정치는 저장소에 없다. "40 라운드"는 사용자 발화이고 측정 기록이 아니다.
6. 외부 인용 일부는 2 차 자료다(Boris Cherny 발언은 제3자 전사본, ImpossibleBench 완화책 수치는 요약 글, Tessl 은 공식 문서 미확인). 요구로 옮길 때 원문을 다시 확인해야 한다.
7. 외부 연구 다수가 프리프린트다(Shefa, Broccia, Calboreanu, Jin & Chen 등). 명세 리뷰 라운드 수와 최종 결함의 관계를 직접 잰 실증 연구는 찾지 못했다.
