# Todo Installable SRS Integration Test Research

| Field | Value |
|---|---|
| Research ID | research-04-todo-installable-srs-integration-test |
| Date | 2026-05-08 |
| Topic | Dynamic two-scope Todo SRS integration test |
| Decision | Use a generated temporary workspace instead of a fixed fixture |

## 1. Research Question

SpecKiwi needs an integration test that creates a realistic virtual project for an installable Todo list management web service. The virtual project must have separate Server and Web Page SRS scopes, then exercise core parsing, CLI read commands, MCP read tools, and MCP mutation tools against that SRS set.

## 2. Senior Research Summary

Research A focused on SRS fixture construction and concluded that a dynamic `mkdtemp` workspace is the best match for the requested scenario. The main reasons are test isolation, direct UTF-8 write coverage, and clear in-test ownership of the Server and Web Page SRS documents.

Research B focused on CLI and MCP integration paths. It confirmed that CLI can be exercised through `main(argv, io)` and MCP can be exercised through `createTestMcpServer`, `registerReadTools`, and `registerMutationTools`. It also found that full CLI/MCP response parity and MCP `add_requirement` patch summary assertions are outside this Todo integration test's partial coverage. `FR-MCP-010` still requires patch summary coverage, so that AC should be handled by dedicated MCP response-contract coverage rather than by this generated Todo workflow.

The team-lead synthesis selected dynamic workspace generation and limited parity assertions. The test should compare domain values and file side effects, not full serialized response objects.

## 3. Adopted Test Shape

The test will create this structure under a temporary root:

```text
docs/
  rule/
    SRS-MD-Rules-v1.0.0.md
  spec/
    00.index.md
    10.server.srs.md
    20.web-page.srs.md
```

The index will register target `todo-installable-v1` and two scope prefixes:

| Scope | Document | Prefix |
|---|---|---|
| Server | `10.server.srs.md` | `SRV` |
| Web Page | `20.web-page.srs.md` | `WEB` |

The initial SRS will contain:

| Requirement ID | Type | Purpose |
|---|---|---|
| `FR-SRV-001` | functional | Todo server CRUD behavior |
| `IR-SRV-001` | interface | REST API contract consumed by the page |
| `FR-WEB-001` | functional | Todo page list and create behavior |

MCP mutation will add `FR-WEB-002` to `20.web-page.srs.md` and then the test will re-run validation.

## 4. Scope Boundaries

Included in this plan:

- Core parser and validator over the generated SRS.
- CLI read commands over the generated SRS.
- MCP read tools over the generated SRS.
- MCP `add_requirement` mutation into the Web Page scope.
- Mutation-after-validation checks.

Excluded from this plan:

- Full CLI/MCP JSON response parity.
- MCP `add_verification_evidence` notes propagation.
- MCP `add_requirement` patch summary AC and `diagnostics` preservation.
- Fixed fixture directory `test/fixtures/workspaces/todo-installable`.

## 6. Final Recommendation

Add a single integration test file, `test/integration/todo-installable-workflow.test.ts`, with local helper functions for workspace generation, UTF-8 file writes, CLI JSON execution, and MCP server creation. Keep assertions structural and deterministic: requirement IDs, scope counts, validation errors, summary totals, generated `FR-WEB-002`, and destination file path.
