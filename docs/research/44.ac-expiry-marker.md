## 0. 결론 요약

- **변형해서 도입할 만하다.** 저장소는 이미 같은 일을 손으로 하고 있다. `- [x] AC-n: Retired in 4.0.0: …; successor X` 형태의 AC 가 **32개 요구에 60개** 있다(§3). 하지만 도구는 이 줄을 살아 있는 AC 로 센다. 그래서 테스트 충분성에서 거짓 gap 이 생기고(요구 5개는 gap 이 전부 retired AC 에서 나온다), 체크되지 않은 retired AC 4개는 요구를 verified 로 올리지 못하게 막는다. 은퇴한 AC 를 덮으려고 테스트를 따로 써서 인용하는 일도 반복됐다.
- **변형할 점**: 사용자 스케치처럼 `~~AC-2: …~~` 로 ID 까지 줄을 그으면, 지금 파서가 그 줄을 **위치 번호(AC-{순번})로 다시 매겨** 엉뚱한 AC 에 묶는다(재현은 §5.1). 그래서 ID 는 그대로 두고 본문에만 줄을 긋고 표식을 붙인다. `- [x] AC-2: ~~원문~~ [EXPIRED 2026-11-03 → FR-FLOW-204]`
- **핵심 규칙 셋**: (1) expired AC 는 모든 통과 조건·집계·충분성 검사에서 빠진다. (2) AC 번호는 다시 쓰지 않는다. 지금 규칙 §21.2-3 은 재번호를 허용하고 `replace_acceptance_criteria` 는 실제로 1부터 다시 매긴다. 이 둘을 막는다. (3) 날짜는 도구가 쓰고, 사유는 Change Notes 행으로 반드시 남긴다.
- **버전 배치**: 5.2.0(도구·규칙 개선). 요구는 최소 2개(파서·규칙 1, 변이 도구 1). 초안은 §8 에 있다.
- **FR-FLOW-024 에 대한 주의**: 이 요구는 Requirement 문장 자체가 AC-1~3 의 행동을 서술한다. 그래서 expired 를 도입해도 **문장을 고치려면 하향이 여전히 필요하다**(`edit-requirement.ts:90-93` 이 verified 요구의 문장 편집을 막는다). 도입으로 얻는 것은 AC 번호 보존, 테스트 인용 정리, 통과 조건 정확성이다. 하향을 없애 주지는 않는다. 또 AC-1~3 이 실제로 효력을 잃는 날은 FR-FLOW-205 AC-1(kiwi-srs Phase 1.5 제거)이 구현되는 날이다. 지금(planned)이 아니다.

## 1. 요청 해석

원문: "이 스코프가 달리면 이 AC 는 이제 없는 것과 다름 없습니다. 대신 expired 된 날짜를 함께 기록해야 합니다."

가능한 읽기는 둘이다.

| 읽기 | 근거 | 결과 |
|---|---|---|
| (가) "이 표식이 **달리면**(붙으면)" — '달다'의 피동 | 위임 지시서의 해석. "스코프"는 표식(태그)을 가리킨다 | **메커니즘**: 표식이 붙은 AC 는 효력이 없다 |
| (나) "이 스코프가 **달라지면**" — 오타 | AC 가 다루는 범위가 다른 요구로 옮겨 가는 FR-FLOW-024 사례와 맞는다 | **발동 조건**: AC 의 범위가 다른 요구로 옮겨 가거나 사라질 때 |

두 읽기는 충돌하지 않는다. (나)는 *언제* expire 하는지, (가)는 *어떻게* 표시하고 취급하는지를 말한다. 이 보고서는 둘을 합쳐 이렇게 읽는다. 「AC 의 범위가 바뀌어 효력을 잃으면 그 AC 에 expired 표식과 날짜를 붙인다. 그 AC 는 지우지 않고 기록으로 남기되 없는 것으로 취급한다.」 덧붙여 speckiwi 에서 「scope」는 `FLOW`·`NODE` 같은 문서 범위 접두사를 뜻하는 용어다. 그런데 FR-FLOW-024 → FR-FLOW-204 는 같은 FLOW 스코프 안의 이동이다. 그래서 「스코프 접두사가 바뀔 때」로 좁게 읽는 해석은 배경 사례와 맞지 않아 버렸다.

## 3. 저장소 실태: 같은 일을 손으로 하고 있다

### 3.1 「Retired」 관례

`docs/spec/*.srs.md` 에서 `^- \[[ xX]\] AC-\d+: Retired` 를 세면 다음과 같다(4.0.0 계획 모드 제거 때 생겼다).

- **32개 요구, 60개 AC.** 파일별로는 30.cli 3, 40.mcp 2, 50.nodejs 19, 60.workflow 36 이다. 요구 상태는 verified 28, implemented 4 다.
- 예: `docs/spec/40.mcp-stdio-interface.srs.md:4686` `- [x] AC-1: Retired in 4.0.0: … successor FR-NODE-211.` (FR-MCP-062)
- 원문은 지워졌다. 남은 것은 은퇴 사유 문장뿐이다. 원래 기준은 git 이력에만 있다.
- 날짜가 아니라 버전("in 4.0.0")만 적혀 있다. 날짜는 Change Notes 행(2026-09-27/28)을 따로 찾아야 나온다.

### 3.2 그 관례가 치르는 비용 (실행 결과)

`node bin/speckiwi coverage --tests --ids <위 32개> --json` 의 결과다.

- retired AC 60개 가운데 **48개가 테스트 줄의 인용을 받고 있다.** 예: `test/mcp/workflow-plan-tools-removed.fr-node-211.test.ts:89` `"FR-NODE-211 AC-1 / FR-MCP-062 AC-1 AC-3: no removed tool is registered…"`. 은퇴한 AC 를 덮으려고 부재 확인 테스트를 쓰고 인용했다. 도구가 은퇴를 모르기 때문이다(`test-sufficiency.ts:113-119` 는 모든 AC 를 센다).
- **12개는 인용이 없어 gap 으로 보고된다.** 그중 **FR-NODE-108, FR-NODE-146, FR-NODE-165, FR-NODE-166, IR-CLI-098 다섯 요구는 gap 전체가 retired AC 다.** 거짓 gap 이다. kiwi-pm 은 gap 이 없는 요구만 implemented 로 올린다.
- **체크되지 않은 retired AC 가 4개다**: FR-NODE-108 AC-3, FR-NODE-120 AC-5, FR-FLOW-052 AC-2, FR-FLOW-061 AC-3(모두 implemented). verified 로 올리려면 모든 AC 가 `[x]` 여야 한다(`update-status.ts:137-145`, `rules.ts:282-288`). 그래서 은퇴한 기준에 체크를 해야 하는 모순이 생긴다.

### 3.3 다른 선례

- **FR-FLOW-022 AC-1**(`60.workflow-release.srs.md:1945`): 아직 `[x]` 로 살아 있다. 대체 사실은 Research / Analysis 의 날짜 붙은 산문(`:1968`)과 요구 단위 `superseded_by FR-FLOW-034` 링크(`:1963`)로만 표현된다. **Change Notes 에는 기록이 없다**(`:1978` 은 Created 한 줄뿐). 규칙 §26-2(`:1218`, AC 의미가 바뀌면 기록)를 어긴 상태다. 도구는 AC-1 을 여전히 유효한 기준으로 본다.
- **부분 supersede 산문**: `30.cli-interface.srs.md:3029` "IR-CLI-017을 supersede한다(AC-1~4·AC-6 계승, AC-5·AC-7 대체)", `40.mcp-stdio-interface.srs.md:3091` (REL-MCP-003 부분 대체), `50.nodejs-implementation.srs.md:5960` "Supersedes the never-overwrite clause of FR-NODE-076 AC-2 only". 모두 요구 단위 링크의 Notes 나 산문으로만 적혀 있다.

- 하향 사이클: "Status -> in_progress/implemented/planned" 이면서 AC 를 언급하는 Change Notes 행이 304개다. 상한치라 전부가 부분 대체는 아니다. 그래도 AC 를 고치려고 하향→수정→재승격을 도는 일이 흔하다는 것은 보여 준다.

## 4. 파서·도구 영향과 바꿀 지점

### 4.1 구현 방식 권고: 파서에서 한 번 가른다

지금 「verified 모양」 술어(AC 1개 이상, 전부 체크, 근거 존재)는 적어도 네 곳에 따로 쓰여 있다. `rules.ts:282-288`, `update-status.ts:137-143`, `implementation-workflow.ts:28-31`, `add-requirement.ts:87-89` 이고, 변형이 `orchestrator/readiness.ts:450-452`, `release-readiness.ts:53-55` 에 더 있다. 각 곳에 `!expired` 필터를 넣으면 같은 판단을 여섯 곳이 나눠 갖게 된다(전역 지침 §10.2 위반).

**권고**: `parseAcceptanceCriteria`(`src/core/parser/ac-parser.ts:62-70`)가 expired 줄을 `criteria` 에 넣지 않고, 별도 배열(예: `expiredCriteria: {id, text, checked, line, date, successor?}`)로 돌려준다. `RequirementRecord.acceptanceCriteria`(`types.ts:249`)에는 살아 있는 AC 만 남는다. 그러면 위 여섯 곳은 **코드를 바꾸지 않아도** expired AC 를 뺀다. expired 를 알아야 하는 몇 곳만 새 배열을 읽는다. 기본값이 안전한 쪽(살아 있는 것만)이다.

## 5. 설계 대안 비교

### 5.1 사용자 스케치 형태의 파싱 위험 (재현)

현재 파서 정규식(`ac-parser.ts:62`)을 그대로 돌린 결과다. AC-2 가 예전에 지워져 번호가 빈 목록을 가정했다.

```
입력                                                                → 파싱된 id
- [x] AC-1: live one                                                → AC-1
- [x] ~~AC-3: moved~~ (expired 2026-11-03, superseded by FR-FLOW-204 AC-1) → AC-2  ← 위치 번호로 다시 매겨짐
- [x] AC-3: ~~moved~~ [EXPIRED 2026-11-03 → FR-FLOW-204]             → AC-3  ← ID 보존
- [x] AC-4: last                                                    → AC-4
```

ID 앞에 `~~` 가 오면 `(?:(AC-\d+):\s*)?` 가 맞지 않는다. 그래서 대체 ID `AC-${criteria.length + 1}` 이 붙는다. 지금 도구나 표식을 모르는 구버전 도구에서 이 줄은 **다른 번호의 살아 있는 AC** 가 된다. ID 를 앞에 두는 형태는 구버전 도구에서도 「체크된 AC-3」으로 읽혀, 도입 전 상태로 자연스럽게 물러난다.

### 5.2 비교표

| 기준 | (A) AC 줄 표식 `AC-n: ~~원문~~ [EXPIRED 날짜 → REQ]` | (A′) 스케치형 `~~AC-n: 원문~~ (expired …)` | (B) AC 삭제 + Change Notes 에 날짜·원문 | (C) 요구 단위 supersede 만 |

FR-FLOW-024 에서 AC-4 를 남기면 그것이 AC-1 이 된다. 그러면 기존 테스트 `FR-FLOW-024 AC-1`(모호성 질문을 단언, `test/skills/kiwi-srs-research-loop-content.test.ts:404-425`)이 **새 AC-1 의 커버로 조용히 잡힌다.** 손으로 번호를 남겨도, 지운 AC 를 인용하는 테스트 줄은 아무도 알리지 않는다(테스트 충분성은 남은 AC 만 돌고, REL-NODE-007 은 AC 를 확인하지 않는다) | 새 요구 ID 를 쓰니 없다. 대신 AC-4 의 인용을 모두 새 ID 로 옮겨야 한다 |

**판단**: (A)를 권한다. (A′)는 호환성 때문에 제외한다. (C)는 「AC 대부분이 옮겨 가는」 경우에 맞는 지금의 수단이고, 계속 그 용도로 둔다. (B)는 번호 재사용 위험 때문에 「아무도 인용하지 않는 AC 를 실수로 추가했을 때」로만 한정한다(§30 의 물리 삭제 조건 `:1418-1423` 과 같은 기준).

## 8. 결론과 권고

- **타당성**: 변형 도입. 사용자의 핵심(효력 상실 + 날짜 기록 + 지우지 않음)은 그대로 살린다. 표식 위치만 ID 뒤로 옮긴다.
- **권고안**: (A) 형태. 파서가 expired 를 별도 배열로 가르고, 전용 변이 도구 하나가 표식·날짜·Change Notes 를 한 패치로 쓴다. AC 번호 재사용을 금지한다.
- **버전 배치**: **5.2.0**. 규칙 문서 개정(번들 규칙 버전 `BUNDLED_RULES_VERSION = "2.5.0"`, `src/core/bootstrap/templates.ts:42` 를 올려야 한다), 파서, MCP/CLI 변이가 모두 도구·규칙 개선이다. 5.1.0 은 §7 의 지금 수단으로 처리한다. FR-FLOW-024 를 깔끔하게 처리하려고 5.1.0 앞으로 당기는 것도 가능하다. 변경 범위가 파서 1곳, 변이 1개, `replace` 수정, 드리프트·충분성 보정 2곳으로 작다(추정). 다만 이는 버전 전략을 바꾸는 일이라 사용자가 결정할 사항이다.

### 8.1 요구 초안 (2개)

**FR-PARSE-0xx — An acceptance criterion marked expired keeps its number and text but no longer counts**

- AC-1: WHEN an acceptance criterion line reads `- [ ] AC-<n>: ~~<text>~~ [EXPIRED <YYYY-MM-DD>]` or ends `[EXPIRED <YYYY-MM-DD> → <REQ-ID>]`, THE parser SHALL return it outside the requirement's live acceptance criteria, with its id, text, checked state, date and successor, and SHALL keep a line that does not match that grammar as a live criterion.
- AC-2: THE verified-shape check, the AC coverage gaps of release readiness, and the test-sufficiency gaps SHALL consider only live criteria, and a requirement whose live criteria are empty SHALL NOT be accepted as verified.
- AC-3: WHEN a test line cites an expired criterion, THE test-sufficiency report SHALL list it separately as an expired citation and SHALL NOT count it as coverage; WHEN an evidence `Covers` cell names an expired criterion, THE evidence SHALL NOT be reported as stale.
- AC-4: WHEN two criteria in one block carry the same AC number, live or expired, THE validator SHALL report an error, and WHEN an expired marker names a successor that does not exist, THE validator SHALL report the same error class as a missing trace requirement reference.
- AC-5: THE bundled rules document SHALL state that AC numbers are never renumbered or reused, that the marker is written and removed only by the tool, and that expiring a criterion to meet the verified conditions is forbidden.

**FR-NODE-2xx / IR-MCP-0xx — expire_acceptance_criterion marks one criterion expired with today's date and a reason**

- AC-1: WHEN `expire_acceptance_criterion` is called with a requirement id, an AC id and a non-empty reason, THE SYSTEM SHALL rewrite that line to the expired grammar with the writer's local date, keep its checkbox, and append a Change Notes row naming the AC and the reason in the same patch.
- AC-2: WHEN a successor id is given, THE SYSTEM SHALL write it into the marker only if that requirement exists, and SHALL refuse without writing otherwise.
- AC-3: THE SYSTEM SHALL refuse without writing WHEN the reason is empty, the criterion is already expired, or it is the requirement's last live criterion, and SHALL NOT require the requirement to leave `verified`.
- AC-4: WHEN `check_acceptance_criteria` or the AC text edit names an expired criterion, THE SYSTEM SHALL refuse and say it is expired; `check_acceptance_criteria` with `all` SHALL leave expired criteria unchanged.
- AC-5: WHEN `replace_acceptance_criteria` runs on a block holding expired criteria, THE SYSTEM SHALL keep the expired lines byte-for-byte and SHALL NOT assign a number an expired criterion holds.
- AC-6: THE CLI SHALL expose the same mutation, and the MCP tool SHALL be classified `req-scoped`.

(ID 는 `add_requirement` 가 정한다. 제목과 문구는 초안이다. scope 는 파서·규칙 = PARSE, 변이 = NODE(+ MCP/CLI 인터페이스 요구)로 나눴다. 규칙 §29.1 의 「다른 시스템 경계」 기준이다. 하나로 합치면 AC 11개가 된다.)

### 8.2 일부러 넣지 않은 것 (사용자 요구 밖)

- expired AC 부활 도구, 날짜를 직접 넘기는 인자, 여러 AC 를 한 번에 expire 하는 배열 입력(한 번에 한 요구는 지키지만 AC 배열은 선택사항).
- 기존 「Retired in 4.0.0」 60줄의 일괄 이전. 원문이 이미 지워졌고 날짜가 줄에 없다. 이전하면 5개 요구의 거짓 gap 과 4개의 체크 모순이 풀린다. 하지만 별도 결정 사항이라 후속 작업으로 남긴다.
- 표식 문법에 거의 맞지만 틀린 줄을 알리는 경고(그런 줄은 살아 있는 AC 로 남는다. 안전 쪽 실패라 생략했다).
- AC 단위 trace 관계(`supersedes_ac` 같은 것). 표식의 `→ REQ-ID` 로 충분하다.

## 9. 범위 밖 관찰 (보고만)

- `editAcceptanceCriteria`(`check-ac.ts:72-106`, CLI `edit-ac`)는 verified 요구를 막지 않는다. 반면 `replace_acceptance_criteria` 와 `update_requirement_fields` 는 `assertEditable` 로 막는다(`edit-requirement.ts:90-93`, `:170`, `:240`). 같은 AC 본문 변경에 통과 조건이 둘로 갈려 있다.
- 「verified 모양」 술어가 네 곳 이상에 복제돼 있다(§4.1). expired 를 파서에서 가르지 않고 소비처마다 거르게 하면 이 복제가 그대로 결함 경로가 된다.
- AC 단위 인용 확인 장치가 없다. 테스트가 존재하지 않는 `REQ AC-n` 을 인용해도 아무도 알리지 않는다(`test-citations.ts:155-164` 는 요구 ID 만 확인한다). 번호를 다시 쓸 때 위험이 바로 이 틈으로 들어온다.
- FR-FLOW-022 AC-1 의 대체는 Change Notes 기록 없이 Research 산문으로만 남아 있다(§3.3). 규칙 §26-2 와 어긋난다.
