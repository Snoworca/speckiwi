## 1. Research Purpose

이 문서는 SpecKiwi v1.0.0 SRS를 기준으로 `speckiwi` CLI 인터페이스를 어떻게 구현할지 연구한 결과를 정리한다. 목표는 구현자가 바로 TDD 계획으로 전환할 수 있도록 command별 책임, core 의존성, 입력 검증, JSON 출력, exit code, mutation 안전성, `add-requirement` 구현 전략을 명확히 하는 것이다.

## 2. Key Conclusions

CLI는 business logic을 직접 구현하지 않는 얇은 adapter여야 한다. `src/cli`는 argv parsing, help, stdout/stderr, exit code, human/json formatting만 담당하고, root resolution, SRS parsing, validation, query, mutation, patch 생성은 `src/core`로 위임한다.

현재 저장소의 `package.json`은 과거 YAML 중심 설명, `node >=20`, `bin: ./bin/speckiwi` 등으로 SRS v1.0.0과 맞지 않는다. 실제 구현 단계에서는 SRS의 Node.js package layout과 `bin: ./dist/cli/index.js`, `engines: >=22`, Markdown-only 설명으로 정리해야 한다.

CLI 구현 순서는 read-only 명령을 먼저 완성한 뒤 mutation 명령을 추가하는 것이 안전하다. parser, validator, normalized record, query가 안정되어야 `update-status`, `check-ac`, `add-evidence`, `add-trace`, `add-requirement`를 최소 변경 patch로 구현할 수 있다.

## 4. Proposed CLI Architecture

Recommended package shape:

```text
src/
├─ cli/
│  ├─ index.ts
│  ├─ commands.ts
│  ├─ context.ts
│  ├─ exit.ts
│  └─ formatters.ts
├─ core/
│  ├─ project-root.ts
│  ├─ parser/
│  ├─ validator/
│  ├─ query/
│  ├─ mutation/
│  ├─ patch/
│  ├─ format/
│  └─ types.ts
└─ mcp/
```

`src/cli/index.ts` should be the executable entrypoint with a Node shebang. It should import the CLI program builder, invoke `runCli(process.argv, process.cwd(), process.stdout, process.stderr)`, and set `process.exitCode`.

`src/cli/commands.ts` should register every command and convert parsed argv into typed command input. The command module should not parse Markdown, touch files directly, or know patch details.

`src/cli/context.ts` should resolve common options into a `CliContext`: project root, output mode, color mode, quiet mode, cwd, stdout, stderr.

`src/cli/exit.ts` should map typed results and known errors to SRS exit codes. This prevents command implementations from scattering numeric exit codes.

`src/cli/formatters.ts` should convert core results into human-readable text, table/plain output, Markdown summary, or JSON. Formatter functions should be deterministic and easy to snapshot test.

## 5. Command Implementation Strategy

### 5.1 Entrypoint and Common Options

Use Commander or a similar Node.js CLI framework only in `src/cli`. The framework should provide command parsing and help generation, while all domain behavior remains in core.

Common options should be registered once and inherited by subcommands:

- `--root <path>`: override root auto-detection.
- `--json`: request machine-readable output.
- `--no-color`: disable ANSI output.
- `--quiet`: suppress non-essential success messages.
- `--help` and `--version`: handled by the CLI framework.

`--json` must be treated as an output contract: stdout must contain valid JSON only, with no banners, progress text, color escape sequences, or mixed human text.

### 5.2 `speckiwi init`

Implementation should use bundled UTF-8 template assets for `00.index.md`, `90.appendix.md`, and `SRS-MD-Rules-v1.0.0.md`. It should create `docs/spec` when absent and refuse to overwrite existing files unless `--force` is set.

The `--agent-file <agents|claude|both|none>` option should create or append the SRS workflow snippet. This is a mutation command, so it should support the same write safety conventions as other mutations even though the SRS does not explicitly require `--dry-run` for `init`.

### 5.3 `speckiwi validate`

Implementation should call a core workspace loader, parser, and validator. `--scope` and `--target` can be applied either before validation for focused checks or after validation for filtered reporting, but global structural errors such as duplicate IDs should still be detectable when possible.

Exit behavior:

- no validation errors: exit `0`.
- validation errors: exit `1`.
- warnings with `--fail-on-warning`: exit `1`.
- invalid arguments: exit `2`.
- file I/O failure: exit `3`.
- fatal parse failure: exit `4`.

`--json` should emit a diagnostics array or a stable validation result object. The appendix defines the diagnostic record shape and should be treated as the minimum JSON contract.

### 5.4 `speckiwi extract`, `list`, and `show`

These commands should use the same normalized requirement record from parser/query core.

`extract` is the lowest-level derived view. It should support filters and optionally include the raw Markdown block. `list` is a user-facing filtered listing with `plain`, `table`, or `json` formatting. `show` retrieves exactly one requirement by ID and can return human text, normalized JSON, or raw Markdown.

Implementation detail:

- Query filtering should use AND semantics for multiple filters.
- Default sort should be target, scope, ID for `list`.
- `show` should return exit `2` for a missing ID because the SRS classifies this as a usage or argument-level failure.

### 5.5 `speckiwi targets` and `scopes`

These commands should parse `00.index.md` Target Map and Scope Map, then join requirement counts from the normalized records. They should not infer unknown scopes or targets from requirements as canonical data. Unknown target/scope occurrences belong in diagnostics from validation.

### 5.6 Mutation Commands for Existing Blocks

`update-status`, `check-ac`, `uncheck-ac`, `add-evidence`, and `add-trace` should share one mutation workflow:

1. Resolve root and load workspace.
2. Parse requirements and diagnostics.
3. Validate command input.
4. Locate target block and line ranges.
5. Build a line-based patch without changing unrelated lines.
6. Validate mutation-specific guards.
7. If `--dry-run`, return patch summary only.
8. If applying, write atomically and preserve newline style.
9. Return changed record or mutation summary.

`update-status` should change only the `Status` row. `check-ac` and `uncheck-ac` should change only matching task-list lines. `add-evidence` and `add-trace` should append one table row to the appropriate section. No mutation command should re-render an entire Requirement Block.

### 5.7 `speckiwi summary --target`

Summary should be a pure query over normalized records plus validation-derived facts. It should include status counts, type counts, blocked list, implemented-but-not-verified list, verified list, and missing evidence list. If `--target` is omitted, SRS says the active target should be used.

### 5.8 `speckiwi links check`

Local Markdown links should be checked with Node.js `fs` and `path`; GitHub URLs should be syntax-checked only by default. `--include-external` can opt into external checks, but the parser performance requirement says default commands must not perform network calls.

Requirement references in Trace Links should be validated against parsed requirement IDs. Broken Requirement references should align with validation diagnostics such as `SRS-E012`.

### 5.9 `speckiwi mcp`

The command should lazily start the MCP adapter and then hand control to stdio transport. In MCP mode stdout is reserved exclusively for MCP JSON-RPC messages. CLI banners, help-like text, startup logs, warnings, and errors must go to stderr.

## 6. Options and Input Validation

Validation should be split into CLI-level validation and core-level validation.

CLI-level validation:

- missing required positional arguments and options.
- enum parsing for `--format`, `--agent-file`, status, type, risk, stability, and verification method where applicable.
- repeated option handling for filters, AC IDs, `--ac`, and `--checked-ac`.
- JSON parsing for structured `--evidence` and `--trace` inputs.
- conflict checks such as `show --json --markdown` if both formats cannot be represented together.

Core-level validation:

- root exists and resolves to a project with `docs/spec/00.index.md`.
- path traversal is rejected for any file-affecting operation.
- target exists in Target Map where required.
- scope exists in Scope Map where required.
- Requirement ID matches the SRS-MD regex and exists for commands that target an existing block.
- status belongs to allowed SRS statuses.
- `verified` status requires all AC checked plus at least one evidence row with non-empty reference.
- mutation commands fail without writing when validation or guard checks fail.

For Windows support, command tests should avoid shell-specific quoting assumptions. Long text values such as requirement statements and rationales should be accepted as normal option strings, and future enhancement can add `--requirement-file` or stdin support if command-line quoting becomes painful. That enhancement is not required by the current SRS.

## 7. JSON Output and Exit Code Contract

### 7.1 JSON Output

The SRS requires JSON output to be a derived view, not the canonical source. The implementation should keep one shared set of serializable types:

- `RequirementRecord`
- `Diagnostic`
- `TargetSummary`
- `ScopeSummary`
- `MutationResult`
- `PatchSummary`

Recommended mutation JSON envelope:

```json
{
  "ok": true,
  "command": "update-status",
  "dryRun": false,
  "file": "docs/spec/30.cli-interface.srs.md",
  "requirementId": "IR-CLI-010",
  "diagnostics": [],
  "patch": {
    "changedLines": 1
  }
}
```

Handled validation results, especially `validate --json`, may return JSON with exit code `1` because validation failure is the command's domain result. Usage errors, I/O errors, fatal parse errors, and mutation-denied errors should write clear error messages to stderr. When `--json` is set, stdout should either contain the command's valid JSON result or remain empty on pre-result failures; it must never contain partial human text.

### 7.2 Exit Codes

| Code | Meaning | CLI Implementation Rule |
|---:|---|---|
| `0` | Success | command completed and guards passed |
| `1` | Validation error | `validate` found errors or warnings with `--fail-on-warning` |
| `2` | Usage, argument, or root resolution error | invalid option, missing required input, missing ID, root not found |
| `3` | File I/O error | read/write failure, permission issue, missing required file |
| `4` | Fatal parse error | parser cannot continue at workspace level |
| `5` | Mutation denied, status transition denied, verified guard failure | no file write allowed on this path |
| `6` | MCP server fatal error | only for `speckiwi mcp` startup/runtime fatal failure |

## 8. `add-requirement` CLI Implementation Strategy

`add-requirement` is the highest-risk CLI mutation because it creates a complete new Requirement Block. It should not be implemented in `src/cli`; the CLI should call `core/mutation/add-requirement`.

Required CLI inputs:

- `--type <Type>`
- `--scope <Scope>`
- `--target <Target>`
- `--title <Title>`
- `--requirement <Text>`
- at least one `--ac <Text>` or `--checked-ac <Text>`

Optional inputs:

- `--status <Status>` with default `planned`
- `--priority <Priority>`
- `--tags <Tags>`
- `--risk <Risk>`
- `--stability <Stability>`
- `--verification-method <Method>`
- `--rationale <Text>`
- `--implementation-notes <Text>`
- `--related-docs <Docs>`
- `--github-issue <Url>`
- `--evidence <JSON>`
- `--trace <JSON>`
- `--dry-run`
- `--json`

Core algorithm:

1. Load `00.index.md` and all scope SRS documents.
2. Resolve `--scope` against Scope Map `Prefix` first. If full scope names are later supported, ambiguous names must be rejected.
3. Validate `--target` against Target Map.
4. Map `--type` to ID prefix using SRS-MD type rules, for example `interface -> IR`.
5. Scan every existing Requirement ID, including `discarded` requirements, and select the next number for `{TYPE_PREFIX}-{SCOPE_PREFIX}-{NNN}`.
6. Normalize AC input into ordered `AC-1`, `AC-2`, ... task list lines.
7. Build metadata table with required fields `Type`, `Target`, `Status` and optional fields in a stable order.
8. Build all fixed sections: Requirement, Rationale, Acceptance Criteria, Verification Evidence, Trace Links, Research / Analysis, Implementation Notes, Change Notes.
9. If status is `verified`, enforce all AC checked and at least one evidence row with non-empty `Reference`.
10. Locate the end of `## 4. Requirements` in the target scope document and insert before the next level-2 heading.
11. Preserve existing newline style and avoid reformatting surrounding content.
12. Run a self-validation pass on the generated block or full workspace before writing, if practical.
13. For `--dry-run`, return generated ID, target file, diagnostics, and patch summary without writing.

Important interpretation: `IR-CLI-019` and `FR-NODE-008` define insertion at the end of the `## 4. Requirements` section. In current scope documents this means before `## 5. Cross-scope Dependencies`, not necessarily at absolute file end.

Structured `--evidence` and `--trace` should be JSON arrays or objects normalized into table rows. Invalid JSON should be a usage error (`2`). Semantically invalid evidence for `verified` should be a mutation guard failure (`5`).

## 9. TDD Test Strategy

Tests should be written before implementation and should run against temporary fixture copies for every mutation command.

Unit test groups:

- `test/cli/argv.test.ts`: command parsing, required options, enum validation, repeated options.
- `test/cli/formatters.test.ts`: human output, JSON output, no ANSI with `--no-color`, quiet mode.
- `test/cli/exit.test.ts`: known error classes to exit code mapping.
- `test/core/query/*.test.ts`: filter AND semantics, target/scope counts, summary lists.
- `test/core/mutation/*.test.ts`: patch generation and guard rules.

Integration test groups:

- `test/cli/read-only.test.ts`: run `validate`, `extract`, `list`, `show`, `targets`, `scopes`, `summary`, `links check` through the built CLI entrypoint.
- `test/cli/mutation.test.ts`: run mutations against temp fixture directories and assert exact changed lines.
- `test/cli/add-requirement.test.ts`: required input failure, successful append, auto ID, discarded ID non-reuse, `verified` guard, dry run no write.
- `test/cli/mcp-command.test.ts`: `speckiwi mcp` stdout/stderr separation at startup boundary.

Fixture requirements:

- valid baseline SRS with multiple scopes and targets.
- duplicate ID fixture.
- missing metadata fixture.
- malformed heading fixture.
- verified guard failure fixture.
- empty evidence and trace tables.
- Windows CRLF fixture.
- scope document with sections after `## 4. Requirements` to verify insertion point.

Regression assertions should include exact file diff checks. For mutation commands, tests should assert unrelated lines remain byte-for-byte unchanged apart from expected newline normalization preservation.

## 10. Major Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| CLI and MCP behavior diverge | Agents and humans see different requirement state | force both adapters to call shared core services and shared schemas |
| JSON stdout polluted by human text | automation breaks | centralize formatter and forbid banners/progress text when `--json` is set |
| Mutation commands reformat documents | Git diff becomes noisy and unsafe | use line-based patch engine; assert exact diffs in tests |
| `verified` status applied without evidence | SRS trust model breaks | implement verified guard in core and reuse it in every mutation path |
| `add-requirement` ID collision or discarded ID reuse | requirement traceability breaks | scan all existing IDs globally before generating next ID |
| Scope insertion point ambiguity | new block could be placed outside Requirements section | use `## 4. Requirements` end as canonical insertion point and test it |
| Windows path and newline differences | CLI fails or corrupts files on Windows | normalize paths for output, use platform-independent path checks, preserve original newline style |
| CLI framework leaks implementation details into core | MCP reuse becomes harder | keep Commander or equivalent imports inside `src/cli` only |
| Current package metadata is stale | bin/runtime/package behavior mismatches SRS | update package metadata early in implementation foundation phase |
| Shell execution from user input | security issue in agent workflows | use Node `fs`/`path`; do not call shell or Git commands from core |

## 11. Suggested Implementation Order

1. Foundation: update package metadata, create `src/cli` skeleton, shared result/error types, stdout/stderr test harness, and root resolution.
2. Parser baseline: implement SRS discovery, index parsing, Requirement Block parsing, normalized record, diagnostics.
3. Validator and query: implement validation registry, filters, target/scope counts, summary calculations.
4. Read-only CLI: implement `validate`, `extract`, `list`, `show`, `targets`, `scopes`, `summary`, `links check`.
5. Patch engine: implement line-based patch primitives, newline preservation, atomic write, dry-run summary.
6. Existing-block mutations: implement `update-status`, `check-ac`, `uncheck-ac`, `add-evidence`, `add-trace`.
7. `add-requirement`: implement shared core mutation service and CLI adapter after parser, validator, and patch engine are stable.
8. MCP launcher boundary: implement `speckiwi mcp` with stdout/stderr contract and reuse existing core services.
9. Help and documentation: complete command-level help examples and README/AGENTS command references.
10. Release validation: run unit, integration, typecheck, lint, mutation diff tests, and SRS traceability review.

## 12. Open Implementation Notes

- The SRS allows Commander or a similar CLI framework. Commander is already present in current dependencies and is acceptable if dependency cleanup keeps it.
- The SRS does not fully specify JSON error envelopes for all non-validation failures. The safest v1.0.0 behavior is strict stdout purity: JSON results on stdout only when a command reaches a result object, all operational errors on stderr.
- `init` dry-run behavior is not specified. It can be deferred unless implementation planning decides consistent mutation UX is worth adding as a non-breaking enhancement.
- Long multi-line requirement statements are not explicitly covered by CLI options. v1.0.0 can accept one-line option values; file/stdin input can be considered for v1.1.0 if needed.
