## 1. 질문과 결론

**질문**: 작업 디렉터리에서 워크트리를 만들어 개발하는데, `/kiwi-wave-master` 는 원본 디렉터리 세션에서 분리된 워크트리의 작업을 진행할 수 없다. 도구 문제인가 스킬 문제인가?

**결론: 도구와 스킬 양쪽에 서로 독립적인 hard blocker 가 있다. 한쪽만 고쳐도 실행되지 않는다.**

- **도구 계층 hard blocker**: SpecKiwi MCP 의 workspace root 는 **서버 프로세스의 cwd 로만** 결정되며, 이는 `REL-MCP-004` / `IR-CLI-045` 로 **명시적으로 설계된 금지**다. Claude Code 는 세션 시작 시 MCP 서버를 1회 기동한 뒤 **세션 cwd 가 워크트리로 바뀌어도 재기동하지 않는다**(§3 실측). 따라서 원본 디렉터리에서 시작한 세션은 그 세션이 살아 있는 동안 SRS mutation 을 **영구히 원본 저장소에** 쓴다. 프롬프트로 우회 불가능하다.
- **스킬 계층 hard blocker**: 하위 실행 스킬 `kiwi-coder`(§0.9) 와 `kiwi-planner`(§0.8) 는 **cwd 외부 path 편집을 critical 게이트로 차단**한다. 호스트 세션 입장에서 워크트리 파일은 전부 cwd 외부이므로, **MCP 문제를 해결하더라도** Task 단위 구현이 하드 중단된다.
- **추가로 스킬 계층에는 조용한 오작동 요인도 있다**: 배포된 `kiwi-wave-master v0.1`(FR-FLOW-029)에는 worktree·root 어휘가 **한 글자도 없고**, root 정합성 preflight 도 없다. 그래서 위 도구 제약이 명시적 실패가 아니라 **잘못된 저장소에 기록**되는 형태로 먼저 나타난다.

한 문장 요약: **도구는 SRS 쓰기를 호스트에 못 박고, 스킬은 코드 쓰기를 cwd 안으로 못 박으며, wave-master 는 둘 중 어느 것도 사전에 알려주지 않는다.**

## 3. 실측 재현 — split-brain 증명

동일 세션에서 다음 순서로 관측했다.

```
(1) 세션 cwd = C:\Work\git\_Snoworca\speckiwi
    mcp_workspace_info → workspaceRoot = C:\Work\git\_Snoworca\speckiwi
                         rootSource     = server-cwd-discovery
                         activeTarget   = v2.4.1

(2) EnterWorktree(path = C:\Work\git\_Snoworca\wt-speckiwi-wave-master-g0)
    → 세션 cwd 이동 성공, Bash `pwd` = /c/Work/git/_Snoworca/wt-speckiwi-wave-master-g0

(3) 같은 세션에서 다시 mcp_workspace_info
    → workspaceRoot = C:\Work\git\_Snoworca\speckiwi   ← 그대로. 이동하지 않음
       activeTarget = v2.4.1                            ← 호스트 값

(4) 워크트리 cwd 에서 CLI 실행
    speckiwi active-target --json → activeTarget = v2.3.0.1, total = 115 REQ  ← 워크트리 값
```

같은 시점 두 저장소의 실제 SRS 상태는 서로 다르다.

| 위치 | `docs/spec/00.index.md` Active Target |
| --- | --- |
| 호스트 `speckiwi/` | `v2.4.1` |
| 워크트리 `wt-speckiwi-wave-master-g0/` | `v2.3.0.1` |

**따라서 한 세션 안에서 도달 가능한 SRS SSOT 가 두 개다.** MCP 는 호스트를, CLI 는 cwd(=워크트리)를 가리킨다. 파일 편집·테스트·`git` 은 워크트리에, MCP 기반 요구사항 authoring·status·evidence·trace link 는 호스트에 기록되는 **split-brain** 이 성립한다. wave-master 의 핵심 계약(§4 target 등록, §6 완료 표시)이 정확히 이 축에 걸쳐 있으므로 스킬은 구조적으로 완주할 수 없다.

## 4. 도구 계층 원인 (5건)

### T1. MCP workspace root 는 프로세스 cwd 전용 — 설계된 금지

`src/mcp/adapter.ts:37` 에서 root 는 서버 프로세스 cwd 로 해석되고, 호출 인자에 `root` 또는 `workspaceRoot` 가 들어오면 `src/mcp/adapter.ts:46-63` 이 **거부**한다.

```
code       : MCP_WORKSPACE_ROOT_UNSUPPORTED
diagnostic : SRS-E075
message    : Per-call workspace root override is not supported;
             start a server for the intended workspace root.
```

주석은 `REL-MCP-004 AC-2: explicit root 소스는 존재하지 않는다` 라고 못 박는다. per-call root 주입은 **버그가 아니라 계약**이다. (팩토리 함수명이 `createTestMcpServer` 이지만 `src/mcp/server.ts:27` 이 이를 그대로 프로덕션 경로로 사용한다.)

### T2. 서버 기동 시 root 지정도 봉쇄됨

`speckiwi mcp --root <path>` 는 숨김 옵션으로 등록되어 있으나 **오직 명확한 에러를 내기 위해서만** 존재한다 (`src/cli/commands/mcp.ts:25-28`).

```
IR-CLI-045: mcp 는 root 옵션을 지원하지 않는다.
            project root 는 서버 프로세스 cwd 탐색으로만 해석된다.
```

MCP 의 root 를 정하는 수단은 **서버 프로세스를 원하는 디렉터리에서 띄우는 것 하나뿐**이다.

### T3. 세션 MCP 는 1회 기동·재기동 없음, 사용자 스코프 등록

`~/.claude.json` 전역 등록은 다음과 같다.

```json
"speckiwi": { "type": "stdio", "command": "cmd", "args": ["/c", "speckiwi", "mcp"], "env": {} }
```

cwd 지정 인자가 없으므로 서버는 **Claude Code 세션의 기동 cwd** 를 상속한다. §3 실측대로 `EnterWorktree` 로 세션 cwd 가 바뀌어도 **이미 떠 있는 stdio 프로세스의 cwd 는 바뀌지 않는다**. 서브에이전트는 세션 MCP 연결을 공유하므로 자식 스킬도 동일하게 호스트에 묶인다.

부수 결함: 위 거부 응답의 `recovery.tool` 은 `restart_mcp_server` 를 가리키는데 **그런 도구는 존재하지 않는다**(`src/` 기준 문자열 1건, 빌드 사본 제외). 에이전트는 존재하지 않는 복구 수단을 안내받고, 애초에 MCP 프로세스 수명은 하네스 소유라 에이전트가 재기동할 수도 없다.

### T4. 셸 cwd 비지속 + 서브에이전트 cwd 상속

Bash 도구는 매 호출 후 세션 루트로 되돌아간다(실측: `cd` 직후 `Shell cwd was reset to C:\Work\git\_Snoworca\speckiwi`). 스킬이 `cd <worktree>` 로 머무르는 전략은 성립하지 않는다. `Agent` 도구의 `isolation: "worktree"` 는 **새 워크트리를 만드는** 옵션이지 **기존 워크트리에 붙는** 옵션이 아니다.

### T5. CLI 와 MCP 의 root 해석이 서로 반대다

`src/core/project-root.ts` 는 cwd 에서 위로 올라가며 `.git` 을 찾는다. 워크트리의 `.git` 은 **파일**이지만 존재 검사는 파일에도 성공하므로 **CLI 의 root = 워크트리**로 해석된다(§3 (4) 실측). 즉 같은 세션에서:

| 표면 | root 해석 근거 | 결과 |
| --- | --- | --- |
| MCP | 서버 프로세스 cwd (고정) | 호스트 |
| CLI | 호출 시점 cwd 탐색 | 워크트리 |

CLAUDE.md 와 kiwi 스킬들이 **CLI 를 MCP 폴백으로 규정**하고 있으므로 이 분기는 실제로 유발된다. 더욱이 SRS mutation lock(`withSrsMutationLock(root, ...)`)은 **root 스코프**라 두 root 의 lock 은 서로를 보지 못한다 — 교차 저장소 동시 쓰기에 대한 상호배제가 없다.

## 5. 스킬 계층 원인 (5건)

### S1. wave-master v0.1 에 root/worktree 개념 자체가 없다

배포본 `kiwi-wave-master/SKILL.md`(169행) 전문에 `worktree`·`워크트리`·`root`·`--wt`·`격리` 어휘가 **모두 0건**이다. Phase 0 은 "입력 문서 해석 + waves.jsonl 경로 해석"만 하고 **어느 저장소에서 실행 중인지 결정·검증하는 단계가 없다**. root 는 암묵적으로 "지금 cwd" 하나로 가정된다.

### S2. 유일한 격리 수단(`--wt`)은 attach 가 아니라 create 다

wave-master 본문에는 격리 위임 규정 자체가 없고, kiwi 계열에서 worktree 를 다루는 스킬은 `kiwi-pipeline` 하나뿐이다. 그런데 `kiwi-pipeline` §2.6.1(FR-FLOW-027)은 다음과 같다.

> `--wt` 또는 worktree 격리 요청 시 … **전용 git worktree 를 새로 생성(create)** 한다 — `git worktree add <path> -b <cycle-branch>`

즉 (a) 사용자가 이미 만든 워크트리를 지정할 수 없고, (b) wave 마다 별도 워크트리가 생겨 **wave 간 누적(앞 wave 가 뒤 wave 의 토대, SKILL §3)이 깨진다**. wave-master 의 전파 목록(§7.2/§7.3)은 `--max`/`--mini`/`--loops` 뿐이라 `--wt` 는 전파되지도 않는다.

### S3. 상태파일 root 규칙이 3종으로 갈린다

| 축 | 해석 규칙 | 근거 |
| --- | --- | --- |
| MCP SRS | 서버 프로세스 cwd | `adapter.ts:37` |
| `waves.jsonl` / `pipeline.jsonl` | `git rev-parse --show-toplevel` | `_shared/kiwi/waves-event.md:13`, `pipeline-event.md:13` |
| `.kiwi/sessions/`, `docs/plans/`, `pm.lock`, `coder.lock` | **cwd 상대** | `kiwi-coder/SKILL.md:10,28,166`, `kiwi-pm/SKILL.md:152-158,176`, `kiwi-planner/SKILL.md:180-182` |

워크트리 안에서 `git rev-parse --show-toplevel` 은 **워크트리 경로**를 돌려준다. 따라서 진행 로그는 워크트리를 따라가고 SRS 는 호스트를 따라간다. 호스트에서 재개하면 워크트리에 쌓인 완료 표시가 보이지 않아 **§0.6 멱등 재개와 §6 mark-complete-only-after-success 가 동시에 무너진다**. 실측상 호스트와 워크트리가 **각각 별도의 `kiwi/pipeline.jsonl`** 을 보유하고 있어 `kiwi-pipeline` 재개(FR-FLOW-026/028)도 이미 분기해 있다. 세 번째 축의 결과로 `pm.lock`·`coder.lock` 이 root 마다 별개 파일이 되어, 두 root 에서 같은 `run_id` 가 동시에 돌아도 동시 실행 방지가 작동하지 않는다.

부수 결함 — `waves-event.md:76-78` 의 emit 예시는 폴백이 죽어 있다.

```bash
WAVE_DIR=$(git rev-parse --show-toplevel 2>/dev/null)/kiwi
[ -z "$WAVE_DIR" ] && [ -d "./kiwi" ] && WAVE_DIR="./kiwi"   # 도달 불가
```

git 실패 시 `WAVE_DIR` 은 빈 문자열이 아니라 `/kiwi` 가 되므로 이후 `-z` 분기가 **절대 발동하지 않는다**.

### S4. root 정합성 preflight 부재 → 조용한 오작동

스킬 어디에도 "MCP 가 보고하는 `workspaceRoot` 가 내 cwd/git-root 와 같은가"를 확인하는 게이트가 없다. 그 결과 §3 의 split-brain 이 **에러 없이** 진행되고, 잘못된 저장소에 요구사항·상태·증거가 기록된 뒤에야 발견된다. 도구 제약은 fail-closed 로 드러났어야 할 사안인데, 스킬이 그 신호를 읽지 않아 fail-open 이 된다.

### S5. 하위 스킬의 `cwd 외부 path 금지` critical 게이트 (스킬 계층 hard blocker)

- `kiwi-coder/SKILL.md:26` §0.9 — "**외부 모듈 수정 금지**. cwd 외부 path 가 sidecar `files[]` 또는 실제 변경에 진입 시 즉시 중단 + AskUserQuestion"
- `kiwi-coder/SKILL.md:65` — "시니어 코더가 cwd 외부 파일 편집 시도 → 즉시 차단 + **CRITICAL**" (사용자 override 없음)
- `kiwi-planner/SKILL.md:37` §0.8 — 동일 게이트, 사이드카에 `external_module_impact` 기록

호스트 세션에서 워크트리 파일은 전부 cwd 외부다. **따라서 T1~T3 을 전부 해결해도** Task 마다 이 게이트가 걸린다. 이 항목이 §1 의 "스킬 계층에도 독립적인 hard blocker 가 있다" 근거다.

## 6. 이미 존재하는 선행 작업 (미병합·미완료)

이 문제는 과거에 인지·착수되었으나 **메인 라인에 병합되지 않았고, 그 브랜치 자체 SRS 기준으로도 완료 상태가 아니다**.

- 브랜치: `work/kiwi-wave-master-multiroot-g0` (워크트리 `C:/Work/git/_Snoworca/wt-speckiwi-wave-master-g0`)
- 커밋: `3c5eb46 harden multi-root wave execution` (59 파일, +11,853), `a12fe15 checkpoint fail-closed Wave G0 host` (132 파일, +20,136) — 합계 약 32,000행
- 그 브랜치에서 `FR-FLOW-029` 는 **DISCARDED** 처리되고 `FR-FLOW-036`(root-bound existing-target orchestration) / `FR-NODE-071`(root-bound wave runtime) / `IR-FLOW-001`(manifest·event 프로토콜) 로 대체되었다.
- **다만 세 요구 모두 `Status = in_progress`** 이며, 브랜치 자체 검증에서 `SRS-W015`("Completed Work Log requirement is not completed") 경고 14건이 나오고 `newWorkCandidates` 에 그대로 남아 있다. Completed Work Log 항목은 있으나 요구 블록은 닫히지 않았다.

핵심 해법 구조는 **런타임(도구) 계층 이동**이다.

| 구성요소 | 역할 |
| --- | --- |
| `wave-spec-client.ts:791-794` | root 마다 **별도 `speckiwi mcp` 프로세스를 `cwd: workspaceRoot` 로 spawn** (`StdioClientTransport`) |
| `wave-root-connector.ts` | root 별 typed client 를 `RootConnector` 로 봉인, readiness 를 호출자 독립적으로 유도 |
| `wave-orchestrator.ts` / `wave-service.ts` | immutable run manifest + exact req allowlist + SHA handoff chain |
| `wave-run-host.ts` / `manifest-child-runner.ts` | child pipeline 실행 호스트 |

설계 원칙은 코드 주석이 그대로 말한다(`wave-spec-client.ts:88-90`).

> The agent host owns one MCP process whose workspace is fixed by its cwd.
> Deliberately absent: root/workspace overrides and caller-supplied readiness attestations.

개정된 `kiwi-wave-master v0.2` 는 **모든 `spec_root` 가 하나의 누적 integration worktree 안에 포함**되어야 하고, `wave-{n}` 을 SRS target 으로 만들지 않으며, `--wt` 를 child 에 전달하지 않는다고 규정한다. root preflight(`connector workspaceRoot == spec_root`)와 `<git-root>/kiwi/...` 경로 고정도 이미 담고 있다.

**그대로 켤 수 없는 이유 2가지**:

1. **security HOLD** — production manifest-child 실행은 `MANIFEST_CHILD_TRUST_SAFETY` 로 동기 fail-closed 한다(`manifest-child-runner.ts:93`). Windows 비권한 샌드박스에서 사용자 `auth.json` deny-read 를 강제할 수 없고 비-Windows 도 승인된 자격증명 경계가 없다. `--auto` 로도 우회 불가.
2. **릴리스 도구에 wave 표면이 없다** — 릴리스된 `speckiwi 2.4.1` 의 `speckiwi workflow --help` 에 `wave` 매치가 0건이다. v0.2 스킬이 참조하는 `workflow wave event-emit` / `workflow_wave_event_emit` 표면이 부재하므로, 런타임 병합 없이 스킬만 교체하면 동작하지 않는다.

## 7. 2차 피해 — 요구 ID 충돌 4건

워크트리마다 `docs/spec/` SSOT 가 독립적이고 ID 할당을 조율하는 수단이 없기 때문에, 두 라인이 **동일 ID 를 서로 다른 요구에 할당**했다.

| ID | 메인 라인 (`feat/2.3.0.1`, v2.4.0 verified) | 워크트리 브랜치 (multiroot-g0, in_progress) |
| --- | --- | --- |
| `FR-NODE-071` | work-mode model supports the tdd mode | Root-bound wave runtime and exact requirement isolation |
| `FR-FLOW-036` | SDS-MD Authoring Rules v1.0.0 and design.md template | kiwi-wave-master root-bound existing-target orchestration |
| `IR-CLI-071` | speckiwi mode accepts tdd | CLI wave manifest, event, resume, requirement-filter surfaces |
| `FR-MCP-052` | MCP work-mode tools get_work_mode / set_work_mode | MCP wave manifest, event, resume, requirement-filter tools |

브랜치가 분기점 이후 신규 도입한 ID 는 위 4건 + `IR-FLOW-001` 5건이며, 메인과 겹치는 것은 **정확히 위 4건**이다(`IR-FLOW-001` 은 메인에 부재이므로 충돌 아님). 메인 4건은 이미 v2.4.0 에서 **verified 로 릴리스**되었다.

따라서 선행 브랜치를 단순 병합하면 `SRS-E002`(Duplicate requirement ID) 4건이 발생한다. 병합 전 `speckiwi repair requirement-id-collisions` 워크플로(진단 → 명시적 keep/rename plan → apply)로 브랜치 측 ID 를 재할당해야 한다.

이 충돌은 본 연구 주제의 **결과물**이다. 워크트리 격리 작업에 spec-root 조율 계약이 없다는 사실이 그대로 ID 공간 분기로 나타났다.

## 8. 해결 방안

### 방안 A — 워크트리 대신 단일 root 브랜치 전환 (가장 단순, 1순위 권장)

워크트리를 만들지 말고 **한 저장소에서 `git switch` 로 브랜치를 전환**해 wave-master 를 실행한다.

- 파일·git·MCP·`kiwi/*.jsonl` **4축이 자동 정렬**되고 T1~T5·S3·S5 가 **모두 발생하지 않는다**
- **ID 공간이 하나로 유지**되어 §7 충돌을 애초에 만들지 않는다
- 비용 0(코드·스킬 변경 없음)
- 적합성: wave-master 는 정의상 **순차 오케스트레이터**(앞 wave 가 뒤 wave 의 토대)라 병렬 워크트리로 얻는 이득이 작다
- 제약: 다른 브랜치 작업과 동시 진행 불가(워크트리의 본래 이점 포기)

### 방안 B — 워크트리에서 세션을 새로 연다 (워크트리를 꼭 써야 할 때)

wave-master 를 호스트 세션에서 실행하지 말고, **워크트리 디렉터리를 cwd 로 하는 Claude Code 세션을 따로 시작**한다. MCP 서버가 워크트리에 pin 되어 4축이 정렬되고, cwd 게이트(S5)도 워크트리 기준으로 맞아떨어진다.

- 비용: 코드·스킬 변경 0
- 근거: T1~T3 이 요구하는 유일한 root 지정 수단이 "그 디렉터리에서 서버를 띄우는 것"이므로, 세션을 그 디렉터리에서 여는 것이 규범적 해법이다
- 확인법: 진입 직후 `mcp_workspace_info.workspaceRoot` 가 워크트리 경로인지 1회 확인
- **세션 중간의 `EnterWorktree` 는 해법이 아니다** — §3 이 반증한다

**주의 — 이 방안은 §7 의 ID 충돌 메커니즘을 재생산한다.** 워크트리의 SRS 는 이미 메인과 분기해 있으므로(v2.3.0.1 / 115 REQ), 거기서 신규 요구를 저작하면 병합 시 5번째 이후 충돌이 생긴다. 따라서 다음 단서가 필수다.

> 분기된 워크트리 세션에서는 **신규 Requirement ID 를 새로 할당하지 않는다**. 기존 요구의 구현·검증만 수행하고, 신규 저작이 필요하면 먼저 spec 을 메인과 동기화하거나 방안 A 로 전환한다.

- 부작용: cwd 가 워크트리가 되면 호스트 `docs/spec/` 이 cwd 외부가 되어 호스트 SRS 는 고칠 수 없다(대개 의도한 바이나 명시 필요)

### 방안 C — 스킬 패치: root preflight 게이트 (소규모, 방안 A/B 와 병행 권장)

fail-open 을 fail-closed 로 바꾸는 최소 변경. 실행을 가능하게 만드는 것이 아니라, **불가능함을 즉시 알리는** 것이 목적이다.

1. **Phase 0 root 정합성 게이트(필수)**: `mcp_workspace_info.workspaceRoot` 와 `git rev-parse --show-toplevel` 을 비교하여 불일치 시 **즉시 중단**하고 방안 A/B 를 안내한다. `--auto` 로도 우회 불가(critical gate).
2. **`waves.jsonl` root 고정**: 경로를 "그때그때의 git-root"가 아니라 run 시작 시 확정한 root 기준으로 pin 하여 재개가 갈리지 않게 한다. 아울러 `waves-event.md:76-78` 폴백 버그(§5 S3)를 수정한다.

**의도적으로 배제한 항목 — `--attach-wt <path>`**: 초안에서 검토했으나 성립하지 않아 철회한다. 세션이 이미 워크트리면 no-op 이고, 호스트 세션이면 T1~T3 상 불가능하며, 위 1번 critical gate 와 정면 충돌한다.

### 방안 D — 런타임 multi-root 호스트 도입 (대형, 별도 트랙)

선행 브랜치의 `wave-spec-client` / `wave-root-connector` / `wave-orchestrator` 계열을 메인에 들인다. root 별로 cwd-bound MCP 프로세스를 spawn 하므로 **한 세션에서 여러 root 를 정당하게 구동**할 수 있다 — 도구 제약을 우회하지 않고 그 제약(프로세스 cwd = root)을 그대로 준수하는 유일한 방식이다.

선결 조건:

1. §7 의 ID 충돌 4건을 `repair requirement-id-collisions` 로 해소
2. `MANIFEST_CHILD_TRUST_SAFETY` **security HOLD 해제 근거 확보** — 미해결 시 병합해도 production 진입 불가
3. 브랜치 3개 요구(`FR-FLOW-036`/`FR-NODE-071`/`IR-FLOW-001`)의 `in_progress` 잔여 작업 마감 (§6)
4. 약 32,000행 규모 변경의 회귀·보안 재검증
5. S5(하위 스킬 cwd 게이트)와 multi-root 실행의 정합 설계 — 게이트를 root 기준으로 재정의해야 한다

### 방안 E — MCP per-call root 허용 (비권장·기각)

`REL-MCP-004` / `IR-CLI-045` 가 의도적으로 금지한 설계다. 되돌리면 root 혼선·교차 저장소 오염 위험이 살아나며, T5 의 lock 상호배제 부재와 겹쳐 위험이 증폭된다. 승인된 대안은 이미 "root 별 서버 인스턴스"(방안 B/D)로 정해져 있다.

**부수 수정(방안 E 와 무관하게 필요)**: `src/mcp/adapter.ts:63` 의 `recovery.tool = "restart_mcp_server"` 는 존재하지 않는 도구를 가리킨다. 실행 가능한 안내(= 의도한 디렉터리에서 세션/서버를 기동하라)로 교체해야 한다. 단 이는 `REL-MCP-004` 계약 문구 변경이므로 SRS 갱신이 선행되어야 한다.
