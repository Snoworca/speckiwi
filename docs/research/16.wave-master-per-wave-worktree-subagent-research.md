# wave 단위 워크트리 격리 + 서브에이전트 실행 가능성 연구

| Field | Value |
| --- | --- |
| Date | 2026-08-08 |
| Target | 2.7.1 (Active Target) |
| Question | `/kiwi-wave-master` 의 각 wave 를 워크트리로 분리하고 서브에이전트에서 진행할 수 있는가? |
| Method | 런타임 실측(`isolation: "worktree"` 서브에이전트 2기) + SRS·스킬 계약 추적 + 독립 서브에이전트 2축 검증(사실 정확성 / 적대적 반박) |
| Prior work | `docs/research/12`, `docs/research/kiwi-orchestrator/{00 charter,02,05,06}` |

본 문서는 운영 연구 산출물이다. 구현 동작은 §8 에 매핑한 Requirement ID 가 관장한다.

> **초안 철회 기록.** 본 문서의 첫 판은 "wave 는 정의상 SRS mutation 을 포함하고 MCP root 가 호스트에 고정되므로 **불가능**하다"고 결론지었다. 적대적 검증이 그 논거를 반박했고, 반박의 근거를 전부 직접 재확인한 결과 **초안의 인과 주장은 틀렸다**. 아래는 정정된 판이며, 틀린 주장이 무엇이었는지는 §7 에 남긴다.

## 1. 결론

**기술적으로는 막혀 있지 않다. 그러나 wave 단위에서는 벽시계 이득이 0 이고, 남는 두 이득(base 브랜치 안전성·롤백 용이성)은 더 값싼 경로로 얻는 편이 낫다.**

세 문장으로 나누면:

1. **"SRS mutation 이 경계를 넘을 수 없어서 불가능"은 사실이 아니다.** 워커는 SRS 를 호출하지 않고 큐에 적고 호스트가 재생하는 분해가 이미 설계돼 있으며(`--defer-srs-mutation`), SRS 를 건드리는 사이클을 워크트리 안에서 도는 것은 이미 `verified` 요구다(`FR-FLOW-027`).
2. **wave 단위 격리는 벽시계 이득이 정확히 0 이다.** wave-master §5 는 앞 wave 가 `complete` 로 기록된 **뒤에야** 다음 wave 를 시작한다. 두 wave 는 원리적으로 겹칠 수 없다. 병렬화할 것이 없는 곳에 격리를 넣는 것이다.
3. **격리가 값을 하는 자리는 wave 가 아니라 wave 안의 task(lane) 다.** 거기서 막고 있는 것은 `--defer-srs-mutation` 인데, 이것은 **설계는 끝났고 phase 2 로 예약된 채 SRS·스킬·코드 어디에도 승격되지 않았다**(§6.1).

즉 답은 "불가능"이 아니라 **"가능하지만 wave 는 자를 자리가 아니다"** 이고, 자를 자리에서 막고 있는 것은 MCP 계약이 아니라 **승격되지 않은 설계 하나**다.

## 2. 오늘 측정한 것

`isolation: "worktree"` 서브에이전트 2기를 띄웠다. 둘 다 read-only 프로브였고 아무것도 쓰지 않아 런타임이 자동 정리했다.

### 2.1 서브에이전트는 진짜 워크트리를 받는다

| 항목 | 측정값 |
| --- | --- |
| cwd | `<repo>/.claude/worktrees/agent-<id>` |
| 브랜치 | `worktree-agent-<id>` (신규 생성) |
| `.git` | 파일 (`gitdir: <repo>/.git/worktrees/agent-<id>`) |
| 정리 | 변경 0건이면 자동 제거 — `git worktree list` 에서 사라짐 확인 |

격리 기구 자체는 실재하고 동작한다.

### 2.2 서브에이전트의 MCP 는 워크트리를 따라가지 않는다

```
git rev-parse --show-toplevel : C:/Work/git/_Snoworca/speckiwi/.claude/worktrees/agent-ac63094b612bac3dd
MCP workspaceRoot             : C:\Work\git\_Snoworca\speckiwi
rootSource                    : server-cwd-discovery
```

`docs/research/12` §4 T3 은 "서브에이전트는 세션 MCP 연결을 공유한다"를 **추론**으로 적었다. 이제 실측이다.

**이 측정의 의미는 초안이 붙인 것과 다르다.** 초안은 여기에 CLI 판독(`speckiwi active-target` → `v2.4.1`)을 나란히 놓아 "SSOT 가 둘"이라고 했는데, `FR-FLOW-042` 요구 본문이 **CLI 는 이 비교의 폴백이 아니다**(CLI 는 호출자 cwd 에서 root 를 해석하므로 검사가 공허해진다)라고 명시한다. 계약을 지키는 에이전트는 MCP 만 본다. 따라서 위 두 줄만이 유효한 증거이고, CLI 판독은 별개 현상 — **워크트리의 `docs/spec/` 이 낡았다**(§2.3) — 의 징후로 읽어야 한다.

그리고 이 상태는 `FR-FLOW-042` preflight 가 **중단시키도록 설계된 바로 그 상태**다. 워크트리 서브에이전트 안에서 wave-master 를 부르면 즉시 halt 한다.

### 2.3 워크트리 기준선은 현재 HEAD 가 아니다 — 다만 규칙은 미확정

직접 측정:

```
worktree HEAD          : 86a090d  (= main, 2026-07-18 "패키지 버전을 2.4.1로 올린다")
git log -1 feat/2.3.0.1: 7e9433d  ← 현재 HEAD, 불일치
세션 시작 HEAD          : e2e10e0  ← 불일치
main..feat/2.3.0.1     : 114 commits
```

**확실한 것**: 워크트리는 현재 브랜치 HEAD 도, 세션 시작 HEAD 도 아닌 커밋에서 열렸고, 오늘 기준으로 `feat/2.3.0.1` 의 커밋 **114개**를 못 본다.

**[철회] 규칙이 "기본 브랜치"라는 초안의 정정은 성립하지 않는다.** `02` §5.2 가 반증을 이미 담고 있다 — 이전 세션의 워크트리들은 `af4e623`(2026-07-30)에 있었는데, 확인 결과 그 커밋은 **`main` 에 없다**(`main` tip 은 2026-07-18). 기본 브랜치 가설로는 그 관측이 설명되지 않는다. `02`/charter C3 의 "세션 시작 HEAD" 가설도 오늘 관측과 어긋난다. **두 가설 모두 반례가 있으므로 기준선 결정 규칙은 미확정으로 남긴다.**

실무적으로는 규칙을 몰라도 결론이 같다: **기본 HEAD 에 기대면 안 되고, 원하는 커밋으로 명시 checkout 해야 한다.** 워크트리는 객체 DB 를 공유하므로 커밋된 sha 로의 이동은 가능하다(charter C3).

## 3. "불가능"이 아닌 이유

### 3.1 SRS 를 건드리는 사이클을 워크트리에서 도는 것은 이미 verified 요구다

`FR-FLOW-027`(Target v2.3.0.1, **Status = verified**, `docs/spec/60.workflow-release.srs.md:2210`):

> When the user requests worktree isolation or passes a `--wt` argument, the kiwi-pipeline skill SHALL create a dedicated git worktree and **run the cycle inside it**.

그리고 `kiwi-pipeline` §2.6.1 은 그 "cycle" 이 **전체 연구→계획→구현 사이클**임을 명시한다. 그 사이클은 kiwi-srs 저작·feasibility stability mutation·planner trace link 를 포함한다. 즉 이 저장소는 "SRS 를 쓰는 사이클이 워크트리 안에서 돈다"를 **이미 요구로 팔고 있다**.

### 3.2 워커가 SRS 를 직접 부르지 않는 분해가 설계돼 있다

`FR-FLOW-102` AC-2(`60.workflow-release.srs.md:6951`)가 직렬 dispatch 를 병렬 dispatch 와 대조하며 기술한다:

> "no `--defer-srs-mutation`, so `kiwi-coder`'s four mandatory MCP mutations execute at the host root"

부정문을 뒤집으면 병렬 dispatch 는 워크트리·전용 브랜치를 갖고 `--defer-srs-mutation` 을 넘긴다는 뜻이다. 설계 문서가 기전을 명시한다(`05.orchestrator-design.md:5707`, R20): 워커는 mutation 을 기존 `mcp_call_log[]` 큐에 `args_hash` dedupe 로 적고, **오케스트레이터가 host root 에서 재생한다**.

이 기전에 **granularity 제약은 없다.** task 에 되면 wave 에도 된다.

### 3.3 락 문제는 남은 blocker 가 아니다 — 이미 끝났다

`FR-NODE-131 — Orchestrator run lock keyed on the git common dir` 는 **Status = verified**, Target `2.6.0-phase1-kiwi-orchestrator` 다. AC-1 이 "한 `.git` 위의 두 워크트리가 같은 락 경로로 해소되고, 두 번째 획득은 `orchestrator-run-lock-held` 로 거부된다"를 고정한다.

단 구분해야 한다 — **SRS mutation 락은 여전히 root 상대다**(`src/core/mutation/srs-lock.ts:9`, `kiwi/.srs.lock`). 재키잉된 것은 **오케스트레이터 run 락**이다. 초안은 이 둘을 뭉쳐 "락 문제 해결됨"이라 했는데, 정확히는 **run 락은 해결, SRS 락은 미해결**이고, 후자는 §3.2 의 분해(워커가 SRS 를 안 부름)를 채택하면 애초에 발동하지 않는다.

### 3.4 MCP 제약은 실재하지만 범위가 좁다

정확한 진술은 이렇다.

| 명제 | 참/거짓 |
| --- | --- |
| `speckiwi mcp` 는 root 옵션을 거부한다 (`IR-CLI-045`) | 참 |
| MCP 도구 호출의 per-call root 는 거부된다 (`SRS-E075`) | 참 |
| **SpecKiwi 전반이 root 를 못 받는다** | **거짓** — `IR-CLI-002` 요구 본문이 "모든 주요 명령에서 공통 옵션 `--root` 지원"을 규정하고, `IR-CLI-045` 의 Implementation Note(`30.cli-interface.srs.md:2970`)가 **`mcp` 서브커맨드만 그 상속의 예외**로 둔다. 즉 `--root` 는 `mcp` 외 명령에서 살아 있다 |
| **한 세션에 MCP root 는 하나뿐이다** | **참** — 그리고 `IR-CLI-082` 의 `orchestrate preflight` 가 `--mcp-root`·`--git-root` 를 함께 받는 것은 이 명제의 반증이 아니라 **집행 수단**이다. 두 값을 받는 이유는 CLI 가 자기 cwd 로 root 를 해석하면 비교가 공허해지기 때문이고, 불일치는 exit 2 로 거부된다 |

진짜 제약은 SpecKiwi 계약이 아니라 **하네스** 쪽이다: 세션 도중 두 번째 stdio MCP 클라이언트를 등록할 수 없고, 에이전트가 자기 서버를 재기동할 수 없다. 그런데 §3.2 의 분해에서는 **워커에게 MCP 핸들이 필요 없다** — 제약이 워커를 구속하지 않는 것이지, 제약이 약한 것이 아니다.

## 4. 그런데도 wave 단위로 할 이유가 없는 이유

**wave 는 계약상 엄격히 직렬이다.**

`kiwi-wave-master` §5:

> 앞 wave 의 pipeline 이 완주(`TASK_DONE`)한 뒤에야 다음 wave 의 pipeline 을 시작한다. … 정확히는 `TASK_DONE` 만으로는 부족하다 — 앞 wave 가 §5.5 **웨이브 종료 상호검증**까지 통과해 `complete` 로 기록된 뒤에야 다음 wave 의 pipeline 을 시작한다.

두 wave 는 어떤 시점에도 겹치지 않는다. 따라서 **per-wave 워크트리의 벽시계 이득은 정확히 0** 이다.

격리가 주는 나머지 이득은 두 개뿐이다 — base 브랜치 안전성과 롤백 용이성.

**그 둘을 `FR-FLOW-027` 로 얻을 수는 없다.** `FR-FLOW-042` 요구 본문이 *"kiwi-wave-master SHALL NOT delegate worktree isolation to `kiwi-pipeline --wt` and SHALL refuse such a request"* 라고 못 박고 AC-7 이 이를 고정하므로, wave run 은 `FR-FLOW-027` 의 merge-or-PR 게이트에 **구조적으로 도달할 수 없다**. 안전성이 목적이라면 값싼 경로는 따로 있다 — **run 전체를 하나의 워크트리에서 돌리되 그 디렉터리를 cwd 로 하는 새 세션을 여는 것**(연구 12 방안 B)이고, 이것은 SRS 변경이 0 이다.

`docs/research/12` §10 Q3 이 한 달 전 같은 질문을 던지고 답을 받지 못했다: *"wave-master 는 순차 오케스트레이터라 방안 A(단일 root 브랜치 전환)로 대체 가능한데, 워크트리를 유지해야 할 별도 이유가 있는가?"* 본 연구의 답은 **없다** 이다.

**그러므로 `kiwi-wave-master` SKILL.md §2.1 의 `wt-delegation-refused` 게이트는 유지가 옳다.**

스킬이 적어 둔 사유("wave 누적을 깨뜨린다")에 대해서는 정밀하게 말해야 한다. **거부 대상인 `kiwi-pipeline --wt` 에 한정하면 그 사유는 옳다** — `FR-FLOW-027` 의 `--wt` 는 `git worktree add <path> -b <cycle-branch>` 로 **새로 생성**할 뿐 앞 wave 의 커밋을 기준으로 열 장치가 없으므로, 그 위임은 실제로 누적을 깬다. 그 사유가 확립하지 **못하는** 것은 "per-wave 격리 일반이 불가능하다"는 명제다(§2.3 의 명시 checkout 이 반례). 그러나 그 일반 명제는 필요하지도 않다 — §4 의 직렬 논거가 더 강하게 같은 결론을 준다.

**주의 — 파급 범위는 verified 요구 둘이다.** 이 사유는 스킬 문구가 아니라 **`FR-FLOW-042` 요구 본문(`60.workflow-release.srs.md:3102`) + AC-7(`:3115`) + `test/skills/kiwi-wave-master-content.test.ts:482,701`(3개 변종 단언)** 에 박혀 있다.

거기에 더해 **`FR-FLOW-088`(verified, `:6000`)이 자기 근거를 이 사유와의 *대비*로 정의한다.** 정확히는 — verbatim 상속되는 것은 **`--wt` 비위임 조항**이고(`:6044` trace link), 누적 사유 자체는 오히려 **명시적으로 거절**된다: Rationale(`:6021`)이 *"phase 1 has no per-wave worktree, so that rationale does not transfer"* 라 하고 AC-5(`:6027`)가 *"do not restate `kiwi-wave-master`'s per-wave-accumulation reason"* 를 요구하며, `test/skills/kiwi-orchestrator-body.fr-flow-074.test.ts:464-469` 가 오케스트레이터 §0 에 **그 거절 문장이 존재함**을 3변종에서 단언한다. FR-FLOW-088 의 Rationale 은 `kiwi-wave-master:144` 를 줄 번호로 지목하기까지 한다.

따라서 FR-FLOW-042 의 사유를 건드리면 FR-FLOW-088 의 "무엇을 거절하는지"가 흔들린다. 문구 교체는 "스킬 소규모 수정"이 아니라 **verified 요구 둘의 동시 개정**이다(§8 rec 2).

## 5. 값이 나오는 자리 — wave 안의 task(lane)

lane 은 실제로 동시 실행되므로 격리가 벽시계로 환산된다. 성립 조건(측정·기록된 것):

| # | 조건 | 근거 |
| --- | --- | --- |
| 1 | 워커는 SRS 를 **직접 호출하지 않고 큐에 적고**, 호스트가 재생한다 | §3.2 (`--defer-srs-mutation` + replay) |
| 2 | Requirement ID 는 fan-out 전에 **호스트에서 전량 할당** | charter C2. 두 root 는 항상 같은 ID 를 할당한다(`02` §6.4 재현, `12` §7 실사고 4건) |
| 3 | 워크트리를 **명시 checkout** 한다 — 기본 HEAD 는 현재 브랜치가 아니다 | §2.3 |
| 4 | 병합 후 `validate` → `sync-index` 를 **의무 단계**로 | charter C4. 인덱스 롤업은 조용히 auto-merge 되어 틀린다 |
| 5 | 공유 레지스트리 파일마다 **동시 작성자 1명** | `02` §6.2 |
| 6 | 워크트리 설치 시 **`NODE_ENV` 고정** | 이 셸은 `NODE_ENV=production`, 그 상태의 `npm ci` 는 devDependencies 를 조용히 빠뜨린다(exit 0) |
| 7 | `speckiwi init` / 스킬 미러 작업은 **절대 병렬화 금지** | 1회 실행이 32개 파일 재작성 |

비용(`02` 측정): 워크트리당 약 **119 MB** + warm cache `npm ci` **4초**. 20개면 디스크 2.4 GB. 경로 길이 최악 188/260자.

이것은 `docs/spec/00.index.md:93` 이 **`2.6.0-phase2-parallel-lanes`** 로 이름 붙인 작업이다 — *"Execution is serial at the host root; concurrent lane execution is 2.6.0-phase2-parallel-lanes."* 현재 Target Map 에 **등록돼 있지 않다**(행은 `2.7.0-verification-integrity` 와 `2.7.1` 에서 끝난다).

## 6. 실재하는 갭 3건

### 6.1 `--defer-srs-mutation` 은 설계만 끝났고 어디에도 승격되지 않았다 (가장 큼)

수신자 계약은 **이미 쓰여 있다**. `05.orchestrator-design.md`:

- `:5600` S12 — *"`kiwi-coder` accepts `--defer-srs-mutation <path>`, recording its four mandatory MCP mutations to a queue instead of calling them."*
- `:5343` — *"**`kiwi-coder`** gains `--defer-srs-mutation <queue_path>` (§5.4)."*
- `:5602` S16 — `kiwi-pm` 의 pass-through 까지 규정
- `:2696` — *"**In phase 1 the field is written and unread** … so the queue, its harvest and its replay do not exist"*, **Phase 2** 로 명시 이관

문제는 **승격이 0** 이라는 것이다.

| 표면 | 상태 |
| --- | --- |
| 설계 문서 (`05`) | **있음** — S12/S16, §5.4, §14 items 11–12 |
| SRS 요구 | **없음** — `FR-FLOW-102` AC-2 가 *"no `--defer-srs-mutation`"* 로 **부정문 안에서만** 이름을 언급 |
| `kiwi-coder` SKILL.md | **없음** — `defer` 문자열 **0건**(5개 사본 전부) |
| `kiwi-orchestrator` SKILL.md | **부정문만** — `:732` "전달하지 않는다"(4개 미러) |
| `src/` | **0건** |

그래서 `kiwi-coder` §0.12 는 여전히 **Task 마다** 4종 mutation(`add_trace_link` / `add_verification_evidence` / `update_status` / `add_completed_work`)을 의무로 규정하고, 이를 유예하는 조항이 **없다**. 오늘 lane 워커를 워크트리에 넣으면 §2.2 의 split-brain 이 **task 단위로** 발생한다.

**이것이 lane 병렬화의 유일한 실질 blocker이며, 다른 어떤 항목보다 앞선다.** 다만 성격은 "계약을 새로 발명해야 함"이 아니라 **"설계된 계약을 SRS·스킬·코드로 승격해야 함"** 이다.

### 6.2 `FR-FLOW-027` 과 `FR-FLOW-042` 가 화해되지 않았다

`FR-FLOW-027`(verified)은 사이클을 워크트리 안에서 돌라고 하고, `FR-FLOW-042`(verified)는 정확히 그 배치에서 halt 한다. **두 요구를 연결하는 것이 없다** — 양쪽 블록의 Trace Links 와 Change Notes 를 모두 확인했고 어느 쪽도 상대를 지명하지 않는다(`FR-FLOW-027` 의 링크는 `FR-FLOW-026`/`T-PH004-01`/`T-PH004-02`, `FR-FLOW-042` 의 링크는 `FR-FLOW-029`/`FR-FLOW-030` 등). `docs/spec/` 내 다른 언급은 `00.index.md:212` 의 Completed Work Log 요약 1줄뿐이다.

이 모순이 지금 드러나지 않는 이유는 wave-master 가 `--wt` 전파를 거부해 두 경로가 만나지 않기 때문이다. 게이트를 유지하는 한 잠복하지만, **모순 자체는 기록돼야 한다.**

### 6.3 `FR-FLOW-027` 에는 실행 증거가 없다

증거 행은 둘이다 — `VE-1 | plan | docs/plans/2026-07-10.speckiwi.v2301-flow.plan.md#T-PH004-02` 와 `VE-2 | test | test/skills/kiwi-pipeline-content.test.ts`. 전자는 계획 참조이고, **유일한 test 증거인 후자는 내용 테스트**다. 즉 **스킬 문서가 그렇게 적혀 있음**은 증명되지만 그 배치가 **실제로 동작함**은 증명되지 않는다. 그리고 §2.2 의 런타임 측정은 그 배치에서 SRS 축이 갈라짐을 보인다.
