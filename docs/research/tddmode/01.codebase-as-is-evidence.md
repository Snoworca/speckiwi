## 2. steps 서브시스템 — "가볍게 작업 후 SRS 승격" 경로는 이미 존재

### (a) 사실 요약

경량 작업 → SRS 승격 파이프라인이 **core에 거의 완결 구현 + MCP 5종 전부 등록**. 라이프사이클:

1. **claim_step** — state.md에 `| step | active | … |` 행 추가(초기 상태 항상 active). write-skew 교차 게이트(동일 REQ 직접충돌=하드블록, depends_on 폐포 전이충돌=force override 가능).
2. **update_step_state** — Status 셀을 active→merging→merged 또는 →abandoned 로 in-place 전이(enum 검증만, 명시적 상태머신 없음).
3. **synthesizeStepSrs** — `docs/spec/steps/<task>/`의 intent.md + trace 샤드(JSONL) + `@step` 코드 주석 + git diff 병합해 `<task>.srs.md` 생성(멱등, 시크릿 리댁션).
4. **promote_step_requirement** — step 요구사항 블록을 body-scope SRS로 승격. **step에서 미리 확정한 canonical ID를 자동생성 없이 그대로 삽입**, 전역 유일성 검증 후 인덱스 재동기화.
5. **diff_steps** — step↔body를 NEW/UPDATE/CONFLICT-PARTIAL/CONFLICT-FULL-GUARDED 분류. **주의: core-only이며 MCP/CLI 미등록(phantom)** — 살베지 때 병합 오케스트레이터(FR-FLOW-015) DISCARD되며 노출 중단.
6. **FR-FLOW-014 `kiwi-step` 스킬 (Status=verified)** — "claim → step 디렉토리에만 저작 → validate_step" 경량 저작 워크플로. 이것이 **"body SRS를 안 건드리고 가볍게 먼저 작업"**의 설계된 형태.

### (c) TDD First 모드 시사점

## 3. vibe / work-mode — 이미 존재하는 "모드" 개념

### (a) 사실 요약

모드는 이미 1급 시민. `StepStateMode = "sdd"|"vibe"|"wait"`(types.ts:457), `StepStateStatus = "active"|"merging"|"merged"|"abandoned"`(types.ts:456).

- **sdd** = spec-driven(SRS 먼저), **vibe** = 경량/바이브 코딩(Active Task 지정 후 나중에 합성·승격), **wait** = 기본/유휴. **이것이 사용자의 "TDD 모드"와 개념적 형제.**
- **CLI 토글 이미 있음**: `speckiwi mode [sdd|vibe|wait]`(인자 없으면 현재 모드 읽기, 잘못된 값 INVALID_MODE exit 2).
- **vibe-gate**: `speckiwi vibe-gate check` — 활성 vibe 태스크에 합성된 step 디렉토리 없으면 exit 1(CI required status check용).
- **vibe 완료 하드게이트(FR-NODE-058)** `evaluateVibeCompletionGate`: touched 폐포의 dirty-edge(모순) 미승인 시 vibe flow 완료 차단(enforced:true), 비-vibe flow는 advisory(enforced:false). "합성됨(step 디렉토리 존재)"과 "모순 검증됨"은 직교.
- "vibe/work-mode salvage"(v2.3.0.1 target 설명)의 실체 = v3.0.0의 이 모드 서브시스템을 v2.3.0.1로 옮겨온 것.

### (b) file:line 증거

- `src/core/types.ts:457`(StepStateMode), `:456`(StepStateStatus)
- `src/cli/commands/read.ts:726-745`(speckiwi mode, IR-CLI-048), `:749-767`(vibe-gate check, IR-CLI-049)
- `src/core/mutation/work-mode.ts:21-54`(WorkMode 모델); FR-NODE-050 `docs/spec/50.nodejs-implementation.srs.md:3817-3845`

### (c) TDD First 모드 시사점

**"TDD 모드"를 새 상태값으로 만들 필요가 거의 없음** — enum에 `tdd` 추가 또는 기존 `vibe`(경량 선작업) 재해석이 최소 변경. 단, 재사용 범위에 주의: **저장·파서·CLI 토글 배관은 그대로 재사용되지만, 강제 게이트 3곳은 `vibe`에 하드코딩**되어 있어 tdd enum 추가만으로는 no-op이 된다 — `read.ts:725`(validModes Set), `read.ts:761`(vibe-gate가 `mode === "vibe"`일 때만 발동, 그 외 `synthesized=true` 기본 통과), `internal.ts:172`(비-vibe는 `{allowed:true, enforced:false}` advisory). 게이트 확장이 별도 작업으로 필요하다 (00 §9 G9).

## 5. 계획/워크플로 문서 도구 (workflow_*)

### (a) 사실 요약

`workflow_*` MCP 도구는 **25종(읽기 17 + 변이 8)**으로 이미 풍부.

- **플랜 태스크 추적**: workflow_plan_status(목록/카운트), workflow_plan_task(단일), workflow_next_plan_task(의존성·드리프트 기반 다음 태스크 산출).
- **파이프라인 이벤트 로그**: workflow_pipeline_status/tail/next/compact(JSONL).
- **아티팩트 해석**: workflow_artifacts_list/latest/resolve.
- **워크로그/세션**: workflow_worklog_tail/emit, workflow_session_status, workflow_resume_hint.
- **검증**: workflow_doctor/diff/schema_check.
- **docs/plans 사이드카 JSON**: schema_version, run_id, target, plan_contract, **tdd_policy**, phases[], tasks[]. 각 task는 req_ids[], acceptance_tests[], verification_cmd, 그리고 **`tdd{applicable, phase(red/green), test_cases[], red_evidence, green_evidence}` 블록** 보유. 상태 SSOT는 사이드카 아닌 pm-state.json.
- 선언적 JSON-Schema/Zod 플랜 스키마는 **없음** — validate.ts 규칙 + 진단코드→outcome 매핑이 사실상 계약.

## 핵심 발견 Top 5

1. **모드 토글은 이미 존재.** StepStateMode=sdd|vibe|wait + `speckiwi mode` CLI + getWorkMode/setWorkMode가 `docs/spec/steps/state.md`에 영속. "TDD 모드"는 새 저장소가 아니라 **enum 확장 또는 vibe 재해석**으로 구현 가능. (types.ts:457, cli/commands/read.ts:726, mutation/work-mode.ts:45)
2. **"가볍게 선작업 → SRS 후행 승격" 엔진이 검증 완료 상태로 존재.** kiwi-step 스킬(FR-FLOW-014, verified)→synthesizeStepSrs 합성→promote_step_requirement 승격(사전 확정 ID 그대로). (60.workflow-release.srs.md:1454, synthesis.ts:245, add-requirement.ts:324)
3. **하지만 이 저장소 자체는 그 모드를 안 씀.** docs/spec/steps/가 없어 fail-open으로 wait. 서브시스템은 전부 optional/fail-open(읽기=빈결과/wait, 쓰기=구조화된 NOT_FOUND). 인프라는 있으나 **드리프트 위험 없이 새로 켤 수 있는 상태.** (parser/discover.ts:65, mutation/work-mode.ts:45)
4. **계획 사이드카에 이미 TDD 데이터 관례 존재 (단 런타임 강제는 없음).** docs/plans/*.sidecar.json이 tdd_policy(전역) + 태스크별 tdd{phase:red/green, test_cases[], red_evidence, green_evidence} 보유. 그러나 런타임 `SidecarTask` 타입(workflow/read.ts:55-63)엔 tdd 필드가 없어 파싱·강제 없음 — 스키마 발명은 불필요하나 enforcement는 신규 작업. (sidecar.json, workflow/read.ts:55)
5. **SDS(설계문서)만 완전 공백.** 문서타입 판별·파서·규칙·검증이 SRS 외엔 전무, 코드는 Document Type 값으로 분기조차 안 함. 새 사이클의 "SDS 작성"만이 **유일한 greenfield**, 저비용 대안은 기존 plan.md/intent.md 재활용. (docs/rule/=SRS-MD Rules 3버전뿐, templates.ts:95)

## 설계 시 함정 (검증 중 발견)

- 테스트 파일명 요구사항 ID ≠ 코드 실제 ID (예: fr-node-043-vibe-merge…test.ts→실제 FR-NODE-058; mode.ir-cli-030.test.ts→실제 IR-CLI-048). SRS 참조 시 **코드 상단 @req 주석 ID를 정본**으로 볼 것.
- diff_steps는 core-only phantom(MCP/CLI 미등록, FR-FLOW-015 DISCARD 잔재). "후행 SRS 자동 diff/병합"까지 가려면 재노출 선결.
