## 1. 설계 원칙

1. **경량 우선**: SDS 1건 = 1~3쪽(권장 상한 약 200줄). 초과 시 작업(step) 분할이 정답이지 문서 확장이 아니다.
2. **테스트보다 앞, 테스트로 번역 가능**: SDS의 수용 계약(§5)은 EARS 문장으로 작성되어 그대로 red 테스트로 번역된다. SDS 없이 테스트만 존재하는 상태를 금지한다(reward-hacking 방어 — 02 주제 1).
3. **결정과 인터페이스만**: 아키텍처 **결정**(trade-off 포함)과 **인터페이스 시그니처**만 담는다. 구현 코드·스키마·API 응답 전문 복붙 금지(Google 안티패턴).
4. **후행 SRS의 원천**: SDS §5의 수용 계약이 후행 SRS 승격(promote) 시 Acceptance Criteria의 원천이 된다. 구현 결과에서 AC를 역산하지 않는다(구현 편향 방어 — 02 주제 4).
5. **SDS 생략 게이트**: trade-off 없는 자명한 변경(오타·주석·단순 버그픽스)은 SDS를 생략하고 §5 수용 계약 스텁(EARS 1~3문장)만 작성할 수 있다.

## 2. 파일 위치와 명명

- 위치: `docs/spec/steps/<task>/design.md` — 기존 step 디렉토리(intent.md와 병렬) 안의 설계 슬롯.
  - 근거: `synthesizeStepSrs`가 이미 step 디렉토리 산출물을 병합해 SRS를 합성하므로, design.md를 합성 입력에 추가하는 것이 최저비용 경로다 ([01.codebase-as-is-evidence.md](./01.codebase-as-is-evidence.md) §2, §6).
- intent.md(무엇을/왜 — 의도)와 design.md(어떻게 — 설계)는 역할이 다르다. 소형 작업은 intent.md 하나로 겸용 가능(§1 원칙 5).

## 3. 문서 구조 (필수 헤딩)

```markdown
# SDS: <작업 제목>

| Field | Value |
|---|---|
| Document Type | sds |
| Task | <step task id> |
| Target | <SpecKiwi target, 예: v2.4.0> |
| Status | draft \| agreed \| superseded |
| Date | YYYY-MM-DD |

## 1. Context & Scope
(배경과 경계. 5줄 이내.)

## 2. Goals / Non-goals
(각각 bullet. Non-goals 명시가 과잉 구현을 차단한다.)

## 3. Architecture Decisions
(ADR 축약형. 결정 1건당: **결정** / 근거 / trade-off / 기각한 대안. 결정당 5줄 이내.)

## 4. Interfaces
(신규·변경 함수/CLI/MCP 도구의 **시그니처와 계약만**. 코드 본문 금지.)

## 5. Acceptance Contracts
(EARS 문장 목록. 각 항목에 `SDS-AC-n` ID 부여.
 형식: "WHEN <조건> THE SYSTEM SHALL <관찰 가능한 동작>."
 각 SDS-AC는 §6에서 최소 1개 테스트에 매핑되어야 한다.)

## 6. Test Plan
(| SDS-AC | 테스트 파일(예정) | 케이스 요약 | 형식의 표.
 red 단계에서 이 표의 테스트가 먼저 작성·실패 확인된다.)

## 7. Open Questions
(미결 사항. business-decision 성격이면 구현 전 사용자 확인.)
```

## 5. 라이프사이클

```
draft ──(사용자/리뷰 합의)──> agreed ──(red 테스트 작성 시작)
agreed ──(설계 변경 필요)──> superseded (새 SDS로 대체; 기존 red 테스트 영향 명시)
```

- **agreed 이전 구현 착수 금지** — Spec Kit Article III의 "사용자 승인 후 테스트" 게이트와 동형. 단 **승인 주체는 작업 크기에 종속**시킨다(속도 상충 방지): 아키텍처 결정(§3)이 비어 있거나 자명한 **소형 작업은 self-agreed**(에이전트 자율 진행 + 사후 검토), §3에 실질 결정이 포함된 **중·대형만 사용자 승인**. 동기적 승인 대기가 TDD First의 속도 목표를 잠식하지 않도록 하는 장치다.
- promote(후행 SRS 승격) 시: SDS §5의 각 SDS-AC → SRS AC로 이관, §6의 테스트 → Verification Evidence(type=test)로 등록. **증거 링크 0건인 요구사항 승격 금지**(traceability density > 0).

## 6. 검증(추후 도구화 후보)

- `validate_step` 확장 또는 신규 `validate_sds`: 필수 헤딩 존재, SDS-AC ↔ Test Plan 매핑 완전성, 길이 상한, EARS 문형 검사(휴리스틱).
- **주의 — 도구화 전까지 본 표준의 게이트(agreed, SDS-AC↔Test 완전성, 생략 조건)는 전부 honor-system이다.** 형식주의 전락을 막기 위해: (a) 검증 도구화(00 §9 G7)를 MVP 필수로 승격하고, (b) 도구 배포 전 잠정 기간에는 kiwi-tdd 스킬(00 §9 G8)의 체크리스트가 위 검사를 **의무** 수행한다(선택 아님). 어느 쪽도 없이 SDS 표준만 배포하는 것은 금지.
- SDS가 테스트의 얇은 래퍼(중복)로 전락하면 존재 가치가 없다 — §1 원칙 5의 생략 게이트("결정·trade-off 없으면 SDS 생략, EARS 스텁만")를 체크리스트 첫 항목으로 둔다.
