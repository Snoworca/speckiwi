## 1. 문제 정의

SpecKiwi 생태계에 TDD를 아는 축이 **둘** 있고 서로를 모른다.

1. **work-mode** — 런타임 1급 상태. `docs/spec/steps/state.md`에 영속되는 `sdd|vibe|wait|tdd` (`src/core/types.ts:457`). 읽기 `getWorkMode`(fail-open → `wait`), 쓰기 `setWorkMode` (`src/core/mutation/work-mode.ts:46-150`). 표면: CLI `speckiwi mode` (`src/cli/commands/read.ts:729-750`), MCP `get_work_mode`/`set_work_mode` (FR-MCP-052). agent snippet v1.6이 에이전트에게 "작업 시작 전 work-mode를 읽으라"고 지시한다(`templates.ts:356-362`).
2. **tdd_policy** — kiwi-planner가 만드는 plan 계약(plan_contract 1.2.0)의 필드 `strict|relaxed|disabled`. planner §0.17이 plan-time 게이트로 강제하고, kiwi-pm §7.1이 `disabled` plan을 HALT하며, kiwi-coder가 sidecar로 소비한다. 기본값은 `relaxed`(planner 자연어 매핑 + validator.mjs:687 폴백).

결과: work-mode가 `tdd`여도 ① kiwi-pipeline/kiwi-pm/kiwi-planner는 이를 조회하지 않아 kiwi-tdd로 자동 라우팅되지 않고(명시 `/kiwi-tdd` 트리거만 동작), ② plan의 tdd_policy는 work-mode와 무관하게 `relaxed`로 고정된다.

## 2. 사실 요약 (조사 확정)

- work-mode를 읽는 스킬은 **kiwi-tdd 하나뿐**(§0.1 halt 게이트). kiwi-step은 mode-agnostic, kiwi-pipeline은 work-mode/tdd_policy **양쪽 모두 언급 0**.
- kiwi-pipeline의 라우팅 구조: 시작 분기 §3(Phase 0), 결정표 §5.1 Table T1, 사이클 체인 §2.5(`kiwi-srs → feasibility → planner → pm → review-fix-loop`).
- **테스트 취약점 1순위**: `test/skills/kiwi-pipeline-content.test.ts:55-57` `CHAINED_FIVE_STAGES` 정규식 — 5단계 화살표 체인의 문자 거리 상한이 좁아 §2.5 본문에 텍스트 삽입 시 즉시 red. → tdd 분기는 **별도 절(Phase 0/§3)로 추가**해야 한다.
- 모든 콘텐츠 테스트는 claude/codex/etc **3 미러 동시 단언** — 본문 변경은 항상 3벌.
- 불변 계약: kiwi-tdd §0.1 halt, kiwi-step claim<validate·body-scope 금지, kiwi-pm §7.1 `disabled` HALT, kiwi-planner §0.17 tdd 필드 필수.
- **신규 런타임 코드 불필요**: 조회(`get_work_mode`/`speckiwi mode`)와 주입(`--tdd-policy`)은 이미 존재하는 표면. 통합의 실체는 스킬 본문 배선.
- fail-open 존중: 모드 미설정 = `wait` = sdd 규칙. 오케스트레이터 분기도 wait/sdd를 기본 비-tdd 경로로 두어야 회귀가 없다.

## 3. 통합 모델 후보

### 모델 A — mode-primary 파생 (work-mode 상위, tdd_policy는 plan-time 파생 기본값)

- **개념**: work-mode를 프로젝트 수준의 상위 선언으로 정의한다. tdd_policy는 plan 계약 필드로 **존속**하되, 기본값이 work-mode에서 파생된다. 명시 `--tdd-policy` 플래그는 항상 파생값을 이긴다(explicit-over-preset — FR-FLOW-034 --loops 선례와 동일한 kiwi 관례).
- **배선**:
  - kiwi-pipeline Phase 0(§3)에 work-mode 조회 게이트 신설: `get_work_mode`(MCP 우선) → `speckiwi mode`(CLI fallback) → 둘 다 부재 시 wait 간주. `mode=tdd` **그리고** 작업이 step-scoped(단일 기능/step 규모)이면 kiwi-tdd로 라우팅; body-scope·대규모 아키텍처 변경은 snippet v1.6 규칙 6에 따라 기존 sdd 체인 유지.
  - kiwi-planner: work-mode 조회를 Phase 0에 추가하고, `mode=tdd`면 tdd_policy 기본을 `strict`로 파생(명시 플래그 우선, 파생 시 WARN 로그). `mode=sdd|wait|vibe`면 현행 `relaxed` 기본 유지.
  - kiwi-pm: 입력 게이트에 "plan의 tdd_policy와 현재 work-mode의 모순(예: mode=tdd + relaxed) 시 경고 1줄" 추가 — HALT 아님(비파괴).
- **매핑 표**: `tdd→strict(파생 기본)`, `sdd/wait→relaxed(현행)`, `vibe→relaxed(현행, vibe 라우팅은 범위 외)`. `disabled`는 어느 모드에서도 파생되지 않음(명시 플래그로만, pm이 여전히 HALT).
- **장점**: 두 축의 서열이 명확해짐(모순 불가능화). 라우팅+정책이 한 번에 정합. 신규 런타임 0.
- **단점**: 스킬 3종(pipeline/planner/pm) × 3미러 = 9파일 수정 + 신규 콘텐츠 테스트. planner 파생 규칙이 자연어 매핑 §1.2와 충돌하지 않도록 문구 정밀도 필요.

### 모델 B — 독립 유지 + 라우팅만 (최소 배선)

- **개념**: 두 축은 독립 유지. kiwi-pipeline Phase 0에만 work-mode 조회를 추가해 `mode=tdd`+step-scoped → kiwi-tdd 라우팅. planner/pm의 tdd_policy는 손대지 않는다.
- **장점**: 최소 변경(pipeline ×3미러 = 3파일). 회귀 표면 최소.
- **단점**: "두 tdd 시스템이 서로 모른다"는 근본 문제의 절반(정책 축)이 미해결 — mode=tdd인데 plan은 relaxed로 생성되는 모순 잔존. 선행 위원회 D2가 요구한 "개념 통합"에 미달할 소지.

### 모델 C — 완전 단일화 (tdd_policy를 work-mode 파생 read-only로 격하)

- **개념**: plan 계약에서 tdd_policy 입력을 제거하고 plan-time에 work-mode에서 항상 파생. plan_contract 1.3.0 브레이킹.
- **장점**: 개념이 하나로 줄어듦.
- **단점**: plan_contract 브레이킹(validator.mjs·pm §0.2·coder 소비까지 연쇄), 기존 plan 산출물 호환 파괴, 스킬 대수술. 이번 범위(스킬 콘텐츠 저작) 대비 과대.
