## 3. 갭 목록 (우선순위)

### P1 (사이클이 물리적으로 끊기는 지점)

- **G1 [대] 합성 엔진 런타임 미노출** — `synthesizeStepSrs`(synthesis.ts:246; FR-NODE-056/073은 unit test로 verified)에 CLI/MCP 표면이 전혀 없음. kiwi-tdd §2.7이 "synthesize(가용 시)"라 쓰지만 항상 수동 폴백. → 신규 `speckiwi step synthesize <task>` + MCP `synthesize_step_srs`.
- **G2 [대] step-mutation의 CLI 패리티 부재** — claim/update_step_state/promote가 MCP 전용. kiwi-step §0.4가 claim의 MCP-only halt를 의도적 설계로 명시하고 있으나, 결과적으로 **MCP 없는 환경에서는 tdd 사이클 진입 자체가 불가** — "MCP 부재 시 CLI fallback" 총칙과 긴장. → CLI 미러 3종 또는 "tdd는 MCP 필수"를 총칙 예외로 명문화(둘 중 하나는 필요; 전자는 구현, 후자는 문서 결정).

### P2 (설계-구현 불일치·가시성)

- **G3 [중] merged 완료 게이트 미결선** — `evaluateVibeCompletionGate`(internal.ts:166, FR-NODE-058/072)가 정의·테스트만 있고 `updateStepState`의 merged 전이에서 호출되지 않음. "merged는 모순검증 후에만"이라는 설계가 배선 안 됨. (검증자 B MEDIUM과 동일 뿌리 — FR-NODE-072 구현 노트에 기록됨)
- **G4 [중] 오케스트레이터 미통합** — kiwi-pipeline/kiwi-pm/kiwi-planner가 work-mode를 읽지 않아 tdd여도 kiwi-tdd로 라우팅되지 않음(명시 `/kiwi-tdd` 트리거만). 또한 planner의 `tdd_policy`(plan 계약)와 work-mode `tdd`가 **별개 tdd 시스템으로 미연결**.
- **G5 [중] list_steps SDS 가시성 0** — design.md 존재·SDS Status(draft/agreed/superseded)가 어떤 조회 도구에도 안 나옴.
- **G6 [중] vibe-gate MCP 대응물 부재** — MCP-only 에이전트가 promote 전 게이트 상태를 자가확인 불가.

### P3 (편의·진단)

- **G7 [소~중] SDS 스캐폴드 부재** — claim이 디렉터리를 만들지 않고 템플릿은 수동 복사. `speckiwi step scaffold <task>`(dir+intent.md+design.md 스텁)로 해소 가능.
- **G8 [소] SDS Status 전이 도구 부재** — design.md 메타 Status를 수동 편집(기존 mutation은 .srs.md 블록 전용).
- **G9 [소] doctor SDS 미인지** — SDS-MD-Rules 설치·drift 검사 없음(checkRulesDrift는 SRS-MD만).
- **G10 [소] codex 런타임 미러 결손** — .agents/skills에 kiwi-tdd 부재는 kiwi-step 선례와 일치(불일치 아님)이나, codex installed 미러 경로로는 step/tdd 계열 전체 미도달. 미러 정책 결정 필요.

## 4. 갭이 아닌 것 (과잉 제안 경계)

- SDS 검증(3표면)·promote 증거 게이트·vibe-gate tdd 확장 — 작동 확인, 손댈 필요 없음.
- `_shared/kiwi/loop-option.md` — `skills/{claude,codex,etc}/_shared/`에 3변형 모두 실재(참조 해소). 갭 헌터가 팀리드의 초기 오판(glob 패턴 오류)을 정정, 재확인 완료.
- kiwi-tdd의 .agents 미러 제외 — kiwi-step 선례 일치.
- design.md 템플릿 자체 — 규칙 문서 §8 + 스킬 체크리스트로 정확성은 보장(스캐폴드는 편의 문제).

## 5. 권고 (후속 SRS 후보 순서)

1. **G1 합성 노출 + G2 결정**(CLI 미러 vs MCP-필수 명문화) — 사이클 후반부가 끊기는 P1부터. G1은 idempotent 엔진이 이미 verified라 노출만 얇게 얹으면 됨.
2. **G3 게이트 결선** — update_step_state의 merged 경로에 evaluateVibeCompletionGate 호출(dirty-edge 소스는 list_dirty_edges 코어 재사용).
3. **G5+G6 가시성** — list_steps에 `sds: {present, status}` 필드, vibe-gate의 MCP read 대응물.
4. G7~G9 편의·진단, G4 오케스트레이터 통합(스킬 개정 — planner tdd_policy와 work-mode의 개념 통합 설계 선행 필요), G10 미러 정책.
