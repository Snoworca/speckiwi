## 1. 사용자 제안 (원 요구)

- 기존 사이클 **연구 → SRS 작성 → 계획 작성 → 구현 → 검증** 은 SRS·계획 선행 비용 때문에 느리다.
- 새 사이클 **연구 → SDS 작성 → 테스트 코드 작성·반복 검증 → 구현 → 회귀테스트 → SRS 후행 작성** 으로 "TDD First 모드"를 추가한다.
- 요구 구성요소: ① 사용자가 "tdd 모드 사용"이라 하면 **상태값이 어딘가 저장**되어 그렇게 동작 ② **SDS 표준**(아키텍처 고려, 과하면 인터페이스+아키텍처 중심의 자체 구현계획 문서) ③ **계획 문서를 빠르게 탐색하는 도구** ④ **CLAUDE.md 기록 내용에 TDD 모드 언급**.

## 2. 한 줄 결론

**타당하며, 대부분 신규 개발이 아니라 기존 서브시스템의 확장이다.** 모드 상태값(`speckiwi mode`, StepStateMode), 경량 선작업 → SRS 후행 승격 엔진(steps/synthesis/promote), red/green 추적 스키마(사이드카 tdd 블록)가 이미 구현·검증돼 있고, **유일한 greenfield는 SDS 표준**이다. 단 네 가지 조건이 필수다: (a) SDS(자연어 계약)를 테스트보다 반드시 앞에 둘 것(reward-hacking 방어), (b) 후행 SRS는 증거 링크 의무로 traceability를 보전할 것, (c) 작업 크기 게이트로 소변경 과잉문서화를 차단할 것, (d) **강제 게이트를 tdd로 확장할 것(G9)** — 현행 게이트 3곳은 전부 `vibe` 하드코딩이라 enum 추가만으로는 조용히 no-op이 된다(검증 F1 [CRITICAL]).

## 4. 정제된 TDD First 사이클 (to-be)

사용자 원안을 유지하되, 각 단계를 기존 도구에 매핑하고 안전 게이트를 삽입한 형태:

| 단계 | 내용 | 사용 도구 (기존/신규) |
|---|---|---|
| 0. 모드 진입 | "tdd 모드 사용" → 상태값 저장 | `speckiwi mode tdd` (**enum 확장**), `docs/spec/steps/state.md`에 영속 |
| 1. 연구 | 짧은 사전조사 (기존과 동일, 축소) | 기존 관행 (docs/research/) |
| 2. step claim | 작업 단위 선점 + 충돌 게이트 | `claim_step` (기존) |
| 3. SDS 작성 | 1~3쪽 경량 설계: 결정+인터페이스+EARS 수용 계약 | `docs/spec/steps/<task>/design.md` (**신규 표준** [03](./03.sds-standard-draft.md)) |
| 4. red | SDS §5 계약 → 실패 테스트 번역, **테스트 먼저 커밋** | 사이드카 `tdd.red_evidence` (데이터 관례 기존, 런타임 강제는 G10) |
| 5. green | 테스트 수정 금지 상태로 최소 구현 → 통과 | 사이드카 `tdd.green_evidence` (동상) |
| 6. 회귀 | 영향 범위 회귀테스트 | 기존 테스트 러너 + 완료 게이트(**tdd 확장 필요 — G9**, 현행 게이트는 vibe 전용) |
| 7. SRS 후행 작성 | step 산출물(design.md+테스트+diff) 합성 → 요구사항 승격 | `synthesizeStepSrs`(합성 입력에 design.md **추가**) → `promote_step_requirement` (기존) + **증거 링크 의무 게이트** (신규) |

핵심: 4·5단계의 "테스트 먼저 커밋 + 테스트 수정 금지"와 7단계의 "증거 링크 0건 승격 금지"가 외부 연구가 확인한 두 실패 모드(reward hacking, 구현 편향)의 직접 방어선이다.

### 4.1 속도 논증 — 무엇이 빨라지고, 무엇이 추가되는가

사용자의 1차 목표는 속도다. 신 사이클은 공짜가 아니므로 절감과 추가 비용을 정면 비교한다:

| 항목 | 기존 사이클 (sdd) | TDD First 사이클 | 순효과 |
|---|---|---|---|
| 앞단 명세 | 정식 SRS 블록 저작(ID·AC·trace·stability, 가드 통과) + 인덱스 동기화 | SDS 1~3쪽 (헤딩 7개, EARS 계약 수 개) | **대폭 절감** — 앞단에서 형식 요건이 가장 무거운 산출물 제거 |
| 계획 | plan.md + 사이드카 + validator (kiwi-planner 전체 사이클) | SDS §6 Test Plan 표가 계획을 겸함 (별도 plan 산출물 없음) | **대폭 절감** — 소·중형 작업에서 계획 단계 자체가 소멸 |
| 구현 루프 | 구현 후 검증 (실패 시 명세→구현 왕복) | red→green 자율 루프 (에이전트 반복에 최적, 02 주제 1) | 절감 (반복당 피드백 즉시) |
| 뒷단 명세 | 없음 (이미 앞에서 작성) | 후행 SRS 승격 (synthesis가 초안 자동 생성 + promote) | **추가** — 단 합성 자동화로 수동 저작보다 저렴 |
| 신규 게이트 | — | 테스트 먼저 커밋, 증거 링크 의무, agreed 게이트 | 추가 (아래 완화) |

순속도 이득의 원천은 "앞단의 무거운 SRS+계획을 뒷단의 자동 합성+승격으로 치환"하는 것이며, 작업이 작을수록 이득이 크다. 반대로 **대형 작업은 SDS가 3쪽을 넘기 시작하는 순간 sdd 모드가 오히려 빠르고 안전**하다(크기 게이트의 근거).

**agreed 게이트의 속도 상충 완화**: SDS `draft→agreed` 사용자 승인(03 §5)은 동기적 병목이 될 수 있다. 크기 게이트에 종속시킨다 — **소형 작업은 self-agreed(에이전트 자율 진행, 사후 검토)**, 아키텍처 결정이 포함된 중·대형만 사용자 승인. 이로써 자율 가속과 안전을 분리한다.

**vibe vs tdd 사용 결정 규칙 (언제 무엇을 쓰나)**:

| 작업 유형 | 모드 | 근거 |
|---|---|---|
| 실험·스파이크·프로토타입 (버릴 수 있음) | vibe | SDS조차 낭비; 살아남으면 synthesis→promote |
| 소·중형 기능/버그픽스 (남길 코드) | **tdd** | SDS 스텁+red 테스트가 품질 하한 보장, 속도 이득 최대 구간 |
| 대형 기능·아키텍처 변경·기존 REQ 수정 | sdd (현행) | SDS가 비대해지는 지점 = SRS 선행이 정당한 지점; 기존 body REQ와의 충돌은 sdd 경로가 안전 |

| 옵션 | 내용 | 평가 |
|---|---|---|
| **A. StepStateMode에 `tdd` 추가 (권장, 단 G9 필수)** | `types.ts:457` enum + `speckiwi mode tdd` + `docs/spec/steps/state.md` `Mode: tdd` | 저장·파서·CLI 토글 배관 재사용, 커밋되어 팀 공유. **주의: 강제 게이트는 재사용 안 됨** — vibe-gate(`read.ts:761`)·완료 하드게이트(`internal.ts:172`)·validModes(`read.ts:725`)가 전부 `vibe` 하드코딩이라, 게이트 확장(G9) 없이는 tdd에서 조용히 no-op. 조정 지점도 enum 1개가 아닌 최소 4곳(types enum, parser STEP_MODE_ENUM, CLI validModes, work-mode의 vibe 전용 Active Task 분기) |
| B. 기존 `vibe` 재해석 (tdd = 제약된 vibe) | vibe 모드에 SDS 필수 + red/green 필수 규율을 얹음 | **vibe는 enforcement 게이트를 가진 유일한 모드**라서 게이트를 공짜로 얻고 F1(게이트 no-op)을 회피 — 배관 관점에선 tdd가 sdd보다 vibe에 가깝다. 대신 의미 충돌(vibe=규율 없는 선작업 vs tdd=테스트 규율 선작업)이 실재하고, 두 규율을 한 모드값에서 구분할 방법이 필요 |
| C. `00.index.md` 메타 표 `\| TDD Mode \| on \|` | 파서 변경 없이 읽힘 | mode 도구 배관과 이원화, 게이트 연동 안 됨. 비권장 |
| D. `.kiwi/` / status-cache / `.speckiwi/` | — | gitignore·캐시·LEGACY라서 부적합 (01 §1) |

권장 A의 의미: **sdd 모드**(SRS 선행 — 현행 유지)와 **tdd 모드**(SDS+테스트 선행, SRS 후행)가 나란히 존재하고, 사용자가 `speckiwi mode`로 전환한다. vibe(자유 선작업)는 그대로 둔다. A와 B의 실질 저울은 "의미 명확성(A) vs 게이트 상속(B)"이며, **A 채택 시 G9(게이트 확장)가 MVP 필수**다.

부작용 주의(옵션 A·B 공통): `state.md`는 **커밋 대상 파일**이다. 팀 공유는 장점이지만 (a) 한 개발자의 모드 전환이 브랜치 전원에 전파되고, (b) 브랜치별 모드가 갈리면 `Mode:` 라인 머지 충돌이 나며, (c) tdd 브랜치를 sdd 브랜치에 머지할 때 모드가 혼입될 수 있다. 정식 설계 시 "모드 라인 머지 충돌은 머지 대상 브랜치 값 우선" 같은 취급 규칙 1개가 필요하다.
