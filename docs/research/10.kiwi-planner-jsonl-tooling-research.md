## 0. Scope and Claim Boundaries

This report is follow-up research for the v2.3.0 tool-improvement target. It is not implementation evidence and does not authorize code changes by itself.

`OPS-FLOW-001` is the related prior research anchor. New code work described here must use the canonical v2.3.0 requirements mapped in Section 6 before implementation.

CLI and MCP names in this document are proposed API sketches unless a Source Evidence Matrix row marks the behavior as already implemented.

The user term `$kiki-planner` was interpreted as the repository skill `$kiwi-planner`.

## 1. Executive Summary

`kiwi-planner`, `kiwi-pm`, `kiwi-coder`, and `kiwi-pipeline` now define a richer operational record than the official SpecKiwi CLI and MCP tools can read or update. The relevant artifacts include:

1. `docs/plans/{run-id}.plan.md`;
2. `docs/plans/{run-id}.sidecar.json`;
3. `docs/plans/{run-id}.validator.json`;
4. `docs/analysis/kiwi-planner-{run-id}/`;
5. `kiwi/pipeline.jsonl` or fallback pipeline locations;
6. `.kiwi/sessions/{run_id}/pm-state.json`;
7. `.kiwi/sessions/{run_id}/state.json`;
8. `.kiwi/sessions/{run_id}/tasks/{task_id}.json`;
9. `.kiwi/sessions/{run_id}/worklog.jsonl`;
10. legacy `docs/plan/**` and `.snoworca/sessions/**` records.

The current official CLI and MCP tools include SRS-oriented reads and mutations, target metadata, notes, links, bootstrap behavior, skill installation, and Completed Work Log support. They still do not provide first-class operations for plan artifact discovery, next task selection, PM resume state, worklog tailing, JSONL validation, pipeline correction handling, or safe checklist mutation. As a result, agents must reread large files, infer state from natural-language skill documents, and sometimes edit Markdown or JSON directly.

The most important v2.3.0 follow-up is therefore not a single checkbox command. It is a small workflow-tooling layer with:

- compact read tools for plan, pipeline, session, and worklog state;
- deterministic next-work-order calculation;
- safe mutation envelopes for checkboxes, task status, JSONL append, and mutation journals;
- validators that understand plan/sidecar/session/worklog consistency;
- artifact and workspace resolvers that make the same path decision in CLI, MCP, and skills.

### 3.7 Operational Decision Rules

The following rules turn the research recommendations into testable behavior. They are not implemented yet, but they define the minimum precision required before v2.3.0 code work starts.

#### 3.7.1 Artifact resolver algorithm

The resolver must return the same answer in CLI, MCP, and skills.

Discovery order:

1. explicit path or explicit run ID;
2. current `docs/plans/**`;
3. current `.kiwi/sessions/**`;
4. legacy `docs/plan/**`;
5. legacy `.snoworca/sessions/**`.

Candidate scoring:

| Signal | Score |
| --- | --- |
| Explicit caller path or run ID match | +100 |
| Current contract path (`docs/plans/**` or `.kiwi/sessions/**`) | +40 |
| Target matches explicit target or Active Target | +30 |
| Plan and sidecar run ID match | +25 |
| Valid parsed `generated_at` | +10 |
| Legacy artifact | -20 |
| Target mismatch | -50 and diagnostic |
| Parse error in required companion | reject candidate |

Tie-breakers after score:

1. `generated_at` descending;
2. file `mtime` descending;
3. relative path ascending.

If two top candidates remain equal after tie-breakers, return `ambiguous_artifact` and do not auto-select unless the caller passes `allowAmbiguousLatest`.

Companion discovery:

1. use plan frontmatter `sidecar_path`;
2. otherwise match basename `{run-id}.sidecar.json`;
3. otherwise search the same directory;
4. otherwise return a missing companion diagnostic.

Confidence:

- `high`: current contract path, target match, plan plus sidecar, matching run ID;
- `medium`: current contract path with one missing noncritical companion;
- `low`: legacy, inferred, missing companion, or target mismatch.

#### 3.7.2 Execution-state precedence

Different artifacts answer different questions. Tools should not merge them by intuition.

| Question | Primary source | Secondary source | Conflict behavior |
| --- | --- | --- | --- |
| What tasks exist? | sidecar `tasks[]` | plan task headings | Sidecar wins; missing plan heading is a diagnostic. |
| What order is legal? | sidecar `depends_on_task` DAG | task id sequence as display only | Dependency cycle blocks next-task selection. |
| Is a task done? | PM `pm-state.json` task status | plan checkbox and worklog terminal event | PM state wins; mismatch returns repairable drift. |
| Can a task start? | Dependency DAG plus PM statuses | coder state for active task | Any dependency not `done` blocks auto selection. |
| Can a session resume? | PM state hashes and lock | coder state hashes and worklog tail | Hash or stale-lock mismatch returns `resume-blocked`. |
| Can a checkbox be written? | PM ownership plus plan hash | exact plan line guard | Child coder ownership or stale hash blocks mutation. |
| What happened recently? | worklog or pipeline parsed JSONL tail | file mtime only as fallback | Invalid JSONL line returns diagnostics with line and byte offset. |

Source ownership:

- sidecar `tasks[]` is the task catalog source of truth;
- sidecar `depends_on_task` is the task ordering source of truth;
- PM `pm-state.json` is execution status source of truth;
- coder `state.json` is active-task and resume-detail evidence;
- worklog is append-only audit evidence;
- plan checkbox/checklist state is display and repair evidence only.

Canonical requirement mapping:

- `task.req_ids` is canonical for execution and SRS trace lookup;
- PM `trace_req_ids` is a derived cache only;
- legacy `task.traces[].req_id` must be migrated or reported as `legacy_trace_field`;
- legacy trace fields must never outrank `task.req_ids`.

Repair outcomes should be explicit:

- `ok`: sources agree;
- `confirmed_done`: PM says done and display/audit sources agree;
- `repairable_drift`: PM state and display artifact disagree, but hashes still match;
- `stale_artifact`: hash or mtime guard changed since state capture;
- `blocked_dependency`: DAG or lifecycle gate prevents next task;
- `needs_user`: PM or pipeline state contains a user question or business decision;
- `invalid_artifact`: JSON/Markdown parsing failed and no safe inference is allowed.

#### 3.7.3 Pipeline `CORRECTION` latest-state algorithm

Pipeline readers must parse JSONL structurally and then compute state:

1. Parse each line as one JSON object; invalid lines become diagnostics and are excluded from state selection.
2. Use `eventKey = skill + ":" + run_id`.
3. A `status=CORRECTION` event must include `corrects_run_id`; the corrected event must exist for the same skill unless the event marks `external: true`.
4. Correction chain max depth is 5. Cycles or deeper chains return `invalid_correction_chain`.
5. Corrected events are excluded from latest-state selection, but remain visible in `tail` output with `correctedBy`.
6. Latest-state selection sorts by parsed timestamp descending, then JSONL line number descending; tail output may still render chronological order.
7. `FAILED` and `NEEDS_USER` block automatic next-step recommendation.
8. `DRY_RUN` is a terminal non-mutating state and must not be collapsed into `TASK_DONE`.

#### 3.7.3.1 Logical delete and `CORRECTION` precedence

Follow-up review for `FR-NODE-031`, `IR-CLI-043`, and `FR-MCP-038` resolved the relationship between `CORRECTION` and logical deletion:

- Do not add `deleted` to the pipeline `status` enum.
- Treat `deleted` as an effective read state created by a guarded tombstone or repair record.
- For pipeline JSONL, logical deletion is represented as `status=CORRECTION` with an optional `operation.kind="logical_delete"` extension, or an equivalent append-only tombstone handled by the JSONL core.
- Existing `schema_version="1.0.0"` events without `operation` remain accepted and active unless a valid tombstone or correction excludes them.
- Logical delete takes precedence over correction. A directly tombstoned event cannot be resurrected by correction-of-correction.
- `includeDeleted` is a read/list/tail option only. Delete mutation inputs require `reason`, `owner`, target identity, stale guards, and idempotency, not `includeDeleted`.
- Plan Markdown deletion must not physically remove task or checkbox lines. The tombstone source of truth belongs in append-only journal, worklog, PM state, or repair records; plan Markdown is only a display projection.

Effective-state computation order:

1. Parse and validate JSONL lines.
2. Reject duplicate active event identities as ambiguous.
3. Validate logical-delete tombstones and apply them first.
4. Validate `CORRECTION` chains and apply them second.
5. Exclude meta, invalid, corrected, and deleted records from latest-state candidates.
6. Sort remaining candidates by timestamp descending, then line number descending.
7. Return `correctedBy`, `deletedBy`, and `inactiveReasons` only in audit or `includeDeleted` views.

Restore or undelete behavior is out of scope for this release slice. Tombstone-of-tombstone, correction-of-tombstone, and plain delete of a `CORRECTION` event must be rejected until a future restore requirement defines safe semantics.

#### 3.7.5 Required workflow read envelope

All plan, artifact, pipeline, session, worklog, and work-order read tools MUST use one compact response envelope. The envelope is not an illustrative shape; it is the minimum contract that CLI and MCP implementations must preserve so agents can consume workflow state without rereading raw Markdown, sidecar JSON, PM state, coder state, pipeline JSONL, and worklog JSONL.

```json
{
  "ok": true,
  "value": {},
  "meta": {
    "tool": "get_next_plan_task",
    "schemaVersion": "workflow-read-v1",
    "workspaceRoot": "/abs/path",
    "target": "v2.3.0",
    "generatedAt": "2026-06-27T00:00:00.000Z"
  },
  "artifacts": [],
  "cursor": null,
  "diagnostics": [],
  "diagnosticsSummary": { "errors": 0, "warnings": 0, "byCode": {} }
}
```

Required fields by tool family:

| Tool family | Required `value` fields | Required support fields | Failure behavior |
| --- | --- | --- | --- |
| workspace/artifact | `workspaceRoot`, `rootSource`, `artifact.kind`, `artifact.relativePath`, `artifact.exists`, `artifact.legacy`, `artifact.confidence` | `artifacts[]`, diagnostics for ambiguity and target mismatch | `ambiguous_artifact`, `artifact_not_found`, or `outside_workspace` with no guessed path |
| plan status/task | `plan.runId`, `plan.planContract`, `taskCount`, status counts, task IDs, dependency state | companion paths, plan and sidecar hashes | `invalid_plan_contract`, `missing_sidecar`, or `task_state_conflict` |
| next task | all plan status fields plus `nextTask`, `ready`, `reason`, `blockedBy[]` | state precedence result and repair outcome | `blocked_dependency`, `dependency_cycle`, or `repairable_drift` |
| pipeline status/tail | `events[]` or latest event, `eventKey`, `status`, `correctedBy`, `blocksAuto` | cursor, invalid-line diagnostics | `invalid_jsonl`, `duplicate_event_key`, or `invalid_correction_chain` |
| session/resume | `runId`, `currentTask`, lock state, hash match state, `resumeKind`, `reason` | PM/coder state paths and worklog cursor | `resume-blocked`, `stale_artifact`, or `pending_repair` |
| work order | `kind`, `target`, `requirementIds`, `nextAction`, `reason`, `blockingDiagnostics` | artifact references and hashes sufficient to resume | `ask-user`, `fix-artifact`, or `blocked` kind instead of a speculative action |

Failure envelope:

```json
{
  "ok": false,
  "error": {
    "code": "ambiguous_artifact",
    "message": "Multiple latest plan candidates have equal score.",
    "recommendedCommands": []
  },
  "diagnostics": [],
  "diagnosticsSummary": { "errors": 1, "warnings": 0, "byCode": { "ambiguous_artifact": 1 } }
}
```

Default responses MUST be compact. Full Markdown or JSON bodies require explicit `includeBody: true`. Every success and failure response MUST include enough paths, hashes, cursors, diagnostics, and recommended follow-up command names for a caller to continue without scanning all workflow artifacts.

#### 3.7.6 Required workflow mutation envelope and write order

Workflow mutations reuse the mutation envelope defined in `docs/research/09.mcp-cli-tool-abandonment-research.md`. The workflow-specific extension MUST expose write ordering and partial-failure state instead of hiding it behind a boolean success flag.

New mutation kinds include:

- `plan_checkbox_check`;
- `plan_checkbox_uncheck`;
- `plan_checklist_item_update`;
- `pm_task_status_update`;
- `jsonl_append`;
- `workflow_repair_record`.

Logical deletion is a companion mutation family, not a synonym for unchecking a task or rolling back PM status. It uses the same envelope but returns `target.state="deleted"` and records a tombstone or repair record. Supported record classes are governed by `FR-NODE-031`; CLI and MCP parity are governed by `IR-CLI-043` and `FR-MCP-038`.

Required mutation response fields:

| Field | Requirement |
| --- | --- |
| `mutation.kind` | One of the workflow mutation kinds above. |
| `mutation.workflow.runId` | Stable workflow run/session ID. |
| `mutation.workflow.taskId` | Task ID when the operation is task-scoped. |
| `mutation.workflow.owner` | `kiwi-pm`, `kiwi-coder`, or `manual-repair`; child coders cannot directly mutate plan checkboxes. |
| `mutation.workflow.pendingRepair` | `null` on complete success; otherwise a repair record with `reason`, `completedOperations[]`, and `pendingOperations[]`. |
| `mutation.operations[]` | Ordered operation records with `type`, `phase`, `filePath`, `line`, `original`, `replacement` or `lines`, `guard`, `result`, `beforeHash`, `afterHash`, and `diagnostics[]`. |
| `mutation.written` | `true` only when every required write is confirmed. `false` for dry-run, idempotent no-op, stale guard, and repairable partial failure. |
| `mutation.result` | `written`, `dry_run`, `already_applied`, `stale`, `forbidden_owner`, `repairable_drift`, or `failed`. |

Multi-artifact write order:

1. Resolve workspace and artifacts with Section 3.7.1.
2. Read plan, sidecar, PM state, coder state, and worklog as needed.
3. Verify plan/sidecar hashes, exact line guard, owner, and task dependency preconditions.
4. Compute idempotency key from the canonical journal identity: `sha256(tool|run_id|task_id|req_id|canonicalJson(flat_args))`; non-requirement-scoped operations use the documented empty stable `req_id` token.
5. If already applied, return `mutation.written:false` and `mutation.result:"already_applied"`.
6. If `dryRun=true`, return the full ordered operation plan with `mutation.written:false` and no file writes.
7. Write or update PM state with a `pending_mutation` entry.
8. Append a worklog `mutation_planned` or `mutation_applying` event.
9. Apply the guarded plan/checklist write when required.
10. Append a worklog `mutation_applied` event after the write succeeds.
11. Update PM state from `pending_mutation` to `confirmed`.
12. Re-read touched files, verify hashes, and return final operation results.

Failure semantics:

| Failure point | Required result | Required state |
| --- | --- | --- |
| Before first write | `written:false`, `result:"stale"` or `result:"forbidden_owner"` | No mutation event and no plan write. |
| PM `pending_mutation` write fails | `written:false`, `result:"failed"` | No later worklog or plan write is attempted. |
| Worklog append fails after PM pending state | `written:false`, `result:"repairable_drift"` | PM state contains `mutation.workflow.pendingRepair` with worklog append pending. |
| Guarded plan/checklist write fails after PM/worklog writes | `written:false`, `result:"repairable_drift"` | PM state contains completed PM/worklog operations and pending plan operation. |
| Final PM confirmation fails | `written:false`, `result:"repairable_drift"` | Worklog records applied mutation; PM state keeps pending repair for confirmation. |
| Post-write hash verification fails | `written:false`, `result:"repairable_drift"` | Response lists all touched files and pending repair steps. |

Atomicity rule: if a single logical operation must touch multiple artifacts, the response MUST expose which artifacts were written, which remain pending repair, and which command can repair or roll forward the mutation. Silent partial success is forbidden.

## 4. Validity Review and Iteration

The 10-axis findings were reviewed for internal consistency before this report was written. The following corrections were applied:

| Initial Finding | Validation Issue | Final Position |
| --- | --- | --- |
| "Add a checkbox tool" | A checkbox alone does not determine whether work is safe to mark done. PM state, task status, and plan SHA must agree. | Add a guarded checklist mutation tool plus PM/session consistency validation. |
| "Next task is the next task ID" | `kiwi-planner` defines `depends_on_task`; task IDs are only stable labels. | Next-task tools must compute readiness from DAG dependencies and PM task statuses. |
| "Use only `docs/plans/**`" | The checkout mostly has legacy `docs/plan/**` and `.snoworca/**` samples. | Artifact discovery must include both current and legacy locations, returning confidence and `legacy` flags. |
| "Use `kiwi-pipeline` for next step" | The skill appends an event for itself; that is not a pure read. | CLI/MCP should provide read-only pipeline status and next recommendation tools. |
| "Store checklist state in `acceptance_tests`" | Planner sidecar checklist entries are test definitions, not execution state. | Execution checks belong in PM/session state or a sidecar progress layer, with idempotent mutation APIs. |
| "Trust `mcp_call_log.args_hash`" | Planner and coder describe different hash inputs and earlier drafts omitted run identity. | Standardize mutation journal keys as `sha256(tool|run_id|task_id|req_id|canonicalJson(flat_args))`. |
| "Resume from coder state alone" | PM stores plan/sidecar SHA, but coder state does not. | Coder state should also store `plan_sha256`, `sidecar_sha256`, `git_head`, `dirty_diff_sha256`, and `task_input_sha256`. |

No finding was accepted solely because a sub-agent proposed it. Each high-priority recommendation was retained only if it matched at least one repository source contract or observed artifact gap.

## 8. Token Reduction Design

A common failure mode is that agents repeatedly read full `plan.md`, sidecar JSON, PM state, and worklog files to answer narrow questions. The proposed tools should return layered summaries:

| Question | Current likely behavior | Proposed compact tool |
| --- | --- | --- |
| "What is the next task?" | Read full plan, sidecar, PM state, worklog | `get_next_work_order` or `get_next_plan_task` |
| "Did task T finish?" | Read PM state and worklog | `get_plan_task` |
| "What happened most recently?" | Read entire `pipeline.jsonl` or worklog | `tail_pipeline_events`, `tail_worklog_events` |
| "Can I resume?" | Read plan, sidecar, PM state, coder state, lock | `get_resume_hint` |
| "Where is the latest plan?" | Glob and inspect multiple dirs | `get_latest_artifact` |

Proposed pagination and tailing `value` fragment:

The following JSON is a `value` fragment shared by tail/list tools. It is intentionally not a full response. Full responses MUST still use the Section 3.7.5 envelope and place this object under `value.pagination` or an equivalent documented `value` field.

```json
{
  "limit": 20,
  "maxLimit": 100,
  "cursor": {
    "path": "kiwi/pipeline.jsonl",
    "byteOffset": 12345,
    "line": 80,
    "mtimeMs": 1782450000000
  },
  "nextCursor": {},
  "hasMore": true
}
```

Default response policy:

- list tools return compact rows by default;
- full Markdown or full JSON bodies require `includeBody: true`;
- tail tools default to the last 5-20 events;
- every response includes enough path and hash data to detect stale follow-up calls.

Measurement requirement before making numeric claims:

1. Build fixtures for current and legacy plan/session artifacts.
2. Record byte counts and approximate token counts for full-file reads needed to answer each question above.
3. Record byte counts and approximate token counts for the proposed compact response.
4. Treat the reduction percentage as verified only after the fixture test prints the before/after values.

Section 3.7.4 defines the minimum measurement scenarios and output fields. A tool can be useful before numeric savings are proven, but release notes should not claim a measured percentage until those tests exist.

## 9. Hallucination Reduction Rules

### 9.1 Use one canonical task-to-requirement field

Current skill text has drift: PM text mentions `task.traces[].req_id`, but planner sidecar tasks use `req_ids` and `trace_links`.

Proposed rule:

- `task.req_ids` is the execution SSOT;
- `trace_links` is graph evidence;
- legacy `traces[]` is rejected by validators or migrated explicitly;
- tools must return `reqIds` from canonical `task.req_ids` only.

### 9.2 Use hash guards for resume

PM state stores `plan_sha256` and `sidecar_sha256`; coder state should also store:

- `plan_sha256`;
- `sidecar_sha256`;
- `git_head`;
- `dirty_diff_sha256`;
- `task_input_sha256`.

Resume tools should fail closed on mismatches and provide a repair recommendation rather than silently continuing.

### 9.3 Standardize mutation journal keys

Planner and coder currently describe different `args_hash` inputs. Standardize all mutation journals on:

```text
sha256(tool|run_id|task_id|req_id|canonicalJson(flat_args))
```

This supersedes earlier local sketches that omitted `run_id`, `req_id`, or canonicalized flat arguments. Implementers must follow the SRS canonical identity requirement rather than the historical draft formulas.

Proposed mutation states:

- `planned`;
- `applied`;
- `confirmed`;
- `failed`;
- `skipped_dry_run`.

This separates "we intended to call this" from "the call definitely reached the SRS".

### 9.4 Hallucination Reduction Acceptance Gates

Hallucination reduction must be measured through deterministic fixture failures, not claimed by intent.

| Risk | Fixture Gate | Passing Behavior |
| --- | --- | --- |
| Wrong requirement field | Fixture includes legacy `task.traces[].req_id` and canonical `task.req_ids` with different values. | Tool returns canonical `reqIds` from `task.req_ids` and reports `legacy_trace_field`. |
| Wrong artifact path | Fixture contains current and legacy plans with similar run IDs. | Resolver selects current artifact by score or returns `ambiguous_artifact`; it never silently picks legacy. |
| Wrong next task | Fixture has task ID order that conflicts with `depends_on_task`. | `get_next_plan_task` follows DAG and reports blocked dependencies. |
| Stale resume state | Fixture changes plan hash after PM state capture. | `get_resume_hint` fails closed with `stale_artifact` or `resume-blocked`. |
| Invalid JSONL inference | Fixture contains malformed line and duplicate event key. | Parser reports line/byte diagnostics and excludes invalid records from latest-state selection. |
| Unsafe manual mutation | Fixture attempts plan checkbox write from child coder ownership. | Mutation rejects ownership and records no plan write. |

Pair-level utility gate with `docs/research/09.mcp-cli-tool-abandonment-research.md`:

| Scenario | Baseline | Compact official path | Required proof |
| --- | --- | --- | --- |
| Agent asks "what should I do next for v2.3.0?" | Read SRS index, target summary, plan files, sidecar, PM state, pipeline JSONL, and worklog manually. | Use compact requirement search/list and `get_next_work_order`. | Measurement output includes byte/token reduction, all required fields present, deterministic next action, no raw Markdown/JSON edit, and no hallucinated field names. |

## 14. Conclusion

The next v2.3.0 tool-improvement work should treat Kiwi planner JSONL and session artifacts as first-class SpecKiwi operational data. The core problem is not that agents lack discipline; it is that the repository now has multiple workflow state files without official compact readers, validators, or safe mutators.

The highest-leverage path is:

1. artifact resolver;
2. read-only status and next-work-order tools;
3. execution-state validators;
4. JSONL/checklist mutation safety;
5. logical-delete repair safety;
6. Kiwi skill migration to those official tools.

That sequence is expected to reduce token use after fixture payload measurements confirm it, narrow the context an agent must hold, and remove several sources of hallucinated field names, wrong artifact paths, and unsafe manual JSON or Markdown edits.

The source-backed code improvement plan for these recommendations is recorded in `docs/research/11.v2.3.0-tooling-code-improvement-plan.md`.
