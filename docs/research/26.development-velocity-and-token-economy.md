## 1. 무엇이 느린가

### 1.1 도구는 느리지 않다

### 1.2 워크플로가 읽기를 지시한다

> "Find the relevant Requirement ID **in the scope SRS files**."

| `60.workflow-release.srs.md` | 10,108 |

그리고 `search_requirements` 와 `speckiwi search` 는 **`skills/**` 130개 파일 어디에도, `CLAUDE.md` 어디에도 없다.** `README.md` 에만 있다. 에이전트가 검색에 도달하는 경로가 워크플로 안에 존재하지 않는다.

### 1.4 실제 사고 두 건에 이 구분을 대입한다

두 번 다 회귀가 아니라 **모순**이었고, 두 번 다 구현이 끝난 뒤에 드러났다. 그리고 두 번 다, 앞에서 400줄이면 막혔다.

### 1.5 그래서 계획 산문은 이것을 막지 못한다

계획서가 있었다면 거기 적혔을 것은 "`FR-NODE-193` 을 구현한다"이다. 그것은 요구의 재서술이지 검사가 아니다. **계획은 산문이고, 산문은 자기가 무엇과 모순되는지 모른다.** 계획을 살리는 것과 모순을 막는 것은 다른 축이며, 후자는 질의로 해결된다.

`FR-PARSE-030` 이 이 논지의 실물 증거다. Status `implemented` 로 진단 코드 셋을 내겠다고 선언하는데, `SRS-W041` 은 레지스트리(`src/core/diagnostic-registry.ts:440`)에서 **다른 요구(`FR-PARSE-021`)가 다른 뜻으로 점유**하고 있고, `SRS-W042`·`SRS-W043` 은 `src`·레지스트리·테스트 어디에도 없다. 계획서가 있었어도 이 사실은 계획서 안에 없다. 잡을 수 있었던 것은 `SRS-W041` 을 한 번 검색하는 것(히트 1개)이다.

## 4. 축 1 — 읽기를 질의로 바꾼다 (선행)

### 4.1 `CLAUDE.md` 워크플로 교체

지금:

> 2. Find the relevant Requirement ID in the scope SRS files.

바꿀 방향:

> 2. 신규·수정 요구가 **이름을 대는 식별자마다** `search_requirements`(CLI `speckiwi search`)를 돌린다. 식별자란 파일 경로, 진단 코드, CLI 플래그, 도구 이름, 함수·타입 이름, 아티팩트 파일명이다. 히트가 0이 아니면 그 요구들을 읽고 모순 여부를 판정한 뒤 작업한다.

주제어가 아니라 식별자로 부르게 만드는 것이 이 문장의 전부다. §1.3 이 그 차이를 값으로 보여준다.

### 4.2 `add_requirement` 가 스스로 검색한다

입력(요구문·AC)에서 식별자를 뽑아 검색하고 **후보를 되돌려 준다.** 차단이 아니라 보고다. 차단으로 만들면 정당한 신규 요구가 막히고, 막히면 우회 경로가 생긴다.

`search_requirements` 는 이미 있다. 없는 것은 호출 시점뿐이다.

### 4.3 검색이 플래그를 찾지 못하는 결함

```
speckiwi search "--force"              → 0 히트
speckiwi search "orchestrator-run.lock" → 0 히트
```

`--force` 는 앞의 `--` 가 옵션으로 파싱되는 것으로 보인다. **플래그를 검색할 수 없으면 §4.1 의 지시가 절반만 작동한다.** `--force` 는 요구를 파괴하는 플래그이므로 이 구멍은 특히 나쁘다.

`orchestrator-run.lock` 의 0 히트는 원인을 확인하지 못했다. SRS 가 그 리터럴 경로를 한 번도 적지 않았을 가능성이 있고(그렇다면 검색 결함이 아니다), 토큰화 문제일 가능성도 있다. **구분되지 않았다.**

### 4.4 왜 이것이 먼저인가

반나절이면 되고, 축 2 의 요구 폐기 작업 자체가 축 1 의 도움을 받는다. 요구 25개를 폐기하려면 그 요구들이 무엇과 얽혀 있는지 먼저 알아야 하고, 그것이 정확히 식별자 검색이다.

## 7. 확인하지 못한 것과, 이 문서가 스스로 반증한 것

### 7.1 작성 중 반증한 다섯 건

1. **"SRS 가 이름을 대지만 코드에 없는 진단 코드 9개"** → **실제 2개.** 나머지 7개(`SRS-E009`·`E026`·`E031`·`W005`·`W006`·`W007`·`W021`)는 `50.nodejs-implementation.srs.md:6468` 의 Implementation Notes 에 코드마다 미구현 사유가 적혀 있다. 의도된 미구현이며 결함이 아니다.
2. **"CLI 60개 중 59개 미사용"** → 인라인 `node -e` 를 거치며 `"\b"` 가 워드 경계에서 백스페이스 문자(U+0008)로 바뀌어 **정규식이 아무것도 매치하지 않았다.** 검사가 돌지 않았는데 결과를 냈다.
3. **"CLI 59개 중 53개 미사용"** → 같은 결함의 재발. 두 번째에야 원인을 확인했고, 이후 모든 실사를 스크립트 파일로 옮겼다.
4. **`scaffold_scope` 를 미사용으로 분류** → `CLAUDE.md` 가 CLI 형태(`speckiwi scaffold-scope … --apply`)로 그것을 권장한다. MCP 이름만 찾아 쌍둥이 CLI 를 놓쳤다.
5. **`README.md` 를 워크플로 소비자로 계산** → `search` 가 "사용됨"으로 잡혔다. **이 문서가 §1 에서 비판하는 "분모가 틀렸다"를 저자가 그대로 저질렀다.**

2·3번은 이 저장소가 반복해 겪는 결함 유형이다. 검사가 조용히 돌지 않고 "깨끗함"을 보고한다. 그것을 잡은 것은 통찰이 아니라 **결과가 상식에 어긋난다는 사실**(60개 중 59개 미사용)이었다.

### 7.2 확인하지 못한 것

- **미사용 표면의 코드 규모.** 파일명 기준으로 1,048줄(src 40,347 중 2.6%)을 냈으나 **과소 계수다.** 큰 공용 파일 안에 흩어진 구현이 빠졌다. 실제 규모는 폐기 결정 후 재측정해야 한다.
- **토큰 환산.** 전부 `chars ÷ 4` 근사다. 한국어 비중이 높아 실제 토큰은 더 크지만 배수는 측정하지 않았다.
- **`orchestrator-run.lock` 검색 0 히트의 원인** (§4.3). 검색 결함인지 SRS 가 그 리터럴을 안 쓰는 것인지 구분되지 않았다.
- **축 1 의 효과 크기.** §1.4 는 사고 두 건에 대한 사후 대입이다. "식별자 검색을 워크플로에 넣으면 모순이 줄어든다"는 인과는 이 문서가 측정한 것이 아니며, 요구로 승격하려면 별도 근거가 필요하다.
- **스킬 변종 89% 동일**은 `kiwi-orchestrator` 한 건의 줄 단위 비교다. 51개 전체의 동일률은 크기 비교로만 추정했다.

## 8. 연구 24·25 와의 관계

- **연구 24**(SRS 다음의 계획)는 "산문 계획은 감가했고 기계 검증 가능한 계획 아티팩트는 상승했다"로 끝난다. 이 문서는 그 뒤를 잇는다. 계획의 자리를 이어받은 것은 **아무것도 없었고**, 계획이 잡았을 유일한 것(기존 요구와의 충돌면)은 계획이 아니라 **질의**로 해결된다.
- **연구 25**(도구가 자기 주장을 검사하게 만들기)와 축이 다르되 어긋나지 않는다. 25 는 *도구가 자기에 대해 하는 진술을 검사하게* 만들고, 이 문서는 *도구가 자기 크기를 줄이게* 만든다. `FR-PARSE-030` 은 두 문서가 같은 대상을 다른 이유로 지목한 지점이다 — 25 의 관점에서는 거짓 진술이고, 이 문서의 관점에서는 사용 0건인 기능이다.
- 25 §3 이 지적한 "증거 참조 해석이 target 스코프라 427개 verified 요구가 무검사"와 이 문서 §1.5 의 `FR-NODE-087` AC-9 (진단 코드 대조가 `docs/rule/**` 에만 적용)는 **같은 형태다.** 검사가 틀린 것이 아니라 분모가 틀렸다. §7.1 의 5번은 저자가 같은 실수를 반복한 기록이다.
