## 0. 한 장 요약

1. **계획 모드는 없애도 된다. 다만 한 번에 지우지 말고, 계획이 맡던 조정 역할을 시멘틱 SDS 로 옮긴 뒤 지운다.** 없앨 대상은 계획을 쓰고 검증하는 `kiwi-planner` 와, 그 계획을 Task 단위로 실행하는 `kiwi-pm` 이다(`kiwi-coder` 는 `kiwi-pm` 이 Task 마다 띄우는 자식이다). 연구 32 는 이 가운데 kiwi-planner 식 계획과 그 검증 루프를 쟀고, 둘 다 강한 모델의 품질에 기여하지 않았다. `kiwi-pm`·`kiwi-coder` 실행 경로 자체는 연구 32 가 재지 않았다(구현은 에이전트 하나가 계획을 읽고 했다). 이 저장소도 2026-07-28 이후 두 달 동안 `kiwi-planner`·`kiwi-pm` 없이 개발됐다.
2. **지우기 전에 옮겨야 할 것이 있다.** 가장 무거운 의존은 `kiwi-orchestrator` 의 R-ORCH 경로다. lane 분할·handoff·allocation·grounding·freeze·resume 이 모두 계획 사이드카의 Task 목록을 입력으로 받는다. 계획 산출물을 입력으로 받는 `src` 파일은 20 개, 계획에 기대는 요구는 64 개(모두 `evolving`), 계획 전용 테스트는 약 39 파일이다.
3. **초경량 SDS 는 시멘틱화할 수 있다. 새 문서 종류가 아니라 기존 SDS 규칙의 경량 프로필(`Profile=lite`)로 둔다.** 필수 절을 Interfaces·Acceptance Contracts·Test Plan 셋으로 줄이고, Interfaces 절에 들여쓰기 목록 3 단계(파일 / 심볼 / 멤버)와 `@req`, `← 호출자`, `Depends` 문법을 쓴다. SRS 해석 결정은 `SDS-AC-n (REQ AC)` 줄로 쓴다. 그러면 기존 검사(SDS-W052)가 해석 결정마다 Test Plan 행을 강제한다. 언어 중립 텍스트 검사로 시작하고, 정밀 검사는 언어 어댑터로 붙인다.
4. **실측으로 효과를 확인했다.** 연구 32 에서 약한 모델이 실패한 "선언했지만 부르지 않은 함수"를, import 줄을 뺀 연결 검사가 잡았다. 같은 검사를 설계 문서 전체에 돌리자 미연결 심볼 5 개가 나왔고 오탐은 0 이었다. 파일 위치 검사는 잘못 배치된 함수 2 개를, 시그니처 검사는 반환형이 `any` 로 약해진 곳 1 개를 찾았다.
5. **구조로 잡히지 않는 실패도 있다.** SRS 의 비직관적 규칙(던지는 오류 코드만 다른 경우)은 어떤 구조 검사로도 잡히지 않는다. 설계 문서의 해석 결정 줄과 동작 테스트로 막는다. 기계는 결정 줄의 요구·AC 가 실재하는지와 그 AC 를 인용한 테스트가 있는지까지 보장한다.
6. **외부 근거는 같은 방향이다.** 강한 모델에서는 작업 분해를 걷어내는 추세다(Anthropic 의 sprint 분해 제거, Claude Code 의 TodoWrite 교체). 반면 조정·영속 역할의 작업 목록은 오히려 도구화되고 있다(Claude Code Tasks, Beads, Kiro wave). 코드에 가까운 설계 형식은 약한 모델의 격차를 가장 많이 메웠다(arXiv 2608.21747). 숨긴 기능 테스트만으로는 설계 문서가 지키는 구조 품질을 재지 못한다는 결과도 같은 연구에 있다.
7. **추천하는 방법**: SRS → 시멘틱 초경량 SDS → 결정적 설계 검사 → 구현(TDD) → 코드 전용 리뷰 1 명 → `--close-reqs`. 진행 추적과 재개는 요구 상태·AC 체크·pipeline 저널과 SDS 자체가 맡는다(§4).

`R-STEP`·`R-PLAN`·`R-ORCH` 는 `kiwi-orchestrator` 가 작업 규모를 보고 고르는 세 실행 경로(rung)다(`skills/claude/kiwi-orchestrator/SKILL.md:244-247`, `:403`).
- `R-STEP`: 작은 작업. `kiwi-tdd` 한 번 → 리뷰 → 끝. 계획을 쓰지 않는다.
- `R-PLAN`: 이미 있는 계획 파일을 실행. `kiwi-pm` → `kiwi-review-fix-loop --close-reqs`.
- `R-ORCH`: 큰 작업. 설계 문서를 쓰고 작업을 wave(3~8 개 하위 목표)로 나눈 뒤, wave 마다 `kiwi-srs` → `kiwi-planner` → lane 분할(계획 사이드카의 Task 별 파일 목록으로 겹치지 않게 묶음) → lane 마다 handoff 문서 → `kiwi-pm` 을 직렬로 돌린다(`:253-300`). 다른 두 경로가 조건에 맞지 않으면 항상 이 경로로 떨어진다.

계획을 참조하는 스킬 디렉터리는 렌더링마다 14 개다. `validator.mjs` 는 네 벌(claude·codex·etc·`.agents`) 있다.

### 1.5 이력

- 계획 모드를 통째로 없애자는 문서는 없었다. 연구 24·30·32 는 모두 "형태를 바꾸라"는 결론이었다.
- **반대 방향의 사용자 결정이 있다.** 2026-08-24 "계획 단계는 유지. 사이드카가 21개 src 파일의 입력이므로"(`docs/plan/3.0.0/00.index.md:56`). 이번 조사의 계수는 20 개다. 이 결정의 근거는 사이드카가 입력이라는 사실이므로, 입력을 SDS 로 옮기면 근거가 사라진다. 그래도 결정을 뒤집는 것은 사용자가 명시해야 한다.
- 실사용: `kiwi/pipeline.jsonl` 의 마지막 planner 이벤트는 2026-07-28 이다. 이후의 대형 작업(계획 3.0, 33 항목)은 손으로 쓴 계획 문서와 서브에이전트 직접 조율로 끝났다.
- 다른 사용자 프로젝트가 `kiwi-planner` 를 얼마나 쓰는지는 확인하지 못했다.

## 2. 외부 근거

### 2.1 "계획"은 네 가지를 가리킨다

외부 연구와 도구가 재는 대상이 다르다. (a) 작업 흐름 단계 순서, (b) 에이전트 내부 할 일 목록 도구(TodoWrite 등), (c) 제품 명세, (d) 사람이 읽는 작업 목록 문서(Spec Kit·Kiro 의 `tasks.md`). 연구 32 가 없앤 것은 (d) 에 가깝다. **(d) 의 유무를 통제 비교한 외부 연구는 찾지 못했다.**

### 2.2 모델 능력에 따라 계획의 효과가 뒤집힌다

- 할 일 목록 도구는 약한 모델(Nemotron-3 30B)의 SWE-Bench 성공률을 +11.6 %p 올렸다. 강한 모델에서는 성공률이 거의 그대로(-2.0, -0.4 %p)이고 비용이 약 30% 줄었다(Fan et al., arXiv 2609.20804, 원문 대조).
- Haiku 4.5 에 할 일 목록 도구를 주자 어려운 문제의 성공이 52/60 에서 45/60 으로 떨어졌다. 저자는 "minimal guidance outperforms detailed procedural scaffolding" 이라고 적었다(arXiv 2508.07468, 원문 대조). 연구 32 에서 긴 계획이 Haiku 를 도중에 멈추게 한 것과 같은 방향이다.
- 잘못되거나 불완전한 계획은 계획이 없을 때보다 해롭다(Liu et al., arXiv 2604.12147, Finding 8).

### 2.3 벤더들은 분해를 걷어내고, 조정은 도구화한다

- Anthropic 은 Opus 4.6 에서 sprint 분해를 통째로 뺐다. 제품 명세를 쓰는 planner 는 남겼는데, 없으면 생성기가 범위를 좁게 잡았기 때문이다. planner 는 세부 구현이 아니라 "product context and high level technical design" 에 집중했다. 세부를 미리 틀리게 적으면 오류가 구현으로 번지기 때문이다.
- Claude Code 는 "개선된 모델에게 할 일 목록이 제약이 됐다"며 TodoWrite 를 Tasks 로 바꿨다. Tasks 는 모델을 이끄는 도구가 아니라 에이전트 사이의 조정 도구다(의존성, 공유, 디스크 영속).
- Claude Code 공식 권고: "If you could describe the diff in one sentence, skip the plan."
- Spec Kit 실사용 보고는 계획 단계만 마크다운 2,067 줄, 에이전트 33 분 + 검토 3.5 시간이었다. 반복 프롬프트로는 에이전트 8 분이었고, 저자는 "I didn't see any qualitative benefit to justify the overhead" 라고 적었다.
- OpenAI 의 ExecPlan 은 작업 목록을 따로 두지 않는다. 설계와 진행을 한 문서에 담고, 체크리스트는 Progress 절에만 허용한다. 마일스톤마다 존재해야 할 타입·인터페이스·함수 시그니처를 적으라고 요구한다.
- 재개·분할·추적 역할은 작업 목록이 사라지지 않고 **도구화**된다: 진행 파일, JSON 기능 목록의 `passes` 플래그, git 로그, 의존성 있는 공유 작업 목록, 파일 잠금 claim. 진행의 기준은 "작업 체크"에서 "검증 가능한 기준(테스트, `passes`)"으로 옮겨 가고 있다(조사자 종합).

### 2.4 설계 문서의 기계 검사는 성숙해 있다

- ArchUnit 은 PlantUML 도표 자체를 규칙으로 쓴다(`adhereToPlantUmlDiagram`). import-linter(`contracts`), dependency-cruiser, Spring Modulith 도 의존 방향을 결정적으로 검사한다.
- OpenAI 는 계층 규칙(Types → Config → Repo → Service → Runtime → UI)을 Codex 가 만든 커스텀 린터로 강제했다(2 차 출처).
- **"Architecture as Capability Equalizer"(Canedo, arXiv 2608.21747)**: 정보량이 같은 설계 명세 다섯 형식을 비교했다. 코드에 가까운 형식(TypeScript 인터페이스 계약 + ArchUnit 식 규칙, OpenAPI)이 약한 모델의 격차를 가장 많이 메웠다. 가장 약한 모델의 라우트 구현률은 산문일 때 33%, TypeScript 계약일 때 100% 였다. 강한 모델에서는 형식 차이가 작았다.
- 같은 연구의 기준선: 설계 지침 없이 기능 요구만 주어도 기능 테스트는 100% 통과했다. 그러나 구조 준수 점수(LLM 심사)는 8.42 에서 5.08 로 떨어졌고, 코드는 평평한 핸들러와 공유 저장소로 흘렀다. **숨긴 인수 테스트는 설계 문서가 지키는 구조 품질을 재지 못한다.** 연구 32 의 "강한 모델은 계획 없이 100%"도 기능 기준의 결과다.
- 한계: 결정적 검사와 LLM 심사의 상관은 약했다(r = 0.21). 의미 수준의 설계 위반은 결정적 검사로 다 잡히지 않는다.

## 3. 초경량 SDS 의 시멘틱화

### 3.1 지금 있는 것

- **tdd 모드 SDS**(`docs/spec/steps/<task>/design.md`)는 기계가 거의 읽지 않는다. 검사는 필수 제목 7 개(SDS-W051), SDS-AC 와 Test Plan 의 대응(W052), 200 줄 상한(W053), Status 값, 설계 생략 기록(E054)뿐이다. `## Interfaces` 절은 파싱하지 않고 코드와도 대조하지 않는다. 이 검사들은 tdd 모드에서만 돈다.
- **speckiwi 에는 심볼 단위 코드 대조 기반이 없다.** AST·tree-sitter·TypeScript 컴파일러 API·LSP 의존성이 없다(런타임 의존성 3 개). 코드 쪽 검사는 trace·evidence 가 가리키는 파일 경로가 있는지와, `@step` 주석을 텍스트로 찾는 것뿐이다.
- 대상 프로젝트 언어는 정해져 있지 않다. 스킬은 10 개 이상 언어의 주석 형식을 다룬다. 그래서 핵심 검사는 언어 중립 텍스트 검사로 두고, 정밀 검사만 언어 어댑터로 붙인다.

### 3.2 문법 제안

사람이 읽는 문서가 먼저다. 기계용 표식은 `@req`, `←`, `→`, `SDS-AC-n (REQ AC)` 넷으로 제한한다. 절 구성은 기존 SDS 규칙의 제목(Interfaces, Acceptance Contracts, Test Plan)을 그대로 쓴다. 코드 블록은 쓰지 않는다(한 줄 다중 선언을 가르려면 언어 문법이 필요하다). 시그니처 본문은 불투명 텍스트로 다룬다.

```markdown
# SDS: todo-service

| Field | Value |
|---|---|
| Document Type | sds |
| Profile | lite |
| Target | v1 |
| Status | draft |
| Lang | ts |
| Root | src |

## Interfaces

### Depends
- index → service → query, activity, snapshot, access → store, validate
- validate → recurrence
- errors → types
- * → types, errors, util

### Files
- `validate.ts` — 인자 형식·필드 규칙 검증과 정규화, 위반은 모두 VALIDATION
  - `parseExpectedVersion(v: unknown): number` — 양의 정수 ← service @req TODO-016
  - `parseCreateInput(v: unknown): Required<CreateTaskInput>` / `parsePatch(v: unknown): TaskPatch` — 기본값 채운 입력 / 허용 키 ← service
- `store.ts` — 인메모리 상태 전부와 과제 트리 탐색
  - `class Store` — 상태 보관과 순번 카운터
    - `touch(t: TaskRecord, now: number): void` — version + 1, updatedAt = now ← service

## Acceptance Contracts
- SDS-AC-1 (TODO-002 AC-3): WHEN expectedVersion 이 양의 정수가 아니면 THE SYSTEM SHALL 버전 비교·삭제 상태 검사보다 먼저 VALIDATION 을 던진다 → `parseExpectedVersion`
- SDS-AC-2 (AUTHZ-003 AC-4): WHEN create* 입력의 id 필드가 아닌 곳에 형식이 잘못된 id 가 오면 THE SYSTEM SHALL INVALID_ARGUMENT 가 아니라 *_NOT_FOUND 를 던진다 → `requireUser`, `requireRole`

## Test Plan
- SDS-AC-1: 변경 메서드 다섯 개에 expectedVersion 0·-1·1.5 → VALIDATION
- SDS-AC-2: getUser·getRole 등 참조 위치에 '' · 'a b' · 65 자 id → *_NOT_FOUND
```

(SDS-AC-2 는 T1 과제의 예시를 함께 보이려고 넣었다. 실제 문서에서는 한 과제의 SDS-AC 만 둔다.)

의미 규칙의 핵심:
- 스팬 하나가 선언 하나다. 심볼 이름은 텍스트만으로 뽑는다(키워드 뒤 식별자, 없으면 첫 `(`·`<`·`:`·`=` 앞의 마지막 식별자).
- **`← 호출자` 는 "이 연결이 빠지면 안 된다"는 작성자의 선언이다.** 적으면 연결 검사가 error, 적지 않으면 warning 이다. 어느 미연결이 치명적인지는 기계가 판단하지 못하기 때문에 작성자가 표시한다.
- 파일 줄의 `@req` 는 그 파일의 심볼이 물려받는다.
- 의존 줄은 층의 사슬이고, 허용 간선은 선언 간선의 추이 폐포다.
- 분량은 권장 60~80 줄, 상한 100 줄을 제안한다(full SDS 상한은 200 줄). 실험 문서 60 줄에 SDS-AC 와 Test Plan 이 10 줄 안팎씩 붙는 크기다(추정).

변환하면서 원본 SDS 의 모호함이 드러났다. `{store, validate → recurrence}` 처럼 중괄호 안에 화살표가 중첩된 줄은 두 줄로 풀어야 했다. 바닥층 `{types, errors, util}` 만으로는 실제 코드의 `errors → types` import 를 설명하지 못해 한 줄이 더 필요했다. 문서가 모호했던 곳을 검사기가 짚어 내는 사례다.

- 공통 기반은 식별자 색인이다. 소스를 한 번 토큰화해 `식별자 → [파일:줄, 문맥]` 을 만들면 가·다·바를 조회로 처리한다.

### 3.4 구조로 잡히지 않는 실패

실패 (b)(AUTHZ-003 AC-4)는 규칙을 지킨 코드와 어긴 코드의 파일·심볼·시그니처·호출·import 가 모두 같다. 분기 안에서 던지는 오류 코드만 다르다. 이것은 동작 속성이라 실행으로만 판정된다. 막는 수단은 두 가지다. SDS-AC 줄(예시의 SDS-AC-2)로 규칙을 구현자의 문맥에 넣고, 그 규칙을 테스트한다. 기계는 기존 W052 와 검사 사·아·자로 "SDS-AC 가 실재하는 AC 를 가리키고, Test Plan 행과 그것을 인용한 테스트가 있다"까지 보장한다. 테스트가 옳은지는 보장하지 못한다.

### 3.5 기존 SDS 규칙과 맞추기: 경량 프로필

사용자가 뜻한 것이 SDS 였으므로, 초경량 SDS 는 새 문서 종류가 아니라 기존 SDS 규칙(`docs/rule/SDS-MD-Rules-v2.5.0.md`)의 **경량 프로필**로 둔다. 처음 판은 이것을 별개 문서로 보고 네 선택지(대체 / 경량 프로필 / 별개 문서 / 공용 문법 블록)를 비교했다. 용어 정정으로 "경량 프로필"이 곧 사용자의 뜻이 되었다.

| 항목 | full SDS (현행) | lite 프로필 (제안) |
|---|---|---|
| 메타 | Document Type=sds, Task, Target, Status, Date | 같음 + `Profile=lite`, `Lang`, `Root` |
| 필수 절 | 7 개 | 3 개: Interfaces, Acceptance Contracts, Test Plan. 나머지 넷(Context & Scope, Goals / Non-goals, Architecture Decisions, Open Questions)은 선택 |
| Interfaces | 자유 형식, 파싱하지 않음 | §3.2 문법(Depends·Files), 검사 가~라·바 |
| SRS 해석 결정 | Architecture Decisions 산문 | `SDS-AC-n (REQ AC): WHEN … SHALL … → 심볼` 줄 |
| 분량 상한 | 200 줄 | 100 줄(제안) |
| 검사 | W050~W053, E054 | 같음 + 가~자 |

얻는 것:
- **문서 종류가 늘지 않는다.** 설계 문서는 SDS 하나이고, 한 개념에 진입점 하나다.
- **기존 도구를 그대로 쓴다.** `scaffold_step`, `validate_step`, `list_steps`, `set_sds_status`, `synthesize_step_srs`.
- **해석 결정의 테스트가 기존 장치로 강제된다.** SDS-AC 로 쓰면 SDS-W052 가 SDS-AC 마다 Test Plan 행을 요구한다. 연구 32 의 실패 (b) 에 대한 방어가 새 코드 없이 생긴다.
- full SDS 도 Interfaces 절을 이 문법으로 쓰면 같은 기계 검사를 받게 할 수 있다(선택 조항).

풀어야 할 것:
1. **범위.** 지금 SDS 는 tdd step 하나에 하나이고(`SDS-MD-Rules:17-19`), SDS 검사는 tdd 모드에서만 돈다(`src/core/validator/validate-scoped.ts:207-216`). 계획을 대신하려면 sdd 모드에서 target 이나 wave 범위로도 SDS 를 쓸 수 있어야 한다. 후보는 두 가지다. (i) 큰 작업을 step 여럿으로 나누고 step 마다 lite SDS 를 둔다. (ii) target 범위 SDS 의 경로를 새로 정한다.
2. **규칙 문서 버전.** 설치되는 SDS-MD 규칙 문서의 버전을 올려야 하고, 소비자 프로젝트에 전파된다.
3. **승격 흐름.** 규칙 문서는 승격할 때 SDS-AC 가 요구의 AC 가 된다고 적지만(`SDS-MD-Rules:85`), 기계 변환은 없다. lite 의 SDS-AC 는 이미 있는 SRS AC 를 가리키는 해석 결정이므로, 새 AC 로 옮기지 않고 가리키는 AC 에 연결만 해야 한다(추정. 규칙 문서 개정이 필요하다).

이 선택도 판단이고 측정하지 않았다.

## 4. 의견과 추천

### 4.1 계획 모드를 완전히 없애도 되는가

**없애도 된다. 순서만 지키면 된다.**

없애도 되는 이유:
1. kiwi-planner 식 계획과 그 검증 루프는 품질에 기여하지 않았다. 강한 모델은 계획 없이 100% 였고, 검증 루프를 붙인 조건의 총 토큰은 계획 없음의 6.9 배였다(연구 32). `kiwi-pm`(과 그 자식 `kiwi-coder`)의 실행 경로는 연구 32 가 재지 않았다. 다만 그 입력이 계획이므로 계획을 없애면 이 경로도 입력을 잃는다. 대신 쓸 실행 경로는 `kiwi-tdd` step 과 직접 구현이다.
2. 약한 모델을 돕던 기능은 초경량 SDS 가 대신한다. Haiku 에서 SDS 는 짧은 계획과 같은 수준(96.5% 대 97.9%)이었고 더 쌌다(연구 32 §7).
3. 이 저장소가 이미 두 달 동안 `kiwi-planner`·`kiwi-pm` 없이 개발됐다.
4. 외부도 강한 모델에서 분해 단계를 걷어내는 추세다(§2.3).

바로 지우면 안 되는 이유:
1. **R-ORCH 가 사이드카를 입력으로 쓴다.** 20 개 `src` 파일, 64 개 요구, 약 39 개 테스트 파일이 계획 산출물에 걸려 있다. 외부 추세도 "조정·영속 역할의 작업 목록은 도구화한다"이지 "없앤다"가 아니다.
2. **2026-08-24 사용자 결정(계획 단계 유지)을 명시적으로 뒤집어야 한다.** 그 결정의 근거가 "사이드카가 src 의 입력"이었으므로, 입력을 SDS 로 옮기면 근거가 사라진다.
3. 다른 사용자 프로젝트의 사용 여부를 모른다. 한 번은 deprecated 로 알린 뒤 다음 major 에서 지우는 편이 안전하다.

lane 분할에 대한 별도 판단: 지금 lane 실행은 직렬이라 벽시계 이득이 없다. SDS Interfaces 절의 Files 목록과 `@req` 가 lane 분할에 필요한 "단위별 write set" 을 준다. 그래도 lane 분할이 실제로 무엇을 사는지 먼저 따져 보고, 값이 없으면 옮기지 말고 없애는 선택지도 있다. 이 판단은 이 연구 범위 밖이다.

### 4.2 추천하는 방법

```text
SRS (EARS AC, 검토 1 회)
  → 초경량 SDS (lite 프로필, 60~100 줄: Interfaces · Acceptance Contracts · Test Plan)
  → 설계 검사, 문서 단계: 결정적 검사 (문법·분량·요구 연결·SDS-AC 의 요구/AC 해석·Test Plan 대응)
  → 구현 (TDD. 강한 모델은 직접, 약한 모델은 SDS 를 받아서. tdd 모드면 kiwi-tdd)
  → 설계 검사, 코드 단계: 결정적 검사 (심볼 위치·연결·의존 방향·드리프트)
  → 코드 전용 리뷰 1 명 (연구 31)
  → --close-reqs
```

- **SDS 에 LLM 검증 루프는 돌리지 않는다.** 검증은 설계 검사(결정적)와 실행(테스트)이 맡는다. 이것이 연구 32 의 결론과 맞다.
- **진행 추적과 재개**는 요구 상태·AC 체크·pipeline 저널과 SDS 자체가 맡는다. 외부의 progress 파일·`passes` 플래그와 같은 역할이다. SDS 는 구현이 끝난 뒤에도 코드 구조와 대응하므로, 드리프트 검사를 계속 돌리면 살아 있는 설계 기록이 된다.
- **구조 품질**: 숨긴 기능 테스트로는 재지 못하는 구조 품질(§2.4)을 의존 방향 검사와 연결 검사가 지킨다. "10 년 가는 솔루션"에 SDS 가 필요한 이유가 여기에 있다.

### 4.3 옮기는 순서 (제안)

1. **요구 등록(sdd 모드)**: SDS lite 프로필, Interfaces 문법, 설계 검사(`validate_step` 확장 또는 새 명령)를 새 요구로 등록한다. SDS-MD 규칙 문서 개정과 sdd 모드에서의 SDS 범위(§3.5)도 함께 정한다. 현재 SRS 에는 심볼·시그니처 대조 요구가 없다.
2. **검사기 구현**: 텍스트 모드로 가·다·라·마·사·아·자를 먼저 만든다. TypeScript 어댑터(나의 타입 비교, 정확한 참조 찾기)는 그다음이다.
3. **작은 확인 실험**: "시그니처 + SDS-AC 해석 결정" 결합형과 "검사 결과를 구현자에게 되먹이는 것"의 효과를 연구 32 와 같은 프로토콜로 Haiku 4 회 정도 잰다. 둘 다 아직 측정하지 않았다.
4. **사이클 교체**: `kiwi-pipeline` 기본 사이클의 `kiwi-planner → kiwi-pm` 을 "SDS 작성 → 구현"으로 바꾼다. `get_next_work_order` 의 `create-plan` 을 `create-sds` 로 바꾼다.
5. **R-ORCH 입력 교체 또는 lane 분할 제거**: 사이드카 대신 SDS 를 받게 하거나, lane 분할의 값을 따져 없앤다.
6. **퇴역**: `kiwi-planner`·`kiwi-pm`·`kiwi-coder`, `workflow_plan_*` 도구, `validator.mjs`, R-PLAN 경로를 deprecated 로 표시한다. 다음 major 에서 지우고, 관련 요구 64 개는 supersede 하거나 discard 한다.

### 4.4 이 결론이 틀릴 수 있는 곳

- 연구 32 는 한 세션 규모 과제만 쟀다. 여러 세션·여러 lane 에 걸친 대형 작업에서 계획의 외부 기억 역할은 재지 않았다.
- 시멘틱 검사의 실측은 실행 1 개(H-T2-D1)에 대한 것이다. 오탐 0 은 표본 하나에서 나온 값이다.
- "시그니처 + SDS-AC 해석 결정" 결합형은 측정하지 않았다.
- 결정적 검사는 의미 수준의 설계 위반을 다 잡지 못한다(arXiv 2608.21747, r = 0.21).
