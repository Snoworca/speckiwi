## 0. 결론 요약

1. **새 스킬 `kiwi-prd`** 를 만든다. 순서는 다음과 같다. 사용자 원문을 가장 먼저 그대로 파일에 쓴다. 한 번에 하나씩 묻는다. 결과를 짧은 PRD 로 정리해 승인을 받는다. 질문 루프는 새로 짓지 않고 **kiwi-srs Phase 1.5 QnA 를 이 스킬로 옮긴다**(복사가 아니라 이동).
2. **kiwi-srs 는 PRD 가 없으면 먼저 kiwi-prd 를 부르고**, 그 PRD 를 이미 있는 `REQ_PATH` 입력으로 받는다(`skills/claude/kiwi-srs/SKILL.md:128`).
3. **PRD 는 입력 기록이고, 요구 원본은 SRS 다.** PRD 항목에는 `PRD-<n>` ID 를 붙이지만, 이것은 Requirement ID 가 아니다. 파서도 SRS 파서와 따로 둔다. SRS 의 요구 heading 정규식은 type prefix 를 닫힌 목록으로 받기 때문이다(`src/core/parser/block-scanner.ts:36-37`).
4. **검증 판정은 셋이다.** (a) 원문 요구를 빠뜨렸거나 받아들이지 않음 = **fail**, (b) 원문 근거 없는 확장 = **drop**(필요하다고 주장하면 **residual**), (c) 원문의 구멍·모순·결함 메우기 = **허용**하되 `fills:` 근거를 단다.
5. **구조화와 도구는 나눠서 넣는다.** 5.1.0 에는 **형식만 고정**한다. 정규식 하나로 읽히는 ID 블록과 인용 블록이다. 검사는 인라인 명령으로 하고, 항목별 판정은 run 분석 파일에 기록한다. 5.2.0 에서는 **도구를 붙인다**. `prd check`, 항목 목록·검색, 판정 원장에서 파생하는 커서(count · current · next · seek), SRS→PRD 참조 해석과 커버리지 보고다. 판정 (a) 의 기계적 핵심인 "어느 PRD 항목을 아무 요구도 인용하지 않는가"는 ID 형식만 고정하면 5.1.0 에서도 문자열 집합 비교로 판정할 수 있다. 도구가 더하는 것은 진단·검색·순회의 편의와, 더 약한 모델에 대한 안전성이다.
6. **컴팩션 대책.** PRD 는 디스크에 있고, 각 라운드의 서브에이전트가 직접 읽는다. 항목별 판정 원장도 디스크에 남아 "몇 번째 항목까지 대조했는가"가 컴팩션 뒤에도 남는다. Superpowers 는 Claude Code 가 컴팩션 뒤 스킬을 2만 자에서 자른다고 보고한다. kiwi-srs 는 44,561자이고 2만 자 지점이 335행이다 **[잘림의 영향은 추정]**. 그래서 새 규칙은 kiwi-srs 앞 2만 자 안에 두고, kiwi-prd 는 2만 자 미만으로 유지한다.
7. 요구 초안: **5.1.0 에 2개**(FR-FLOW-204, FR-FLOW-205), **5.2.0 에 3개**(PRD 검사·읽기·검색 / 커서와 판정 원장 / SRS→PRD 참조 해석과 커버리지). 기존 FR-FLOW-024 의 AC-1~3 은 대체가 필요하다.

## 3. 스킬 이름과 위치

**이름 `kiwi-prd`.** `kiwi-intent` 는 step `intent.md`·kiwi-srs `intent.json`·오케스트레이터 intent 조사자와 겹친다. `kiwi-req` 는 REQ-ID 와 헷갈린다. `kiwi-brainstorm` 은 발산으로 읽힌다.

**위치: 단독 스킬로 두고, kiwi-srs Phase 1.5 를 이 스킬로 옮긴다.** 근거는 셋이다. 첫째, 작은 스킬은 컴팩션 뒤에도 통째로 남는다. 둘째, 질문 루프가 한 곳에만 있게 된다(kiwi-hot-fix → kiwi-bug-repro 선례). 셋째, 사용자가 "요구만 정리"를 직접 부를 수 있다.

```
/kiwi-prd "요청"             → PRD 작성·승인 → "다음: /kiwi-srs REQ_PATH=<prd>"
/kiwi-srs "요청"(PRD 없음)    → Phase 0 → kiwi-prd → REQ_PATH=<prd> 로 Phase 1 부터
/kiwi-srs REQ_PATH=<prd>      → 승인 표시·해시값 확인 → Phase 1 부터
```

kiwi-prd 는 `REQ_PATH` 가 없을 때만 부른다. 오케스트레이터·wave-master 는 excerpt 를 `REQ_PATH` 로 넘기므로 wave 마다 대화가 열리지 않는다.

## 4. PRD 형식 (5.1.0 에 고정할 최소 구조)

### 4.1 위치와 문법 선택

- **위치:** `docs/prd/{YYYY-MM-DD}.{slug}.prd.md`, 커밋 대상. `docs/spec` 밖이므로 workspace 탐색(`discover.ts:54`)이 읽지 않고, 요구로 파싱되지 않는다.
- **SRS 파서는 재사용하지 않는다.** 요구 heading 정규식에 `PRD` prefix 를 더하면 PRD 항목이 요구로 파싱된다. 그러면 두 번째 요구 원본이 생기고, Requirement ID 할당·상태 규칙이 따라붙는다. 따라서 **SRS-MD 와 생김새는 같고 정규식은 다른 별도 문법**을 쓴다. lite SDS 와 같은 선택이다(`lite-sds.ts` 가 자기 문법과 진단 코드를 갖는다).
- **재사용하는 것:** 표 파서 `parseMarkdownTableResult`(진단 코드를 인자로 넘길 수 있다, `table.ts:51`), 펜스 처리 방식(`block-scanner.ts:40-70`), `<path>@sha256:` 포인터 규약(run-ledger :82), `exclusion_class` 어휘.

### 4.2 문법

```markdown

> 입력 기록이다. 요구 원본이 아니다 — 무엇을 만들지는 docs/spec 의 SRS 가 정한다.
```

**규칙**

| 요소 | 규칙 | 기계 검사 (5.1.0 은 인라인, 5.2.0 은 `prd check`) |
|---|---|---|
| `U-<n>` 원문 블록 | `## 1. User Request` 안에만 둔다. 인용 블록은 바이트 그대로, 덧붙이기만 한다 | §1 바이트 sha256 = `Request SHA256` |
| `PRD-<n>` 항목 | `## 2. Items` 안에 둔다. 파일 안에서 1부터 빠짐없이 순서대로. heading 정규식은 `^### PRD-(\d+) — (.+)$` | ID 중복·결번 없음 |
| `Kind` | `intent` / `user` / `goal` / `in-scope` / `exclusion` / `proposal` 의 닫힌 목록 | 목록 밖 값 거부 |
| `Exclusion Class` | Kind=exclusion 일 때만. wave-decomposition 의 다섯 값 | 다른 Kind 에 있으면 거부 |
| `Source` | proposal 이 아니면 `U-<n>` 하나 이상 | 가리키는 U 블록이 있음 |
| 인용 | proposal 이 아니면 인용 블록 하나 이상. 그 문자열이 Source 의 U 블록에 그대로 있어야 한다 | 부분 문자열 일치 |
| `State` | `confirmed` / `proposed` / `rejected` | — |
| proposal | 인용 대신 `Reason` 행. 사용자가 승인하면 `State=confirmed`, 이때도 `Kind=proposal` 은 유지한다 (누가 말했는지가 남는다) | — |
| 금지 | Requirement ID, AC 줄, `SHALL`, `Status`(요구 의미의) | 정규식으로 거부 |

**문서 순서가 곧 순회 순서다.** `PRD-1..N` 이 빠짐없이 이어지므로 "전체 개수 N, 현재 인덱스 i, 다음 = i+1" 이 파서 없이도 성립한다. 에이전트는 `grep -c '^### PRD-'` 로 개수를, `grep -n '^### PRD-'` 로 위치를 얻는다.

### 4.3 PRD 와 SRS 의 역할 분담

| 내용 | PRD (입력 기록) | SRS (요구 원본) |
|---|---|---|
| 사용자가 한 말 | `U-n` 원문 | 넣지 않는다. Trace `Doc`·`informed_by` 로 PRD 를 가리킨다 |
| 왜 필요한가 | `Kind=intent` 항목 | `#### Rationale`: 이 요구가 어느 PRD 항목에서 왔고, 각 AC 의 근거가 무엇인지(`AC-3 ← PRD-4`, `AC-4 fills PRD-4/구멍`) |
| 누가·무엇을 이루나 | `user`·`goal` | (선택) target goal 한 줄 |
| 무엇을 만드나 | `in-scope` (풀이 수준) | Requirement statement 와 EARS AC — **결정은 여기서** |
| 무엇을 만들지 않나 | `exclusion` + `Exclusion Class` | 요구의 **부정 AC**(SHALL NOT). scope 전체에 해당하면 §2 Out of Scope |
| 에이전트가 채운 것 | `proposal` + `Reason` + `State` | 승인된 것만 AC 로 |
| 상태·증거 | 없음 | Status, Verification Evidence |

**충돌 규칙.** 무엇을 만들지는 SRS 가 이긴다. 그러나 둘이 어긋나는 것 자체가 검증 finding 이다. PRD 는 SRS 를 대조하는 기준이지, 두 번째 원본이 아니다. 역방향 링크(PRD → REQ-ID)는 두지 않는다. 따로 어긋나기 때문이다.

## 5. 질문 방식

1. **원문을 먼저 쓴다.** 질문·조사보다 앞서 `U-1` 을 쓴다.
2. **묻기 전에 본다.** kiwi-srs 안에서 불렸으면 Phase 1 산출물을 읽고, 단독이면 사용자가 가리킨 파일과 `search_requirements` 만 본다.
3. **첫 메시지 하나.** 되짚기 + in-scope / exclusion 초안 + proposal 목록, 그리고 **질문 하나**. 사용자가 부르지 않았으면 "이대로 진행하라고 하셔도 됩니다" 한 줄을 붙인다(brainstorming :77-82).
4. **질문은 경계에만 쓴다.** 답에 따라 in-scope·exclusion 항목이 바뀌는 것만 묻는다. 세부 기본값은 proposal 로 보여 주고, 사용자가 목록을 한 번에 고치게 한다(:268 "A default they never heard is one they couldn't reject").
5. **열린 질문이 먼저다**(:98-101).
6. **멈추는 기준.** 경계를 바꾸는 미해결 질문이 0개이거나 사용자가 "진행"이라고 하면 멈춘다. 진동 가드는 kiwi-srs :358 의 것을 옮긴다.
7. **승인 전 SRS mutation 금지**(HARD-GATE 대응).
8. **`--auto`.** 질문 없이 원문에서 뽑고 `Status=unapproved` 로 둔다. 결정 위원회(FR-FLOW-025)는 proposal 은 정할 수 있지만 in-scope 를 늘리거나 exclusion 을 지우지는 못한다.

빌더 확인은 넣지 않는다. kiwi-srs Phase 1 intent analyst 의 `ambiguities`(:274-287)와 Phase 3 이 같은 책임을 진다.
**[추정]** 짧은 요청이면 질문은 0~2개다.

## 6. 검증 판정 (a)(b)(c)

### 6.1 판정 표

| 판정 | 조건 | 처리 | 기계로 판정되는 부분 |
|---|---|---|---|
| **(a) fail — 원문 미수용** | `intent`·`goal`·`in-scope` 항목을 근거로 인용하는 요구·AC 가 없다. 또는 SRS 가 그 항목과 반대로 말한다 | 루프 통과 불가. 저작자가 메운다 | "인용 없음"은 집합 차이(PRD 항목 ID − SRS Rationale 에 나온 ID)로 판정. "반대로 말함"은 검증자 판단 |
| **(b) 확장 — drop / residual** | 추가 항목이 아무 PRD 항목도 인용하지 않고 `fills:` 도 없다. 또는 `exclusion` 항목에 해당한다 | 기본 drop(사유 보고). "이것 없이는 PRD-n 이 성립하지 않는다"고 주장하면서 구멍을 대지 못하면 residual | "인용 없음"은 문자열 판정. "제외에 해당"은 검증자 판단 |
| **(c) 구멍·모순·결함 메우기 — 허용** | `fills: PRD-n / 구멍\|모순\|결함 / 이것 없이는 PRD-n 이 성립하지 않거나 검증할 수 없거나 모순인 이유 한 문장` 을 단다. 그 항목의 경계 안에서 가장 작은 메우기다 | 반영. 근거는 Rationale 에 | `fills:` 형식과 PRD-n 존재는 문자열 판정. "경계 안인가"는 검증자 판단 |

**판정 순서:** ① 해시값·인용 ID·인용 문자열 검사(불일치면 `prd-record-tampered` 로 정지, `--auto` 에서도 정지) → ② exclusion 에 닿으면 (b) → ③ 포함 항목을 인용하면 반영, (c) 면 `fills:` 필수 → ④ 인용이 없으면 (b).

- **모순 해소는 오버엔지니어링이 아니다.** 루프가 직접 푼다. 의도(intent)에 맞고 범위가 가장 작은 쪽을 고르고, kiwi-prd 가 PRD 에 `proposal`(Reason="모순 해소: PRD-a vs PRD-b")로 덧붙여 알린다. 진행은 막지 않는다. 다만 in-scope 를 없애거나 exclusion 을 뒤집는 해소는 residual 로 보낸다.
- **생성된 리서치는 근거가 아니다.** FR-FLOW-024 AC-4 산출물은 (c) 의 방법을 고르는 참고로만 쓴다. 사용자가 넘긴 문서는 PRD `U-n` 에 경로와 sha256 을 적은 뒤에만 인용할 수 있다.
- **종료:** (a)=0, 반영된 (b)=0(drop 또는 residual 보고만), 모든 (c) 에 `fills:` 가 있을 때 통과한다. residual 이 남으면 `NEEDS_USER`(FR-FLOW-203 AC-11 과 같은 모양). 사용자가 답하면 kiwi-prd 가 `U-n` 을 덧붙이고 항목을 고치고 해시값을 다시 쓴다. **범위는 사용자의 말로만 늘어난다.**
- 5.1.0 의 kiwi-srs pass/fail 전환 작업(srs-passfail-research, ac-gapfill-research)과 문장을 맞춰야 한다. 그 결과는 보지 못했다.

### 6.2 항목 단위 순회 (두 방향)

**정방향 PRD → SRS.** `PRD-1` 부터 `PRD-N` 까지 하나씩 받는다. 각 항목에 대해 그것을 인용한 요구·AC 를 찾는다. 찾는 방법은 Rationale 의 근거 표, 그리고 Trace `Doc` notes 의 `prd=PRD-n` 이다. 그 뒤 판정을 한 줄 기록한다. `in-scope`·`intent`·`goal` 에서 판정은 `accepted`(근거 REQ/AC 를 적는다) 또는 `(a) missing` / `(a) contradicted` 다. `exclusion` 에서는 `respected` 또는 `(b) violated`(어긴 REQ/AC) 다. `proposal` 에서는 `State` 와 SRS 반영 여부가 맞는지를 본다.

**역방향 SRS → PRD.** 같은 순회를 target 의 요구로 돈다. 요구와 AC 를 하나씩 받아 근거(PRD-n 인용 또는 `fills:`)를 확인한다. 근거가 없으면 (b) 다. 역방향은 **새 커서가 필요 없다.** `list_requirements` 가 이미 `offset`/`limit`/`total`/`nextOffset` 페이지를 준다(`discovery.ts:87-102`). `limit=1` 로 count·현재·다음이 된다. 필요한 것은 판정을 남길 원장뿐이다.

**두 방향 모두 필요한 이유.** 정방향은 (a)를, 역방향은 (b)를 잡는다. (c) 는 역방향에서 `fills:` 를 확인할 때 잡힌다.

## 7. 커서와 판정 원장

### 7.1 연산 (5.2.0 도구)

사용자 설명("전체 카운트 → 현재 인덱스와 항목 → 인덱스 +1 → 다음 항목")을 그대로 연산으로 옮긴다.

| 연산 | 입력 | 반환 |
|---|---|---|
| `count` | prd 경로 | `{ total, prd: "<path>@sha256:<hex>" }` |
| `current` | prd 경로, run_id, direction(`prd-to-srs`·`srs-to-prd`) | `{ index, total, item: { id, kind, title, quote, source }, prd }` |
| `next` | 위 + 현재 항목의 판정(`verdict`, `refs`, `note`) | 판정을 원장에 기록하고, 인덱스 +1 한 항목을 같은 모양으로 반환. 끝이면 `{ index: total, done: true, summary }` |
| `seek` | 위 + index | 그 항목을 반환. 판정은 바꾸지 않는다 |
| `reset` | prd, run_id, direction | 같은 run 에 새 라운드를 연다 (`round +1`, 인덱스 1) |

**`next` 는 현재 항목의 판정 없이는 넘어가지 않는다.** 판정 없이 넘기면 그 항목이 조용히 빠진다. 이는 (a) 를 놓치는 바로 그 경로다. 틀린 사용은 즉시 실패해야 한다(전역 §10.1). 건너뛰려면 `verdict: "deferred"` 와 사유를 명시하고, 종료 보고에 남긴다.

**반환값에는 늘 `index`·`total`·항목 ID·원문 인용이 함께 담긴다.** 에이전트는 매 호출마다 진행 위치와 사용자 원문을 다시 본다. 컴팩션 뒤에도 다음 호출 한 번이면 위치와 원문이 돌아온다.

### 7.2 영속 위치와 규칙

- **원장:** `kiwi/prd/{run_id}.jsonl`. 한 줄이 판정 하나다: `{ prd: "<path>@sha256:<hex>", direction, round, index, item, verdict, refs[], note, ts }`. `kiwi/waves.jsonl` 처럼 기계 상태이므로 gitignore 한다. 디스크에 있으므로 컴팩션에는 살아남는다. 사람이 볼 결과는 kiwi-srs 완료 보고와 `eval_iter{N}.json` 으로 나간다.
- **커서는 따로 저장하지 않고 원장에서 파생한다.** 현재 인덱스 = (같은 prd 해시값·direction·round 에서 판정이 기록된 마지막 index) + 1 이다. 재개 카드가 저널의 파생물이라는 run-ledger 원칙(:84)과 같다. 변경 가능한 인덱스 파일이 따로 없으므로, 인덱스와 판정이 어긋날 수 없다.
- **run 분리:** 파일이 `run_id` 마다 따로다. 동시에 도는 두 검증 run 은 서로의 커서를 보지 않는다. 한 run 안에서는 쓰는 주체가 하나(메인 세션)이고, 덧붙이기만 한다. 따라서 락이 필요 없다(전역 §11).
- **무효화:** `count`·`current`·`next` 는 매번 PRD 의 현재 해시값을 계산한다. 원장 줄의 해시값과 다르면 그 줄들은 **무효**가 된다. 커서는 1로 돌아가고, 반환값에 `invalidated: { previous, current, judged: n }` 를 싣는다. PRD 가 바뀐 이유가 정당한 덧붙임(kiwi-prd 가 쓴 residual 답)이면 새 해시값으로 다시 돌면 된다. 아니면 `prd-record-tampered` 다. 둘은 PRD `Request SHA256` 행이 갱신됐는지로 가른다. kiwi-prd 만 이 행을 갱신한다.

### 7.3 5.1.0 에서의 대체 (도구 없이)

- 개수와 위치는 `grep -c '^### PRD-'` 와 `grep -n '^### PRD-'` 로 얻는다. 문서 순서가 고정이라 인덱스 = 번호다.
- 판정은 kiwi-srs 가 이미 쓰는 `docs/analysis/kiwi-srs-{run-id}/eval_iter{N}.json` 에 `prd_items[]`(정방향)와 `srs_items[]`(역방향) 배열로 기록한다. 배열 순서 = 항목 순서다. 재개할 때는 마지막 기록 다음 항목부터 돈다.
- 해시값은 인라인 `node -e` 한 줄로 계산하고, 인용은 부분 문자열로 비교한다.
- 한계: 판정을 적지 않고 넘어가는 실수를 막는 장치가 없다. 그래서 검증자 프롬프트에 "배열 길이 = PRD 항목 수" 를 확인시키고, 메인이 `jq length` 로 확인한다(기계 검사).

### 7.4 순회가 실제로 돕는 정도

- 검증자는 라운드마다 새로 띄우는 서브에이전트다. 짧은 PRD(10~30 항목) 하나를 대조하는 동안 그 서브에이전트가 컴팩션되는 일은 드물다 **[추정]**. 따라서 5.1.0 에서 커서의 컴팩션 효과는 주로 **메인 세션 쪽**에 있다. 메인 세션은 라운드를 넘나들며 판정 결과를 추적해야 하는데, 이것은 파일 원장(§7.3)으로 충분히 막힌다.
- 커서 도구가 크게 돕는 경우는 셋이다. PRD 가 길 때, 더 약한 모델이 검증할 때(연구 32: 약한 모델은 짧고 구조화된 입력에서 더 나았다 — 저장소 메모), 그리고 "판정 없이 넘어가기"를 구조적으로 막아야 할 때다.

**권고: 단계적으로 간다.**

- **5.1.0 (스킬):** §4.2 형식을 **고정**한다. 정규식 하나로 읽히는 블록이므로 파서가 없어도 에이전트가 읽고 grep 할 수 있다. 판정은 인라인 검사 + `eval_iter{N}.json` 배열로 기록한다. 그러면 (a) 의 핵심(인용 없는 항목)과 (b)·(c) 의 형식 검사가 이미 기계로 판정된다.

## 9. RBAC 사례

### 9.1 원문 (재구성)

원래 원문은 남지 않았다(바로 그것이 문제 1이다). 이번 대화의 내용을 재구성했다.

> nodejs 의 express 를 자바 버전으로 만드는데, 여기에 사용자 편의 기능을 RBAC 을 붙이고 내가 인터페이스와 파일 스토어만 만들어서 사용자가 상속 받아서 DB로 붙일 수 있게 하라.

### 9.2 PRD 항목 (발췌, §4.2 형식을 표로 줄임)

| ID | Kind | 인용 (U-1) | 풀이 |
|---|---|---|---|
| PRD-1 | intent | 「사용자가 상속 받아서 DB로 붙일 수 있게」 | 권한 관리를 바로 쓰되 저장소는 사용자가 자기 DB 에 붙인다 |
| PRD-2 | in-scope | 「nodejs 의 express 를 자바 버전으로 만드는데」 | 이 요청의 바탕인 자바 웹 프레임워크 |
| PRD-3 | in-scope | 「사용자 편의 기능을 RBAC 을 붙이고」 | 역할 기반 접근 제어 |
| PRD-4 | in-scope | 「인터페이스와 파일 스토어만 만들어서」 | 저장소 인터페이스 하나 + 파일 구현 하나 |
| PRD-5 | in-scope | 「사용자가 상속 받아서 DB로 붙일 수 있게」 | 사용자 구현으로 파일 스토어를 바꿔 끼울 수 있다 |
| PRD-6 | exclusion (`user-excluded`) | 「인터페이스와 파일 스토어만」 | DB 별 구현(PostgreSQL·MySQL·Oracle), 테이블·스키마 생성, 초기값 적재는 만들지 않는다 |
| PRD-7 | exclusion (`external-ownership`) | 「사용자가 상속 받아서 DB로 붙일 수 있게」 | DB 연동은 프레임워크 사용자가 맡는다 |
| PRD-8 | proposal (Reason: 의존성 없음, 사람이 고치기 쉬움) | — | 파일 형식은 JSON |

첫 메시지의 질문(하나):

> 파일 스토어는 실행 중에 역할·권한을 바꿔 파일에 저장하는 것까지 해야 하나요, 아니면 시작할 때 읽기만 하면 되나요? 저장까지라면 동시에 고칠 때의 처리가 들어가서 만들 것이 달라집니다.

사용자가 "저장까지"라고 답했다고 하자. 이 답은 `U-2` 로 덧붙고, PRD-4 의 풀이는 "읽기·쓰기 파일 구현"이 된다.

### 9.3 판정 예

| 판정 | 예 | 이유 |
|---|---|---|
| **(a) fail** | SRS 에 파일 스토어 요구만 있다. 저장소 인터페이스는 공개되지 않았고, 사용자 구현을 등록하는 AC 도 없다 | 정방향 순회에서 PRD-5 를 인용하는 AC 가 0이다. 고칠 것: "WHEN 사용자가 저장소 인터페이스를 구현한 클래스를 등록하면 THE SYSTEM SHALL 파일 스토어 대신 그 구현으로 역할과 권한을 읽고 쓴다" |
| **(b) drop** | "운영에는 DB 가 필요하다. PostgreSQL·MySQL·Oracle 저장소와 RBAC 테이블 생성을 추가하라" | 역방향 순회에서 근거가 없고, PRD-6·PRD-7 exclusion 에 닿는다. 사유와 함께 drop. 사고 때 실제로 만들어진 것이다 |
| **(b) residual** | "역할 계층(상속)이 없으면 RBAC 이 실용적이지 않다" | 어느 항목도 계층을 말하지 않고, PRD-3 이 계층 없이 성립하지 않는다는 구멍도 대지 못한다. 사용자 결정 |
| **(c) 구멍** | "파일에 동시에 써도 깨지지 않게, 임시 파일에 쓴 뒤 이름을 바꿔 원자적으로 저장한다" — `fills: PRD-4 / 구멍 / U-2 에서 실행 중 저장을 요구했는데, 동시 쓰기에서 파일이 깨지면 PRD-4 가 성립하지 않는다` | 사용자가 원한 기능을 제대로 만들기 위한 메우기다. 반면 "여러 서버 프로세스용 분산 락"은 원문에 다중 프로세스가 없으므로 (b) 다 |
| **(c) 결함** | 인터페이스가 파일 경로(`Path`)를 인자로 받는다 → 저장 매체를 드러내지 않는다는 AC 를 추가한다. `fills: PRD-5 / 결함 / 매체를 드러내는 시그니처로는 DB 구현이 그 인터페이스를 구현할 수 없다` | 원문 요구의 결함을 고치는 것이지 확장이 아니다 |

**SRS 쪽 표현.** RBAC 저장소 요구에 부정 AC 를 둔다. "THE SYSTEM SHALL NOT ship a database-specific store implementation or schema-creation code." Rationale 에 `PRD-6, PRD-7 ← docs/prd/2026-11-03.java-express-rbac.prd.md` 를 적는다. 그러면 기존 §0.G4 경계 게이트와 검증자가 SRS 안에서도 제외를 본다.

## 12. 요구 초안

모두 `Type=functional`, `Stability=draft` 로 시작하고, 구현 전에 사용자 승인을 받는다. 5.1.0 은 Target Map 에 먼저 등록한다. ID 는 도구가 배정한다(아래 번호는 가정).

### 12.1 5.1.0 (스킬)

#### FR-FLOW-204 — kiwi-prd 가 사용자 원문을 그대로 남기고, 승인받은 구조화 PRD 를 SRS 저작의 입력으로 만든다

Requirement: kiwi-prd SHALL write the user's request verbatim to a PRD before any investigation or question, collect the missing intent and scope one question at a time, and obtain the user's approval of the PRD. The PRD is an input record with a fixed block grammar, not a requirements source.

- AC-1: WHEN kiwi-prd receives a request, THE SYSTEM SHALL write it unchanged as block `U-1` under `## 1. User Request` before any investigation subagent, question, or SRS mutation, and SHALL append each later user answer as the next `U-<n>` without rewriting earlier blocks.
- AC-2: THE PRD SHALL list its items under `## 2. Items` as `### PRD-<n> — <title>` blocks, numbered from 1 without gaps. Each item SHALL carry a metadata table with `Kind` from {intent, user, goal, in-scope, exclusion, proposal}, `Source`, and `State`, and an exclusion SHALL carry an `Exclusion Class` from the wave-decomposition list.
- AC-3: EVERY item other than a proposal SHALL quote a passage that appears verbatim in the `U-<n>` block its `Source` names. Anything the agent supplied SHALL be a proposal with a `Reason`, and SHALL keep `Kind=proposal` after the user confirms it.
- AC-4: THE skill SHALL ask at most one question per message, only about a point whose answer changes an in-scope or exclusion item, and SHALL show detail defaults as proposals instead of asking about them.
- AC-5: WHILE the PRD is not approved, THE SYSTEM SHALL NOT call any SRS mutation tool. WHEN `--auto` is set, THE SYSTEM SHALL record `Status=unapproved`, and the decision committee SHALL NOT add in-scope items or remove exclusion items.
- AC-6: WHEN the PRD is approved or a user block is appended, kiwi-prd SHALL write the sha256 of the `## 1. User Request` section bytes to the `Request SHA256` row, and no other skill SHALL write that row.
- AC-7: THE PRD SHALL carry no Requirement ID, acceptance criterion line, or SHALL statement, and SHALL state at its top that it is an input record and that `docs/spec` is the requirements source.
- AC-8: THE kiwi-prd SKILL.md SHALL stay under 20,000 characters in every shipped rendering, and `kiwi-prd` SHALL be listed in the bundled skill list.

#### FR-FLOW-205 — kiwi-srs 가 PRD 항목을 하나씩 대조해, 원문 미수용은 실패, 근거 없는 확장은 drop·residual, 구멍 메우기는 근거와 함께 허용한다

Requirement: kiwi-srs SHALL author from an approved PRD and SHALL judge, item by item and in both directions, whether the SRS accepts every PRD item and whether every requirement and criterion it writes is grounded in one.

- AC-1: WHEN kiwi-srs is invoked without `REQ_PATH`, THE SYSTEM SHALL invoke kiwi-prd first and use its PRD as `REQ_PATH`. The former Phase 1.5 question loop SHALL NOT remain in kiwi-srs.
- AC-2: THE SYSTEM SHALL pass the PRD path, not a paraphrase, to every authoring, verification, and improvement subagent, and SHALL recompute the PRD hash at the start of each round and on resume. WHEN the hash differs from `Request SHA256`, THE SYSTEM SHALL stop at critical gate `prd-record-tampered`, also under `--auto`.
- AC-3: EACH verification round SHALL record one verdict per PRD item, in item order, in `prd_items[]` of `eval_iter{N}.json`, and one verdict per requirement and criterion in `srs_items[]`. A round whose `prd_items[]` length differs from the PRD item count SHALL NOT pass.
- AC-4: WHEN an intent, goal, or in-scope item is cited by no requirement or criterion, or is contradicted by one, THE verdict SHALL be fail and the loop SHALL NOT pass.
- AC-5: WHEN a requirement or criterion cites no PRD item and carries no `fills:` basis, or falls under an exclusion item, THE SYSTEM SHALL drop it and report the reason. WHEN the verifier asserts it is necessary without naming the hole, THE SYSTEM SHALL carry it as residual.
- AC-6: WHEN an addition fills a hole, contradiction, or defect, THE SYSTEM SHALL accept it only with `fills: PRD-<n> / <kind> / <reason>` in the requirement's Rationale. A resolution that removes an in-scope item or reverses an exclusion SHALL go to residual. A research document kiwi-srs generated SHALL NOT serve as basis.
- AC-7: WHEN a residual remains at the end, kiwi-srs SHALL end `NEEDS_USER`. The rules of AC-2 to AC-6 SHALL appear within the first 20,000 characters of every shipped kiwi-srs rendering.

### 12.2 5.2.0 (도구)

#### (가) PRD 검사·읽기·검색

Requirement: speckiwi SHALL parse PRD files under `docs/prd/` with a grammar of its own — not the requirement grammar — and SHALL offer a check, an item list, an item read, and a search over them.

- AC-1: `speckiwi prd check` (MCP `check_prd`) SHALL report, each with its own diagnostic code: a gap or duplicate in `PRD-<n>` numbering, a `Kind` or `Exclusion Class` outside its list, a `Source` naming no `U-<n>` block, a quote absent from its source block, a `Request SHA256` mismatch, and a Requirement ID or SHALL statement inside the PRD.
- AC-2: THE PRD parser SHALL NOT make any PRD item visible to the requirement queries or mutations, and SHALL reuse the shared markdown table parser rather than a second implementation.
- AC-3: THE item list SHALL return items in document order with the same page fields as the requirement list (`total`, `offset`, `returned`, `nextOffset`), and the item read SHALL return one item with its kind, quote, source, and the PRD pointer `<path>@sha256:<hex>`.
- AC-4: THE PRD search SHALL use the same ranked index as requirement search, so that a mixed Korean–English query ranks PRD items the same way it ranks requirements.

#### (나) 커서와 판정 원장

Requirement: speckiwi SHALL offer a cursor over the items of a PRD, and over the requirements and criteria of a target, whose position is derived from an append-only verdict ledger on disk, so that a verification run can resume after compaction at the first item it has not judged.

- AC-1: THE cursor SHALL offer `count`, `current`, `next`, `seek`, and `reset`, and every response SHALL carry `index`, `total`, the item ID, its quote, and the PRD pointer.
- AC-2: WHEN `next` is called without a verdict for the current item, THE SYSTEM SHALL refuse it. Skipping an item SHALL require the explicit verdict `deferred` with a reason.
- AC-3: THE ledger SHALL be `kiwi/prd/<run_id>.jsonl`, appended one verdict per line, and the current index SHALL be computed from it rather than stored. Two run IDs SHALL NOT read or write each other's ledger.
- AC-4: WHEN the PRD hash differs from the hash on the ledger lines of the current round, THE SYSTEM SHALL treat those lines as void, return `invalidated` with the previous and current hash, and restart at index 1.

#### (다) SRS → PRD 참조 해석과 커버리지

Requirement: speckiwi SHALL resolve a requirement's reference to a PRD item and report, for a target, the PRD items no requirement cites and the requirements and criteria that cite no PRD item.

- AC-1: WHEN a Trace `Doc` reference or a Rationale basis names `docs/prd/<file>.prd.md#PRD-<n>`, `links check` SHALL report a reference whose file or item does not exist.
- AC-2: `speckiwi prd coverage --target <t>` SHALL list every intent, goal, and in-scope item cited by no requirement or criterion of the target, and every criterion of the target with neither a PRD citation nor a `fills:` basis.
- AC-3: THE coverage SHALL NOT judge whether an addition stays within its cited item or whether the SRS contradicts an item. It reports only what string comparison decides, and states that the rest is left to the verifier.
