# Requirement Stability Lifecycle Research

| Field | Value |
|---|---|
| Product | SpecKiwi |
| Topic | Requirement Stability lifecycle |
| Date | 2026-05-10 |
| Status | proposed |
| Related SRS | `FR-PARSE-015`, `FR-FLOW-010` |

## 1. Research Question

`Stability=draft` is useful only if it is separated from implementation status and connected to validator, release, and agent workflow behavior. This research defines that separation and records the implementation implications.

## 2. Current State

- `Status` already means implementation and verification progress: `planned`, `in_progress`, `blocked`, `implemented`, `verified`, `discarded`.
- `Stability` is currently parsed as optional requirement metadata.
- `docs/rule/SRS-MD-Rules-v1.0.0.md` documents `volatile`, `evolving`, `stable`, and `frozen`.
- `src/core/types.ts` currently accepts only `stable`, `evolving`, and `volatile`.
- New requirement rendering currently defaults `Stability` to `evolving`.
- CLI and MCP accept a stability string for new requirements, but validation rejects values outside the code enum.
- Therefore `draft` should not be documented as already-supported behavior. It should be introduced through planned SRS requirements that align rules, code, CLI, MCP, fixtures, and agent instructions.

## 3. Decision

Keep `Status` and `Stability` orthogonal.

`Status` answers whether implementation and verification work is complete.

`Stability` answers whether the requirement text and acceptance criteria are mature enough to use as an implementation contract.

Recommended canonical `Stability` values:

| Stability | Meaning | Agent / Release Treatment |
|---|---|---|
| `draft` | Requirement wording, scope, or acceptance criteria may still change. | Not implementation-ready by default; agents should ask before target-scoped implementation. |
| `evolving` | Requirement is concrete enough for implementation, but still has known change risk. | Implementable with caution; release readiness may warn if unresolved. |
| `stable` | Requirement is implementation-ready. | Normal implementation and release candidate state. |
| `frozen` | Requirement is change-controlled for a target or release baseline. | Changes require explicit Change Notes and review. |
| `deprecated` | Requirement is retained for traceability but should not guide new implementation. | Exclude from new-work recommendations unless explicitly requested. |

`volatile` should be treated as a legacy value. Existing documents may keep it during a compatibility window, but new generated requirements should not emit it. Migration should map `volatile` to either `draft` or `evolving` based on whether the requirement is implementation-ready.

## 4. Validator Implications

- Unknown `Stability` values remain validation errors.
- `draft` is a valid value only after the code enum and rules are updated.
- Active targets containing non-discarded `draft` requirements should produce a warning in normal validation or target summary.
- Release readiness should block a release target that still contains non-discarded `draft` requirements.
- `verified` plus `Stability=draft` should be diagnosed because `verified` means both implementation evidence and the requirement contract are ready enough to trust.
- `frozen` changes should require Change Notes.
- `deprecated` requirements should remain searchable and traceable but should not appear as default new implementation work.

## 5. Agent Workflow Implications

When answering current work status requests, agents should report both:

- implementation progress from `Status`; and
- requirement maturity from `Stability`.

Before implementing a requirement with `Stability=draft` or `Stability=deprecated`, an agent should stop and ask whether to stabilize, replace, or explicitly override the requirement first. `Stability=evolving` may proceed, but the work summary should mention the change risk.

## 6. Required Follow-up

The SRS should add planned requirements for:

- stability taxonomy and validator behavior;
- generated default stability behavior;
- release readiness and current-work summaries that expose stability;
- managed `AGENTS.md` and `CLAUDE.md` guidance that explains `Status` versus `Stability`;
- fixture and regression coverage for `draft`, `frozen`, `deprecated`, and legacy `volatile`.
