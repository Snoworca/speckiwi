# 17. 배포 가능 상태 복원 연구 — 검증의 재현성 · 릴리스 트레인 · 명세 무결성

작성 2026-08-10. 세 축으로 나누어 조사했다 — **A 검증의 재현성 / B 릴리스 엔지니어링 / C 명세 무결성**.

조사 제약: 저장소 **읽기 전용**으로 묶었다 — 다른 작업 스트림이 `src/core/workflow/*`,
`src/core/lock/exclusive-lock.ts`, `src/mcp/*` 에 미커밋 변경을 들고 있기 때문이다. 측정은 전부
`git worktree` 로 만든 **격리된 체크아웃**에서 수행했고, 메인 워킹트리는 건드리지 않았다.

**방법에 대한 정직한 기록**: 세 축을 병렬 조사 에이전트로 띄웠으나 세션 내에 결과를 반환하지 않았다.
따라서 본문의 모든 주장은 **직접 실측**이며, 각 절에 측정 명령과 값을 남겼다.

교차검증이 비는 것을 그대로 두지 않으려고, 문서의 머리 결론(§3.1)에 대해서는 **스스로 반증을
시도했다** — 다섯 개의 대체 가설을 세우고 각각 기각했다(§3.1.1). 그 과정에서 원래 주장의 **절반이
과장이었음**이 드러나 D-1 을 D-1a/D-1b 로 갈랐고, 부수 결함 D-11 을 새로 찾았다. 반증 시도를
하지 않았다면 둘 다 놓쳤을 것이다.

나머지 항목은 그만한 적대적 검토를 받지 못했다. 특히 §2.1 의 `harvest.fr-node-104` 원인 판정
(§5 D-10)처럼 **미확정으로 표시한 항목은 독립 확인 전까지 결론으로 쓰지 말 것.**

본 문서가 정본이다.

## 0. 요약 — 질문이 바뀌었다

들어갈 때의 질문은 "실패 11건을 고치면 배포 가능한가"였다. 조사 결과 그 질문은 잘못 놓여 있다.
확정된 사실 셋이 질문을 다시 세운다.

1. **"11 실패"는 개발자 한 사람만 보는 숫자다.** 그 값은 미커밋 작업이 섞인 워킹트리에서 나온다.
   커밋 상태를 CI 와 같은 조건으로 체크아웃하면 **158 실패 / 11 파일**이다(§1).
2. **`main` 은 120 커밋 뒤에 있고, 그 120 커밋은 CI 를 한 번도 통과한 적이 없다.** CI 는
   `pull_request` 와 `main` push 에만 걸리는데 작업은 `feat/2.3.0.1` 에서만 진행됐다. npm `@latest`
   `2.4.1` 은 정확히 `main` 의 tip 이다. 즉 `2.5.0`~`2.7.2` 전체가 미검증·미배포 상태로 쌓여 있다(§3).
3. **그리고 가장 중요한 것: 소비자에게 배포되는 패키지의 거버넌스 훅이 무동작 스텁이다.**
   `speckiwi init` 은 pre-commit 훅과 trace 훅을 설치한다고 선언하지만, 그 원본이 tarball 에 없어
   실제로는 `process.exit(0)` 스텁을 쓴다(§3.1). 이 저장소 안에서만 동작한다.

세 번째가 이 조사의 결론을 바꾼다. 배포를 막는 결함을 고치는 문제가 아니라, **이미 배포된 것이
제 기능을 하지 못하고 있었다**는 문제다.

### 제품 목적에 비춘 무게

SpecKiwi 의 명제는 하나다 — *요구사항이 단일 진실원천이고, 증거 없이는 `verified` 가 아니며,
그 증거는 재현 가능하다.* 이 제품은 남의 저장소를 **통치**하기 위해 존재한다. 그래서 같은 결함이라도
무게가 다르다.

- 테스트가 워킹트리에서만 통과한다 → 다른 제품이면 불편, **이 제품이면 명제의 부정**이다.
  `verified` 가 "내 컴퓨터에서는 됐다"는 뜻이 되기 때문이다.
- 거버넌스 훅이 스텁으로 배포된다 → 다른 제품이면 기능 결손, **이 제품이면 통치 실패**다.
  사용자는 게이트가 켜져 있다고 믿는데 게이트가 없다.

## 1. 측정 — 세 환경, 그리고 왜 세 번째가 필요했는가

같은 커밋(`96bb052`)을 세 조건에서 전체 스위트로 측정했다.

| 환경 | 결과 | 이 숫자의 의미 |
|---|---|---|
| 메인 워킹트리 (sentinel 대피 후) | **11 실패** / 5102 통과 | 개발자가 보는 값. 다른 스트림의 **미커밋 구현이 테스트를 통과시키고 있다** |
| 격리 체크아웃, Windows 기본(`autocrlf=true`) | 303 실패 / 4800 통과 | **145 건이 CRLF 변환 인공물** |
| **격리 체크아웃, LF (= CI 동등)** | **158 실패 / 4945 통과, 11 파일** | **CI 가 실제로 볼 값** |

세 번째 측정이 필요했던 이유는 두 번째가 나를 속였기 때문이다. 처음에는 두 번째 값(303)을 보고
"`skills/_shared` 가 미추적이라 wave 테스트 134건이 깨진다"고 판단해 보고까지 했다. **틀렸다.**
내가 조회한 `skills/_shared/…` 는 존재하지 않는 경로였고(실제는 `skills/<variant>/_shared/…`),
그 경로들은 전부 추적 중이다(`claude 11/11 · codex 11/11 · etc 12/12`, `skills/` 전체 미추적 0건).

진짜 원인은 **줄바꿈**이었다.

```
core.autocrlf = true,  .gitattributes 없음

skills/claude/_shared/kiwi/verify-loop.md
  워킹트리   bare-LF   16383 B
  새 체크아웃 CRLF     16532 B      <- git status 는 "변경 없음"으로 보고

skills/claude/kiwi-wave-master/SKILL.md
  양쪽 모두  CRLF      56185 B      <- 즉 저장소가 LF/CRLF 혼재
```

`autocrlf=true` 는 읽을 때 정규화하므로 git 은 차이를 보고하지 않는다. 그래서 **육안·`git status`·
`git diff` 어느 것으로도 보이지 않고, 새 체크아웃에서만 드러난다.**

> **교훈 1.** 이 저장소에서 "clean checkout 에서 무엇이 깨지는가"를 물을 때 Windows 기본 설정으로
> 체크아웃하면 답이 145건 부풀려진다. CI 와 비교하려면 `git -c core.autocrlf=false worktree add` 로
> 받아야 한다.

## 2. 축 A — 검증의 재현성

### 2.1 줄바꿈 정책 부재 (HIGH)

- **사실**: `core.autocrlf=true`, `.gitattributes` 없음, 커밋된 블롭에 LF/CRLF 혼재.
- **영향**: Windows 기여자는 CI 결과를 재현할 수 없다. 텍스트 단언 기반 테스트(스킬 본문 계약,
  파서, 진단)가 로컬에서만/CI 에서만 깨지는 두 방향 모두 가능하다.
- **아이러니**: 이 저장소에는 이 문제를 위한 자체 가드가 이미 있다.
  `test/core/orchestrator/harvest.fr-node-104.test.ts` 의 케이스 이름이 그대로
  *"the three suites pass under filters plus **autocrlf**, from three cwds"* 이다. 그리고 **그 가드가
  격리 체크아웃에서 실패한다**(메인 워킹트리에서는 2/2 통과).
- **권고**: `.gitattributes` 에 `* text=auto eol=lf` 를 두고 커밋된 블롭을 정규화한다.
  단, 이는 shipped `skills/**` 마크다운의 바이트를 바꾸므로 **§3 의 tarball 문제와 같은 릴리스에
  묶어야 한다.** 대안(단언을 줄바꿈 무관하게 고치기)은 표면이 넓고 재발을 막지 못한다.
- **미확정**: `harvest.fr-node-104` 실패가 순수 autocrlf 문제인지, 아니면 내 측정 환경(중첩 worktree +
  junction 된 `node_modules`)의 인공물인지는 **실제 CI 에서 확인해야 한다.** 이 문서는 단정하지 않는다.

### 2.2 git-ignored 콘텐츠에 대한 테스트 의존 (CRITICAL — 실은 §3.1 의 증상)

`test/core/mutation/fr-node-039-trace-hook.test.ts` 와 `fr-node-040-pre-commit-hook.test.ts` 는
`docs/.kiwi/hooks/*.mjs` 를 실행한다. 그 경로는 `.gitignore:28` (`.kiwi/`) 에 걸려 **추적되지 않는다.**
격리 체크아웃에서 `MODULE_NOT_FOUND` 로 17건이 실패한다.

이것을 "테스트가 ignored 파일에 의존한다"로만 읽으면 절반만 본 것이다. 같은 사실의 다른 절반이
§3.1 이며, 그쪽이 훨씬 무겁다.

### 2.3 hermeticity 가드의 운영 비용 (MEDIUM)

`test/support/hermeticity-guard.ts` 는 매 테스트 후 저장소 루트의 sentinel 6종을 검사해 발견 시
**삭제하고 throw** 한다. 그중 4종(`.mcp.json`, `docs/spec/steps`, `.claude/skills`,
`.codex/hooks.json`)은 정상적으로 워킹트리에 존재하는 미추적 콘텐츠다. 따라서 **모든 테스트 실행 전에
그 4종을 대피시켜야 한다.**

- 이 조사 중 실제로 발화했다. 단일 파일 타깃 실행을 래퍼 없이 돌려 4종이 삭제됐고, 백업에서
  49개 파일을 바이트 동일 복원했다(손실 0).
- **증상이 오귀인되기 쉽다**: 가드는 *마침 그때 돌던 테스트 하나*를 실패시킨다. 즉 "이 파일에
  예상보다 실패가 하나 많다"로 나타난다. 실제로 그 1건을 기존 문제로 넘겼다가 뒤늦게 발견했다.
- **권고**: 고정 sentinel 목록 대신 **실행 전 스냅샷과의 차분**으로 판정하고, 사전 존재분은 무시한다.
  그러면 `npm test` 가 워킹트리에서 그대로 안전해지고 대피 절차 자체가 사라진다.

> **교훈 2.** 오염 가드가 "발견 즉시 삭제"를 택하면, 정상 콘텐츠가 그 경로에 존재하는 순간
> 가드 자체가 파괴 도구가 된다. 삭제는 격리 실패의 대가가 아니라 **격리 설계의 실패**를 알리는
> 신호여야 한다.

## 3. 축 B — 무엇이 실제로 배포되는가

### 3.1 **[CRITICAL] 거버넌스 훅이 무동작 스텁으로 배포된다**

이 조사의 최대 발견이다.

`src/core/bootstrap/init-project.ts:166-174`:

```ts
/** Reads a bundled docs/.kiwi runner shipped with the package, or undefined when absent. */
async function loadBundledHookRunner(name: string): Promise<string | undefined> {
  const candidate = fileURLToPath(new URL(`../../../docs/.kiwi/hooks/${name}`, import.meta.url));
  ...
}
```

`:184-188`:

```ts
for (const runner of ["pre-commit.mjs", "trace.mjs"] as const) {
  const bundled = await loadBundledHookRunner(runner);
  await writeIfMissing(..., bundled ?? "#!/usr/bin/env node\nprocess.exit(0);\n", ...);
}
```

즉 `init` 은 **패키지 자신의 `docs/.kiwi/hooks/`** 에서 런너를 읽어 대상 프로젝트에 복사한다.
그런데 실측:

```
npm pack --dry-run --json
  tarball 총 파일 수        796
  docs/.kiwi 항목           []            <- 없음
  docs/ 항목                docs/rule/SRS-MD-Rules-v2.5.0.md
                            docs/rule/SDS-MD-Rules-v2.5.0.md
package.json files
  ["bin","dist","docs/rule/SRS-MD-Rules-v2.5.0.md",
   "docs/rule/SDS-MD-Rules-v2.5.0.md","skills/codex","skills/claude","skills/etc"]
```

원본 파일의 상태:

```
docs/.kiwi/hooks/pre-commit.mjs   exists=yes  tracked=no  ignored-by .gitignore:28 (.kiwi/)
docs/.kiwi/hooks/trace.mjs        exists=yes  tracked=no  ignored-by .gitignore:28 (.kiwi/)
```

**결론**: 소비자 머신에서 `loadBundledHookRunner` 는 언제나 `undefined` 를 돌려주고, `init` 은
`process.exit(0)` 스텁을 설치한다. 원본이 동작하는 곳은 이 저장소뿐이며, 그건 파일이 워킹트리에
미추적 상태로 남아 있기 때문이다.

폴백은 `d165542`(2026-07-08)에 도입됐고, 이후 배포된 릴리스는 `2.4.0`·`2.4.1`(2026-07-18) 두 건이다.
npm `@latest` 가 여전히 `2.4.1` 이므로 **지금 설치되는 버전이 곧 스텁이 든 버전이다.**

#### 3.1.1 반증 시도 — 절반은 살아남고 절반은 완화된다

이 주장이 문서의 머리 결론이므로 **직접 반증을 시도했다.** 다섯 경로를 확인했다.

| 반증 가설 | 결과 |
|---|---|
| `postinstall`/`prepare` 가 훅을 내려받는다 | `scripts` 에 `prepack=npm run build` 뿐. **기각** |
| 빌드가 `dist/` 로 훅을 내보낸다 | `find dist -name "pre-commit.mjs" -o -name "trace.mjs"` → 없음. **기각** |
| 다른 코드가 그 파일을 쓴다 | `src/` 전체에서 두 파일명을 쓰는 곳은 `init-project.ts` 하나. **기각** |
| 훅 로직이 `src/` 에 문자열로 내장돼 있다 | `init-project.ts` 에 게이트 로직 0건. **기각** |
| tarball 어딘가에 다른 이름으로 들어간다 | 796 파일 중 `kiwi/hooks`·`pre-commit.mjs`·`trace.mjs` **0건**. **기각** |

기본 주장은 살아남았다. 그러나 반증 과정에서 **주장을 반으로 갈라야 한다**는 사실이 나왔다.

**(a) vibe 게이트 — 완화된다.** `src/cli/commands/read.ts:806-811` 에 CI 용 `vibe-gate check` 가 있고,
그 주석이 존재 이유를 명시한다: *"Wire as a remote required status check to block unsynthesized
vibe/tdd commits **where local hooks can be bypassed**."* 이 명령은 실제로 출하되며
(`dist/cli/commands/read.js`), `README.md:450` 에 사용법이 있고 MCP `check_vibe_gate` 로도 미러된다.
즉 **로컬 훅이 못 미더울 때를 위한 권위 있는 경로가 이미 설계·출하돼 있다.** 따라서 vibe 정책은
"강제 수단이 없다"가 아니라 "로컬 편의 게이트가 조용히 무동작"이다.

**(b) trace 훅 — 완화되지 않는다.** `docs/.kiwi/trace` 를 쓰는 대체 경로가 `src/` 에 **없다**.
그리고 이 훅은 요구사항이 명시적으로 지목한다:

- `FR-NODE-054` (implemented) — *"an installed PostToolUse hook script at `docs/.kiwi/hooks/trace.mjs`"*
- `IR-CLI-047` (implemented) — *"`speckiwi init` SHALL … install the agent governance hooks and
  docs/.kiwi runner scaffold"*
- `FR-NODE-052`·`FR-NODE-053` — 그 훅을 `.claude/settings.json` / `.codex/hooks.json` 에 등록

요구사항이 "설치된 스크립트"를 요구하는데 설치되는 것은 빈 스텁이다. **vibe 모드의 편집 추적은
어떤 소비자 환경에서도 기록된 적이 없다.**

> **교훈 4.** 반증을 시도하지 않았다면 (a)를 (b)와 같은 무게로 보고했을 것이다. 조용한 폴백이
> 위험한 이유는 기능이 사라져서가 아니라, **어느 절반이 사라졌는지 아무도 구분할 수 없어서**다.

#### 3.1.2 부수 발견 — trace 훅의 `@req` 가 무관한 요구사항을 가리킨다

```

test/core/mutation/fr-node-039-trace-hook.test.ts   (파일명이 같은 ID)
그러나 그 테스트 헤더 :7             // FR-NODE-054 — trace.mjs per-edit hook …
그리고 FR-NODE-039 의 실제 내용      refresh_compatibility_check / revoke_compatibility_check
                                    (src/core/mutation/add-compatibility-check.ts 가 정당하게 사용)
```

세 갈래가 어긋나 있다. 실제 소유자는 **FR-NODE-054** 이고, 훅 파일의 `@req` 와 테스트 파일명이
둘 다 무관한 요구사항 번호를 달고 있다. 추적성 도구가 `@req` 를 신뢰하는 제품에서 이는 그 자체로
결함이다(§5 D-11).

관련 요구사항 5건이 이 훅의 동작을 서술하며 전부 `implemented` 다(`verified` 아님 — 그래서 거짓
`verified` 주장은 없다): `IR-CLI-047`, `FR-NODE-052`, `FR-NODE-053`, `FR-NODE-054`, `FR-NODE-055`.

**세 결함이 하나의 뿌리에서 나온다**: 훅 런너가 (a) ignored 이고 (b) 미추적이며 (c) tarball 에 없다.
`.gitignore:28` 의 `.kiwi/` 패턴이 **런타임 산출물 디렉터리**(`.kiwi/` 세션 상태)와 **패키지 소스**
(`docs/.kiwi/hooks/`)를 같은 이름으로 싸잡은 것이 원인이다.

**권고 (순서 고정)**
1. `.gitignore` 를 좁힌다 — 런타임 `.kiwi/` 만 무시하고 `docs/.kiwi/hooks/` 는 예외로 되살린다
   (`!docs/.kiwi/hooks/`).
2. 두 런너를 커밋한다.
3. `package.json` `files` 에 `docs/.kiwi/hooks` 를 추가한다.
4. tarball 에 두 파일이 들어갔는지 **테스트로 고정한다**(§6.1 G-1).

### 3.2 릴리스 트레인 (HIGH)

```
main tip            86a090d  2026-07-18  "패키지 버전을 2.4.1로 올린다"
npm @latest         2.4.1                 <- main tip 과 일치
최고 git 태그        2.5.2                 <- 이 브랜치의 조상이지만 미배포

버전 범프 이력       2.5.1 → 2.6.0 → 2.7.0 → 2.7.1 → 2.7.2  (전부 미배포)
main → HEAD         fast-forward 가능
```

- `2.5.1`·`2.5.2` 는 태그가 있으나 배포되지 않았고, `2.6.0`·`2.7.x` 는 태그도 배포도 없다.
- CI 는 `pull_request` / `main` push 에만 걸린다. 이 브랜치로의 push 는 CI 를 돌리지 않는다.
  **따라서 120 커밋 중 CI 를 통과한 것은 0건이다.**
- `main` 은 fast-forward 가능하므로 병합 자체는 깨끗하다. 문제는 병합 시점에 CI 가 처음으로
  158 실패를 마주한다는 것이다.

### 3.3 릴리스 게이트가 이름보다 약하다 (HIGH)

`scripts/release-check.mjs --strict` 는 현재 `ready: true` 를 돌려준다. 그 술어는
**활성 타깃에 등록된 요구사항** 범위다: blocked 0, planned 0, implementedNotVerified 0,
missingEvidence 0 …

그런데 활성 타깃 `2.6.0-phase2-parallel-lanes` 의 실제 작업(설계 05 의 스테이지 ②③④ — 워크트리
분할, 레인별 검증, 레인별 병합)은 **요구사항으로 등록조차 되어 있지 않다.** 등록되지 않은 미완은
게이트에 보이지 않으므로 `ready: true` 가 나온다.

즉 이 게이트는 **"등록된 것 중 미완이 없다"**를 말하는데, 읽는 사람은 **"할 일이 없다"**로 읽는다.
증거 기반 완료를 명제로 삼는 제품에서 이 간극은 그 자체로 결함이다.

또한 이 게이트는 **테스트를 돌리지 않는다.** `release-check` 가 green 이어도 스위트는 red 일 수 있고,
지금이 정확히 그 상태다.

## 8. 이 조사가 남기는 한 문장

> 이 제품은 "증거 없이는 `verified` 가 아니다"를 팔면서, 정작 자기 증거를 **개발자 워킹트리에서만**
> 재현할 수 있는 상태였고, 남의 저장소에 설치하는 게이트는 **빈 스텁**이었다.
