# 22. 워크플로 JSONL 내구성 — 무엇이 실제로 깨지는가

> **이 문서는 미검증 작업 노트다.** LLM 리뷰를 거치지 않았다. 확정된 계약은 `docs/spec` 의 요구가 정본이며, 여기의 주장이 요구가 될 때 코드에 대해 다시 확인된다 — 그 확인이 이 산문을 읽는 것보다 강하다. 실측한 것과 재현하지 못한 것을 절마다 구분해 표시했다.
>
> 조사 계기: 사용자가 다른 프로젝트에서 `kiwi/pipeline.jsonl` 이 깨져 **수동 복구한 실제 사고 이력**을 보고했고, "사용할수록 느려지는 것 아닌가"를 함께 물었다. 두 질문을 실측으로 답하는 것이 목적이다.

작성 2026-08-19. 측정 환경: Windows 11, Node 24, speckiwi 2.12.0 (`dist` 빌드).

---

## 0. 결론 먼저

세 가지가 사실로 확인됐고, 그중 **애초에 의심했던 것은 하나도 없다.**

| 의심 | 실측 결과 |
|---|---|
| 동시 쓰기로 줄이 섞인다 | **아니다** — 6프로세스 × 64KB 줄에서도 240/240 무결 |
| 프로세스 중단이 부분 줄을 남긴다 | **재현 실패** — 8MB 쓰기를 8ms 만에 kill 해도 완전히 쓰임 |
| `waves.jsonl` 의 락 없는 read-modify-write 가 줄을 잃는다 | **사실 — 2026-08-20 정정.** 최초엔 재현 실패로 적었으나(시간 비율로 겨냥 + writer 스탬프 게이트에 막힘), candidate 파일로 창을 계측하니 3/3 재현. 도구는 `written:true` 로 성공을 보고하고 파일은 유효하게 남는다 — **무증상 손실**. §2.3 |
| 파일이 커져 느려진다 | **사실이나 완만** — 32배 파일에 append 4배 |
| 형식이 맞지 않는 줄 하나가 전체를 잠근다 | **사실, 그리고 이것이 사고의 원인** |
| 새 프로젝트에서 도구 경로가 부트스트랩된다 | **아니다 — 첫 emit 이 예외로 죽는다** |

즉 **파일은 견고하고, 정책이 취약하다.**

## 1. 성능 — 사실이나 급하지 않다

`appendWorkflowJsonl` 은 한 줄을 붙일 때마다 `parseWorkflowJsonl` 로 **파일 전체를 읽어 파싱**한다(`src/core/workflow/jsonl.ts:425`). append 하나가 O(n)이고 누적은 O(n²)이다.

**실측** — 각 수치는 새로 시드한 파일에 append 7회의 중앙값:

| 기존 줄 | 크기 | append | 파싱 | 순수 fs append |
|---|---|---|---|---|
| 250 | 270 KB | 10.4 ms | 5.9 ms | 1.81 ms |
| 1,000 | 1.1 MB | 23.6 ms | 9.8 ms | 2.94 ms |
| 4,000 | 4.3 MB | 21.4 ms | 17.3 ms | 0.64 ms |
| 8,000 | 8.6 MB | 42.3 ms | 35.0 ms | 0.41 ms |

파일이 32배일 때 append 는 4배. **비용의 대부분이 파싱이고, 디스크가 아니다** — 순수 fs append 는 크기와 무관하게 1ms 안팎이다.

누적 실측: 빈 파일에 800회 append = 3.6초(평균 4.5ms). 100회일 때 평균 3.0ms이므로 800회까지 1.5배 열화.

**판단**: 이 저장소의 `kiwi/pipeline.jsonl` 은 3주에 41줄이다. 이 궤적이면 성능이 문제가 되기 전에 다른 것이 먼저 문제가 된다. **지금 고칠 이슈가 아니다.**

*(초기 측정에서 "4,000줄에서 5배"라고 적었으나 표본이 적어 과장이었다. 위 표가 정정된 수치다.)*

## 2. 파일은 잘 깨지지 않는다 (실측)

### 2.1 동시 append — 안전

6개의 **별도 프로세스**가 각 40줄씩 같은 파일에 append. 별도 프로세스인 것이 중요하다 — 같은 프로세스 안의 쓰기는 이벤트 루프에서 직렬화되므로 아무것도 증명하지 못하고, 스킬은 각자 셸 프로세스에서 쓴다.

| 줄 크기 | 결과 |
|---|---|
| ~200 B | 240/240 present, malformed 0, 미종료 꼬리 없음 |
| ~4 KB | 240/240, malformed 0 |
| ~64 KB | 240/240, malformed 0 |

`O_APPEND` 가 PIPE_BUF 를 훨씬 넘는 64KB 줄에서도 원자적으로 동작했다.

### 2.2 중단 — 재현 실패

8MB 짜리 한 줄을 쓰는 도중 8ms 후 `process.exit(1)`. 파일은 8,388,915 바이트로 **완전히** 쓰였고 부분 줄이 없었다. 더 공격적인 중단(SIGKILL, 디스크 가득 참)은 시험하지 않았다 — **부분 줄이 불가능하다는 뜻은 아니고, 흔한 경로로는 만들지 못했다는 뜻이다.**

### 2.3 `waves.jsonl` 갱신 손실 — ~~재현 실패~~ **재현됨 (2026-08-20 정정)**

`appendWavesLine`(`src/cli/commands/orchestrate.ts`, 현재 939~968행)은 전체 읽기 → candidate 전체 쓰기 → rename 이고 **락이 없다**. 코드상 읽기와 rename 사이에 창이 존재한다.

**최초 시도(2026-08-17) — 재현 실패.** 3,000줄(3.1MB) 저널에 도구 왕복 765ms. 그 구간의 30%~95% 지점 9곳에서 셸 방식 append 를 끼워 넣었고 9/9 전부 살아남았다. 당시 이렇게 적었다 — *"창이 없다는 증명이 아니라, 이 방법으로는 닫지 못했다는 기록이다. 정확히 하려면 읽기 시점을 계측해 그 직후를 노려야 한다."*

**정정(2026-08-20) — 그 계측을 붙이니 즉시 재현된다.** 계측 도구는 candidate 파일 자체다: 그 파일은 읽기가 끝난 뒤 생성되고 rename 직후 지워지므로, **존재하는 동안이 곧 창**이다. 그 순간에 원본으로 append 하면:

```
preload 2,000 / 8,000 / 20,000 줄 — 3회 전부 동일
  injectedInsideWindow : true
  cliExit              : 0
  cli stdout           : {"ok":true,"applied":true,"written":true,"violations":[],"diagnostics":[]}
  linesAfter           : preload + 1        (자기 줄만 늘었다)
  cliOwnLinePresent    : true
  injectedLinePresent  : false              <-- 끼어든 줄이 사라졌다
```

**최초 시도가 실패한 이유**는 타이밍만이 아니었다. 시간 비율로 겨냥한 9곳 중 상당수는 창 밖이었고, 무엇보다 **preload 줄에 `writer` 스탬프가 없으면 `unstamped-writer`(severity=error)로 append 자체가 rename 전에 거부**된다 — 이 재현에서도 스탬프를 붙이기 전까지는 `gate: run-invariant-drift` 로 막혀 아무것도 잃을 수 없었다. 즉 첫 실험은 창을 못 맞춘 것과 게이트에 막힌 것이 겹쳐 있었다.

**두 결함이 한 함수에 있다.**

1. **갱신 손실** — rename 이 읽기 이후의 모든 append 를 덮는다. 파일은 **항상 문법적으로 유효**하게 남으므로 어떤 진단도 이것을 잡을 수 없고, 도구는 `written: true` 로 성공을 보고한다. 탐지 수단이 없다.
2. **candidate 경로 공유** — `${relativePath}.candidate` 는 고정 이름이라 동시 실행 시 A 의 `finally { rm }`(966행)이 B 의 candidate 를 지운다. 이쪽은 `ENOENT ... rename` 으로 시끄럽게 실패하므로 조용하지 않다.

우선순위가 바뀐다: 이 항목은 §6 의 "재현 후 판단"이 아니라 **실증된 무증상 데이터 손실**이다.

## 3. 진짜 원인 — 형식 불일치 한 줄이 전체를 잠근다

### 3.1 차단하는 진단은 100% warning 이다

```ts
// src/core/workflow/jsonl.ts:432
if (policy === "halt" && diagnostics.length > 0) {
  return mutationFail("MUTATION_DENIED", "Workflow JSONL append halted by diagnostics", diagnostics);
}
```

**severity 를 보지 않고 개수만 본다.** 그리고 `parseWorkflowJsonl` 이 만드는 진단은 전부 `warning` 이다 — `SRS-W052`(파싱 실패) · `SRS-W053`(키 중복) · `SRS-W054`(CORRECTION 체인) · `SRS-W055`(스키마 버전) · `SRS-W056`(후행 LF 없음) · `SRS-W069`(tombstone). 유일한 `error` 인 `SRS-E032` 는 이 배열에 들어가지 않고 별도 경로로 반환된다.

즉 **`halt` 가 차단하는 대상은 정의상 전부 경고다.**

**실측** — 임시 프로젝트에서 CLI 로:

| 파일 상태 | 결과 |
|---|---|
| `schema_version` 없는 줄 1개 | `MUTATION_DENIED` (`SRS-W055`) |
| 전 줄 정상이나 후행 LF 없음 | `MUTATION_DENIED` (`SRS-W056`) |
| 전부 정상 | `ok: true` |
| 같은 파일에 `policy: "warn"` | `ok: true` |

### 3.2 이 저장소가 지금 그 상태다

`kiwi/pipeline.jsonl` 41줄 중 35·36행에 `schema_version` 키가 **없다**. 나머지 39줄은 `1.0.0`. 결과:

```
would a normal append succeed?  ok=false
  code=MUTATION_DENIED  message=Workflow JSONL append halted by diagnostics
with policy="warn"              ok=true
```

**손상이 아니라 구버전 형식이다.** 그 필드가 생기기 전 스킬이 쓴 줄이고, 스키마가 올라간 뒤 도구가 그것을 읽고 막혔다.

### 3.3 자가복구 코드가 도달 불가능하다

`jsonl.ts:439` 는 후행 LF 가 없으면 앞에 `\n` 을 붙여 쓴다 — 정확히 `SRS-W056` 상황을 고치는 코드다. 그런데 `SRS-W056` 은 `:432` 에서 이미 거부된다. **기본 정책에서 이 복구는 실행될 수 없다.** `policy: "best-effort"` 인 verification-ledger 두 호출에서만 산다.

### 3.4 검사가 거꾸로 걸려 있다

`skills/claude/_shared/kiwi/pipeline-event.md:126-171` 기준, **`kiwi-orchestrator` 만** MCP `workflow_pipeline_emit` 을 쓰고 나머지 전 스킬은 셸 `echo >> pipeline.jsonl` 을 쓴다.

**실측**: 도구 경로가 `MUTATION_DENIED` 로 거부한 바로 그 파일에 셸 방식 append 는 그대로 성공했다(1 → 2줄).

즉 **검사를 안 받는 경로가 파일을 만들고, 검사를 받는 경로가 그 결과 때문에 막힌다.** 사고의 구조가 이것이다.

## 4. 새 프로젝트에서 도구 경로가 부트스트랩되지 않는다 (실측)

`kiwi/pipeline.jsonl` 이 아직 없는 저장소에서 첫 emit:

```
exit 4
{"ok":false,"error":{"code":"WORKSPACE_PARSE_ERROR",
 "message":"ENOENT: no such file or directory, realpath '...\\kiwi\\pipeline.jsonl'"},
 "recovery":{"command":"init"}}
kiwi/ afterwards: (kiwi/ not created)
```

락 식별자 해석이 `realpath()` 로 경로를 정규화하는데(`src/core/workflow/artifact-lock.ts:52`) 미존재 경로에서 throw 한다. 디렉터리를 만드는 `mkdir` 은 `appendWorkflowJsonl` 안에 있어 **그보다 뒤**다(`jsonl.ts:438`).

셸 경로는 `mkdir -p` 를 스스로 하므로 영향받지 않는다 — 그래서 이 결함이 여태 드러나지 않았다.

## 5. 두 저널의 정책이 정반대다

| 축 | `pipeline.jsonl` | `waves.jsonl` |
|---|---|---|
| 쓰기 커널 | `appendWorkflowJsonl` (`open("a")` + fsync) | `appendWavesLine` (전체 재작성 → rename) |
| 뮤테이션 락 | 있음 | **없음** |
| 차단 임계 | `diagnostics.length > 0` (**warning 포함**) | `severity === "error"` 만 |
| 파싱 진단 소비자 | 읽기 도구가 노출 | **없음** (`WavesJournalView.diagnostics` 참조자 0건) |
| 검증 범위 | **파일 전체** | 해당 run + engine 만 |

`waves.jsonl` 은 깨진 JSON 줄이 있어도 append 가 통과한다. `pipeline.jsonl` 은 경고 하나로 영구 차단된다. **같은 파서를 쓰면서 정책이 반대다.**

`src/core/orchestrator/waves-validate.ts:616-620` 의 주석이 이 문제를 이미 알고 있다 — 과거 줄에 error 를 매기면 그 run 의 모든 저널 쓰기가 `run abort` 까지 포함해 거부되어 run lock 을 풀 수단이 없어진다는 것. 그래서 `abort_gate` **한 규칙에만** 위치 의존 완화를 넣었다. 나머지 26개 규칙에는 같은 완화가 없다.

## 6.1 수정 결과 (2026-08-19, `2.13.1-journal-resilience`)

후보 1·2·3 을 구현했다. 4~7 은 손대지 않았다.

| 요구 | 무엇 | CLI 실측 |
|---|---|---|
| `FR-NODE-193` | halt 가 개수 대신 **severity** 를 읽는다 | 레거시 줄 있는 파일: exit 5 → **exit 0** |
| `FR-NODE-193` | 후행 LF 복구가 살아났다(§3.3 의 죽은 코드) | 개행 없는 파일: exit 5 → **exit 0** |
| `FR-NODE-194` | 락 식별자가 미존재 경로를 감당한다 | 새 프로젝트 첫 emit: exit 4 → **exit 0**, `kiwi/pipeline.jsonl` 생성 |

경고는 여전히 결과에 실린다 — 차단만 하지 않는다. 파일 내용은 고치지 않는다: 읽을 수 없는 줄은 그대로 두고 그 뒤에 붙인다.

**뮤테이션 4/4 red** — 원래 결함 복원, 파서 진단에 error severity 부여, 락이 다시 존재를 요구, 복구 prefix 제거.

### 이 과정에서 드러난 것 (기록 가치)

**AC 두 개가 잘못된 계층을 지목했다.** 부트스트랩 테스트를 `appendWorkflowJsonl` 에 직접 걸었더니 **수정 전에도 통과**했다 — 그 함수는 락을 거치지 않고, 실패는 락에서 났기 때문이다. 멱등성 AC 도 같은 실수였다(그건 `mutation.ts` 의 계약이다). 둘 다 구현 전에 발견해 AC 를 고쳤다.

**`error` 차단 경로는 현재 도달 불가능하다.** severity 필터를 통째로 비워도 스위트가 green 이었다 — 파서가 error 를 만들지 않으므로 필터가 아직 아무것도 막지 않는다. "error 는 여전히 막힌다"고 단언하는 테스트를 쓰는 것은 거짓이 되므로, 대신 **그 전제 자체를 고정**했다: 파서 진단이 전부 warning 임을 단언한다. 누군가 error 진단을 추가하면 그 단언이 깨지고, 저널이 잠기는 조건이 조용히 바뀌는 대신 의도적 결정을 강요받는다.

## 7. 이 문서가 답하지 못한 것

- 사용자가 겪은 사고의 **원본 파일을 보지 못했다.** 여기의 원인 규명(§3)은 이 저장소의 동일 증상에 기반한 추론이다. 그 파일이 다른 방식으로 깨졌을 수 있다.
- 부분 줄과 갱신 손실은 **재현 실패**다. 없다는 증명이 아니다.
- `waves.jsonl` 쪽 26개 규칙의 과거-줄 차단은 코드로 읽었을 뿐 실행하지 않았다.
