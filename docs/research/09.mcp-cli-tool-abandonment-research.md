# SpecKiwi MCP and CLI Tool Abandonment Research

| Field | Value |
| --- | --- |
| Date | 2026-06-25 |
| Target | v2.3.0 |
| Requirement | OPS-FLOW-001 |
| Status | Research complete; v2.3.0 implementation SRS bridge created |

This report is an operational research artifact. It justifies v2.3.0 SRS work, but implementation behavior is governed by the canonical Requirement IDs mapped in Section 6.

## 1. Executive Summary

Coding agents abandon SpecKiwi MCP/CLI tools for SRS read, change, and add workflows because the official tools do not yet cover the complete agent loop:

1. find the right Requirement ID without raw Markdown search;
2. register or select the correct target without editing `00.index.md`;
3. create or update a requirement with Active Target defaulting;
4. preview all mutations safely;
5. preserve all advertised fields through CLI and MCP adapters;
6. receive actionable diagnostics and structured JSON errors;
7. trust the published docs, appendix, skills, and package smoke tests.

The most urgent defects are not cosmetic. Some documented features are missing, some adapter fields are silently dropped, and some `dryRun` paths mutate files through MCP because schema/handler parity is incomplete. These gaps directly explain why agents eventually use `rg`, `sed`, or direct Markdown edits.

## 3. Critical Findings

### 3.1 MCP evidence/trace/AC mutations can ignore dry-run and drop notes

Core supports `dryRun` for AC, evidence, and trace mutations in `src/core/mutation/check-ac.ts`, `src/core/mutation/add-evidence.ts`, and `src/core/mutation/add-trace.ts`. The MCP schema and adapter do not expose or forward those fields consistently:

- `src/mcp/server.ts` schemas omit `dryRun` for `check_acceptance_criteria`, `add_verification_evidence`, and `add_trace_link`.
- `src/mcp/tools/mutation-tools.ts` forwards neither `dryRun` nor `notes` for evidence/trace paths.
- Non-retained sub-agent dogfood on temp fixtures indicated `dryRun: true` could still write evidence and omit supplied notes. Current source inspection confirms the adapter-forwarding defect; a durable fixture must preserve the before/after hashes and persisted row proof before implementation is marked verified.

Impact: an agent that trusts MCP for safe preview can mutate SRS files unintentionally and lose evidence context.

Required improvement:

- add schema fields and handler forwarding for `dryRun` and `notes`;
- add MCP tests that inspect unchanged files for dry-run and exact persisted `Notes` cells;
- add CLI/MCP parity tests for AC/evidence/trace mutation envelopes.

Durable evidence requirement:

| Evidence Item | Required retained proof |
| --- | --- |
| MCP dry-run no-write | Fixture path, MCP call args, file hash before, file hash after, and assertion that hashes match. |
| Evidence notes round-trip | Fixture path, MCP call args, persisted Verification Evidence row, and exact `Notes` cell comparison. |
| Trace notes round-trip | Fixture path, MCP call args, persisted Trace Links row, and exact `Notes` cell comparison. |
| Adapter source gap | Source line references showing schema fields and handler forwarding before and after the fix. |

### 3.2 Target registration and Active Target defaulting are documented but not implemented

The appendix and current agent workflow mention `set-active-target --create` and Active Target defaulting, but current tools reject those paths:

```sh
node bin/speckiwi set-active-target v9.9.9 --create --dry-run --json
# error: unknown option '--create'

node bin/speckiwi add-requirement --type functional --scope FLOW --title "x" --requirement "x" --ac "x" --dry-run --json
# error: required option '--target <target>' not specified
```

Implementation evidence:

- `src/cli/commands/mutations.ts` registers no `--create` option for `set-active-target`.
- `src/core/mutation/set-active-target.ts` rejects unregistered targets.
- `src/cli/commands/mutations.ts` makes `--target` required for `add-requirement`.
- `src/mcp/server.ts` makes `add_requirement.target` required.

Existing planned requirements already identify the gap: `IR-CLI-023`, `FR-MCP-015`, `FR-NODE-014`, and `FR-FLOW-011`.

Required improvement:

- implement explicit target creation with type and description defaults;
- make requirement creation target optional with `targetSource: explicit|active-target`;
- return structured error when both explicit target and Active Target are empty;
- add core, CLI, MCP, and agent-workflow tests.

### 3.3 Official read tools are poor substitutes for `rg`

Agents need to find relevant requirements quickly. Current read tools still push them to raw Markdown search:

- `list` and MCP `list_requirements` return full records including `markdown` by default, producing large payloads.
- `list --format` is accepted but ignored.
- `extract` is documented with filters but implements only `--include-markdown` and `--json`.
- filters are exact metadata filters only: target, status, type, scope, tag.
- there is no first-class search over title, Requirement, Rationale, Research, AC text, evidence references, trace links, or Related Docs.

Reproductions:

```sh
node bin/speckiwi extract --target v2.2.3 --json
# error: unknown option '--target'

node bin/speckiwi list --target v2.2.3 --format ids
# still prints full JSON-like records, including Markdown
```

Required improvement:

- make list compact by default: `id`, `title`, `target`, `status`, `stability`, `scope`, `filePath`, `headingLine`;
- add `--include-markdown` or `--detail full`;
- implement `speckiwi search` and MCP `search_requirements`;
- add filters for stability, priority, missing evidence, related docs, evidence reference, trace reference, and new-work candidate.

### 3.4 Diagnostics are real but not actionable enough

Parser and validation diagnostics are not consistently helpful for agent recovery.

Confirmed issues:

- `validate` double-counts parser diagnostics because read paths prepend `workspace.diagnostics` and `validateWorkspace()` also seeds them.
- Target Map and Scope Map diagnostics usually point only to `docs/spec/00.index.md`, not the offending row.
- human read commands hide diagnostics unless `--json` is used.
- CLI runtime errors such as missing requirement under `show --json` print plaintext instead of a JSON error envelope.
- MCP mutation error conversion strips diagnostics arrays from failures.

Reproductions:

```sh
node bin/speckiwi --root test/fixtures/workspaces/parser-hardening-malformed-tables validate --json
# SRS-E021, SRS-W016, and SRS-W017 appear twice

node bin/speckiwi --root test/fixtures/workspaces/index-drift-duplicate-target validate --json
# SRS-E022 has filePath but no line

node bin/speckiwi show NO-SUCH-ID --json
# prints "Requirement not found: NO-SUCH-ID" to stderr, not JSON
```

Required improvement:

- introduce one canonical diagnostics aggregator or dedupe by `code|filePath|line|requirementId|message`;
- preserve row line numbers for Target Map, Scope Map, summaries, and Completed Work Log;
- include compact diagnostics in human output when nonzero;
- preserve diagnostics and `diagnosticsSummary` in MCP error envelopes;
- add recovery hints such as `recommendedCommands` or `nextActions`.

### 3.5 Tool-created requirements cause index summary drift

`add_requirement` appends a Requirement Block but does not update Status Summary or Requirement Type Summary. This immediately causes validation warnings:

```sh
node bin/speckiwi validate --json
# SRS-W019 Status Summary count drift
# SRS-W020 Requirement Type Summary count drift
```

This occurred after adding `OPS-FLOW-001` through the MCP tool. It is a dogfood-quality issue: the safe tool leaves the workspace in a warning state, so agents distrust the tool and inspect or patch index Markdown.

Required improvement:

- either update index rollups during requirement/status/type mutations, or add an explicit `speckiwi sync-index --dry-run` and MCP `sync_index`;
- expose a patch preview for summary updates;
- test that add/update mutations do not introduce summary drift.

## 4. High Priority Design Improvements

### 4.1 Granular requirement editing tools

Current tools can create a requirement, toggle AC checks, add evidence/trace, update status/stability, append limited notes, set target metadata, and add completed work. They cannot safely:

- edit requirement title;
- edit Requirement statement;
- add, update, delete, or reorder AC text;
- update metadata such as priority, risk, tags, related docs, verification method, GitHub issue;
- update or delete evidence/trace rows.

Required new tools:

- `update_requirement_field`;
- `update_requirement_metadata`;
- `add_acceptance_criterion`;
- `update_acceptance_criterion`;
- `delete_acceptance_criterion`;
- `update_verification_evidence`;
- `delete_verification_evidence`;
- `update_trace_link`;
- `delete_trace_link`.

All should support dry-run, minimal patch previews, stale snapshot guards, and Change Notes policy.

### 4.2 Unified mutation envelope

Mutation success payloads vary and often omit the changed record or useful patch context. Define a single mutation envelope:

```json
{
  "ok": true,
  "value": {},
  "mutation": {
    "kind": "evidence_add",
    "filePath": "docs/spec/60.workflow-release.srs.md",
    "dryRun": true,
    "written": false,
    "staleGuard": {
      "sha256": "expected-file-hash",
      "line": 100,
      "original": "| old | row |"
    },
    "operations": [],
    "hunks": [],
    "preview": "",
    "updatedRecord": {}
  },
  "diagnostics": [],
  "diagnosticsSummary": { "errors": 0, "warnings": 0, "byCode": {} }
}
```

This should replace operation-name-only previews for agent-facing flows.

Current drift to close:

- `addRequirement` can produce a patch summary, while AC/evidence/trace mutations mostly expose `{ written }` style results.
- MCP `resultToMcp` converts failures to `{ ok:false, error }` and does not preserve diagnostics arrays.
- CLI and MCP do not expose the same dry-run controls for the same core mutations.

Minimum contract for A+ implementation readiness:

| Field | Rule | Verification |
| --- | --- | --- |
| `mutation.kind` | Stable enum such as `status_update`, `ac_check`, `evidence_add`, `trace_add`, `requirement_add`, `target_set`, or `index_sync`. | Core tests assert every mutation returns a kind. |
| `mutation.filePath` | Repository-relative path for single-file mutations; workspace mutations return operation-level paths. | Snapshot tests reject absolute paths in public envelopes. |
| `mutation.dryRun` | Mirrors the effective write mode after CLI/MCP/core default resolution. | Dry-run tests compare file hash before and after every mutation. |
| `mutation.written` | `false` for dry-run and idempotent no-op; `true` only after the patch writer reports a write. | Idempotent tests assert already-applied operations do not report writes. |
| `mutation.staleGuard` | Includes file hash and/or exact original line when a stale write could corrupt state. | Stale snapshot tests fail closed before writing. |
| `mutation.operations[]` | Structured operations with `type`, `filePath`, `line`, `original`, and `replacement` or `lines`. | Tests verify no operation references a path outside project root. |
| `mutation.hunks[]` | Human-readable patch preview derived from the same operations. | CLI and MCP snapshots use the same hunk generator. |
| `mutation.preview` | Compact string preview for clients that cannot render structured hunks. | CLI human output and MCP payload derive from the same preview. |
| `mutation.updatedRecord` | Present when a single Requirement or Target is changed; omitted only for workspace-wide operations. | Adapter parity tests compare core and MCP output shapes. |
| `diagnosticsSummary` | Always included on success and failure. | Failure tests assert diagnostics are not stripped by MCP conversion. |
| `error` | On failure, structured error keeps `code`, `message`, optional `diagnostics`, and optional `recommendedCommands`. | `show MISSING --json` and failed MCP mutations return JSON envelopes. |
| compatibility | Existing `patch` payload remains as an alias during v2.3.0 migration. | Smoke tests for current consumers continue passing. |

Mutation safety preconditions:

1. The core mutation computes a patch plan before writing.
2. CLI and MCP expose the same dry-run field for every mutation that can write.
3. Stale snapshot guards use either an exact original line check or a file hash check before applying the write.
4. Table-cell mutation inputs reject or escape pipe and newline characters consistently.
5. Change Notes policy is explicit for structured edits: metadata/body/AC edits add notes, while pure evidence/trace appends do not rewrite unrelated sections.

### 4.3 Schema, docs, and skill signature parity

Current drift examples:

- appendix documents `--ref`, while CLI uses `--reference`;
- appendix documents `--create`, while CLI lacks it;
- appendix documents Active Target defaulting, while CLI/MCP require target;
- appendix MCP examples use shapes that do not match `toolSchemas`;
- `src/mcp/schemas.ts` is stale relative to `src/mcp/server.ts`;
- skill docs mention parameters such as `includeContent` and `stability` that runtime schemas do not expose.

Required improvement:

- define a single tool registry source for CLI help, MCP schemas, appendix examples, and skill snippets;
- add tests that parse appendix MCP examples against `toolSchemas`;
- add tests that compare documented CLI options with Commander registration;
- add a skill-doc signature scanner.

### 4.4 MCP workspace and environment clarity

MCP root behavior is fragile for multi-workspace agents:

- MCP tools resolve root from server startup dependencies or process cwd;
- schemas do not accept a per-call workspace/root field;
- startup may auto-init the cwd if no SRS root is found;
- README examples show `speckiwi mcp` before explicit `--root`.

Required improvement:

- add `get_workspace_info`;
- recommend explicit `--root` in registration docs;
- consider optional per-tool `workspace` for multi-root clients;
- add cross-workspace MCP tests with two temp SRS roots.

### 4.5 Compact search and discovery contract

Search and compact listing must be deterministic enough to replace routine `rg` usage:

| Behavior | Contract |
| --- | --- |
| default projection | `list` and `list_requirements` return compact records by default: `id`, `title`, `target`, `status`, `stability`, `scope`, `filePath`, and `headingLine`. |
| `ids` projection | CLI `--format ids` and MCP `format: "ids"` return only an ordered string array of IDs plus diagnostics. |
| `compact` projection | CLI `--format compact` and MCP `format: "compact"` return the default compact fields and never include Markdown. |
| `full` projection | CLI `--format full` and MCP `format: "full"` may include metadata, sections, evidence, trace, and Markdown when requested. |
| `fields[]` projection | MCP callers can request a subset of compact/full fields; unknown fields return a structured error. |
| `includeMarkdown` | Defaults to `false`; ignored for `ids` and rejected if it would contradict `format: "compact"`. |
| Markdown body | Full Markdown requires `--format full`, `--include-markdown`, or MCP `includeMarkdown: true`. |
| query fields | Search covers title, Requirement, Rationale, Research, AC text, evidence references, trace references, Related Docs, tags, and GitHub issue. |
| ranking | Exact Requirement ID match first, then title exact/substring, then metadata, then body text. Ties sort by target recency, file path, and heading line. |
| snippets | Search returns one to three snippets with `field`, `text`, `line`, and highlighted match offsets when line data exists. |
| filters | Target, scope, status, stability, priority, missing evidence, related docs, trace reference, evidence reference, and new-work candidate. |
| pagination | CLI and MCP support `limit` and `cursor`; default limit is compact enough for agent use. |
| diagnostics | Invalid filters return structured JSON errors and suggested valid values. |

## 5. Packaging And Install Findings

Packaging/install issues make the tools unavailable or untrusted before normal SRS work starts:

- `package.json` version is `2.2.4`, while `package-lock.json` still reports `2.2.3`.
- `scripts/version-check.mjs` fails with package-lock mismatch.
- smoke tests expect `2.2.3` and `skills/claude/kiwi-pm/skill.md`, while sources use `SKILL.md`.
- `speckiwi skills install ... --dry-run --json` reports `requiresMcp: true` but `mcpPreflight.status` remains `not_checked`.
- MCP server reports hardcoded version `1.0.0` while package version is `2.2.4`.
- package docs and skills disagree on whether CLI fallback is allowed for normal SRS mutation workflows.

Required improvement:

- derive smoke expected version from `package.json`;
- fix package-lock version drift before release checks;
- align packed skill path expectations with actual file names;
- add `speckiwi doctor mcp` or `skills install --check-mcp`;
- wire MCP server version to package metadata;
- add packed tarball smoke test that starts MCP and calls `get_active_target`.

## 10. Conclusion

SpecKiwi has enough core pieces to manage Markdown SRS safely, but the agent-facing tool contract is incomplete. The v2.3.0 release should prioritize tool reliability over new surface area:

1. make existing mutation tools safe and truthful;
2. complete target/defaulting workflows;
3. add search and compact discovery;
4. make diagnostics actionable;
5. test real coding-agent workflows;
6. make package install and MCP startup verifiable.

## 11. Follow-up Validation Notes

Date: 2026-06-26.

Four independent follow-up reviewers rechecked this report against the current checkout and found the core conclusions still valid. The following clarifications should guide later SRS authoring and implementation:

- The `notes` issue is an adapter-forwarding defect for evidence and trace mutations. The MCP schemas expose `notes` for those tools, but `src/mcp/tools/mutation-tools.ts` does not forward it to the core mutation functions. `check_acceptance_criteria` has no `notes` concept.
- The `dryRun` issue is broader: MCP schemas and handlers do not expose or forward `dryRun` for AC, evidence, and trace mutations even though the core functions support it.
- The index summary drift finding describes a mutation aftermath, not the current repository state. The checkout can validate cleanly after manual or tool-assisted rollup repair, but `add_requirement` itself still does not update Status Summary or Requirement Type Summary.
- The package/version findings remain factual in the current checkout: package metadata, smoke expectations, and MCP server metadata need a release-hardening pass.
- Design recommendations such as granular requirement editing, unified mutation envelopes, compact search, and workspace resolution are implementation proposals now mapped to canonical v2.3.0 Requirement IDs in Section 6. Use those IDs as the implementation contract instead of treating this report as a parallel requirements source.

The source-backed implementation plan derived from this report and the Kiwi planner follow-up is recorded in `docs/research/11.v2.3.0-tooling-code-improvement-plan.md`.

Until these are addressed, agent instructions should explicitly permit manual SRS-MD edits only as a documented tool-gap workaround, not as a normal path.
