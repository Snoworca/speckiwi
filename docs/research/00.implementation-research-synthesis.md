## 1. 목적

이 문서는 3개 서브에이전트가 작성한 SpecKiwi v1.0.0 구현 연구 문서를 취합한 통합본이다. 목적은 개별 연구 결론을 하나의 구현 방향, 모듈 경계, TDD 전략, 리스크 관리 기준으로 정리하여 이후 `docs/plan/step*.*/` 구현 계획으로 바로 전환할 수 있게 하는 것이다.

이 문서는 코드 구현을 포함하지 않는다. 기존 SRS 문서도 수정하지 않는다.

## 2. 원문 연구 문서

## 3. 통합 결론

세 연구 문서의 결론은 일관된다.

1. SpecKiwi의 원본은 `docs/spec/**/*.srs.md`와 `docs/spec/00.index.md` Markdown이다.
2. YAML, front matter, DB, 별도 source-of-truth는 만들지 않는다.
3. `src/core`가 root resolution, UTF-8 file read, SRS discovery, parser, validator, query, mutation, patch engine을 소유한다.
4. `src/cli`와 `src/mcp`는 domain logic을 구현하지 않고 core service만 호출한다.
5. parser는 Markdown 전체 AST 재렌더링이 아니라 SRS-MD 제한 구조를 line 단위로 파싱하고 line range를 보존한다.
6. mutation은 Requirement Block 전체 재출력이 아니라 line-based patch로 최소 변경만 수행한다.
7. `add-requirement`와 `add_requirement`는 모두 `FR-NODE-008` shared Requirement Block 생성 mutation service 위에 구현한다.
8. `verified` 상태는 모든 AC checked와 최소 1개 non-empty evidence reference가 있을 때만 허용한다.
9. CLI `--json` stdout과 MCP stdio stdout은 자동화 계약이므로 사람이 읽는 로그와 섞이면 안 된다.
10. 구현은 read-only core와 adapter를 먼저 안정화한 뒤 mutation과 release verification으로 확장해야 한다.

## 6. Core 구현 전략

### 6.1 Parser

권장 parser 흐름은 다음과 같다.

1. root를 결정한다.
2. `docs/spec/00.index.md`에서 Target Map, Scope Map, SRS Documents table을 파싱한다.
3. `docs/spec/**/*.srs.md` 파일을 발견한다.
4. 모든 파일을 UTF-8로 읽고 newline style과 line array를 보존한다.
5. `### {RequirementID} — {Title}` heading을 기준으로 Requirement Block range를 만든다.
6. metadata table, fixed `####` sections, AC task list, evidence table, trace table을 제한형 parser로 추출한다.
7. parser result는 partial parsing을 지원하고 diagnostics 후보를 함께 반환한다.

보존해야 할 위치 정보는 file path, block start/end, heading line, metadata row line, section range, AC line, evidence/trace table range다. mutation 안정성은 이 line range 품질에 의존한다.

### 6.2 Validator

validator는 parser와 분리된 rule registry로 구현한다. 주요 rule group은 다음이다.

| Rule Group | Examples |
|---|---|
| Identity | duplicate ID, heading format, ID regex |
| Metadata | missing table, required field omission, enum violation |
| Type and Scope | ID prefix/type mismatch, Scope Map mismatch |
| Sections | missing fixed section, duplicate fixed section |
| Acceptance Criteria | malformed task item, empty AC |
| Verified Guard | unchecked AC, missing evidence, empty evidence reference |
| Evidence and Trace | required columns, broken Requirement reference |
| Index Consistency | unknown target, missing scope document |
| Links | missing local Related Docs, malformed issue link |

하나의 Requirement Block 오류가 전체 workspace 조회를 중단하지 않도록 fatal parse failure를 최소화해야 한다.

### 6.3 Query

query service는 parser 결과와 validator diagnostics를 읽기 전용으로 조합한다.

필수 기능:

- exact requirement lookup
- target/status/scope/type/tag filter
- normalized record list
- includeMarkdown option
- target summary
- scope summary
- validation diagnostics passthrough

CLI와 MCP 결과 일치를 위해 `RequirementRecord`, `Diagnostic`, `TargetSummary`, `ScopeSummary`, `MutationResult`, `PatchSummary` 타입을 공유한다.

### 6.4 Mutation and Patch

mutation은 공통 흐름을 따른다.

1. root와 대상 path를 안전하게 resolve한다.
2. 최신 workspace를 다시 읽는다.
3. 대상 requirement 또는 scope document를 찾는다.
4. 입력 schema와 domain guard를 검증한다.
5. line-based patch plan을 만든다.
6. dry-run이면 파일을 쓰지 않고 patch summary만 반환한다.
7. apply 직전 expected original line/range를 확인한다.
8. temp file write와 atomic rename으로 저장한다.
9. 변경 후 필요한 범위를 재파싱하거나 full validation self-check를 수행한다.

patch engine은 `replaceLine`, `insertLines`, `appendLines`, `replaceRange` 같은 primitive만 알고 문서 의미는 모르게 둔다.

## 7. `add-requirement` 통합 전략

`IR-CLI-019`와 `FR-MCP-010`은 같은 core service `FR-NODE-008`을 호출해야 한다.

필수 입력:

- `type`
- `scope`
- `target`
- `title`
- `requirement`
- `acceptanceCriteria`

선택 입력:

- `status`, default `planned`
- `priority`
- `tags`
- `risk`
- `stability`
- `verificationMethod`
- `rationale`
- `implementationNotes`
- `relatedDocs`
- `githubIssue`
- `evidence`
- `traceLinks`
- `research`
- `changeNotes`
- `dryRun`

생성 알고리즘:

1. `00.index.md`와 scope SRS files를 파싱한다.
2. `scope`를 Scope Map `Prefix` 기준으로 해석한다.
3. `target`을 Target Map 기준으로 검증한다.
4. `type`을 SRS-MD Type/Prefix map으로 변환한다.
5. 전체 Requirement ID를 스캔하고 `discarded` ID도 재사용하지 않는다.
6. 다음 ID를 `{TYPE_PREFIX}-{SCOPE_PREFIX}-{NNN}` 형식으로 생성한다.
7. complete Requirement Block을 렌더링한다.
8. `status = verified`이면 모든 AC checked와 evidence reference 존재를 검증한다.
9. 대상 scope 문서의 `## 4. Requirements` 끝, 즉 다음 H2 앞에 삽입한다.
10. newline style과 주변 줄을 보존한다.
11. dry-run이면 generated ID, target file, patch summary, diagnostics만 반환한다.

중요한 해석: 사용자 요구의 "문서의 끝"은 SRS 구조상 scope 문서 전체 끝이 아니라 `## 4. Requirements` section 끝으로 반영하는 것이 맞다. 현재 SRS 문서에서는 보통 `## 5. Cross-scope Dependencies` 바로 앞이다.

## 8. CLI 구현 전략

CLI는 `src/cli` 내부에서만 CLI framework를 사용한다. Commander를 유지해도 되지만 domain logic은 넣지 않는다.

주요 책임:

- argv parsing
- help/version
- common options: `--root`, `--json`, `--no-color`, `--quiet`
- stdout/stderr routing
- exit code mapping
- human/json formatting

권장 exit code:

| Code | Meaning |
|---:|---|
| 0 | success |
| 1 | validation error |
| 2 | usage, argument, or root resolution error |
| 3 | file I/O error |
| 4 | fatal parse error |
| 5 | mutation denied, status transition denied, verified guard failure |
| 6 | MCP server fatal error |

`--json` 사용 시 stdout은 valid JSON만 포함해야 한다. validation failure처럼 domain result가 있는 경우 exit code가 `1`이어도 stdout JSON은 허용된다. usage/I/O/fatal parse 같은 pre-result failure는 stderr에 오류를 쓰고 stdout은 비워두는 편이 안전하다.

## 9. MCP와 Workflow 구현 전략

MCP server는 `speckiwi mcp`로 시작하고 stdio transport를 사용한다.

MCP adapter 규칙:

- stdout은 JSON-RPC 메시지 전용이다.
- logs, warnings, startup failure는 stderr로 보낸다.
- SDK import는 `src/mcp` 내부로 격리한다.
- 모든 tool/resource handler는 core service를 호출한다.
- domain failure는 structured error result로 반환하고 protocol failure와 구분한다.

필수 tool은 다음 core function에 대응한다.

| MCP Tool | Core Service |
|---|---|
| `list_requirements` | `listRequirements(project, filters)` |
| `get_requirement` | `getRequirement(project, id, options)` |
| `validate_spec` | `validateProject(project, filters)` |
| `update_status` | `updateStatus(project, input)` |
| `check_acceptance_criteria` | `setAcceptanceCriteriaChecked(project, input)` |
| `add_verification_evidence` | `addVerificationEvidence(project, input)` |
| `add_trace_link` | `addTraceLink(project, input)` |
| `summarize_target` | `summarizeTarget(project, target?)` |
| `add_requirement` | `addRequirement(project, input)` |

workflow/release 판단은 별도 상태 저장소 없이 normalized records, diagnostics, evidence 상태를 재계산해서 만든다. `ready` 판단은 validation errors, blocked items, planned/in_progress items, implemented-not-verified items, high/critical unverified items가 없어야 true가 된다.

## 10. 통합 TDD 전략

모든 구현은 Red, Red 확인, Green, Green 확인, Refactor, Regression 확인 순서로 진행한다.

| Test Group | Focus |
|---|---|

| `test/core/parser/*.test.ts` | index parser, block scanner, metadata, sections, AC, evidence, trace, CRLF |
| `test/core/validator/*.test.ts` | duplicate ID, metadata, enum, target/scope, verified guard, trace refs |
| `test/core/query/*.test.ts` | lookup, filters, summaries, includeMarkdown |

| `test/core/mutation/*.test.ts` | status, AC, evidence, trace, add-requirement |
| `test/cli/*.test.ts` | argv, formatters, exit codes, JSON stdout purity, read-only and mutation commands |

## 11. 주요 리스크와 완화책

| Risk | Impact | Mitigation |
|---|---|---|
| Markdown whole-file rewrite | noisy and unsafe Git diff | line-based patch only, exact diff tests |
| CLI/MCP logic divergence | human and agent see different behavior | shared core services and parity tests |
| `verified` false positive | requirement trust model breaks | common verified guard in core mutation |
| ID collision or discarded ID reuse | traceability breaks | scan all existing IDs globally before generation |
| Scope insertion ambiguity | requirement inserted into wrong section | Scope Map prefix and `## 4. Requirements` insertion rule |
| stdout contamination | JSON automation or MCP protocol breaks | formatter boundary and stdio cleanliness tests |
| Windows newline/path issues | corrupted files or failing CLI | CRLF fixtures, `path`/`fs` APIs, newline preservation |
| MCP SDK churn | adapter breakage | isolate SDK in `src/mcp`, pin stable version |
| path traversal/symlink escape | read/write outside root | realpath boundary checks in core |
| current package metadata stale | runtime mismatch with SRS | foundation phase updates package metadata to Markdown/Node >=22/bin dist |

## 12. 권장 구현 순서

1. Foundation
   - `package.json`을 SRS에 맞게 정리한다.
   - Node `>=22`, TypeScript ESM, Vitest, strict TS, shared result/error/types skeleton을 준비한다.
   - root resolution, UTF-8 read, newline detection, safe path utility의 실패 테스트를 먼저 만든다.

2. Core Read Path
   - `00.index.md` parser, SRS discovery, Requirement Block scanner를 구현한다.
   - metadata, fixed sections, AC, evidence, trace parser와 normalized record를 추가한다.

3. Validation and Query
   - validator rule registry와 diagnostics shape를 고정한다.
   - lookup, filters, target/scope summary, release summary의 core query를 구현한다.

4. CLI Read-only Commands
   - `validate`, `extract`, `list`, `show`, `targets`, `scopes`, `summary`, `links check`를 core 위에 얇게 구현한다.
   - JSON stdout purity와 exit code mapping을 먼저 테스트한다.

5. Patch Engine
   - line-based patch primitives, dry-run, stale guard, atomic write, newline preservation을 구현한다.
   - exact diff golden tests를 회귀 게이트로 둔다.

6. Existing Requirement Mutations
   - `update-status`, `check-ac`, `uncheck-ac`, `add-evidence`, `add-trace`를 구현한다.
   - verified guard와 no-write-on-failure를 공통화한다.

7. Requirement Creation
   - `FR-NODE-008` add requirement service를 구현한다.
   - CLI `add-requirement`와 MCP `add_requirement`는 이 service만 호출한다.

8. MCP Adapter
   - stdio server, metadata, tools, resources, schemas, structured error conversion을 구현한다.
   - stdout JSON-RPC cleanliness를 subprocess integration test로 검증한다.

9. Workflow/Release Verification
   - evidence workflow, readiness summary, CI examples, AGENTS/CLAUDE snippet generation을 구현한다.
   - release readiness는 Git tag 자동화가 아니라 deterministic summary로 제한한다.

10. Release Gate
    - unit/integration/typecheck/lint/perf/SRS traceability review를 통과시킨다.

## 15. 완료 판단 기준

이 취합 연구를 기반으로 한 구현은 다음 조건을 만족해야 한다.

- parser, validator, query, mutation이 `src/core`에 있고 CLI/MCP가 이를 공유한다.
- 모든 SRS-MD source-of-truth는 Markdown으로만 유지된다.
- mutation은 line-based patch로 최소 diff를 만든다.
- `verified` guard가 CLI/MCP/core 전 경로에서 동일하게 적용된다.
- `add-requirement`와 `add_requirement`가 같은 `FR-NODE-008` core service를 호출한다.
- CLI JSON output과 MCP stdio output이 자동화 계약을 깨지 않는다.
- no-write-on-failure, root boundary, CRLF preservation, discarded ID non-reuse가 테스트로 보장된다.
- 구현 후 evidence와 AC/status 갱신이 SRS workflow에 따라 남는다.
