## 1. 연구 목적

이 문서는 SpecKiwi v1.0.0의 MCP stdio interface와 workflow/release verification 기능을 어떤 구조와 순서로 구현해야 하는지 정리한다. 코드 구현은 포함하지 않는다.

핵심 결론은 다음과 같다.

- MCP adapter는 얇게 유지하고 모든 조회, 검증, 변경은 `src/core` service가 담당해야 한다.
- stdio transport에서는 stdout을 JSON-RPC 메시지 전용으로 보존하고 모든 로그는 stderr로 보내야 한다.
- MCP tool failure는 schema/unknown tool 같은 protocol error와 요구사항 도메인 실패를 분리해야 한다.
- workflow/release 판단은 별도 상태 저장소 없이 normalized requirement records, diagnostics, evidence table을 재계산해서 만든다.
- `add_requirement`는 MCP adapter에 직접 구현하지 말고 `FR-NODE-008`의 공통 Requirement Block 생성 mutation service만 호출해야 한다.

## 4. MCP tool/resource 구현 전략

### 4.1 Recommended module boundary

```text
src/
├─ mcp/
│  ├─ server.ts       # creates McpServer, stdio transport, metadata
│  ├─ tools.ts        # registers tools and schemas, maps results/errors
│  ├─ resources.ts    # registers speckiwi:// resources/templates
│  └─ adapter.ts      # SDK-specific glue only
└─ core/
   ├─ project-root.ts
   ├─ parser/
   ├─ validator/
   ├─ query/
   ├─ mutation/
   ├─ patch/
   └─ types.ts
```

`src/mcp` must not parse Markdown or edit files directly. It should:

1. resolve root once at server startup;
2. register tool schemas;
3. call core service functions;
4. convert core result to MCP tool/resource result;
5. convert core error to MCP-safe structured error;
6. send logs only to stderr.

### 4.2 Tool registration model

The tool registry should be data-driven:

| Field | Example |
|---|---|
| `name` | `list_requirements` |
| `kind` | `read` or `mutation` |
| `inputSchema` | schema from `src/core/schemas` or adapter-local schema mirroring core type |
| `outputSchema` | normalized result or mutation result schema |
| `handler` | function calling core service |

This allows tests to assert that every SRS-required tool exists and that mutation tools are distinguishable from read-only tools.

Recommended result convention:

```json
{
  "content": [
    { "type": "text", "text": "{...serialized JSON fallback...}" }
  ],
  "structuredContent": {
    "ok": true,
    "data": {}
  },
  "isError": false
}
```

For domain failures, return `isError: true` with a structured error object. Reserve JSON-RPC protocol errors for malformed MCP requests, unknown tools, server crashes, and resource read failures that should be handled by the MCP layer.

### 4.3 Tool-specific strategy

| Tool | Core function shape | Notes |
|---|---|---|
| `list_requirements` | `listRequirements(project, filters)` | filter validation should normalize scope prefix and target |
| `get_requirement` | `getRequirement(project, id, options)` | return `not_found` domain error for missing ID |
| `validate_spec` | `validateProject(project, filters)` | read-only; include summary counts and rule IDs |
| `update_status` | `updateStatus(project, { id, status, reason, dryRun })` | verified guard belongs in core mutation |
| `check_acceptance_criteria` | `setAcceptanceCriteriaChecked(project, { id, acIds, checked, dryRun })` | `["all"]` expands from parsed record |
| `add_verification_evidence` | `addVerificationEvidence(project, input)` | validate local file references with root safety before patching |
| `add_trace_link` | `addTraceLink(project, input)` | validate referenced Requirement ID when type is Requirement |
| `summarize_target` | `summarizeTarget(project, target?)` | target omitted means active target from `00.index.md` |
| `add_requirement` | `addRequirement(project, input)` | core generates ID, renders block, applies patch, validates result |

### 4.4 Resource strategy

`FR-MCP-009` resources should be computed views over the same core query layer.

| Resource URI | Source | Recommended content |
|---|---|---|
| `speckiwi://index` | index parser and target/scope maps | Markdown summary plus JSON-compatible summary metadata |
| `speckiwi://requirements/{id}` | `getRequirement` | normalized record and optional original Markdown |
| `speckiwi://targets/{target}` | `summarizeTarget` | release readiness summary for target |
| `speckiwi://scopes/{scope}` | scope map and filtered requirements | scope summary and requirement list |

Use the custom `speckiwi://` scheme already documented in the appendix. Resource reads must not accept arbitrary filesystem paths. If resource templates are implemented, template variables should be enum-like identifiers such as `{id}`, `{target}`, `{scope}`, not path fragments.

## 5. path/root safety와 structured error 전략

### 5.1 Root resolution and path boundary

The MCP server should build one immutable project context at startup:

1. Accept `--root <path>` or auto-detect upward using `.git` or `docs/spec/00.index.md`.
2. Resolve root with `fs.realpath`.
3. Verify `docs/spec/00.index.md` is inside root and readable.
4. Keep `rootRealPath` and `rootDisplayPath` in `ProjectContext`.

Every path operation should go through one core utility:

```text
resolveInsideRoot(rootRealPath, candidatePath, options)
```

Rules:

- reject absolute paths outside root;
- normalize relative paths against root;
- reject path traversal where `path.relative(root, target)` starts with `..` or is absolute;
- use `fs.realpath` for existing paths to catch symlink escapes;
- for paths that do not exist yet, validate the nearest existing parent and final normalized path;
- return display paths as POSIX-style relative paths where possible.

For SRS writes, the user/tool should not supply a direct file path. `scope` must map to the primary document in `00.index.md`, and that mapped document must pass the root boundary check.

### 5.2 Mutation safety

All mutation tools should use a common transaction-like flow:

1. parse current project;
2. validate input and target block/table/section;
3. prepare line-based patch in memory;
4. apply patch to an in-memory document copy;
5. run targeted validation or full validation on the modified copy;
6. if `dryRun`, return patch summary without writing;
7. write only after all checks pass;
8. re-read changed file and return normalized changed record.

The patch engine should preserve newline style and touch only required lines. For high-risk writes, use a temp file plus atomic rename where supported. If atomic rename conflicts with preserving file permissions, capture and restore mode metadata.

### 5.3 Error taxonomy

Recommended domain error shape:

```json
{
  "code": "status_transition_denied",
  "message": "Cannot mark requirement verified before all AC are checked and evidence exists.",
  "severity": "error",
  "file": "docs/spec/40.mcp-stdio-interface.srs.md",
  "line": 326,
  "requirementId": "FR-MCP-004",
  "diagnostics": []
}
```

Recommended codes:

| Code | Use |
|---|---|
| `not_found` | missing Requirement ID, scope, target, resource |
| `invalid_input` | domain-level schema/enum issue after MCP schema validation |
| `parse_error` | malformed SRS blocks preventing operation |
| `validation_error` | SRS validation failed |
| `status_transition_denied` | verified guard or illegal status transition |
| `path_outside_root` | root safety violation |
| `mutation_denied` | dry-run mismatch, missing section/table, ambiguous target |
| `conflict` | file changed between read and write, duplicate generated ID |
| `io_error` | read/write failure |
| `internal_error` | unexpected failure with sanitized message |

MCP mapping:

- invalid JSON-RPC request, unknown tool, or SDK-level schema mismatch: protocol error;
- valid tool call with missing Requirement ID, verified guard failure, validation failure, path denial: tool result with `isError: true`;
- missing resource: JSON-RPC resource error such as `-32002` with structured `data`;
- fatal server startup error: process exits with code `6` and writes explanation to stderr.

## 6. workflow/release evidence strategy

### 6.1 Evidence mutation

`add_verification_evidence` should append exactly one row to the target block's `#### Verification Evidence` table.

Evidence rules:

- `type`, `reference`, and `covers` are required.
- Evidence ID should be generated as `VE-{n}` by scanning existing evidence rows in the block.
- `covers` should accept `AC-1`, comma-separated AC IDs, or `all`.
- local file references must exist and resolve inside root.
- URL references should be syntactically valid but should not require network access during normal validation.
- never invent issue, PR, test, or file paths.

### 6.2 AC and status workflow

The implementation workflow should keep these state meanings strict:

| State | Required evidence posture |
|---|---|
| `planned` | no implementation claim |
| `in_progress` | implementation underway |
| `implemented` | code appears complete but verified evidence is incomplete |
| `verified` | all AC checked and at least one evidence row with non-empty reference |
| `blocked` | implementation or verification cannot proceed |
| `discarded` | requirement retained for history but not active |

Recommended agent flow:

1. `list_requirements` filtered by target/status/scope.
2. `get_requirement` before implementation.
3. after code/tests, `add_verification_evidence`.
4. `check_acceptance_criteria` for only verified ACs.
5. `update_status` to `implemented` or `verified` based on guard result.
6. `summarize_target` to review release readiness.

### 6.3 Release readiness summary

`summary --target` and `summarize_target` must share a core function. Recommended output fields:

```json
{
  "target": "v1.0.0",
  "statusCounts": {},
  "typeCounts": {},
  "blocked": [],
  "plannedOrInProgress": [],
  "implementedNotVerified": [],
  "criticalOrHighUnverified": [],
  "missingEvidence": [],
  "diagnosticsSummary": {
    "errors": 0,
    "warnings": 0,
    "byCode": {}
  },
  "ready": false
}
```

`ready` should be true only when there are no validation errors, no blocked items, no planned/in_progress items in the target, no implemented-not-verified items, and no critical/high unverified items. The SRS does not require automatic release tagging, so baseline tags remain documentation/workflow only.

### 6.4 CI and agent instruction

CI examples should be documentation artifacts, not hidden behavior:

- install Node.js LTS;
- install package dependencies;
- run `npm run build`;
- run `speckiwi validate --strict` or `npm exec speckiwi validate -- --strict`;
- optionally run `speckiwi summary --target v1.0.0 --json` and fail on `ready = false` only if release gate is explicitly desired.

`speckiwi init --agent-file` should append the appendix AGENTS/CLAUDE snippet without rewriting existing files. Duplicate insertion should be avoided with a marker or exact block detection.

## 7. `add_requirement` MCP 구현 전략

`FR-MCP-010` should be implemented as an adapter over `FR-NODE-008`.

### 7.1 Input contract

Required:

- `type`
- `scope`
- `target`
- `title`
- `requirement`
- `acceptanceCriteria`

Optional:

- `status`
- `priority`
- `tags`
- `risk`
- `stability`
- `verificationMethod`
- `rationale`
- `implementationNotes`
- `relatedDocs`
- `githubIssue`
- `evidence`
- `traceLinks`
- `research`
- `changeNotes`
- `dryRun`

`acceptanceCriteria` should be an ordered array of objects:

```json
[
  { "text": "필수 입력이 없으면 structured error를 반환한다.", "checked": false }
]
```

### 7.2 Core creation algorithm

1. Parse `00.index.md` and validate `scope` against Scope Map prefix.
2. Validate `target` against Target Map.
3. Map `type` to ID prefix using SRS-MD rules.
4. Scan all existing Requirement IDs in `docs/spec/**/*.srs.md`, including discarded requirements.
5. Generate next ID as `{TYPE_PREFIX}-{SCOPE_PREFIX}-{NNN}`.
6. Validate title format constraints and metadata enum values.
7. If `status` is omitted, default to `planned`.
8. If `status = verified`, require every AC checked and at least one evidence row with non-empty `Reference`.
9. Render a complete Requirement Block with required metadata and fixed sections.
10. Insert the block at the end of the scope document's `## 4. Requirements` section, immediately before the next H2 section.
11. Preserve existing newline style.
12. Validate the generated block or whole project before write.
13. Return generated ID, normalized record, target file, inserted line, and patch summary.

### 7.3 Failure cases that must not write

| Case | Error code |
|---|---|
| unknown scope prefix | `not_found` |
| unknown target | `not_found` |
| unsupported type | `invalid_input` |
| duplicate generated ID due to race | `conflict` |
| missing `## 4. Requirements` section | `mutation_denied` |
| `verified` without checked AC/evidence | `status_transition_denied` |
| local evidence outside root | `path_outside_root` |
| rendered block fails validation | `validation_error` |

### 7.4 Patch summary

Return a compact summary usable by both CLI and MCP:

```json
{
  "operation": "add_requirement",
  "dryRun": false,
  "file": "docs/spec/40.mcp-stdio-interface.srs.md",
  "generatedId": "FR-MCP-011",
  "insertedAfterLine": 825,
  "lineDelta": 42,
  "changedSections": ["Requirements"]
}
```

## 8. 통합 테스트 전략

### 8.1 Test fixture matrix

| Fixture | Purpose |
|---|---|
| valid project | all MCP read tools/resources |
| missing ID | `get_requirement`, mutation not_found |
| invalid metadata | `validate_spec` diagnostics |
| verified guard failure | `update_status`, `add_requirement` denial |
| CRLF SRS document | newline preservation |
| path traversal reference | root safety denial |
| discarded requirement ID | add_requirement must not reuse ID |
| high/critical unverified target | release readiness summary |

### 8.2 MCP stdio tests

Integration tests should spawn the built CLI:

```text
node dist/cli/index.js mcp --root <temp-fixture-root>
```

Then use either the official MCP client SDK or a small newline-delimited JSON-RPC harness to verify:

- initialize succeeds with name/version/capabilities;
- `tools/list` contains every required tool;
- read-only tools do not change fixture file hashes;
- mutation tools change only expected lines in copied temp fixtures;
- stdout contains no banners or logs;
- stderr logs do not break protocol;
- malformed tool input is rejected predictably;
- server exits cleanly on stdin close.

### 8.3 Tool behavior tests

| Tool | Required tests |
|---|---|
| `list_requirements` | filters, empty result, scope/type/status/tag combinations |
| `get_requirement` | includeMarkdown true/false, not_found |
| `validate_spec` | diagnostics shape and summary counts |
| `update_status` | legal status, illegal enum, verified guard, dryRun |
| `check_acceptance_criteria` | single AC, multiple ACs, all, missing AC |
| `add_verification_evidence` | VE ID generation, local file validation, table insertion |
| `add_trace_link` | Requirement reference validation, URL/doc trace |
| `summarize_target` | default active target, readiness blockers |
| `add_requirement` | ID generation, section insertion, verified guard, dryRun, duplicate/race guard |

### 8.4 Workflow tests

Workflow/release behavior should be tested at core level first and through MCP second:

- target with blocked requirement is not ready;
- target with planned/in_progress requirement is not ready;
- target with implemented but not verified requirement is not ready;
- target with critical/high unverified requirement is not ready;
- target with validation errors is not ready;
- verified requirements require checked AC and evidence;
- diagnostics summary includes error/warning counts and rule IDs.

## 9. 주요 리스크와 완화책

| Risk | Impact | Mitigation |
|---|---|---|
| MCP SDK version churn | adapter code breaks near release | keep SDK imports only in `src/mcp`; pin stable v1.x unless v2 is stable and selected |
| stdout contamination | MCP server unusable | ban `console.log` in MCP path; test stdout message stream |
| duplicate CLI/MCP logic | inconsistent behavior | all behavior goes through core service; adapter tests compare CLI and MCP outputs |
| Markdown rewrite diff | poor review quality | line-based patches only; snapshot minimal diff tests |
| path traversal/symlink escape | writes or reads outside root | `realpath` root checks; reject arbitrary resource paths |
| invented or invalid evidence | false verified status | local file existence checks; verified guard; no network-required evidence validation |
| race during mutation | duplicate IDs or lost edits | re-read before write; compare file hash/mtime; detect duplicate generated ID after patch |
| target/scope ambiguity | requirement inserted into wrong file | scope prefix is canonical; reject ambiguous full names |
| release summary overreach | tool becomes project manager | summary reports readiness facts only; no Git tag or PR automation |
| resource URI misuse | arbitrary file read | custom `speckiwi://` identifiers only; no file path resource template |

## 10. 구현 순서 제안

1. Foundation: align package metadata with Node LTS/TypeScript ESM, choose and pin MCP SDK line, add shared types for `RequirementRecord`, `Diagnostic`, `PatchSummary`, `DomainError`.
2. Core read path: implement root resolution, index parsing, SRS discovery, Requirement Block parser, normalized records, query filters.
3. Core validation: implement rule registry and diagnostics summary required by `validate_spec` and workflow release readiness.
4. Core mutation path: implement line-based patch engine, status/AC/evidence/trace mutations, dry-run, root-safe local reference validation.
5. Requirement creation: implement `FR-NODE-008` add requirement service with ID generation, block rendering, section insertion, validation, and patch summary.
6. MCP adapter: register stdio server, metadata, tools, resources, schema mappings, and structured error conversion.
7. Workflow/release: implement shared summary function, README/AGENTS/CI examples, baseline tag documentation.
8. Integration verification: add Vitest integration tests for CLI/MCP parity, stdio cleanliness, mutation minimal diff, path safety, and release readiness.

## 11. Open implementation decisions

| Decision | Recommendation |
|---|---|
| MCP SDK major version | Pin production-stable v1.x first; keep a small spike to validate v2 only when it is stable enough |
| Tool error representation | Use tool result `isError: true` for domain errors; protocol errors only for request/server protocol failures |
| Resource payload format | Return Markdown-readable text plus structured JSON where SDK supports it |
| Release readiness `ready` flag | Include a boolean, but keep criteria documented and deterministic |
| `add_requirement` insertion point | Use end of `## 4. Requirements` section, before the next H2, matching current SRS |

## 12. 완료 판단 기준

Implementation can be considered aligned with this research when:

- every MCP requirement from `IR-MCP-001` through `FR-MCP-010` maps to a tested adapter behavior;
- every workflow requirement from `FR-FLOW-001` through `OBS-FLOW-001` maps to docs, summary logic, or diagnostics output;
- CLI and MCP outputs are generated from the same core services;
- mutation tools fail without file changes on guard, validation, parse, and path errors;
- `add_requirement` uses the shared core mutation service and passes verified guard tests;
- integration tests demonstrate stdio protocol cleanliness and root boundary enforcement.
