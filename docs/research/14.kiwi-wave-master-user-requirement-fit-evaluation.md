# kiwi-wave-master 사용자 요구 적합성 평가 (라운드 1)

## 0. 평가 대상 요구

> "웨이브 마스터를 사용하여 **설계만 있다면** 기존 아키텍처를 개선하거나, **기존 구조를 해치지 않고** **구현을 멈추지 않고 끝까지 이어나가면서** 검증개선 루프로 **설계나 사용자 의도대로 모두 구현되어 있는지 확인**하고 완전하지 않으면 **개선을 반복**하여야 한다."

분해:

| ID | 요구 |
|---|---|
| R1 | 설계 문서 하나만으로 착수 가능 |
| R2 | 기존 아키텍처를 개선하거나, 최소한 기존 구조를 훼손하지 않음 |
| R3 | 구현이 멈추지 않고 끝까지 진행 |
| R4 | 검증-개선 루프가 **설계·사용자 의도** 대비 완전성을 확인 |
| R5 | 불완전하면 개선을 반복 |

## 1. 평가 방법

독립 서브에이전트 3기를 병렬 투입했다. 각 평가자에게는 위 요구 원문과 저장소 소스 경로만 주고, 메인 세션의 잠정 결론·다른 평가자의 산출은 전달하지 않았다.

| 축 | 대상 요구 | 결론 |
|---|---|---|
| A — 실행 연속성 | R3 | **불충족** |
| B — 설계·의도 충실도 | R1 · R4 · R5 | **불충족** |
| C — 기존 구조 보존 | R2 | **부분 충족** |

근거는 저장소 소스(`skills/claude/**`)로 한정했다. 설치된 런타임(`~/.claude/skills/`)은 구버전이라 근거에서 제외했다.

메인 세션이 기계적으로 교차 확인한 항목:

- `--create` / target 등록 mutation 을 문서화한 kiwi 스킬 — 저장소 전체 **0건**
- `kiwi-coder` 의 테스트 불가침 조항 — **0건** (`kiwi-tdd:22` §0.5 에만 존재하며 tdd work-mode 전용)
- `kiwi-review-fix-loop:467` — `--skip-regression` 부재 시 **영향 회귀만** 실행
- `kiwi-wave-master` 본문의 `--run` — **0건**

## 2. 사전 조건 (요구와 무관한 하드 블로커)

설치된 런타임 `~/.claude/skills/kiwi-wave-master/SKILL.md` 는 **169줄**로, 저장소 소스(337줄)의 `§2.1 run-root preflight`·`§5.5 웨이브 종료 상호검증`이 **없다**. `_shared/kiwi/waves-event.md` 도 런타임은 `1.0.0`, 소스는 `1.1.0` 이다.

즉 지금 `/kiwi-wave-master` 를 호출하면 검증개선 루프가 아예 없는 구버전이 실행된다. v2.4.2·v2.4.3 작업이 미커밋·미설치인 데서 온다. 아래 결함을 모두 고쳐도 **런타임 동기화(`speckiwi init -g`) 없이는 어느 것도 실제 실행에 반영되지 않는다.**

## 4. 종합 판정

세 축의 결론이 서로 다른 이유를 정리하면 결함의 구조가 드러난다.

- **R3(멈추지 않음)** 은 안전 게이트가 많아서가 아니라, **정상 흐름에 필요한 경로가 문서화되지 않아서** 깨진다 — target 등록 경로 부재(C2), `--run` 모순(H1), wave 내부 재개 부재(H7). 이들은 안전과 무관한 순수 누락이다.
- **R4(설계 대비 완전성)** 은 검증 계층이 약해서가 아니라 **분모가 SRS 로 고정되어 있어서** 깨진다. §5.5 는 SRS 대비로는 매우 엄격하지만(외부 분모 고정·add-only 교차반박·수정 없는 clean 라운드), 설계→SRS 사이의 유실은 원리적으로 볼 수 없다.
- **R2(기존 구조 보존)** 은 보호가 "테스트가 잡아준다" 에 걸려 있는데 **그 테스트를 지킬 규칙이 빠져 있다**(H9) 는 것이 핵심이다. 여기에 전체 스위트 미실행(H10)·기준선 부재(M2)가 겹친다.

교집합에서 나오는 결론: 게이트를 더 얹을 문제가 아니라, **분모를 설계까지 끌어올리고 · 정상 경로의 누락을 메우고 · 회귀 보호의 근거를 불가침으로 만드는** 세 가지가 필요하다.

## 5. 라운드 1 이후

본 문서는 라운드 1 평가의 고정 기록이다. 개선은 별도 서브에이전트가 CRITICAL → HIGH → MEDIUM → LOW 순으로 수행하고, 개선 후 새 평가자로 라운드 2 를 돌린다.
