## 1. Claude Code: `claude mcp add -s user`

### 1a. What it writes, and where — MEASURED + DOCUMENTED
- Command: `claude mcp add -s user kiwiisotest -- node "C:/x/bin/speckiwi" mcp`
  - stdout: `Added stdio MCP server kiwiisotest with command: node C:/x/bin/speckiwi mcp to user config` / `File modified: D:\Temp\ccmcp\home\.claude\.claude.json`, exit 0.
  - With `CLAUDE_CONFIG_DIR` set, the file is `<CLAUDE_CONFIG_DIR>\.claude.json`. Without it, the docs say `~/.claude.json`, which on Windows is `%USERPROFILE%\.claude.json` (the real one exists at `C:\Users\beom\.claude.json`). On the first write it also makes a backup under `<config>\backups\.claude.json.backup.<ts>`.
  - The entry goes into the **top-level** `mcpServers` map, not into `projects[<path>]`:
    ```json
    "mcpServers": { "kiwiisotest": { "type": "stdio", "command": "node", "args": ["C:/x/bin/speckiwi","mcp"], "env": {} } }
    ```
  - Local scope (the default `-s local`) also lives in `~/.claude.json`, but under that project's path (docs: "stores it in `~/.claude.json` under that project's path").
- Docs: https://code.claude.com/docs/en/mcp ("MCP installation scopes": User → stored in `~/.claude.json`); https://code.claude.com/docs/en/settings (`~/.claude.json` holds MCP server configurations; on Windows `~/.claude` = `%USERPROFILE%\.claude`; `CLAUDE_CONFIG_DIR` relocates the home-directory files).
- Running `claude mcp add -s user` again with an existing name: `MCP server kiwiisotest already exists in user config`, **exit 1**. It does not overwrite. MEASURED.
- Windows launchers: `claude mcp add -s user kiwicmd -- speckiwi mcp` (the npm `.cmd` shim) and `... -- npx -y speckiwi mcp` both reported `✔ Connected` in `claude mcp get`, so `cmd /c` is not needed in 2.1.308. MEASURED.

### 1b. Detecting an existing user-scope `speckiwi` — MEASURED
- `claude mcp get <name>`:
  - When the name is missing: `No MCP server named "kiwiisotest". Run \`claude mcp add\` to add one.`, **exit 1**.
  - When it is present: exit 0, with output that includes `Scope: User config (available in all your projects)`, `Status: ...`, `Type: stdio`, `Command:`, `Args:`.
  - The only option is `-h`. There is no `--json` and no `--scope` (`claude mcp get --help`).
  - It **health-checks the server, which spawns it**. The probe log showed one spawn for each `get` or `list`.
- `claude mcp list`: always exits 0. It prints `name: command args - ✔ Connected` per server and also spawns every approved server. Help text: "Unapproved .mcp.json servers are shown as ⏸ Pending approval and not connected to".
- **Caveat (MEASURED):** when the same name exists in user scope and in the project `.mcp.json`, `claude mcp get`/`list` showed the **User** entry, even after the project entry was approved via `.claude/settings.local.json` `enabledMcpjsonServers`. `list` also printed a `[Conflicting scopes]` diagnostic. The real session (`claude -p`) launched the **project** entry instead (probe tag `project`). So `mcp get` does not tell you which entry a session will use.
- A detection approach that spawns nothing: parse `${CLAUDE_CONFIG_DIR ?? homedir}/.claude.json` and check that top-level `mcpServers.speckiwi` exists. The path is MEASURED with CLAUDE_CONFIG_DIR set. The file format is not a documented contract (docs: "Claude Code writes it for itself; you don't need to edit it"). Reading it is fine. Writing it by hand is not advisable.

### 1c. Precedence when the same name is in project `.mcp.json` and user scope — DOCUMENTED + MEASURED
- Docs (https://code.claude.com/docs/en/mcp, "Scope precedence"): "Claude Code connects to it once, using the definition from the highest-precedence source. The entire server entry from that source is used; fields are not merged across scopes. 1. Local scope 2. Project scope 3. User scope 4. Plugin-provided servers 5. claude.ai connectors." Duplicates across the three scopes are matched **by name**.
- MEASURED: with user `kiwiisotest → cwdprobe.js user` and project `.mcp.json kiwiisotest → cwdprobe.js project`, `claude -p` (no login) spawned only the `project` one.
- Consequence for 4.1.1: a leftover project `.mcp.json` `speckiwi` key **shadows** the user-scope registration. For example, this repo's `.mcp.json` still says `npx -y speckiwi mcp`, which beats a user-scope entry. That is why `upgrade` has to remove the project key.

### 1d. Working directory of a user-scope stdio server — MEASURED (with one caveat); DOCUMENTED only via CLAUDE_PROJECT_DIR
- `claude -p "say hi"` started in `D:\Temp\ccmcp\proj\sub` (git repo root `D:\Temp\ccmcp\proj`). It failed at "Not logged in" but had already spawned the MCP servers. Probe result: `cwd = D:\Temp\ccmcp\proj\sub`, `CLAUDE_PROJECT_DIR = D:\Temp\ccmcp\proj\sub`.
  - So the server's cwd is **the directory the session started in, not the git root**. The same holds for a project `.mcp.json` found in a parent directory: started from `sub`, the project server also ran with cwd=`sub`.
  - `claude mcp list`/`get` spawn with cwd = the invocation directory.
- Caveat: the session measurement ran unauthenticated, because the isolated config had no login. I did not run an authenticated session, since that would write to the real `~/.claude.json`. The spawn happened before the auth failure, so it should be the same code path, but that is not proven.
- Docs: no statement about cwd. The only related text: "Claude Code sets `CLAUDE_PROJECT_DIR` in the spawned server's environment to the project root, so your server can resolve project-relative paths without depending on the working directory." It also notes that referencing it in `command`/`args` of a user-scoped entry requires `${CLAUDE_PROJECT_DIR:-.}` syntax. MEASURED: "project root" in practice meant the start directory (`sub`), not the git top level.
- Impact on speckiwi: the MCP server's `server-cwd-discovery` gets a subdirectory when the user starts Claude there. That works if discovery walks up to `docs/spec/00.index.md`; check `src/mcp/workspace-root.ts`. `CLAUDE_PROJECT_DIR` is an extra signal the server could read.

### 1e. Is a `cwd` setting available? — UNKNOWN (not documented)
- `claude mcp add --help` has no `--cwd` option (options: `--callback-port, --client-id, --client-secret, -e/--env, -H/--header, -s/--scope, -t/--transport`).

## 2. Claude Code skills, same name in `<project>/.claude/skills` and `~/.claude/skills` — DOCUMENTED

https://code.claude.com/docs/en/skills, "Resolve skills that share a name":
> Two of enterprise, personal, and project | Enterprise over personal, and personal over project. With `deploy` in both `~/.claude/skills/` and the project's `.claude/skills/`, `/deploy` runs the personal one

Only one copy loads, and the **personal (global) copy wins**. So once global skills are installed, project copies are dead weight: a newer project copy is silently shadowed by an older global one. Nested `<subdir>/.claude/skills` is different: both load, as `/subdir:name`. Project skills are searched from the start directory up to the repo root, or the worktree root in a linked worktree.

  2. speckiwi's global Codex destination `$CODEX_HOME/skills` is the **deprecated** location. The documented one is `~/.agents/skills`. Both are still read today; the real machine already has `C:\Users\beom\.codex\skills\kiwi-*`.

### 3c. MCP server working directory / `cwd` key — DOCUMENTED + SOURCE + MEASURED

### HIGH — design risk in rule (b): do not let the block auto-run `speckiwi upgrade`
In 4.1.1, `speckiwi upgrade` is planned to remove the project's skill copies and its `.mcp.json` speckiwi key once it sees a global install. That global install is on the agent user's machine. `.mcp.json` and project skill dirs are usually committed and shared, so an agent that upgrades unasked because its CLI is newer would strip the MCP registration and skills from every teammate who has no global install. The rule therefore says "report and propose, run only when the user agrees" (wording above). The alternative is to make upgrade's removal step opt-in. Either way, the decision should be explicit in the 4.1.1 SRS.
