# 윈도우에서 kiwi-orchestrator 가 락에 걸리는 문제 조사

작성 2026-10-21. 환경: Windows 11 Enterprise 10.0.26200, Node v24.16.0 (libuv 1.52.1), Git 2.48.1.windows.1, speckiwi 4.0.0 (저장소 `dist`, 작업 트리 기준). 저장소 파일은 고치지 않았다. 재현은 세션 스크래치 패드 `...\scratchpad\lock\` (C:, NTFS) 에서 했고, `D:\Temp\lockrepro` (exFAT) 는 파일 의미론 비교에만 썼다. 재현 스크립트는 모두 `C:\Users\beom\AppData\Local\Temp\claude\C--Work-git--Snoworca-speckiwi\5cbf0665-779a-434f-94da-4eaaef0b85e3\scratchpad\lock\` 에 있다.

## 0. 결론 먼저

"가끔 락에 걸려 멈춘다"를 설명하는 원인은 하나가 아니라 넷이다. 가능성이 높은 순서로 적는다.

| 순위 | 원인 | 윈도우 전용인가 | 증거 강도 | 멈춤 길이 |
|---|---|---|---|---|
| 1 | **run lock 의 named-pipe fence 가 살아 있는 MCP 서버에 남는다.** MCP 로 `lock` 한 세션이 살아 있는 동안, 다른 세션이나 CLI 가 `run unlock` 으로 lock 파일을 지워도 그 뒤의 `run lock` 이 `owner: null` 로 계속 거절된다. `run status` 는 `holder: null` 을 보고하므로 원인을 찾을 길이 없다 | **예** (fence 는 win32 에서만 동작) | **재현함** (E4, E4b) | 그 MCP 서버(= 그 Claude/Codex 세션)가 끝날 때까지 |

## 2. 윈도우 고유 실패 양상 (코드 대조)

### 2.1 named-pipe fence 가 파일 lock 과 따로 산다 — 원인 1

`acquireKernelFence` (`src/core/lock/exclusive-lock.ts:160-182`) 는 win32 에서만 `\\.\pipe\<namespace>-<sha256(lock 경로)>` 로 `net.Server.listen` 한다. 이미 누가 듣고 있으면 `EADDRINUSE` → `null` → 취득은 **파일을 보지도 않고** `held` 를 낸다(`:455-459`). 보유자를 `readHolderAt` 으로 읽는데, 파일이 없으면 `holder` 가 비어 `owner: null` 이 된다.

fence 는 `releaseExclusiveLock` 이 **같은 프로세스 안의 capability** 로 불릴 때만 닫힌다(`:661`). 그런데

- MCP 다리는 CLI `main` 을 서버 프로세스 안에서 돌린다(`src/mcp/tools/read-tools.ts:145-156`). 그래서 MCP 로 `lock` 하면 fence 가 MCP 서버 수명 동안 열려 있다(`server.unref()` 는 프로세스 종료만 막지 않을 뿐 닫지 않는다).
- `run unlock` 과 `run abort` 는 `releaseHeldRunLock` (`run-lock.ts:182-192`) 으로 간다. 자기 프로세스에 capability 가 있으면 그것을 풀고, 없으면 **파일만 지운다**(`rm(lockPath, {force:true})`). 다른 프로세스가 쥔 fence 는 건드릴 수 없다.

그래서 "다른 프로세스가 MCP 로 잡은 lock 을 CLI 나 다른 세션의 MCP 로 푼다"는, FR-NODE-197 AC-4/AC-7 이 지원한다고 적은 바로 그 동작이 윈도우에서는 반쪽만 된다. 파일은 사라지고 fence 는 남는다. 이후 상태는 이렇다.

- `run status` → `holder: null` (파일이 없으므로)
- `run lock` (CLI 든 MCP 든) → `orchestrator-run-lock-held`, `owner: null`
- 스킬 §3.1 은 `holder` 가 `null` 이면 해제 대상에서 **제외**하라고 지시한다. 그러니 에이전트는 풀 수단도 없다.

FR-NODE-207 AC-7 과 Implementation Notes 는 "MCP 서버 프로세스 두 개의 경합은 측정하지 않았다"고 스스로 적어 두었다. E4b 가 바로 그 경우다. 이 머신에는 지금 `speckiwi mcp` 노드 프로세스가 50 개 떠 있다(부모 cmd.exe, 그 위 claude.exe 26 · codex.exe 16 · node.exe 8). 장수 MCP 서버가 여럿 공존하는 것이 평소 상태라는 뜻이다.

### 2.2 pid 생존과 pid 재사용 — L3 와 레거시 L2

`processIsAlive` (`exclusive-lock.ts:140-148`) 는 `process.kill(pid, 0)` 이 `ESRCH`·`EINVAL` 이 아니면 살아 있다고 본다. 윈도우는 pid 를 빨리 재사용한다. E8 에서 죽은 프로세스 20 개의 pid 하나가 `cmd /c exit` 428 번(8.2 초) 만에 다른 프로세스에 다시 배정됐다. `npm test` 한 번이 수천 개의 프로세스를 띄우는 이 저장소에서는 짧은 시간이다. lease 가 없는 sentinel(L3 전부, 그리고 FR-NODE-207 이전에 쓰인 L2 레거시)은 보유자가 죽고 그 pid 가 재사용되면 무관한 프로세스가 끝날 때까지 "보유 중"이다. 다만 L3 는 정상 경로에서 한 번의 append 동안만 잡히므로 이것은 **크래시 + 재사용**이 겹칠 때만 생긴다(**가설**, 결정적 재현은 안 했다).

L1 은 pid 를 아예 보지 않는다. 죽은 보유자도 TTL 60 초가 끝날 때까지 기다리게 한다(E1).

### 2.3 종료 처리가 돌지 않는 종료

Claude Code 가 Bash 를 시간 초과로 끊거나 서브에이전트를 멈추거나, 사용자가 터미널을 닫으면 윈도우에서는 `TerminateProcess` 와 같다. `finally`·exit 핸들러가 돌지 않는다. 그래서

- L1: 60 초 정지(E1, `taskkill /F` 로 재현).
- L1: `open(wx)` 와 JSON 기록 사이(중앙값 1.7 ms, p95 2.6 ms, E9)에 죽으면 빈 파일이 남고 **영구 정지**(E2). `srs-lock.ts:118-124` 의 `createLockFile` 은 L2/L3 의 `publishExclusive` 와 달리 실패 시 파일을 지우지 않는다. guard 파일도 같다.
- L2: 12 시간.
- L5: 30 분 HALT (LLM 의 "finally" 는 프로세스가 죽으면 없다).

### 2.4 EPERM / delete-pending

E5 결과: **NTFS(C:)** 에서 Node 24 의 `rm` 은 다른 프로세스가 연 파일도 이름을 즉시 지운다(POSIX 삭제 의미). 지운 뒤 `readFile` 은 `ENOENT`, 다음 `open(wx)` 는 성공했다. **exFAT(D:)** 에서는 같은 순서에서 `readFile` → `EPERM`, `open(wx)` → `EPERM` 이었다. 그러니 FR-NODE-203 이 기록한 "delete-pending 이 EPERM 을 낸다"는 파일 시스템에 따라 갈린다. D: 같은 exFAT·네트워크 드라이브에 저장소를 둔 사용자는 더 자주 맞는다.

그래도 NTFS 에서 EPERM 은 났다. E6 의 SRS lock 부하에서 `withSrsMutationLock` 밖으로 `EPERM` 예외가 1000 번 성공당 0~6 건 튀어나왔고, 출처는 전부 guard 파일의 `open(wx)` 였다(E6 의 스택). L1 은 `createLockFile` 의 `open(wx)` 가 `EEXIST` 가 아닌 오류를 내면 그대로 던진다(`srs-lock.ts:141`). MCP 에서는 도구 오류로 보인다. 같은 부하에서 `unreadable-lock` 판정이 1000 성공당 45 건 나왔다. 이것은 "누군가 lock 을 쥐고 있다(owner unknown)"로 보고되는 **거짓 거절**이다. 막 만들어져 아직 비어 있는 파일을 읽거나, EPERM 으로 읽지 못한 경우다.

### 2.5 `git worktree remove` 와 열린 핸들

E7 결과: Node 가 연 파일 핸들은 `remove --force` 를 막지 않았다(Node 는 FILE_SHARE_DELETE 로 연다). 반면 **다른 프로세스의 cwd 가 워크트리 안이면** `git worktree remove --force` 가 `error: failed to delete '…/wt2': Permission denied`, exit 255 로 실패했다. git 은 이미 등록을 지운 뒤라 `worktree list` 에는 없고, 다시 하면 `is not a working tree` 로 실패하며, 빈 디렉터리는 남는다. 스킬의 `release-lane` 복구는 "`git worktree remove` 를 다시 한다"뿐이라 이 상태를 설명하지 못한다. lane 워커의 셸·vitest 워커·에디터·백신이 cwd 나 비공유 핸들을 쥐면 생긴다.

잠긴 워크트리는 `remove` 도 `remove --force` 도 거절하고 `remove -f -f` 를 요구한다(E7 앞부분).

### 2.6 대소문자·긴 경로

- 대소문자: L2/L3 의 fence 이름은 `canonical()` 이 win32 에서 소문자로 바꾼 경로로 만든다(`exclusive-lock.ts:111-114`). 출력 경로에 `C--work-git` 과 `C--Work-git` 이 섞여 나오는데(Claude 가 만든 스크래치 경로 자체가 그렇다) 같은 fence 로 수렴하므로 문제를 만들지 않았다. L1 은 `path.join(root, "kiwi/.srs.lock")` 으로 같은 파일을 가리키므로 대소문자 영향 없음.
- 긴 경로: 연구 문서 `docs/research/kiwi-orchestrator/02.worktree-parallelism-feasibility.md` §7.1 이 `core.longpaths` 미설정, 최악 188/260 자로 측정해 두었다. 이번 조사에서 락과 엮인 긴 경로 실패는 보지 못했다.

| `speckiwi doctor` | — | 어떤 lock 도 점검하지 않는다 |
| 스킬 | P.5 거절 시 critical gate 로 멈춤 | 거절을 만났을 때 사용자에게 제시할 복구 절차(status 로 보유자 확인 → 이전 run 이면 unlock) 가 없다. halt 는 lock 을 풀지 않는다 |

## 5. 원인별 최소 수정

### 원인 1 — 유령 fence (FR-NODE-197, FR-NODE-207 소유. 새 요구로 기록하는 것이 맞다)

도구 쪽, 가장 작은 것부터:

1. **fence 를 run lock 에서 취득 시점에만 쓴다.** run lock 은 lease 로 다스리도록 바뀌었으므로(FR-NODE-207) fence 를 잡은 채 `activeCapabilities` 에 보관할 이유가 없다. `acquireExclusiveLock` 에 "취득 뒤 fence 를 바로 닫는다" 선택을 두고 run lock 만 켜면, 파일이 유일한 진실이 되고 `unlock` 이 완전한 해제가 된다. artifact lock(L3)은 지금처럼 둔다.
2. 그게 싫다면 최소한 fence 가 `EADDRINUSE` 인데 **파일이 없을 때** 거절 사유를 따로 낸다(예: `holder: null, reason: "fence-held-by-live-process"`). 지금은 "보유자 없음"과 "보유자 모름"이 같은 `owner: null` 이다.

스킬 쪽: §3.1 에 "`lock` 이 `owner: null` 로 거절되고 `status` 가 `holder: null` 이면, 이전에 MCP 로 lock 을 잡았던 Claude/Codex 세션이 아직 열려 있다는 뜻이다 — 그 세션을 닫거나 그 세션에서 `unlock` 을 부르라"를 적는다.

### 원인 2 — 12 시간 lease 와 halt (FR-NODE-207, FR-NODE-197, FR-FLOW-170, IR-CLI-085 소유)

도구 쪽:

1. **거절 응답에 해제 방법을 싣는다.** `orchestrator-run-lock-held` 에 holder 의 `pid`·`acquiredAt`·`lease_expires_at` 과 `speckiwi orchestrate run unlock --json` 안내 한 줄. 이것만으로 "가끔 막힌다"가 "명령 하나로 푼다"가 된다.
2. `run status` 에 `leaseExpiresAt` 과 `pidAlive`(같은 host 일 때)를 더한다. 판정에는 쓰지 않고 보고만 한다(FR-NODE-207 의 결정을 되돌리지 않는다).

스킬 쪽:

1. `§V.halt` 가 P.5 lease 를 어떻게 하는지 정한다. halt 는 재개를 전제하므로 풀지 않는 것이 맞을 수 있다. 그렇다면 halt 보고에 "이 run 을 버리려면 `run abort`, 이어 가려면 `--resume`" 을 반드시 적게 한다.
2. P.5 거절 시: `status` 로 보유자를 읽어 사용자에게 보여 주고, 그 보유자가 이전에 버려진 run 인지 묻는 절차를 둔다. `--auto` 에서도 이 게이트는 사용자 결정이므로(0.G) 질문이 구체적이어야 한다.

### 원인 3 — SRS mutation lock (REL-NODE-005, IR-CLI-038, FR-MCP-032 소유, REL-NODE-008 AC-6 관련)

도구 쪽, 각각 독립적으로 작다:

1. **해제가 guard 를 못 잡으면 짧게 재시도한다**(`srs-lock.ts:242`). guard 는 수십 ms 만 잡히므로 15 ms 간격 수백 ms 로 충분하다. 또는 해제는 guard 없이 "내 requestId 인 경우에만 rename 후 삭제"로 한다(L2/L3 의 `quarantine` 패턴과 같다).
2. **빈·깨진 lock 을 mtime grace 뒤 회수한다.** L2/L3 의 `TORN_SENTINEL_GRACE_MS` (5 초) 규칙과 같게. symlink 거절은 유지한다.
3. `createLockFile` 이 쓰기 실패 시 만든 파일을 지운다(`publishExclusive` 와 같게, FR-NODE-177 의 규칙).
4. `open(wx)` 의 `EPERM` 과 lock 읽기의 `EPERM` 을 "held"로 읽는다(FR-NODE-203 과 같은 처리).
5. 선택: mutation 이 바로 실패하지 말고 몇 초 기다리는 옵션. 병렬 wave 에서 거절 대부분이 정상 경합이다.
6. 진단: `SRS_LOCKED` 메시지에 "lock 파일이 비었거나 깨졌다 → `kiwi/.srs.lock` 을 지워도 된다(보유자가 없을 때)"를 넣고, `doctor` 가 lock 잔존을 점검한다.

### 원인 4 — 워크트리 잠금 (전용 요구 없음. 새 요구 후보)

스킬 쪽(`parallel-waves.md`, `run-ledger.md` `dispatch-lane`·`release-lane`, `worktree-lane.md:116`):

1. "`locked … (pid N)` 이면 살아 있다"를 "`locked … (pid N)` 이고 **그 pid 가 살아 있으면**"으로 바꾼다. 윈도우에서는 `tasklist /FI "PID eq N"` 또는 `node -e "process.kill(N,0)"`. 죽었으면 `git worktree unlock` 뒤 수확/재-dispatch 판정으로 간다.
2. `release-lane` 에 실패 처리를 적는다: `Permission denied` 면 그 디렉터리를 cwd 로 쓰는 프로세스(셸·vitest·에디터)를 먼저 끝내고, git 등록이 이미 사라졌으면(`is not a working tree`) 남은 빈 디렉터리만 지운 뒤 `git worktree prune`.
3. git `index.lock`: 동시에 git 프로세스가 없음을 확인한 뒤에만 지운다는 한 줄을 run 복구 절에 둔다.

### kiwi-pm `pm.lock` (FR-FLOW-113 AC-5 는 위치만 다룬다. 전용 요구 없음)

스킬 쪽: 같은 host 판정에 pid 생존 확인을 더한다(죽은 pid 면 30 분을 기다리지 않고 회수). `started_at` 이 없는 파일은 mtime 으로 판정한다고 적는다. `coder.lock` 문장은 남은 문장인지 확인한다.

## 6. 한계와 남은 측정

### 6.1 하지 않은 것

- 실제 kiwi-orchestrator run 을 처음부터 돌려 멈춤을 재현하지는 않았다. 각 락을 따로 재현했다.
- 사용자 머신의 실제 사고 로그(어느 게이트·어느 메시지에서 멈췄는지)는 없다. 위 순위는 재현 가능성과 노출 빈도로 매긴 추정이다. 사용자가 멈춘 지점의 출력(`gate` 값, `owner` 가 null 인지, `SRS_LOCKED` 인지, 아니면 아무 출력 없이 기다리는지)을 주면 원인을 하나로 좁힐 수 있다.
- 백신(Defender)·인덱서·OneDrive 가 비공유 핸들을 쥐는 경우는 재현하지 않았다.
- L3 의 pid 재사용 고착은 결정적으로 재현하지 않았다(재사용 속도만 쟀다).
- POSIX 는 재지 않았다.

### 6.2 이번에 쓴 원시 출력

`scratchpad\lock\e6-run2.out`, `e6-r1.out`~`e6-r4.out`(+ `.err`) 에 E6 의 원시 결과가 있다.

### 6.3 E6 의 해석 한계

- 6 번 중 3 번(A · C · F) 61 초 정지. C 와 F 는 회수 기록(SRS-W068)이 lock 의 주인을 남겼고, 둘 다 실행 내내 살아 있던 워커였다. 그래서 "해제가 일어나지 않았다"는 재현된 사실이다.
- 해제가 빠진 분기가 guard 충돌인지 해제 시 읽기 실패인지는 계측하지 않았다. 둘 다 같은 함수(`withSrsMutationLock` 의 `finally`)이므로 수정 위치는 같다.
- 부하는 실제보다 세다(빈 mutation, 5~15 ms 간격). 실제 병렬 wave 는 mutation 이 훨씬 드물다. 그러니 실제 빈도는 더 낮다. 다만 한 번 나면 그 60 초 동안 모든 세션의 SRS mutation 이 거절되고, 에이전트가 이를 "락에 걸렸다"고 보고하기에 충분하다.
- 6 번 모두 끝난 뒤 `kiwi/.srs.lock` 과 guard 는 남지 않았다(영구 잔존은 아님).
