**그래프의 저작·검증·동결까지는 있고, 그래프의 병렬 실행은 없다.**

## 1. 병렬 실행 — 가장 중요한 축의 확정 판정

판정: **분석은 완전, 실행은 부재.** 독립 반증 3기(코드·요구·테스트 관점)가 전부 반증에 실패했고, 오히려 판정을 강화하는 증거를 추가했다.

- 스킬 스스로 첫 문단과 §10 에서 직렬을 선언한다 — "벽시계 단축을 제공하지 않는다" (`kiwi-orchestrator/SKILL.md:12,744`)
- `src/core/orchestrator/**` 전체에 `Promise.all`/`allSettled`/`race`/worker_threads **0건** (반증 1)
- 테스트 표면의 유일한 동시성은 run-lock 상호배제 테스트 — 병렬 실행의 반대 증거 (반증 2)
- `2.6.0-phase2-parallel-lanes` 는 Target Map 에 **completed** 로 표시되지만(`00.index.md:72`), 승인된 요구 10건은 전부 주변 인프라(replay 큐·워크트리 역할 게이트·.gitignore)다. **비차단 dispatch·join·loop L·per-lane merge 는 0건** (반증 3, 요구 전수)
- 코드가 라벨을 직접 반박한다: `orchestrate.ts:101` 주석 "phase 2 가 완료되면 비어 있다" — 그 아래 :105 에 `lane audit|harvest|release|status` 4행이 여전히 미등록
- `--lanes N` 은 동시성이 아니라 **공개되는 분할표의 stage 당 lane 개수** 상한이다. 초과분은 연속 stage 로 쪼개진다(`lane-plan.ts:238`). 실측: 인자 검증 자체가 없고(`orchestrate.ts:1370` `Number.parseInt` 무검증) `--lanes 9999` 는 통과 — 본문의 "최대 8"은 도구가 강제하지 않는다. `--lanes abc` 의 거동은 **입력 의존적**이다(§13 검토 H-2 재실측): lane 이 형성되는 계획에서는 `lane-plan-incomplete` 라는 원인을 가리키지 않는 진단으로 실패하고, **epilogue-only 계획에서는 조용히 통과한다**
- phase 1 에서 실제로 병렬 spawn 되는 것: intake 조사자 3기(연구), kiwi-coder 내부 Sonnet×2(검증). **구현 단위 병렬은 0**
- `kiwi-pm` 은 병렬 Task spawn 을 **Out of Scope (v0.1)** 로 명시하고 v0.2 후보로 적어 두었다(`kiwi-pm/SKILL.md:1210,1219`)

**함정 (병렬을 켤 때 첫 스텝에서 깨진다):** §18 이 지시하는 `orchestrate preflight --lane-plan <lanes.lock.json>` 은 실제 `lanes.lock.json` 형식과 비호환이다 — 실측: `--lane-plan is not a lane plan …: lanes.writeSet is not a list of paths` 로 거부. 또한 `lanes.lock.json` 의 경로가 세 곳(§1.1 / CLI 기본값 / §18)에서 전부 다르다.

## 2. 그래프는 저작되고 검증되지만 스케줄링에 쓰이지 않는다 (G3)

사용자가 말한 "그래프 엔지니어링"의 그래프는 이미 존재한다 — planner 사이드카의 `phase.depends_on` + `task.depends_on_task` 2층 DAG, `validator.mjs` C16/C24 가 순환·참조 무결성을 실제로 검사한다. 그러나:

- `kiwi-pm` 은 그래프를 **순서 제약으로만** 소비한다 (독립 Task 동시 실행은 v0.2 후보)
- 오케스트레이터 lane 플래너는 `depends_on_task` 를 **순환 탐지에만** 읽고, 실제 분할은 **write-set 충돌 그래프**로 한다 (`lane-plan.ts:113-135`)

즉 **그래프 저작 ○ / 그래프 검증 ○ / 그래프 실행 ×.**

## 3. 산문 계약 vs 기계 강제 — 이 감사의 반복 패턴

거의 모든 축에서 같은 구조가 나왔다: 스킬 본문의 서술은 상세하고, 그 서술이 요구(FR-FLOW-*)로 고정되어 있으며, 검증 테스트는 **스킬 마크다운 텍스트에 대한 정규식 매칭**이다. 런타임 강제는 별개 문제다.

**기계가 실제로 강제하는 것** (코드 호출자 확인):
- 라우팅 커널 `computeRoute` + rung 재계산 금지(`route-lock.ts:169`), D4 임계
- freeze lock 의 키 존재 + sha256 내용주소화
- 검증 라운드 산술: cap·streak·분모 일치·수정 라운드 금지·회귀 부분집합 (`verification-gate.ts`)
- lane 계획: 3분할 파티션 불변(`assertLanePlanPartition`), 비-코드 → epilogue 라우팅 (FR-NODE-147, 27/27)
- `decideAutoGate` — 테스트 전용이 아니라 CLI/MCP 런타임 호출자 실재 (`orchestrate.ts:1758`)

**어휘에만 존재하고 발화자가 없는 게이트** (사문): `non-code-write-set-refused` · `unknown-write-set-refused` · `unmarked-normative-prose` · `design-intake-insufficient` · `serial-unit-failed` · `partition-review-unrecorded`. 호출자 0 인 커널 export 11개 (`scanProse`, `evaluateSerialUnitGate`, `computeRunProgress` 등).

실측 구멍 둘: `journal append` 는 **verb 를 검사하지 않는다** (`verb:"intake-batch"` 통과, `abort_gate` 는 어휘 거부 — 비대칭). 게이트의 critical 여부는 도구가 판정하지 않고 **호출자가 boolean 으로 선언**한다 (`orchestrate.ts:732`).

> 이 절의 발견은 `docs/next/2026-08-02.orchestrator-phase1-state.md` 와 §12 Release Residue 가 이미 인정한 상태의 재확인이다 — 새 결함이라기보다 "동결된 미충족"의 목록화다.

## 5. 지금 도구로 가장 가까운 조합

## 6. 요구 승격 후보 (결정 대기 — 여기서 구현하지 않는다)

우선순위는 사용자가 원한 것과의 거리 순.

1. **이슈 배치 intake** — "여러 이슈를 받아 분류·순서화" 는 전 스킬 공백(G7). 새 진입 표면이거나 orchestrator intake 의 복수화
2. **DAG 기반 병렬 dispatch** — 그래프는 이미 있으므로(G3) 실행기만 문제. kiwi-pm v0.2 후보(독립 Task 병렬 spawn)와 phase2 lane 실행 중 어느 층에서 여는지가 설계 결정
3. **인도 연결** — 오케스트레이터 계열 종료 시 commit-auto-pr 로의 명시적 연쇄 또는 next_hint (G1). 자동 연쇄 금지는 의도된 설계이므로 "금지 유지 + 안내 강화"와 "옵트인 연쇄" 중 결정 필요
4. **`computeRunProgress` 배선** (G5) — 커널 존재, verb 만 없음. 소규모
5. **사문 게이트 정리** — 발화자 없는 게이트 6개는 스킬 자신의 규칙("술어 없는 게이트 선언은 생략보다 나쁘다", SKILL.md:49) 위반. 배선하거나 표에서 제거하거나, §12 Release Residue 처럼 명시 이월
6. `--lanes` 인자 검증, `lanes.lock.json` 경로 3원화 해소, `--lane-plan` 형식 비호환 (병렬을 켜기 전 선행 수리)

# II부 — 하네스 설계 연구 (2026-08-19, 서브에이전트 3기 병렬)

> I부(§0~§7) 감사가 확정한 갭 위에서, 사용자가 원하는 "요구사항 또는 여러 이슈만 받아 오케스트레이터 역할을 하는 하네스"의 설계를 서브에이전트 3기가 독립 조사했다. 세 보고서는 §9~§11 에 **원문 그대로** 실었고 heading 만 한 단계 내렸다. I부와 마찬가지로 미검증 작업 노트이며, file:line 인용은 조사 시점(2026-08-19, feat/2.3.0.1)의 것이다.

## 8. I부 판정의 정정 3건 (research-graph 실측)

연구 B 가 재현으로 I부의 판정 셋을 정정했다. I부 본문의 해당 자리에도 표시해 두었다.

1. **`--lanes abc` (I부 §1) — 거동은 입력 의존적이다.** 인자 검증이 없는 것은 사실이다(`orchestrate.ts:1370` `Number.parseInt` 무검증). 결과는 계획 모양이 정한다 — lane 이 형성되면 NaN 이 빈 stage 를 만들고 `assertLanePlanPartition` 이 `lane-plan-incomplete` 라는 **원인을 가리키지 않는 진단**으로 실패시키고, lane 이 하나도 형성되지 않는 계획(epilogue-only)에서는 `splitByCap` 이 호출되지 않아 **조용히 통과한다**(§13 검토 H-2 가 두 입력으로 재실측). `--lanes 9999` 통과는 맞다. N4 수리의 수용 테스트를 "abc 가 실패하는지"로 잡으면 epilogue-only 계획에서 green 이 나는 잘못된 게이트가 된다.
2. **G8 "중간 재계획 불가" — 과장.** 합법 경로 둘이 명문화되어 실재한다: `amend-design`(wave 당 2회, append-new-artifact 규칙) + wave 추가(run 당 3회, §0.5 가 재분해가 아니라고 명시). 실제 갭은 **다중 lane 이 동시에 서로 다른 설계 항목을 반증하면 상한 2가 즉시 소진되는 케이스의 처리 부재**다(연구 B N6).
3. **"phase2 completed 는 주변 인프라뿐" (I부 §1 반증 3) — 절반만 맞다.** dispatch/join 은 확실히 없다. 그러나 **replay 인프라(SRS mutation 유예 → host 재생)는 착지해 런타임으로 왕복 동작한다** — `replay plan` → `replay apply` 실측, 승인 게이트가 `tool-not-deferrable`/`target-not-frozen` 으로 실제 거부. 병렬 하네스가 SRS 안전성을 위해 새로 만들 것은 없다.

### 1. 입력 표면 설계

#### 1.1 현재 존재하는 이슈 진입 표면 — 전수

| 스킬 | 진입 형태 | 근거 | 배치인가 |
|---|---|---|---|
| `kiwi-orchestrator` | `--issue <n>` 단수, Phase 1.a intake 소스 | `skills/claude/kiwi-orchestrator/SKILL.md:963` | 아니오 |
| `kiwi-wave-master` | 에픽 이슈 번호 1개(§8 진입 모드) | `skills/claude/kiwi-wave-master/SKILL.md:73, 462-485` | 아니오(에픽 1건) |
| `kiwi-pipeline` | "이슈 #123" 번호 1개, research-first 분기 | `skills/claude/kiwi-pipeline/SKILL.md:180-194` | 아니오 |

**감사의 G7 을 재확인했다.** 저장소 전체에서 `gh issue list` 를 실행하는 자리는 위 마지막 한 줄뿐이고, 그것은 커밋 메시지의 `Closes #N` 매칭 후보를 뽑는 용도이지 작업 intake 가 아니다. 즉 **여러 이슈를 받아 작업으로 만드는 진입 표면은 0개**다.

#### 1.2 하네스가 받아야 할 입력 4형태와 취득 방법

**(a) 이슈 번호 목록** — `gh issue view <n> --repo <r> --json number,title,body,labels,milestone,state,stateReason,assignees,url` 를 번호마다 1회. 이 호출 자체는 `kiwi-orchestrator/SKILL.md:353` 의 S8 producer 와 동일하므로 새 도구 의존이 아니다.

**(b) `gh issue list` 쿼리** — `--label`/`--milestone`/`--assignee`/`--state`/`--search` 조합. 주의: 기본 `--limit` 은 30 이라 조용히 잘린다. 배치 intake 는 **잘림이 곧 분모 손실**이므로 `--limit` 을 명시하고 반환 개수와 대조해야 한다(§6 위험 R2).

**(c) 메타 이슈 — 실측 분석 (`#1498`)**

실제로 `gh issue view 1498 --repo hancomins/orchestrationgrid-server-java --json body,title,labels,milestone` 를 실행해 본문을 파싱한 결과:

| 관측 | 값 |
|---|---|
| 체크리스트 총 항목 | **77** (`- [x] #` 66 + `- [ ] #` 11) |
| H3 그룹 | 3개 — `### 완료 (66)` / `### 미완료 (8)` / `### 기능 로드맵 (3 등록)` |
| 선두 `#번호` 를 가진 항목 | **77 / 77 (100%)** — `- [{x| }] #\d+ <제목>` 패턴이 예외 없이 성립 |
| GitHub **네이티브** 하위 이슈 | **0** (`gh api repos/.../issues/1498/sub_issues` → `0`, `sub_issues_summary.total` = 0) |
| `[x]` 인데 실제로는 폐기된 항목 | **2** (`#769` "**폐기(deferred)**", `#1316` "**폐기**") |
| 라벨 | `기능` 1개 / 마일스톤 없음 |

파싱 관점의 결론 넷:

1. **본문 텍스트가 유일한 링크 소스다.** `gh issue view --json` 의 필드 목록에는 `subIssues` 가 아예 없고(실측: `assignees, author, body, closed, closedAt, closedByPullRequestsReferences, comments, createdAt, id, isPinned, labels, milestone, number, projectCards, projectItems, reactionGroups, state, stateReason, title, updatedAt, url`), `gh api .../sub_issues` 도 0을 반환한다. 따라서 `- [ ] #NNNN` 정규식 파싱이 **대안이 아니라 유일한 경로**다.
2. **이것은 라우팅 계약에 직접 부딪힌다.** `kiwi-orchestrator/SKILL.md:370` 의 D4 는 `S8.linked_sub_issues >= 2` 를 술어로 갖는데, 이 필드를 네이티브 API 로 채우면 **#1498 같은 메타 이슈에서 0 이 나온다**. 다행히 같은 D4 의 `S8.task_list_groups >= 1` 이 3(H3 그룹 3개)으로 발화하므로 판정 자체는 옳게 나오지만, `linked_sub_issues` 는 **producer 가 실질적으로 존재하지 않는 필드**다. (테스트 픽스처도 이 값을 상수 0 으로만 고정한다 — `test/support/route-probe-document.ts:29`)
3. **체크박스 상태 ≠ 작업 상태.** 66건의 `[x]` 중 2건은 완료가 아니라 폐기다. 본문이 스스로 그렇게 선언한다 — "닫힌 것은 사유와 무관하게 완료에 두되, 폐기된 항목은 사유를 함께 적습니다." 체크박스만 읽는 파서는 **폐기를 완료로 읽는다**. 실제 상태는 `gh issue view <n> --json state,stateReason` 으로 항목마다 재확인해야 하고, 이것이 배치가 단수 intake 보다 비싼 진짜 이유다(77회 조회).
4. **분류 축이 본문에 이미 선언되어 있다.** "분류 기준은 *무엇을 하는 일인가* 입니다. **미완료**는 이미 합의된 계약이 어긋나 있어 **고치는** 일이고, **기능 로드맵**은 지금 없는 역량을 **새로 만드는** 일입니다." → 사람이 이미 수행한 분류가 H3 헤딩으로 물질화되어 있다. **하네스는 이것을 재발명하지 말고 채택해야 한다**(§2.4).

**(d) 자연어 요구사항 뭉치** — 기존 `intake-qna` 동사(`_shared/kiwi/run-ledger.md:116`)와 3-stance 조사자(`kiwi-orchestrator/SKILL.md:580`)가 이미 담당한다. 배치에서 새로 필요한 것은 **"이 뭉치가 항목 몇 개인가"를 고정하는 단계**뿐이다.

#### 1.3 입력 표면 권고

닫힌 4값 `input_kind` 를 선언한다: `issue-numbers` · `issue-query` · `meta-issue` · `prose-batch`. 근거: 기존 intake 소스 분류가 **닫힌 3값**(`kiwi-orchestrator/SKILL.md:579 — 얇은 의도 / 연구·설계 문서 / GitHub 이슈`)이라는 선례를 그대로 따르는 것이며, 열린 문자열은 이 저장소의 모든 분류 계약이 거부하는 형태다.

네 형태는 전부 **동일한 정규형 — `item[]`** 으로 수렴시킨다. 그래야 이후 단계가 입력 형태를 다시 알 필요가 없다.

#### 2.1 재사용 가능한 기존 계약 — 실사 결과

| 커버리지 게이트 | "어느 묶음에도 배정되지 않은 항목 **전량** 보고, 상위 N 건 보고 금지" | `wave-decomposition.md:76-84` |

**재사용 불가한 것 — 이것이 이 연구의 핵심 마찰이다**

`orchestrate issue` CLI 는 이미 존재하는 **이슈 원장**이지만 GitHub 이슈용이 아니다. `kiwi/orchestrator/issues.json` 에 사는 **wave 경계 내부 이슈** 원장이며, 분류가 닫힌 6값으로 코드에 하드코딩되어 있다:

```
src/core/orchestrator/issue-ledger.ts:11
ISSUE_CLASSES = ["local-defect","missing-task","design-gap",
                 "new-wave-required","design-contradiction","out-of-run"]
```

실측으로 확인했다 — GitHub 배치용 분류를 넣으면 거부된다:

```
$ node bin/speckiwi orchestrate issue open --dry-run --json \
    --payload '{"issueId":"i-1","class":"github-batch","summary":"x"}'
{"ok":false,"gate":"wave-issues-open","violations":[{"code":"issue-class-invalid",
 "detail":"classification github-batch is outside the closed list"}]}
```

즉 **`orchestrate issue` 는 이름이 겹칠 뿐 배치 intake 에 재사용할 수 없다.** 이 사실은 §4 의 구현 위치 판정을 상당 부분 결정한다.

#### 2.2 분류 축 — 4축 제안

사용자가 말한 축 그대로, 각 축을 **닫힌 목록**으로 고정한다.

**축 1 · `work_kind` — 무엇을 하는 일인가 (닫힌 5값)**

| 값 | 뜻 | #1498 근거 |
|---|---|---|
| `defect` | 코드가 계약을 어겼다 | "미완료 … 결함" |
| `contract-gap` | 계약이 비어 있다 | "계약 공백" |
| `doc-integrity` | 문서가 코드와 어긋났다 | "문서 정합" (`#1108`) |
| `feature` | 지금 없는 역량을 새로 만든다 | "기능 로드맵 … 지금 없는 역량을 **새로 만드는** 일" |
| `debt` | 구조 부채 | "부채" |

이 5값은 발명이 아니다. #1498 본문이 미완료 그룹을 "결함 · 계약 공백 · 문서 정합 · 부채"로 스스로 열거하고, 별도 그룹으로 "기능 로드맵"을 둔다. **사람이 이미 쓴 어휘를 채택**하는 것이 하네스가 사람 분류와 싸우지 않는 유일한 방법이다.

**축 2 · `scale` — 규모 (닫힌 4값)**

`hot-fix` / `step` / `plan` / `epic`. **이 축은 새 판정기를 만들지 않는다** — 기존 route probe 의 disqualifier 사다리를 항목마다 1회 돌린 결과를 그대로 쓴다(`SKILL.md:365-384`, 선택 순서 `R-PLAN → R-STEP → R-ORCH` 고정). 근거: 감사가 지적한 대로 스킬 선택이 "run 당 1회"인 것이 문제이지(`23.graph-engineering-fit-audit.md:25`) 판정 커널 자체는 이미 옳고 기계로 강제된다(같은 문서 `:63`).

**축 3 · `write_set` — 의존/충돌 (묶음의 진짜 결정자)**

같은 대상을 건드리는 항목은 같은 묶음. **이 축에는 이미 구현된 커널이 있다** — 오케스트레이터 lane 플래너는 의존 DAG 가 아니라 **write-set 충돌 그래프**로 분할한다(`src/core/orchestrator/lane-plan.ts:113-135`, 감사 `:53` 이 인용). 배치 묶음에 그대로 쓸 수 있는 유일한 기성 알고리즘이다.

단 함정이 하나 있다. 감사 `:46` 이 실측한 대로 `orchestrate preflight --lane-plan <lanes.lock.json>` 은 실제 `lanes.lock.json` 형식과 **비호환**이고(`lanes.writeSet is not a list of paths`), `lanes.lock.json` 경로가 세 곳에서 다르게 적혀 있다. 이 커널을 배치에서 호출하려면 그 선행 수리가 필요하다.

> **[검토 정정 — §13.2 C-1]** 이 축의 전제가 연구 B §2.4 의 실측과 모순된다. lane-plan 의 fold 규칙은 **단독 성분이면서 의존자가 없는 task 를 전부 serial epilogue 로 접는데**, 서로 무관한 GitHub 이슈 N건은 정의상 전부 그 형태다 — 검토자가 독립 8-task 사이드카로 재실측: `laneCount 0, serialEpilogue 8`. 게다가 트리아지 전 이슈에는 `files[]` 선언이 없어 `unknown-write-set` 경로로도 묶음이 생기지 않는다. 따라서 "그대로 쓸 수 있는 유일한 기성 알고리즘"은 성립하지 않는다. 실현 경로는 두 갈래다: `connectedComponents` 를 별도 표면으로 노출(현재 CLI/MCP 에 없음)하거나, 배치 묶음은 자체 union-find 로 계산하고 lane-plan 은 `H-ORCH` 항목 **내부**에서만 쓴다. §12.3 쟁점 4 로 승격했다.

**축 4 · `priority`** — 자유 정수가 아니라 **선언 출처**로 고정: `label` / `milestone` / `meta-issue-group-order` / `user-declared`. 근거 없는 우선순위는 재개 세션에서 재구성되지 않는다.

#### 2.3 묶음(batch) 규칙

```
group_key = (work_kind, scale, write_set_component)
```

세 축의 곱이 묶음이고, `priority` 는 묶음 **간 순서**만 정한다. 이유: 앞의 셋은 "같이 실행해도 되는가"를 결정하고 마지막 하나는 "먼저 하는가"를 결정하므로, 넷을 한 키에 섞으면 우선순위가 다른 두 독립 항목이 강제로 분리된다.

#### 2.4 사람 분류의 우선권 — 명시 규칙

메타 이슈가 이미 그룹핑을 갖고 있으면(#1498 의 H3 3그룹) **그것이 축 1 의 초기값이고 하네스의 재분류는 그 위의 제안이다.** 하네스가 사람 분류를 뒤집으려면 항목별 사유를 남기고 사용자 확인을 받는다.

근거: 이 저장소는 같은 원칙을 이미 두 번 적용한다 — "out-of-scope 는 판단이 아니라 기록이다"(`wave-decomposition.md:82`), "도구는 분류의 **형식**을 검사하고 그 **옳음**을 검사하지 않는다"(`kiwi-orchestrator/SKILL.md:886`).

```
kiwi/pipeline.jsonl           -> tracked-eligible
kiwi/waves.jsonl              -> IGNORED
kiwi/orchestrator/issues.json -> IGNORED
kiwi/backlog.jsonl            -> tracked-eligible
```

**이것이 설계 결정 하나를 강제한다.** 배치 backlog 를 `kiwi/orchestrator/` 아래에 두면 **gitignore 되어 클론·다른 머신·다른 에이전트에서 사라진다.** 77건짜리 이슈 트리아지는 며칠에 걸치고 리뷰 대상이며 팀이 공유하는 산출물이므로, `waves.jsonl` 이 아니라 `pipeline.jsonl` 쪽 취급을 받아야 한다.

#### 3.2 스키마 권고 — 양면 SSOT (jsonl 단독도, md 단독도 아니다)

이 저장소에는 **양면 SSOT 선례가 두 개** 있다:

- wave 이슈: `issues.md`(사람) + `issues.lock.json`(기계) — `kiwi-orchestrator/SKILL.md:864`
- 계획: `plan.md` + 사이드카 JSON "양면 SSOT" — kiwi-planner 스킬 설명

배치 backlog 도 같은 형태를 따른다. 이유가 각각 명확하다 — **분류는 사람이 검토해야 하고**(축 4개 중 3개가 판단이다), **진행은 기계가 재개해야 한다**(append-only).

```
docs/backlog/{run_id}/backlog.md         사람이 읽고 고치는 분류표 (git 추적)
```

**`kiwi/backlog.jsonl` 한 줄 스키마** (`waves-event.md` §2.1 의 필수 8필드 형태를 그대로 모방):

#### 3.3 세션이 끊겨도 재개되려면 영속되어야 하는 것 — 정확히 5가지

`run-ledger.md:1-5` 의 진단("원장이 없으면 중단된 동작과 시작되지 않은 동작을 구분할 수 없다")을 배치에 옮기면:

1. **입력 분모의 동결** — "이 run 은 항목 77개를 받았다". 재조회로 다시 세면 그 사이 새 이슈가 생겨 분모가 조용히 늘어난다. `backlog.lock.json` 의 digest 가 이것을 고정한다.
2. **항목별 분류와 그 근거** — 재개 세션에는 조사자도 대화도 없다(`SKILL.md:571` 이 route probe 를 `idempotent-by-key` 로 둔 것과 같은 이유).
3. **묶음(group_key) 배정 전량** — 미배정 항목은 §2.1 의 커버리지 게이트가 전량 보고해야 하므로.
4. **dispatch 사실과 그 자식 run_id** — `run-ledger.md:122` 의 `dispatch-route` 가 `externally-visible` 인 것과 동일한 이유: **살아 있을 수 있는 자식을 다시 dispatch 하면 중복 구현이 생긴다.** 배치에서는 이 위험이 항목 수만큼 곱해진다.
5. **인도(delivery) 부작용** — 이슈 코멘트·닫기·PR 은 되돌릴 수 없다. `externally-visible` 로 선언하고 재진입 전에 `gh issue view --json state,comments` 로 확인한다.

#### 3.4 verb 어휘와 그 강제 수준 — 실측한 한계

배치 verb 는 기존 닫힌 enum 밖이다(`run-ledger.md:112-151` 에 `intake-qna`/`intake-document`/`intake-issue` 는 있으나 배치는 없다). 신설 후보: `intake-batch`(pure-reauthor) · `classify-batch`(pure-reauthor) · `freeze-backlog`(idempotent-by-key) · `dispatch-item`(**externally-visible**) · `deliver-item`(**externally-visible**).

**단, 이 어휘가 실제로 강제되는지는 확인해야 한다. 실측 결과 강제되지 않는다:**

```
$ node bin/speckiwi orchestrate journal append --dry-run --json --run-id r1 \
    --payload '{...,"verb":"intake-batch"}'
{"ok":true,"violations":[],"diagnostics":[]}      # enum 밖 verb 가 통과
```

소스에서 확인한 이유: `isVerb`/`isPhase1Verb` 의 **유일한 호출자는 재개 카드**다 — `src/core/orchestrator/resume-card.ts:142` 가 `next_action.verb` 에 대해 `unknown-verb` 를 올린다. 저널 줄의 `verb` 필드를 검사하는 코드는 없다.

> **[검토 정정 — §13.2 H-1]** 원문의 괄호 주장("`abort_gate` 검사는 validate 시점이고 append dry-run 은 통과했다")은 **사실과 반대다.** 검토자 재실측: `abort_gate:"totally-made-up-gate"` 는 append dry-run 에서 `{"ok":false, "gate":"run-invariant-drift", "violations":[{"code":"abort-gate-outside-vocabulary"}]}` 로 **즉시 거부**되고, `GATE_IDS` 멤버는 통과한다. 즉 **verb 는 미검사·abort_gate 는 append 시점 검사**라는 비대칭이 실재하며 이는 I부 §3 이 이미 정확히 적은 내용이다. 이 정정은 선행 수리 후보 17 의 성격을 바꾼다 — 강제 지점은 발명 대상이 아니라 **이미 존재하고**(append 경로의 어휘 검사), 배치 verb 는 그 검사에 얹으면 된다.

감사 §3 이 "journal append 는 verb 를 검사하지 않는다"고 적은 것과 일치하며, 위치를 한 단계 더 좁혔다. 배치 verb 를 새로 선언할 때 **선언만으로는 아무것도 강제되지 않는다**는 뜻이다.

#### 4.2 권고 — (i) 새 독립 스킬, 단 실행은 재발명하지 않는다

**권고 이유 세 가지.**

1. **(ii)·(iii) 의 마찰은 파라미터가 아니라 구조다.** 오케스트레이터의 run 은 "단일 동결 설계 하나를 여러 wave 로 펴는 것"이고, wave-master 의 wave 는 "앞이 뒤의 토대인 사슬"이다. 77건의 독립 SSO 이슈는 둘 다 아니다. `--issue` 를 배열로 바꾸는 것은 한 줄이지만, 그 뒤의 `P-DESIGN-FROZEN` · `invariant_digest` · `computeRoute` 1회 · wave 추가 3회 상한이 전부 **단수를 전제로 설계된 불변식**이다. 감사가 "run 당 소스 1개"를 불변으로 적은 것(`:23`)은 인자 서술이 아니라 이 불변식들의 요약이다.

2. **사용자가 원한 "항목마다 적절한 스킬 선택"은 (i) 에서만 가능하다.** 감사 `:25` 가 확정한 대로 기존 오케스트레이터는 rung 당 스킬 사슬이 고정이다. 배치의 본질은 "이건 hot-fix, 저건 wave, 저건 문서 수정"이므로 **디스패처가 반드시 실행기 바깥에 있어야 한다.**

3. **감사가 "이 단계의 스킬은 없다"고 명시한 자리와 정확히 일치한다.** `23.graph-engineering-fit-audit.md:92` 는 다수 이슈 경로를 `0단(메인 세션이 gh issue list 를 읽고 손으로 분류·순서화 — 이 단계의 스킬은 없다)` 으로 적었다. 권고안은 그 0단을 스킬로 만드는 것이지 새 계층을 창설하는 것이 아니다.

**범위 경계 — 반드시 명시해야 하는 것.** `kiwi-backlog` 는 **intake · 분류 · 원장 · dispatch · 인도**만 한다. 구현·검증 루프·wave 실행은 **한 줄도 재구현하지 않고** 기존 스킬에 위임한다. 근거: 감사 §3 의 반복 패턴이 "산문 계약은 상세한데 런타임 강제가 없다"이고, 새 스킬이 실행까지 서술하면 그 패턴을 한 번 더 만든다.

**메타 이슈는 (iii) 을 서브루틴으로 부른다.** `kiwi-wave-master §8` 의 "에픽 본문 구조 · 태스크 리스트 · 연결된 하위 이슈 세 갈래"(`SKILL.md:470`)는 #1498 같은 입력에 대해 이미 옳다. 새로 쓰지 말고 `input_kind=meta-issue` 일 때 그 추출을 재사용한다 — 단 §1.2 에서 실측한 대로 "연결된 하위 이슈" 갈래는 이 저장소 대상에서 **0을 반환하므로** 본문 파싱 갈래가 실질적 유일 경로임을 그 계약에 적어야 한다.

### 6. 위험

**R1 · 이름 충돌이 조용한 오해를 만든다 (HIGH).** `orchestrate issue open|plan|resolve|defer|list` 는 이미 존재하며 GitHub 이슈와 무관하다(`src/core/orchestrator/issue-ledger.ts:11`, `kiwi/orchestrator/issues.json`). 에이전트가 "이슈 원장이 이미 있다"고 읽고 GitHub 배치를 그곳에 밀어 넣으면 `issue-class-invalid` 로 거부되거나(실측 확인) 더 나쁘게는 `out-of-run` 같은 기존 값으로 우겨넣어 wave 종료 게이트를 오염시킨다.

**R2 · 분모가 조용히 잘린다 (HIGH).** `gh issue list` 기본 `--limit` 은 30. 77건 메타 이슈를 쿼리로 받으면 47건이 침묵 속에 사라지고, 커버리지 게이트는 **받은 30건 기준으로 100%** 를 보고한다. `wave-decomposition.md:76` 의 "전량 보고" 원칙이 입력 단계에서 이미 깨진다.

**R3 · 체크박스를 완료로 읽는다 (HIGH).** #1498 에서 실측 2건(`#769`, `#1316`). 비율은 3%지만 **폐기된 항목을 완료로 읽으면 그 작업이 영원히 재개되지 않는다** — 조용하고 되돌릴 수 없는 종류의 오류다.

**R4 · dispatch 중복 실행 (HIGH).** `run-ledger.md:122` 가 단수 run 에서도 경고하는 "살아 있을 수 있는 자식을 다시 dispatch 하지 않는다"가 배치에서는 항목 수만큼 곱해진다. 77건 배치의 재개 시 실패 하나가 77개 중복 구현이 될 수 있다.

**R5 · 인도 부작용은 되돌릴 수 없다 (HIGH).** 이슈 닫기·코멘트·PR 은 배치에서 **한 번에 수십 건**이 나간다. `kiwi-pipeline/SKILL.md:144` 가 "커밋·push 는 외부 부작용이고 wave 마다 자동으로 일어나면 되돌릴 수 없다"며 자동 연결을 끊은 것과 동일한 논리가 배치에서 훨씬 강하게 적용된다.

## 10. 연구 B — DAG 기반 병렬 서브에이전트 실행 설계 (research-graph)

### 0. 한 장 요약

**병렬 실행기를 새로 설계할 필요가 거의 없다. 부품은 거의 다 실재하고 런타임으로 동작한다 — 없는 것은 "동시에 spawn 하고 join 하는 호출자" 하나다.**

실측으로 확인한 것:

| 부품 | 상태 | 확인 방법 |
|---|---|---|
| 의존 DAG 저작·검증 | 실재 | `lane-plan.ts:113` 순환탐지, `conflict.ts:313` 전이폐포 |
| write-set 충돌 기반 lane 분할 | **실재, 런타임 동작** | `orchestrate schedule plan` 실행 성공 |

| 재생 승인 게이트(allowlist·target) | **실재, 실제로 거부함** | `set_active_target` 거부 실측 |

**첫째, 이미 깔린 인프라의 양이 압도적이다.** phase2 로 이연된 6단계(`SKILL.md:323`) 중 재생 절반은 이미 착지해 있다. 실측:

**둘째, (i) 은 계층이 틀렸다.** kiwi-pm 이 자기 Task 들을 동시 spawn 하면 write-set 충돌 분할(`conflict.ts:299`)·수렴 레지스트리·serial epilogue 라우팅을 pm 이 다시 구현해야 한다. 그 로직은 이미 `lane-plan.ts` 에 있고 kiwi-pm 은 그것을 읽지 않는다. 같은 책임을 두 곳이 나눠 갖게 된다.

**셋째, kiwi-pm 은 이미 병렬 피호출자로 완성돼 있다.** §1.5 6종 플래그가 정확히 "레인 하나를 실행하는 계약"이고, 스킬 본문이 명시적으로 말한다:

> §2.1 의 "sequential spawn 이라 race 없음" 전제는 **약화되는 것이 아니라 해소**된다 — unit 마다 자기 파일을 갖는다. (`kiwi-pm/SKILL.md:213`)

(iii) 은 권고하지 않는다 — 이득이 없고, 위 계약을 전부 재발명해야 하며, 저널·재개·인도 어디에도 붙지 않는다.

### 2. 병렬 안전성 경계 — 기존 코드가 이미 아는 것

#### 2.1 닫힌 충돌 enum이 경계를 전부 규정한다

`conflict.ts:22-34` 의 11값 enum 은 4개 그룹으로 나뉘고, 각 그룹이 정확히 하나의 스케줄링 의미를 갖는다.

| 그룹 | 멤버 | 의미 |
|---|---|---|
| `SAME_LANE_REASONS` (`:39`) | `write-set-overlap` · `tdd-pair` · `req-shared` · `learned-coupling` | **같은 lane 강제** — 연결 성분으로 합침 |
| `ORDERING_REASONS` (`:48`) | `task-dependency` · `phase-dependency` | **stage 순서만** — 같은 lane 으로 묶지 않음 |
| `STAGE_BARRIER_REASONS` (`:42`) | `unknown-write-set` · `module-barrier` | 그 lane 이 **stage 를 독차지** (`lane-plan.ts:230`) |
| `SERIAL_EPILOGUE_REASONS` (`:45`) | `srs-write` · `non-code-write-set` | **lane 부적격** → 직렬 epilogue |

`convergence-point` 만 4-way 로 갈린다(`run-ledger.md:237`): `exclusive-lane` 은 lane 적격(단 wave 전체 유일), 나머지 셋(`orchestrator-only`·`replay`·`regenerate`)은 epilogue.

#### 2.2 SRS mutation 직렬화는 두 겹으로 보장된다

1. **계획 시점** — `SRS_MUTATION_VERBS` 11개(`conflict.ts:128-140`) 중 하나를 `action` 에 담은 task 는 `srs-write` edge 를 받아 epilogue 로 라우팅(`:385`). 기본 수렴 레지스트리의 `CP-02` 가 `docs/spec/**` 전체를 `orchestrator-only` 로 덮는다(`run-ledger.md:262`).
2. **실행 시점** — 레인은 `--defer-srs-mutation` 으로 큐에만 적고(`worktree-lane.md:54`), host 가 `replay apply` 로 재생. `admitReplayCalls`(`replay-admission.ts:62`)가 **모듈 상수** allowlist 4종(`:18-23`) 밖을 `tool-not-deferrable` 로, 동결 target 밖을 `target-not-frozen` 으로 거부.

세 번째 겹은 role 게이트다 — lane 의 `write_set` 이 `docs/spec/` 를 건드리면 배치 자체가 `lane-write-set-touches-srs` 로 거부된다(`worktree-topology.ts:172`).

#### 2.3 재생의 멱등성 — 재개가 행을 중복시키지 않는 구조

`add_completed_work` 와 `add_verification_evidence` 는 append 이므로 순진한 재개가 행을 복제한다. 세 장치가 막는다:

- **키는 `(tool, argsHash)` 쌍** — 해시 단독이면 `update_status` 와 `add_completed_work` 가 `{id, target}` 같은 args 모양을 공유해 서로를 삼킨다(`replay.ts:76-78`).
- **`args_hash` 는 재계산**하고 큐에 적힌 값을 믿지 않는다(`replay.ts:67`) — 큐를 쓰는 주체가 레인이기 때문.
- **시도 1건당 1줄을 dispatch *전에* append**(`replay-apply.ts:85`). 배치로 마지막에 쓰면 정확히 그 기록이 필요한 run(중간에 죽은 run)의 회계를 잃는다. 실패로 기록된 호출은 `remaining` 으로 **되돌아오지 않는다**(`replay-admission.ts:123` 주석).

#### 2.4 ⚠️ 결정적 발견 — lane 플래너는 "완전 독립 task"에 병렬도 0 을 낸다

실측 3건(`orchestrate schedule plan --lanes 4`):

| 입력 | 결과 |
|---|---|
| **독립 code task 8개** (각자 파일, 각자 REQ, 의존 0) | **lane 0개, stage 0개, epilogue 8개 — 병렬 전무** |
| REQ 4개 × (red, green) TDD 쌍 8 task | **lane 4개, stage 1개, epilogue 0개 — 완전 병렬** |
| 4가지 × 3단 체인 12 task | lane 8개 / stage 2개 + **epilogue 4개**(각 체인의 말단) |

원인은 `lane-plan.ts:319` 의 fold 규칙이다:

```ts
if (component.length === 1 && !hasDependents.has(component[0])) {
  folded.push(component[0]);   // → serial epilogue
```

설계 근거는 코드 주석이 인용한 05 §5.3 이다 — "per-lane overhead is fixed and per-lane gain is proportional to the work inside"(`lane-plan.ts:313-318`). 논리적으로 타당하다. 그러나 귀결은:

> **병렬도는 DAG 의 폭이 아니라 "같은-lane 연결 성분의 크기"가 결정한다.** DAG 의 모든 sink 는, 단독 성분이면 직렬화된다.

실제 kiwi-planner 산출물은 `tdd-pair`·`req-shared` edge 로 task 를 묶으므로 두 번째 행에 가깝다(그래서 이 규칙이 실전에서 안전하다). 하지만 **비-TDD·1-task-per-REQ 계획은 통째로 직렬화된다.** 병렬 하네스를 켜기 전에 이 규칙을 유지할지(그리고 planner 가 항상 쌍을 만들도록 강제할지) 결정해야 한다.

### 3. 세션 생존성 — 디스크 영속 + 멱등 재스폰

#### 3.1 이 문제는 이미 원칙으로 답이 나와 있다

> 레인이 살아 있는 동안 **재-dispatch 하지 않는다.** 워크트리는 세션 이름과 달리 **디스크 아티팩트이므로 재개에 강하다** — 그것이 이 조정 방식의 부수 이점이다. (`worktree-lane.md:114`)

`run-ledger.md:226` 의 금지 목록도 같은 말을 한다: "살아 있을 수 있는 lane 을 다시 dispatch 하지 않는다 — **사용자에게 묻는다**".

#### 3.2 "이 task 는 이미 착지했다"의 술어 — 커밋 존재가 정답

세 후보 중 무엇을 쓰는가에 대한 답은 코드에 이미 있다.

**채택: git trailer 4종 일치.** `lane-state.ts:125` `hasMergeWitness`:

```ts
export const MERGE_WITNESS_TRAILERS = ["Orch-Run", "Orch-Wave", "Orch-Stage", "Orch-Lane"];
// 넷 전부가 이 unit 을 지명해야 한다. 셋만 든 커밋은 같은 run 의 다른 unit 것이고
```

세션과 완전히 무관하다 — 공유 객체 DB 위의 커밋만 읽는다. `kiwi-pm --commit-lane-work` 가 Task 마다 이 5 trailer(+`Orch-Task`)를 단 커밋 1개를 만들므로(`kiwi-pm/SKILL.md:222`), 재개한 세션은 커밋 로그만 보고 어느 Task 가 착지했는지 안다.

**기각: `verification_cmd` 재실행.** 판정 수단으로는 필수지만(호스트가 직접 1회 실행, `worktree-lane.md:79`) "이미 했는가"의 술어로는 비싸고, 레인의 자기보고 green 은 애초에 판정이 아니다(devDependencies 누락 함정, `worktree-lane.md:48,81`).

**보조: `lane_disposition`.** 커밋이 없어도 정산된 lane 이 있다 — 강등·격리·반증. `readLaneDisposition`(`lane-state.ts:55`)이 **verb 필터 없이** 모든 result 줄을 읽는다. 주석이 이유를 명시한다:

> phase 1 의 운반체는 `execute-unit`, phase 2 는 `verify-lane`/`collect-lane` 이다. phase-2 동사로만 키를 잡은 독자는 phase-1 의 반증을 부재로 읽고, 재개한 세션이 반증된 unit 을 통합한다. (`lane-state.ts:49-51`)

**최종 술어** = `evaluatePriorStagesIntegrated`(`lane-state.ts:162`): 앞선 모든 stage 의 모든 lane 이 *커밋 증인을 갖거나* *종국 disposition 을 갖는다*. 주석이 이 논리합을 "느슨하게 한 것이 아니라 교정"이라 부른다 — 병합만 요구하면 정당하게 강등된 lane 하나가 그 wave 를 **영영 재개 불가**로 만든다(`:155-157`).

#### 3.3 jsonl 에 남길 것 — 이미 전부 정의돼 있고, 오늘 write 된다

실측: `waves.jsonl` 은 병렬 어휘를 **오늘 그대로 받아들인다.**

```
{"ok":true,"written":true}

$ … '{…,"event":"result","verb":"dispatch-lane","lane":"lane-1","stage":1,
      "lane_disposition":{"kind":"refuted",…},"proof":[{"kind":"git-trailer","ref":"deadbeef"}]}'
```

필드 출처: `waves-event.md:70`(`lane`) · `:71`(`stage`) · `:74`(`isolation{workspace_ref,base_sha,head_sha,merge_sha}`) · `:80`(`deadline_at` — **"`dispatch-lane` intent 줄의 lane 마감 시각"으로 이미 정의됨**) · `:83`(`lane_disposition` 닫힌 4값) · `:85`(`proof`) · `:67`(`event: intent|result`).

**재개 불변식**(`run-ledger.md:100`):

> 현재 run 에서 `(verb, wave, lane)` 키마다 마지막 줄은 `result` 여야 한다. 짝 없는 `intent` 는 그 verb 가 중단되었다는 뜻이다.

`dispatch-lane` 은 `externally-visible`(`journal-schema.ts:93`)이므로 짝 없는 intent 를 만나면 재진입 **전에** 커밋 확인을 하고, 그래도 해소가 안 될 때만 `interrupted-external-action` 을 올린다 — 이 게이트는 `--auto` 라도 중단한다(`run-ledger.md:156`).

**증거 강도 규칙**도 그대로 재사용된다: `journal` 은 판정 줄의 단독 증명이 될 수 없고, 외부 재계산 가능한 5종(`git-ancestor`·`git-ref`·`git-trailer`·`digest`·`mcp-state`) 중 최소 하나를 동반해야 한다(`run-ledger.md:176`, `waves-event.md:101`).

#### 3.4 대조(reconciliation)는 lane 단위로 이미 설계돼 있다

`run-ledger.md:184`: lane 마다 4관측 `J(k)`(마지막 저널 줄) · `B(k)`(커밋 존재) · `A(k)`(정산 여부) · `D(k)`(disposition)를 독립 분류한 뒤 축약. **비교는 하나의 `(wave, stage)` 쌍으로 스코프한다** — 전체를 비교하면 아직 시작 안 한 stage 의 lane 이 분모에 들어와 정상 run 이 `divergent` 로 떨어진다(`:182`).

즉 §3 의 요구사항은 **새로 설계할 것이 거의 없고, `dispatch-lane` intent/result 를 실제로 쓰는 호출자만 있으면 된다.**

### 4. 재계획(G8) 완화 — 합법 경로는 이미 둘 다 존재한다

감사의 G8("중간 재계획 불가")은 **과장이다.** 두 개의 합법 경로가 명문화돼 있고, 정확히 요청된 형태("노드 추가만" / "미착수 노드만")로 이미 제한돼 있다.

#### 4.1 경로 A — `amend-design` (wave 안, 상한 2회)

`SKILL.md:888` §13.4. 트리거는 **실행 단위가 설계 항목을 반증했을 때**: 동결된 `[D-nnn]` 를 기술대로 구현할 수 없다고 판정한 단위는 `design_item_id` 와 증거를 보고하고 멈춘다(`lane-design-refuted`, critical).

승인된 수정의 5단계(`:896-900`):

1. 새 `design/00.design.{seq}.md` + 새 `00.design.lock.json`. **어느 쪽도 제자리 편집 금지.**
2. 옛 digest·새 digest·반증된 `[D-nnn]`·증거를 지명하는 저널 줄 append.
3. 카드의 `frozen.design_lock` 포인터 이동 + `invariant_digest` 재계산. **포인터를 안 옮기면 정당한 수정이 드리프트로 읽힌다.**
4. loop W·P·F 의 분모를 새 lock 에서 재동결하고 영향 라운드 **재시작**.
5. 영향받은 각 단위는 새 handoff 위에서 `execute-unit` **한 번**으로 재실행.

**상한 2회, 3번째는 `design-contradiction-at-wave-boundary`**(`:902`, `:104`). 그 게이트는 `abort-run` 이고 **위원회가 결정할 수 없다** — "위원회는 설계의 어느 쪽 절반을 버릴지에 투표하게 되기 때문"(`:872`).

이것이 `run-ledger.md:212` 의 **append-new-artifact 규칙**이며, 정당한 수정과 드리프트를 구별하는 장치다.

#### 4.2 경로 B — wave 추가 (run 당 상한 3회)

`wave-master/SKILL.md:22` §0.5 가 명시적으로 예외를 둔다:

> 발견된 설계 **커버리지 갭**을 닫기 위해 새 wave 를 **추가**하는 것은 본 원칙의 명시적 예외이며 **재분해가 아니다**. 이때 **이미 등록된 wave 의 순서는 바뀌지 않는다**.

`SKILL.md:871` 의 6값 이슈 분류가 라우팅을 규정한다: `local-defect`→리뷰루프 / `missing-task`→`--req-filter`+`--plan-run-id` 재진입 / `design-gap`→새 아티팩트+증분 SRS / `new-wave-required`→wave 추가(상한 3, `wave-master:337`) / `design-contradiction`→abort / `out-of-run`→기록.

`P-WAVE-ISSUES-CLOSED` 4연언(`SKILL.md:877`)이 다음 wave 를 막는다. **`out-of-run` 과 `new-wave-required` 는 `--auto` 라도 사용자 동의를 요구한다**(`:884`).

#### 4.3 병렬을 켤 때 이 위에 추가할 것

기존 규칙과 충돌하지 않는 최소 확장 3가지:

1. **"미착수 노드만 재작성" 은 이미 강제된다.** `execute-unit` 재개 규칙이 "커밋이 이미 있는 unit 을 다시 실행하지 않는다 — 재실행은 중복 구현을 만든다"(`run-ledger.md:142`). 착수된 노드는 커밋으로 잠긴다.
2. **"노드 추가만" 은 stage 경계에서만.** `amend-design` 5단계는 이미 stage 재-dispatch 를 전제한다. 병렬에서는 여기에 **살아 있는 형제 lane 의 처분**을 정해야 한다(§5.3).
3. **`amend-design` 의 상한 2를 lane 수로 나누지 않는다.** wave 당 2회이지 lane 당 2회가 아니다. 8-lane wave 에서 lane 3개가 각각 다른 `[D-nnn]` 을 반증하면 즉시 상한 초과다 — 이 케이스의 처리는 현재 문서에 **없다**(신규 요구 후보 N6).

### 5. 동시성 상한 · 예산 · 실패 처분

#### 5.1 옵션 어휘는 이미 명명돼 있다

`SKILL.md:973`: **`--isolation` · `--install-concurrency` · `--install-stagger` · `--lane-deadline` · `--poll-interval` · `--serial` 이 전부 phase2 이연 옵션으로 이미 선언됨.** `--serial` 은 phase 1 에서 구현 안 함 — "유일하게 존재하는 모드를 요청하는 옵션이기 때문". 새 이름을 발명할 필요가 없다.

`--lanes N` 은 동시성이 아니라 **stage 당 lane 개수 상한**이다(`lane-plan.ts:31` 주석, `:237` `splitByCap`). 초과분은 연속 stage 로 쪼개진다. 병렬을 켜면 이 값이 **사실상 동시성 상한이 된다** — 한 stage 의 lane 은 전부 동시 실행되므로.

#### 5.2 Agent 도구 동시 spawn 의 실무 상한

**저장소 근거 없음** — 하드 상한을 명시한 코드·문서가 없다. 다만 이 저장소는 이미 병렬 spawn 관용구를 **연구·검증 용도로** 쓴다:

- `kiwi-srs-from-code/SKILL.md:306` — "**단일 메시지에서 모든 scope agent 를 동시 spawn**"
- `kiwi-srs-research/SKILL.md:423` — "3 Opus 를 `Agent { run_in_background: true }` 로 동시 spawn. 시간 상한 `--research-timeout`(기본 240초)"
- `kiwi-srs-feasibility/SKILL.md:476` — "다수 후보 병렬 호출. 메인은 4분 시간 상한 후 일괄 수신"

즉 **패턴은 실증됐다(연구 3~5기 규모).** 구현 단위 병렬은 0. `lanes.lock.json` 의 기본 `--lanes 4`(`orchestrate.ts:1318`)를 초기 상한으로 삼는 것이 기존 계약과 정합적이다.

#### 5.3 예산 계약과 그 알려진 구멍

`--subagent-budget N` 의 계약(`SKILL.md:967`):

> run 전체 서브에이전트 spawn 상한. 소진 시 현재 루프를 `verdict = fail-cap` 과 `reason_class = "budget-exhausted"` 로 닫고 **다음 stage 경계에서** `abort-run` 으로 멈춘다.

`reason_class="budget-exhausted"` 는 `waves-event.md:127` 의 닫힌 어휘 멤버이므로 기록 가능하다. **그대로 재사용하면 된다** — "다음 stage 경계에서 멈춘다"는 이미 병렬을 전제한 문장이다(직렬이면 stage 경계가 의미가 약하다).

**단, 알려진 구멍이 있다.** SRS 자신이 기록한다(`docs/spec/50.nodejs-implementation.srs.md:10782`):

> 두 budget abort 경로 — `--run-budget` 초과와 `--subagent-budget` 소진 — 은 **게이트 식별자를 전혀 지명하지 않으므로** `run abort` 를 정직하게 호출할 수 없다. 이것은 실제 갭이며 타입을 넓혀 닫지 않고 여기 보고한다.

즉 예산 소진 abort 는 `abort_gate` 에 쓸 값이 없다. 병렬은 예산 소진을 훨씬 자주 밟으므로 이 갭이 실효화된다(신규 요구 후보 N5).

#### 5.4 실패한 가지의 처분 — 죽이지 않는다

기존 계약이 답을 갖고 있고, 답은 **"다른 가지를 계속 간다"** 이다.

- `lane_disposition` 4값(`journal-schema.ts:215`)은 전부 **종국(terminal)** 이며 "lane 이 병합 없이 run 을 떠날 때"를 위해 존재한다. `refuted` 는 반증, `quarantined` 는 격리, `demoted` 는 강등, `coupling-reset` 은 결합 재설정.
- 반증된 단위의 커밋은 **"`frozen.integration_branch` 에 되돌려지지 않은 채 그대로 남는다"**(`SKILL.md:892`). 롤백하지 않는다.
- 정산된 lane 은 "병합되지 않았다는 사실만으로 다시 실행하지 않는다"(`run-ledger.md:198`).
- 실패의 전파는 `serial-unit-failed` 3 disjunct(`SKILL.md:762`): `verification_cmd` 가 **같은 handoff 로 1회 재시도 후에도** 비-0 / 커밋 0개인데 `intentionally_empty` 선언도 없음 / `kiwi-pm` 이 `NEEDS_USER`·`FAILED` 반환.

**반대로 재생 실패는 run 을 세운다.** `REPLAY_FAILURE_GATE = "srs-mutation-replay-failed"`(`replay-apply.ts:20`), 그리고 "실패는 run 을 계속 진행시키지 않고 멈춘다 — 계속하면 실패한 호출에 의존할 수 있는 호출들을 계속 적용하게 되고, 기록은 어떤 단일 run 도 만들지 않은 상태를 서술하게 된다"(`:66-70`).

**정리: 코드 lane 실패는 격리하고 계속, SRS 재생 실패는 전면 중단.** 이 비대칭은 의도적이고 옳다.

### 8. 직전 감사(23번 문서) 정정 3건

조사 중 재현으로 확인한 차이다.

1. **"`--lanes abc` 가 검증 없이 통과"(23번 §1) — 부정확.** 통과하지 않는다. `lane-plan-incomplete` 로 **실패**한다. 문제는 무검증이 아니라 **진단이 원인을 가리키지 않는다**는 것이다. `--lanes 9999` 가 통과한다는 나머지 절반은 맞다.

| `H-PIPE` | `Skill(kiwi-pipeline, "이슈 #N --wt --auto --body-scope")` **[§13.2 H-3·M-1 — `--wt` 는 run-root 침묵 이탈과 인터록, `--body-scope` 는 미정의 토큰(자연어 선언으로 재서술 필요)]** | **없음 — pipeline 이 §2.6.3 에서 이미 PR 을 연다** | `--body-scope` 명시 필수 (§1.6) |
| `H-ORCH` | `Skill(kiwi-orchestrator, "… --run-budget M --subagent-budget K")` | `kiwi-commit-auto-pr` (옵트인, §3) | 예산 2종. rung 재판정 금지 |

`kiwi-wave-master` 는 표에서 **뺀다.** 근거: `R-ORCH` 는 스킬 호출이 아니라 `_shared/kiwi/wave-decomposition.md`·`verify-loop.md`·`run-ledger.md` 를 **직접** 구동하며, 오케스트레이터는 형제를 결코 호출하지 않는다고 네 가지 근거와 함께 선언한다(`kiwi-orchestrator/SKILL.md:496-503`). 둘 다 표에 넣으면 하네스가 **오케스트레이터가 짓기를 거절한 판별자**를 스스로 지어야 한다. 예외 하나: 사용자가 이름으로 지목하면 그대로 통과시킨다 — 오케스트레이터 자신이 같은 규칙을 갖는다(`SKILL.md:505`).

> 부수 근거: 예산이 있는 대형 경로는 오케스트레이터뿐이다(`SKILL.md:966-967`). 그리고 `kiwi-wave-master` 는 `.agents/skills` 미러에서 **의도적으로 제외**되어 있다(`.agents/skills/.speckiwi-mirror-exclusions.json` — hermeticity leak sentinel).

#### 2.3 경계선 하나로 요약

> **하네스는 *무엇을 언제 누구에게* 만 정한다. *어떻게 되었는지* 는 정하지 않는다.**
> 검증 verdict·finding severity·요구 status·커밋 내용은 전부 엔진이 소유하고, 하네스는 그 결과를 **읽어 원장에 옮길 뿐** 재해석하지 않는다.

이 경계가 무너지는 구체적 신호 셋: 하네스가 (a) 자체 검증 라운드를 돌기 시작하면, (b) finding 을 재분류하면, (c) 자식 PASS 를 자기 게이트 충족으로 읽으면. (c)는 `verify-loop.md:125` 가 이미 명시적으로 금지한 우회다.

### 3. 인도(G1) 연결 설계

#### 3.1 실측 — 오늘 인도가 일어나는 자리

| 스킬 | commit-auto-* 참조 | 성격 |
|---|---|---|
| `kiwi-orchestrator` | **0건** (grep 결과) | PR·병합이 금지 닫힌 목록에 있음 (`SKILL.md:163`, `938`, `981`) |
| `kiwi-wave-master` | **0건** (grep 결과) | per-wave pipeline 을 `--cycle --from=feasibility --run` 으로 부른다 — `--wt` 없음, 그리고 `--wt` 위임 자체를 거부 (`SKILL.md:189`, `151`) |
| `kiwi-pipeline` | §2.6.3 **실제 호출 1곳** + T1 표 참조 | `--wt` + `--auto` 완료 시 `kiwi-commit-auto-pr` 호출, base 직접 병합은 금지 (`SKILL.md:176`) |
| `kiwi-hot-fix` | `next_hint` 힌트 + 외부 의존성 표 | "사용자 결정 또는 `/kiwi-commit-auto-push`" (`SKILL.md:439`, `491`) |
| `kiwi-review-fix-loop` | 동일 | (`SKILL.md:638`, `712-713`) |

**따라서 저장소 전체에서 인도를 자동으로 잇는 코드 경로는 정확히 하나다.** 나머지는 전부 힌트다.

#### 3.2 설계 — 금지를 존중하면서 하네스 층에서만 여는 법

금지 문장을 정확히 읽으면 그것은 **run 내부** 계약이다:

> "run 이 정상적으로 끝나면 통합 브랜치는 **그 자리에 남기고** run 보고서에 호명한다. **오케스트레이터는 그것을 base 브랜치에 병합하지 않고 PR 도 열지 않는다**" (`run-ledger.md:282`)

그 근거는 두 가지로 적혀 있다 — (1) 커밋·push 는 되돌릴 수 없는 외부 부작용이고 wave 마다 자동으로 일어나면 안 된다(`kiwi-pipeline/SKILL.md:144`), (2) 병합자는 병합 직후 `validate` → `sync-index` 를 **의무로** 실행해야 하는데 오케스트레이터가 사용자를 대신해 이행할 수 없다(`run-ledger.md:284`).

두 근거 모두 **엔진이 자기 run 도중에 하는 것**을 겨눈다. 엔진이 반환하고 통합 브랜치가 검증된 상태로 남은 **뒤**, 별도 홉이 PR 을 여는 것은 (1)의 "wave 마다"에 해당하지 않고, (2)의 의무는 PR 본문으로 이관할 수 있다. 그러므로:

**규칙 D-1.** 하네스는 인도 코드를 **작성하지 않는다.** `kiwi-commit-auto-push` / `-pr` 를 **편집 없이 그대로** 호출한다 — `kiwi-pipeline` §2.6.3 의 `OQ-027-autopr` 규약과 동일 형태.

**규칙 D-2.** 인도는 **엔진 종료 후의 별도 홉**이며 엔진 인자로 주입하지 않는다. 엔진의 `critical_gates[]` 나 금지 목록을 하네스가 완화하는 경로는 존재하지 않는다.

**규칙 D-3.** `--deliver` 는 닫힌 enum `none | push | pr` 이며 **base 브랜치 직접 병합은 어떤 값에도 없다.**

**규칙 D-4.** 기본값은 `--auto` 유무가 정한다 — 이것은 새 결정이 아니라 `kiwi-pipeline` §2.6.2/§2.6.3 이 이미 내린 결정의 복제다.

| 조건 | `--deliver` 기본값 |
|---|---|
| `--auto` 없음 | `none` — 항목마다 "이 한 줄이면 인도된다"를 보고만 한다 |
| `--auto` 있음 | `pr` |

**규칙 D-5.** 항목 type 별 인도 홉:

| rung / type | 인도 홉 | 사유 |
|---|---|---|
| `H-DIRECT` + `repo-admin` | `gh issue comment` → `gh issue close` 직접 | 커밋이 없으므로 commit-auto-* 가 할 일이 없다 |
| `H-DIRECT` + `prose-doc` | `kiwi-commit-auto-push` | `Closes #N` trailer + 이슈 코멘트가 여기 있다 (`kiwi-commit-auto-push/SKILL.md:190`, `227-256`) |
| `H-HOTFIX` / `H-TDD` | `kiwi-commit-auto-push` | 두 스킬의 `next_hint` 가 이미 이것을 가리킨다 |
| `H-PIPE` | **없음** | pipeline 이 §2.6.3 에서 이미 열었다. 하네스가 또 부르면 **PR 이 둘** 생긴다 |
| `H-ORCH` | `kiwi-commit-auto-pr` | 통합 브랜치 → PR. 그 PR body 에 §3.3 의무를 싣는다 |

**규칙 D-6.** `H-ORCH` 인도 홉의 PR body 에는 오케스트레이터 run 보고서가 호명한 **이행 불가 의무**를 그대로 옮긴다 — "이 PR 을 병합한 뒤 base 브랜치에서 `validate` → `sync-index` 를 이 순서로 실행할 것"(`run-ledger.md:284`). 이것이 금지를 존중하는 방식이다: 의무가 사라지는 게 아니라 **사람이 읽는 자리로 이동**한다.

#### 3.3 인도가 절대 자동화되면 안 되는 지점

`kiwi-commit-auto-push` 는 push 충돌만은 자율 결정 원칙의 예외로 사용자 확인을 강제한다(`SKILL.md:277`). `kiwi-commit-auto-pr` 는 fork repo·보호 브랜치 직접 commit 요청 시 질문한다. 하네스는 이 게이트들을 **자식 게이트 bubble** 로 받아 즉시 중단해야 한다 — `kiwi-orchestrator/SKILL.md:526` 의 상속 안전 규칙 둘째 항("자식이 자기 게이트를 bubble 하면 부모 표에 같은 이름의 행이 없어도 무조건 중단")을 그대로 상속한다.

### 4. 진행 추적·예산·재개

#### 4.1 원장 — 하네스가 소유하는 최소치

**설계 결정: 하네스 원장은 파생물이 아닌 것만 담는다.** `run-ledger.md:83` 의 "카드는 파생물이다" 원칙을 한 층 위에 적용한다.

```
kiwi/conductor/{conductor_run_id}/items.jsonl        (append-only)
kiwi/conductor/{conductor_run_id}/resume-card.json   (전체 재작성, 상한)
```

원장이 담는 것 (닫힌 목록):

| 필드 | 왜 파생될 수 없는가 |
|---|---|
| `item_id`, `source_ref` (이슈 번호 / 문서 heading path) | intake 가 만든 값. 어디에도 없다 |
| `route` = `{rung, removed[], decisive, probe_digest}` | 하네스 사다리의 산출 |
| `engine_run_ids[]` | **항목 ↔ run 바인딩. 이것이 원장의 존재 이유다** — 이게 없으면 `pipeline.jsonl` 의 어느 이벤트가 어느 항목 것인지 알 수 없다 |
| `state` ∈ `queued \| routed \| dispatched \| engine-done \| delivered \| blocked \| abandoned` | 항목 수준 상태 |
| `delivery` = `{mode, ref}` | 인도 결과 |
| `budget_spent` | §4.3 |

원장이 담지 **않는** 것: wave 진행, 라운드 카운터, finding, REQ status, verdict. 전부 엔진 저널에서 읽는다.

#### 4.2 진행률 조회 — `computeRunProgress` 배선이 선행 조건

```ts
// src/core/orchestrator/waves-validate.ts:673
export function computeRunProgress(view: WavesJournalView): RunProgress
// → { waveStatuses, firstIncompleteWave, needsFinalVerify, runComplete }
```

`src/` 안에 호출자가 **0개**다(테스트 6파일만). 하네스가 `H-ORCH` 항목의 진행을 물으려면 이 커널을 CLI verb + MCP 도구로 배선해야 한다. 감사가 G5 로 "소규모"라 적은 그대로이며, 메모리에 남은 교훈 — *"순수 커널에 호출자 0, 게이트 셋 발화 불가"* — 의 같은 종류다.

다른 항목 type 의 진행 조회 수단:

| rung | 조회 | 실재 여부 |
|---|---|---|
| `H-ORCH` | `computeRunProgress` | **커널만 있음 — 배선 필요** |
| `H-PIPE` | `workflow pipeline-status` / `pipeline-tail` | 실재 (`node bin/speckiwi workflow --help` 확인) |
| `H-PIPE` 내부 Task | `workflow plan-status`, `session-status`, `resume-hint` | 실재 |
| `H-TDD` | `list_steps`, `speckiwi step ...` | 실재 |
| `H-HOTFIX` | `.kiwi/sessions/{run-id}/state.json` | 스킬 규약 (`kiwi-hot-fix/SKILL.md:35`) |
| `H-DIRECT` | (없음 — 하네스 원장이 유일한 기록) | — |

#### 4.3 `pipeline.jsonl` 구독 — 가능하지만 창 고정이 필수

가능하다. `pipeline.jsonl` 은 `{git_root}/kiwi/pipeline.jsonl` 로 run 시작에 pin 되고(`pipeline-event.md:13-21`), 모든 kiwi-* 스킬이 종료 시 1줄 append 하며, `workflow pipeline-tail` 이 읽기 표면이다.

**단 두 가지 함정이 있고 둘 다 이미 실패 이력이 있다.**

1. **저장소당 1개 append-only 공유 파일이다.** 창을 고정하지 않으면 다른 항목의 이벤트를 자기 것으로 읽는다 — `kiwi-wave-master/SKILL.md:233` 이 wave 단위에서 정확히 이 문제를 겪고 "`pipeline_run_ids` 의 **모든** run 과 타임스탬프로 경계 짓는다"로 해결했다. 하네스는 항목 단위로 같은 규약을 쓴다: **`engine_run_ids[]` 전량 + dispatch 타임스탬프**.
2. **재진입 emit 키.** 같은 run 을 다시 돌리면 bare `run_id` 는 멱등 skip 되어 새 `TASK_DONE` 이 남지 않는다. `{run_id}#r{n}` 접미사가 규약이다(`pipeline-event.md:152-160`). 하네스가 항목을 재시도하면 이 키를 부여해야 하고, 그러지 않으면 **하네스가 영원히 완료 신호를 못 본다.**

또한: `next_hint` 는 **emit 한 스킬이 스스로 쓴 값**이고 T1 은 기계에 없다(`read.ts:607`). 하네스는 `next_hint` 를 신뢰 경계 밖의 자기신고로 다루고, 항목 완료 판정은 `status ∈ {TASK_DONE}` + 엔진 고유 증거(통합 브랜치 sha / `runComplete` / promote 결과)로 이중 확인해야 한다.

#### 4.4 예산

| 층 | 상한 | 실재 |
|---|---|---|
| `kiwi-orchestrator` | `--run-budget <mins>`, `--subagent-budget N` | 실재하되 **결함 있음** |
| `kiwi-pipeline` / `kiwi-wave-master` / `kiwi-pm` | **없음** | 감사 G6 |
| 하네스 | 신설 필요 | — |

오케스트레이터 예산의 알려진 결함 — SRS 가 직접 적어 두었다:

> "두 budget abort 경로 — `--run-budget` 초과와 `--subagent-budget` 소진 — 는 **게이트 식별자를 전혀 지명하지 않으므로**, 이 변경 뒤에는 `run abort` 를 정직하게 호출할 수 없다. 이것은 진짜 갭이고 여기서 보고한다" (`docs/spec/50.nodejs-implementation.srs.md:10782`)

따라서 **하네스 예산은 자식 예산에 기대어 회계할 수 없다.** 하네스 층 상한 설계:

| 인자 | 의미 | 소진 시 |
|---|---|---|
| `--max-items N` | 이 실행에서 처리할 항목 수 상한 | 남은 항목을 `queued` 로 남기고 종료 보고 |
| `--item-budget <mins>` | 항목 하나의 벽시계 상한 | 그 항목 `blocked` + `reason_class` 기록, 다음 항목으로 |
| `--subagent-budget K` | `H-ORCH` 에 **그대로 전달** + 하네스 자체 spawn 도 여기서 차감 | 다음 항목 경계에서 중단 |

`--max-items` 는 **무인 실행 종료를 보장하는 유일한 경계**다 — `kiwi-wave-master` 의 `wave-append-cap-exhausted`(run 당 wave 추가 3회)와 같은 역할이며, 그 스킬이 그 상한에 붙인 사유("상한이 없으면 종료 보장이 없다", `SKILL.md:337`)가 그대로 적용된다. `--drive` 가 그것마저 열지 못하는 닫힌 목록에 들어 있다는 사실도 참고(`SKILL.md:444`).

#### 4.5 컴팩션·세션 교체 후 재개

절차 (순서 고정):

1. **원장 읽기** — `items.jsonl` + `resume-card.json`. 카드가 원장과 어긋나고 원장이 상위집합이면 카드를 재생성한다(`card-stale`). 그 밖의 불일치는 중단 (`run-ledger.md:83`, `197`)
2. **항목마다 recovery class 적용** — 하네스 verb 도 `pure-reauthor` / `idempotent-by-key` / `externally-visible` 셋 중 하나를 선언한다:

| 하네스 verb | class | 중단 시 |
|---|---|---|
| `classify-items` | pure-reauthor | 다시 수행 |
| `probe-item` | idempotent-by-key | 저장된 probe 를 **읽는다**. 다시 판정하지 않는다 |
| `freeze-item-route` | idempotent-by-key | 내용주소화. 다이제스트 동일하면 무동작 |
| `dispatch-item` | **externally-visible** | **살아 있을 수 있는 자식을 다시 dispatch 하지 않는다.** 자식의 `pipeline.jsonl` 이벤트를 먼저 확인 |
| `deliver-item` | **externally-visible** | `gh pr list --head` / `git log` trailer 로 이미 인도됐는지 먼저 확인 |

`probe-item` 이 `pure-reauthor` 가 **아닌** 이유는 orchestrator `probe-route` 와 같다 — 재수행이 다른 rung 을 낼 수 있다(`run-ledger.md:120`).

3. **엔진 재개는 엔진에 위임** — `orchestrate resume` / wave-master §0.6 첫 미완료 wave / `kiwi-pm --resume`. 하네스가 엔진 내부 상태를 재구성하지 않는다.

**재개의 가장 큰 실전 위험**(메모리 `kiwi-bg-agent-session-scoped-unreachable`): 백그라운드 teammate 이름은 **런타임 세션 스코프**라, 세션이 바뀌면 이전 세션에 spawn 한 에이전트가 전부 unreachable 이 된다. 따라서 하네스는 **살아 있는 에이전트에 메시지를 보내는 방식으로 재개하지 않는다** — 디스크 아티팩트(원장 + 엔진 저널)에서만 상태를 복원하고, 재spawn 은 `args_hash` 멱등 키로 한다.

## 12. 종합 — 세 연구의 합성과 남은 결정

### 12.1 세 권고는 하나의 그림으로 합쳐진다

| 연구 | 권고 | 층 |
|---|---|---|
| A (intake) | 새 독립 스킬 — intake·분류·원장·dispatch·인도만, 실행은 재발명하지 않음 | 지휘 층 |
| C (harness) | 새 스킬 `kiwi-conductor` — 항목 라우팅 사다리(H-DIRECT→…→H-ORCH)·원장·인도 홉·예산 | 지휘 층 |
| B (graph) | orchestrator phase2 lane 실행기 완성 — kiwi-pm 은 병렬 피호출자로 이미 완성 | 실행 층 |

**A 와 C 는 같은 스킬의 두 절반이다.** A 의 `kiwi-backlog` 와 C 의 `kiwi-conductor` 는 이름만 다를 뿐 책임이 정확히 이어진다 — A 가 §1~§3(입력→분류→원장), C 가 §1~§4(라우팅→위임 경계→인도→수명주기). 하나의 스킬로 합쳐야 하며(§10.2 중복 금지), 이름은 결정 대기다. 이 문서는 이후 `kiwi-conductor` 로 통칭한다.

**B 는 독립 트랙이다.** conductor 는 병렬 실행 없이도 성립한다(항목을 순서대로 기존 엔진에 넘기는 것만으로 G1·G5·G7 이 닫힌다). 병렬은 실행 층(phase2 완성)의 일이고, conductor 가 완성된 뒤 `H-ORCH` 항목의 내부에서만 발현한다. **두 트랙을 한 target 에 묶지 않는 것**이 각자의 검증을 가능하게 한다.

### 12.2 두 연구가 독립적으로 수렴한 지점 (신뢰도 높음)

- **재개는 디스크 아티팩트에서만** — A §3.3, B §3, C §4.5 전부 같은 결론. 근거도 동일(`run-ledger.md`, 세션-스코프 unreachable 실사고)
- **`dispatch` 는 externally-visible** — 살아 있을 수 있는 자식 재-dispatch 금지. A R4, B §3.1, C §4.5 의 verb 표
- **인도는 엔진 종료 후 별도 홉** — A §5 후보 14, C §3(D-1~D-6). 엔진의 금지 계약을 완화하지 않는다
- **verb 선언만으로는 아무것도 강제되지 않는다** — A §3.4 실측, B N8, C 는 그 전제 위에서 설계. **단 반례가 하나 있다(§13.2 H-1)**: `abort_gate` 는 append 시점에 어휘 검사로 실제 거부된다. verb 미검사·abort_gate 검사의 비대칭이 정확한 서술이며, 배치 verb 의 강제는 발명이 아니라 그 기존 검사에 얹는 일이다

### 12.5 결정 — 2026-08-19 사용자 확정: "결정사항은 모두 권장 사항을 따라간다"

1. **스킬 이름과 범위** — ✅ **`kiwi-conductor` 단일 스킬(A+C 합본) 승인.** 범위는 intake·분류·원장·라우팅·dispatch·인도·예산이며, 구현·검증 루프·wave 실행은 한 줄도 재구현하지 않고 기존 스킬에 위임한다(연구 A §4.2 범위 경계 + 연구 C §2.3 경계선).
2. **fold 규칙(B N3)** — ✅ **현행 유지.** 규칙의 근거(per-lane overhead 고정, 이득은 내부 작업량 비례)는 타당하고 실제 planner 산출물은 `tdd-pair`/`req-shared` 로 묶여 안전하다(연구 B §2.4). planner 에 쌍 강제를 추가하지 않는다. 배치 묶음은 C-1 권고대로 **conductor 자체 union-find** 로 계산하고 lane-plan 은 `H-ORCH` 항목 내부 전용으로 남긴다.
3. **인도 기본값** — ✅ **D-1~D-6 채택**: `--auto` 없으면 `none`(항목마다 인도 명령을 보고만), 있으면 `pr`. A R5(배치 대량 외부 부작용)는 위험으로 존치하되, D-3(닫힌 enum — base 직접 병합은 어떤 값에도 없음)과 §3.3 자식 게이트 bubble(push 충돌·보호 브랜치는 `--auto` 라도 중단)이 방어선이다.
4. **병렬 트랙 착수 시점** — ✅ **conductor 선행, 병렬(phase2 lane 실행기 완성)은 별도 target 으로 이후 착수.** 두 트랙을 한 target 에 묶지 않는다(§12.1 — conductor 는 병렬 없이도 G1·G5·G7 을 닫는다).
5. **`H-PIPE` 인도 인터록(§13.2 H-3)** — ✅ **옵션 (b): `H-PIPE` 는 `--wt` 없이 host root 에서 돌리고, 인도는 다른 rung 과 동일하게 conductor 의 종료 후 별도 홉(`kiwi-commit-auto-pr`)으로 연다.** 이 항목만은 문서에 단일 권장안이 없어 문서 자신의 수렴 결론에서 도출했다 — §12.2 가 세 연구의 수렴 지점으로 "인도는 엔진 종료 후 별도 홉"을 들었고, (b) 만이 그 원칙·run-root 불변 유지·`kiwi-pipeline` 4사본 게이트 신설 불요를 동시에 만족한다. 이 결정으로 §11 1.5/D-5 표의 `H-PIPE` 행("인도 홉 없음, `--wt` 포함")은 **개정**된다 — `H-PIPE` 도 인도 홉을 갖고, pipeline 의 §2.6.3 자동 PR 은 발동 조건(`--wt`) 자체가 오지 않으므로 이중 PR 위험도 소멸한다.
