## 0. 요약

1. **현재 검색은 한국어에서 사실상 쓸 수 없습니다.** 한국어 질의 38개에서 MRR 0.053 입니다. 한국어로 쓴 요구를 한국어로 찾을 때도 원문과 글자가 똑같은 2건만 찾았고, 영어로 쓴 요구를 한국어로 찾은 20건은 모두 0건이었습니다.
2. **한국어 토큰화는 형태소 분석기 없이 "단어 안 문자 2-gram" 으로 충분합니다.** 한국어로 쓴 요구에서 Recall@10 0.944, MRR 0.948 이 나왔습니다. 형태소 분석기(Kiwi · Okt)의 0.911~0.920 과 같거나 낫습니다. 조사가 붙은 경우와 띄어쓰기가 다른 경우("저장소루트 자동탐지", "파싱성능")를 모두 풀었고, 색인 생성 시간도 늘지 않았습니다.
3. **교차 언어(한국어 질의 → 영어 본문)는 토큰화로는 풀 수 없습니다. 효과가 있었던 것은 한국어→영어 용어집으로 질의를 넓히는 방법 하나뿐이었습니다.** 용어집이 없으면 Recall@10 0.075 이고, README 의 한영 대응 줄에서 자동으로 뽑은 용어집과 독립적으로 쓴 용어집을 합치면 0.43~0.52 가 됩니다. 질의어를 미리 본 용어집으로는 0.55~0.68 까지 올라갑니다. 용어집이 얼마나 많은 용어를 덮느냐가 성능을 좌우합니다.
4. **같은 요구를 영어로 물으면 MRR 0.922, 한국어로 물으면 용어집을 써도 0.396 입니다**(같은 의도의 질의 16쌍). 검색을 부르는 쪽은 대개 한국어와 영어를 둘 다 아는 LLM 에이전트이므로, 에이전트가 한국어 요청을 영어 검색어로 바꾸거나 두 언어를 함께 넣게 하는 지침이 도구 쪽 용어집보다 효과가 큽니다. 한 문자열에 두 언어를 함께 넣으면 MRR 0.773 이었습니다.
5. **권고:** 구문 일치 결과를 앞세운 하이브리드 BM25F, 한글은 단어 안 2-gram, 번들 한국어→영어 용어집 확장(가중치 0.6), 형태소 분석기 의존성 없음, 에이전트 지침에 이중 언어 검색을 명시합니다. 영어 · 식별자 검색은 1차 측정대로 하이브리드에서 손실 없이 좋아집니다(§8).

### 1.2 동작 요약 **[사실]**

- **매칭 방식:** 질의 전체를 한 덩어리로 보는 부분 문자열 검색입니다. `query.trim().toLowerCase()` 를 각 필드의 `toLowerCase()` 결과에서 `indexOf` 로 찾습니다(`discovery.ts:161-173`). 토큰 분리 · 어간 처리 · 정규식 · 퍼지 매칭이 모두 없습니다.
- **한국어 처리:** 따로 처리하는 것이 없습니다. 한글에는 대소문자가 없으므로 소문자 변환도 효과가 없습니다. 그래서 한국어 질의는 조사 · 어미 · 띄어쓰기까지 원문과 똑같은 문자열일 때만 찾힙니다. 한 단어짜리 질의("탐지")는 부분 문자열이라서 찾히지만, 단어가 둘 이상이면 그 사이의 조사와 띄어쓰기까지 같아야 합니다.
- **검색 필드**(`discovery.ts:138-151`): `id`, `title`, `requirement`, `rationale`, `research`, `acceptanceCriteria`, `verificationEvidence`, `traceLinks`, `relatedDocs`, `changeNotes`. `tags` 와 `implementationNotes` 는 검색하지 않습니다.
- **정렬:** 관련도가 아니라 요구 ID 사전순입니다(`discovery.ts:180`). DISCARDED 요구도 섞여 나옵니다.
- **스니펫:** 질의가 처음 나타난 지점의 앞 60자, 뒤 100자를 잘라 필드 순서대로 최대 3개를 돌려줍니다(`discovery.ts:153-159`, `172`).
- **결과 상한:** 기본값이 없습니다(`discovery.ts:89`, `page.limit = null`).
- **출력 모양:** `--format` · `--fields` 를 받지만 검색은 이를 무시하고 고정 모양을 돌려줍니다(`discovery.ts:182-195`).

## 3. 현재 검색의 한국어 실패: 실제 출력 **[사실]**

`node bin/speckiwi search "<질의>" --json` 의 출력에서 레코드 ID · 제목 · 스니펫과 `page` 만 남겼습니다.

```text
### speckiwi search "저장소 루트 자동 탐지" --json
{"records":[{"id":"FR-ARCH-002","title":"저장소 루트 자동 탐지","snippets":[{"field":"title","text":"저장소 루트 자동 탐지"}]}],"page":{"total":1,"offset":0,"limit":null,"returned":1,"nextOffset":null,"truncated":false}}
```

```text
### speckiwi search "저장소의 루트를 자동으로 탐지" --json
{"records":[],"page":{"total":0,"offset":0,"limit":null,"returned":0,"nextOffset":null,"truncated":false}}
```

**띄어쓰기가 다르면 0건입니다.** 원문은 "저장소 루트 자동 탐지" 와 "일반 저장소 파싱 성능"(PERF-PARSE-001)입니다.

## 5. 교차 언어: 한국어 질의로 영어 요구 찾기

### 5.1 용어집 확장의 효과 **[사실]**

질의의 한글 단어(그대로, 조사 제거형, 붙여 쓴 경우는 용어집 키로 앞에서부터 가장 길게 나눈 조각)를 용어집에서 찾아, 나온 영어 단어를 가중치 0.6 으로 질의에 더했습니다. 한→영 20개의 결과입니다.

| 한글 처리 | 용어집 | R@5 | R@10 | MRR |
|---|---|---|---|---|
| `bi` | 없음 | 0.075 | 0.075 | 0.115 |
| `bi` | `mined`(README 자동 추출) | 0.250 | 0.341 | 0.295 |
| `bi` | `blindNoEx` | 0.192 | 0.192 | 0.209 |
| `bi` | **`mined + blindNoEx`(누설 없음)** | **0.301** | **0.425** | **0.435** |
| `bi` | `blind`(누설 있음) | 0.402 | 0.538 | 0.484 |
| `bi` | `mined + blind`(누설 있음) | 0.368 | 0.550 | 0.525 |
| `ws` | `mined + blindNoEx` | 0.419 | 0.521 | 0.461 |

- 용어집은 한→영 R@10 을 0.075 에서 0.43~0.52(누설 없음), 0.55~0.68(누설 있음)로 올렸습니다. 한글 처리 방식 사이의 차이보다 용어집 유무와 범위의 차이가 훨씬 큽니다.
- 한→영에서는 2-gram 이 공백 분리보다 약간 낮았습니다(R@10 0.425 대 0.521). 2-gram 조각이 한국어로 쓴 다른 요구에 엉뚱하게 걸리기 때문입니다 **[추정]**. 다만 차이는 질의 20개 중 2개 정도에 해당하므로 잡음 범위와 겹칩니다.

### 5.2 용어집으로도 남는 실패 **[사실]**

| 질의 | `bi + mined+blindNoEx` 순위 | 원인 |
|---|---|---|
| 스킬 설치 원본 | 16위 | "원본" → `source` 가 누설 통제로 빠졌다. 남은 `skill` · `install` 은 너무 흔한 단어다 |
| 스코프 이름 바꾸기 | 212위 | "스코프" 가 자동 추출 용어집에 없다(README 는 "범위" 로 번역했다) |
| 요구를 다른 타깃으로 옮기기 | 91위 | "옮기" → `move` 는 누설 통제로 빠졌다. 정답은 `retarget` 이라는 영어 동의어를 쓴다 |

## 10. 권고와 설계

### 10.1 판정

**BM25F 를 하이브리드로 붙이고, 한국어 처리를 그 기본 동작에 넣기를 권고합니다.** 기본값으로 켜고, 이전 동작이 필요할 때를 위해 exact 모드를 둡니다.

### 10.2 한국어 처리 방식

1. **한글 토큰화:** 연속한 한글 음절을 한 단어로 보고, 단어 안 문자 2-gram 을 색인 용어로 씁니다. 한 글자 단어는 그대로 둡니다. 색인과 질의에 같은 규칙을 씁니다. 조사 · 어미 제거와 형태소 분석은 하지 않습니다.
   - 근거: 한→한 R@10 0.944, MRR 0.948 로 비교한 방식 중 최상위이고, 띄어쓰기 차이를 푸는 유일한 무의존 방식입니다. 색인 크기는 공백 분리의 약 1.03배(이 코퍼스)~1.21배(한국어만 있는 경우)입니다.
2. **한영 경계:** "completed-work와" 처럼 붙어 있는 문자열은 라틴 부분과 한글 부분을 나눕니다. 라틴 부분은 영어 규칙(소문자, 영숫자 분리, camelCase · snake_case 분리, 간이 어간 처리, 불용어 제거)을 따릅니다.
3. **한국어→영어 용어집 확장:** 질의의 한글 단어를 번들 용어집에서 찾아 나온 영어 단어를 가중치 0.6 으로 질의에 더합니다. 찾는 순서는 원형, 조사 제거형, 용어집 키로 앞에서부터 가장 길게 나눈 조각입니다.
   - 용어집은 `src/core/query/` 옆의 정적 데이터 파일 하나로 둡니다. 설정 옵션이나 프로젝트별 확장은 지금 만들지 않습니다.
   - 처음 내용은 README 의 한영 대응 줄에서 자동으로 뽑은 후보(이 연구의 `mine-glossary.mjs` 방식)를 사람이 다듬어 만듭니다. SRS 제목의 영어 용어, 그리고 음차어(스킬 · 리뷰 · 루프 · 게이트 · 캐시 · 타깃/타겟 · 스코프 등)와 개념어를 덮게 합니다.
   - README 의 한국어 절반이 바뀔 때 후보를 다시 뽑아 빠진 용어를 찾는 기계적 검사를 둘 수 있습니다. 이것은 별도 판단 대상입니다 **[추정]**.
4. **에이전트 지침:** 사용자가 한국어로 요청하면 검색어에 한국어 단어와 영어 단어를 함께 넣으라고 스킬과 에이전트 지침 블록에 적습니다. 같은 의도에서 영어 MRR 0.922, 한국어만 0.396, 두 언어 혼합 0.773 이었습니다(§5.3).
5. **하지 않는 것:** 형태소 분석기 의존성(§6), 음차 자동 변환(규칙 기반 음차는 오탐이 많아 측정하지 않았습니다), 임베딩 기반 의미 검색(이 연구 범위 밖).

### 10.3 랭킹과 출력

- 1단: 현재와 같은 구문 부분 문자열 일치. 대상 필드도 현재와 같게 둡니다(IR-CLI-029 AC-3).
- 2단: 핵심 필드 BM25F(`id` 3, `title` 3, `tags` 2, `requirement` 1.5, `acceptanceCriteria` 1). k1=1.2, b=0.75 입니다. 질의 단어의 절반 이상이 맞아야 하고, 단어 하나는 그 자신이나 용어집 확장 중 하나가 맞으면 맞은 것으로 칩니다.
- 같은 단 안에서 DISCARDED 는 맨 뒤로, 동점은 요구 ID 오름차순으로 둡니다.
- 검색에만 기본 상한 20 을 둡니다.
- 결과마다 `score`, `match`, `matchedTerms` 를 추가 필드로 붙입니다.
- exact 모드(`--exact` / `match: "exact"`)는 5.1.x 와 같은 결과(구문 일치, ID 순, 상한 없음)를 돌려줍니다.

### 10.4 직접 구현

라이브러리(MiniSearch)와 형태소 분석기 모두 품질 이득이 없었습니다. 품질을 좌우한 부분(한글 2-gram, 용어집 확장, 하이브리드, 강등)은 어느 쪽이든 직접 써야 했습니다. 토크나이저 · 색인 · 점수 · 스니펫 · 용어집 확장을 합쳐 약 150~200줄로 예상합니다 **[추정]**. 용어집 데이터는 별도이며, 약 400~600항목 기준 15~30 KB 입니다(이 연구의 용어집이 16 KB · 72 KB).

## 11. 5.2.0 요구 초안(등록하지 않음)

### 초안 A: 코어 랭킹 검색(구문 일치 우선, 한국어 처리 포함)

- 유형 · 범위: FR, NODE(`src/core/query/`)
- 제목: Ranked requirement search that keeps exact-phrase matches first and handles Korean text
- Statement: The requirement search core SHALL return every record whose searched text contains the whole query ahead of records that match only part of the query's words, SHALL order each group by a field-weighted BM25 score with the requirement ID as tie-breaker, and SHALL index Hangul text as in-word character bigrams so Korean queries match regardless of particles and spacing.
- AC
  - AC-1: WHEN the whole query occurs case-insensitively in a record's searched fields, THE SYSTEM SHALL include that record and rank it ahead of every record that matches by words only.
  - AC-2: WHEN a record does not contain the whole query but matches at least half of the query's words in its ID, title, tags, statement or acceptance criteria, THE SYSTEM SHALL include it after the phrase matches, ordered by descending BM25F score, with equal scores ordered by ascending requirement ID.
  - AC-3: WHEN a query or a record contains Hangul, THE SYSTEM SHALL split each run of Hangul syllables into its in-word character bigrams (a one-syllable run stays whole) for both indexing and querying, so that a query differing from the record only by attached particles or by spacing (for example "저장소의 루트를" or "저장소루트" for "저장소 루트") still matches it.
  - AC-4: WHEN a matching record is DISCARDED, THE SYSTEM SHALL rank it after every non-discarded record of the same group.
  - AC-5: WHEN a record is returned, THE SYSTEM SHALL report its match kind (`phrase` or `terms`), the query words it matched and its score beside the existing fields, and every snippet SHALL contain a matched term.
  - AC-6: WHEN the caller asks for exact matching, THE SYSTEM SHALL return only the phrase matches in requirement ID order with no default limit, identical to the result before this requirement.

### 초안 B: 한국어→영어 용어집 확장

- 유형 · 범위: FR, NODE(`src/core/query/`)
- 제목: Korean query words expand to their English equivalents from a bundled glossary
- Statement: The requirement search core SHALL expand each Hangul word of a query with the English words a bundled Korean-to-English glossary lists for it, at a lower weight than the word itself, so a Korean query reaches requirements written in English.
- AC
  - AC-1: WHEN a Hangul query word, its form with a trailing particle or ending removed, or a longest-first segmentation of it into glossary keys is found in the bundled glossary, THE SYSTEM SHALL add the listed English words to the query at a weight below that of the query's own words.
  - AC-2: WHEN a record matches a query word only through an expansion, THE SYSTEM SHALL count that word as matched for the half-of-the-words rule and SHALL report both the Korean word and the English word that matched.
  - AC-3: WHEN `리뷰 루프 라운드 상한` is searched on this repository's SRS, THE SYSTEM SHALL return FR-FLOW-145 within the first ten results (회귀 고정용 대표 질의. 구현 시 질의 3~5개로 늘린다).
  - AC-4: THE SYSTEM SHALL keep the glossary as one static data file shipped with the package and SHALL NOT read any glossary from the network or from the user's machine.
  - AC-5: WHEN the query has no Hangul word, THE SYSTEM SHALL produce exactly the result it produces without the glossary.

### 초안 C: CLI · MCP 표면

- 유형 · 범위: IR, CLI 와 FR, MCP(두 요구로 나눌 수 있다)
- 제목: search and search_requirements return ranked results under a default limit, with an exact mode
- Statement: `speckiwi search` and MCP `search_requirements` SHALL return the ranked search result under a default limit of 20 records, SHALL accept an exact mode that restores phrase-only matching, and SHALL return the same result for the same query and filters.
- AC
  - AC-1: WHEN `speckiwi search` or `search_requirements` runs without a limit, THE SYSTEM SHALL return at most 20 records and report `total`, `nextOffset` and `truncated` in `page`.
  - AC-2: WHEN `--exact` is passed to `speckiwi search` or `match: "exact"` to `search_requirements`, THE SYSTEM SHALL return the exact-matching result of the core.
  - AC-3: WHEN the same query, filters, limit and offset are given to the CLI and to MCP, THE SYSTEM SHALL return the same record IDs in the same order with the same snippets and page.
  - AC-4: WHEN no word of the query occurs in the SRS or in the glossary, THE SYSTEM SHALL return an empty result with exit code 0 (IR-CLI-100 AC-5 의 테스트 질의 교체와 함께 처리).
  - AC-5: THE SYSTEM SHALL describe ranking, Korean handling, the default limit and the exact mode in the `search_requirements` tool description and in `speckiwi search --help`.

### 초안 D: MCP 색인 메모리 재사용

- 유형 · 범위: FR, MCP
- 제목: The MCP server reuses the search index while the SRS files are unchanged
- AC
  - AC-1: WHEN `search_requirements` is called again for the same workspace root and the SRS file hash is unchanged, THE SYSTEM SHALL answer from the index already built.
  - AC-2: WHEN any file under `docs/spec/` changes between two calls, THE SYSTEM SHALL rebuild the index before answering.
  - AC-3: WHEN two calls for the same key arrive while the index is being built, THE SYSTEM SHALL build it once and answer both from that build.
  - AC-4: THE SYSTEM SHALL NOT create or modify any file to build or keep the index.

### 초안 E: 에이전트 지침의 이중 언어 검색(FLOW)

- 유형 · 범위: FR, FLOW(에이전트 지침 블록과 `search_requirements` 를 부르는 스킬)
- 제목: Agents search the SRS in its own language and add English words when the user writes in Korean
