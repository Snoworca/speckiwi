## 1. Purpose

This document consolidates research for resolving every priority identified in the SpecKiwi spec-management effectiveness analysis.

The research followed the requested loop:

1. Three research agents split the work.
2. Two evaluator agents reviewed the three research outputs.
3. The three research agents revised their recommendations from the evaluator feedback.
4. This document synthesizes the final result.

No implementation was performed in this research step.

## 2. Final Judgment

SpecKiwi already works as a practical Git-native Markdown SRS workflow tool, but its current `verified` SRS state is stronger than what the implementation and release gate actually prove.

The hardening work should be treated as a new `v1.2.0` governance target, not as small cleanup.

The main decision is:

> Make release readiness, parser validation, diagnostic codes, agent files, package init, table mutation safety, and CLI/MCP read contracts consistent enough that `verified` means the tool can actually prove the requirement.

## 3. Current Strategic Gaps

### 3.1 SRS Target State Drift

`docs/spec/00.index.md` currently records `Active Target | v1.1.0` and a `Completed Work Log` row for v1.1.0 completion, while the Target Map still marks `v1.1.0` as active.

Relevant anchors:

- `docs/spec/00.index.md:9`
- `docs/spec/00.index.md:47-49`
- `docs/spec/00.index.md:85-89`

Recommended policy:

1. Add a new target `v1.2.0` for hardening.
2. Make `Active Target` point to `v1.2.0` when this work starts.
3. Move `v1.1.0` out of active status.
4. Decide whether `released` is an official Target Map status. Current rules list `planned`, `active`, `frozen`, `completed`, `archived`, while the index uses `released`.

Relevant anchors:

- `docs/rule/SRS-MD-Rules-v1.0.0.md:306-314`
- `docs/spec/00.index.md:47`

Recommended decision: officially add `released` to Target Map status enum, with meaning “release-readiness passed and baseline is immutable.” Keep `completed` for done but not necessarily released targets.

## 4. Revised Priority Model

### P0: Trust the Current Workflow

P0 items block strong trust in the current SRS workflow.

| Area | P0 Requirement |
|---|---|
| Release governance | Redefine release readiness as a core contract, not just a script wrapper. |
| Evidence and AC coverage | Verify every verified requirement across `docs/spec`, including evidence reference existence and AC coverage. |
| Active target release check | Use Active Target by default or fail if no target is explicit/active. Remove hard-coded `v1.0.0` default. |
| Diagnostic registry | Create a code-level diagnostic registry and make rules docs/tests match it. |
| Parser correctness | Add fenced-code awareness, block boundary rules, duplicate section detection, nested AC detection, forbidden heading content diagnostics, malformed table diagnostics. |
| Table mutation safety | Apply one shared table-cell safety policy to every mutation that writes Markdown table cells. |
| Canonical agent files | Add or enforce root `AGENTS.md` and `CLAUDE.md`; demote lowercase `agents.md` to non-canonical or mirror it intentionally. |
| Package init rules | Load bundled rules package-relative, not cwd-relative. |

### P1: Consistency and Release Maturity

| Area | P1 Requirement |
|---|---|
| Index validation | Validate duplicate targets, duplicate scope prefixes, multiple active rows, scope document existence, unregistered `.srs.md`, Status Summary drift, Requirement Type Summary drift. |
| Completed Work Log | Define latest ordering and prevalidate new rows while leaving historical rows as warnings. |
| CLI/MCP parity | Normalize summary, targets, validate, active-target, completed-work, diagnostics shape across CLI/MCP. |
| MCP resource shape | Choose one resource payload policy and document compatibility impact. |
| CI and coverage | Add GitHub Actions and coverage thresholds for core parser/validator/mutation/workflow layers. |
| Concurrency | Add optimistic stale-file/stale-insert guards for generated ID mutations. |

### P2: Long-Term Maturity

| Area | P2 Requirement |
|---|---|
| Read diagnostics UX | Expand optional diagnostics summaries across read commands/tools. |
| Fixture corpus | Add code fence, duplicate section, nested AC, malformed table, stale evidence, broken local path, CRLF, and multi-scope drift fixtures. |
| Derived rollups | Consider derived/auto-updated Status Summary and Requirement Type Summary. |
| AST parser | Consider AST-backed Markdown parsing only after line parser hardening reaches its limit. |

## 5. P0 Research Detail

### 5.1 Release Readiness Core Contract

The release gate should be centered on `src/core/workflow/release-readiness.ts`, not on `scripts/release-check.mjs`.

Current contract is too small:

- `src/core/workflow/release-readiness.ts:10-19`
- `src/core/workflow/release-readiness.ts:36-52`

Recommended `ReleaseReadinessSummary` fields:

```ts
interface ReleaseReadinessSummary {
  target: string;
  targetSource: "explicit" | "active-target";
  ready: boolean;
  diagnosticsSummary: DiagnosticsSummary;
  blocked: string[];
  plannedOrInProgress: string[];
  implementedNotVerified: string[];
  criticalHighUnverified: string[];
  missingEvidence: string[];
  acCoverageGaps: Array<{ requirementId: string; missingAcIds: string[] }>;
  missingEvidenceReferences: Array<{ requirementId: string; reference: string }>;
  brokenTraceLinks: string[];
  warnings: string[];
  baselineCommand: string;
}
```

Release target resolution:

1. If CLI/script provides target, use it.
2. Else use `workspace.index.activeTarget`.
3. If active target is empty, return `ready=false`.

This matches the active target workflow in SRS:

- `docs/spec/60.workflow-release.srs.md:187`
- `docs/spec/60.workflow-release.srs.md:207`

### 5.2 Evidence and AC Coverage Gate

Current verified guard only checks:

- every AC is checked
- at least one evidence row has a non-empty reference

Relevant anchors:

- `src/core/validator/rules.ts:25-30`
- `src/core/validator/rules.ts:84-85`

P0 release acceptance should check:

1. Every verified requirement has all AC checked.
2. Every AC is covered by evidence `Covers = all` or explicit `AC-N`.
3. Local evidence references exist under the project root.
4. URL evidence is syntactically valid.
5. Command evidence is classified and policy-controlled.
6. Requirement trace links resolve.

Evidence parser already stores `covers`:

- `src/core/parser/evidence-parser.ts:7-15`

The release gate must actually use it.

### 5.3 Diagnostic Registry

Current diagnostic meaning is scattered and inconsistent.

Recommended registry shape:

```ts
interface DiagnosticDefinition {
  code: string;
  severity: "error" | "warning" | "info";
  title: string;
  messageTemplate: string;
  sourceRule: string;
  since: string;
}
```

P0 acceptance:

1. All `diagnostic(...)` calls use a code from the registry.
2. Rules doc diagnostic table is generated from or contract-tested against the registry.
3. Tests assert `SRS-E001`, `SRS-E002`, etc. have one meaning.

Relevant anchors:

- `docs/rule/SRS-MD-Rules-v1.0.0.md:1439-1466`
- `src/core/parser/block-scanner.ts:31-32`
- `src/core/validator/rules.ts:55-85`

### 5.4 Parser Boundary and Code Fence Rules

Current scanner:

- scans every line beginning `### `
- ignores fenced code state
- ends blocks at next requirement heading or EOF

Relevant anchor:

- `src/core/parser/block-scanner.ts:23-40`

Recommended rule change:

1. Parse requirement blocks inside `## 4. Requirements`.
2. Ignore headings inside fenced code blocks.
3. End a requirement block at the next valid requirement heading, next relevant top-level `## ` section, or EOF.

Migration impact:

- Current `record.markdown` for the final requirement may include trailing document sections.
- Tests and downstream consumers relying on that accidental inclusion must be updated.
- SRS rule text must change before implementation because current rule says next requirement or EOF.

Relevant rule anchor:

- `docs/rule/SRS-MD-Rules-v1.0.0.md:490`

### 5.5 Parser Diagnostics Fixture Set

P0 parser fixture minimum:

| Fixture | Expected Behavior |
|---|---|
| code fence contains `### FR-...` | No requirement record and no malformed heading diagnostic from fenced content. |
| duplicate `#### Requirement` in one block | Error diagnostic with line of duplicate section. |
| nested `- [ ] AC-2` | Error diagnostic and not counted as top-level AC. |
| heading contains `[link](x)` | Error diagnostic. |
| heading contains `**bold**` | Error diagnostic. |
| heading contains inline code | Error diagnostic. |
| heading contains emoji | Error diagnostic. |
| table row cell count mismatch | Error or warning diagnostic depending on table type. |

### 5.6 Shared Table Cell Safety

Recommended policy for v1.2.0:

- Reject pipe `|` and newline in table cells for all mutation commands.
- Do not support escaped pipe round-trip yet.
- Expose one shared helper used by all table-writing mutations.

Affected paths:

- `src/core/mutation/render-requirement.ts:50-61`
- `src/core/mutation/add-evidence.ts:16-24`
- `src/core/mutation/add-trace.ts:17-27`
- `src/core/mutation/add-completed-work.ts:118-123`

6. Status Summary drift
7. Requirement Type Summary drift

Status/type rollups exist in the index:

- `docs/spec/00.index.md:61-82`

### 6.2 Completed Work Log Policy

Current query returns the first N matching rows:

- `src/core/query/completed-work.ts:32-35`

Recommended policy:

1. Define default ordering as latest by `Date` descending, then source line descending.
2. Optionally support `--order file|latest`.
3. Existing historical inconsistent rows remain validator warnings.
4. New mutation rows are prevalidated by default.
5. Add explicit override for intentionally historical/incomplete rows.

Prevalidation checks:

- target exists unless target is empty
- each scope token exists
- each requirement ID exists
- referenced requirements are `implemented` or `verified`

Relevant anchors:

- `src/core/mutation/add-completed-work.ts:111-133`
- `src/core/validator/rules.ts:110-130`

### 6.4 MCP Resource Payload Policy

Two viable options:

1. Envelope all resources:

```json
{
  "ok": true,
  "value": {},
  "diagnostics": [],
  "diagnosticsSummary": { "errors": 0, "warnings": 0, "byCode": {} }
}
```

2. Raw domain payload for all resources.

Recommended: envelope all resources for consistency and diagnostics, but introduce compatibility carefully because `speckiwi://completed-work` currently returns raw `{ completedWork }` in stdio tests.

Relevant anchor:

- `test/mcp/stdio-purity.test.ts:60-63`

### 6.5 CI and Coverage

CI is currently documented as example-level, not enforced.

Relevant anchors:

- `docs/spec/60.workflow-release.srs.md:235-264`
- `docs/ci/spec-validation-example.md:5`
- `package.json:45-53`

P1 recommendation:

- Add `.github/workflows/ci.yml`.
- Run `npm ci`, `npm run build`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:integration`, `npm run release:acceptance`, `npm run release:check`, `npm run perf:srs`.
- Add `test:coverage` script.
- Set global coverage threshold around 80%.
- Set parser/validator/mutation/workflow threshold around 90%.

### 6.6 Optimistic Concurrency and Stale Insert Guard

Generated IDs are vulnerable to concurrent mutation.

Relevant anchors:

- `src/core/mutation/add-requirement.ts:26-33`
- `src/core/mutation/add-requirement.ts:133-145`
- `src/core/mutation/add-evidence.ts:20`
- `src/core/patch/patch-plan.ts:29-36`

P1 policy:

1. Add file snapshot hash or mtime/size to `TextFile`.
2. Re-read file before write.
3. If hash changed, return `STALE_PATCH`.
4. For insert operations, add neighbor/section-end precondition.
5. For generated IDs, allow one safe reparse/retry or return retry guidance.

Do not start with lock files unless optimistic checks prove insufficient.

## 8. Implementation Sequencing Recommendation

Do not implement all items as one patch. The correct sequence is:

1. Update SRS target/status and add v1.2.0 hardening requirements.
2. Build diagnostic registry and parser fixtures first.
3. Harden parser/validator and table mutation safety.
4. Redefine release-readiness core and full traceability acceptance.
5. Fix package-relative rules loading and canonical root agent files.
6. Normalize CLI/MCP summary/read/resource contracts.
7. Add index consistency validation and completed-work prevalidation/latest ordering.
8. Add optimistic concurrency/stale insert guard.
9. Add CI/coverage gates.
10. Re-run release readiness for `v1.2.0`, then add Completed Work Log row only after implementation is complete.

## 10. Final Recommendation

The next step should not be direct coding. The next step should be an SRS update for `v1.2.0` that records the hardening target and adds the draft requirements above.

Once the SRS is updated, implementation planning can split work into at least four phases:

1. Parser/diagnostics/table safety.
2. Release governance/evidence gate.
3. Agent/package/CLI/MCP contract hardening.
4. Consistency/concurrency/CI maturity.

This keeps the project aligned with its own rule: implementation should follow SRS requirements, not retroactively justify them.
