## 1. 요약

wave-master 에는 **wave 종료 시점에 그 wave 를 전체로 바라보는 검증이 없다.** 현재 흐름은
`per-wave /kiwi-pipeline 이 TASK_DONE` → `waves.jsonl 에 complete append` → `다음 wave` 세 단계이며,
(a)와 (b) 사이에는 어떤 판단 단계도 존재하지 않는다.

이 공백은 "검증이 부족해서"가 아니라 **구조적**이다 (§3). 기존 검증 계층은 전부
*task 단위* 또는 *diff 단위*로 동작하므로, **wave 의 요구사항 집합 전체를 완성된 산출물과 대조하는 주체가
파이프라인 어디에도 없다.**

본 연구는 그 자리에 **두 검증자의 add-only 교차반박 루프**를 놓고, 그 통과를
`complete` 기록의 **선행 조건**으로 만드는 설계를 채택한다 (§5).

## 3. 왜 기존 계층으로는 안 되는가 (핵심 근거)

wave 하나는 이미 매우 두꺼운 검증을 통과한다 — kiwi-coder 당 Sonnet×4 TDD 검증 + 정형 검사 + 7축 까칠 리뷰,
kiwi-planner 검증 서브에이전트 + validator + 커버리지 루프, 마지막에 kiwi-review-fix-loop.
그럼에도 다음 네 가지는 **구조적으로 탐지 불가**하다.

| # | 공백 | 왜 구조적인가 |
|---|---|---|
| G1 | **wave 의 AC 집합 ↔ 완성된 산출물 대조가 아무데서도 일어나지 않음** | planner 커버리지 루프는 *코드가 존재하기 전* plan↔SRS 만 대조하고, 그 `verification-complete` 마킹은 **영속적**이라 이후 재검증되지 않는다. coder 는 Task 1개를 그 Task 명세와 대조한다. review-fix-loop 의 게이트는 "리뷰어가 CRITICAL/HIGH 를 못 찾음"이지 "모든 AC 가 실현됨"이 아니다 |
| G2 | **부분 구현은 diff 국소 기준으로 무결함** | AC 의 60% 만 구현된 diff 는 그 60% 범위에서 일관되고 테스트되고 결함이 없다. 나머지 40% 는 **diff 안에 없으므로** diff 를 읽는 리뷰어는 원리적으로 볼 수 없다. 리뷰어를 한 명 더 붙여도 해결되지 않는 **스코프 문제** |
| G3 | **Task 간·wave 간 상호작용** | coder 의 검증 단위는 Task 다. 두 Task 가 각각 옳으면서 합성이 틀릴 수 있다. 더 중요하게, wave N 이 wave N-1 의 이미 verified 된 AC 를 깨뜨려도 **wave N-1 의 AC 집합을 스코프에 넣는 계층이 없다.** §3 이 "앞 wave 가 뒤 wave 의 토대"라 규정하므로 이 공백은 wave 수에 비례해 커진다 |
| G4 | **승급에 wave 단위 증거 점검이 없음** | pm 이 wave target REQ 를 implemented 로 올리고 review-fix-loop `--close-reqs` 가 "회귀 PASS + finding 0" 으로 verified 로 올린다 — 즉 **증거의 존재**가 아니라 **이의의 부재**가 근거다. 프로젝트 CLAUDE.md 는 증거 없는 verified 를 금지한다 |

**실증**: `docs/analysis/kiwi-2axis-eval-2026-07-11` 에서 `FR-FLOW-022 AC-2` 미완이
구현 · 좁은 content 테스트 · **3라운드 kiwi-review-fix-loop** · Axis A 자신의 r1/r2 를 **전부 통과**한 뒤
Axis A r3 의 AC 단위 정독에서 처음 검출됐다. G1/G2 의 존재 증명이다.

## 4. 설계 결정 (5인 위원회)

사용자 부재 결정이므로 5인 위원회가 자동결정했다. 렌즈: 관례정합 / 안전·거버넌스 / 비용·실용 / 검증엄밀·안티게이밍 / 사용자의도.

| ID | 결정 | 표 | 요지 |
|---|---|---|---|
| D1 | **C+ 하이브리드** | C 3표 | 두 검증자가 **동일한** 증거 번들을 보되 **stance** 로 분리. 증거를 분리하면 상호검증이 원리적으로 불가능(A 기각). 순수 2축 관례(B)는 "구현과정"을 조용히 삭제 |
| D2 | **B-adversarial (add-only)** | B계열 5/5 | r1 독립·격리 → r2 교차반박. 상대 finding **기각 불가(add-only)**, 병합은 기계적 합집합 |
| D3 | **`complete` append 직전** | **5/5** | 유일하게 FAIL 이 기계적 결과를 갖는 위치 |
| D4 | **optional 필드만, 1.0.0→1.1.0** | **5/5** | status enum 추가 금지 |
| D5 | **review-fix-loop 위임 + 조건부 pipeline 재진입** | 4:1 | wave-master 내부 전용 fixer 신설 **금지** |
| D6 | Normal=**수정 없는 clean 라운드**, --max=2연속, cap **5/8** | 4:1 | cap 소진은 **PASS 가 아니다** |
| D7 | 잔여 CRITICAL/HIGH 는 --auto 로도 HALT + `critical_gates[]` 신설 | **5/5** | 현재 미선언 = `--auto` 비활성이라는 **기존 결함** 동반 해소 |
| D8 | **신규 타깃 v2.4.3** | **5/5** | v2.4.2 목표는 run-root 무결성으로 명시 한정 |

### 4.1 D2 가 add-only 여야 하는 이유

일반적인 상호 판정(각자 상대 finding 을 기각 가능)은 **담합 보상**을 만든다 — 두 에이전트의 국소 이해가
모두 "wave 를 끝내는 것"을 가리키므로, 최단 경로는 **상호 기각**이다. 검증자에게 지우개를 쥐어주는 셈이다.
add-only 로 두면 기각으로 얻는 것이 없고, **상대가 놓친 것을 찾는 행위만이 점수가 되는** 유일한 동작이 된다.

닫는 경로는 셋뿐이며 전부 감사 가능하다: (i) 수정 후 **제기한 축**이 재검증하여 clean, (ii) **제기한 축**이
반대 증거와 함께 철회, (iii) 양 축 만장일치 재분류 — 단 (iii)이 포함된 라운드는 **연속 clean 스트릭에 산입되지 않는다**
(기각에 라운드 비용을 물려 유인을 역전).

### 4.2 D3 가 만장일치인 이유

`complete` 는 **취소 불가**다 — append-only 이고 전이도에 `complete → failed` 간선이 없으며 §0.6 이
완료 wave 를 영구 skip 시킨다. 검증을 `complete` **뒤**에 두면 크래시·컨텍스트 소진·중단 1회가
미검증 wave 를 **영구히** 건너뛰게 만들고, FAIL 이 어떤 후속 동작도 바꾸지 못하므로 게이트가 **장식**이 된다.
앞에 두면 실패 표현이 무료다 — wave 가 `in_progress` 로 남고 §0.6 이 그대로 재진입시킨다. 새 상태도, 새 재개 규칙도 필요 없다.

### 4.3 비용 (반대 의견 반영)

비용 렌즈는 D1 을 A(과정/결과물 분리)로 밀며 "Axis B=품질은 방금 끝난 review-fix-loop 의 재탕"이라 지적했다.
이 지적은 채택되어 설계에 **명시적 out-of-scope 문장**으로 반영됐다 — 본 계층은 **hunk 단위 코드 리뷰를 재수행하지 않는다.**
새 계층이 값을 하는 조건은 *diff* 가 아니라 **wave 단위 증거**를 보는 것이다.

추정 한계비용: 공통 경우(1라운드 clean) 검증자 2회 ≈ wave 당 +2~4%. 최악(cap 5 + 수정 사이클) ≈ +10~20%.
wave 하나가 이미 80~100 서브에이전트 규모임을 감안하면 수용 가능하다.

## 5. 채택 설계

> §5 는 위원회가 **결정한 시점의** 설계다. 구현 후 3라운드 교차검증에서 이 중 여러 항목이 결함으로
> 드러나 바뀌었다 — 최종 출하 형태와의 차이는 **§9** 에 전부 기록했다. 두 절을 함께 읽어야 한다.

### 5.1 배치

```
per-wave /kiwi-pipeline → TASK_DONE
        ↓
[신규] Phase 3.5 웨이브 종료 상호검증 루프   ← 본 연구의 대상
        ↓ (통과해야만)
waves.jsonl 에 complete append → 다음 wave
```

### 5.2 증거 번들 (양 검증자 공통, run 시작 시 pin 된 root 기준)

wave 의 **구현과정**을 읽으려면 다음이 도달 가능해야 한다. `pipeline_run_id` 는 스키마상 optional 이지만
**wave-master 자신의 기록에서는 필수**로 격상한다 — 이것이 wave 에서 `.kiwi/sessions/{run_id}/` 로 가는
유일한 링크이기 때문이다.

| 증거 | 내용 |
|---|---|
| `kiwi/pipeline.jsonl` (해당 wave 창) | 사이클 각 단계의 status/summary/next_hint |
| `kiwi/waves.jsonl` (해당 wave) | order/target/scope/in_progress ts |
| `.kiwi/sessions/{pipeline_run_id}/worklog.jsonl` | Task 별 TDD 단계, **skip/override 기록** |
| `docs/plans/{run-id}.plan.md` + `.sidecar.json` | wave 가 *하기로 한* 것 |
| `docs/analysis/kiwi-review-fix-loop-*/report.md` | finding·severity·라운드·회귀 결과 |
| speckiwi MCP `list_requirements` / `summarize_target` (wave target) | **외부에서 고정된 AC 분모** |
| wave 창의 git diff | 최종 결과물 |

wave 창은 그 wave 의 `pipeline_run_id` + `in_progress` 타임스탬프로 경계 짓는다.

### 5.3 두 검증자

| | 검증자 1 | 검증자 2 |
|---|---|---|
| 주 stance | wave SRS **의도 실현** + **과정 적합** | **결과물 품질** + **교차 wave 회귀 위험** |
| roll-up | `ALL_MATCH` / `GAPS` | `substantive_clean` |
| 필수 산출 | wave target 의 **모든** REQ/AC 를 `list_requirements` 에서 가져와 행 단위 열거, 각 행 `intent_match` + **해소 가능한 증거 포인터** | finding 별 `severity` + `severity_class` |
| 무효 조건 | `checked ≠ expected`, 미해소 증거 포인터 | 산출물 부재/파싱 실패 |

**out-of-scope (양 축 공통)**: hunk 단위 코드 리뷰는 kiwi-review-fix-loop 의 책임이며 여기서 재수행하지 않는다.

AC 분모를 **검증자 자신이 정하지 않고** `list_requirements(target=wave-n)` 에서 가져오는 것이 핵심이다 —
산문은 줄일 수 있어도 **호명은 줄일 수 없고**, 제3자가 같은 목록을 재도출해 행 단위로 재검사할 수 있다.

### 5.4 라운드 구조

```
r1: 검증자 2기 병렬 spawn (격리 — 메인 세션의 결론·정당화 미전달)
r2: 교차반박 — 각자 상대의 finding 목록(주장 + 증거 포인터만, rationale/verdict/confidence 제외)을 받아
    추가(add) 또는 확인(confirm) 만 가능. 기각 불가
    → 병합 = 기계적 합집합 (검증자에게도 메인에게도 재량 없음)
불통과 시: 수정 위임 → 재검증 (라운드 +1)
```

### 5.5 종료 조건

| 모드 | PASS |
|---|---|
| Normal | 병합 후 `CRITICAL=0 AND HIGH=0` AND Axis A `ALL_MATCH` **이며, 그 라운드에서 수정이 적용되지 않았을 것** |
| `--max` | 위 조건 + `MEDIUM=0` 을 **2라운드 연속** |

"수정 없는 clean 라운드" 조항이 저비용 상한을 안전하게 만든다 — 검증자가 본 적 없는 상태에 PASS 를 찍는 것을 막고,
수정이 있었다면 **반드시** 재검증 라운드가 돌게 만든다(= 사용자가 요구한 "반복 개선"의 최소 요건).

cap: 기본 **5**, `--max` **8**, `--mini` 3, `--loops N` 우선(비치명 WARN) — `loop-option.md` v1.0 준수.
**cap 소진은 PASS 가 아니다** — `verdict=fail-cap`, `complete` 미기록, 잔여 전량 보고 후 사용자 결정.

### 5.6 개선(수정) 주체

| finding 종류 | 처리 |
|---|---|
| 품질·회귀·구현 결함 | `/kiwi-review-fix-loop` 위임 (**명시 범위 전달** — 작업이 이미 커밋됐으면 working-tree diff 가 비어 clean 오보) |
| Axis A 갭 중 **계획 자체가 없던** 것 | 해당 wave 의 `/kiwi-pipeline` 재진입 (코드 리뷰어는 계획 항목을 만들 수 없음) |
| SRS 수준(증거 부재 등) 코드로 못 닫는 것 | 잔여로 이관 + 사용자 결정 |
| **이전 wave** 를 건드려야 하는 것 | critical HALT (`complete` 취소 불가 + §0.5 경계) |

**금지**: (a) wave-master 내부 전용 fixer 신설, (b) fixer 의 SRS AC 본문 수정, (c) 기존 테스트 약화·삭제,
(d) fixer 또는 메인의 `severity_class` 작성. **review-fix-loop 자신의 PASS 는 wave 게이트를 충족하지 않는다** —
wave 수준 finding 은 오직 두 축의 재검증으로만 닫힌다.

### 5.7 기록 (waves-event 1.1.0, optional 필드만)

`phase` ("pipeline"|"wave-verify"), `verification` { `rounds` `cap` `verdict`(pass|fail-residual|fail-cap)
`axis_a`{roll_up, expected, checked} `axis_b`{substantive_clean, open{}} `residual[]` `report_path` }.

- `residual[]` 는 **전량**이어야 하며 truncation 금지. 명시적 빈 배열은 반증 가능한 주장이고, 필드 부재는 침묵이다.
- **`complete` 인데 그 run 에 선행 통과 wave-verify 기록이 없으면 무효** — 재개는 그 wave 를 미완료로 간주한다.
  이 조항이 "계층을 통째로 건너뛰기"를 사후 탐지 가능하게 만든다(건너뛴 저널은 기존과 바이트 동일해지므로).
- 라운드 카운터는 재개 시 **누적**(소비는 영속), verdict 는 **비영속**(승인은 비영속).

### 5.8 `critical_gates[]` (신규 선언)

`auto-option.md` §5 상 **미선언 = `--auto` 비활성**이므로, 현재 wave-master 는 `--auto` 를 상세히 문서화하면서도
SSOT 상 비활성인 **모순 상태**다. 신규 게이트가 등록될 채널 자체가 없으므로 본 작업에서 함께 해소한다.

| gate_id | 성격 |
|---|---|
| `run-root-preflight-mismatch` | 기존 §2.1 전사 |
| `wt-delegation-refused` | 기존 §2.1 전사 |
| `child-pipeline-needs-user-or-failed` | 기존 §0.4 전사 |
| `wave-verify-residual-critical` | **신규** — 잔여 CRITICAL/HIGH 또는 Axis A `GAPS` 또는 cap 소진 |
| `wave-verify-cross-wave-fix-required` | **신규** — 이전 wave 의 완료 target 을 건드려야 함 |

기존 3건을 함께 전사하는 이유: 신규 1건만 선언하면 `--auto` 가 이 스킬에서 처음으로 활성화되면서
**나머지 게이트들이 부작용으로 위원회 판단 대상이 된다.** 전사는 그 부작용을 중화한다.
**단, 선언 자체가 `--auto` 의 실질 동작을 바꾸는 변경임을 Change Notes 에 명시한다.**

## 6. 안티-게이밍 규칙 (엄밀성 렌즈)

| 게이밍 경로 | 차단 규칙 |
|---|---|
| 훑고 PASS | Axis A PASS 는 wave target **전 REQ/AC 행 열거** 필수 + `checked == expected` 결정적 대조 |
| 키워드 인용을 증거로 | 모든 `full` 행에 **해소 가능한** 증거 포인터(존재하는 file:line 또는 존재하는 test id) 필수; 미해소 시 라운드 무효 |
| 기준을 약화 | fixer 의 SRS AC 본문 수정 금지, 테스트 약화·삭제 금지(kiwi-tdd §0.5 확장), `severity_class` 는 제기한 축만 작성 |
| cap 소진을 PASS 로 | cap 소진 = `fail-cap`, `complete` 미기록, 잔여 전량 |
| 1회 정독을 2회로 보고 | r2+ 는 **새로 spawn** 하고 직전 finding 을 stripped 형태로만 수신 (인라인 자가검증 금지) |
| 상호 기각으로 clean | **add-only** — 기각 권한 없음; 만장일치 재분류는 스트릭 미산입 |
| 계층 통째로 skip | wave-verify 기록 없는 `complete` 는 무효 |

## 7. 남은 위험 (해소하지 않음, 명시)

1. **분모 자체의 게이밍** — Axis A 는 주어진 목록을 검증할 뿐 그 목록이 빈약한지는 구조적으로 알 수 없다.
   §0.5 는 wave 경계의 *실행 중* 재분할만 막고 **최초 분해**는 감독하지 않는다.
2. **상관된 사각지대** — 같은 증거 번들을 읽는 두 LLM 은 같은 것을 놓칠 수 있다. stance 분리와 출력 스키마
   분리로 완화할 뿐 제거되지 않는다.
3. **false-red 로 인한 이탈** — add-only 는 담합을 막는 대신 환각 finding 이 정상 wave 를 cap 까지 붙잡을 수 있다.
   철회·재분류 경로가 밸브이며, 너무 좁게 쓰면 사용자가 계층 자체를 쓰지 않게 된다.
4. **`--auto` 활성화의 파급** — 기존 결함 해소가 곧 동작 변경이다.

## 9. 검증이 설계를 바꾼 지점

구현 후 독립 검증자 2기(의도+과정 / 품질+회귀)를 **6라운드** 돌렸다. 각 라운드는 직전 finding 을
주장·증거 포인터만 남긴 형태로 넘기고 add-only 로 운영했다. 아래는 §5 의 결정을 **뒤집거나 보강한**
항목만 추린 것이다 — 세부 문구는 SRS(FR-FLOW-044~046)와 스킬 본문이 SSOT 다.

| # | §5 의 결정 | 검증이 밝힌 문제 | 최종 |
|---|---|---|---|
| 1 | 검증 기록을 루프 종료 후 1회 기록 | 루프 **도중** 죽으면 `rounds` 가 하나도 안 남아 재개가 0 부터 다시 센다 — 계약이 약속한 크래시 내성이 거짓이 되고 불안정한 wave 가 `fail-cap` HALT 에 영영 닿지 못한다 | **라운드마다** 기록 |
| 2 | `complete` 무효 조항을 무조건 적용 | 기능 이전에 쓰인 모든 `complete` 를 소급 무효화 → 진행 중인 에픽이 wave-1 부터 재실행. §0.6 멱등 재개 위반 | `schema_version` 1.1.0 이상에만 적용 |
| 3 | (위 유예의 부작용은 미인지) | 버전은 **단속 대상인 생산자가 스스로 쓰는 값** — 1.0.0 으로 낮춰 쓰면 그게 곧 우회 | 유예를 **run 단위**로 판정 |
| 4 | 증거 번들을 `pipeline_run_id` 로 키잉 | `.kiwi/sessions/`·`docs/plans/` 는 **plan run-id**(planner SSOT) 로 키잉된다 — 존재하지 않는 경로를 지시하고 있었다 | plan run-id 로 정정 |
| 5 | (4의 정정이 과일반화) | `docs/analysis/` 는 **스킬마다 자체 run-id** — review-fix-loop 보고서는 그 스킬 이벤트의 `artifacts.analysis_dir` 에서 온다 | 분리 서술 |
| 6 | 재분류 close 경로를 스트릭 제외로 가격 | **Normal 모드에는 스트릭이 없다** → 기본 설정에서 상호 기각이 무료. §5.5.3 이 닫으려던 담합 보상이 그대로 열림 | 모드 무관 **추가 라운드** 강제 |
| 7 | `--max` 스트릭 2연속 (전 변종) | `etc` 호스트 프로파일은 **3연속**을 요구하고 `--max` 가 기본 — 같은 파일 안에 상충하는 두 종료 조건 | etc 만 3, 사유 명시 |
| 8 | "모든 wave 이벤트에 `pipeline_run_id`" | wave 시작 시점에는 pipeline 이 없어 **충족 불가능** | `complete`·`wave-verify` 한정, 첫 `in_progress` 는 **필드만** 생략 |
| 9 | `verdict` 에 `fail-residual` 선언 | 그 값을 **생산하는 규칙이 없음**(고아 enum) | 생산 조건 명시 |
| 10 | `phase` enum 에 `pipeline` 선언 | 동일 — 아무도 쓰지 않음 | wave 시작 이벤트가 기록 |
| 11 | `complete` 앞에 "선행 통과 기록" 요구 | 그 기록을 **쓰는 지시가 없어** 정상 run 의 모든 `complete` 가 무효 | §5.5.6 emit 지시 신설 |
| 12 | 다음 wave 는 `TASK_DONE` 뒤 시작(기존 문장 유지) | 검증 중인 wave 위에 다음 wave 를 쌓게 됨 → halt 게이트 무의미 | 상호검증 통과까지 게이트 |

라운드 4~6 이 추가로 뒤집은 것:

| # | 문제 | 최종 |
|---|---|---|
| 13 | `verdict` enum 이 **종료값만** 있는데 라운드마다 verdict 를 쓰라고 함 — 중간 라운드가 `pass`(게이트 조기 붕괴) 아니면 `fail-residual`(도는 루프를 실패로 읽음) 중 하나를 골라야 했다 | **`in-progress`** 비종료 값 신설 + 게이트를 **최신 1줄** 판정으로 |
| 14 | `r1`/`r2` 표기가 **두 라운드**로 읽혀 add-only 교차반박이 생략 가능해 보임 — Normal PASS 를 단계 1 병합만으로 선언 가능 | "**한 라운드 = 세 단계 전부**", 단계 2 생략 라운드는 **무효** |
| 15 | 조기 종료 문장이 무조건적이라 `--max` 연속 스트릭을 무력화 | **Normal 모드 한정** + "`--max` 에는 조기 종료 없음" 명시 |
| 16 | 1.1.0 유예를 **자기 신고 버전**으로 판정 → 1.0.0 으로 낮춰 쓰는 것이 곧 우회 | **run 단위** 판정 |
| 17 | `list_requirements` 기본이 **compact projection** 이라 AC 를 싣지 않음 — 문자 그대로 따르면 REQ 개수만 세고 AC 정독이 사라짐 | AC 포함 투영 또는 `get_requirement` 명시 |

| 19 | 재개 시 `run_id` 동일성 미규정 — run 스코프 게이트와 재개 횡단 카운터가 다른 run 에 살 수 있음 | 같은 `run_id` 재사용 명시 |

### 9.1 테스트 품질에 대한 기록

검증자들이 **자연어 계약 테스트의 고질적 실패 모드**를 반복 실증했다. 6라운드에 걸쳐 살아남은 뮤테이션이
**27건**, 매 라운드 **새로운 클래스**가 나왔다:

| 라운드 | 생존 뮤테이션 클래스 |
|---|---|
| 1–2 | 문자 창 근접성 (`windowsAround(...).some(...)`) — 옆 문장이 같은 토큰을 공급 |
| 3 | 표 행 삭제 — 설명 산문이 대신 만족 |
| 4 | **헤지** (MUST→SHOULD, "…하되 필요하면 …할 수 있다") — 앵커 토큰은 그대로 |
| 5 | **인접 문단 예외**, 주어 치환, 출처 교체, 범위 축소, 세션 스코핑 |
| 6 | **단계 순서 치환**, 수량자 약화(모든→표본), 술어 극성 반전, 면제 확대, 예제/규범 desync, 숫자 desync |

구체 예: 기본 cap 5 를 7 로 바꿔도 통과(`\b5\b` 가 `### 5.5.1` 헤딩 번호에 걸림) / `cap 소진 → 그대로 진행`
으로 뒤집어도 통과(다음 문장이 `complete` 토큰 공급) / stance 표의 두 열을 통째로 바꿔도 통과(열 결속 부재).
전부 **행·열·문장 단위 앵커**와 **부정형 단언**으로 교체했고, 최종적으로 누적 **58개 뮤테이션이 모두 red** 다.

교훈 셋:

1. `windowsAround(...).some(...)` 같은 **문자 창 근접성**은 규범을 고정하지 못한다. 규범이 표 행이면
   그 행 자체를(`/^\|\s*Normal\s*\|.../m`), 표 열이면 셀 인덱스를, 부정 규칙이면 **부정형 자체를** 단언한다.
2. **토큰 존재 단언은 헤지에 무력하다.** 금지 규칙에는 헤지 어휘(`수 있다`·`권장`·`원칙적으로`) 부재를
   같은 문장 범위에서 함께 단언해야 한다.
3. **적대적 검증자에게는 수렴이 없다.** 자연어 계약은 라운드마다 새로운 우회 클래스를 허용한다 —
   본 작업은 6라운드에서 상한 규약(§5.5.4 기본 5)에 따라 **잔여 보고 후 중단**했고, 요구는
   `verified` 가 아니라 `implemented` 로 남겼다. cap 소진을 PASS 로 쓰지 않는다는 자기 규칙의 dogfooding 이다.
