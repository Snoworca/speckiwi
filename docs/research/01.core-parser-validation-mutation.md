## 1. Research Purpose

이 문서는 SpecKiwi v1.0.0 SRS를 기준으로 core/parser/validator/query/mutation 구현 방법을 연구한 결과다. 목적은 구현자가 바로 TDD 계획으로 전환할 수 있도록 Markdown-only 원본성, 제한형 SRS-MD parsing, validation rule registry, line-based patch mutation의 경계를 명확히 잡는 것이다.

이 연구는 다음 문서를 기준으로 한다.

- `docs/spec/SRS-MD-Rules-v1.0.0.md`
- `docs/spec/00.index.md`
- `docs/spec/10.product-architecture.srs.md`
- `docs/spec/20.parser-validation.srs.md`
- `docs/spec/50.nodejs-implementation.srs.md`
- `docs/spec/90.appendix.md`

## 2. Key Conclusions

SpecKiwi core는 Markdown 문서를 데이터베이스처럼 다루면 안 된다. 원본은 Git-tracked Markdown이고, JSON과 normalized record는 파생 view다.

가장 안전한 구현 방식은 다음 구조다.

1. UTF-8 파일을 line 단위로 읽고 newline style을 감지한다.
2. `00.index.md`에서 Target Map과 Scope Map을 먼저 파싱한다.
3. `docs/spec/**/*.srs.md` 파일을 탐색하고 Requirement Block line range를 만든다.
4. block 내부의 metadata table, fixed sections, AC task list, evidence table, trace table을 제한형 parser로 추출한다.
5. validator는 parser 결과와 index map을 받아 독립 rule registry로 diagnostics를 생성한다.
6. query service는 validated 여부와 무관하게 가능한 normalized record를 조회/요약한다.
7. mutation service는 parser가 보존한 line range만 사용하여 patch plan을 만들고, dry-run과 stale guard를 거친 뒤 최소 줄만 변경한다.

Markdown AST로 문서 전체를 재출력하는 방식은 v1.0.0 요구사항과 맞지 않는다. 읽기 parsing에는 제한형 Markdown parser를 쓰되, 쓰기는 반드시 line-based patch로 유지해야 한다.

## 5. Parser Implementation Strategy

### 5.1 Workspace Parsing Flow

파서는 workspace 단위 API를 중심으로 설계한다.

1. root를 결정한다.
2. `docs/spec/00.index.md`를 읽고 Target Map, Scope Map, SRS Documents table을 추출한다.
3. `docs/spec/**/*.srs.md`를 찾되 `SRS-MD-Rules-v1.0.0.md`와 appendix는 requirement source로 취급하지 않는다.
4. 각 파일을 UTF-8로 읽고 newline style, BOM 여부, line array를 보존한다.
5. `### {RequirementID} — {Title}` heading을 스캔해서 block start/end line range를 만든다.
6. block 첫 table을 metadata table로 파싱한다.
7. `####` heading을 section map으로 파싱하고 중복 heading을 diagnostics 후보로 남긴다.
8. AC, evidence, trace는 section별 specialized parser가 record와 line number를 만든다.
9. parser result는 `requirements`와 `diagnostics`를 함께 반환한다.

### 5.2 Line Range Preservation

mutation의 품질은 parser가 line range를 얼마나 정확히 보존하는지에 달려 있다. 모든 주요 record에는 최소한 다음 위치 정보가 필요하다.

- file path
- block start/end line
- heading line
- metadata table start/end line
- metadata row line by field key
- section start/end line
- AC item line
- evidence table header/separator/body end line
- trace table header/separator/body end line

line number는 내부적으로 0-based를 쓰고, diagnostics와 JSON output에서는 1-based로 변환하는 방식을 권장한다.

### 5.3 Restricted Markdown Parsing

전체 Markdown renderer를 구현하지 않는다. SRS-MD 규칙이 요구하는 제한형 구조만 인식한다.

- heading parser: `###` requirement heading과 `####` section heading만 의미 있게 처리한다.
- table parser: pipe table 한 줄 row만 처리하고 cell line break는 error로 본다.
- task parser: `- [ ]`와 `- [x]`만 AC로 인식한다.
- link parser: local link 존재 검증은 validator rule에서 별도 처리한다.

이 접근은 full Markdown AST보다 단순하지만 ad hoc 문자열 치환과 다르다. 각 Markdown 구조마다 작은 parser와 명확한 diagnostics를 둔다.

## 6. Validator Implementation Strategy

validator는 parser와 분리된 rule registry로 구현한다. parser는 가능한 한 많이 읽고, validator는 SRS-MD 위반을 error/warning으로 분류한다.

권장 rule group은 다음과 같다.

| Rule Group | Examples |
|---|---|
| Identity | duplicate ID, heading format, ID regex, em dash warning/error |
| Metadata | missing table, missing Type/Target/Status, enum violation |
| Type and Scope | ID prefix/type mismatch, scope segment missing from Scope Map |
| Sections | missing Acceptance Criteria, duplicate fixed section heading |
| Acceptance Criteria | nested task list, malformed AC id, empty AC text |
| Verified Guard | unchecked AC, no evidence row, empty evidence reference |
| Evidence and Trace | required columns, trace requirement reference existence |
| Index Consistency | target not registered, scope document missing from index |
| Links | local Related Docs missing, malformed GitHub Issue warning |
| Quality Warnings | high risk without Research / Analysis, too many tags |

diagnostics는 appendix의 shape를 따른다.

- `code`: `SRS-E001` 또는 `SRS-W001` 형식
- `level`: `error` 또는 `warning`
- `message`: 사람이 이해 가능한 설명
- `file`, `line`, `requirementId`

중요한 정책은 fatal parse failure를 최소화하는 것이다. 파일 I/O 실패와 index 부재는 상위 error로 보고하되, 하나의 잘못된 Requirement Block 때문에 나머지 block 조회가 중단되면 안 된다.

## 7. Query Service Implementation Strategy

query service는 parser/validator의 파생 모델만 사용한다. 파일을 직접 재파싱하거나 Markdown을 직접 다루지 않는다.

필수 capability는 다음과 같다.

- requirement id exact lookup
- target/status/scope/type/tag filter
- normalized record list
- includeMarkdown 옵션
- target summary
- scope summary
- validation diagnostics passthrough

MCP와 CLI 결과 일치를 위해 query output은 `RequirementRecord` 배열과 summary object를 공통 타입으로 반환해야 한다. 사람이 읽는 CLI table/text는 `src/core/format` 또는 CLI adapter의 formatter에서만 만든다.

MCP server에서는 성능을 위해 in-memory workspace snapshot을 둘 수 있다. 다만 원본성은 없으며, request마다 file mtime을 확인해 필요한 경우 재파싱하는 정도로 제한하는 것이 SRS와 맞다.

## 8. Mutation Service Implementation Strategy

mutation service는 read model과 patch engine 사이의 orchestration layer다.

공통 흐름은 다음과 같다.

1. root와 대상 path를 안전하게 resolve한다.
2. 최신 파일과 workspace를 다시 읽는다.
3. 대상 requirement 또는 scope document를 찾는다.
4. 입력을 schema로 검증한다.
5. 상태 전이와 verified guard 등 mutation-specific guard를 적용한다.
6. patch plan을 만든다.
7. dry-run이면 patch summary와 diagnostics만 반환한다.
8. apply 전 expected original line을 다시 확인한다.
9. temp file write와 rename으로 atomic write를 수행한다.
10. 변경 후 필요한 범위만 재파싱하거나 전체 validator self-check를 수행한다.

모든 mutation은 실패 시 파일을 변경하지 않아야 한다. 이 요구는 validation 실패, guard 실패, stale line mismatch, path safety 실패 모두에 적용한다.

## 9. Requirement Block Generation Strategy

`FR-NODE-008`은 core mutation 중 가장 위험도가 높다. 권장 입력 모델은 다음과 같다.

필수 입력:

- `type`
- `scope`
- `target`
- `title`
- `requirement`
- `acceptanceCriteria`

선택 입력:

- `status`, default `planned`
- `priority`, `tags`, `risk`, `stability`, `verificationMethod`
- `rationale`
- `implementationNotes`
- `relatedDocs`, `githubIssue`
- `evidence`
- `traceLinks`
- `research`
- `changeNotes`
- `dryRun`

ID 생성 규칙:

1. `type`을 SRS-MD Type/Prefix map으로 변환한다.
2. `scope`는 우선 Scope Map의 `Prefix`와 정확히 비교한다.
3. full Scope name을 지원한다면 동일 이름/별칭이 둘 이상인 경우 거부한다.
4. 저장소 전체 Requirement ID를 스캔한다.
5. 같은 `{typePrefix}-{scopePrefix}` 조합의 최대 번호를 찾는다.
6. `discarded` 상태의 ID도 기존 ID로 취급하여 재사용하지 않는다.
7. 기본 폭은 3자리로 생성하고, 기존 최대 폭이 4자리면 4자리를 유지한다.

block rendering 규칙:

- heading은 `### {ID} — {Title}`로 렌더링한다.
- metadata table에는 최소 `Type`, `Target`, `Status`를 포함한다.
- 권장 field는 값이 없으면 `-` 또는 omission 중 하나로 일관되게 처리해야 한다. SRS 최소 템플릿과 CLI/MCP reference를 고려하면 `GitHub Issue`, `Related Docs`는 `-`로 두는 편이 안전하다.
- AC는 입력 순서대로 `AC-1`, `AC-2`를 자동 부여한다.
- `status = verified` 생성은 모든 AC가 checked이고 evidence row가 하나 이상이며 reference가 비어 있지 않을 때만 허용한다.
- evidence/trace table은 row가 없어도 header와 separator를 렌더링한다.
- `Change Notes`에는 기본적으로 생성일과 최초 작성 사유를 남기는 것이 review에 유리하다.

## 10. Line-Based Patch Strategy

### 10.1 Patch Model

patch engine은 문서 의미를 알 필요가 없다. parser가 제공한 line range와 mutation service가 계산한 expected line만 처리한다.

권장 operation:

- `replaceLine(file, line, expected, replacement)`
- `insertLines(file, beforeLine, lines)`
- `appendLines(file, lines)`
- `replaceRange(file, startLine, endLineExclusive, expectedLines, replacementLines)`

각 operation은 다음 검사를 가져야 한다.

- 대상 file이 project root 내부인지 확인한다.
- line range가 현재 파일 길이 안에 있는지 확인한다.
- expected original line/range가 현재 파일과 일치하는지 확인한다.
- patch operation이 서로 겹치지 않는지 확인한다.

### 10.2 Newline Preservation

파일 읽기 단계에서 newline style을 감지한다.

- 첫 newline이 `\r\n`이면 CRLF로 write한다.
- 첫 newline이 `\n`이면 LF로 write한다.
- newline이 없는 파일은 LF를 기본값으로 둔다.
- 마지막 newline 존재 여부는 가능하면 보존한다. 다만 새 block append 시 Scope SRS 문서는 최종 newline을 유지하는 것이 좋다.

### 10.3 Requirement Block Append Position

새 Requirement Block은 scope 문서의 `## 4. Requirements` section 끝에 추가한다.

알고리즘:

1. scope prefix로 대상 Scope SRS file을 찾는다.
2. 해당 파일에서 `## 4. Requirements` heading line을 찾는다.
3. 그 다음 `## ` level heading을 찾는다.
4. 다음 `## ` heading이 있으면 그 직전의 trailing blank line을 정리한 위치에 삽입한다.
5. 다음 `## ` heading이 없으면 파일 끝에 삽입한다.
6. 기존 block 사이 공백은 두 줄 이하로 유지한다.
7. 삽입 patch는 대상 위치 주변만 바꾸고 다른 section을 재정렬하지 않는다.

이 방식은 `## 5. Cross-scope Dependencies` 앞에 새 block을 넣는 것이며, SRS 문서 끝 전체가 아니라 Requirements section 끝이라는 사용자 요구와 SRS 구조를 동시에 만족한다.

## 11. TDD Test Strategy

테스트는 구현보다 먼저 작성하고, 실패 이유를 확인한 뒤 최소 구현으로 통과시켜야 한다.

### 11.1 Parser Tests

- 정상 fixture에서 모든 Requirement Block ID, title, line range를 추출한다.
- metadata required fields와 optional fields를 추출한다.
- AC checked/unchecked와 AC id를 line number와 함께 추출한다.
- empty evidence/trace table을 row 0개로 파싱한다.
- malformed heading, nested task list, duplicate section을 diagnostics 후보로 남긴다.
- CRLF fixture에서 line range와 newline style이 유지된다.

### 11.2 Validator Tests

- duplicate ID는 `SRS-E001` error다.
- metadata table 누락과 required field 누락은 error다.
- Status/Type enum 위반은 error다.
- ID prefix와 Type 불일치는 error다.
- Target Map 미등록은 warning이다.
- Scope Map 미등록은 error다.
- verified 상태에서 unchecked AC 또는 evidence 부재는 error다.
- Requirement trace reference가 없으면 error다.

### 11.3 Query Tests

- id lookup은 정확히 하나의 normalized record를 반환한다.
- target/status/scope/type/tag filter는 조합 가능해야 한다.
- summary는 status별/type별 count와 blocked/implemented/verified list를 반환한다.
- includeMarkdown 옵션은 raw block을 포함하고 기본값에서는 제외한다.

### 11.4 Mutation Tests

- `update-status`는 Status row 한 줄만 바꾼다.
- `check-ac`는 지정 AC line만 바꾼다.
- `add-evidence`와 `add-trace`는 table body 끝에 row 하나만 넣는다.
- verified guard 실패 시 파일 변경이 없다.
- dry-run은 patch summary만 반환하고 파일 변경이 없다.
- stale expected line mismatch는 파일 변경 없이 mutation denied를 반환한다.
- CRLF fixture에서 mutation 후 CRLF가 유지된다.
- add requirement는 다음 ID를 생성하고 Requirements section 끝에만 block을 삽입한다.
- discarded ID가 있어도 번호를 재사용하지 않는다.

### 11.5 Integration Tests

- CLI와 MCP adapter는 같은 core result를 반환한다.
- `speckiwi validate`와 MCP `validate_spec` diagnostics가 동일하다.
- mutation command와 MCP mutation tool이 같은 guard와 patch summary를 사용한다.
- 임시 디렉터리 fixture에서만 write test를 실행한다.

## 12. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Markdown table cell의 `|` 문자 처리 | metadata/evidence 파싱 오류 | escaped pipe만 허용하거나 unescaped pipe를 validation error로 보고한다. |
| heading dash 혼용 | requirement block 경계 오인식 | em dash heading만 정상 block start로 인정하고 hyphen/colon은 diagnostics로 보고한다. |
| block 내부 `###` 사용 | block 조기 종료 | SRS 규칙대로 새 block으로 간주하고 section validation에서 오류를 만든다. |
| line range stale | 잘못된 줄 변경 | apply 직전 expected original line/range를 비교한다. |
| 동시 write | ID 충돌 또는 patch 충돌 | write 직전 workspace를 재파싱하고 atomic write를 사용한다. |
| CRLF/LF 혼합 | 불필요한 대량 diff | 파일별 newline style을 감지하고 patch output에 그대로 적용한다. |
| verified 상태 오판 | 허위 검증 완료 | 모든 AC checked, evidence row 존재, non-empty reference guard를 공통화한다. |
| scope name ambiguity | 잘못된 문서에 새 block 삽입 | scope prefix를 canonical input으로 삼고 ambiguous full name은 거부한다. |
| parser fatal failure 과다 | 일부 오류 때문에 전체 조회 불가 | partial parse result와 diagnostics를 함께 반환한다. |
| MCP SDK 변경 | core compile 영향 | SDK import를 `src/mcp` adapter 내부로 제한한다. |
| shell execution 위험 | agent 연결 환경 보안 문제 | Git/root/link 처리는 Node fs/path API만 사용한다. |
| 성능 저하 | CLI/MCP 응답 지연 | O(n) line scan, table parser 최소화, MCP mtime 기반 snapshot refresh를 사용한다. |

## 13. Proposed Implementation Order

권장 순서는 위험이 낮은 읽기 모델에서 시작해 mutation으로 확장하는 방식이다.

1. Foundation
   - TypeScript ESM, `engines.node >=22`, Vitest, strict TS config, core type skeleton을 준비한다.
   - `project-root`, UTF-8 read, newline detection, safe path utility test를 먼저 작성한다.

2. Parser 1
   - index parser, SRS file discovery, requirement heading scanner를 구현한다.
   - 정상 fixture와 malformed heading fixture를 Red/Green으로 처리한다.

3. Parser 2
   - metadata, fixed section, AC, evidence, trace parser를 추가한다.
   - line range preservation을 mutation test의 선행 조건으로 검증한다.

4. Validator
   - rule registry와 core diagnostics를 구현한다.
   - duplicate ID, required metadata, enum, target/scope, verified guard 순서로 rule을 추가한다.

5. Query
   - lookup, filter, summary를 구현한다.
   - CLI/MCP adapter가 아직 없어도 core JSON snapshot test로 계약을 고정한다.

6. Patch Engine
   - replaceLine, insertLines, hunk summary, dry-run, stale guard, atomic write를 구현한다.
   - CRLF와 minimal diff golden test를 우선한다.

7. Existing Requirement Mutations
   - update-status, check-ac, add-evidence, add-trace를 구현한다.
   - verified guard는 mutation 공통 guard로 뺀다.

8. Requirement Block Creation
   - add-requirement core mutation을 구현한다.
   - ID generation, scope/target validation, block rendering, append patch, dry-run을 독립 test로 고정한다.

9. Adapter Integration
   - CLI와 MCP adapter는 core 완료 후 얇게 붙인다.
   - CLI/MCP 결과 동일성 test를 regression gate로 둔다.

10. Release Verification
   - 500 block parser benchmark, link check, package script, full validation을 release readiness gate에 넣는다.
