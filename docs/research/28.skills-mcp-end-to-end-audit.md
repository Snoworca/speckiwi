## 이 문서를 읽는 방법

이 문서는 두 가지 질문에 답한다.

1. 사람이 결정문 한 장, 연구 문서 한 편, 또는 GitHub 이슈 하나만 주었을 때, 스킬과 MCP 도구만으로 구현과 코드 리뷰까지 끝낼 수 있는가.
2. 그 과정에서 정확도를 높이지 못하면서 시간과 토큰만 쓰는 자리는 어디인가.

각 결함에는 파일 경로와 줄 번호, 그 파일에 실제로 있는 문장, 그리고 **그 지적이 틀렸다면 무엇으로 반증되는지**를 함께 적었다. 반증 조건이 없는 지적은 싣지 않았다.

용어를 먼저 정리한다.

| 용어 | 뜻 |
|---|---|
| 스킬 | 코딩 에이전트가 읽는 지시 문서. `skills/claude/kiwi-srs/SKILL.md` 같은 파일이다. 호출될 때 본문 전체가 에이전트의 컨텍스트에 올라간다. |
| MCP 도구 | 에이전트가 함수처럼 호출하는 도구. `add_requirement`, `update_status` 등 100개가 있다. |
| 요구(REQ) | `docs/spec/` 아래 Markdown 에 기록된 요구사항 한 건. `FR-NODE-188` 같은 ID 를 갖는다. |
| Status | 요구의 진행 상태. `planned`, `in_progress`, `blocked`, `implemented`, `verified`, `discarded` 여섯 값이다. |
| Stability | 요구의 성숙도. `draft`, `evolving`, `stable`, `frozen`, `deprecated` 다섯 값이다. |
| 게이트 | 조건을 만족하지 못하면 진행을 멈추는 검사 지점. |

## 1. 검수 대상과 규모

| 항목 | 수치 | 확인 방법 |
|---|---|---|
| 스킬 | 17개 × 3 렌더링(claude · codex · etc) | `ls -d skills/*/kiwi-*` |
| 공용 조각 | `skills/*/_shared/kiwi/` 아래 12개 파일 | 디렉터리 열거 |
| MCP 도구 | **100개** | MCP 서버를 기동해 받은 `tools/list` 응답 |
| claude 렌더링 본문 합계 | 868,000 바이트 남짓 | 파일 크기 합산 |

MCP 도구 100개는 두 경로로 등록된다. `src/mcp/server.ts` 의 `toolSchemas` 객체가 73개를 직접 나열하고, 같은 파일 528줄의 `...orchestrateToolSchemas()` 가 `src/cli/commands/orchestrate.ts` 의 CLI 바인딩에서 27개를 파생시킨다. 그다음 631줄의 `sdk.registerTool(name, {...})` 이 전체를 순회 등록한다.

**이 파생 구조는 잘 설계된 부분이다.** `src/mcp/server.ts:53` 의 주석이 의도를 밝힌다.

> derived from the CLI bindings so a tool cannot declare a field

CLI 명령과 MCP 도구가 같은 소스에서 나오므로, 한쪽만 고쳐지고 다른 쪽이 조용히 어긋나는 일이 구조적으로 차단된다.

### 1.1 검수 과정에서 팀리드가 두 번 틀렸다

이 사실을 먼저 적는 이유는, 아래 발견들이 어떤 검증을 거쳤는지 보이기 위해서다.

팀리드가 서브에이전트들에게 "실재 도구 목록은 `registerTool` 을 grep 해서 얻으라"고 지시했다. 이 방법은 두 번 틀렸다.

1. 첫 번째 오류 — `orchestrate_*` 27개가 CLI 바인딩 파생이라 grep 에 잡히지 않는다. 이 기준선을 그대로 썼다면 27개를 "실재하지 않는 도구"로 잘못 판정했을 것이다.
2. 두 번째 오류 — 정정한 기준선(96개)도 틀렸다. `registerTool(` 다음 줄에 이름이 오는 멀티라인 등록 4건(`set_active_target`, `set_target_goal`, `workflow_record_reclassification`, `apply_requirement_id_collision_repair`)을 놓쳤다.

두 오류 모두 서브에이전트가 잡았다. 세 번째 축은 애초에 grep 을 쓰지 않고 MCP 서버를 실제로 기동해 `tools/list` 응답을 받았으므로 처음부터 100개였다.

**세 축 모두 "실재하지 않는 도구를 부르는 스킬은 0건"이라는 같은 결론에 독립적으로 도달했다.**

## 2. 질문 1에 대한 답 — 진입점에서 구현까지

### 2.1 판정

| 진입점 | 판정 | 조건 |
|---|---|---|
| (A) 사용자가 자연어로 쓴 결정문 | **조건부 도달** | `kiwi-pipeline` 을 첫 홉으로 잡을 때. 요구 등록 단계에서 계약 위반이 발생한다(§2.3). |
| (B) 연구 자료 문서 | **조건부 도달** | `kiwi-wave-master` 또는 `kiwi-pipeline` 경로에 한정. `kiwi-orchestrator --design-doc` 로 들어가면 Phase 3.c′ 에서 멈춘다(§2.4). |
| (C) GitHub 이슈 | **조건부 도달** | 버그성 이슈는 `kiwi-hot-fix` 로 완주. 기능성 이슈는 연구에서 요구 등록으로 넘어가는 이음매의 입력이 문서에 없다(§2.5). |

세 경로 모두 요구 등록 단계에서 `kiwi-srs` 를 공유하므로, §2.3 의 결함은 셋 모두에 걸린다.

`kiwi-orchestrator` 의 스킬 설명 첫 문장이 이 질문에 정확히 대응한다.

> 얇은 의도·연구문서·GitHub 이슈를 받아 intake → 라우팅 → 설계 동결 → wave 분해 → 병렬화 분석 공개 → 영문 handoff → 자체 통합 브랜치 위 직렬 실행 → 사후 검증 → 요구 승급까지 하나의 재개 가능한 run 으로 완주시키는 설계-우선 오케스트레이터

즉 사용자의 질문은 이 스킬이 스스로 선언한 계약과 같다. 그래서 이 검수는 "그 선언이 실제로 지켜지는가"를 확인하는 일이 되었다.

### 2.2 실제 호출 순서

각 진입점에서 스킬이 어떤 순서로 이어지는지 실제로 그려 본 결과다.

```
(A) 결정문
    kiwi-pipeline  →  kiwi-srs  →  [조건부] kiwi-srs-feasibility
                                →  kiwi-planner  →  kiwi-pm  →  kiwi-review-fix-loop

(B) 연구 문서
    kiwi-wave-master  →  wave별 target 등록  →  kiwi-pipeline --from=feasibility  →  구현
    kiwi-orchestrator --design-doc  →  3.b  →  3.c  →  [3.c′ 에서 정지]

(C) GitHub 이슈
    버그성:   kiwi-hot-fix  →  gh issue view  →  회귀 테스트  →  수정  →  kiwi-srs-sync
    기능성:   kiwi-pipeline §2.7  →  kiwi-srs-research(GITHUB_ISSUE)  →  [이음매 입력 불명]  →  kiwi-srs
```

이음매 자체는 대부분 존재한다. 끊기는 곳은 흐름이 아니라 **요구 등록 단계의 내부 계약**이다.

### 2.3 CRITICAL — `kiwi-srs` 가 지시하는 status 값이 존재하지 않는 값이다

**무슨 일이 일어나는가.** 단계별로 적는다.

1. `kiwi-srs` 가 신규 요구의 status 를 `proposed` 로 지정하라고 지시한다.
2. `add_requirement` 도구가 그 값을 **검사하지 않고 그대로 파일에 쓴다.**
3. 검증기 `validate` 를 돌리면 `SRS-E005` **error** 가 난다. `proposed` 는 존재하지 않는 status 이기 때문이다.
4. 그런데 `kiwi-srs` 자신의 종료 조건 첫 항목이 "`validate_spec` PASS" 다.

**즉 이 스킬은 자기 지시를 따르면 자기 종료 조건을 통과할 수 없다.**

근거는 이렇다.

> `skills/claude/kiwi-srs/SKILL.md:485`
> 신규 REQ 기본 status: **`proposed`** (사용자 미승인).

```ts
// src/core/types.ts:1-8
export const REQUIREMENT_STATUSES = [
  "planned",
  "in_progress",
  "blocked",
  "implemented",
  "verified",
  "discarded"
] as const;
```

```ts
// src/core/mutation/add-requirement.ts:208
    status: input.status ?? "planned",
```

```ts
// src/core/validator/rules.ts:643-644
      if (!includes(REQUIREMENT_STATUSES, record.status)) {
        diagnostics.push(diagnostic("SRS-E005", "error", `Invalid status for ${record.id}`, ...));
```

> `skills/claude/kiwi-srs/SKILL.md:843` (§14 수렴 기준)
> - `validate_spec` PASS

**원인은 쓰기 두 종류의 비대칭이다.**

| 쓰기 | 검사 | 근거 |
|---|---|---|
| 값을 **바꾸는** 쓰기 (`update_status`) | enum 강제 | `src/core/mutation/update-status.ts:106` — `if (!isRequirementStatus(input.status)) return mutationFail("USAGE", ...)` |
| 값을 **만드는** 쓰기 (`add_requirement`) | 검사 없음 | `src/core/mutation/add-requirement.ts:208` — 입력을 그대로 기록 |

`src/mcp/` 와 `src/cli/commands/mutations.ts` 어디에도 `REQUIREMENT_STATUSES` 참조가 **0건**이다(팀리드 직접 확인). 따라서 `proposed` 는 **설정할 수는 없지만 생성할 수는 있는 값**이다.

설계 의도는 코드 주석에 남아 있다.

> `src/core/mutation/add-requirement.ts:436`
> is gated: any other status is free to land and can be promoted through the guarded transition.

`verified` 만 막고 나머지는 자유롭게 착지시키는 설계인데, 그 "나머지"에 enum 밖 값이 포함되어 버렸다.

**이것은 오타 하나가 아니다.** `proposed` 를 정상 status 로 전제하는 스킬이 넷이다.

| 스킬 | 줄 | 어떻게 쓰는가 |
|---|---|---|
| `kiwi-srs` | `:485` | 신규 요구의 기본값으로 지시 |
| `kiwi-pm` | `:949` | `STATUS_ORDER = ["proposed", "planned", "in_progress", "implemented", "verified"]` — 순서 정의의 첫 원소 |
| `kiwi-review-fix-loop` | `:130` | skip 대상 예시로 이름을 지목 |
| `kiwi-srs-feasibility` | `:64` | `REQ.status ∈ {proposed, planned, blocked}` — 정책 분기 조건 |

스킬 계층은 **7값 enum** 을 전제하고 동작하며, 코드 계층은 6값이다. `kiwi-srs:485` 한 줄만 고치면 `kiwi-srs-feasibility:64` 의 분기가 죽은 조건이 된다.

**추가 파급 — 그 요구는 작업 후보 목록에 오르지 않는다.**

```ts
// src/core/query/summary.ts:39-41
export function isNewWorkCandidate(record: RequirementRecord): boolean {
  return (record.status === "planned" || record.status === "in_progress" || record.status === "blocked") && record.stability !== "draft" && record.stability !== "deprecated";
}
```

`proposed` 는 세 값 어디에도 없으므로 `newWorkCandidates` 에 영원히 오르지 않는다. `blocked`·`implementedNotVerified`·`missingEvidence` 도 각각 다른 status 를 요구하므로 모두 비켜간다. 남는 자리는 임의 문자열을 조용히 받는 개수 딕셔너리 하나뿐이다(`summary.ts:159`). 즉 그 요구는 **ID 목록에는 한 번도 나타나지 않고 이름 없는 개수 버킷으로만 존재한다.**

**반증 조건**: `REQUIREMENT_STATUSES` 에 `proposed` 가 있거나, `add_requirement` 가 그것을 `planned` 로 정규화하면 이 지적은 거짓이다.

**이 결함은 이미 한 번 일어났고 데이터만 수리되었다.** 네 SRS 파일에 같은 문구의 Change Notes 가 11건 남아 있다.

> `docs/spec/50.nodejs-implementation.srs.md:5441` (같은 문구가 30·40·50·60 네 파일에 총 11건)
> `| 2026-07-16 | Status -> planned | SRS-E005 fix: proposed is not a valid status in SRS-MD Rules v3.0.0; registration intended planned. |`

2026-07-16 에 요구 11개가 이 값으로 착지해 검증 오류를 냈고, 그때 **요구의 값만 고치고 그 값을 지시하는 스킬은 그대로 두었다.** 현재 저장소는 깨끗하다 — `node bin/speckiwi validate --json` 결과 `SRS-E005` 0건, error 급 진단 0건(2026-08-25 실행). 그러나 스킬 넷은 지금도 같은 값을 지시하므로 재발 대기 상태이고, 이 검수가 같은 결함을 다시 찾은 것이다. 원인을 두고 증상만 고치면 어떻게 되는지를 이 저장소 자신이 기록해 두었다.

### 2.3.1 CRITICAL — `kiwi-srs` 가 항상 실패하는 mutation 호출을 지시한다

§2.3 과 뿌리는 같으나 증상이 다르다. §2.3 은 잘못된 값이 **착지하는** 경우이고, 이것은 호출이 **아예 실행되지 않는** 경우다.

conflict 로 분류된 요구의 처분 절차에서 이렇게 지시한다.

> `skills/claude/kiwi-srs/SKILL.md:499`
> `update_status { id: "REQ-X", status: "draft" }` — 자동 폐기 회피. status 만 변경, `stability` 필드 불변. 변경 사유는 §7 Change Notes 가 SSOT

`draft` 는 Stability 값이지 Status 값이 아니다. 그리고 값을 바꾸는 쓰기는 enum 을 강제한다.

```ts
// src/core/mutation/update-status.ts:106
  if (!isRequirementStatus(input.status)) return mutationFail("USAGE", `Invalid status: ${input.status}`);
```

따라서 이 호출은 **반드시 `USAGE` 실패로 끝난다.** 지시문이 "`stability` 필드 불변"을 명시하므로 `update_stability` 로 갈아타는 것은 지시된 의미를 바꾸는 행위이고, Status 쪽에는 "draft" 를 뜻하는 값이 아예 없다. conflict 로 분류된 요구는 사람이 처분을 정해 주어야 다음으로 간다.

**반증 조건**: `isRequirementStatus` 가 `draft` 를 수용하거나, `kiwi-srs` 에 이 단계의 대체 절차가 적혀 있으면 거짓이다.

### 2.4 CRITICAL — 신규 요구가 draft 로 착지하는데 오케스트레이터에 승급 홉이 없다

**무슨 일이 일어나는가.**

1. 신규 요구는 `stability=draft` 로 만들어진다. 이것이 기본값이다.
2. `kiwi-srs` 는 stability 를 넘기지 않고, 승급 평가를 `kiwi-srs-feasibility` 의 책임이라고 적는다.
3. 그런데 `kiwi-orchestrator` 의 R-ORCH 경로에는 그 스킬을 부르는 홉이 **없다**고 문서 자신이 밝힌다.
4. readiness 판정은 `draft` 를 통과시키지 않으므로 Phase 3.c′ 게이트가 발화한다.
5. 그 게이트는 자동 진행 옵션으로도 우회할 수 없다.

```ts
// src/core/mutation/render-requirement.ts:4
export const DEFAULT_REQUIREMENT_STABILITY = "draft";
```

```ts
// src/core/orchestrator/readiness.ts:351
function isLifecycleReady(record: SpecRequirementRecord): boolean {
  return ["planned", "in_progress", "implemented", "verified"].includes(record.status)
    && ["evolving", "stable", "frozen"].includes(record.stability);
}
```

> `skills/claude/kiwi-orchestrator/SKILL.md:523`

### 3.2 CRITICAL — 요구를 한 건도 닫지 못해도 "완료"로 끝난다

**무슨 일이 일어나는가.**

가장 무거운 것은 `orchestrate_validate` 다. 이것은 `FR-NODE-188` 이 만든 저널 검증기이며, 종료 리뷰 의무를 강제할 유일한 기계 참조물이다. **그 요구 자신이 이 위험을 예견했다.**

> `docs/spec/50.nodejs-implementation.srs.md:12088`
> The refusal SHALL be reached from the run-close path a caller actually executes, not only from a pure predicate, because a validator nothing invokes is the same absent guarantee in a better disguise.

검증기는 실재하고 배선되어 있다(`src/core/orchestrator/waves-validate.ts:647`, CLI 는 `src/cli/commands/orchestrate.ts:1921`). 그러나 실제 run 에서 그 코드에 도달시키는 주체는 에이전트이고, **에이전트에게 그것을 실행하라고 말하는 문장이 없다.**

> **2026-08-25 정정 — 이 절의 초판은 여기서 두 가지를 틀렸다.** 대응 계획을 세우던 중 드러났고 팀리드가 소스로 확인했다.
>
> **첫째, `kiwi-orchestrator` 경로에서는 코드가 이미 검증기를 부른다.** `orchestrate_journal_append` 가 부르는 `appendWavesLine`(`src/cli/commands/orchestrate.ts:949`)은 새 줄을 붙인 후보 파일을 만들어 `validateProspectiveJournal`(`:1031`)에 통과시키고, 진단이 나오면 `written: false` 로 쓰기를 거절한다(`:980-983`). 그 함수의 doc 주석이 의도를 밝힌다 — "the stamp, the validate-then-rename and the refusal path move with it". 즉 종료 리뷰가 빠진 완료 줄은 그 경로에서 애초에 착지하지 못한다. "실행시키는 자동 경로가 없다"는 초판의 서술은 이 경로에 대해 거짓이다.
>
> **둘째, 그 검증은 `kiwi-wave-master` run 에 미치지 않는다.** 초판이 놓친 사실이며 첫째보다 무겁다. 검증 뷰를 만드는 줄이 engine 을 하드코딩한다.
>
> ```ts
> // src/cli/commands/orchestrate.ts:1046
> const view = await parseWavesJournal(root, { runId, engine: "kiwi-orchestrator", relativePath: candidateRelative });
> ```
>
> 그리고 뷰는 engine 이 다른 줄을 버린다(`src/core/orchestrator/waves-journal.ts:73` — `if (engineOf(event) !== options.engine) continue;`). `engineOf` 는 `engine` 필드가 `"kiwi-orchestrator"` 가 아닌 모든 줄을 `DEFAULT_ENGINE` 으로 읽고(`waves-journal.ts:35-37`), 그 기본값은 `kiwi-wave-master` 다(`journal-schema.ts:21`). `orchestrate_journal_append` 바인딩에는 `--engine` 이 없다(`src/cli/commands/orchestrate.ts:252`).
>
> 따라서 **wave-master run 이 이 도구로 종료 줄을 append 하면 후보 뷰가 비고, 빈 뷰의 진단은 0건이며, 어떤 줄도 거절되지 않는다.** 검증이 있다고 믿어지는 자리에 구멍이 있는 것이므로, 검증이 아예 없는 것보다 나쁘다.
>
> 이 정정은 §3.6 의 결론을 뒤집지 않는다. **스킬 텍스트가 19종을 호명하지 않는다는 사실은 그대로이고**, 게이트 발화 조건이 코드에 없어 산문 독해가 곧 게이트 실행이 된다는 §5.2 의 진단도 그대로다. 바뀌는 것은 처방이다 — "검증기를 부르게 하자"가 아니라 "이미 부르는 경로의 engine 필터를 고치고, 부르지 않는 경로를 찾자"가 된다.

오케스트레이터가 종료 시점에 지시하는 것은 SRS 검증뿐이며, 그것은 저널을 열지 않는다.

> `skills/claude/kiwi-orchestrator/SKILL.md:493`
> close-out 뒤에 `validate` → `sync-index` → `validate --fail-on-warning` 을 실행하고 `post-merge-index-drift`(critical)를 거친 다음 마감 이벤트 1건을 emit 한다.

**반증 후보를 팀리드가 직접 확인했고 전부 무너졌다.**

| 반증 후보 | 결과 |
|---|---|
| git 훅이 `orchestrate validate` 를 자동 실행하는가 | `src/node/hooks/`, `scripts/`, `.husky/` 에서 0건 |
| 릴리스 체크가 저널을 검증하는가 | `scripts/release-check.mjs` 에서 `orchestrate`·`waves.jsonl`·`validate` 모두 0건 |

**결정적 보강 사실**: `src/core/orchestrator/auto-gate.ts:60-80` 은 게이트 **ID 이름의 닫힌 목록**이다. 술어가 아니다. `post-merge-index-drift`, `plan-coverage-unclosed` 등 게이트 이름은 코드에 등재되어 있으나 **그것을 발화시키는 조건은 코드에 없다.** 에이전트가 스킬 산문을 읽고 스스로 판단한다. 호명되지 않는 도구 19종이 바로 그 술어 역할을 했어야 할 표면이다.

**반증 조건**: 네 사본 중 하나라도 run 종료·라운드 기록·라우팅 동결·handoff 검증 시점에 해당 도구를 실행하라는 문장을 담고 있으면 거짓이다.

전체 스킬에서 validation ERROR 로 중단하는 게이트는 **단 하나**이며, 구현·리뷰·승격 사슬 밖에 있다.

### 3.10 가장 견고한 축 — 실패 시 정지

이 축은 충족으로 판정했다. 근거를 적는다.

- `critical_gates[]` 가 스킬마다 선언되어 자동 진행을 차단한다.
- 자식 스킬이 자기 게이트를 올리면 부모 표에 행이 없어도 무조건 정지한다(자식 선언 승계).
- 라운드 상한에 도달해도 PASS 가 아니다.
- 진동이 감지되면 즉시 `fail-residual` 이다.
- 빈 코드 범위는 PASS 가 아니라 중단이다.

다만 `critical_gates[]` **밖**의 판단 지점은 자동 진행에서 조용히 통과한다. 오케스트레이터가 이 위험을 정확히 지목했다.

> `skills/claude/kiwi-orchestrator/SKILL.md:491`
> 그 폴백 확인 게이트는 자식의 `critical_gates[]` 밖이라 `--auto` 에서는 위원회가 답하고 아무도 묻지 않는다 — 그렇게 통과한 종료 hop 은 진짜 구멍을 기록된 통과로 바꾼다.

같은 위험이 `kiwi-pm` §6.4 와 `kiwi-coder` §8.4 에 그대로 남아 있다.

## 4. 질문 3에 대한 답 — 시간과 토큰이 어디로 가는가

### 4.1 판정 기준을 먼저 밝힌다

사용자가 전제를 정했다. **대형 솔루션에서 요구대로 정확히 구현되어야 하는 곳에 쓰이므로 루프가 과한 것 자체는 낭비가 아니다.** 따라서 "루프가 많다"는 것만으로는 발견이 되지 않는다. 그 자리를 없앴을 때 **정확도가 떨어지지 않는 이유**를 댈 수 있어야 발견이다.

이 기준 때문에 기각한 것이 있다. 팀리드가 넘긴 렌더링 크기 차이를 통째로 절감액으로 쓰는 것은 **기각되었다.** 축약분의 일부가 실제로 정확도에 기여하기 때문이다.

예를 들어 codex 렌더링의 이 한 문장은 claude 쪽 세 규칙을 합친 것이다.

> `skills/codex/kiwi-review-fix-loop/SKILL.md`
> | §0.4 | Mock shortcuts, cwd-external edits, and signature text are critical violations. |

claude 쪽 원문 셋과 비교하면 무엇이 빠졌는지 보인다.

> `skills/claude/kiwi-review-fix-loop/SKILL.md:24`
> | §0.4 | **Mock 금지** (regex 자동 탐지). CRITICAL severity. kiwi-coder §0.6 계승 |
>
> `:25` | §0.5 | **외부 모듈 수정 금지**. cwd 외부 path 가 fix diff 에 진입 시 §0.G4 발동 |
>
> `:26` | §0.6 | **시그니처 금지** (CLAUDE.md §6). 커밋·코드 주석·PR 응답 코멘트·산출물 어디에도 AI 식별 정보 금지 |

codex 문장에는 탐지 수단, **어느 게이트가 발동하는지**, 적용 범위가 빠져 있다. 어느 게이트가 발동하는지는 자동 진행 상황에서 멈출지 진행할지를 가르는 값이므로, 이것을 빼면 정확도가 떨어진다.

| §3.8(2) verdict | `pass` + `not-applicable-empty-window` 가 완료 인정 | "뒤의 둘은 방면하지 않는다" |

공통점이 있다. **어느 쪽도 상대를 검사하지 않는다.** 스킬 텍스트를 코드 상수와 대조하는 테스트가 있었다면 넷 다 즉시 실패했을 것이다.

§2.3 이 특히 위험한 이유는 **자기은폐적**이기 때문이다. `kiwi-pm` 이 `proposed → implemented` 전이에 성공하는 순간 무효한 값이 사라지고 이후 `validate` 는 깨끗하다. 그 값이 존재했다는 사실이 어디에도 남지 않는다. 검증기가 그것을 볼 수 있는 창은 `kiwi-srs` 종료와 `kiwi-pm` 종료 사이뿐이다.

### 5.2 원인 B — 판정 주체가 판정 대상과 같다

§3.9 의 네 자리가 전부 이 형태다. 그리고 이것을 기계 검증으로 바꿀 도구가 **실재하는데 아무도 부르지 않는다**(§3.6).

`FR-NODE-188` 이 이 위험을 정확한 문장으로 예견해 두었다.

> a validator nothing invokes is the same absent guarantee in a better disguise

그리고 그 예견대로 되었다. 검증기는 구현되고 배선되었으나, 실제 run 에서 그것을 실행시키는 문장이 스킬에 없다.

### 5.3 §4 는 §3 과 연결되어 있다

MCP 도구 100개에 설명이 하나도 없다는 사실(§4.4)이 스킬 비대(§4.2)의 원인 하나다. 도구가 자기를 설명하지 못하므로 스킬이 대신 설명한다. 그리고 그 산문이 게이트 술어까지 떠맡게 되면(§3.6) **에이전트의 독해가 곧 게이트 실행이 된다.**

## 6. 무엇을 먼저 고쳐야 하는가

우선순위를 붙인다. 각 항목의 완료 조건은 "그것을 어긴 상태가 자동으로 실패가 되는가"다.

| 순위 | 무엇을 | 왜 먼저인가 | 완료 조건 |
|---|---|---|---|
| 1 | `add_requirement` 가 status enum 을 강제하도록 | §2.3 이 세 진입점 전부에 걸리고 자기은폐적이라 사후 발견이 어렵다. 그리고 2026-07-16 에 이미 11건이 발생해 데이터만 수리된 전력이 있다 | enum 밖 값으로 `add_requirement` 를 부르면 `USAGE` 실패. **정정 대상을 `proposed` 라는 토큰이 아니라 status 가 놓이는 자리로 잡는다** — §2.3.1 의 `update_status { status: "draft" }` 처럼 다른 토큰으로 같은 위반이 있다. `kiwi-srs-feasibility:64` 의 분기가 죽지 않게 한다 |
| 2 | 구현 사슬이 `check_acceptance_criteria` 를 부르도록 | §3.3 이 "증거 있는 승격 미충족"의 직접 원인이다. 정답이 `kiwi-srs-from-code:357` 에 이미 적혀 있다 | 리뷰 루프의 도구 화이트리스트에 그 도구를 추가하고, 승격 시퀀스를 그 스킬의 문장과 같게 맞춘다 |
| 3 | 후보가 1건 이상인데 승격 0건이면 중단하도록 | §3.2 가 §2.3 과 결합하면 신규 target 의 **기본 결과**가 거짓 완료가 된다 | `candidates_total > 0 && verified_transitioned == 0` 이면 `TASK_DONE` 이 아니다 |
| 4 | 종료 경로가 `orchestrate_validate` 를 실행하도록 | §3.6. 검증기가 이미 있으므로 배선만 하면 된다 | run 종료 시 그 도구를 부르라는 문장이 네 사본 전부에 있고, 부르지 않은 run 이 실패로 판정된다 |
| 5 | 스킬 텍스트를 코드 상수와 대조하는 테스트 | §5.1 의 네 결함을 한 번에 막는다 | status enum, verdict 집합, 도구 이름이 스킬과 코드에서 일치하지 않으면 스위트가 실패한다 |
| 6 | claude 렌더링에 `references/` 도입 | §4.2. 정확도 손실 0이고 codex 에 선례가 있다 | `kiwi-orchestrator` §V 와 세 rung, `kiwi-review-fix-loop` 의 PR·close-reqs 절을 분리 |
| 7 | `get_active_target` 뒤의 `summarize_target` 호출 제거 | §4.3. 차집합이 공집합임이 실행으로 확인되었다 | 다섯 스킬의 선결 호출 지시에서 두 번째 호출을 뺀다 |
| 8 | MCP 도구에 `description` 부여 | §4.4. §4.2 의 근본 원인이며 상용구 32% 도 함께 정리된다 | 100개 도구가 각자의 설명을 갖는다 |

1~5번은 정확도에 직결되고, 6~8번은 비용에 직결된다. 사용자 전제("루프가 과해도 괜찮다")에 따라 **1~5번이 6~8번보다 우선한다.**

## 8. 이 검수의 방법과 한계

**방법.** 독립 서브에이전트 3기를 병렬로 투입했다. 각 축에 편향 없는 입력(원본 질문, 파일 경로, 제약)만 주고 팀리드의 결론이나 가설은 전달하지 않았다. 각 축이 결과를 낸 뒤 팀리드가 핵심 주장을 소스에서 직접 재확인했다.

**교차 확인이 실제로 작동한 사례.**

- 팀리드가 준 도구 기준선이 두 번 틀렸고 두 번 다 서브에이전트가 잡았다(§1.1).
- 팀리드가 넘긴 렌더링 크기 차이를 낭비 축이 **기각**했다. 축약분의 일부가 정확도에 기여한다는 것을 codex 와 claude 원문을 대조해 보였다(§4.1).
- 세 축이 독립적으로 "실재하지 않는 도구를 부르는 스킬은 0건"이라는 같은 결론에 도달했다.
- 팀리드가 먼저 발견한 `kiwi-reviewer` 부재를 담당 축은 찾지 못했으나, 대신 더 깊은 원인(AC 체크 호출자 부재)을 찾았다. 둘은 같은 결함의 두 면이다(§3.3).

**한계.**

- **런타임 실행으로 재현하지 않았다.** §2.3 과 §3.3 은 소스 대조로 판정했다. 실제로 요구를 만들어 확인하려면 저장소의 요구 문서를 수정해야 하는데, 이 검수는 읽기 전용으로 수행했다.
- **전역 설치된 speckiwi 버전이 이 저장소 소스와 같은지 확인하지 않았다.** 설치본이 더 최신이면 enum 이 다를 여지가 있다. 저장소 소스 기준으로는 인용이 정확하다.
- **스킬 전문을 통독하지 않았다.** 큰 파일은 절 제목으로 구조를 파악한 뒤 관련 절만 정독했다. `kiwi-pipeline`, `kiwi-hot-fix`, `kiwi-planner`, `kiwi-srs` 계열의 일부는 도구 이름 대조에만 포함되었다.
- **이 문서는 요구가 아니다.** 상단 고지대로, 여기의 판단이 구현 근거가 되려면 먼저 요구로 승격되고 그 요구를 근거로 구현되어야 한다.
