## 1. Purpose

This document consolidates the implementation research for two related workflow features:

1. `docs/spec/00.index.md` should always contain an `Active Target` metadata row, but new workspaces may leave it empty.
2. `docs/spec/00.index.md` should include a concise Completed Work Log so humans and coding agents can answer requests such as “show the current in-progress work and completed work summary.”

The research goal is to define the implementation direction before changing code. This document does not modify the SRS contract by itself and does not implement the feature.

## 2. Research Inputs

Three subagents reviewed the same goal from separate perspectives.

| Perspective | Focus | Main Conclusion |
|---|---|---|
| SRS/index schema | `00.index.md` structure, SSOT boundaries, rules | Add `Completed Work Log` as an index-level summary after Requirement Type Summary. Requirement Blocks remain source of truth. |
| Core parser/mutation/query | Type model, parser, line patch, init template | Add `completedWork` to `IndexDocument`; parse with existing table parser; add optional append mutation. |
| CLI/MCP/agent UX | Commands, tools, resources, guide text | Add read and mutation interfaces for completed work; agent status answers should combine active target, requirement status queries, and completed work log. |

## 3. Core Decision

`Completed Work Log` should be allowed in `docs/spec/00.index.md`, but it must be defined as a derived, human-readable rollup.

It is not the source of truth for completion.

The source of truth remains:

- Requirement `Status` metadata row
- Acceptance Criteria checked state
- Verification Evidence rows
- Requirement-level Change Notes

The index log is a fast summary for people and agents. If a Completed Work Log row conflicts with Requirement Blocks, Requirement Blocks win and validation should report diagnostics.

## 4. Recommended Index Shape

Add a new section after `## 6. Requirement Type Summary`.

```md
## 7. Completed Work Log

| Date | Target | Scope | Requirement IDs | Summary |
|---|---|---|---|---|
| 2026-05-10 | v1.0.0 | CLI, MCP | IR-CLI-008, FR-MCP-008 | Active Target 조회/갱신 UX를 CLI와 MCP에 연결했다. |
```

Then renumber later sections:

| Old Section | New Section |
|---|---|
| `## 7. Cross-scope Dependencies` | `## 8. Cross-scope Dependencies` |
| `## 8. Open Questions` | `## 9. Open Questions` |
| `## 9. Reference Documents` | `## 10. Reference Documents` |
| `## 10. Change Notes` | `## 11. Change Notes` |

Parser code should not rely on the exact number. It should find a heading matching:

```regex
^##\s+\d+\.\s+Completed Work Log$
```

This keeps the parser robust if the index section order changes later.

## 5. Table Contract

| Column | Required | Format | Notes |
|---|---:|---|---|
| `Date` | yes | `YYYY-MM-DD` | Use explicit dates for reproducible tests. |
| `Target` | optional | Target Map value | Can be empty for cross-target or targetless work. |
| `Scope` | optional | Scope prefix/name, comma-separated | Prefer Scope Map prefix for machines. |
| `Requirement IDs` | optional | comma-separated IDs | Empty is allowed for non-requirement administrative work, but requirement-linked rows are preferred. |
| `Summary` | yes | one line | No line breaks; avoid pipe characters. |

Recommended example:

```md
| 2026-05-10 | v1.0.0 | NODE, CLI | FR-NODE-009, IR-CLI-003 | Active Target metadata를 init/query/mutation 흐름에 연결했다. |
```

## 6. Active Target Policy

The planned policy should be:

1. `init` always creates an `Active Target` metadata row.
2. If no active target is chosen yet, the value is empty:

```md
| Active Target |  |
```

3. An explicitly empty `Active Target` row means “no active target is set.”
4. Do not infer a fallback target when the row exists and is empty.
5. For legacy indexes without an `Active Target` row, fallback to the first Target Map row with `Status = active`, then to the first target.

This differs from the current interim implementation, where an empty metadata value falls back to the Target Map. The implementation should distinguish between:

- row missing: legacy fallback allowed
- row present but empty: active target remains empty

Init behavior should also be clarified:

| Init Input | Active Target Row | Target Map |
|---|---|---|
| no `--target` | empty | header-only Target Map |
| `--target v1.0.0` | empty by default, unless explicit policy changes | row for `v1.0.0`, recommended status `planned` |

The user preference is that init creates an empty Active Target even when target rows exist. Therefore target activation should be a separate explicit action through `set-active-target` or MCP `set_active_target`.

## 7. Agent Workflow

When asked for current work status, agents should follow this sequence:

1. Read `docs/spec/00.index.md`.
2. Read Active Target via MCP `get_active_target` or CLI `speckiwi active-target --json`.
3. If Active Target is set, use it as the default target filter.
4. If Active Target is empty, report that no active target is set and do not invent a target.
5. List current work from Requirement Blocks:
   - `in_progress`
   - `blocked`
   - `implemented` but not verified
   - missing evidence
6. Read Completed Work Log for the recent completed work summary.
7. Answer with separate sections for current work and completed work.

For mutation work, if Active Target is empty and no target is specified in the user request, the agent should ask which target to use or call `set-active-target` after user confirmation.

## 8. Core Implementation Direction

### 8.1 Types

Add a new type:

```ts
export interface CompletedWorkEntry {
  date: string;
  target: string;
  scope: string;
  requirementIds: string[];
  summary: string;
  line?: number;
}
```

Extend `IndexDocument`:

```ts
export interface IndexDocument {
  metadata: Record<string, string>;
  activeTarget: string;
  targets: TargetEntry[];
  scopes: ScopeEntry[];
  completedWork: CompletedWorkEntry[];
}
```

### 8.2 Parser

Reuse the existing Markdown table parser.

Parser behavior:

- Missing Completed Work Log section: `completedWork = []`
- Present section with empty table: `completedWork = []`
- Present table rows: map rows into `CompletedWorkEntry`
- `Requirement IDs`: split by comma, trim each ID, drop empty strings
- Preserve row line where possible

Do not emit errors just because the Completed Work Log is missing. This preserves compatibility with older workspaces.

### 8.3 Validation

Suggested diagnostics:

| Case | Severity | Rationale |
|---|---|---|
| Date is non-empty and not `YYYY-MM-DD` | warning | The log is summary metadata, not core requirement state. |
| Target is non-empty and not in Target Map | warning | Historical rows may reference removed targets. |
| Scope is non-empty and not in Scope Map | warning | Historical rows may reference renamed scopes. |
| Requirement ID not found | warning | Prefer warning because old IDs may have been migrated. |
| Requirement ID found but status is not `implemented` or `verified` | warning | The log conflicts with source-of-truth status. |
| Summary contains a pipe character in mutation input | mutation deny | Current parser is not escape-aware enough for safe round-trip. |

Release readiness must not depend on Completed Work Log.

### 8.4 Query

Two options are viable.

MVP option:

- Add `completedWork` to `IndexDocument`.
- Include target-filtered `completedWork` in `TargetSummary`.
- Existing `summary`, `active-target`, MCP `summarize_target`, MCP `get_active_target`, and `speckiwi://active-target` become more useful.

Expanded option:

- Add a dedicated completed work query service with filters:
  - `target`
  - `scope`
  - `since`
  - `limit`

Recommended: implement MVP first, then add dedicated commands/tools if needed.

### 8.5 Mutation

Add a core mutation such as:

```ts
addCompletedWork(root, input)
```

Suggested input:

```ts
{
  date: string;
  target?: string;
  scope?: string;
  requirementIds?: string[];
  summary: string;
  dryRun?: boolean;
}
```

Line patch policy:

1. Read `docs/spec/00.index.md`.
2. Find `Completed Work Log` heading by regex, not exact number.
3. If missing, append a full section at the end or before Change Notes. Prefer before Change Notes if deterministic insertion is practical.
4. If heading exists but table is missing, insert the empty table under the heading.
5. If table exists, insert the new row at `table.endLine`.
6. Reject inputs containing `|` until the table parser supports escaped pipes.
7. Preserve newline style through the existing patch engine.

## 9. CLI and MCP Direction

### 9.1 CLI

Read command:

```sh
speckiwi completed-work [--target T] [--scope S] [--since YYYY-MM-DD] [--limit N] [--json]
```

Mutation command:

```sh
speckiwi add-completed-work \
  --date 2026-05-10 \
  --target v1.0.0 \
  --scope CLI \
  --requirements IR-CLI-008,FR-MCP-008 \
  --summary "Active Target 조회/갱신 UX를 CLI와 MCP에 연결했다."
```

Convenience command, optional:

```sh
speckiwi work-status [--target T] [--json]
```

This would combine active target, in-progress/blocked/implemented-not-verified requirements, missing evidence, and completed work log rows.

### 9.2 MCP

Read tools:

```text
list_completed_work
get_work_status
```

Mutation tool:

```text
add_completed_work
```

Resources:

```text
speckiwi://completed-work
speckiwi://completed-work/{target}
speckiwi://work-status
```

MVP can omit `get_work_status` and rely on `get_active_target`, `list_requirements`, and `list_completed_work`.

## 13. Open Decisions

| ID | Decision | Recommendation |
|---|---|---|
| OD-001 | Should `init --target` set Active Target? | No. Create the target row but leave Active Target empty; activation should be explicit. |
| OD-002 | Should Completed Work Log missing section be an error? | No. Missing section should parse as empty for backward compatibility. |
| OD-003 | Should unknown Requirement IDs in the log be errors? | Warning. Historical logs may outlive requirement renames. |
| OD-004 | Should `work-status` be implemented in MVP? | Optional. MVP can combine existing list/summary with completed-work commands. |
| OD-005 | Should table pipes be escaped or rejected? | Reject in mutation until the table parser supports escaped pipes. |

## 14. Final Recommendation

Implement Completed Work Log as a lightweight index-level summary, not as a second source of truth. Pair it with explicit empty Active Target semantics so agents can honestly report whether a current target is configured. The most stable implementation is:

1. Empty Active Target row on init.
2. Completed Work Log empty table on init.
3. Parser exposes `index.completedWork`.
4. Validator warns on inconsistencies.
5. CLI/MCP provide read and append operations.
6. Agent instructions explain how to answer current-work status requests by combining Active Target, requirement status, and Completed Work Log.
