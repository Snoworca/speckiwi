## 0. 요약 — 가설은 수치로 확정됐다

> **비용의 뿌리는 검증 횟수가 아니라 "산문은 LLM 만 검증할 수 있다"는 가정이다. 그 가정이 틀렸다.**

이 저장소의 완료 로그·핸드오프·research 문서에 **기록된 검증 결함 56건**을 전수 분류한 결과:

| 분류 | 건수 | 비율 | 뜻 |
|---|---|---|---|
| **MECHANICAL** | 38 | **67.9%** | 스크립트/테스트/lint 가 잡을 수 있었다 |
| **HYBRID** | 10 | 17.9% | 기계가 후보를 지목하고 사람이 확정 |
| **JUDGMENT** | 8 | 14.3% | 읽어야만 잡힌다 |

즉 **비싼 LLM 라운드가 잡아온 것의 2/3 는 CPU 가 공짜로 잡을 수 있었고**, LLM 이 진짜로 필요한 잔여는 14%다. 근본 해결책은 검증을 줄이는 것이 아니라 **주장을 기계 검증 가능한 형태로 옮겨 LLM 을 그 14% 에만 쓰는 것**이다.

교차 일치의 증거: A 축이 README 결함 8건을 독립 분류한 결과(기계 4/8)와, B 축이 doc-lint 설계로 커버리지를 독립 추정한 결과(4/8)가 **서로를 모른 채 일치**했다.

## 1. (A) 결함 전수조사 — 무엇이 실제로 잡혔나

56건의 출처: `docs/spec/91.completed-work-log.md` 전 항목, `00.index.md` §7, 핸드오프 §5.3 의 "자기유발 결함 8건", research 18 §9.7. 전체 표는 조사 원본에 있고, 여기서는 **빈도순 기계화 가능 패턴 Top 5** 만 옮긴다:

| 순위 | 패턴 | 건수 | 예 |
|---|---|---|---|
| 1 | **개수/enum/집합을 SSOT 에서 파생하지 않아 조용히 어긋남** | 8 | workflow 하위명령 "30 vs 29 vs 28 세 값이 갈림", 미등록 진단 코드, 주입 지점 1개 주장(실제 2) |
| 2 | **결함이 있어도 통과하는 약한 단언** | 4 | 핵심 호출을 지워도 green 이던 FR-MCP-056 테스트 — 전부 뮤테이션으로 폐쇄 |
| 3 | **조용한 데이터 손실 / 비멱등 쓰기** | 6 | `--force` 가 저자 행 덮어씀, CRLF 혼입, 하위 디렉터리에서 scaffold |
| 4 | **문서/스펙 내부·상호 모순** | 4 | "동시 실행" 주장 vs 스킬 본문의 명시적 부인 |
| 5 | **3변형 스킬·미러 간 내용 드리프트** | 3 | 404줄 뒤처진 전역 설치 스킬 |

**기계가 절대 못 잡는 것(HONEST_LIMITS)** — 이것이 LLM 검증의 정당한 영역이다:
- 문장 구조가 참인 사실을 거짓으로 뒤집는 순수 어법 오류 (핸드오프 §5.3 #7)
- "비용이 상환됐다" vs "증가가 멈췄다" 같은 의미 뉘앙스
- 범위 경계 판단 ("reads or mutates 는 너무 넓다" — 이번 2.11.0 에서 실제 발생)
- **증거가 존재하고 통과하지만 기준이 주장하는 속성을 단언하지 않는 것** (AC-7 두 번째 증명 사례) — 이번 세션 가장 값비싼 발견들이 이 부류였고, 뮤테이션 테스트만이 잡는다

## 2. (B) doc-lint — 만들 것이 거의 없다, 이미 있다

**부분적 발견**: `test/release/tool-signature-parity.test.ts` 가 라이브 commander 트리를 in-process 로 빌드해 문서·스킬을 대조하는 **기법**을 이미 갖고 있고, 그 `DOC_AND_SKILL_ROOTS` 는 `docs/spec/90.appendix.md`·`AGENTS.md`·`CLAUDE.md`·skills 4종만 덮으며 **`README.md` 를 빼놓았다**.

> **§2 정정 2 (2026-08-17)** — 초판은 여기서 *"이미 doc-lint 다, README 만 추가하면 된다"* 고 결론지었다. **틀렸다.** 구현자가 실측했다: `DOC_AND_SKILL_ROOTS` 가 구동하는 것은 명령 실재성 검사가 아니라 **폐기 시그니처 4토큰 blocklist** 다. README 를 그 목록에 넣으면 알려진 나쁜 문자열 4개를 금지할 뿐, 명령·앵커·도구명·개수는 여전히 아무도 안 본다.
>
> 6라운드를 부른 결함은 **형태가 반대**다 — 문자열이 잘 형성돼 있는데 더 이상 참이 아닌 주장. 그것은 commander 트리·도구 레지스트리·doctor 검사 목록을 ground truth 로 삼는 별도 하네스가 필요하다. 따라서 **기법은 재사용하되 하네스는 분리**한다. §6-1 의 "몇 줄이면 끝" 이라는 비용 추정도 그만큼 낙관적이었다 — README 를 blocklist 에 넣는 한 줄은 여전히 값싸고 유효하지만, 그것이 doc-lint 는 아니다.

**실행 프로브(실측)**: CLI 트리를 걸어 얻은 유효 경로에 대해 README 의 fenced `speckiwi` 명령이 **전부 해소(0 미해결)**. 앵커는 0 깨짐 — 단 GitHub 자동 슬러그 규칙으로 검사하면 **전부 오탐**이고, 이 저장소의 실제 관례(`<a id="...">`)를 ground truth 로 써야 한다. **잘못된 ground truth 는 검사 부재보다 나쁘다**는 실측 교훈.

> **§2 정정 (2026-08-17, 구현 중 발견)** — 이 절의 초판이 적은 수치 셋이 틀렸고, 구현자가 반박해 실측으로 확정했다. 아이러니하게도 **이 문서가 진단한 결함 패턴 1위("개수를 SSOT 에서 파생하지 않아 드리프트")를 이 문서 자신이 저질렀다.**
>
> | 초판 | 실측 | 원인 |
> |---|---|---|
> | 도구 100개 = `Object.keys(server.tools)` | **키 107개 중 `resource:` 7개를 뺀 100개** | 프로브는 필터를 썼는데 문서가 그 사실을 빠뜨림 |
> | fenced 명령 130줄 | **134줄** | `npx speckiwi …` 형태 4줄을 프로브 정규식이 놓침 |
> | CLI 경로 160개 | **159개** | 재실측 불일치 |
>
> 그래서 본문은 **깨지기 쉬운 숫자를 지우고 성질만 남긴다**(§6-2 의 개수↔열거집합 레지스트리가 하려는 바로 그것). 확정 수치는 요구의 검증 증거에만 둔다 — 거기서는 테스트가 붙잡고 있어 드리프트하면 red 가 난다.

제안 검사 카탈로그(효과순): ① fenced 명령 실재성 ② 앵커 ③ MCP 도구명(100개 런타임 열거, `*` 는 prefix 판정) ④ **개수↔열거집합 대조**(과거 "세 값이 갈린" 결함의 해법 — 문구→열거자 명시 레지스트리로, 자유 NLP 금지) ⑤ 파일 경로 실재성 ⑥ CLI↔MCP 플래그 패리티(CLI 전용 플래그 allowlist 필요) ⑦ 요구 ID 실재성. 이스케이프 해치는 `<!-- doc-lint: ignore -->` + 비실행 예시는 `text` fence.

배치: `test/release/` 에 vitest 로 — doctor 가 아니라. doctor 는 소비자 워크스페이스용이고, 이 검사는 이 저장소의 PR 시점에 내부 심볼(`buildCommand`, `toolSchemas`)을 직접 import 해야 하기 때문이다.

## 3. (C) 검증 장부 — 델타 검증, 기존 인프라로 60~70%

라운드마다 문서 **전체**를 재감사하는 것이 두 번째 낭비다. 결함은 압도적으로 가장 새 텍스트에 몰린다(이번 세션 실증).

**설계 요지**:
- **단위 = heading-section.** diff-hunk 는 줄번호가 밀려 키가 불안정하고, claim 단위는 추출기가 없다. heading 은 안정적 정체성이 있고, `computeSemanticSha`(`records.ts:45`) 의 normalize-then-hash 관용구를 거의 그대로 이식할 수 있다.
- **저장 = `kiwi/verification-ledger.jsonl`** — skill 소유 run 상태 관례(`pipeline.jsonl`·`waves.jsonl` 와 동일). `docs/.kiwi/`(도구 소유)·`.kiwi/`(세션 단위)는 소유권이 다르다.
- **clean/dirty 판정은 `listDirtyEdges`(`summary.ts:73`) 의 whitelist 게이트 로직을 이식** — compat-check 가 이미 "싼 해시 비교로 비싼 판단의 재실행을 회피"하는 정확히 같은 사상이다.
- **프로토콜**: 오케스트레이터가 섹션 해시를 장부와 대조해 **dirty 섹션 + 전후 N 줄만** 검증자에게 넘긴다.
- 무매칭 키는 **항상 dirty**(재검증 쪽으로 fail open — 비용은 들지만 거짓 신뢰는 없음).

**절감 추정**(README 1,200줄, 라운드당 5% 변경 가정): 라운드당 검증자 입력 ~9,500 → ~2,250 토큰(**75~80% 절감**), 1라운드 전체 감사 + 5라운드 델타의 6라운드 루프 전체로 **~64% 절감**.

**정직한 한계**: ① 부실하게 검증돼 clean 캐시된 섹션은 영구히 재검사 안 됨 → 승격/target 마감 전 전체 재감사 1회를 정책으로 보강. ② **개별 섹션은 참인데 바뀐 주변 맥락에서 거짓이 되는 교차 의존은 구조적으로 못 잡는다** — 전체 문서 리뷰만 잡는 부류이며, 이 설계는 그것을 포기하는 대가로 토큰을 산다. 과장하지 않는다.

## 4. (D) 위험 비례 검증 정책 — 라운드 수가 아니라 증거로 정지

이력 실증: **CRITICAL/HIGH 를 실제로 잡은 것은 전부 뮤테이션 테스트와 적대적 실행이었다.** 5~6라운드째의 일반 LLM 리뷰가 잡은 기록이 없다. 반대로 6라운드 README 루프는 **자기 수정으로 결함 8건을 새로 들여왔다**. 또한 "3중 동시 스위트 실행" 낭비는 커버리지 문제가 아니라 동시성 버그로, 정책이 아니라 도구 수준(`--no-file-parallelism` + hermeticity guard)에서 이미 해결돼 있다.

**정책 매트릭스(요약)** — 전체 표는 조사 원본:

| 클래스 | 검증 수단 | 정지 조건 |
|---|---|---|
| **A. 안전 경계/fail-closed 게이트** | 뮤테이션(전 조항) + 적대적 실행 1회 + 3+ 서브에이전트 감사, **다중 라운드 루프는 폐지**(뮤테이션이 결함당 더 싸고 강함) | CRITICAL=0 ∧ HIGH=0 ∧ 전 조항 red-확인 뮤테이션 증거 |
| **B. 계약**(스키마·저널·SRS AC) | 뮤테이션(전 AC) + 2축 교차검증, 루프는 변경 표면에 한정 | CRITICAL=0 ∧ HIGH=0 ∧ per-AC 뮤테이션 + 2축 ALL_MATCH |
| **C. 테스트 있는 행위 코드** | TDD + AC 한정 뮤테이션, 루프 ≤3, N-에이전트 감사는 교차 절단 시만 | CRITICAL=0 ∧ HIGH=0, **LOW 잔존해도 정지** |
| **D. 에이전트 지시(SKILL.md)** | 미러/드리프트 검사 + 변경 섹션 델타 1~2라운드; 안전 인접 섹션은 B 등급 | 1 독립 패스에서 HIGH+=0 |
| **E. 사람용 산문(README)** | **doc-lint 기계 패스 + 델타 1라운드, 끝** — 단 파괴적 명령(`--force`) 문단만 A 등급 상속 | doc-lint clean + 1라운드, **LOW 잔존해도 정지** |
| **F. 주석** | `@req` 실재성 기계 검사만; 코드 재서술 주석은 **검증 아닌 삭제** 대상 | — |

**기존 보증과의 정합** — 조용히 약화하지 않는다:
- **보존**: 자기검증 금지, TDD 의무, CRITICAL/HIGH 0 바닥, 계약의 다축 교차검증.
- **등가 대체**: "MEDIUM+ 0 까지 균일 루프" → C/D/E 에서 "CRITICAL+HIGH 0, 증거로 정지". 근거: MEDIUM+ 급 실포착은 전부 뮤테이션/적대 패스에서 나왔다.
- **진짜 완화 — 사용자 결정 필요**: D/E 의 LOW 추적 포기와 루프 캡. 이것이 이 연구가 설계하라고 요청받은 바로 그 트레이드이므로 **명시적으로 플래그**한다.

**부수 발견 — `@req` 검사 공백**: `@req <ID>` 주석이 test 257파일 + src 85+ 파일에 쓰이는데, 이를 `docs/spec` 실재 요구와 대조하는 기계 검사가 **하나도 없다**(ESLint 규칙 0, 스크립트 0). grep-and-resolve 한 개로 메워지는 실제 갭.

## 5. 네 축의 합류점 — 한 문장

> **주장을 SSOT 에서 파생시키고(①), 파생 불가능한 산문은 델타만 다시 보고(②), LLM 은 뮤테이션이 증명 못 하는 판단 잔여에만 태운다(③).**

과거 README 결함 8건에 적용해 보면: doc-lint 가 4건(#1,2,3,6), 미러/패리티 검사가 1건 후보(#8), 남는 진짜 LLM 몫은 3건(#4,5,7) — 6라운드가 1라운드 델타로 줄고, 그 1라운드도 8건이 아닌 3건 부류만 찾으면 된다.
