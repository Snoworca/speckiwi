# Requirement ID Allocation Status Cache Research

## 1. Context

Related SRS anchor: `OPS-FLOW-001`

SpecKiwi `add_requirement` currently generates the next Requirement ID by parsing the workspace and scanning existing Requirement IDs. This is safe because `docs/spec/**/*.srs.md` remains the canonical source of truth, but it can become expensive in very large projects.

The current implementation path is:

- `addRequirement()` calls `parseWorkspace(root)`.
- `generateNextRequirementId()` scans `workspace.records`.
- Before writing, `addRequirement()` reparses the workspace to detect stale generated-ID conflicts.

This means one Requirement registration can require full workspace parsing more than once.

## 2. Problem

For small and medium SRS repositories, full Markdown parsing is simple and robust. For very large repositories, it can become slow because every generated ID mutation must inspect all Requirement Blocks.

The cost is not mainly `Math.max()` over existing numbers. The main cost is constructing `workspace.records` from all SRS Markdown files before the ID counter can be calculated.

The naive alternative, keeping an in-memory counter, does not fit stdio MCP well. A stdio server may be short-lived, restarted by the client, or run separately from CLI invocations. In-memory state would also diverge between CLI and MCP processes.

## 3. Proposed Direction

Use `kiwi/.status.json` as a derived, disposable status cache for Requirement ID allocation.

This file must not become a source of truth. The canonical source remains:

```text
docs/spec/**/*.srs.md
```

The cache is only an optimization. If it is missing, malformed, stale, or unsafe, SpecKiwi must fall back to the current full workspace scan.

## 4. Candidate File Shape

```json
{
  "schemaVersion": "1.0.0",
  "generatedAt": "2026-06-27T00:00:00.000Z",
  "source": "derived-cache",
  "specFingerprint": {
    "docs/spec/00.index.md": "sha256...",
    "docs/spec/50.nodejs-implementation.srs.md": "sha256..."
  },
  "idCounters": {
    "FR:NODE": 22,
    "IR:CLI": 33,
    "FR:MCP": 25
  },
  "srsLock": {
    "state": "unlocked",
    "lockFile": "kiwi/.srs.lock",
    "owner": null,
    "operation": null,
    "acquiredAt": null,
    "expiresAt": null,
    "lastMessage": null
  }
}
```

The key format can be changed, but it should include both requirement type prefix and scope prefix. For example:

```text
FR:NODE
IR:CLI
REL:FLOW
```

## 5. Add Requirement Flow

Recommended flow:

```text
1. Read kiwi/.status.json.
2. Validate schemaVersion and source.
3. Validate spec fingerprints against current docs/spec files.
4. If the cache is valid and fresh, allocate next ID from idCounters.
5. If the cache is missing, broken, or stale, fall back to full workspace parse.
6. Before writing, still check that the selected ID does not already exist.
7. After successful mutation, regenerate or update kiwi/.status.json.
8. Write the cache atomically.
```

The cache can reduce repeated full scans, but it cannot remove the final collision check. Collision protection remains necessary because users can edit Markdown directly and because multiple CLI/MCP processes can run concurrently.

## 6. Freshness and Invalidation

The cache must be considered invalid when any of the following changes:

- `docs/spec/00.index.md`
- Any registered scope SRS document
- Scope Map entries
- Requirement ID format rules
- Requirement type prefix mapping
- Cache schema version

Freshness can be checked with SHA-256 fingerprints. `mtime` alone is weaker and can miss edge cases. A practical compromise is `size + mtime + sha256`, where SHA calculation can be limited to SRS files known from the last index parse.

If validation fails, the system must not fail the mutation only because the cache is bad. It should rebuild from canonical SRS Markdown.

## 7. Atomic Write Discipline

Because CLI and MCP can both update the workspace, `kiwi/.status.json` writes should be atomic:

```text
1. Write kiwi/.status.json.tmp-<pid>-<random>.
2. fsync when practical.
3. Rename temp file to kiwi/.status.json.
```

The cache update should happen only after the SRS mutation succeeds. If cache write fails after the SRS mutation succeeds, the mutation can still return success with a warning because the cache is rebuildable.

## 8. Adversarial Lock Review

The status JSON should include SRS lock state, but it should not be the only lock authority.

Adversarial conclusion:

- Good idea: show lock state in `kiwi/.status.json`.
- Bad idea: make `kiwi/.status.json` itself the only lock.
- Safer design: use a separate atomic SRS lock file and mirror its current state into `kiwi/.status.json`.

Reasoning:

`kiwi/.status.json` is a derived cache. Derived caches must be deletable and rebuildable. If the same file is also the only lock authority, then deleting or regenerating the cache can accidentally clear a real mutation lock.

Recommended split:

```text
kiwi/.srs.lock
  actual SRS mutation lock, acquired through atomic create/open semantics

kiwi/.status.json
  derived cache plus mirrored lock status for diagnostics and tool UX
```

This keeps the cache disposable while preserving write-safety semantics.

## 9. Lock Behavior

The lock is SRS-only. It applies to mutations that can write:

- `docs/spec/**`
- `docs/rule/**` when SRS rule files are part of the mutation contract
- SRS index rollups
- SRS mutation cache files that affect Requirement ID allocation

It should not block unrelated research notes, pipeline logs, or workflow artifacts unless a specific operation also mutates SRS files.

Read-only operations should remain available while a lock is active:

- `list`
- `show`
- `summary`
- `validate`
- MCP read tools

Write operations should fail fast when an active non-stale SRS lock exists.

Expected CLI message:

```text
SRS mutation lock is active by <owner> for <operation> until <expiresAt>. Retry later, or pass --ignore-lock only if you are certain the previous mutation is stale.
```

Expected MCP structured error:

```json
{
  "ok": false,
  "error": {
    "code": "SRS_LOCKED",
    "message": "SRS mutation lock is active by <owner> for <operation> until <expiresAt>.",
    "remediation": "Retry later or pass ignoreLock=true only if the previous mutation is stale."
  },
  "diagnostics": [
    {
      "code": "SRS_LOCKED",
      "severity": "warning",
      "message": "SRS mutation lock is active."
    }
  ]
}
```

## 10. Ignore Lock Escape Hatch

The CLI and MCP mutation surfaces should expose an explicit lock bypass:

```text
CLI: --ignore-lock
MCP: ignoreLock: true
```

This bypass must be narrow:

- It only bypasses the SRS mutation lock.
- It must not bypass stale patch guards.
- It must not bypass generated-ID collision checks.
- It must not bypass table-cell safety.
- It must not bypass validation of trace targets.
- It must produce diagnostics recording that the lock was ignored.

This is an operator escape hatch for stale locks, not a general unsafe mode.

## 11. Lock TTL and Owner Metadata

The lock needs enough metadata for users and agents to decide whether to wait or escalate:

```json
{
  "schemaVersion": "1.0.0",
  "owner": {
    "processKind": "cli",
    "pid": 12345,
    "hostname": "device-name",
    "command": "add-requirement",
    "requestId": "uuid-or-random-token"
  },
  "operation": "add_requirement",
  "scope": "SRS",
  "target": "v2.3.0",
  "acquiredAt": "2026-06-27T00:00:00.000Z",
  "expiresAt": "2026-06-27T00:02:00.000Z"
}
```

TTL is required because a CLI or stdio MCP process can die while holding a lock. A stale lock may be ignored or replaced only after the tool proves it is expired, or after the caller explicitly uses `--ignore-lock` / `ignoreLock: true`.

## 12. Safety Rules

The cache must follow these rules:

- Never allocate an ID that is not rechecked against canonical SRS records before write.
- Never treat `kiwi/.status.json` as canonical evidence.
- Never require users to manually edit the cache.
- Never block normal operation because the cache is absent.
- Never reuse discarded or existing Requirement IDs.
- Never allow stale cache data to override Markdown-derived records.
- Never rely on `kiwi/.status.json` alone to enforce mutation locking.
- Never let `--ignore-lock` disable stale patch checks, generated-ID collision checks, or SRS-MD safety validation.
- Never let a stale lock block the repository forever.

## 13. Expected Benefit

The cache helps most when:

- The repository has many SRS files.
- Requirement registration happens repeatedly in one workflow.
- stdio MCP restarts often and cannot rely on process memory.
- CLI and MCP share the same repository-local cache.

It does not eliminate all parsing. Validation, summary, trace checking, and stale write protection still need canonical SRS reads. It specifically optimizes the hot path for generated ID allocation.

The lock state helps most when:

- Multiple agents or CLI/MCP clients can mutate SRS files concurrently.
- A stdio MCP server restarts and process-local lock state is lost.
- Agents need a clear retry-later message instead of guessing why mutation failed.
- A stale lock must be diagnosed and bypassed intentionally.

## 14. Three-Agent Usability Review: External Completed Work Log

Three read-only sub-agent reviews evaluated whether Completed Work Log rows should remain embedded in `docs/spec/00.index.md` or move to a separate Markdown file linked from the index.

Reviewed perspectives:

- Agent UX and real workflow ergonomics.
- Parser, mutation, CLI, MCP, bootstrap, and test compatibility.
- Adversarial failure modes across stale cache, stale lock, link rot, dual source-of-truth risk, hallucination, and stdio MCP process boundaries.

### 14.1 Synthesis

Moving Completed Work Log rows out of `00.index.md` is a real usability improvement, but only if the official CLI and MCP tools remain the normal read/write interface.

Recommended direction:

```text
docs/spec/00.index.md
  small navigation index, target map, scope map, summaries, and a link to the completed-work log

docs/spec/05.completed-work.md
  canonical Markdown storage for Completed Work Log rows
```

This should not create a new requirement source of truth. Completed Work Log remains a read-only summary and audit surface. Requirement completion remains governed by Requirement Block `Status`, checked Acceptance Criteria, Verification Evidence, and Change Notes.

The strongest usability argument is token and attention control. Agents frequently need `00.index.md` only to discover the active target, scope files, and current summaries. A long Completed Work Log makes the index noisier and encourages manual table edits. A linked log file keeps the index small while preserving human-readable Markdown history.

The strongest counterargument is complexity. Current code is tightly coupled to `00.index.md`:

- `discoverSrsFiles()` reads `docs/spec/00.index.md` as the fixed index entry point.
- `parseIndexDocument()` finds `## N. Completed Work Log` inside the index.
- `listCompletedWork()` and `summarizeTarget()` read `workspace.index.completedWork`.
- `validateWorkspace()` diagnostics currently report completed-work issues against `docs/spec/00.index.md`.
- `addCompletedWork()` patches `docs/spec/00.index.md` directly and also handles legacy five-column to six-column `Report Paths` migration.
- CLI and MCP are thin adapters over the shared core path, so the core contract must change before documentation can claim the split.

Therefore this is not a documentation-only cleanup. It is a parser/discovery/mutation compatibility feature.

### 14.2 Usability Contract

The external completed-work log should follow these rules:

- `docs/spec/05.completed-work.md` is the preferred write target once present.
- `00.index.md` links to the external log and should not keep growing with new rows.
- Existing `00.index.md` Completed Work Log tables remain readable for backward compatibility.
- New writes go to exactly one target file; do not bidirectionally sync `00.index.md` and `05.completed-work.md`.
- If both the legacy index table and the external file contain non-empty rows, tools must either merge with explicit source diagnostics or report a migration warning; they must not silently ignore one side.
- `speckiwi completed-work`, `speckiwi add-completed-work`, MCP `list_completed_work`, MCP `add_completed_work`, and `speckiwi://completed-work` keep their existing command names, resource URIs, and JSON payload shape.
- `Report Paths` grammar remains lexical only. Report path existence checks should be an opt-in validation mode, not a default release blocker.
- `add-completed-work` must not implicitly migrate historical rows as a hidden side effect. Migration should be a separate dry-run-capable operation.

### 14.3 Bounded Payload Requirement

Moving rows to another file will not reduce agent token usage if summaries still return the full log by default.

The read contract should also support bounded payloads:

- Default target summaries should include a recent limited subset, total count, and `hasMore`.
- Full history should be obtained through `completed-work` / `list_completed_work` with explicit filters such as `target`, `since`, `limit`, and ordering.
- MCP responses should preserve diagnostics and source references so an agent can decide whether to request more history.

This pairs with the v2.3.0 compact-read work: token reduction should be measured, not assumed.

### 14.4 Safe Development Sequence

Recommended implementation sequence:

1. Add failing tests proving `docs/spec/05.completed-work.md` is read while existing CLI/MCP completed-work payloads remain unchanged.
2. Extract Completed Work Log table parsing from `index-parser.ts` into a shared parser that accepts a `TextFile` and records source file path and line.
3. Extend discovery with an optional completed-work file, without making its absence a validation error.
4. Preserve legacy index table reads when the external file is absent.
5. Update validator diagnostics to point at the row source file rather than hard-coding `docs/spec/00.index.md`.
6. Route `addCompletedWork()` through a canonical target-file resolver: external file if present, otherwise current index fallback.
7. Add an explicit migration command later, with dry-run preview and conflict diagnostics.
8. Update bootstrap templates, SRS-MD rules, appendix command reference, fixtures, and MCP/CLI parity tests.

### 14.5 Adversarial Constraints

The completed-work split, `kiwi/.status.json`, and SRS lock design only improve usability if they do not become additional canonical state.

Required constraints:

- `kiwi/.status.json` remains a disposable derived cache.
- SRS mutation locking uses a separate atomic lock file, with lock state mirrored into `kiwi/.status.json` only for diagnostics.
- `ignoreLock` bypasses only the SRS mutation lock and never bypasses stale patch guards, generated-ID collision checks, table-cell safety, trace validation, or SRS validation.
- Completed Work Log rows never become verification evidence.
- Link rot should be diagnosable, but default validation should not fail merely because a report path target is absent unless an explicit strict report-link mode is requested.
- Concurrent mutation tests must cover active lock denial, stale lock recovery, crash recovery, ignored-lock diagnostics, and cache regeneration.

### 14.6 Measurement Criteria

The usability claim should be accepted only if implementation evidence shows:

- Lower default `00.index.md` token footprint after bootstrap and after long-running projects accumulate logs.
- `summarize_target` and MCP summary payloads expose bounded completed-work data by default.
- `add_requirement` median and p95 latency improve on large fixtures when the status cache is fresh.
- Cache hit rate, fallback rate, and cache invalidation reasons are observable in diagnostics or debug output.
- Generated-ID collision escapes remain zero.
- Agent workflow fixtures show fewer raw Markdown fallbacks for completed-work additions and current-work status checks.
- CLI/MCP parity tests prove unchanged JSON payload shape for completed-work reads and writes.

## 15. Ten-Axis Decision Committee: CORRECTION and `deleted`

A 10-axis read-only decision review evaluated the ambiguous relationship between pipeline `CORRECTION`, workflow logical deletion, plan checkbox mutation, SRS locking, backward compatibility, and measurable token savings.

### 15.1 Decision Summary

The committee accepts the research direction as conditionally valid, with these binding decisions:

- Do not add `deleted` to the pipeline `status` enum. Pipeline status remains `TASK_DONE`, `NEEDS_USER`, `FAILED`, `DRY_RUN`, or `CORRECTION`.
- Treat `deleted` as an effective read state created by a guarded tombstone or repair record, not as a normal execution status.
- For pipeline JSONL, logical deletion should use `status="CORRECTION"` with an optional `operation.kind="logical_delete"` extension, or an equivalent append-only tombstone record handled by the shared JSONL core. Old `schema_version="1.0.0"` events without `operation` remain valid active events.
- For plan Markdown, deletion must not remove or rewrite task lines as the deletion source of truth. The tombstone belongs in an append-only journal, worklog, PM state, or repair record; plan display is only a projection.
- `includeDeleted` belongs to read, list, and tail operations. It must not be required for delete mutation inputs.
- `ignoreLock` remains SRS-lock-only. It must not bypass workflow stale guards, generated-ID collision checks, table-cell safety, trace validation, or SRS validation.
- The three Doc230 candidate areas now have canonical SRS requirements. Implementation must use those IDs instead of the research candidate labels.

### 15.2 Latest-State Precedence

Workflow readers should compute effective state in this order:

1. Parse each JSONL line structurally. Invalid or non-object lines produce diagnostics and are excluded from state selection.
2. Validate schema version, required fields, timestamp, status, and event identity.
3. Compute stable identity, such as `eventKey = skill + ":" + run_id` for pipeline events. Duplicate active event keys are ambiguous and excluded from latest-state selection.
4. Validate logical-delete tombstones first. A tombstone must include target identity, reason, owner, timestamp, idempotency key or journal key, source hash or stale guard, and record class.
5. Apply logical deletion before correction. A deleted target is inactive by default and cannot be resurrected by a later correction.
6. Validate and apply correction chains. `CORRECTION` requires `corrects_run_id` unless explicitly marked `external:true`; chain depth above 5 or cycles are invalid.
7. Exclude meta records, corrected records, deleted records, and invalid records from latest-state candidates.
8. Select latest active state by parsed timestamp descending, then JSONL line number descending.
9. Only active `FAILED` or `NEEDS_USER` blocks automatic next-step recommendation. Deleted or corrected failures do not block automation.
10. Tail and audit views may show all valid lines, but must annotate `correctedBy`, `deletedBy`, and `inactiveReasons`.

Restore or undelete behavior is out of scope for the first logical-delete implementation. Tombstone-of-tombstone, correction-of-tombstone, and plain deletion of `CORRECTION` events must be rejected unless a future restore requirement defines a separate safe contract. Correction-of-correction may be allowed only when the correction graph remains deterministic and does not resurrect a directly tombstoned record.

### 15.3 CLI and MCP Contract

Logical delete commands and tools should be thin adapters over one core mutation envelope.

Minimum mutation input:

- `runId`
- `recordClass`
- `recordId`
- `owner`
- `reason`
- `staleGuard`
- optional `dryRun`
- optional `idempotencyKey`

Minimum mutation output:

- `ok`
- `value`
- `mutation.kind`
- `mutation.dryRun`
- `mutation.written`
- `mutation.result`
- `mutation.journalKey`
- `mutation.idempotencyKey`
- `mutation.journalState`
- `mutation.operations[]`
- `mutation.pendingRepair`
- `diagnostics`
- `diagnosticsSummary`

Recommended names:

```text
CLI: speckiwi workflow delete --class <recordClass> --id <recordId> --run-id <runId> --owner <owner> --reason <text> --stale-guard <guard> --json
MCP: delete_workflow_record({ runId, recordClass, recordId, owner, reason, staleGuard, idempotencyKey?, dryRun? })
```

Read surfaces should expose `includeDeleted` separately:

```text
speckiwi pipeline tail --include-deleted --json
speckiwi worklog tail --run-id <runId> --include-deleted --json
speckiwi plan status --run-id <runId> --include-deleted --json
```

### 15.4 Compatibility and Migration

Pipeline event schema should evolve by optional minor-version fields, not by changing required v1.0.0 semantics.

- Existing `schema_version="1.0.0"` pipeline events remain accepted.
- `schema_version="1.1.0"` may add optional `operation`, `deleted`, or tombstone metadata.
- Unsupported major versions fail clearly.
- Legacy `.snoworca` worklogs without pipeline schema fields are parsed only in legacy mode with diagnostics, not as strict pipeline events.
- Codex and etc shared `pipeline-event.md` copies must be updated together when this schema is formalized.

## 16. Ten-Axis Research: Merge-Time Requirement ID Collision Repair

### 16.1 User Scenario

The common real-world renumbering case is not aesthetic cleanup. It occurs when multiple worktrees or branches add new SRS requirements in parallel, then Git merges both branches and the same generated Requirement ID appears in more than one Requirement Block.

This creates `SRS-E002` after the merge. The right tool is therefore a merge-time collision repair workflow, not a general "renumber all requirements" or "compact gaps" feature.

### 16.2 Decision

Build a guarded Requirement ID collision repair capability only for actual duplicate-ID failures.

The tool should:

- Run only when validation detects duplicate Requirement IDs, or when the user explicitly names a duplicate ID that exists in the parsed workspace.
- Diagnose every occurrence in the duplicate group with `filePath`, `headingLine`, title, status, stability, target, marker state, and a block hash.
- Require an explicit survivor/renamed occurrence selection before applying a write.
- Allocate a replacement ID through the same canonical allocation rules as `add_requirement`, using the status cache only as an optimization.
- Preserve Status, Stability, Acceptance Criteria, Verification Evidence, and free-text content unless the user selects a separate SRS-supported mutation.
- Fail closed on ambiguous inbound references instead of guessing.
- Re-run validation and target summary after apply.

The tool should not:

- Offer general gap-filling, pretty numbering, or repo-wide arbitrary renumbering.
- Reuse IDs from discarded, deprecated, or deleted records.
- Rewrite research files, analysis files, raw pipeline logs, evidence notes, or arbitrary prose references.
- Convert duplicate requirements to `verified`, `discarded`, or `deleted` as part of the ID repair unless a separate guarded mutation is requested.

### 16.3 Ten-Axis Findings

| Axis | Focus | Finding |
| --- | --- | --- |
| 1 | Git merge provenance | During an active merge, `HEAD`, `MERGE_HEAD`, `merge-base`, index stages, and `AUTO_MERGE` can help identify branch side. After a completed merge, reliable provenance requires explicit base/ours/theirs refs or merge parents. Squash, rebase, and fast-forward cases cannot be inferred safely. |
| 2 | Parser and validator diagnostics | `SRS-E002` currently proves the duplicate exists but is too thin for repair because it reports the later occurrence rather than a full duplicate group. Repair needs grouped diagnostics with all occurrences and stable block identity. |
| 3 | ID status cache | `kiwi/.status.json` improves hot-path allocation in one checkout but cannot coordinate independent worktrees. It remains a derived accelerator, not a global allocator. Merge-time repair is still needed. |
| 4 | Core mutation architecture | Existing patch application is single-file and snapshot-guarded. Collision repair can touch multiple SRS files, trace tables, index rows, and completed-work rows, so it needs a multi-file patch plan, journal, and rollback/pending-repair strategy. |
| 5 | Structured reference boundaries | Safe automatic edits are limited to the selected block heading and unambiguous structured rows. Ambiguous trace, evidence, research, analysis, and pipeline references must be report-only or explicitly selected. |
| 6 | CLI UX | CLI should expose diagnose/plan/apply commands with JSON-first output, dry-run previews, explicit occurrence mapping, and no broad `--force`. `--ignore-lock` may bypass only the SRS lock. |
| 7 | MCP UX | MCP should expose the same core service through structured tools. Active locks, ambiguity, and partial failures should be tool results with diagnostics, not protocol errors. |
| 8 | Regression fixtures | Tests must cover same-file duplicates, cross-file duplicates, ambiguous references, completed-work references, stale snapshots, active locks, idempotent reruns, and post-apply validation. |
| 9 | SRS decomposition | Existing `FR-NODE-027`, `REL-NODE-005`, `FR-NODE-019`, `IR-CLI-028`, and `FR-MCP-032` are dependencies, not full coverage. A new core repair requirement plus CLI/MCP/workflow requirements is needed. |
| 10 | Agent workflow | Agent instructions should say: after merge/rebase, validate first; if `SRS-E002` appears, run repair diagnose/dry-run; do not hand-edit IDs unless no supported tool exists and the user explicitly authorizes a minimal SRS-MD patch. |

### 16.4 Proposed Workflow

The merge workflow should be deterministic:

1. Resolve normal Git conflict markers first. The repair tool must fail if `<<<<<<<`, `=======`, or `>>>>>>>` remains in `docs/spec/`.
2. Run `speckiwi validate --json` or MCP `validate_spec`.
3. If no `SRS-E002` exists, do not run ID repair.
4. If `SRS-E002` exists, run diagnose/dry-run:

```sh
speckiwi repair requirement-id-collisions diagnose --json
speckiwi repair requirement-id-collisions plan --id FR-XXX-001 --json
```

5. Select which occurrence keeps the old ID and which occurrence receives a new ID. The selection must use `filePath + headingLine + blockHash`, not only the old ID.
6. Apply from an explicit plan:

```sh
speckiwi repair requirement-id-collisions apply --plan /tmp/req-id-repair.json --json
```

7. Re-run:

```sh
speckiwi validate --fail-on-warning --json
speckiwi summary --target v2.3.0 --json
```

For MCP parity, the equivalent tools should be:

- `diagnose_requirement_id_collisions`
- `plan_requirement_id_collision_repair`
- `apply_requirement_id_collision_repair`

The MCP result should preserve the same mutation envelope, diagnostics, diagnostics summary, generated replacement ID, patch preview, ambiguity report, lock state, written files, and retry guidance as the CLI JSON output.

### 16.5 Replacement ID Allocation Policy

Replacement allocation should use the canonical parsed SRS records, with `kiwi/.status.json` only as a fast path.

Rules:

- Derive the prefix from the original duplicate ID unless the user explicitly supplies a valid replacement ID.
- Use the next available integer after the maximum active or historical ID for the same prefix.
- Do not reuse IDs from discarded, deprecated, deleted, superseded, or stale records.
- Perform a final full parse collision check immediately before write.
- Treat a stale, missing, corrupt, or locked status cache as a fallback condition, not as a reason to proceed unsafely.
- If two repair commands race and choose the same generated ID, the loser must return a stale/generated-ID collision envelope and write nothing.

### 16.6 Reference Update Boundary

The repair planner should classify references into three groups.

Automatically safe:

- The selected duplicate Requirement heading.
- The selected block's unambiguous self-reference rows when they structurally refer to the same Requirement Block.
- Explicitly mapped Trace Links rows where `Type=Requirement`, the cell value exactly equals the old ID, and the plan identifies which occurrence the row means.
- Explicitly mapped Completed Work Log `Requirement IDs` cells when the row is part of the same selected repair plan.

Report-only by default:

- Inbound trace rows from other requirements when more than one occurrence could be intended.
- Evidence Reference and Notes text.
- Change Notes, Research Notes, Rationale, Implementation Notes, and free prose.
- `docs/research`, `docs/analysis`, and `kiwi/pipeline.jsonl`.

Never automatic in this tool:

- Status transitions.
- Stability transitions.
- Acceptance Criteria completion changes.
- Verification Evidence claims.
- Bulk archive/finalize behavior.
- Physical deletion of Requirement Blocks.

If two duplicate blocks are actually the same logical requirement, the safe path is still two-step:

1. Repair duplicate IDs first so every block has a unique ID.
2. Use separate guarded SRS mutations to mark one requirement as discarded/deleted/superseded according to SRS-MD rules.

Leaving a discarded block with the duplicate old ID is invalid because `SRS-E002` remains.

### 16.7 Core Service Shape

The Node core should expose shared services that both CLI and MCP call:

```ts
type RequirementIdCollisionOccurrence = {
  requirementId: string;
  filePath: string;
  headingLine: number;
  blockHash: string;
  title: string;
  target?: string;
  status?: string;
  stability?: string;
};

type RequirementIdCollisionPlan = {
  duplicateId: string;
  keep: RequirementIdCollisionOccurrence;
  rename: RequirementIdCollisionOccurrence;
  replacementId: string;
  referencePolicy: "leave_ambiguous" | "explicit_edits_only";
  referenceEdits: Array<{
    filePath: string;
    line: number;
    from: string;
    to: string;
    reason: string;
  }>;
  dryRun: boolean;
  ignoreLock?: boolean;
};
```

Required service operations:

- `diagnoseRequirementIdCollisions(root)` returns all duplicate groups and repair readiness diagnostics.
- `planRequirementIdCollisionRepair(input)` returns a multi-file patch plan without writing.
- `applyRequirementIdCollisionRepair(input)` acquires the SRS mutation lock, revalidates snapshots, applies the plan, journals partial state, and returns the unified mutation envelope.

Multi-file apply should extend the current single-file patch discipline:

- Precompute snapshots for every touched file.
- Verify all snapshots before any write.
- Write temp files and rename atomically per file.
- Keep a transaction journal with completed and pending operations.
- Attempt rollback on partial failure.
- Return `pendingRepair` metadata if rollback cannot restore the workspace.
- Never report `written:true` unless every planned write is confirmed.

### 16.8 CLI Contract

Recommended command group:

```sh
speckiwi repair requirement-id-collisions diagnose --json
speckiwi repair requirement-id-collisions plan \
  --id FR-ARCH-001 \
  --keep docs/spec/10.product-architecture.srs.md:5 \
  --rename docs/spec/10.product-architecture.srs.md:24 \
  --allocate-next \
  --write-plan /tmp/req-id-repair.json \
  --json
speckiwi repair requirement-id-collisions apply --plan /tmp/req-id-repair.json --json
```

Options:

- `--replacement-id <id>`: explicit replacement ID instead of next available.
- `--dry-run`: default for `plan`; optional preview mode for `apply`.
- `--ignore-lock`: bypasses only the SRS mutation lock and records diagnostics.
- `--reference-edit <path:line:from=to>`: explicit structured reference edit.
- `--base <ref> --ours <ref> --theirs <ref>`: optional provenance hints when no active merge metadata remains.

The CLI should refuse:

- Duplicate ID repair when validation does not contain the selected duplicate.
- A write without an explicit plan or explicit occurrence mapping.
- Ambiguous inbound reference rewriting without explicit reference edits.
- `--force` semantics that bypass stale patch, validation, lock safety beyond lock-only ignore, or generated-ID collision checks.
