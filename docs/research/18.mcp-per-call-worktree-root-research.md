# 18. MCP 도구의 per-call worktree root 인자 — 조사와 개선 계획

- 작성: 2026-08-16
- 상태: **조사 완료 / 착수 전 (요구 저작 필요)**
- 발단: 사용자 지시 — "대부분 워크트리에서 작업하는데 세션은 메인 세션이다. MCP 도구에 워크트리 절대 경로 인자가 필요하다."
- 사용자 판정: 기동 인자 금지는 유지, **메서드 인자까지 금지하는 것은 잘못이다**

---

## 0. 요약

100개 MCP 도구 중 **per-call 경로 인자가 필요한 것은 53개**(`orchestrate_*` 27 + `workflow_*` 26)이고, **47개(SRS 계열)는 필요하지 않다** — 계약상 호스트 루트에 묶여야 하기 때문이다.

`workflow_*` 26개는 **이미 `path` 인자를 받는다.** 문제는 인자의 부재가 아니라 **해소 기준**이다: 모든 경로가 `path.join(root, …)` 로 MCP root 에 접합되므로, 워크트리의 산출물을 가리킬 수 없다.

즉 이 작업은 "100개 도구에 인자 추가"가 아니라 **53개 도구의 경로 해소 기준을 root 고정에서 호출자 지정으로 여는 것**이며, 47개는 지금대로 두는 것이 맞다.

## 1. 현재 상태 (실측)

### 1.1 root 는 서버 프로세스에 결속된다

`src/mcp/server.ts:20` — `IR-CLI-045 / REL-MCP-004: MCP 서버 기동 표면은 root 파라미터를 노출하지 않는다 (cwd discovery 전용).`

`resolveMcpStartupRoot()` 가 cwd 상위 탐색으로 root 를 1회 정하고, `createMcpServer({ root })` 로 전 도구에 주입된다. 세션 도중 변경 경로는 없다.

### 1.2 경로는 전부 root 에 접합된다

`src/core/workflow/artifacts.ts:119` `path.join(root, relativeDir)` · `:286` `path.join(root, relativePath)`

`workflow_*` 가 받는 `path` 는 **root 기준 상대 경로**이며 절대 경로 입력 경로가 없다.

### 1.3 report path 는 절대 경로를 명시적으로 거부한다

`src/mcp/server.ts:36-41` — `reportPathSchema` 가 `REPORT_PATH_TOKEN_REGEX` 로 `repository-relative POSIX report path; **no absolute paths**, traversal, URL schemes, backslash, pipe, comma, newline, or #` 를 강제한다.

이 스키마는 `add_completed_work` 의 `reportPaths` 에 쓰인다. **절대 경로 도입 시 이 규칙과 충돌하므로 범위를 명확히 갈라야 한다**(§4.3).

### 1.4 금지 요구의 정확한 형태

`REL-MCP-004`(status `implemented`, stability `evolving`, target `v2.3.0`, 태그 `user-directive`)

| AC | 내용 | 이번 변경 대상 |
|---|---|---|
| AC-1 | envelope 에 workspaceRoot·rootSource·index path·active target 노출 | 유지 (오히려 강화 필요) |
| AC-2 | `rootSource` 는 `server-cwd-discovery` / `auto-init` 만, explicit 없음 | **개정 필요** |
| AC-3 | **per-call root/workspaceRoot 인자는 지원하지 않고 fail-closed 거부** | **철회 대상** |
| AC-4 | `startMcpServer`/`McpServerOptions` 는 root 파라미터 미노출 | **유지** (사용자 명시) |
| AC-5 | multi-root 테스트가 sibling repository 를 읽거나 변이하지 않음을 증명 | **재정의 필요** (§4.2) |
| AC-6 | 문서·agent instruction 이 workspace identity 확인을 요구 | 유지·확장 |

Rationale 원문: *"사용자 지시(2026-07-06)로 MCP의 root 파라미터를 전면 제거한다 … rootSource의 explicit 분기를 제거하여 「서버가 뜬 곳 = 작업 대상」으로 단순화"*.

**AC-3 과 AC-4 를 한 요구에 묶은 것이 이번 마찰의 원인이다.** 기동 인자 금지(AC-4)의 근거 — 잘못된 root 로 서버가 떠서 조용히 오염되는 것 — 는 per-call 인자에는 그대로 적용되지 않는다. per-call 은 호출마다 의도가 명시되므로 오히려 **덜** 조용하다.

## 3. 재개봉 선행조건 셋의 현재 상태

다중 root 는 5회 거절됐고(2026-05-26 / 07-06 / 07-27 / 07-31 / 08-07), 재개봉 선행조건 셋이 기록돼 있다. 이번 변경이 그 셋을 어떻게 통과하는지:

### (a) `FR-FLOW-043` AC-2/AC-5 재정의

현행: *"run 자신의 cwd 기준 1회 평가, **MCP root 로는 절대 해소 안 함**"*.

→ **재정의 불필요, 오히려 이번 설계가 이 요구와 정렬한다.** 저널이 cwd 를 쓰는 이유는 "실행 위치가 진실"이라는 원칙인데, per-call root 는 그 원칙을 MCP 표면으로 확장하는 것이다. 다만 **우선순위를 명시**해야 한다: per-call root 가 주어지면 그것이, 없으면 cwd 가, MCP root 는 어느 경우에도 저널을 해소하지 않는다.

### (b) 대상 배치의 요구 ID 충돌·validate 오류 정리

→ **A군을 제외함으로써 원천 차단.** 요구 ID 발급과 SRS mutation 이 호스트에만 남으므로 충돌 자체가 발생하지 않는다. 이것이 이번 제안이 과거 제안과 갈리는 지점이다 — 과거 안은 SRS 까지 다중 root 로 열었다.

### (c) `pinning.ts` 의 `ls-tree --full-tree` 저장소-최상위-기준 경로 처리

→ **미해결. 착수 전 조사 필요.** 워크트리의 git common dir 은 호스트와 공유되므로 `--full-tree` 결과가 어느 최상위 기준인지 확인해야 한다. §5 의 선행 작업으로 둔다.

## 4. 설계 제안

### 4.1 인자 이름과 형태

```
workspaceRoot?: string   // 절대 경로. 생략 시 현행 동작(MCP root)
```

- **이름**: `root` 가 아니라 `workspaceRoot` — `AC-1` 이 이미 envelope 에 `workspaceRoot` 를 싣고 있어 같은 개념에 같은 이름을 쓴다. 진입점 하나 원칙.
- **절대 경로만 허용**. 상대 경로를 허용하면 "무엇에 대한 상대인가"가 다시 모호해진다.
- **생략 가능**. 생략 시 오늘과 동일하게 동작하므로 기존 호출자는 무변경.

### 4.2 안전 게이트 (AC-5 계승)

per-call root 를 열되 **아무 디렉터리나 되는 것은 아니다.** 다음을 모두 만족해야 수용한다.

1. **git common dir 이 MCP root 와 동일**해야 한다 — 즉 같은 저장소의 워크트리여야 한다. sibling repository 는 거부한다(AC-5 의 보호 대상 유지).
2. **`docs/spec/` 아래를 읽거나 쓰는 도구는 거부**한다 — A군은 애초에 인자를 노출하지 않고, B·C군이 SRS 경로를 만지려 하면 fail-closed.
3. **거부는 구조화 진단으로** — `workspace-root-not-a-worktree` · `workspace-root-crosses-repository` · `workspace-root-forbidden-for-srs` 세 코드.

이 셋이 있으면 AC-5 의 "sibling repository 를 읽거나 변이하지 않음"은 **더 강하게** 유지된다 — 오늘은 root 가 하나뿐이라 검사할 것이 없었지만, 이제 명시적 검사가 생긴다.

### 4.3 report path 규칙과의 관계

`reportPathSchema` 는 절대 경로를 금지한다(§1.3). **이 규칙은 건드리지 않는다.**

`reportPaths` 는 Completed Work Log 에 기록되는 **저장소 상대 식별자**이고, `workspaceRoot` 는 **해소 기준**이다. 층이 다르므로 공존한다: `workspaceRoot` 가 기준을 정하고, 그 안에서 report path 는 여전히 상대다.

### 4.4 envelope 강화 (AC-1·AC-6)

응답 envelope 의 `rootSource` 에 값 하나를 추가한다.

| 값 | 의미 |
|---|---|
| `server-cwd-discovery` | 현행 |
| `auto-init` | 현행 |
| **`per-call-workspace-root`** | 호출이 명시 |

`workspaceRoot` 는 이미 envelope 에 있으므로 **호출자는 자기가 어느 루트에서 답을 받았는지 항상 확인할 수 있다.** 이것이 AC-6 이 요구하는 identity 확인을 per-call 상황으로 확장하는 방법이다.

## 7. 판단

사용자 지적이 맞다. `REL-MCP-004` 는 **성격이 다른 두 금지를 한 요구에 묶었다.**

- **기동 인자 금지(AC-4)** — 근거 있다. 서버가 뜬 곳이 곧 작업 대상이라는 단순성이 잘못된 root 기동의 조용한 오염을 막는다. **유지한다.**
- **per-call 인자 금지(AC-3)** — 같은 근거가 적용되지 않는다. per-call 은 호출마다 의도가 명시되고 envelope 로 관측되므로 오히려 덜 조용하다. **철회 대상이다.**

그리고 과거 5회 거절된 다중 root 안과 이번 안은 **범위가 다르다.** 과거 안은 SRS 를 포함한 전면 다중 root 였고, 이번 안은 SRS 를 호스트에 고정한 채 run/plan 상태만 여는 것이다. 거절 사유의 핵심(요구 ID 충돌·인덱스 분기)이 **구조적으로 발생할 수 없다.**

착수는 선행조건 (c) 조사 뒤에 판정한다. → **§8 에서 조사 완료. 착수 가능.**

- 방법: 이 저장소에 **실제 linked worktree** 를 detached 로 생성하고, 별도의 **sibling repository** 를 하나 만들어 대조. 측정 후 둘 다 제거(`git worktree remove --force` + `prune`).
- 환경: `git version 2.48.1.windows.1`

### 8.1 질문

`pinning.ts:310` 의 `ls-tree -r -z --full-tree <expectedHead> -- <requested…>` 가 **워크트리에서 어느 최상위를 기준으로** 경로를 내는가. 워크트리는 git common dir 을 호스트와 공유하므로, 공유된 common dir 때문에 호스트 최상위 기준으로 경로가 나올 가능성을 배제해야 했다.

### 8.2 측정

같은 커밋 `2d0ccb5` 를 네 위치에서 조회했다.

| # | 실행 cwd | 요청 pathspec | 출력 경로 |
|---|---|---|---|
| 1 | 호스트 최상위 | `src/core/orchestrator/pinning.ts` | `src/core/orchestrator/pinning.ts` |
| 2 | **워크트리 최상위** | `src/core/orchestrator/pinning.ts` | `src/core/orchestrator/pinning.ts` |
| 3 | **워크트리 하위(`src/core`)** | `src/core/orchestrator/pinning.ts` | `src/core/orchestrator/pinning.ts` |
| 4 | 워크트리 하위(`src/core`) | `orchestrator/pinning.ts` | **(빈 결과)** |
| 5 | 워크트리 하위(`src/core`), `--full-tree` **없이** | `orchestrator/pinning.ts` | `orchestrator/pinning.ts` |

blob OID 는 1·2·3 이 전부 동일했다.

### 8.3 결론 — 선행조건 (c) 는 해소된다

**`--full-tree` 는 cwd 에 대해 양방향으로 독립이다.** 출력 경로만이 아니라 **요청 pathspec 의 해석 기준도** 최상위로 고정된다(4 가 빈 결과인 것이 그 증거이고, 5 는 플래그를 빼면 둘 다 cwd 상대로 되돌아감을 보여 그 원인이 `--full-tree` 임을 확정한다).

그리고 그 "최상위"는 **커밋 트리의 최상위**다 — 호스트든 워크트리든 같은 커밋을 조회하면 같은 경로가 나온다. 워크트리가 common dir 을 공유하는 것은 **객체 저장소를 공유한다는 뜻일 뿐**, 경로 기준을 호스트로 끌어가지 않는다.

> **판정: 워크트리라는 사실 자체는 `pinning.ts` 에 아무 영향이 없다.**

### 8.4 남는 제약 — 워크트리 고유가 아닌, 이미 있던 불변

git 이 내는 경로는 최상위 기준이고, `pinning.ts:421` 은 그것을 `path.join(root, …)` 로 디스크에 접합한다. 따라서 **`root` 가 git 최상위여야** 두 기준이 일치한다.

이것은 새 위험이 아니라 저장소에 이미 있는 **`root == git 최상위` 불변**이며, 워크트리는 이를 새로 깨지 않는다(워크트리 최상위 = 워크트리 디렉터리). 다만 이번 설계는 그 불변을 **호출자가 지정하는 값**으로 옮기므로, 게이트가 이를 명시적으로 강제해야 한다.

깨졌을 때의 거동도 확인했다: 기준이 어긋나면 `readWorktreeDocument` 의 `lstat`(`:425`)이 존재하지 않는 경로에서 던진다. **조용히 틀리지 않고 시끄럽게 실패한다.** 그러므로 이 제약은 fail-closed 로 이미 보호되고 있고, 게이트는 진단 품질을 위한 것이지 안전의 최후 보루가 아니다.

### 8.5 부수 발견 1 — 게이트 primitive 는 **이미 존재한다**

§4.2 의 "git common dir 이 같아야 한다" 는 검사를 새로 만들 필요가 없다. `src/core/orchestrator/run-lock.ts:81` `resolveGitCommonDir(cwd)` 가 정확히 그것이며, 이미 `orchestrate.ts` 네 곳에서 쓰인다.

그리고 그 함수는 이 조사가 발견한 **두 함정을 이미 처리한다**:

| 함정 | 실측 | `resolveGitCommonDir` 의 처리 |
|---|---|---|
| `rev-parse --git-common-dir` 의 **원시 출력이 위치마다 형태가 다르다** — 호스트에서는 상대(`.git`), 워크트리에서는 절대 | 호스트 `.git` / 워크트리 `C:/Work/git/_Snoworca/speckiwi/.git` | `--path-format=absolute` 로 양쪽을 절대로 통일 (`:85`) |
| Windows **대소문자** — git 은 realpath 표기를 돌려주므로 호출자가 넘긴 표기와 다를 수 있다 | 넘긴 `…/C--Work-git--…` 에 대해 git 이 `…/C--work-git--…` 반환 | 반환값에 `realpath` 적용 (`:94`) |

원시 출력을 그대로 비교하는 게이트를 새로 짰다면 **호스트에서 오탐으로 거부**했을 것이다. §10.2(한 개념에 진입점 하나)에 따라 **이 함수를 재사용한다.** 대조도 이미 증명돼 있다 — `test/core/orchestrator/run-lock.fr-node-102.test.ts:111`·`:132` 가 호스트와 linked worktree 의 common dir 이 같음을 단언한다.

### 8.6 부수 발견 2 — `pinning` 의 도달 범위는 좁다

`pinHandoff` 의 호출자는 `src/cli/commands/orchestrate.ts:1262` **한 곳뿐**이다. 즉 선행조건 (c) 가 걸린 표면은 C군 전체가 아니라 그 한 명령이다. (c) 가 해소됐으므로 이 사실은 이제 범위 축소용이 아니라, **회귀 테스트를 어디에 둘지**를 알려준다.

## 9. 구현 seam 실측 — §5 단계 2 의 전제가 틀렸다

§5 단계 2 는 *"`path.join(root, …)` 호출부를 단일 resolver 로 모은다 (오늘 `artifacts.ts` 만 6곳)"* 라고 적었다. **이 전제는 실측과 다르다.** 모을 것이 아니라 **이미 모여 있다.**

### 9.1 경로 해소는 이미 단일 함수다

`src/core/fs/safe-path.ts:4` `resolveInsideRoot(root, candidate)` 하나가 workflow 계층 전체의 경로 해소를 담당하며, `src/` 안에서 **14개 호출부**가 이것을 경유한다(`artifacts.ts` 3 · `jsonl.ts` 2 · `mutation.ts` 4 · `validate.ts` 1 · `add-requirement.ts` 2 등).

따라서 이 작업은 **경로 해소의 리팩터가 아니라 `root` 인자의 출처를 바꾸는 것**이다. 새 resolver 를 만들면 §10.2(같은 책임을 두 곳이 나눠 갖지 않는다) 위반이다.

**단계 2 를 다시 쓴다**: "resolver 를 만든다" → **"호출부에 흘러드는 `root` 를 per-call 로 선택하는 지점을 하나로 정한다."**

### 9.2 거부 지점도 이미 단일하다 — 그리고 그것이 이 작업의 유일한 수정 지점이다

`src/mcp/adapter.ts:45-70` `unsupportedWorkspaceInput()` 이 AC-3 의 fail-closed 거부를 구현하고, `:81` `registerTool` 이 **등록되는 모든 도구를 이 함수로 감싼다**. `createMcpServer`(`server.ts:28`)는 `createTestMcpServer` 를 감싸므로 **100개 도구 전부가 이 한 줄을 지난다.**

```ts
// adapter.ts:81
tools[name] = async (input) => unsupportedWorkspaceInput(input) ?? attachWorkspace(await handler(input));
```

즉 현행 거부는 **도구를 구분하지 않는다** — `root` 든 `workspaceRoot` 든 입력에 있기만 하면 거부한다(`:46`). 이번 변경의 형태가 여기서 정해진다:

> 거부를 없애는 것이 아니라 **도구 분류에 따라 조건부로** 만든다. A군 47개는 지금의 거부를 **그대로 유지**하고, B·C군만 통과시킨 뒤 해소된 root 를 핸들러에 넘긴다.

이것이 §2.1 의 "A군은 변경하지 않는다" 를 **코드로 강제**하는 방법이다 — 분류를 등록 시점 metadata 로 두면, 새 SRS 도구가 추가돼도 기본값이 거부 쪽이다(§10.1: 안전한 쪽이 기본값).

### 9.3 착수 전 반드시 해결할 함정 — `resolveInsideRoot` 가 root 를 **생성한다**

```ts
// safe-path.ts:5
await mkdir(root, { recursive: true });
```

`resolveInsideRoot` 는 첫 줄에서 root 를 **없으면 만든다.** 오늘은 root 가 MCP 기동 시 확정된 하나뿐이라 무해하지만, root 를 호출자가 지정하게 되면 **오타 난 절대 경로가 거부되는 대신 그 디렉터리를 만들어낸다.**

이것은 §8.4 에서 확인한 "시끄럽게 실패한다" 의 **예외**다. 여기서는 조용히 성공한다 — 그리고 조용한 성공이 진단보다 나쁘다.

> **설계 결론**: 게이트는 `resolveInsideRoot` **안**에 두면 안 된다(그 함수는 이미 root 를 신뢰한다). `workspaceRoot` 의 존재·git 최상위 여부·common dir 일치를 **`registerTool` 래퍼에서, 어떤 핸들러도 호출되기 전에** 판정해야 한다.

부수 확인: `resolveInsideRoot` 는 절대 경로 candidate 를 받으면 root 안에 있는지 검사해 밖이면 던진다(`:15-18`). 따라서 오늘 워크트리 절대 경로를 `path` 인자로 넣으면 `Path is outside project root` 로 **이미 거부된다** — 사용자가 겪는 마찰의 정확한 형태가 이것이다.

### 9.4 §5 작업 순서 갱신

| # | 원안 | 갱신 |
|---|---|---|
| 2 | `path.join` 을 단일 resolver 로 모음 | **삭제.** 이미 `resolveInsideRoot` 하나다 (§9.1) |
| 2′ | — | **신규**: `registerTool` 래퍼에 도구 분류 metadata 를 도입하고, per-call root 해소를 그 한 곳에서 수행 (§9.2) |
| 3 | 게이트 구현 | 위치를 못박는다 — **핸들러 호출 이전, `registerTool` 래퍼 안**. `resolveInsideRoot` 안에 두지 않는다 (§9.3). 대조는 `resolveGitCommonDir` 재사용 (§8.5) |

### 9.5 실제 수정 지점은 셋뿐이다

53개 도구 각각을 고치는 작업이 아니다. root 가 도구로 흘러드는 경로가 **군마다 하나씩**이기 때문이다.

| 군 | root 주입 지점 | 실측 |
|---|---|---|
| **C군 `orchestrate_*`** | `read-tools.ts:152` → `orchestrateArgv(binding, input, deps.root)` | `orchestrate.ts:303` 이 `[...(root ? ["--root", root] : []), "orchestrate", …]` 로 argv 를 만든다 |
| **B군 `workflow_*`** | **둘이다 — §9.7 정정** | `read-tools.ts:51` `projectRoot(deps)` 는 read 17개만. 나머지 9개는 `mutation-tools.ts:33` `root(deps, input)` |
| **게이트/거부** | `adapter.ts:81` `registerTool` 래퍼 | 100개 도구 전부가 통과 |

즉 변경은 **"`deps.root` 를 쓰던 두 지점이 per-call 로 해소된 root 를 쓰게 하고, 그 해소와 검증을 세 번째 지점에서 한 번 한다"** 이다.

**C군이 특히 싸다**: CLI 는 이미 `--root <path>` 전역 옵션으로 임의 root 를 받는다. MCP 가 그것을 `deps.root` 로 고정하고 있을 뿐이므로, C군은 **CLI 쪽 신규 능력이 필요 없다.**

### 9.6 이 조사가 뒤집은 §5 의 가정 요약

| §5 원안이 가정한 것 | 실측 |
|---|---|
| 선행조건 (c) 가 착수를 막는다 | **막지 않는다.** `--full-tree` 는 cwd 독립 (§8.3) |
| 흩어진 `path.join` 을 resolver 로 모아야 한다 | **이미 `resolveInsideRoot` 하나다** (§9.1) |
| 게이트를 새로 만들어야 한다 | **`resolveGitCommonDir` 가 이미 있고 함정 둘을 이미 처리한다** (§8.5) |
| 53개 도구에 인자를 노출해야 한다 | **주입 지점이 군당 하나, 총 셋이다** (§9.5) |
| 위험은 sibling repository 접근이다 | 그것도 맞으나, **더 조용한 위험은 `resolveInsideRoot` 의 `mkdir`** — 오타 경로를 거부하지 않고 만든다 (§9.3) |

## 10. `orchestrate_preflight` 예외 — 미결 해소

§2.3 과 §6 은 `orchestrate_preflight` 를 "설계 결정 필요" 로 남겼다. **결정할 것이 없다 — 이미 결정돼 있다.**

### 10.1 preflight 는 root 를 인자로 받는다, 이미

```
// orchestrate.ts:217 (MCP 바인딩)
{ tool: "orchestrate_preflight", path: ["preflight"], kind: "read",
  options: [o("--mcp-root", "mcpRoot", "string", true), o("--git-root", "gitRoot", "string", true)] }
```

둘 다 **required** 다. 그리고 CLI 정의(`orchestrate.ts:1040-1043`)에 그 이유가 요구 참조와 함께 박혀 있다:

> `@req IR-CLI-082 AC-6` — both roots are arguments; neither is derived from the process cwd, **because the CLI resolves cwd and the MCP server fixes its own, so an in-tool read is vacuous.**

`preflightRunRootForRole(request, probes)`(`worktree-topology.ts:154`)는 넘겨받은 두 root 를 판정할 뿐 어떤 경로도 해소하지 않는 **순수 판정 함수**다.

> **결론: `preflight` 에 `workspaceRoot` 를 추가하지 않는다.** 판정 대상을 지정하는 인자가 이미 둘 있는데 세 번째를 더하면 §10.1(한 개념에 진입점 하나)을 정면으로 어긴다. 예외로 "제외"하는 것이 아니라, **이미 이 작업이 하려는 일을 하고 있으므로 손댈 것이 없다.**

`--lane-plan <path>` 만은 여전히 root 상대로 해소되므로 B·C군의 일반 규칙을 따른다.

### 10.2 그리고 이것이 이 작업 전체의 가장 강한 근거다

`IR-CLI-082 AC-6` 의 논거를 그대로 옮기면 이렇게 된다:

> MCP 서버는 자기 root 를 고정한다. 따라서 도구가 root 를 **안에서 읽는 것은 공허하다**(vacuous). 그러므로 root 는 **인자여야 한다.**

이 저장소는 **이 논거를 이미 한 번 받아들여 요구로 승격했다.** `REL-MCP-004` AC-3 의 전면 금지와 `IR-CLI-082` AC-6 의 "root 는 인자여야 한다" 는 같은 저장소 안에서 서로 어긋나 있고, 그 모순이 실제 도구 하나(`preflight`)에서 이미 후자 쪽으로 해소돼 있다.

즉 이번 변경은 새 원칙의 도입이 아니라 **이미 채택된 원칙을 나머지 도구로 넓히는 것**이다. §7 의 판단(AC-3 철회)에 이 근거를 추가한다.

`REL-MCP-004` 를 supersede 하는 요구는 Trace Links 에 **`IR-CLI-082` 를 `related_to` 로** 걸어 이 선례를 끊기지 않게 할 것.

| `projectRoot(deps)` | `read-tools.ts:51` | workflow **read 17개** |
| `root(deps, input)` | `mutation-tools.ts:33` | workflow **mutation 9개** |

17 + 9 = 26 으로 런타임 수와 맞는다. 9번째(`workflow_record_reclassification`, `mutation-tools.ts:472`)는 도구 이름을 다음 줄에 두고 등록해 단순 grep 패턴에서 빠진다 — 이 조사가 처음에 8로 세고 넘어간 이유다.

### 9.7.3 그리고 이것이 단순한 누락이 아니라 함정인 이유

`root(deps, input)` 의 호출부는 **38곳**이고, 그중 workflow 는 9개뿐이다. 나머지에는 `update_status`(`:205`) · `supersede_requirement`(`:607`) 같은 **SRS 변이 도구가 들어 있다.**

```ts
// mutation-tools.ts:33 — 이미 input 을 받지만 명시적으로 버린다
async function root(deps: McpDependencies, input: Record<string, unknown>) {
  void input;
  return resolveProjectRoot(process.cwd(), deps.root);
}
```

시그니처가 이미 `input` 을 받고 `void input;` 으로 버리므로, **"여기서 `input.workspaceRoot` 를 존중하게 하면 된다"가 가장 자연스러운 수정으로 보인다.** 그것을 하면 **A군 SRS 변이 도구 전체가 같이 열린다** — 요구 ID 가 두 곳에서 발급되는, 다중 root 를 다섯 번 거절시킨 바로 그 실패다.

> **결론: 공유 헬퍼의 의미를 바꾸지 않는다.** 유효 root 는 §9.2 의 분류 게이트(`adapter.ts:81` `registerTool` 래퍼)가 도구별로 정하고, 헬퍼는 그 결과를 받기만 한다. `root(deps, input)` 의 `void input;` 은 **초대가 아니라 경고로 읽어야 한다.**

### 9.7.4 교훈

§9.5 의 오류는 "한 파일에서 패턴이 일관되게 보였다"에서 나왔다 — `read-tools.ts` 만 보고 `mutation-tools.ts` 를 열지 않았다. **군을 도구 이름의 접두사로 정의해 놓고 실측은 파일 단위로 했기 때문에**, 같은 접두사가 두 파일에 걸쳐 있다는 사실이 통째로 보이지 않았다.

다음 단계의 census 는 **파일이 아니라 등록된 도구 이름에서 출발**할 것 — 런타임에서 이름을 뽑고, 각 이름이 어디서 등록되는지 역추적한다. 그 순서로 했다면 이 오류는 발생할 수 없었다.

`IR-CLI-082` 의 Rationale 원문이 주석과 일치함을 확인했다 — *"the MCP server fixes `workspaceRoot` to its own process cwd, so the agent obtains the two values and the tool performs the judgment-free comparison."* 즉 **현행 우회책은 "에이전트가 root 를 대신 조달한다"** 이고, 이번 작업은 그 우회를 일반화하는 것이다.

## 11. 발견 — MCP 로는 lane 이 자신을 lane 이라고 말할 수 없다

§10 을 확인하다 별개의 갭을 실측했다. **이번 작업의 정중앙에 있으므로 범위에 넣어야 한다.**

### 11.1 실측

`orchestrate_preflight` 의 MCP 바인딩(`orchestrate.ts:217`)이 노출하는 옵션은 **`--mcp-root` 와 `--git-root` 둘뿐**이다.

CLI 는 셋을 더 갖는다(`orchestrate.ts:1045-1047`): `--role <host|lane>`(기본값 `"host"`) · `--lane-id` · `--lane-plan`. **바인딩에 없으므로 `orchestrateArgv` 는 이들을 argv 에 실을 수 없다**(`:304` 는 `binding.options` 만 순회한다).

### 11.2 귀결

MCP 로 호출된 preflight 는 **언제나 `--role host`** 로 판정된다. 그리고 `preflightRunRootForRole`(`worktree-topology.ts:157-162`)의 host 분기는:

```ts
if (isLinkedWorktree(request.gitRoot, probes)) {
  return { ok: false, reason: "host-root-is-a-linked-worktree", topology };
}
```

> **워크트리에서 MCP 로 preflight 를 부르면 lane 임을 선언할 방법이 없고, host 로 판정돼 거부된다.**

역할을 **선언**하게 만든 것은 의도된 설계다(`@req IR-CLI-093` — *"Inferring it from the roles would let any worktree of the repository satisfy 'this must be a lane'"*). 문제는 그 선언 수단이 **CLI 에만 있다**는 것이다. 워크트리 위상을 검증하라고 만든 게이트가 정작 MCP 표면에서는 워크트리를 표현하지 못한다.

### 11.3 범위 반영

이것은 §5 의 어느 단계에도 없던 항목이다. 그러나 사용자의 문제 진술 — *"대부분 워크트리에서 작업하는데 세션은 메인 세션"* — 에 정확히 걸리므로 **단계 5 에 포함한다**: `orchestrate_preflight` 바인딩에 `--role` · `--lane-id` · `--lane-plan` 을 노출한다.

§10 의 결론(preflight 에 `workspaceRoot` 를 추가하지 않는다)은 유지된다. **추가할 것은 root 가 아니라 역할 선언 수단이다.**

§4 의 잔여 항목 표에 이미 형제 갭이 하나 있다(`orchestrate_validate` 바인딩에 `--engine` 부재). 같은 원인 — **바인딩이 CLI 옵션의 부분집합인데 그 부분집합이 무엇을 잃는지 단언하는 것이 없다.** 개별 옵션을 하나씩 더하기 전에 이 부분집합 관계 자체를 검사 대상으로 삼을지 판단할 것.
