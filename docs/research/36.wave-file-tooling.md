## 0. 요약

1. 파일은 24 종 가까이 된다. 이 중 **도구가 내용을 만들어 쓰는 것**은 lanes lock, freeze lock, 라우팅 probe/lock, replay 기록, 검증 장부, 이슈 원장 정도다. **나머지는 에이전트가 손으로 만든 JSON/Markdown** 이거나, 도구를 거치더라도 **본문 전체를 에이전트가 조립해 넘기는** 형태다(§1).
2. 가장 큰 문제는 "도구를 거친다"는 문장과 실제 사이의 틈이다. `journal append` 는 줄 전체를 인라인 JSON 으로 받고 `writer` 하나만 찍는다. `card write` 는 에이전트가 계산한 `invariant_digest` 를 검사만 한다. `resume` 은 git 사실과 digest 를 에이전트가 모아 넘겨야 하며, 스킬이 적은 재개 명령은 실행하면 실패한다(§2 P2·P4·P5).
3. `kiwi-wave-master` 는 저널을 여전히 셸 `echo >>` 로 쓰고 도구 스탬프를 손으로 적는다. 이를 고치는 요구 `FR-FLOW-156` 은 `planned` 상태다(§2 P1).
4. 스케줄은 SDS 에 묶여 있다. `schedule waves` 는 `--sds` 가 필수이고 lock 의 드리프트 입력이 SDS digest 다. 다만 커널 `computeLanePlan` 은 `{waveId, writeSet}` 만 받으므로 **입력 경로 하나만 더하면 SDS 없이 돌 수 있다**(§2 P14, §4.4).
5. 권고: 새 저장 형식이나 단일 원장으로 갈아엎지 않는다. **"계산은 도구가 한다" 원칙으로 기존 동사를 보강**하고(선택지 A), 여기에 **wave 선언 파일 하나와 `schedule waves --waves`** 를 더한다(선택지 B 의 최소분). 4.1.0 첫 단계 후보는 §5 의 R1~R5 다.

## 2. 문제 지점과 근거

### P1. wave-master 저널은 셸로 쓰고, 도구 스탬프를 손으로 적는다
- 공유 계약의 emit 예시가 `echo '{… "writer":"speckiwi-orchestrate/{pkgVersion}" …}' >> "$WAVE_DIR/waves.jsonl"` 이다(`waves-event.md:217`, `:220`, `:223`). `writer` 는 "도구가 매 write 마다 찍는 스탬프"라고 정의되어 있는데(`waves-event.md:66`) 에이전트가 직접 적는다.
- 같은 공유 계약 묶음 안에서 문장이 어긋난다. `parallel-waves.md:37` 은 `kiwi/waves.jsonl` 을 "호스트만, 도구를 거쳐" 쓴다고 하고, `run-ledger.md:102` 는 "에이전트가 JSONL 을 손으로 이어붙이지 않는다"고 한다.
- SRS 가 이미 이 우회를 알고 있다. `FR-FLOW-155` Change Note: "The shipped `kiwi-wave-master` does not reach it - `_shared/kiwi/waves-event.md` section 5 tells it to emit with a shell redirect"(`docs/spec/60.workflow-release.srs.md` FR-FLOW-155 블록, `:10592` 부터). 고치는 요구 `FR-FLOW-156` 은 Status `planned`(`docs/spec/60.workflow-release.srs.md:10695`, 본문 `:10712`).
- 결과: wave-master run 의 줄은 append 시점 검증을 받지 않는다. 연구 22 도 같은 비대칭을 적었다 — 셸 경로는 검사 없이 파일을 만든다(`docs/next/2026-08-19.outstanding-work.md:66`).

### P2. `journal append` 는 줄 전체를 에이전트가 조립한다
- 입력은 `--payload <json>` 인라인 하나다(`orchestrate.ts:1514-1523`, 파싱 `:767-779`). 파일 입력 옵션이 없어 Windows 셸에서 큰 JSON 인용이 번거롭다(코드 읽기 기준, 실행 측정 안 함).
- 도구가 채우는 것은 `writer` 하나다(`orchestrate.ts:1030`). `ts` 는 채우지 않고, `schema_version` 은 "caller's `schema_version` as given and SHALL NOT fill a missing one"이 요구다(`docs/spec/50.nodejs-implementation.srs.md` FR-NODE-213 AC-6, `:14201` 부터).
- 필수 필드 집합은 런타임에서 읽히지 않는다: "nothing at runtime reads it, which is the point — it is the contract, as data"(`src/core/orchestrator/journal-schema.ts:389`, 집합 `:391-392`). 검증기가 강제하는 필수 필드는 `status` 하나라고 코드 주석이 말한다(`src/core/orchestrator/waves-journal.ts:43`, 검사 `src/core/orchestrator/waves-validate.ts:148-154`). 즉 `ts`·`summary`·`order`·`target` 이 빠진 줄도 append 된다(코드 읽기, 실행 확인 안 함).
- `verification` 객체 하나에 하위 필드가 11개다(`waves-event.md:104-117`). 예시 한 줄이 1,000자를 넘는다(`waves-event.md:217`).

### P3. intent 의 `inputs_digest` 는 양쪽 다 에이전트 값이다
- `inputs_digest` 는 "intent 시점의 그 verb 선언 입력들에 대한 sha256"이다(`waves-event.md:69`). verb 마다 무엇이 선언 입력인지는 계약에 없다.
- 재개의 digest 2 는 저널의 `inputs_digest` 를 `driftInputs.freshIntentDigests` 와 비교하는데(`src/core/orchestrator/resume.ts:300-308`), 그 비교값도 `--facts` 로 에이전트가 넘긴다(`resume.ts:83-101`, `orchestrate.ts:1316-1323`).
- 스킬 스스로 같은 꼴을 경계한다 — "한쪽을 도구가 스스로 채우게 두면 대조의 두 변이 한 출처에서 나오고 … 영원히 발화하지 못한다"(`SKILL.md:148`). digest 2 는 두 변이 모두 에이전트에서 나온다.

### P4. 재개 카드의 digest 를 에이전트가 계산해야 한다
- `invariant_digest` 는 도구 내부의 `canonicalJson` 위 sha256 이다(`src/core/orchestrator/resume-card.ts:105-107`). `card write` 는 계산하지 않고 일치만 검사해 `invariant-digest-mismatch` 로 거절한다(`resume-card.ts:162`, `:203-207`).
- 카드 `frozen` 안의 lock 포인터도 `…@sha256:…` 형식으로 에이전트가 적는다(`run-ledger.md:43-47`).
- 저장소 안에 반대 원칙의 선례가 있다: 검증 장부는 "해시는 도구가 문서에서 직접 계산한다 — 에이전트가 적어 낸 해시는 증거가 아니다"(`skills/claude/_shared/kiwi/verify-loop.md:176`).

### P5. 스킬이 적은 재개 명령은 실행하면 실패한다 (실행 확인)
- 스킬의 고정 재개 절차 3단계는 `speckiwi orchestrate resume --json` 이다(`SKILL.md:137`).
- 코드는 `--run-id` 를 요구하고(`orchestrate.ts:1262`, `requireOption` `:840-843`), `--facts` 가 없으면 `"--facts must supply both gitFacts and driftInputs; the tool never invents them"` 으로 실패한다(`orchestrate.ts:1316-1323`).
- 2026-10-20 실행: `node bin/speckiwi orchestrate resume --json` → `{"ok":false,"error":"--run-id is required"}`. `--run-id x` 를 주면 카드 부재로 `resume-card-missing-or-invalid` 다.
- `--facts` 의 `gitFacts` 는 브랜치·조상 여부·워크트리·잠김 여부·heartbeat mtime·통합 head·host status 경로·trailer 커밋 목록이다(`resume.ts:31-50`). `driftInputs` 는 lock digest, lock 이 기록한 입력, SDS digest 재계산값, intent digest, route digest 다(`resume.ts:83-101`). 컴팩션 직후의 에이전트가 이것을 전부 손으로 모아야 재개할 수 있다.
- wave-master 는 카드가 없어 같은 사실을 저널 워커 줄에서 직접 읽는다(`parallel-waves.md:196`) — 읽기 동사가 없다.

### P6. `--depends` 와 `existing-paths.json` 을 stage 마다 손으로 다시 만든다
- `--depends` 는 이미 병합된 의존을 빼되 키는 남겨야 하고, 키를 빠뜨리면 "도구가 앞 wave 전부에 의존한다고 보아 까닭 없이 직렬로 돈다"(`parallel-waves.md:66`). 잘못 만들어도 오류가 아니라 조용한 직렬화다.
- 의존 선언의 원본은 분해 결과(`wave-decomposition.md:38-40`)인데, 이것이 기계가 읽는 파일로 남지 않는다. `waves.lock.json` 의 필수 키는 `waves`·`wave_count` 뿐이라(`freeze.ts:178`) `depends_on` 이 그 안에 있다는 보장도 없다.
- `existing-paths.json` 은 `git ls-files` 를 JSON 배열로 옮긴 것인데(`parallel-waves.md:66`) 도구가 같은 저장소에서 직접 얻을 수 있는 값이다.

### P7. 경로 규약이 산문에 있고, 도구 기본값과 다르다
- `schedule waves --out` 기본값은 `waves/lanes.lock.json`(`orchestrate.ts:1624`), `schedule show --lock` 도 같다(`:1689`). 계약은 stage 경로 하나만 허용한다 — "lock 경로는 이 한 가지 철자뿐이다"(`parallel-waves.md:66`).
- `freeze` 기본 `--out` 은 `kiwi/orchestrator/{run_id}/{target}.lock.json` 이라 같은 target 을 두 번 동결하면 덮어쓴다. 스킬은 "`--out` 은 target 마다 준다"로 막는다(`SKILL.md:326`, 코드 `orchestrate.ts:1584`).
- 이슈 원장 기본값은 run 과 wave 성분이 없는 `kiwi/orchestrator/issues.json`(`orchestrate.ts:1746`, `:1841`)인데, 스킬의 이슈 산출물은 wave 범위의 `waves/wave-{n}/issues.md` 와 `issues.lock.json` 이다(`SKILL.md:796`).
- 도구가 `run_id`·`stage`·`wave` 로 경로를 유도하지 않으므로 경로 정확성은 에이전트 기억에 달렸다.

### P8. 같은 사실을 두 곳이 나눠 갖는다
- 이슈: 손 Markdown `issues.md` 와 도구 원장 JSON 이 따로 있다(`SKILL.md:796-798`). 연구 23 은 이를 "양면 SSOT" 선례로 들었지만(`docs/research/23.graph-engineering-fit-audit.md:290`) 두 면을 모두 손과 도구가 따로 쓰면 한쪽만 고쳐진다.
- wave 상태: orchestrator 는 카드 `done[]`/`open[]` 과 저널 둘에, wave-master 는 저널에만 둔다(`parallel-waves.md:196`). 카드는 파생물이라고 계약이 말하지만(`run-ledger.md:83`) 그 파생을 도구가 하지 않는다(P4).

### P9. MCP 검증기는 wave-master 저널을 볼 수 없다
- `orchestrate_validate` 바인딩 설명: "This binding declares no engine, so a journal another engine wrote is read as zero lines and answers clean"(`orchestrate.ts:283`). CLI 는 `--engine` 이 있다(`orchestrate.ts:1935`). 스킬이 이 차이를 산문으로 우회한다(`SKILL.md:1189`).
- 고치는 요구 `FR-NODE-199` 는 `planned`(`docs/spec/50.nodejs-implementation.srs.md:13151`).

### P10. 읽고 검사하는 도구가 없는 손 파일
- `constraints.json`·`convergence-registry.json`·`design-baseline.json`·`dispatch.json`·`manifest.json` 은 `src/**` 에서 읽는 코드가 없다(grep, 2026-10-20). `existing-paths.json` 만 `schedule waves` 가 읽는다(`orchestrate.ts:1636`).
- 검사 커널이 있어도 부르는 곳이 없는 경우가 기록되어 있다: `evaluateSerialUnitGate`·`evaluatePartitionReviewGate` 는 "have no production caller"(`docs/spec/60.workflow-release.srs.md:7202`). `manifest.json` 의 `intentionally_empty` 를 판정할 `unit-gate.ts` 가 그 커널이다.
- 연구 28 은 "19종의 미호명 도구가 담당했어야 할 판정이 손으로 쓴 아티팩트로 대체"된다고 적었다(`docs/research/28.skills-mcp-end-to-end-audit.md:558`, 목록 `:458`). 그 뒤 일부는 스킬에 호명되었으나(예: `SKILL.md:316`, `:324`, `:798`) 손 파일을 검사하는 동사는 여전히 없다.

### P11. 이미 겪은 사고 (해결됨, 원인 부류는 남음)
- `waves.jsonl` 동시 append 손실: "재현됨 3/3 … `written:true` 로 성공을 보고하면서 동시 append 를 삼키고"(`docs/research/22.workflow-jsonl-durability.md:19`, `:69`; `docs/next/2026-08-19.outstanding-work.md:69`). 지금은 잠금 + O_APPEND 로 고쳐졌다(`orchestrate.ts:1063-1072`, FR-NODE-196 `docs/spec/50.nodejs-implementation.srs.md:12881`).
- append 검증 뷰의 engine 고정: wave-master 줄이면 후보 뷰가 비어 아무것도 거절하지 않았다(`docs/research/28.skills-mcp-end-to-end-audit.md` §3.6 정정 블록). 지금은 줄의 engine 을 읽는다(`orchestrate.ts:1031-1035`, FR-FLOW-155).
- 두 저널의 정책이 반대: `pipeline.jsonl` 은 경고 하나로 막히고 `waves.jsonl` 은 깨진 줄이 있어도 append 가 통과한다(`docs/research/22.workflow-jsonl-durability.md:168-176`). 남은 부류의 공통점은 **검사가 쓰기 경로에 있지 않거나, 쓰기 경로가 검사를 우회한다**는 것이다.

### P12. 상태가 두 집에 산다
- `kiwi/waves.jsonl` 과 `kiwi/orchestrator/` 는 gitignore 다(`.gitignore:12-13`). stage lock·freeze·이슈 md 는 `docs/research/{work}/` 아래 커밋된다(`parallel-waves.md:115`). 연구 23 이 이 구분을 실측했다(`docs/research/23.graph-engineering-fit-audit.md:272-284`). 다른 기계에서 재개하면 저널과 카드가 없다. 이번 연구 범위 밖이지만 단일 원장 선택지(§4.3)를 평가할 때 걸린다.

### P13. 스케줄이 SDS 에 묶여 있다
- `schedule waves` 는 `--sds` 가 필수다(`orchestrate.ts:1618`). 각 SDS 는 lite SDS 이름 규칙과 `sds check` 를 통과해야 한다(`orchestrate.ts:884-892`). 쓰기 집합은 SDS 의 Files ∪ Test Plan 테스트 파일이다(`src/core/sds/lite-sds.ts:623`, `parallel-waves.md:58`).
- lock 의 드리프트 입력이 `sds_digests` 다(`freeze.ts` `LANE_PLAN_INPUT_PINS`, FR-NODE-213 AC-2). 워커 판정 PW-8 도 "변경 경로 ⊆ SDS 쓰기 집합"이다(`parallel-waves.md:155`).
- 연구 35 는 SDS 쓰기 집합이 병렬을 직렬로 바꿨고 SDS 없는 병렬이 가장 빨랐다고 보고했다(`docs/research/35.sds-brownfield-loose-srs-structure-parallel.md:27`, `:154-158`). 권고 1·4 가 kiwi-sds 선택화와 쓰기 집합 통과 조건 재설계다(`:171-174`). 이 연구 자체도 미검증 노트다.
- 반면 커널은 SDS 를 모른다: `LanePlanInput` 은 `waves`(`{waveId, writeSet}`), `dependencies`, `laneCap` 셋이다(`src/core/orchestrator/lane-plan.ts:17-22`). SDS 를 읽는 곳은 CLI 로더 `loadScheduledWaves` 하나다(`orchestrate.ts:937-958`). lane 역할 검사도 lock 의 `{laneId → writeSet}` 만 읽는다(FR-NODE-213 AC-4).

## 4. 설계 선택지

### 4.1 공통 원칙 (세 선택지 모두에 적용)

1. **계산은 도구가 한다.** 해시·스탬프·시각·경로는 도구가 만든다. 에이전트가 낸 값은 받지 않거나 무시한다(선례 `verify-loop.md:176`, `round record`).
2. **경로는 도구가 유도한다.** `--run-id`·`--stage`·`--wave` 와 run contract 의 `work_root` 로 경로를 정하고, 명시 `--out` 은 그 값과 다를 때 거절한다. 기본값 하나가 계약 경로와 일치해야 한다(§10.1 "기본값만으로 올바르게").
3. **기계 상태는 JSON/JSONL 하나, Markdown 은 도구가 만든 보기이거나 digest 로 고정된 산문뿐.** 손으로 유지하는 두 면(md + json)을 두지 않는다.
4. **새 동사는 기존 `orchestrate` 트리 아래에 둔다.** `orchestrate wave` 컨테이너가 이미 있다(`orchestrate.ts:1837`). 최상위 `speckiwi wave` 를 새로 만들면 같은 개념의 진입점이 둘이 된다.

### 4.2 선택지 A — 기존 동사 보강 ("도구가 계산한다")

내용:
- `journal append` 가 `ts` 와 `schema_version`(현행 값)을 채우고, 필수 필드 집합을 검사하며, `--payload-file` 을 받는다. `schema_version` 미기입 금지(FR-NODE-213 AC-6)는 **줄을 그대로 쓰는 경로**에 대한 규칙이므로, 도구가 조립하는 동사(아래 B)와 구분해야 한다.
- wave-master 가 `journal append` 를 쓴다(이미 `FR-FLOW-156` planned).
- `card write` 가 `invariant_digest`·`written_at` 을 계산한다. payload 의 값은 거절한다.
- `resume` 이 `--facts` 가 없으면 git 사실과 drift 입력을 스스로 모은다. `--run-id` 가 없으면 계약대로 "자기 engine 의 가장 최근 미완료 run"을 고른다(`waves-event.md:194`).
- `schedule waves` 가 `--existing-paths` 가 없으면 dispatch base 에서 `git ls-files` 를 직접 읽는다.
- MCP `orchestrate_validate` 에 engine(이미 `FR-NODE-199` planned).

| 항목 | 평가 |
|---|---|
| 비용 | 작다. 요구 5~6개, 대부분 CLI 한 곳과 계약 문장 수정. resume 사실 수집이 가장 크다(git 호출 다수) |
| 위험 | 낮음~중간. resume 이 git 을 직접 읽으면 "커널은 시계·git 을 모른다"는 현 구조(`resume.ts:35-38` 주석)를 CLI 층에서 지켜야 한다 — 수집은 CLI, 판정은 커널 |
| 이전 영향 | 기존 파일 형식 그대로. 스킬 문장 몇 곳 수정. 옛 run 은 그대로 읽힌다 |
| 남는 문제 | 손 JSON(제약·레지스트리·기준선·dispatch·manifest)과 SDS 의존(P13)은 그대로 |

### 4.3 선택지 B — wave 선언 파일 + 타입 동사 (A 를 포함)

A 에 더해:
- **wave 선언 파일** `{root}waves/waves.json` 하나를 기계 원본으로 둔다. 항목은 `{ wave, order, depends_on[], files[], sds[]?, existing_modules[]?, scope? }`. 분해 결과가 처음으로 기계가 읽는 파일이 된다. `freeze waves` 는 이 파일을 body 로 받는다(필수 키에 항목 스키마 검사 추가).
- `orchestrate wave declare --file <path>`: 스키마 검사, 순서·의존 사이클 검사, wave 경계 불변(`kiwi-wave-master/SKILL.md:28` §0.5 — 기존 wave 의 순서·의존 변경 거절, 추가만 허용)을 도구가 판정한다.
- `orchestrate wave status --run-id [--engine]`: `computeRunProgress` 와 `latestPerWave` 를 표로 돌려주는 읽기 동사. wave-master 의 손 재개 읽기(`parallel-waves.md:196`)를 대신한다.
- `orchestrate wave record --wave <n> --status <s> --phase <p> [--sds-id] [--diff-window base..head] [--summary]`: wave 상태 줄을 도구가 조립한다(`round record` 와 같은 꼴). 큰 `verification` 객체는 이미 `round record` 몫이다.
- `schedule waves --waves <waves.json> --stage <s>`: 준비 집합·병합 차감 의존·쓰기 집합을 선언 파일과 저널에서 도구가 계산한다. `--depends` 손 작성(P6)이 사라진다. lock 의 드리프트 입력은 선언 파일의 digest 와 (있으면) SDS digest.
- 손 JSON 다섯(dispatch·manifest·제약·레지스트리·기준선)은 같은 패턴의 `--file` 검사 동사(`orchestrate check <kind> <path>`)로 묶는다 — 쓰기는 에이전트가 해도 형태는 도구가 판정한다. 쓰기 동사까지 만드는 것은 수요가 확인된 뒤.

| 항목 | 평가 |
|---|---|
| 비용 | 중간. A + 요구 4~6개. 스키마 정의, 스케줄 입력 경로, 상태 읽기/쓰기 동사, 스킬 두 개와 공유 계약 4개 수정 |
| 위험 | 중간. 선언 파일과 SDS 쓰기 집합이 함께 있을 때 어느 쪽이 이기는지 정해야 한다(§4.5). wave 경계 불변을 도구가 강제하면 지금은 산문으로만 허용되는 예외(커버리지 갭 wave 추가)를 정확히 표현해야 한다 |
| 이전 영향 | 새 run 만 선언 파일을 쓴다. `--sds`/`--depends` 경로는 한 릴리스 동안 남기고 `--waves` 와 동시 사용은 파싱 시점에 거절(진입점 하나 원칙의 과도기 처리) |
| 얻는 것 | 의존·쓰기 범위의 단일 원본, SDS 없는 스케줄, wave-master 재개 읽기 동사 |

### 4.4 선택지 C — run 원장 하나로 통합

- 저널·카드·lock·이슈 원장·매니페스트를 run 당 한 JSONL(또는 한 디렉터리 + 한 색인)로 합치고, lock 과 카드를 원장에서 파생한다.

| 항목 | 평가 |
|---|---|
| 비용 | 크다. 저장 커널, resume, freeze, 이슈, 검증기를 다시 쓰고 스킬 본문(`kiwi-orchestrator` 1,256줄, `kiwi-wave-master` 590줄, 공유 계약 13개)을 고친다 |
| 위험 | 높다. 현재 동결은 **커밋된 문서를 git blob 으로 고정**하는 설계다(`parallel-waves.md:115`, `orchestrate.ts:1573-1576`). gitignore 된 원장(P12)으로 합치면 이 증거 종류(`git-ancestor`·`digest` 우선, `run-ledger.md:166-180`)가 약해진다. 저널은 "잘려 나가기 가장 쉬운 산출물"이라는 계약 전제(`waves-event.md:97`)와도 충돌한다 |
| 이전 영향 | 진행 중 run 은 이어갈 수 없다. 4.0.0 이 이미 "run-predates-4.0.0" 거절을 한 번 썼다(`orchestrate.ts:1288-1289`) — 두 번째 단절 |
| 판단 | 지금은 권하지 않는다. 파일이 많은 것 자체보다 **각 파일을 검사하는 동사가 없는 것**이 문제다 |

### 4.5 SDS 없이 wave 쓰기 범위를 선언하는 방법

- 선언 위치: wave 선언 항목의 `files[]`. 분해 단계에서 호스트가 `existing_modules`(`wave-decomposition.md:42`)와 예상 신규 경로로 채운다. 단위는 저장소 상대 경로와 디렉터리 접두(`src/core/x/`)로 시작한다. glob 은 레지스트리 경로 문법(`run-ledger.md:253`)을 재사용할 수 있으나 겹침 판정이 집합 교집합에서 패턴 교집합으로 바뀌므로 첫 단계에서는 뺀다.
- 기본값(안전한 쪽): `files` 가 없거나 빈 wave 는 **다른 모든 wave 와 겹친다고 보고 혼자 stage 를 갖는다**. 도구는 이를 경고 진단으로 알린다. 병렬은 선언한 wave 만 얻는다. 근거: §10.1 "안전한 쪽이 기본값".
- SDS 가 있을 때: 쓰기 집합 = `files` ∪ SDS 쓰기 집합. SDS 는 범위를 좁히지 않고 넓히기만 한다. lock 은 선언 digest 와 SDS digest 를 둘 다 기록하고, `LANE_PLAN_INPUT_PINS` 가 `LanePlanInput` 키에 묶여 있으므로(`freeze.ts`, FR-NODE-138 AC-6) 입력 추가가 기록 필드 추가를 컴파일 시점에 강제한다.
- 워커 판정 PW-8 의 "변경 경로 ⊆ SDS 쓰기 집합"은 "⊆ lock 의 그 lane `writeSet`"으로 바뀐다. 문장만 바뀌고 lock 필드는 그대로다.
- 연구 35 의 "SDS 없이 병렬 + 병합 해소 hop"(`docs/research/35…:174`)은 겹침을 허용하는 별도 정책이다. 이 문서는 그것을 기본값으로 두지 않는다 — 표본 2쌍이고 두 wave 의 동작이 독립인 경우만 쟀다(`:186`). 필요하면 나중에 `--overlap merge` 같은 명시 선택으로 더한다.
- 공유 등록부 같은 핫 파일은 기존 수렴 레지스트리의 `orchestrator-only` 로 `files` 에서 빼는 장치를 그대로 쓴다(`run-ledger.md:242-251`). 그러려면 레지스트리를 읽는 도구가 필요하다(P10) — B 의 검사 동사가 그 첫걸음이다.

## 5. 권고와 4.1.0 최소 첫 단계

**권고**: 선택지 A 전부 + 선택지 B 의 최소분(선언 파일·`schedule waves --waves`·`wave status`). C 는 보류.

순서는 "SDS opt-in 이 들어오면 바로 깨지는 것"과 "지금 실행하면 실패하는 것"을 먼저 둔다.

아래는 요구로 옮길 수 있게 적은 **후보 문장**이다. 요구를 만들지 않았다. ID 는 정하지 않았다.

- **R1 (SDS 없는 스케줄)** — `orchestrate schedule waves` SHALL accept a wave declaration file whose entries carry `wave`, `depends_on[]` and `files[]`, and SHALL plan stages without any SDS file when given one. A wave with no declared files SHALL be placed alone in its stage and reported by a warning diagnostic. When SDS files are named for a wave, its write set SHALL be the union of `files` and the SDS write set. The lanes lock SHALL record the declaration's digest so that resume detects a changed declaration as `lane-plan-drift`. `--waves` together with `--sds` or `--depends` SHALL be refused at parse time.
  - 검증: SDS 0개로 두 wave 를 한 stage 에 넣는 테스트, `files` 없는 wave 직렬화 테스트, 선언 변경 시 드리프트 테스트.
- **R2 (재개 명령이 그대로 돈다)** — `orchestrate resume` without `--facts` SHALL collect the git facts and drift inputs it needs from the repository itself, and without `--run-id` SHALL select the most recent incomplete run written by its engine. The command the skill's resume procedure names SHALL exit 0 on a resumable run.
  - 검증: `SKILL.md:137` 의 명령 그대로 실행하는 통합 테스트(지금은 red — §2 P5 실행 결과).
- **R3 (digest 는 도구가 계산)** — `orchestrate card write` SHALL compute `invariant_digest` and `written_at` itself and SHALL refuse a payload that supplies either. `journal append` SHALL fill `ts`, SHALL accept the line from a file as well as inline, and SHALL refuse a line missing a field the contract declares required.
  - 주의: FR-NODE-213 AC-6("SHALL NOT fill a missing `schema_version`")과 부딪히지 않게 `schema_version` 은 채우지 않는다. 이 AC 를 바꿀지는 별도 결정이다.
- **R4 (wave-master 도 도구로 쓴다)** — 이미 `FR-FLOW-156`(planned)·`FR-NODE-199`(planned) 이 덮는다. 4.1.0 에 넣을지만 정하면 된다. `waves-event.md` §5 의 `echo` 예시를 지우고 `writer` 를 손으로 적는 문장을 없앤다.
- **R5 (wave 상태 읽기)** — `orchestrate wave status --run-id <id> [--engine <e>]` and its MCP twin SHALL report, for every wave of the run, the latest status, phase, `sds_id`, stage and lane computed by the same predicate resume uses, and whether the run is complete or needs final verification. It writes nothing.
  - 검증: round record 줄과 program-counter 줄이 상태를 바꾸지 않는다는 기존 술어(FR-NODE-159, FR-NODE-168)를 이 동사로도 확인.

4.1.0 범위 판단: R1·R2 가 필수(SDS opt-in 과 실행 실패), R3·R5 가 같은 릴리스에 들어가면 좋고, R4 는 이미 요구가 있으니 일정만 정한다. 손 JSON 검사 동사(`orchestrate check <kind>`)와 Markdown 보기 생성은 4.1.x 이후.

스킬 쪽 변경(요구 승격 뒤): `parallel-waves.md` §3 의 스케줄 명령과 `--depends` 문단, §5 PW-8 의 쓰기 집합 문장, `waves-event.md` §5, `run-ledger.md` §2 의 카드 쓰기, `kiwi-orchestrator/SKILL.md` §1 의 재개 명령. 미러는 `speckiwi skills mirror --write` 로 다시 만든다.
