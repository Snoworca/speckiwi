# 15. 오케스트레이터 run-root 와 다중 모듈 배치 연구

작성 2026-08-07. 3축 병렬 조사(현행 계약 실측 / root 결정 경로·소비자 배치 / 설계 대안)의 교차 대조.
조사 축의 원본은 세션 스크래치패드에 있고, 본 문서가 정본이다.

조사 제약: 세 축 모두 저장소 **읽기 전용**으로 묶었다 — 다른 작업 스트림이 `src/core/workflow/*`,
`src/core/lock/exclusive-lock.ts`, `src/mcp/*` 에 미커밋 변경을 들고 있었기 때문이다. 축 C 에는
조사자의 사전 판단을 전달하지 않고 "현행 유지"를 1번 후보로 넣어 자기 최선안에 대한 반론까지 요구했다.

---

## 0. 요약 — 질문이 바뀌었다

들어갈 때의 질문은 "다중 모듈 저장소에서 `orchestrate preflight` 의 등가 규칙을 완화할 것인가"였다.
조사 결과 그 질문은 잘못 놓여 있다. 확정된 사실 셋이 질문을 다시 세운다.

1. **술어를 완화해도 다중 모듈에서 오케스트레이터는 돌지 않는다.** `pinHandoff` 가
   `git ls-tree --full-tree` 의 저장소 최상위 기준 경로를 run root 에 이어 붙이므로, run root 가
   중첩되면 `freeze` 가 술어와 무관하게 깨진다(§6).
2. **`SRS root == git root` 는 speckiwi 전체의 미명시 불변인데, 강제하는 곳이 이 게이트 하나뿐이다.**
   나머지 11개 표면은 하위 root 에서 조용히 틀린 일을 한다(§4). 게이트만 열면 시끄러운 거부가
   다섯 몸통에 걸친 조용한 손상으로 바뀐다.
3. **현행 유지도 안전지대가 아니다.** 게이트는 같은 값을 두 번 넘기면 통과한다 — 테스트가 그
   동작을 고정하고 있다(§3.3). 영구히 빨간 게이트는 위조가 쉽고, 결과는 split-brain 에
   **거짓 증명**이 얹힌 상태다.

따라서 개선의 방향은 "게이트를 여는 것"이 아니라 **미명시 불변을 명시적·위조 불가능하게 만들고,
어긋난 배치를 조용히가 아니라 크게 알리는 것**이다. 다중 모듈 지원은 그와 분리된 별개의 결정이며,
이 저장소에서 이미 네 번 거절된 사안이다(§5.3).

## 1. 게이트가 실제로 하는 일

`src/core/orchestrator/preflight.ts` 는 65줄, import 0. `normaliseRoot(a, b, probe)` 가 네 규칙을
누적 적용하며 처음으로 `===` 가 성립하는 지점을 돌려준다.

| 순서 | 규칙 | 내용 |
|---|---|---|
| 1 | `separators` | 구분자 정규화 |
| 2 | `trailing-separator` | 후행 구분자 제거 |
| 3 | `windows-case` | Windows 대소문자 |
| 4 | `realpath` | 앞 셋이 못 붙였을 때만 실경로 해소 |

포함(containment) 개념은 존재하지 않는다. 순수 문자열 등가다.
CLI(`src/cli/commands/orchestrate.ts:729-747`)는 불일치 시 exit 2 와
`{ok:false, gate:"run-root-preflight-mismatch", violations:[comparison]}` 로 거부한다.

`--mcp-root` 와 `--git-root` 는 **둘 다 필수이며 기본값이 없다**. 스킬(§1, `SKILL.md:145`)이 그 이유를
적어 두었다: 한쪽을 도구가 스스로 채우면 대조의 두 변이 한 출처에서 나와 P.1 이 잡으려는 불일치가
영원히 발화하지 못한다. 이 논거는 옳고, 뒤의 어떤 제안도 이것을 뒤집지 않는다.

## 3. 게이트가 막은 사건, 그리고 막지 못하는 것

### 3.1 실제 사건은 형제 저장소였다

규칙은 측정된 split-brain 에서 왔다(`docs/research/12.kiwi-wave-master-worktree-isolation-research.md:44-72`,
커밋 `b79102e`): 한 세션에서 두 **형제** 저장소가 서로 다른 Active Target 을 들고 갈라졌다.
포함 술어로 바꿔도 형제 사고는 그대로 잡힌다. 즉 이 사건은 등가를 요구하지 않는다.

같은 문서 `:127` 이 하나를 더 남겼다: **SRS mutation lock 은 root 스코프라 서로를 보지 못한다.**
git common dir 에 놓이는 run lock 과 비대칭이다. 이것은 형제·중첩 양쪽에 해당하는 별개 위험이다.

`:201` 의 거절된 브랜치가 전제로 삼았던 것이 바로 **포함**이었다는 점도 기록해 둔다.

### 3.2 게이트의 진짜 역사적 실패는 다른 데 있었다

`src/core/health/doctor.ts:440-447` 이 기록한다 — 설치된 스킬 사본이 404줄 낡아 **게이트 자체가
빠져 있었던** 사례. 규칙의 강도가 아니라 배포 정합이 실패한 것이다.

### 3.3 현행 게이트는 위조 가능하다 (직접 확인)

`test/cli/orchestrate-surface.ir-cli-082.test.ts:216-234` 가 고정하는 동작:

```
--mcp-root <one> --git-root <other>  →  exit 2, gate=run-root-preflight-mismatch
--mcp-root <one> --git-root <one>    →  exit 0, ok=true
```

두 인자에 같은 값을 넣으면 통과한다. 다중 모듈 사용자가 P.1 을 통과시키려면 모듈 경로를 양쪽에
넣기만 하면 되고, 그 순간 게이트는 **검사가 아니라 통과 증명**이 된다. 그래서 O1(현행 유지)은
"아무것도 안 하니 안전"이 아니다. 지금은 거부가 영구적이라 위조 유인이 최대인 상태다.

## 4. 미명시 불변과 그것을 어기는 11개 표면

하위 디렉토리 SRS root 는 **도달 가능하지만 지원되지 않는다.**

- `src/core/project-root.ts:21` 은 `docs/spec/00.index.md` **또는** `.git` 을 root 신호로 받고
  둘 사이 우선순위가 없다.
- `init` 은 cwd 에 고정하며 상위 탐색을 하지 않는다(`src/cli/commands/mutations.ts:103`).
- 그러나 `README.md:43, :87` 은 root 가 곧 Git 저장소라고 말하고, `upgrade` 의 가드 주석은
  하위 디렉토리 스캐폴딩을 실수라고 부르며(`mutations.ts:142-144`),
  `docs/spec/00.index.md:107` 은 "multi-root runtime hosting" 을 범위 밖으로 명시한다.

즉 `SRS root == git root` 는 **문서화되지 않은 불변**이고, 이를 검사하는 곳은
`orchestrate preflight` 하나뿐이다.

하위 root 에서 SRS 읽기·mutation·repair 는 정확히 동작한다. 조용히 틀리는 것은 다음이다.

| # | 표면 | 증상 |
|---|---|---|
| B1 | 파이프라인 저널 | 스킬은 `{git_root}/kiwi/pipeline.jsonl` 을 고정(`skills/claude/_shared/kiwi/pipeline-event.md:11-21`), 도구는 `<root>/kiwi/` 로 해소(`src/core/workflow/artifacts.ts:78, :346`) → **실제로 갈라진 두 파일** |
| B2 | `.kiwi/sessions/*/pm.lock` | root 별로 쪼개져 두 run 이 동시에 "그" 락을 보유 |
| B4 | pre-commit hook | 하위 root 에는 설치되지 않음(`src/core/bootstrap/init-project.ts:195-198`) |
| B5/B7 | `.claude` / `.codex` / `.mcp.json` / skills | 하위 디렉토리에 설치되어 무력 상태 |
| B8 | doctor | `.git` 관련 검사가 **0건** — 어긋난 배치를 진단하지 못함 |
| B10 | MCP 세션 | 한 세션은 다섯 몸통 중 하나만 볼 수 있음 |
| B11 | validate | git 최상위에서 0 errors 로 보고되지만 저장소 전체는 2,319건 보유 |

게이트만 여는 변경은 이 11개를 그대로 둔 채 오케스트레이터를 그 위로 올려보내는 일이다.

## 6. 술어와 무관한 하드 블로커

`src/core/orchestrator/pinning.ts:302-312` 의 `readTree` 는

```
git ls-tree -r -z --full-tree <head> -- <paths>
```

를 쓴다. `--full-tree` 출력은 **저장소 최상위 기준 경로**다. 그것을 run root 에 이어 붙이므로
(`pinning.ts:511` 부근), run root 가 저장소 최상위가 아니면 핸드오프 pinning 이 어긋난다.
등가를 포함으로 바꾸든 두 root 로 쪼개든, **이것을 함께 고치지 않으면 다중 모듈에서 `freeze` 는
돌지 않는다.** 축 C 의 대안 비교에는 이 항목이 없었다 — 축 A 가 뒤늦게 찾았고, 그래서 어떤
"게이트만 완화" 안도 성립하지 않는다.

## 7. 구조 — 이미 두 root 를 모델링하고 있다

세 축이 독립적으로 같은 지점을 짚었다.

- **재개 카드에 두 필드가 이미 있다**: `src/core/orchestrator/resume-card.ts:49`
  `run_root: { git_toplevel: string; mcp_workspace_root: string }`. `computeInvariantDigest`
  (`:92-107`)가 이미 덮고 `run-invariant-drift` 게이트가 이미 재검사한다. **한 번도 서로
  비교되지 않을 뿐이다.**
- **주석이 게이트와 모순된다**: `src/cli/commands/orchestrate.ts:382-385` 는 오케스트레이터의
  아티팩트가 git root 옆에 살고 run 이 `docs/spec/` 없는 저장소에서 실행될 수도 있다고 적는다.
- **그런데 실행은 root 하나로 수렴한다**: `runRoot() = --root ?? cwd`(`orchestrate.ts:386-389`)가
  19개 호출 지점(저널·락·`writeUnderRoot`·`resolveGitCommonDir`·핸드오프 pinning)에 같은 값을
  먹인다. 이것은 SRS 해소기(`project-root.ts:14-30`)가 **아니다** — orchestrate 에서 한 번도
  호출되지 않는다.
- MCP 경로에서는 `--root <deps.root>` 가 주입되어(`orchestrate.ts:256`) run root = MCP root,
  CLI 경로에서는 cwd. **두 표면이 호환되는 이유가 바로 등가 규칙이다.**
- run lock 만 git common dir 기준(`src/core/orchestrator/run-lock.ts:81-102`)이라 "내부"면 충분하고
  "동일"일 필요가 없다.

결정적 함의: 런 계약의 고정 경로들(`SKILL.md:157-163`)이 **어느 root 기준인지 어디에도 적혀 있지
않다.** 지금 그 모호함이 무해한 유일한 이유는 게이트가 root 를 하나로 보장하기 때문이다.
술어부터 풀면 시끄러운 거부가 두 root 에 걸친 조용한 분산으로 바뀐다 — FR-FLOW-042/043 이 막으려던
바로 그 피해가 수리를 통해 되돌아온다.

부수 발견: `src/mcp/adapter.ts:37` 은 `path.resolve(cwd)` 를, `src/mcp/tools/read-tools.ts:47` 은
상위 탐색을 쓰는데 **둘 다 `rootSource: "server-cwd-discovery"` 로 보고**한다. 에이전트가 어느
표면을 읽었느냐에 따라 `--mcp-root` 로 넘기는 값이 달라질 수 있다. 어떤 선택지를 택하든 별도로
다뤄야 한다.

### Phase 3 — B1 파이프라인 저널 분기 — **철회 (2026-08-07, 착수 전 정정)**

착수 직전 `FR-FLOW-043`(verified) 을 읽고 이 계획이 틀렸음을 확인했다.

- **AC-5** 는 파이프라인 이벤트 경로를 "문서화된 위치 체인을 run 자신의 cwd 기준으로 한 번만
  평가하고 **MCP 가 보고한 root 로는 절대 해소하지 않는다**"로 고정한다.
- **AC-2** 는 git 실패 시 cwd·home fallback 이 실제로 도달 가능해야 한다고 요구한다.
- 그 요구의 Research 절은 거절된 `work/kiwi-wave-master-multiroot-g0` 가 저널을
  `<git-root>/kiwi/` 로 고정하고 두 fallback 을 제거한 것이 **AC-2 와 충돌한다**고 이미 적어 두었다.

따라서 "스킬을 도구의 `<root>/kiwi` 에 맞춘다"는 두 verified AC 를 뒤집는 변경이고, 그 요구가
막으려던 실패(진행 로그가 요구사항과 갈라지는 것)를 되살린다. 반대 방향으로 도구를 git 최상위에
맞추는 것도 `--root` 사용을 깨뜨린다.

정정된 판단: **B1 은 독립적 결함이 아니라 §4 불변을 어긴 배치의 결과다.** 지원되는 배치에서는
두 경로가 같은 파일이므로 분기가 존재하지 않는다. 어긋난 배치에서는 Phase 2 의 doctor 경고가
이 결과를 이름으로 지목한다(FR-NODE-179 AC-4 가 파이프라인 저널을 명시적으로 요구). 별도 요구를
세우지 않는다.

### Phase 4 — 구조 분리 → **재정의 (2026-08-07, 착수 시 정정)**

착수 시 `orchestrate.ts` 를 전수 조사한 결과 계획된 `gitRoot()`/`srsRoot()` 분리는 실제와 맞지
않았다: **이 명령은 `docs/spec` 을 한 번도 건드리지 않는다.** `parseWorkspace` 도
`resolveProjectRoot` 도 호출하지 않고, 만드는 `ProjectRoot` 는 전부 저널·아티팩트 경로용 래퍼다.
즉 오케스트레이터 안에 SRS root 는 존재하지 않으며, "어느 root 기준인가"라는 §7 의 모호함은
코드에 이미 답이 있다 — 아티팩트 root(`--root ?? cwd`) 기준이다. 이름만 쪼개는 리팩터는
동작을 바꾸지 않으므로 요구가 될 수 없고, 만들 가치도 없다.

실제 갭은 다른 곳에 있었다. 재개 카드는 `run_root: { git_toplevel, mcp_workspace_root }` 를
설계 때부터 들고 있고 `computeInvariantDigest` 가 그것을 덮는데, **그 쌍은 소스 전체에서
타입 선언(`resume-card.ts:49`) 외에 어디에도 등장하지 않는다.** 아무도 세계와 대조하지 않으므로
digest 는 "카드가 바뀌지 않았다"만 증명하고 "이 세션이 그 저장소에 있다"는 증명하지 않는다.
preflight 는 run 의 시작을 지키지만 재개에는 대응물이 없었고, 노출은 오히려 재개 쪽이 크다 —
재개 세션에는 자신을 반박할 대화가 없다.

**FR-NODE-180 으로 구현**: 재개는 카드가 pin 한 git 최상위를 재개 중인 root 의 실제 최상위와
대조하고, 다르거나 저장소가 없으면 `run-invariant-drift` 로 거부한다. 새 게이트 id 없음.

### Phase 5 — 다중 모듈 지원 → **증거로 차단됨 (2026-08-07)**

사용자가 전 Phase 를 승인했으나, Phase 3·4 를 진행하며 나온 새 사실이 이 Phase 의 비용을
계획 시점보다 크게 올렸다. 착수하지 않고 사실을 기록한다.

1. **verified 요구 두 건을 추가로 뒤집어야 한다.** `FR-FLOW-043` AC-2 는 git 실패 시 cwd·home
   fallback 이 도달 가능할 것을, AC-5 는 파이프라인 경로를 run 자신의 cwd 기준으로 한 번만
   평가하고 MCP root 로는 절대 해소하지 않을 것을 요구한다. 다중 root 세계에서 "run 자신의 cwd"
   는 다섯 몸통 중 어느 것인지 정해지지 않는다. 계획서가 예상한 대상은 FR-NODE-153·IR-CLI-082·
   FR-FLOW-042 였고, 이 둘은 그 목록에 없었다.
2. **거절된 브랜치가 정확히 이 두 AC 를 위반했다.** `FR-FLOW-043` 의 Research 절이
   `work/kiwi-wave-master-multiroot-g0` 가 저널을 `<git-root>/kiwi/` 로 고정하고 두 fallback 을
   제거한 것을 AC-2 와의 **충돌**로 이미 기록해 두었다. 같은 설계를 다시 하면 같은 충돌이 난다.
3. **여는 대상 배치가 아직 그것을 감당하지 못한다.** §5.2 — 한 몸통이 2,307 errors 를 안고 있고,
   `FR-PLUGIN-001` 이 두 root 에서 서로 다른 요구를 가리킨다. 요구 ID 네임스페이스가 root 사이에서
   이미 충돌하는 상태 위로 오케스트레이션을 올리는 것은 순서가 뒤바뀐 일이다.
4. **비-다중-모듈 세계에서는 고칠 것이 없다.** §6 의 pinning 결함은 run root 가 저장소 최상위가
   아닐 때만 발화한다. 그 배치를 열지 않는 한 지금 고치는 것은 사변적 작업이다.

따라서 남은 착수 조건은 "재론 금지 해제" 하나가 아니라 셋이다 — (a) FR-FLOW-043 AC-2/AC-5 를
다중 root 아래에서 어떻게 재정의할지 먼저 정하고, (b) 대상 배치의 요구 ID 충돌과 validate 오류를
먼저 정리하고, (c) 그 뒤에 아래 순서를 밟는다.

```
Phase 4 완료(구조 테스트 green)
  → pinning 의 저장소 최상위 기준 경로 처리(§6)
  → O6 최상위 등가 술어 + O7 선언·고정

```
