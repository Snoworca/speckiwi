## 0. 요약

1. **SRS 가 정한 동작과 회귀는 모든 실행이 100% 였다.** 실험 A 12 회, 실험 B 12 쌍 모두 결정 테스트 51/51, 회귀 160/160 이었다. SDS 가 동작 품질을 올린 사례는 이번에도 없다.
2. **SRS 의 빈틈을 기존 관례대로 메우는 일에서는 Haiku 에게 SDS 가 도움이 됐다.** 실험 A 관례 테스트(33 건)에서 Haiku S 는 29·28·31 (평균 88.9%), Haiku D 는 3 회 모두 33 이었다. Sonnet 은 두 조건 모두 3 회 33 이었다. 빈틈은 공정했다: 정답표를 보지 않은 Opus 가 코드만 읽고 49 개 단언 모두 같은 답을 냈다.
3. **구조 품질에 대한 SDS 효과는 모델과 상황에 따라 방향이 바뀌었다.**
   - 새 구현(실험 C): Sonnet 은 SDS 로 맹검 점수가 약 1 점 올랐다(파일 하나로 합친 재채점에서 2.52 → 3.50). Haiku 는 +0.25 였다.
   - 기존 코드 변경(실험 A): Haiku 는 SDS 로 크게 좋아졌다(맹검 2.87 → 4.33, 재사용 규칙 위반 3.0 → 0.67). Sonnet 은 오히려 나빠졌다(3.77 → 3.37, 위반 0.67 → 2.0).
4. **SDS 의 오류는 구현으로 그대로 옮겨졌다.** Opus 가 쓴 SDS 3 개 중 2 개가 기존 관례에서 벗어난 지시를 하나씩 담고 있었다. Sonnet 은 그 지시를 SDS 를 받은 실행에서 예외 없이 따랐다. 실험 A 의 Sonnet D 구조 점수가 떨어진 원인이 이것이다(§3.3).
5. **병렬 wave 에서 SDS 쓰기 집합은 값을 하지 못했다.** 두 wave SDS 의 쓰기 집합이 공유 파일 5 개에서 겹쳐 kiwi-orchestrator 규칙대로는 직렬이 된다. SDS 없이 병렬로 돌린 쪽이 가장 빨랐다. Sonnet 은 병합 충돌이 0 건이었고, Haiku 의 충돌(4~5 hunk)은 중립 해소자가 15 초, 약 8 만 토큰에 풀었다. 품질은 세 조건이 같았고, SDS 직렬은 토큰이 약 2 배였다.

### 1.2 실험 A — 기존 코드 + 느슨한 SRS

조건 S 는 SRS 만, D 는 SRS 와 `A.sds.md` 를 받는다. 지시문은 같고 D 에만 "The design spec/A.sds.md was agreed for this work; follow it." 한 문장이 더 있다. 작업 폴더는 `base` 사본(git 포함)이고 숨긴 테스트·참조·다른 실행은 보이지 않는다.

### 1.3 실험 B — 병렬 wave

wave 1 = FR-CMT, wave 2 = FR-WCH. 동작은 서로 독립이지만 `errors.ts`·`audit-event.ts`·`ports.ts`·`memory.ts`·`app.ts` 를 함께 고친다. 두 wave SDS 의 쓰기 집합(Files ∪ Test Plan)은 바로 이 5 개 파일에서 겹쳤다. kiwi-orchestrator 는 쓰기 집합이 겹치는 wave 를 다른 stage 로 가르므로(`skills/claude/kiwi-orchestrator/SKILL.md` §7 의 `exclusive-lane` 행), SDS 조건은 직렬이 된다.

| 조건 | 내용 |
|---|---|
| P-S | SDS 없이 두 워커가 같은 base 사본에서 병렬. "다른 엔지니어가 병렬로 하고 git merge 로 합친다"고 알린다. 병합 충돌은 고정 지시문의 중립 해소자(Sonnet 5.5, 숨긴 테스트 비공개)가 푼다 |

벽시계는 병렬이면 두 워커 중 긴 쪽 + 해소자, 직렬이면 합, Q-D 는 SDS 작성(둘 중 긴 쪽)을 더했다. 토큰은 워커·해소자·SDS 작성 합계다.

## 3. 해석

### 3.1 동작 품질: SDS 는 여전히 무관하다

느슨한 SRS 와 기존 코드라는 조건을 더해도, SRS 가 정한 동작은 모든 실행이 맞췄다. 연구 34 의 결론("품질을 결정한 것은 SRS")이 이 범위에서도 유지된다.

### 3.2 관례 메우기: 값은 SDS 가 아니라 "코드를 읽은 결과" 에 있다

Haiku D 가 관례를 모두 맞춘 것은 SDS 에 Opus 의 코드 해석이 계약 줄로 들어 있었기 때문이다. Sonnet 은 같은 해석을 스스로 해냈다. 따라서 SDS 가 하는 일은 설계라기보다 **강한 모델이 읽은 관례를 약한 모델에게 넘기는 것**이다. 이 효과는 Haiku 에게만 있었고, Haiku 끼리도 실행마다 흔들렸다(28~33).

### 3.3 구조: SDS 는 구조를 고정하고, 고정된 것이 틀리면 그대로 퍼진다

- 새 구현에서는 기준이 될 구조가 없으므로, SDS 가 파일 분할과 시그니처를 정해 주면 Sonnet 의 구조가 좋아졌다.
- 기존 코드에서는 구조가 이미 코드에 있다. Sonnet 은 SDS 없이도 기존 헬퍼를 잘 재사용했다(위반 0.67). SDS 를 받자 SDS 의 지시가 코드의 관례보다 앞섰다. `A.sds.md` 는 SDS-AC-8 에서 "본문과 다시 계산한 멘션이 같으면 그대로 반환"을 정했고, Sonnet D 3 회는 모두 `applyPatch` 대신 직접 비교를 짰다(R4a). 멘션 파싱 안에서 `.trim()` 을 다시 부른 것도 SDS 의 "trimmed body 에서 매칭" 문구를 옮긴 결과다(R1c). 숨긴 테스트는 통과했으므로 동작 결함은 아니고 재사용 결함이다.
- `W2.sds.md` 의 `data { taskId }` 는 관례 위반이었고, SDS 를 받은 워커 4 개가 모두 따랐다.

**SDS 3 개 중 2 개가 관례에서 벗어난 지시를 하나씩 담았다.** kiwi-sds 기본 모드에는 LLM 검증이 없고 `speckiwi sds check` 는 문법만 본다. 그러므로 이 오류를 잡을 단계가 없다. SDS 를 충실히 따르는 모델일수록 이 오류를 그대로 옮긴다.

### 3.4 병렬 wave: 쓰기 집합 선언은 이번 조건에서 비용만 늘렸다

- 실제 기능 둘은 오류 코드 등록부·공개 진입점처럼 거의 언제나 같은 파일을 건드린다. 그래서 SDS 쓰기 집합 규칙은 병렬을 직렬로 바꾼다. 이번 기능에서 병렬의 이점이 SDS 때문에 사라졌다.
- SDS 없는 병렬의 충돌은 "양쪽 추가를 다 살린다"로 기계적으로 풀렸다. 해소 비용(15 초, 8 만 토큰)은 SDS 작성 비용(25 만 토큰, 2 분)보다 작았다.
- 품질은 세 조건이 같았다. 두 wave 가 같은 심볼을 따로 만든 경우도 없었다.

### 3.5 사전 등록한 판정 규칙의 적용

| 규칙 | 조건 | 결과 |
|---|---|---|
| 1 (선택 단계로) | A 에서 D 가 어느 지표로도 낫지 않고, B 에서 P-D 이득 없음 | **부분 충족.** Sonnet 은 충족(동작 동일, 구조는 더 나쁨). Haiku 는 미충족(관례 +11%p, 구조 +1.5) |
| 2 (기존 코드에만) | A 에서 D 가 관례·구조에서만 낫다 | **Haiku 에만 해당.** Sonnet 은 기존 코드에서 오히려 나빴다 |
| 3 (쓰기 집합 유지) | P-S 가 충돌·중복을 내고 P-D 가 막으면서 Q-S 보다 빠르다 | **불충족.** SDS 쪽이 직렬이 되어 가장 느렸다 |
| 4 (쓰기 집합도 불필요) | P-S 충돌이 해소자로 싸게 풀리고 품질이 같다 | **충족** |

## 4. 권고

1. **kiwi-sds 를 기본 사슬의 필수 단계에서 빼고 선택 단계로 둔다.** 구현자가 Sonnet 급 이상이면 이번 네 관점 어디에서도 이득이 없었고, 기존 코드에서는 구조가 나빠졌다.
2. **구현자가 Haiku 급이고 기존 코드를 고칠 때는 SDS 를 쓴다.** 이때 SDS 의 값은 강한 모델이 읽은 관례를 넘기는 데 있다. 그러니 SDS 작성자는 반드시 강한 모델이어야 한다.
3. **SDS 를 쓰면 "코드 관례와 어긋나는 계약" 을 잡는 검사를 붙일 것을 검토한다.** 지금은 그 오류를 잡는 단계가 없다(§3.3). 검토 방식은 이번에 재지 않았다.
4. **병렬 wave 의 쓰기 집합 게이트를 다시 설계할 것을 검토한다.** 후보는 "SDS 없이 병렬 + 병합 해소 hop" 이다. 공유 등록부 같은 핫 파일은 kiwi-orchestrator 의 `orchestrator-only` 수렴 레지스트리로 빼는 기존 장치도 있으나, 이번 실험에서는 쓰지 않았다.

이 권고는 모두 SRS 변경(FR-FLOW-182~184, kiwi-orchestrator 의 병렬 계약)이 먼저다. sdd 모드에서 요구로 올린 뒤 구현한다.

## 5. 한계

1. **표본이 작다.** 실험 A 는 칸당 3 회, 실험 B 는 2 쌍이다. Haiku 의 관례 점수는 같은 조건 안에서 28~33 으로 흔들렸다.
2. **코드베이스와 기능이 하나다.** 2 천 줄 규모의 합성 코드베이스다. 실제 저장소(수만 줄, 문서화되지 않은 관례, 오래된 코드)에서는 관례 찾기가 더 어렵다.
3. **SDS 는 실험당 한 번만 썼다.** SDS 의 오류 2 건은 그 한 번의 산물이다. 작성 편차와 오류율은 재지 않았다.
4. **모든 입력을 Opus 가 만들었다.** 코드베이스, SRS, 빈틈 정답, 숨긴 테스트, 참조 구현, SDS 가 모두 같은 모델 계열이다. 빈틈 공정성은 다른 Opus 인스턴스로 확인했을 뿐이다.
5. **구조 점수는 LLM 검토자의 판단이다.** 검토자 간 편차가 큰 실행이 있었고, 기계 중복 지표는 검토자와 반대 방향이었다. 재사용 규칙 판정도 Opus 1 명이 했다. `R4a`(applyPatch 사용)는 SDS 의 선택이 배열 비교 함정을 피하려는 의도였을 수 있어 결함으로 보기 어려운 면이 있다.
6. **벽시계에 동시 실행 부하가 섞였다.** 최대 12 개를 동시에 돌렸다. 직렬 조건의 벽시계는 에이전트 시간의 합이며, 사이의 조율 지연은 넣지 않았다.
7. **병렬 실험의 두 wave 는 동작이 독립이다.** wave 2 가 wave 1 의 코드를 호출하는 경우(인터페이스 합의가 필요한 경우)는 재지 않았다.
8. **구현자는 사용자 전역 CLAUDE.md(TDD 강제)를 받았다.** 실제 kiwi-coder 사슬(TDD 검증 서브에이전트, 리뷰 루프)은 거치지 않았다.
