## 1. Scope Overview

이 문서는 SpecKiwi를 사용하는 개발자와 AI coding agent의 구현 전후 workflow, release readiness, CI validation, baseline 운영을 정의한다.

## 2. Scope Boundaries

### In Scope

- 구현 전 SRS 탐색
- 구현 후 evidence 갱신
- release readiness summary
- CI validation 예시
- AGENTS.md 및 CLAUDE.md instruction
- baseline tag 운영

### Out of Scope

- 프로젝트 관리 도구 연동 자동화
- issue 자동 생성
- PR 자동 생성
- 배포 자동화

## 3. Assumptions and Constraints

- SRS는 Git에 저장된다.
- release 판단은 target/status/evidence summary를 기준으로 한다.
- agent는 CLI 또는 MCP를 통해 SRS를 사용할 수 있다.

- [x] AC-6: Requirement trace links resolve to existing requirement IDs or are reported as broken trace links.

#### Requirement

SpecKiwi repositories must provide canonical root `AGENTS.md` and `CLAUDE.md` managed instruction blocks, and init must upsert the current managed block deterministically.

#### Rationale

Many coding agents discover uppercase root instruction files; relying only on lowercase or stale agent files weakens SRS workflow enforcement.

#### Acceptance Criteria

### FR-FLOW-010 — stability-aware agent and release workflow

| Field | Value |
| --- | --- |
| Type | functional |

| Risk | high |
| Stability | evolving |
| Verification Method | test, inspection |
| GitHub Issue | - |
| Related Docs | docs/research/07.requirement-stability-lifecycle-research.md |

#### Requirement

SpecKiwi must expose requirement `Stability` in agent current-work workflows, target summaries, and release readiness so humans and agents can distinguish draft requirements from implementation-ready, frozen, and deprecated requirements.

#### Rationale

Coding agents need more than implementation `Status` to decide whether work can proceed. A `planned` requirement can still be too unstable to implement, and a `verified` requirement should not remain `draft`.

#### Acceptance Criteria

- [x] AC-1: Current work status workflow reports active target plus `Status` and `Stability` counts for target-scoped requirements.
- [x] AC-2: Agents must stop before implementing non-discarded requirements with `Stability=draft` or `Stability=deprecated` unless the user explicitly overrides the workflow.
- [x] AC-3: Target summary and release readiness expose stability blockers or warnings separately from status blockers.
- [x] AC-4: Release readiness blocks release of a target that still contains non-discarded `draft` requirements.
- [x] AC-5: Managed `AGENTS.md` and `CLAUDE.md` instructions explain `Status` versus `Stability` and the required behavior for `draft` requirements.
- [x] AC-6: CLI and MCP JSON outputs for active target, target summary, and current work status include enough stability data for agents to answer status questions without scanning raw Markdown.
- [x] AC-7: Completed Work Log remains a summary only; `Stability` does not replace Requirement Block `Status`, Acceptance Criteria, Verification Evidence, or Change Notes as the source of truth.

### FR-FLOW-011 — next target authoring workflow

| Risk | medium |
| Stability | evolving |
| Verification Method | test, inspection |
| GitHub Issue | - |
| Related Docs | AGENTS.md; CLAUDE.md |

#### Requirement

SpecKiwi agent instructions must define how agents handle a user request such as "set the next target to 2.1.0" and ensure subsequent SRS authoring uses that Active Target by default.

#### Rationale

Active Target is useful only if agents consistently consult it before target-scoped SRS changes. The workflow must prevent agents from writing new requirements to stale targets after the user selects a new goal version.

#### Acceptance Criteria

- [ ] AC-1: Agent workflow reads Active Target before creating or updating target-scoped requirements.
- [ ] AC-2: When the user asks to set a new target that is not registered, the workflow uses MCP `set_active_target` with creation enabled or CLI `speckiwi set-active-target <target> --create`.
- [ ] AC-3: After target assignment, agents confirm the resolved Active Target through MCP `get_active_target` or CLI `speckiwi active-target --json`.
- [ ] AC-4: Subsequent SRS creation uses the resolved Active Target unless the user explicitly supplies a different target.
- [ ] AC-5: If Active Target is empty and no explicit target exists, agents stop and ask for the target before making target-scoped SRS changes.
- [ ] AC-6: Managed `AGENTS.md` and `CLAUDE.md` instructions document the next-target workflow and the difference between explicit target and Active Target defaulting.
