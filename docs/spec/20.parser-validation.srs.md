## 1. Scope Overview

이 문서는 SRS Markdown 문서 탐색, Requirement Block 파싱, normalized requirement record 생성, validation rule 적용을 정의한다.

## 2. Scope Boundaries

### In Scope

- SRS 파일 탐색
- Requirement heading 파싱
- metadata table 파싱
- Acceptance Criteria 파싱
- Verification Evidence 및 Trace Links 파싱
- validation diagnostics 생성

### Out of Scope

- Markdown 전체 렌더링
- 일반 문서 요약
- 외부 URL 네트워크 검증
- YAML 또는 다른 요구사항 포맷 파싱

## 3. Assumptions and Constraints

- SRS 문서는 SRS-MD Authoring Rules v1.0.0을 따른다.
- 파서는 가능한 한 부분 파싱을 제공한다.
- 기본 명령은 네트워크 호출을 하지 않는다.

### FR-PARSE-011 — fenced-code-aware requirement block scanner

| Field | Value |
| --- | --- |
| Type | functional |
| Target | v1.2.0 |

| Priority | high |
| Tags | parser, block-scanner, code-fence |

#### Requirement

SpecKiwi parser는 fenced code block 내부의 heading-like text를 Requirement heading으로 해석하지 않고, Requirement Block을 문서화된 Requirements section boundary 안에서만 추출해야 한다.

#### Rationale

현재 line-based scanner는 code fence와 후속 section boundary를 충분히 구분하지 못해 정상 Markdown 예시를 requirement로 오인하거나 마지막 block에 문서 후속 section을 포함할 수 있다.

#### Acceptance Criteria

- [x] AC-1: fenced code block 안의 `### FR-...` 텍스트는 requirement record를 만들지 않는다.
- [x] AC-2: fenced code block 안의 malformed heading-like text는 malformed requirement heading diagnostic을 만들지 않는다.
- [x] AC-3: Requirement Block은 다음 valid requirement heading, 다음 관련 top-level `##` section, 또는 파일 끝에서 종료된다.
- [x] AC-4: parser fixture set maps to the research Parser hardening acceptance group with code fence heading, malformed heading inside code fence, and final block boundary regression cases.

#### Requirement

Workspace parser MUST recognise a Target Goal meta block placed after the Target Map table and expose the parsed goal text on the workspace records so read-side tools can surface per-target goals.

#### Rationale

Three-agent review (2026-05-16) rejected adding a Goal column to the Target Map table because the existing parser hardcodes column index order and renderRow positions; inserting a new column risks breaking backward compatibility on existing SRS workspaces. A separate meta block (heading-based) under or adjacent to the Target Map preserves the table schema and stays Markdown-native.

#### Acceptance Criteria

- [x] AC-1: AC-1: parser detects '### Target: <token>' subsection under the Target Map area in 00.index.md or 90.appendix.md and extracts the body until the next heading of equal or higher level.
- [x] AC-2: AC-2: a '**Goal:**' inline label inside the block is normalised into a single goal string (multi-paragraph preserved as newline-joined).
- [x] AC-3: AC-3: parser exposes the parsed goals via `ParsedWorkspace.index.targetGoals: Record<string, string>` keyed by target token (the `targetGoals` field lives on `IndexDocument`, reachable through `workspace.index.targetGoals`).
- [x] AC-4: AC-4: absence of the meta block does not generate a diagnostic; targetGoals stays empty.
- [x] AC-5: AC-5: an automated parser test reads a fixture with two target goal blocks and asserts both texts are extracted with codepoint equality (verbatim non-ASCII, tab, and escape preservation; multi-paragraph bodies are joined with single `\n`).
- [x] AC-6: AC-6: goal text accepts CR/LF/TAB but rejects other control characters at the mutation layer (consistency with reason policy).
