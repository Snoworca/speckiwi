## 1. CLI Command Reference

### 1.1 Global Usage

```text
speckiwi <command> [options]
```

Common options:

| Option | Meaning |
|---|---|
| `--root <path>` | Project root. If omitted, SpecKiwi searches upward for `.git` or `docs/spec/00.index.md`. |
| `--json` | Print machine-readable JSON to stdout. |
| `--no-color` | Disable ANSI color. |
| `--quiet` | Reduce non-essential output. |
| `--help` | Print command help. |
| `--version` | Print package version. |

### 1.3 Command Details

#### `speckiwi init`

```text
speckiwi init [--root <path>] [--target <target>] [--scope <name:prefix>] [--force]
```

Behavior:

- Checks `docs/`, `docs/spec/`, and `docs/rule/`, then creates missing directories.
- Creates `docs/spec/00.index.md` as an empty SRS index when absent.
- Creates `docs/spec/90.appendix.md` when absent.
- Refreshes the bundled authoring rules documents in `docs/rule/` to the versions the tool ships and removes the stale versioned rules files they supersede.
- Creates or updates uppercase `AGENTS.md` and `CLAUDE.md`.
- Upserts the current SpecKiwi managed block by versioned heading and suffix marker; an existing rules link alone is not a skip condition.
- Does not overwrite author-owned files — the index, the scope SRS documents, the appendix and the step state — unless `--force` is set. The rules documents are tool-owned and are refreshed without it.

#### `speckiwi validate`

```text
speckiwi validate [--root <path>] [--strict] [--fail-on-warning] [--scope <scope>] [--target <target>] [--json]
```

Exit behavior:

- `0`: no errors.
- `1`: validation errors, or warnings with `--fail-on-warning`.
- `2`: invalid arguments.
- `3`: file I/O failure.
- `4`: fatal parse failure.

#### `speckiwi add-requirement`

```text
speckiwi add-requirement --type <Type> --scope <Scope> [--target <Target>] --title <Title> --requirement <Text> --ac <Text> [--ac <Text>...] [--checked-ac <Text>...] [--status <Status>] [--priority <Priority>] [--tags <Tags>] [--risk <Risk>] [--stability <Stability>] [--verification-method <Method>] [--rationale <Text>] [--implementation-notes <Text>] [--evidence <JSON>] [--trace <JSON>] [--dry-run] [--json]
```

Behavior:

- Generates the next Requirement ID from type prefix and scope prefix.
- Appends the generated Requirement Block to the end of the target scope document's `## 4. Requirements` section.
- Uses explicit `--target` when provided; otherwise uses `00.index.md` Active Target.
- Fails without changing files when both explicit target and Active Target are empty.
- Defaults `Status` to `planned` when omitted.
- Defaults `Stability` to `draft` when omitted.
- Rejects unknown `Stability` values and rejects legacy `volatile` for new Requirement Blocks.
- Rejects `verified` unless every AC is checked and at least one Verification Evidence row has a non-empty reference.

#### `speckiwi set-target-status`

```text
speckiwi set-target-status <Target> <planned|active|frozen|completed|released|archived> [--dry-run] [--ignore-lock] [--json]
```

Behavior:

- Rewrites one Target Map row's `Status` cell and nothing else. `Target`, `Type` and `Description` are left byte-identical.
- Rejects a status outside the vocabulary the authoring rules document defines, and an unregistered target.
- Rejects `active` while another row already holds it; moving the active target is `set-active-target`'s job, because it also updates the `Active Target` metadata row.
- CLI-only. Recording a target as `released` is a release decision, not agent work.

#### `speckiwi set-active-target`

```text
speckiwi set-active-target <Target> [--create] [--type <version|release|milestone|phase|objective|experiment>] [--description <text>] [--dry-run] [--json]
```

Behavior:

- Without `--create`, rejects targets that are not already registered in the Target Map.
- With `--create`, appends a Target Map row when the target is missing, then marks that target active.
- The departing target's status is derived from its own requirements rather than fixed to `planned`: it becomes `completed` when the target carries at least one live requirement and every one is `verified`, and stays `planned` otherwise. Discarded requirements are excluded. Completion is not inferred when the workspace reports parse errors. `released` is never derived — record it with `set-target-status`.
- Updates the `Active Target` metadata row and keeps at most one Target Map row with `Status=active`.

#### `speckiwi add-completed-work`

```text
speckiwi add-completed-work --date <YYYY-MM-DD> --summary <Text> [--target <Target>] [--scope <Scope>] [--requirements <IDs>] [--report <Path>...] [--allow-incomplete] [--dry-run] [--json]
```

Behavior:

- Appends a Completed Work Log row after prevalidating target, scope, and requirement references.
- Accepts repeatable `--report <Path>` options. Report paths are persisted in the optional trailing `Report Paths` column.
- Existing five-column Completed Work Log tables remain readable. A five-column table is upgraded to six columns only when report paths are written.
- Report paths are repository-relative POSIX paths and are serialized as comma-separated values. Blank paths, absolute paths, `./` or `../` prefixes, `..` segments, URL schemes, backslashes, pipes, commas, CR/LF, and `#` are rejected.

#### `speckiwi update-status`

```text
speckiwi update-status <RequirementID> <Status> [--dry-run] [--reason <text>] [--json]
```

Allowed statuses:

```text

in_progress
blocked
implemented
verified
discarded
```

`verified` guard:

- All Acceptance Criteria must be checked.
- Verification Evidence must contain at least one row.
- Evidence reference must not be empty.

#### `speckiwi mcp`

```text
speckiwi mcp [--transport stdio]
```

Rules:

- Default transport is `stdio`.
- The `mcp` command does not support `--root` (IR-CLI-045). Running `speckiwi --root <path> mcp` or `speckiwi mcp --root <path>` exits with a usage error (exit code 2) instead of starting the server.
- The server resolves the project root from the server process current working directory by searching upward for `.git` or `docs/spec/00.index.md`.
- If no project root can be found, the server treats the current working directory as a new project root and creates the default SRS structure before handling MCP calls.
- If a project root exists but `docs/spec/00.index.md` is missing, the server creates the default SRS structure before handling MCP calls.
- stdout is reserved for MCP JSON-RPC messages.
- stderr is used for logs.
- The server must not print banners or human-readable logs to stdout.

Read commands:

```text
speckiwi workflow pipeline tail [shared read options]
speckiwi workflow pipeline compact [shared read options]
speckiwi workflow session-status [shared read options]
speckiwi workflow worklog-tail [shared read options]
speckiwi workflow work-order next [shared read options] [--measure] [--pipeline-path <path>] [--explain] [--profile <default|compact|explain>] [--context-profile <default|compact>]
```

Mutation commands:

```text
speckiwi workflow pipeline-emit --event <json> --run-id <runId> [--path <pipeline.jsonl>] [mutation options]
speckiwi workflow worklog-emit --event <json> --run-id <runId> [--path <worklog.jsonl>] [mutation options]
speckiwi workflow repair-record --event <json> --run-id <runId> [--path <worklog.jsonl>] [mutation options]
speckiwi workflow logical-delete --record-type <type> --record-id <id> --reason <text> --run-id <runId> [--path <pipeline.jsonl>] [mutation options]
```

Behavior:

- Read commands resolve canonical workflow artifacts and omit logically deleted records unless `--include-deleted` is set.
- `work-order next` is the compact next-step surface for agents that need to reduce prompt tokens.
- Mutation commands require `runId` and use idempotency, owner, expected hash, reason, and dry-run guards where provided.
- `logical-delete` records a deletion/tombstone event; normal tail/status views hide deleted records by default.

#### `speckiwi repair requirement-id-collisions`

```text
speckiwi repair requirement-id-collisions diagnose [--json]
speckiwi repair requirement-id-collisions plan --duplicate-id <id> --keep <file:line:blockHash> --rename <file:line:blockHash> [--replacement-id <id>|--allocate-next] [--reference-edit <json>...] [--write-plan <path>] [--json]
speckiwi repair requirement-id-collisions apply --plan <path> [--dry-run] [--ignore-lock] [--json]
```

Behavior:

- `diagnose` is read-only and reports duplicate Requirement ID occurrences with `filePath`, `headingLine`, and `blockHash`.
- `plan` is read-only unless `--write-plan` is provided, and writes only the explicit repair plan artifact.
- `apply` mutates only from an explicit plan and allows `--ignore-lock` only for the guarded SRS mutation lock bypass.
- Collision repair is for merge-time duplicate IDs, not general renumbering, gap filling, bulk archive, or status/stability changes.

#### `speckiwi skills install`

```text
speckiwi skills install <codex|claude|etc|hermes> <skill|all> [-g|--global] [--dest <dir>] [--category <name>] [--dry-run] [--json]
speckiwi skills add <codex|claude|etc|hermes> <skill|all> [-g|--global] [--dest <dir>] [--category <name>] [--dry-run] [--json]
```

Behavior:

- Project installs create generated runtime mirrors under the target agent skill directory.
- `--dry-run` returns the planned copy set without writing.
- `--global` and `--dest` are mutually exclusive.
- `--category` is valid only for Hermes global installs.

#### `speckiwi doctor`

```text
speckiwi doctor [--json]
```

Behavior:

- Checks package identity, CLI bin entrypoint, package-lock alignment, packaged Kiwi skill entrypoints, MCP metadata, MCP tool schemas, active target read, validation read, and dry-run mutation wiring.
- Exits with code `5` when any doctor check fails.

## 3. MCP Tool Reference

### 3.1 Tool Summary

| Tool | Mutates Files | Purpose |
|---|---:|---|
| `add_compatibility_check` | yes | Records a first compatibility claim between two requirements, creating the edge on whichever of the two sorts lower, and refuses a requirement paired with itself, a discarded or deprecated endpoint, a frozen holding block, and a pair already recorded. |
| `add_completed_work` | yes | Appends one dated row to the Completed Work Log — target, scope, requirement ids, summary and report paths — refusing the whole write when a name it carries does not resolve: an unregistered target or scope, a requirement id no block holds, or a requirement not yet implemented, which `allowIncomplete` waives on its own. |
| `add_requirement` | yes | Creates a new requirement block in the scope document, allocating the next id in the series that the type prefix and the scope prefix share, and can seed criteria, evidence and trace rows in the same call. |
| `add_roadmap_item` | yes | Allocates the next `RM-<n>` and appends a milestone or feature to `docs/roadmap.md`, creating the file with its banner when it is absent, with a `Created` history row carrying the reason; `fromTarget` makes the item of a registered target, borrowing its goal as the purpose. |
| `add_trace_link` | yes | Adds one Trace Link row to a requirement — type, reference, relation, notes — recording what the requirement connects to rather than what proves it; a row of type Requirement whose reference names no known block is refused, and a row to a discarded requirement is refused unless it records the supersede, with relation supersedes or superseded_by. |
| `add_verification_evidence` | yes | Adds one Verification Evidence row to a requirement — type, reference, the criteria it covers, notes — which is what makes a `verified` status defensible. |
| `append_section_note` | yes | Appends text to one narrative section of a requirement (Rationale, Research / Analysis or Implementation Notes), or replaces that section's body outright. |
| `apply_requirement_id_collision_repair` | yes | Carries out an explicit keep/rename mapping for one duplicate Requirement ID, refusing anything the mapping does not name, and never renumbering, beautifying or bulk-editing. |
| `check_acceptance_criteria` | yes | Ticks or unticks acceptance criteria of one requirement, leaving their wording untouched. |
| `check_prd` | no | Checks one PRD file under `docs/prd` against the kiwi-prd grammar: gaps and duplicates in `PRD-<n>` numbering, a Kind or Exclusion Class outside its list, a Source naming no `U-<n>` block, a quote absent from its source, a Request SHA256 mismatch, and requirement grammar that has no place in a PRD. |
| `check_prd_coverage` | no | Compares one PRD file with the SRS of a target by string only: the intent, goal and in-scope items no requirement or criterion of the target cites, the requirements that cite no PRD item, and the criteria with neither a PRD citation nor a `fills:` basis. |
| `check_review_round` | no | Judges the latest round of a kiwi-review-fix-loop run from the `limits` and `rounds[]` the lead recorded in `.kiwi/sessions/<runId>/state.json`: whether a round of 2 or later listed every code file that changed between the previous round's `tree_sha` and its own, or recorded why it widened to the full scope; whether blocking findings introduced by earlier rounds are more than half of its blocking findings; and whether the run passes, continues, or stops NEEDS_USER on a residual, its round cap or its token budget. |
| `check_roadmap` | no | Checks `docs/roadmap.md` against the roadmap grammar — item numbering, metadata rows, value sets, coarse dates, milestones, dependency cycles, history rows and the names it points at in the SRS — and returns each `ROADMAP-` diagnostic with `passed` false while an error remains; the same answer `speckiwi roadmap check --json` prints. |
| `check_sds` | no | Parses one lite-profile SDS file under `docs/sds` and returns its structural and reference diagnostics beside a summary of the files, test files, requirement ids, acceptance contracts and dependency chains it declares — the same answer `speckiwi sds check` prints. |
| `check_test_sufficiency` | no | Reports, for every acceptance criterion of the requirements in a target or an id list, the test lines that cite the requirement id together with that criterion, and for a lite SDS whether each contract's planned test file exists and cites it — the same answer `speckiwi coverage --tests` prints. |
| `check_vibe_gate` | no | Answers whether the vibe/tdd synthesis gate passes: an active vibe or tdd task with no synthesized step directory, or a tdd task with no written acceptance contract (acceptance lines in its intent stub, or an authored design document), fails it. |
| `claim_step` | yes | Opens a step and declares what it will touch — one scope and any number of requirement ids — so a second session cannot claim overlapping ground; naming a supersede target that is verified or frozen is refused outright. |
| `diagnose_requirement_id_collisions` | no | Finds every duplicate Requirement ID in the workspace and, for each, the occurrences that carry it with their file, heading line and block hash — the three coordinates a repair plan must name. |
| `edit_requirement_fields` | yes | Edits the scalar fields of one requirement — title, statement, priority, risk, tags, related documents, verification method, GitHub issue — leaving criteria and table rows alone. |
| `edit_requirement_table_rows` | yes | Updates or deletes rows of one requirement's Verification Evidence, Trace Links or Change Notes table through an explicit operation list; no other table is reachable from here, and appending a row belongs to the `add_*` tools and the status tools rather than to this one. |
| `expire_acceptance_criterion` | yes | Marks one live acceptance criterion of a requirement expired: the line keeps its number and checkbox, its text is struck through and stamped with today's local date and an optional successor requirement, and the mandatory `reason` lands in a Change Notes row of the same patch. |
| `get_active_target` | no | Names the Active Target the SRS index records, together with its goal, its status and stability rollups, its blockers and the workspace diagnostics as they stand — those are counted over every document, not narrowed to this target. |
| `get_next_work_order` | no | Names the action a run should take next — by default `implement-requirements` for the open requirement IDs no finished kiwi-pm session covers, resuming or reporting a blocked kiwi-pm session over them, asking the user, or stopping — beside the requirements that action covers and the context it needs. |
| `get_prd_item` | no | Returns one item of a PRD file by its `PRD-<n>` ID with its kind, state, quote, source, body and the `<path>@sha256:<hex>` pointer of the PRD as read, and refuses an ID the file does not hold with PRD_ITEM_NOT_FOUND. |
| `get_requirement` | no | Returns one requirement block by identifier — metadata, statement, acceptance criteria, evidence and trace rows — optionally with its raw Markdown. |
| `get_roadmap_item` | no | Returns one roadmap item by its `RM-<n>` ID with its scope requirement IDs, Change History, schedule baseline, `replanCount`, health and `slipDays`, and the earlier dates the SRS records — Status change notes and Completed Work Log rows — as candidates for its actual dates; the same JSON, at `schema: 1`, that `speckiwi roadmap show --json` prints. |
| `get_work_mode` | no | Reports the persisted work mode (`sdd`, `vibe`, `tdd` or `wait`) and the Active Task recorded beside it, falling open to `wait` when the state document is absent or unreadable rather than failing the call. |
| `init_project` | yes | Lays down the SRS scaffold a project needs — index, first scope document, appendix, step state — skipping each one that already exists, while the tool-owned files are rewritten on every run: the bundled rules documents, whose stale versioned copies are deleted, and the managed block inside `AGENTS.md` and `CLAUDE.md`. |
| `list_compat_edges` | no | Projects the same `checked_compatible` edge set as the dirty-edge reader and returns identical rows; the two spellings exist so a caller can name the traceability reading instead of the staleness one. |
| `list_completed_work` | no | Pages the Completed Work Log — date, target, scope, requirement ids, summary and report paths — newest first by default and filterable by target, scope or a since date. |
| `list_dirty_edges` | no | Enumerates every `checked_compatible` edge with its classification — clean, dirty, orphaned or missing — optionally narrowed to one target. |
| `list_prd_items` | no | Pages the items of one PRD file in document order, each with its title, kind, state, quote, source and the PRD pointer, under the page fields the requirement list uses (`total`, `offset`, `returned`, `nextOffset`). |
| `list_requirements` | no | Enumerates requirement records filtered structurally — by target, status, type, scope, tag, stability, priority, missing evidence, related document, evidence or trace reference, or new-work candidacy — in identifier order, with paging and field projection. |
| `list_roadmap_items` | no | Pages the items of `docs/roadmap.md` in document order, each with the status, blocked flag, acceptance-criterion progress and schedule health computed from the SRS on the as-of date, filtered by status, kind, target or milestone, under the page fields the requirement list uses (`total`, `offset`, `returned`, `nextOffset`) — the same JSON, at `schema: 1`, that `speckiwi roadmap list --json` prints. |
| `list_steps` | no | Returns the rows of `docs/spec/steps/state.md` in dependency order, each with its status, its dependencies, and whether its SDS design document exists and what status that document carries, and reports cycles, orphan dependencies and supersede conflicts as advisories rather than errors. |
| `list_targets` | no | Lists every target the Target Map registers — its type, status and description, each with the status and stability rollups, blockers and goal a target summary carries — beside the Active Target, the same answer `speckiwi targets --json` prints. |
| `mcp_workspace_info` | no | Reports which repository this MCP server bound to at startup — the root, how that root was discovered, the index path and the package version. |
| `orchestrate_auto_gate` | no | Applies the --auto decision rule to one gate ballot the caller supplies and returns the verdict: adopt the recommended option, adopt the default-if-auto option, adopt a majority over the votes already in the payload, or escalate and halt for the user. |
| `orchestrate_card_write` | yes | Replaces the resume card of a run — the frozen block a resumed session compares its world against. |
| `orchestrate_duplication_plan` | no | Audits lane diffs against the lanes' declared write sets, which bound each lane's candidates to the paths it said it would touch, and proposes the duplication candidates a reviewer should look at. |
| `orchestrate_freeze` | yes | Content-addresses one run artifact set — design, waves, lanes, issues or postmortem — pinning the named document by its git blob id and the declared inputs by their digest, and refusing a body that omits a field its kind requires. |

| `orchestrate_issue_list` | no | Lists the wave issue ledger's rows, optionally for one wave, each with its classification and disposition. |

| `orchestrate_preservation_check` | no | Reports the preservation layer of the diff between two revisions (head defaulting to HEAD): every file that existed at base and is deleted or renamed, every exported name of a JavaScript or TypeScript file that is gone or whose parameter list or type text changed, and every deleted test file, removed test case, assertion removed from a case that remains, added skip or focus marker and commented-out case. |

### 4.1 MCP Resource Payload Policy

v1.2.0 resources use an envelope-all payload policy. The domain-specific resource payload is always nested under `value`, and diagnostics are carried at the envelope level:

```json
{
  "ok": true,
  "value": {},
  "diagnostics": [],
  "diagnosticsSummary": { "errors": 0, "warnings": 0, "byCode": {} }
}
```

Compatibility note: `speckiwi://completed-work` had documented raw `{ completedWork }` behavior in v1.1.0-era requirements. During the v1.2.0 compatibility window, clients should treat `value.completedWork` as canonical and may support the raw shape only when talking to older v1.1.x servers.

### 7.1 Target Status and Diagnostic Governance

Target Map status values:

| Status | Meaning |
|---|---|
| `planned` | Target is defined but work has not started. |
| `active` | Target is the current work target. |
| `frozen` | Target scope is frozen and requires explicit review for meaningful changes. |
| `completed` | Target requirements are complete but not necessarily released as an immutable baseline. |
| `released` | Target passed release-readiness and is treated as an immutable baseline. |
| `archived` | Historical target that is generally not modified. |

v1.2.0 planned hardening requires a code-level diagnostic registry. Registry entries must include code, severity, title, message template, source rule, and since fields, and the rule document diagnostic table must be contract-tested against that registry.

`SRS-E001` through future diagnostic codes are governed by `src/core/diagnostic-registry.ts`; code emission through `diagnostic()` fails when a code is unknown or emitted with a severity that differs from the registry.

v1.2.0 planned hardening also requires index diagnostics for duplicate targets, duplicate scope prefixes, multiple active target rows, missing scope documents, unregistered scope SRS documents, Status Summary drift, and Requirement Type Summary drift.

v1.3.0 stability diagnostics extend the registry with `SRS-W022` for legacy `volatile`, `SRS-E033` for verified draft requirements, and `SRS-W023` for draft requirements in active or released targets. Unknown stability values continue to use `SRS-E011`.

v2.1.1 Completed Work Log report path diagnostics add `SRS-W024` for malformed lexical report path tokens. This warning does not make report paths verification evidence and does not check whether report files exist.

## 9. AGENTS.md / CLAUDE.md Addition

v1.2.0 planned hardening treats uppercase root `AGENTS.md` and `CLAUDE.md` as canonical agent instruction files. Init and the MCP init_project tool must upsert the current managed block by versioned heading and suffix marker, preserving unrelated user content and replacing legacy or older SpecKiwi blocks. Lowercase `agents.md` is retained as a compatibility mirror only; new automation should read the uppercase canonical files first.

The block itself is not reproduced here. It was, and the copy went stale: it sat at an older
version, in the language the block no longer uses, naming a rules document filename that had
moved — while every requirement around it had been repaired. A sample that states what the tool
writes has to be read from the tool.

| What | Where |
|---|---|
| The block's text | `renderAgentInstructionSnippet` in `src/core/bootstrap/templates.ts` |
| Its heading and end marker | `AGENT_INSTRUCTION_HEADING_PREFIX` and `AGENT_INSTRUCTION_END_MARKER` |
| Its version | `AGENT_INSTRUCTION_VERSION` |
| The heading an older version wrote | `LEGACY_KOREAN_AGENT_HEADING_PREFIX`, kept so init can find and replace such a block |

To see the current block, run `speckiwi init --dry-run` in an empty directory and read what it
reports it would write.
