```text
speckiwi <command> [options]
```

Common options:

| Option | Meaning |

### 1.3 Command Details

#### `speckiwi init`

```text
speckiwi init [--root <path>] [--target <target>] [--scope <name:prefix>] [--force]
```

Behavior:

- Checks `docs/`, `docs/spec/`, and `docs/rule/`, then creates missing directories.
- Creates `docs/spec/00.index.md` as an empty SRS index when absent.
- Creates `docs/spec/90.appendix.md` when absent.
- Creates `docs/rule/SRS-MD-Rules-v1.0.0.md` from the bundled rules template when absent.
- Creates or updates uppercase `AGENTS.md` and `CLAUDE.md`.
- Upserts the current SpecKiwi managed block by versioned heading and suffix marker; an existing rules link alone is not a skip condition.
- Does not overwrite existing files unless `--force` is set.

#### `speckiwi validate`

```text
speckiwi validate [--root <path>] [--strict] [--fail-on-warning] [--scope <scope>] [--target <target>] [--json]
```

Exit behavior:

- `0`: no errors.
- `1`: validation errors, or warnings with `--fail-on-warning`.
- `2`: invalid arguments.
- `3`: file I/O failure.
- `4`: fatal parse failure.

#### `speckiwi add-requirement`

```text
speckiwi add-requirement --type <Type> --scope <Scope> [--target <Target>] --title <Title> --requirement <Text> --ac <Text> [--ac <Text>...] [--checked-ac <Text>...] [--status <Status>] [--priority <Priority>] [--tags <Tags>] [--risk <Risk>] [--stability <Stability>] [--verification-method <Method>] [--rationale <Text>] [--implementation-notes <Text>] [--evidence <JSON>] [--trace <JSON>] [--dry-run] [--json]
```

Behavior:

- Generates the next Requirement ID from type prefix and scope prefix.
- Appends the generated Requirement Block to the end of the target scope document's `## 4. Requirements` section.
- Uses explicit `--target` when provided; otherwise uses `00.index.md` Active Target.
- Fails without changing files when both explicit target and Active Target are empty.
- Defaults `Status` to `planned` when omitted.
- Defaults `Stability` to `draft` when omitted.
- Rejects unknown `Stability` values and rejects legacy `volatile` for new Requirement Blocks.
- Rejects `verified` unless every AC is checked and at least one Verification Evidence row has a non-empty reference.

#### `speckiwi set-active-target`

```text
speckiwi set-active-target <Target> [--create] [--type <version|release|milestone>] [--description <text>] [--dry-run] [--json]
```

Behavior:

- Without `--create`, rejects targets that are not already registered in the Target Map.
- With `--create`, appends a Target Map row when the target is missing, then marks that target active.
- Updates the `Active Target` metadata row and keeps at most one Target Map row with `Status=active`.

#### `speckiwi add-completed-work`

```text
speckiwi add-completed-work --date <YYYY-MM-DD> --summary <Text> [--target <Target>] [--scope <Scope>] [--requirements <IDs>] [--report <Path>...] [--allow-incomplete] [--dry-run] [--json]
```

Behavior:

- Appends a Completed Work Log row after prevalidating target, scope, and requirement references.
- Accepts repeatable `--report <Path>` options. Report paths are persisted in the optional trailing `Report Paths` column.
- Existing five-column Completed Work Log tables remain readable. A five-column table is upgraded to six columns only when report paths are written.
- Report paths are repository-relative POSIX paths and are serialized as comma-separated values. Blank paths, absolute paths, `./` or `../` prefixes, `..` segments, URL schemes, backslashes, pipes, commas, CR/LF, and `#` are rejected.

#### `speckiwi update-status`

```text
speckiwi update-status <RequirementID> <Status> [--dry-run] [--reason <text>] [--json]
```

Allowed statuses:


`verified` guard:

- All Acceptance Criteria must be checked.
- Verification Evidence must contain at least one row.

#### `speckiwi mcp`

```text
speckiwi mcp [--transport stdio]
```

Rules:

- Default transport is `stdio`.
- The `mcp` command does not support `--root` (IR-CLI-045). Running `speckiwi --root <path> mcp` or `speckiwi mcp --root <path>` exits with a usage error (exit code 2) instead of starting the server.
- The server resolves the project root from the server process current working directory by searching upward for `.git` or `docs/spec/00.index.md`.
- If no project root can be found, the server treats the current working directory as a new project root and creates the default SRS structure before handling MCP calls.
- If a project root exists but `docs/spec/00.index.md` is missing, the server creates the default SRS structure before handling MCP calls.
- stdout is reserved for MCP JSON-RPC messages.
- stderr is used for logs.
- The server must not print banners or human-readable logs to stdout.

Mutation commands:

Behavior:

- Read commands resolve canonical workflow artifacts and omit logically deleted records unless `--include-deleted` is set.
- `work-order next` is the compact next-step surface for agents that need to reduce prompt tokens.
- Mutation commands require `runId` and use idempotency, owner, expected hash, reason, and dry-run guards where provided.
- `task-check`, `task-uncheck`, and `checklist-set` update planner Markdown checkboxes through guarded workflow mutations.
- `logical-delete` records a deletion/tombstone event; normal tail/status views hide deleted records by default.

#### `speckiwi repair requirement-id-collisions`

```text
speckiwi repair requirement-id-collisions diagnose [--json]
speckiwi repair requirement-id-collisions plan --duplicate-id <id> --keep <file:line:blockHash> --rename <file:line:blockHash> [--replacement-id <id>|--allocate-next] [--reference-edit <json>...] [--write-plan <path>] [--json]
speckiwi repair requirement-id-collisions apply --plan <path> [--dry-run] [--ignore-lock] [--json]
```

Behavior:

- `diagnose` is read-only and reports duplicate Requirement ID occurrences with `filePath`, `headingLine`, and `blockHash`.
- `plan` is read-only unless `--write-plan` is provided, and writes only the explicit repair plan artifact.
- `apply` mutates only from an explicit plan and allows `--ignore-lock` only for the guarded SRS mutation lock bypass.
- Collision repair is for merge-time duplicate IDs, not general renumbering, gap filling, bulk archive, or status/stability changes.

#### `speckiwi skills install`

```text
speckiwi skills install <codex|claude|etc|hermes> <skill|all> [-g|--global] [--dest <dir>] [--category <name>] [--dry-run] [--json]
speckiwi skills add <codex|claude|etc|hermes> <skill|all> [-g|--global] [--dest <dir>] [--category <name>] [--dry-run] [--json]
```

Behavior:

- Project installs create generated runtime mirrors under the target agent skill directory.
- `--dry-run` returns the planned copy set without writing.
- `--global` and `--dest` are mutually exclusive.
- `--category` is valid only for Hermes global installs.

#### `speckiwi doctor`

```text
speckiwi doctor [--json]
```

Behavior:

- Checks package identity, CLI bin entrypoint, package-lock alignment, packaged Kiwi skill entrypoints, MCP metadata, MCP tool schemas, active target read, validation read, and dry-run mutation wiring.
- Exits with code `5` when any doctor check fails.

### 4.1 MCP Resource Payload Policy

v1.2.0 resources use an envelope-all payload policy. The domain-specific resource payload is always nested under `value`, and diagnostics are carried at the envelope level:

```json
{
  "ok": true,
  "value": {},
  "diagnostics": [],
  "diagnosticsSummary": { "errors": 0, "warnings": 0, "byCode": {} }
}
```

Compatibility note: `speckiwi://completed-work` had documented raw `{ completedWork }` behavior in v1.1.0-era requirements. During the v1.2.0 compatibility window, clients should treat `value.completedWork` as canonical and may support the raw shape only when talking to older v1.1.x servers.

### 7.1 Target Status and Diagnostic Governance

Target Map status values:

| Status | Meaning |
|---|---|
| `planned` | Target is defined but work has not started. |
| `active` | Target is the current work target. |
| `frozen` | Target scope is frozen and requires explicit review for meaningful changes. |
| `completed` | Target requirements are complete but not necessarily released as an immutable baseline. |
| `released` | Target passed release-readiness and is treated as an immutable baseline. |
| `archived` | Historical target that is generally not modified. |

v1.2.0 planned hardening requires a code-level diagnostic registry. Registry entries must include code, severity, title, message template, source rule, and since fields, and the rule document diagnostic table must be contract-tested against that registry.

`SRS-E001` through future diagnostic codes are governed by `src/core/diagnostic-registry.ts`; code emission through `diagnostic()` fails when a code is unknown or emitted with a severity that differs from the registry.

v1.2.0 planned hardening also requires index diagnostics for duplicate targets, duplicate scope prefixes, multiple active target rows, missing scope documents, unregistered scope SRS documents, Status Summary drift, and Requirement Type Summary drift.

v1.3.0 stability diagnostics extend the registry with `SRS-W022` for legacy `volatile`, `SRS-E033` for verified draft requirements, and `SRS-W023` for draft requirements in active or released targets. Unknown stability values continue to use `SRS-E011`.

v2.1.1 Completed Work Log report path diagnostics add `SRS-W024` for malformed lexical report path tokens. This warning does not make report paths verification evidence and does not check whether report files exist.

## 9. AGENTS.md / CLAUDE.md Addition

v1.2.0 planned hardening treats uppercase root `AGENTS.md` and `CLAUDE.md` as canonical agent instruction files. Init and MCP startup init must upsert the current managed block by versioned heading and suffix marker, preserving unrelated user content and replacing legacy or older SpecKiwi blocks. Lowercase `agents.md` is retained as a compatibility mirror only; new automation should read the uppercase canonical files first.

```md
# SpecKiwi SRS 워크플로 v1.4

This repository uses `docs/spec/` as the required source of truth for requirements.

Before making any code, test, CLI, MCP, or documentation change, agents MUST:
1. Read `docs/spec/00.index.md`.
2. Find the relevant Requirement ID in the scope SRS files.
3. Mention the Requirement ID in the work summary.
4. If no matching requirement exists, stop and ask whether to create/update an SRS requirement first.

Requirement metadata has two separate lifecycle fields:
- `Status` tracks implementation and verification progress.
- `Stability` tracks requirement maturity and change-control maturity.

Agents MUST stop before implementing a non-discarded requirement with `Stability=draft` or `Stability=deprecated` unless the user explicitly overrides that workflow.

TDD principle:
- Agents MUST follow TDD for behavior changes: write or update a failing automated test for the relevant Requirement ID before implementation, make the smallest change to pass, then refactor while keeping tests green.
- If no meaningful automated test can be written, agents MUST stop before implementation and explain the exception and alternative verification evidence.

Agents MUST NOT:
- Implement behavior that is not covered by an SRS requirement.
- Create an alternate requirements source outside `docs/spec/`.
- Change requirement IDs manually.
- Mark requirements as verified without evidence.
- Introduce or invoke bulk-archive / bulk-finalize tooling that flips multiple requirements to `verified` or empties Active Target without per-requirement evidence and stability gate checks.

When SpecKiwi MCP tools are available, agents MUST use them for requirement lookup and safe SRS updates. If MCP is unavailable, use the `speckiwi` CLI.

Current work status workflow:
1. Read the active target with MCP `get_active_target`, or CLI `speckiwi active-target --json` if MCP is unavailable.
2. If `activeTarget` is empty, report that no active target is set and ask which target to use before making target-scoped changes.
3. Read `summary.countsByStatus`, `summary.countsByStability`, `summary.stabilityBlockers`, `summary.stabilityWarnings`, and `summary.newWorkCandidates` before selecting work.
4. Read open work with MCP `list_requirements` for `status=in_progress`, `status=blocked`, and `status=implemented`; CLI fallback is `speckiwi list --status <status> --json`.
5. Check missing verification evidence through `summary` or MCP `summarize_target` before saying work is complete.
6. Read recent completed work with MCP `list_completed_work`; CLI fallback is `speckiwi completed-work --json`.

Next target authoring workflow:
1. If the user asks to set the next target, first read the current Active Target and Target Map.
2. If the target is not registered, use a supported target-registration mutation such as MCP `set_active_target` with creation support, or CLI `speckiwi set-active-target <target> --create` when that option is available.
3. If the configured MCP/CLI cannot register the target, stop before target-scoped SRS changes and report the tool gap, unless the user explicitly authorizes a minimal SRS-MD patch.
4. After target assignment, confirm the resolved Active Target with MCP `get_active_target`, or CLI `speckiwi active-target --json` if MCP is unavailable.
5. When the user provides a target goal, record it with MCP `set_target_goal`, or CLI `speckiwi set-target-goal <target> --goal <text>` if MCP is unavailable.
6. For later SRS creation, omit the target only when the tool supports Active Target defaulting; otherwise pass the confirmed Active Target explicitly.
7. If the user provides an explicit different target for a requirement, the explicit target wins over Active Target.

Completed Work Log is a read-only summary for agents. Requirement Block status, Acceptance Criteria, Verification Evidence, and Change Notes remain the source of truth for completion.

<!-- /SpecKiwi SRS 워크플로 -->
```
