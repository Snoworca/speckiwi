## 1. Scope Overview

이 문서는 SpecKiwi v1.0.0의 제품 경계, Markdown-only 원본성, local-first architecture, CLI와 MCP의 공통 core 구조를 정의한다.

## 2. Scope Boundaries

### In Scope

- Markdown SRS source of truth
- YAML 미사용 정책
- 별도 DB 없는 저장소 로컬 동작
- CLI와 MCP가 공유하는 core service
- 최소 변경과 안전한 mutation 원칙

### Out of Scope

- 구체적인 CLI 명령별 option semantics
- 구체적인 MCP tool input schema
- Node.js package file layout 세부 구현

## 3. Assumptions and Constraints

- 요구사항 원본은 Markdown 문서다.
- JSON 출력은 파생 결과다.
- Node.js package metadata는 `package.json`으로 관리할 수 있다.

## 4. Requirements

#### Requirement

SpecKiwi는 명령 실행 위치에서 상위 디렉터리로 탐색하여 Git 저장소 루트 또는 `docs/spec/00.index.md`가 있는 프로젝트 루트를 자동 탐지해야 한다.

#### Rationale

사용자는 매번 `--root`를 지정하지 않고도 저장소 내부 어디서든 명령을 실행할 수 있어야 한다.

#### Acceptance Criteria

- [x] AC-2: `--root`가 지정되면 자동 탐지보다 우선한다.
- [x] AC-3: 일반 CLI 조회/변경 명령은 루트를 찾지 못하면 exit code `2`와 명확한 오류 메시지를 출력한다.
- [x] AC-4: `speckiwi mcp`도 `--root`가 없으면 server process의 현재 작업 디렉터리에서 같은 root 탐지를 수행한다.
- [x] AC-5: MCP server startup에서는 루트를 찾지 못한 빈 작업 디렉터리를 현재 디렉터리 root로 간주하고 SRS 기본 구조를 자동 생성한다.
- [x] AC-6: MCP server startup에서 명시적 `--root`가 주어지면 해당 경로는 존재하는 디렉터리여야 하며, 존재하지 않는 경로를 자동 생성하지 않는다.

### FR-ARCH-005 — Mutation tool kind classification metadata

| Field | Value |
| --- | --- |
| Type | functional |
| Target | v2.2.2 |
| Status | verified |
| Priority | high |
| Tags | governance, mutation, policy |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |

#### Requirement

All SpecKiwi mutation tools (CLI and MCP) MUST declare a kind classification (req-scoped, log-append, or workspace) in their schema metadata. The kind drives id-arity enforcement: req-scoped tools accept exactly one Requirement ID and reject array inputs at the schema layer.

#### Rationale

Three-agent design review (architecture, governance, UX) on 2026-05-16 converged on replacing positive-form 'single-id' policy + exception list with a typed classification. This avoids endless exception negotiation when new mutations are added and lifts bulk-mutation prohibition from textual rule (CLAUDE.md / SRS-MD-Rules v1.1.0 §30.3) to schema-level enforcement.

#### Acceptance Criteria

- [x] AC-1: AC-1: every mutation tool registered in src/mcp/tools/mutation-tools.ts declares exactly one of kind in {req-scoped, log-append, workspace}.
- [x] AC-2: AC-2: req-scoped tools reject id input of array type at zod schema layer (USAGE error).
- [x] AC-3: AC-3: log-append tools may accept requirementIds: string[] but MUST NOT alter any Requirement Block status or stability fields.
- [x] AC-4: AC-4: workspace tools do not accept any Requirement ID field.
- [x] AC-5: AC-5: an automated test enumerates registered mutation tools and asserts each declares a kind.
- [x] AC-6: AC-6: SRS-MD-Rules v1.1.0 §30.3 Tool Compliance references this classification as the canonical enforcement mechanism.

#### Requirement

SpecKiwi v2.3.0 must define product-level authority boundaries for SRS Markdown, workflow artifacts, derived caches, and lock files so tool-improvement features do not create alternate requirements sources of truth or ambiguous operational state.

#### Rationale

The 10-axis SRS usefulness review found that v2.3.0 introduces workflow JSONL, derived status cache, and lock files but the architecture scope still only describes the v1.0.0 Markdown/core boundary.

#### Acceptance Criteria

- [x] AC-1: docs/spec Markdown remains the only canonical requirements source; workflow artifacts such as plans, pipeline JSONL, sessions, PM state, coder state, and worklogs are operational inputs or audit artifacts, not canonical Requirement Blocks.
- [x] AC-2: kiwi/.status.json is treated only as a disposable derived cache; missing, stale, or corrupt cache content triggers canonical parsing fallback and visible diagnostics or regeneration metadata.
- [x] AC-3: kiwi/.srs.lock or the documented successor lock file is the authoritative SRS mutation exclusion mechanism; deleting or regenerating derived cache files never releases an active lock.
- [x] AC-4: CLI, MCP, and skill-facing workflow projections report artifact source kind, path, workspace root, and hash or mtime when combining SRS and workflow state.
- [x] AC-5: Tests or inspection cover no alternate requirements source creation, cache corruption fallback, lock/cache separation, and workspace-boundary behavior for mixed SRS and workflow artifact reads.

### REL-ARCH-003 — The MCP surface contract is checked against the instantiated server, not against the registry

| Field | Value |
| --- | --- |
| Type | reliability |
| Target | v2.5.1 |
| Status | verified |
| Priority | high |
| Tags | mcp, release-contract, parity |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | docs/next/2026-07-30.numbering-and-2.5.0-residuals.md |

#### Requirement

The release contract for the MCP surface shall compare the ToolSpec registry's declared MCP tool names against the tools an instantiated server actually registers, in both directions. A registry entry naming a tool the server does not register, and a server tool absent from the registry, shall each fail the contract.

#### Rationale

Declaring `mcpName: "upgrade_project"` on a CLI-only registry entry — a tool no server registers — left every existing parity test passing, because the schema map those tests compare against is itself derived from the registry. The registry was therefore checked against itself, and only a requirement's own hand-written assertion caught the fabrication. A contract that cannot fail on a fabricated name is not a contract. Found on 2026-07-30 by the independent per-AC audit of `IR-CLI-076`, which enumerated the live server to establish the CLI-only claim.

#### Acceptance Criteria

- [x] AC-1: Every MCP name the registry declares is present among the tools an instantiated server registers.
- [x] AC-2: Every tool an instantiated server registers, excluding resource handlers, is declared by exactly one registry entry.
- [x] AC-3: A registry entry that declares a tool name the server does not register fails the contract, demonstrated by constructing that state rather than asserting it abstractly.
- [x] AC-4: The comparison reads the instantiated server rather than any registry-derived projection, so it cannot be satisfied by the registry agreeing with itself.
