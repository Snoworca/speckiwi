## 1. 작업 목적

이 계획은 CLI와 MCP 구현이 SRS와 맞지 않는 항목을 닫기 위한 구현 계획이다. 목표는 테스트가 통과하는 현재 상태를 유지하면서, SRS가 요구하는 출력 payload, option 계약, exit code, structured error, patch summary, root boundary, cross-platform 검증 증거를 코드와 테스트로 맞추는 것이다.

작업 완료 후에는 CLI와 MCP 관련 SRS 항목의 주요 미충족 finding이 재현 테스트로 닫혀야 한다.

## 3. 프로젝트 온보딩 컨텍스트

SpecKiwi는 `docs/spec` Markdown SRS를 source of truth로 쓰는 Node.js TypeScript CLI와 stdio MCP server다. 이 계획은 새 기능을 늘리는 작업이 아니라 이미 verified로 표기된 CLI/MCP SRS 항목이 실제 코드와 맞지 않는 gap을 닫는 remediation 작업이다.

주요 디렉토리 맵:

| Path | Role |
|---|---|
| `src/core/fs/` | root boundary, UTF-8 file read, path normalization |
| `src/core/parser/` | SRS discovery and Markdown parsing |
| `src/core/query/` | list, get, summary, link checks |
| `src/core/mutation/` | status, AC, evidence, trace, add-requirement mutation services |
| `src/cli/` | Commander based CLI entrypoint and command registration |
| `src/mcp/` | MCP test adapter, SDK server bridge, tools, resources, structured error mapping |
| `test/cli/` | CLI adapter tests |
| `test/mcp/` | MCP tool/resource/stdio tests |
| `test/core/` | core service unit tests |
| `test/integration/` | generated workspace integration tests |

핵심 규칙:

- 모든 파일 읽기와 쓰기는 UTF-8로 수행한다.
- SRS 문서 수정은 관련 Requirement Block의 evidence와 Change Notes만 대상으로 한다.
- CLI와 MCP는 core service를 공유해야 한다.
- SRS와 다른 option 이름을 추가 호환 alias 없이 교체하면 기존 테스트가 깨질 수 있으므로, 기존 이름을 유지하고 SRS 이름을 추가 지원한다.
- structured error code는 MCP outward contract에서 SRS lower-case taxonomy로 정규화한다.
- root boundary는 symlink realpath 기준으로 닫는다.

빌드와 테스트 치트시트:

| Purpose | Command |
|---|---|
| Build | `npm run build` |
| Typecheck | `npm run typecheck` |
| Lint | `npm run lint` |
| CLI/MCP suite | `npm run test:integration` |
| Release SRS trace | `npm run release:acceptance` |
| Full test | `npm test` |

도움 요청 경로: SRS 해석이 막히면 `docs/spec/30.cli-interface.srs.md`와 `docs/spec/40.mcp-stdio-interface.srs.md`의 Requirement Block을 우선한다. 구현 계약이 모호하면 core service는 공통 계약, CLI/MCP adapter는 표면 계약으로 분리해서 판단한다.

## 9. TDD 수행 원칙

각 TASK는 Red 단계에서 해당 SRS gap을 재현하는 실패 테스트를 먼저 추가한다. Green 단계는 production code를 최소 변경으로 수정한다. Refactor 단계는 CLI/MCP adapters가 core service를 공유하도록 중복을 줄인다. 모든 Phase 완료 전에는 SRS evidence를 수정하지 않는다. 각 TASK 표의 `TDD order`가 TASK별 Red/Green/Refactor 완료 조건이다.

## 10. 계획 리뷰 절차

계획 리뷰어는 다음을 확인한다.

| Reviewer | Required Checks |
|---|---|

| Security Reviewer | root boundary, symlink, structured error remediation이 측정 가능한 테스트로 닫히는지 확인한다. |
| Junior Determinism Reviewer | TASK 필수 필드, source_anchors, acceptance_tests, rollback, 금지 표현을 확인한다. |

CRITICAL 또는 HIGH finding이 있으면 계획 파일과 sidecar를 수정한 뒤 다시 리뷰한다.

## 11. 코드 리뷰 절차

구현 후 리뷰어는 다음을 확인한다.

- Red 실패 테스트가 SRS gap을 직접 재현했는가.
- CLI와 MCP가 SRS option 이름을 지원하면서 기존 호환 옵션을 깨뜨리지 않는가.
- MCP outward structured error code가 lower-case SRS taxonomy인지 확인한다.
- mutation response에 record, diagnostics, patch summary가 보존되는가.
- symlink root escape 테스트가 read와 write 모두를 막는가.
- SRS evidence가 실제 실행한 테스트 명령만 참조하는가.

## 12. 완료 기준

- P1~P4의 모든 acceptance_tests가 통과한다.
- `npm run build`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:integration`, `npm run release:acceptance`가 PowerShell에서 통과한다.
- POSIX runtime에 설치된 dependency 환경에서 같은 gate가 통과한다.
- 미충족으로 식별된 CLI/MCP SRS ID가 테스트와 구현으로 닫힌다.
- 관련 SRS Requirement Block에 새 verification evidence가 추가된다.

## 13. 용어집

| Term | Meaning |
|---|---|
| structured error taxonomy | MCP tool이 반환하는 domain error code 체계다. 이 계획은 lower-case SRS code를 outward contract로 둔다. |
| patch summary | mutation이 어떤 파일에 몇 개 operation을 적용했는지 설명하는 `PatchSummary`다. |
| root boundary | project root 밖 파일 read/write를 금지하는 filesystem security boundary다. |
| symlink escape | root 내부 path가 symbolic link를 통해 root 밖 realpath로 이어지는 보안 결함이다. |
| summary payload | target별 status/type/blocked/evidence 목록을 담는 CLI/MCP 공통 summary output이다. |
| compatibility alias | 기존 사용자 입력을 깨뜨리지 않기 위해 SRS 이름과 함께 유지하는 option alias다. |
