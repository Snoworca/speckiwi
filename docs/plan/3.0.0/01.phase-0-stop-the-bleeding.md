## P0-1 — 루프 쓰기 범위 게이트

### 문제

개선 루프를 도는 세 스킬 중 **어느 것도 무엇을 고쳐도 되는지 말하지 않는다.**

| 스킬 | 쓰기 범위 선언 | `docs/research` 언급 |
|---|---|---|
| `kiwi-review-fix-loop` | 0 | 0 |
| `kiwi-coder` | 0 | 0 |
| `kiwi-hot-fix` | 0 | 0 |

그 결과 최근 40커밋 중 16개가 `docs/research`·`docs/next` 를 건드렸고, 6개는 SRS·코드 수정에 딸려 들어갔다(`1b593ef`, `5596732`, `d751220`, `2bc44c9`, `c5b148b`, `0121f9c`).

게이트 어휘는 이미 있는데 발화 지점이 오케스트레이터 lane 에만 있다.

| 게이트 | 발화 지점 |
|---|---|
| `non-code-write-set-refused` | `src/core/orchestrator/lane-plan.ts` |
| `lane-write-set-touches-srs` | `src/core/orchestrator/worktree-topology.ts` |
| `unknown-write-set-refused` | **어디에서도 발화하지 않음** |

### 왜 이것이 낭비인가

`CLAUDE.md` 의 검증 강도 정책이 **"연구 문서에는 LLM 검토를 아예 돌리지 않는다"**고 못박는다. 검토하지 않기로 한 문서를 개선 루프가 고치고 있다. 그 문서의 주장은 요구로 승격될 때 코드와 재대조되므로, 산문을 다듬는 비용은 회수되지 않는다.

### 할 일

1. 허용 경로를 스킬 셋에 명시한다. 기본 허용은 `src/**` · `test/**` · `docs/spec/**` · 계획 사이드카.
2. `docs/research/**` · `docs/next/**` · `docs/plan/**` 은 **사용자가 명시적으로 지시했을 때만** 연다.
3. `unknown-write-set-refused` 를 lane 밖에서도 발화시킨다. 지금 이 게이트는 어휘에만 있고 호출자가 0이다.

### 틀렸을 때 무엇이 깨지는가

허용 목록을 너무 좁게 잡으면 정당한 수정이 막히고, 막히면 우회 경로가 생긴다. **차단이 아니라 거부 후 사유 보고**로 만든다. 사용자가 지시하면 열리는 문이어야 한다.

### 검증

입력이 무엇인지 지정한다. 지정하지 않으면 실행자마다 다르게 판정한다 — 스킬에 주는 자연어인지 게이트 함수의 인자인지가 갈린다.

- **게이트 함수에 write-set 배열을 직접 넣는 단위 테스트.** `["docs/research/26.md"]` 는 거부되고 사유가 실린다. `["src/core/x.ts"]` 는 통과한다.
- **명시적 지시 플래그가 켜지면 같은 배열이 통과한다.**
- **미러 체크로 산문 쪽을 기계화한다** — 세 스킬이 선언한 허용 경로 목록이 게이트 상수와 일치한다. 산문에 적어 두는 것만으로는 준수를 단언할 수 없으므로, 목록 자체를 상수에서 파생시킨다.
- 게이트 어휘에서 그 id 를 지우면 테스트가 red 가 된다(뮤테이션).

## P0-2 — `search` 가 플래그를 찾지 못하는 결함

### 문제

```
$ node bin/speckiwi search "--force"
error: unknown option '--force'  (Did you mean --format?)
```

매처 문제가 아니라 commander 가 질의를 옵션으로 파싱하는 것이다. 명세에 `--force` 가 여러 번 등장하며, **하필 요구 인덱스를 무증상으로 파괴하는 `init --force` 가 그중 하나다.**

### 초판이 이 자리에 적은 두 번째 재현은 거짓이었다

초판은 *"표준 탈출 수단인 `--` 도 듣지 않는다"*고 적고 `too many arguments ... got 2` 를 인용했다. **`--` 는 두 셸 모두에서 정상 동작한다.**

```
$ node bin/speckiwi search -- "--force"     → 요구 7건, 스니펫 실물
$ node bin/speckiwi search -- "--zzzznotareal"  → 0건       (대조군)
```

인용된 오류는 도구 결함이 아니라 **측정 방법의 산물**이었다. PowerShell 의 `--%` 정지 파싱 토큰이 줄 나머지를 전부 인자로 삼켜 `2>&1` 까지 argv 에 실렸고, `--` 뒤 피연산자가 둘이 되어 나온 오류다.

```
node argvdump.js --% search -- --force 2>&1 | Select-Object -First 3
  → ["search","--","--force","2>&1"]      ← "got 2" 의 정체
```

**연구 26 §7.1 의 2·3번과 같은 계열이다.** 그때는 셸이 이스케이프를 깨뜨려 *아무것도 매치하지 않은 채* 결과를 냈고, 여기서는 셸 토큰이 인자를 *덧붙여* 없는 결함을 만들었다. 방향만 반대이고 원인은 같다 — **셸을 거친 인자를 실측으로 확인하지 않았다.**

그러므로 이 항목의 심각도는 내려간다. 에이전트에게 동작하는 경로가 이미 있다. 그래도 고치는 이유는, 에이전트가 자연히 치는 형태가 맨 형태이기 때문이다.

### 할 일

CLI 진입에서 질의를 옵션 파싱 대상에서 빼거나, `--` 이후를 질의로 받도록 고친다. 구현 위치는 `search` 명령 등록부이고, 매처(`src/core/query/discovery.ts:161`)는 건드리지 않는다.

### 틀렸을 때

P2-2 의 워크플로 문안이 "식별자마다 검색하라"고 지시하는데 **플래그를 검색할 수 없으면 그 지시가 절반만 작동한다.** 그래서 Phase 2 의 선행이다.

### 이 항목에서 뺀 것

초판은 `orchestrator-run.lock` 의 0 히트도 같은 결함으로 묶었다. **검토에서 측정한 결과 결함이 아니다** — 명세에 그 리터럴이 0회 출현한다(`src` 에서 1개 파일이 경로를 조립할 뿐이다). 찾을 것이 없었던 것이지 검색이 깨진 것이 아니다.

### 검증

- **`search "--force"` 의 결과가 `search -- "--force"` 의 결과와 같다.** 이미 동작하는 경로가 기준값이므로 별도 수치를 적지 않는다.
- 존재하지 않는 플래그 질의는 0건을 낸다(대조군).
- MCP `search_requirements` 경로는 JSON 인자를 받으므로 영향이 없어야 한다. 그것도 확인한다.

> ⚠️ **초판은 여기에 "24회 등장을 반영한 히트를 낸다"고 적었다. 두 가지가 틀렸다.**
> 첫째, **단위가 다르다.** 24는 명세 전체의 리터럴 출현 수이고 검색이 내는 것은 요구 7건이므로, "24회 히트"는 어떤 올바른 구현으로도 나오지 않는다.
> 둘째, **개수 리터럴을 게이트에 박는 것은 이 계획 §0 규칙 1 위반이며 P0-3 이 없애려는 결함 형태 그 자체다.** 다음 요구가 `--force` 를 한 번 언급하는 순간 조건이 거짓이 되는데 깨진 것은 아무것도 없다. `"9 passed"` 사고(`00.index.md` §0)와 같은 모양이다.

## P0-3 — AC 리터럴 대 배포 상수 대조 검사

### 문제

이것이 **v3.0.0 의 최우선 항목**이다. 연구 27 §3.6 이 근거다.

이력 24건 중 (가)12 + (다)의 노후화 3 = **15건**, 그리고 지금 살아 있는 모순 후보 4건이 **전부** 같은 형태다. **AC 가 문자열·경로·버전·개수를 직접 못박고 SSOT 에서 파생하지 않는다.** 그 값을 바꾸는 후속 요구가 착지해도 옛 AC 는 `[x]` 인 채 남는다.

### 선례가 둘 있고 둘 다 효과가 기록되어 있다

- `IR-CLI-082` AC-4 를 상수 `ORCHESTRATE_DEFERRED_VERB_ROWS` 에서 파생시켰다. Change Note: *"so it cannot go stale the way it just did"*
- `FR-NODE-051` 의 버전 스냅샷 리터럴을 배포 상수 참조로 교체했다(`docs/next/2026-07-29.rules-2.5.0-and-open-residuals.md` §3.5)

**그 수리가 나머지에 적용되지 않았고 C1~C4 가 그 대가다.**

### 할 일

**첫 단계는 레지스트리 신설이다. 초판은 이것을 할 일에 넣지 않았다.**

검토에서 확인한 사실이다 — `src/core/bootstrap/templates.ts` 에는 레지스트리가 **없다.** 대조 대상이 개별 `export const` 로 흩어져 있다. 실측하면 그 파일의 `export const` 는 12개이고 그중 문자열 값은 10개이며, **둘은 템플릿 리터럴**(`BUNDLED_SRS_RULES_FILENAME` · `BUNDLED_SDS_RULES_FILENAME`)이라 정적 파싱형 구현이 놓치기 쉽다. **하필 그 둘이 C2a 의 대조 대상이다.** 저장소의 실제 레지스트리는 `src/core/diagnostic-registry.ts` 의 `DIAGNOSTIC_DEFINITIONS` 하나뿐이다. **레지스트리를 먼저 만들지 않으면 어떻게 구현해도 결국 하드코딩이 되고, 게이트 조건 5 가 자동 실패한다.**

1. `templates.ts` 의 대조 대상 상수를 `DIAGNOSTIC_DEFINITIONS` 형태의 레지스트리로 승격한다.
2. 각 항목에 **`current` / `legacy` 역할 필드**를 둔다. 이름이 `LEGACY_` 로 시작하는 export 는 `legacy` 다.
3. AC 텍스트에서 그 종류의 리터럴을 뽑아 레지스트리와 대조하는 진단을 신설한다.
4. **그 진단을 `DIAGNOSTIC_DEFINITIONS` 에 등록하고 `validateWorkspace()` 와 `validateWorkspaceScoped()` 안에서 내보낸다. severity 는 `warning` 이상이다.**

**4번을 빠뜨리면 나머지가 전부 무의미하다.** 검사가 테스트에서만 불리면 도구는 자기를 검사하지 않고 에이전트는 이 진단을 마주치지 않는다. 이 저장소는 **순수 커널에 호출자가 0이라 게이트 셋이 발화하지 못한 사건**을 이미 겪었고, 소스 스캔 두 개가 green 을 유지하는 동안 배선 테스트만 배포 결함을 잡아낸 사건도 겪었다.

**발화 지점을 `validateWorkspace()` 로 못박는 이유가 있다.** 이 저장소에는 `readDiagnostics` 가 세 벌 있다.

```
src/cli/commands/read.ts:86       [...workspace.diagnostics, ...validateWorkspace(workspace).diagnostics]
src/mcp/resources.ts:26           동일
src/mcp/tools/read-tools.ts:100   동일
```

셋 다 같은 한 줄이므로 **그 함수 안에서 내면 세 채널이 함께 따라온다.** 다만 `--step` 경로와 MCP `validate_step` 은 `validateWorkspaceScoped()` 를 타므로 **네 번째 채널이며 따라오지 않는다.** 그래서 두 함수 모두에 넣는다. 반대로 "validate 경로에 배선한다"고만 하면 CLI 한 벌만 배선해도 문면이 충족되고, **`CLAUDE.md` 가 우선하라고 지시하는 MCP 경로는 비어 있게 된다.** 세 채널 각각에서 진단이 나오는 것을 확인하고, `validateWorkspace` 에서 떼면 셋 다 red 가 되는 테스트를 둔다.


**severity 를 `warning` 이상으로 못박는 이유가 있다.**

```
DiagnosticSeverity = "error" | "warning" | "info"
splitDiagnostics   → errors(error) · warnings(warning) 만 담는다
validate 종료코드  → errors.length > 0 || (failOnWarning && warnings.length > 0)
```

`info` 로 내면 네 채널 전부에서 발화하면서도 `validate --fail-on-warning` 이 **errors 0 warnings 0 을 유지한다.** 배선을 다 해 놓고도 도구가 아무것도 막지 못하는 상태가 된다. `diagnostic()` 이 등록값과 다른 severity 를 이미 거부하므로, `DIAGNOSTIC_DEFINITIONS` 에 `warning` 이상으로 등록하는 것만으로 집행된다.

| SSOT 종류 | 대조 대상 |
|---|---|
| 에이전트 안내 버전·heading·end marker | `AGENT_INSTRUCTION_VERSION`, `AGENT_INSTRUCTION_HEADING_PREFIX`, `AGENT_INSTRUCTION_END_MARKER` |
| 번들 규칙 파일명·버전 | `BUNDLED_SRS_RULES_FILENAME`, `BUNDLED_SDS_RULES_FILENAME`, `BUNDLED_RULES_VERSION`, `BUNDLED_SDS_RULES_VERSION` |
| 진단 코드 | `DIAGNOSTIC_DEFINITIONS` |
| **증거 참조 해석 범위** | P0-5 (3) 이 위임하는 자리. target 스코프를 벗어난 verified 요구도 대상에 든다 |

**C4 는 이 표에 없다.** 초판 개정 과정에서 `.agents/skills/**` 미러와 대조하면 잡힌다고 넣었다가 뺐다 — AC 가 지목하는 것은 `~/.claude/skills/` 홈 설치본이며 저장소 미러가 아니다. 자세한 것은 `00.index.md` §4.1 의 구분표에 있다.

진단 코드 대조는 **이미 존재하되 분모가 좁다.** `FR-NODE-087` AC-9(`test/core/bootstrap/bundled-rules-completeness.fr-node-087.test.ts:196-204`)가 `loadBundledRulesDocument()` 하나만 읽는다. **`docs/spec/**` 까지 확장하는 것이 이 항목의 절반이다.**

### 그 분모가 좁다는 실물이 P0-5 에서 나왔다

`FR-PARSE-038` 을 구현하며 확인한 것이다. 번들 규칙 문서 §15 의 정본 표는 **처음부터 옳았다** — Priority·Risk·Stability 의 값 집합이 코드의 상수와 일치한다. 틀린 것은 코드 쪽 remediation 셋이었다.

**그런데 어느 완성도 테스트도 그것을 보지 못했다.** `FR-NODE-087` AC-9 와 `FR-NODE-086` 의 짝은 둘 다 **진단 코드 집합만** 대조하고 remediation 본문은 대조하지 않는다. 그래서 도구가 문서와 어긋난 값을 에이전트에게 안내하는 동안 두 검사가 계속 green 이었다.

**분모가 좁다는 것이 추상적 위험이 아니다.** 같은 파일을 읽는 검사가 이미 둘 있었는데도 드리프트가 보이지 않았고, 그것을 잡은 것은 **집합으로 쓴 완성도 조건 하나**였다. `00.index.md` §4.1 조건 5 가 요구하는 형태다.

### `legacy` 를 구분하지 않으면 검사가 C1 을 놓친다

```
templates.ts:124   AGENT_INSTRUCTION_HEADING_PREFIX     = "# SpecKiwi SRS workflow v"
templates.ts:129   LEGACY_KOREAN_AGENT_HEADING_PREFIX   = "# SpecKiwi SRS 워크플로 v"
```

둘이 나란히, 같은 `@req FR-NODE-086` 아래 있다. 레거시 쌍은 지울 수 없다 — `init` 이 옛 버전이 심은 블록을 찾아 제자리에서 교체하려면 그 리터럴이 필요하다.

그러므로 모듈의 문자열 export 를 통째로 훑으면 **C1 이 문제 삼는 바로 그 한글 heading 이 "배포 상수와 일치"로 판정되어 조용히 통과한다.** 레지스트리에서 `legacy` 로 표시된 값과 일치하는 AC 리터럴은 통과가 아니라 **발화**여야 한다.

### 파생만으로는 부족하다 — 완성도 테스트를 함께 둔다

P2-3 이 용어집을 추가하며 **세 번째 번들 상수를 만든다.** 레지스트리가 있어도 P2-3 구현자가 등록을 빠뜨리면 결과는 하드코딩과 같다. 문제가 한 층 위로 옮겨갈 뿐이다.

그래서 완성도 테스트를 함께 둔다. **분모는 `templates.ts` 하나가 아니라 `src/core/bootstrap/**` 전체**이며, 값의 종류(평문 문자열 · 템플릿 리터럴 · 정규식)를 가리지 않는다. 분모를 한 파일로 좁히면 P2-3 이 용어집 상수를 다른 파일에 두는 순간 조용히 빠져나간다. 선례가 `FR-NODE-087` AC-9 이고, **그 선례가 분모를 좁게 잡아 실패한 사례이기도 하다.**

이것이 `00.index.md` §4.1 게이트 조건 5 이며, **`P0-3 → P2-3` 의존을 함께 닫는다.**

### C2b · C3 · C4 는 이 항목의 대상이 아니다

**리터럴 대조 검사는 리터럴이 틀린 것만 잡는다. 진술의 범위가 틀린 것은 잡지 못한다.** 살아 있는 모순 넷을 그 기준으로 가른 표가 `00.index.md` §4.1 에 있다. 이 항목이 지는 것은 **C1 과 C2a** 둘뿐이다.

빠지는 셋은 이렇다.

- **C2b** — `FR-NODE-009` AC-9 와 `FR-MCP-011` AC-11 이 *"force 없이 기존 파일을 덮어쓰지 않는다"*고 무한정으로 적었다. `FR-NODE-085` 가 규칙 문서에 한해 뒤집었는데 **두 요구 어디에도 supersede 기록이 없다.** 틀린 리터럴이 없으므로 대조할 것이 없다.
- **C3** — `--mini` 를 둘러싼 수량자 충돌이고 **`--mini` 는 `src/**` 에 0회 출현한다**(실측).
- **C4** — AC 가 `~/.claude/skills/` 홈 설치본의 상태를 주장한다. **저장소 밖 환경이므로 대조할 대상이 실재하지 않으며**, 증거 셀이 *"NO INSTALLED COPY EXISTS"* 라고 이미 자백하고 있다.

셋 다 `P1-2` · `P1-3` · `P1-4` 가 손으로 닫고 Phase 1 게이트가 각 절의 검증으로 판정한다.

> **이 구분이 게이트의 핵심이다.** 초판 게이트도 2판 게이트도 "C1~C4 전부"라고 적어 **검사가 도달할 수 없는 것을 요구했다.** 같은 실수를 세 번째로 하지 않으려면, 새 모순을 이 게이트에 넣기 전에 **대조할 SSOT 가 실재하는지 먼저 실행으로 확인한다.**

### 틀렸을 때

검사가 너무 넓으면 정당한 역사 기술(Change Notes 의 옛 버전 언급)까지 잡는다. **대상은 Acceptance Criteria · Requirement 본문 · 참조 샘플 블록이고, Change Notes·Implementation Notes 는 제외한다.**

### 범위를 "요구 블록 안"으로 그으면 놓치는 자리가 있다

초판은 대상을 "Acceptance Criteria 와 Requirement 본문"으로만 적었다. 실측에서 **요구 블록 밖에 있으면서 이력도 아닌 자리**가 나왔다.

`docs/spec/90.appendix.md` §9 는 제목이 "AGENTS.md / CLAUDE.md Addition" 이고, 에이전트가 써 넣어야 할 블록을 본문에 그대로 보여 준다. 그 샘플이 **한글 heading `v1.6`** 이고 배포 상수는 영문 `v1.9` 다.

**이것은 Change Notes 와 성격이 정반대다.** Change Notes 의 옛 버전 언급은 "그때 그랬다"는 기술이므로 낡아도 옳다. 참조 샘플은 "지금 이렇게 쓰라"는 지시이므로 **낡으면 그대로 틀린다.** 그리고 사람은 읽지 않고 에이전트가 복사한다.

제외 기준을 위치가 아니라 **성격**으로 긋는다 — *과거를 기술하는 절은 제외하고, 현재를 지시하는 절은 포함한다.*

**판정에 쓸 수 있는 사실:** C1 이 걸린 요구는 **7건**이고(`IR-CLI-003` · `FR-MCP-011` · `FR-NODE-009` · `FR-FLOW-005` · `FR-NODE-075` · `FR-NODE-077` · `FR-FLOW-016`), 여기에 이 부록 샘플이 더해진다.

> ⚠️ **`FR-FLOW-016` 을 음성 대조군으로 적었던 자리가 있었고 틀렸다.** 잘린 출력에서 *"the current versioned heading"* 만 보고 파생 형태라고 판단했는데, 원문은 **`the current versioned heading (`# SpecKiwi SRS 워크플로 v1.4`)`** 로 파생 문구 옆에 리터럴을 괄호로 달고 있다. **파생 문구가 있다는 것이 리터럴이 없다는 뜻이 아니다.** 검사는 파생 문구와 리터럴이 같은 문장에 공존하는 경우를 잡아야 하며, 이것이 음성 대조군을 고를 때 특히 조심할 형태다.

### 검증 — `00.index.md` §4.1 의 6조건

**게이트 본문은 `00.index.md` §4.1 이 정본이다.** 조건을 여기 복제하지 않는다 — 두 곳에 적으면 한쪽만 고쳐진다.

착수할 때 순서만 옮겨 둔다.

1. 레지스트리를 만들고 검사를 구현한 뒤, **`validate` 에 배선한다.**
2. C1 과 C2a 의 기대 페이로드를 **열거 스크립트로 뽑아 별도 파일로 동결**한다. **자리 수를 손으로 세지 않는다** — 초판은 "최소 10"이라고 적었는데 실측 재고가 그보다 크게 많았고, 모자란 재고가 그대로 합격 기준이 될 뻔했다.
3. 검사 코드 · 레지스트리 · 기대 페이로드 · 픽스처를 **한 커밋으로 동결**한다.
4. 그다음에야 분리된 서브에이전트에게 심기를 맡긴다.

**3번이 4번보다 먼저다.** 순서가 바뀌면 심은 것을 본 뒤 레지스트리에 흡수할 수 있게 되어, 조건 4 가 재려는 것이 사라진다.

> 왜 이렇게까지 하는가. 초판 게이트("C1~C4 발화")는 답이 계획서에 적혀 있어 하드코딩으로 통과했다. 2판 3조건과 3판 4조건은 독립 검토가 각각 무너뜨렸다 — 무너진 방식 일곱을 `00.index.md` §4.1 에 기록했다. **이 검사는 저장소가 반복해 밟은 결함을 잡으려는 것이므로, 그 결함을 검사 자신이 밟으면 아무것도 남지 않는다.** 특히 3판에서 드러난 것 — 배선 없는 순수 함수 — 은 이 저장소가 이미 겪은 사고 형태다.

## P0-5 — 에이전트가 따르면 틀리는 안내 수리

출처: 연구 25. 초판이 이 문서를 반영하지 않았다.

### 왜 Phase 0 인가

전제가 이것을 승격시킨다. **사람은 도구 출력을 읽지 않는다. 에이전트가 읽고 그대로 따른다.** 사람이라면 이상하다고 느끼고 다른 데를 볼 안내를, 에이전트는 실행한다. UX 결함이 아니라 정확성 결함이다.

### (1) `explain` 이 존재하지 않는 enum 을 안내한다

실행으로 확인했다.

```
$ node bin/speckiwi explain SRS-E006
remediation: Set Priority to a supported value (P0, P1, P2, P3).
```

코드의 실제 정의는 `src/core/types.ts:24` 의 `PRIORITY_LEVELS = ["critical","high","medium","low","optional"]` 이다. **겹치는 값이 0개다.** 안내를 그대로 따르면 오류가 재현된다.

**결함은 3건이다.** 이 자리를 두 번 정정했고 두 번 다 모자랐다 — 자세한 것은 아래 상자에 있다.

| 진단 | 도구가 안내하는 값 | 코드의 실제 정의 | 판정 |
|---|---|---|---|
| `SRS-E005` Status | `draft, …` | `REQUIREMENT_STATUSES` — 첫 값이 **`planned`** | **첫 값 불일치** |
| `SRS-E006` Priority | `P0, P1, P2, P3` | `PRIORITY_LEVELS` | **교집합 0** |
| `SRS-E007` Risk | `low, medium, high` | `RISK_LEVELS` — **`critical` 포함** | **누락 1** |
| `SRS-E011` Stability | 다섯 값 | `STABILITY_LEVELS` | 일치 |

`SRS-E011` 이 레거시 값을 뺀 것도 옳다. 그것은 `LEGACY_STABILITY_LEVELS` 로 분리되어 있어 "supported" 목록에 들어가면 안 된다.

셋의 실패 방식이 서로 다르다.

- **`SRS-E005` 와 `SRS-E006`** 은 안내를 따르면 **같은 진단이 다시 발화한다.** 에이전트가 그 자리에 갇힌다. `SRS-E005` 가 권하는 `draft` 는 하필 **Stability 값**이다.
- **`SRS-E007`** 은 안내를 따르면 **성공한다.** 다만 유효한 값 하나가 영영 선택지에서 빠지고, 명세에 `Risk: critical` 인 요구가 실재하므로 에이전트가 그것을 "고치면" 위험도가 강등된다. **진단은 끝까지 침묵한다.** 이쪽이 더 나쁘다.

> ⚠️ **이 자리를 두 번 정정했고 두 번 다 모자랐다.**
> 초판은 연구 25 를 받아 "3건 중 나머지 둘을 찾아 고친다"고 적었다. 전수 대조라며 다시 세어 "결함은 2건"으로 고쳤다. **둘 다 틀렸다 — 결함은 3건이다.**
>
> 원인은 실사 스크립트였다. `remediation:` 과 문자열이 **같은 줄에 있어야** 잡도록 짜여 있었는데 `SRS-E005` 만 두 줄에 걸쳐 있었다. **이 계획이 내내 지적해 온 것과 같은 계열의 누락을 실사 자신이 저질렀다.**
>
> **세 번째를 잡은 것은 검토 라운드가 아니라 테스트다.** AC-4 를 "값을 나열하는 remediation 중 파생에서 빠진 것이 0건"으로 쓰고 구현하자, 그 자리에서 `SRS-E005` 를 지목했다. **완성도 조건을 개수가 아니라 집합으로 쓰면 만든 쪽이 못 본 것도 잡힌다** — `00.index.md` §4.1 조건 5 가 같은 원리다.

설명이 아예 없다. 이 저장소가 실행 금지 1순위로 걸어 둔, `docs/spec/00.index.md` 를 템플릿으로 덮어써 요구 인덱스를 **무증상으로 파괴**하는 플래그다. 에이전트가 `--help` 를 읽고 안전하다고 판단할 근거가 그대로 있다.

### (4) 소스에 남은 NUL 리터럴

연구 25 가 5줄로 보고했고 전수 조사로 확인했다.

```
src/core/orchestrator/conflict.ts:290          src/core/parser/workspace-parser.ts:18
src/core/orchestrator/handoff.ts:493           test/core/mutation/fr-node-039-trace-hook.test.ts:341
src/core/orchestrator/resume.ts:305
```

인과를 실행으로 확정했다. **절단이 아니라 파일 단위 억제이고, 재귀일 때만 조용하다.**

```
rg -l "priorPostmortemDigests" resume.ts   → 찾는다, exit 0        (파일을 명시하면)
rg -l "priorPostmortemDigests" src/        → 0건,   exit 1        (재귀 — 알림이 없다)
rg -l --text "priorPostmortemDigests" src/ → 찾는다
rg --files src/                             → 170개 전부 나열       (순회에서 빠지지는 않는다)
```

파일을 명시하면 `rg` 가 `binary file matches (found "\0" byte around offset ...)` 라는 알림을 내며 매치 줄만 감춘다. `-c` 는 개수를 그대로 낸다. **그러나 재귀 검색에서는 알림도 없이 결과에서 통째로 빠진다.**

**알아채기 어려운 이유가 바로 그 비대칭이다.** 파일을 직접 지목해 확인하면 멀쩡히 나오므로, 재귀 검색이 0건을 낸 것을 "없구나"로 읽게 된다. 이 계획의 공통 제약이 그것 때문에 존재한다.

> ⚠️ **초판은 이 자리에 "NUL 을 만나는 지점까지만 읽고 자른다"고 적고 두 명령의 출력을 맞바꿔 인용했다.** `binary file matches` 는 `rg -n` 이 낸 것이지 `rg --files-with-matches` 가 낸 것이 아니었고, `priorPostmortemDigests` 는 `resume.ts` 의 52·77·305행에 있어 **NUL 이전에도 존재**하므로 "NUL 이후라 사라진다"는 설명이 성립하지 않았다. **출력을 붙여 놓고 어느 명령이 낸 것인지 확인하지 않은 결과다.**

> ✅ **닫혔다.** `NFR-NODE-001` 로 다섯 소스의 아홉 자를 이스케이프로 바꿨다. `rg -l "priorPostmortemDigests" src/` 가 0건에서 1건이 됐고, 원시 NUL 이 되돌아오면 스위트가 red 가 된다.

### 초판의 처방은 필요 이상으로 위험했다

초판은 *"대체 구분자로 바꿀 수 있는지 판정한다"*고 적고, 위험으로 *"직렬화된 키가 저장된 아티팩트와 호환이 깨질 수 있다"*를 달았다. **결함은 구분자 값이 아니라 소스의 표기다.**

다섯 자리 모두 이스케이프가 아니라 **원시 NUL 바이트가 소스 파일에 직접 박혀 있다**(`charCodeAt` 이 0 을 낸다). 이스케이프였다면 역슬래시와 `0` 두 문자였을 것이고 `rg` 도 멀쩡했을 것이다.

그러므로 **`"\u0000"` 이스케이프로 표기만 바꾼다.** 런타임 문자열이 바이트 단위로 동일하므로 값이 바뀌지 않고, 따라서 영속 아티팩트 호환성 문제가 **발생하지 않는다.** 구분자를 실제로 교체할 이유가 없다.

`"\0"` 대신 `"\u0000"` 을 쓰는 이유는, 뒤에 숫자가 오면 8진 이스케이프로 해석될 여지가 있어서다.

### 틀렸을 때

`explain` 의 remediation 은 문자열이므로 고치기 쉽고, 그래서 **틀린 값을 다른 틀린 값으로 바꾸기도 쉽다.** 각 remediation 이 지목하는 enum 을 코드의 실제 정의에서 **파생**시킨다. P0-3 과 같은 원리다.

**표기만 바꾸는 것으로 그친다.** 값을 바꾸려 들면 직렬화된 키가 저장된 아티팩트와 호환이 깨질 수 있다. 그럴 이유가 없으므로 그러지 않는다.

### 검증

- **`explain` 이 안내하는 값이 코드의 enum 정의와 일치한다.** `PRIORITY_LEVELS` · `RISK_LEVELS` · `STABILITY_LEVELS` 중 하나에 값을 더하면 테스트가 red 가 된다(뮤테이션). 레거시 목록(`LEGACY_STABILITY_LEVELS`)은 안내에 들어가지 않는다.
- `init --help` 의 `--force` 행에 파괴 경고가 있다.
- **(3) 증거 참조 해석의 분모** — target 스코프 밖의 verified 요구도 증거 참조 해석 검사를 받는다. **분모를 target 스코프로 되돌리면 테스트가 red 가 된다.** 이 조건이 없으면 (3)은 어느 게이트에도 닿지 않는다.
- **원시 NUL 이 소스에서 0개가 된다.** 판정은 `charCodeAt` 전수 검사로 하고, `rg` 재귀 검색이 각 파일의 NUL 이후 심볼을 찾아내는 것으로 확인한다 — `rg -l "priorPostmortemDigests" src/` 가 지금은 0건이고 수리 후에는 1건이어야 한다.
