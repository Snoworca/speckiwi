## 전제 (사용자 확정, 2026-08-24)

> **목적은 빠르면서 정확한 SDD 도구다.**
> **사람은 코드도 스펙 문서도 읽지 않는다. 오직 코딩 에이전트에게 질문할 뿐이다.**

이 전제가 세 가지를 뒤집는다.

**1. "사람이 직접 부르는 명령"이라는 판정 기준은 무효다.** 초판 P3-3 은 `doctor` · `explain` · `search` · `stale` 같은 명령을 "사람이 터미널에서 직접 부르니 남긴다"로 살렸다. 사람이 부르지 않는다. **에이전트가 사용자 질문에 답하려고 부른다.** 그러므로 판정은 "사람이 쓰는가"가 아니라 **"에이전트가 도달할 수 있는가"** 다.

**2. 도달 불가 표면은 뚱뚱한 것이 아니라 배선이 빠진 것이다.** CLI 59개 중 33개, MCP 73개 중 19개가 스킬과 `CLAUDE.md` 어디에도 없다. 사람이 README 를 읽지 않으므로 **README 에만 있는 것은 존재하지 않는 것과 같다.** 폐기 대상이 아니라 노출 대상이다. 유지 비용만 내고 아무것도 돌려주지 않는 상태이므로 지금이 더 나쁘다.

**3. 도구가 에이전트에게 하는 진술의 정확성이 UX 문제가 아니라 정확성 문제다.** `explain SRS-E006` 이 존재하지 않는 enum(`P0,P1,P2,P3`)을 안내하는데 실제 값은 `critical`/`high`/`medium`/`low` 다. 사람이라면 이상하다고 느끼고 다른 데를 볼 것이다. **에이전트는 그대로 따르고 오류를 재현한다.** 그래서 Phase 0 로 올렸다.

## 0. 이 계획을 읽는 법

**이 계획은 산문이므로 썩는다.** 연구 26 §3.1 이 그 실물을 기록했다 — `docs/plan/v2.2.2-mutation-governance/plan.md` 는 테스트 케이스 수를 `"9 passed"` 로 못박았고 오늘 그 파일은 12개를 낸다. 세 정규식 전부 불일치하며 아무도 몰랐다.

그래서 이 계획은 다음 규칙으로 쓴다.

1. **수치를 복사하지 않는다.** 근거 문서의 절을 가리킨다. 수치가 필요하면 측정 명령을 적는다.
2. **각 항목에 "틀렸을 때 무엇이 깨지는가"를 적는다.** 이것이 계획이 잡을 수 있는 유일한 것이다(연구 24 §3.6, 연구 27 §2 의 I18).
3. **완료 판정은 이 문서가 아니라 요구의 AC 가 한다.** 여기 적힌 것은 착수 순서일 뿐이다.

**존재하지 않는 경로를 일부러 인용한 자리가 셋 있다. 고치지 말 것.** 없다는 사실이 근거다.

### 4.1 Phase 0 게이트 — 다섯 판이 연속으로 무너졌다

**초판**은 이것이었다.

> P0-3 의 검사가 **C1~C4 를 전부 발화**시킨다.

**공허했다.** C1~C4 의 구체가 `02.phase-1-live-contradictions.md` 에 어느 요구의 어느 리터럴인지까지 적혀 있다. 그 넷을 하드코딩한 검사도 통과한다. **자기가 잡을 답을 미리 아는 검사는 검사가 아니다.**

**2판**은 그 자리에 3조건(C1~C4 발화 · 미지의 리터럴 N개 발화 · 레지스트리 파생)을 놓았다. 그것을 쓴 쪽이 곧 계획을 쓴 쪽이었고 아무도 검토하지 않았다. 2026-08-24 에 독립 3축 검토를 받았고 **세 축이 각각 무너뜨렸다.** 무너진 방식이 다섯이며, 이 기록을 남기는 이유는 3판도 같은 방식으로 무너질 수 있기 때문이다.

**(1) 조건 1 이 달성 불가능했다.** C3 은 `--mini` 를 둘러싼 두 AC 의 수량자 충돌인데 **`--mini` 는 `src/**` 에 0회 출현한다**(실측). 대조할 배포 상수가 존재하지 않는다. Phase 0 의 게이트가 Phase 0 의 작업으로 도달할 수 없는 것을 요구했다.

**(2) 조건 3 의 "상수 레지스트리"가 존재하지 않았다.** `src/core/bootstrap/templates.ts` 는 개별 `export const` 다(`:33` `:43` `:44` `:124` `:125`). 저장소의 실제 레지스트리는 `src/core/diagnostic-registry.ts` 의 `DIAGNOSTIC_DEFINITIONS` 하나뿐이다. 그리고 손으로 나열한 배열도 문면상 "레지스트리"이며 "패턴 목록"이 아니므로, P2-3 이 상수를 추가할 때 조용히 무효화되는 결과가 그대로 남는다.

**(3) 조건 3 을 소박하게 구현하면 조건 1 을 무너뜨린다 — 가장 날카로운 것.**

```
templates.ts:124   AGENT_INSTRUCTION_HEADING_PREFIX     = "# SpecKiwi SRS workflow v"
```

#### 레지스트리 항목은 값이 아니라 형태와 값을 함께 갖는다

5판이 여기서 무너졌다. 대조군을 "레지스트리 값이 아닌 것"으로 정의했더니 **C2a 의 `SDS-MD-Rules-v1.0.0.md` 가 조건 3 으로는 음성 대조군이고 조건 2 로는 필수 발화**가 됐다. 원인은 실측으로 드러났다 — `templates.ts` 의 `LEGACY_` 상수는 **한글 heading 과 end marker 둘뿐이고**(`:129` `:130`) 규칙 파일명의 레거시 상수는 존재하지 않는다. 그 값은 어떤 레지스트리 값과도 같지 않다.

값만 비교하면 이 부류를 영원히 못 잡는다. 그러나 **파생 형태는 소스에 이미 있다.**

```ts
BUNDLED_SDS_RULES_FILENAME = `SDS-MD-Rules-v${BUNDLED_SDS_RULES_VERSION}.md`
```

그러므로 레지스트리 항목은 **현행 값**과 **파생 형태**를 함께 담고, 판정은 이렇게 한다.

| AC 안의 문자열 | 판정 |
|---|---|
| 형태에 맞고 값이 현행과 **다르다** | **발화** |
| 형태에 맞고 값이 현행과 같다 | 통과 |
| 어떤 형태에도 맞지 않는다 | 통과 — **여기가 음성 대조군 자리다** |


#### 완성도는 "등록"이 아니라 "분류"를 단언한다

분모를 넓히면 SSOT 가 아닌 상수가 딸려 들어온다. 실측에서 드러났다 — `src/core/bootstrap/**` 의 `export const` 는 15개이고 그중 `SKILL_PROVISION_AGENTS = ["claude","codex"]`(`init-project.ts:39`)가 있다. **이 항목에 조건 5 의 발화 테스트를 걸면 검사가 AC 의 "claude"·"codex" 를 전부 발화시켜 조건 3 을 깬다.** 명세의 AC 행 중 그 두 낱말을 담은 것이 100행을 넘는다.

그러므로 완성도 테스트가 단언하는 것은 **모든 export 가 셋 중 하나로 분류되어 있다**는 것이다.

| 분류 | 뜻 | 발화 테스트 |
|---|---|---|
| `current` | 현행 SSOT 값 | **있다** |
| `legacy` | 지울 수 없는 옛 값. AC 에 나오면 발화 | **있다** |
| `not-an-ssot` | AC 가 인용할 대상이 아님. **사유를 함께 적는다** | 없다 |

분류를 빠뜨린 export 가 하나라도 있으면 red 다. **`not-an-ssot` 도 선택이므로, 새 상수가 조용히 빠져나가는 길은 없다.**

**분모는 SSOT 상수를 담은 모듈 전체다** — `src/core/bootstrap/**` 만으로는 좁다. P0-3 의 대조 대상 표가 이미 `DIAGNOSTIC_DEFINITIONS`(`src/core/diagnostic-registry.ts`)를 담고, P0-5 가 같은 원리로 파생시키라는 `PRIORITY_LEVELS`·`RISK_LEVELS`·`STABILITY_LEVELS` 는 `src/core/types.ts` 에 있다. **둘 다 `bootstrap` 밖이므로, 분모를 그 디렉터리로 못박으면 P0-3 이 자기 대조 대상 두 축을 완성도 검사에서 배제한다.** 모듈 목록 자체를 레지스트리가 들고, 목록에 없는 곳에 SSOT 상수를 두면 잡히지 않는다는 사실을 그 자리에 적어 둔다.

**형태 매칭만으로 발화시키면 안 된다.** `RULES_DOCUMENT_FILENAME_PATTERN`(`:50`)은 정규식이라 현행 파일명도 똑같이 매칭한다. 그것만 쓰면 "규칙 파일명이 보이면 발화"하는 검사가 되어 **낡음 정보를 0비트도 담지 않은 채** 조건 2~5 를 통과한다. 반드시 **형태 일치 그리고 값 불일치**여야 한다.

---|---|---|---|
| **C1** | 요구 **7건** + 부록 §9 참조 샘플 | 한글·옛 버전 heading 리터럴 대 `AGENT_INSTRUCTION_*` | **P0-3 검사** |
| **C2a** | `FR-NODE-076` 을 포함한 **여러 요구** | `SDS-MD-Rules-v1.0.0.md` 대 `BUNDLED_SDS_RULES_FILENAME`(v2.5.0). **`FR-NODE-076` 한 자리가 아니다** — 실측에서 다른 요구와 부록·완료 로그에도 같은 리터럴이 있었다. 재고는 열거 스크립트가 만든다 | **P0-3 검사** |
| **C2b** | `FR-NODE-009` AC-9 · `FR-MCP-011` AC-11 | *"force 없이 기존 파일을 덮어쓰지 않는다"* — **무한정 범위**. `FR-NODE-085` 가 규칙 문서에 한해 뒤집었으나 **두 요구 어디에도 supersede 기록이 없다** | **P1-2 자기 절 검증** |
| **C3** | `FR-FLOW-022` 대 `FR-FLOW-034` | 수량자·부정 충돌. `--mini` 는 `src/**` 에 0회 | **P1-3 자기 절 검증** |
| **C4** | 기준 20건 | AC 가 **저장소 밖 환경 상태**(`~/.claude/skills/`)를 주장한다. 대조할 대상이 존재하지 않으며, 증거 셀이 *"NO INSTALLED COPY EXISTS"* 라고 자백한다 | **P1-4 자기 절 검증** |

**C2b · C3 · C4 는 대조할 SSOT 가 존재하지 않는다.** 리터럴이 틀린 것이 아니라 진술의 범위나 대상이 틀린 것이므로, 어떤 리터럴 대조 검사로도 발화하지 않는다. 게이트가 그것을 요구하면 **Phase 0 이 자기 작업으로 도달할 수 없는 것을 자기 게이트로 삼는다.**

> **C4 를 P0-3 에 넣으려던 시도가 한 번 있었고 틀렸다.** 저장소 안의 `.agents/skills/**` 미러와 대조하면 잡힌다고 적었으나, **AC 가 지목하는 것은 `~/.claude/skills/` 이며 미러가 아니다.** 서로 다른 두 산출물을 같은 것으로 본 오류였다. 이 기록을 남기는 이유는, 검사 범위를 넓히고 싶을 때 **대조 대상이 실재하는지 실행으로 먼저 확인하라**는 것이 이 게이트가 세 판에 걸쳐 배운 것이기 때문이다.

**C2b 가 C2a 보다 조용해서 더 나쁘다.** C2a 는 `FR-NODE-085` 가 Trace Links 에 *"Supersedes the never-overwrite clause of FR-NODE-076 AC-2 only"* 라고 남겨 두어 흔적이 있다. C2b 는 그 흔적조차 없이 두 요구가 `[x]` 인 채 거짓이 됐다.

레지스트리는 **신설이며 `current` / `legacy` 를 구분한다.** `legacy` 값과 일치하는 AC 리터럴은 통과가 아니라 **발화**다. 이 구분이 없으면 위 (3)에 의해 조건 1 이 무너진다. 그리고 조건 4 의 완성도 테스트가 없으면, 레지스트리는 하드코딩 문제를 한 층 위로 옮길 뿐이다 — P2-3 구현자가 새 상수를 등록하지 않으면 결과가 같다.

## 5. 전 페이즈 공통 제약

- `speckiwi init`(특히 `--force`) · `skills install` · `upgrade` · `remove` 를 이 저장소 대상으로 실행하지 않는다. `--force` 는 `docs/spec/00.index.md` 를 무증상으로 파괴한다. `skills mirror --write` 는 허용되며 `.agents/skills/**` 의 유일한 정당 writer 다.
- `git checkout` · `restore` · `stash` · `clean` · `reset --hard` 금지.
- `rg` 재귀 검색 금지 — 다섯 파일의 의도적 NUL 바이트 때문에 조용히 잘린다. `readFileSync` 로 읽는다. **예외: P0-5 (4)의 검증은 `rg` 가 정상화되는 것 자체가 증거이므로 그 자리에서는 쓴다.**
- 인라인 `node -e` 에 정규식 이스케이프를 넣지 않는다. 셸을 거치며 `\b` 가 백스페이스 문자로 바뀌어 **아무것도 매치하지 않은 채 결과를 낸다**(연구 26 §7.1 의 2·3번이 그 사례).
- `npm install` 을 맨으로 돌리지 않는다. 셸에 `NODE_ENV=production` 이 걸려 devDependencies 가 정리된다. 빌드·pack 은 `NODE_ENV=development`, 테스트는 `NODE_ENV=test`.
- 전체 스위트는 `npm test` 로 돌리고 출력을 `tail` 로 자르지 않는다.
- CLI 는 `node bin/speckiwi` 로 부른다. `node dist/cli/index.js` 는 출력 없이 exit 0.
- `bin/speckiwi` 를 spawn 하는 테스트는 `dist/` 를 실행하므로, `src/` 만 고치고 재빌드하지 않으면 변경이 보이지 않는다.
- 커밋 메시지에 어떤 시그니처도 넣지 않는다. 제목에 `Phase {n}` 같은 진행 표식도 넣지 않는다.
- **커밋에 `docs/research/**` 와 `docs/next/**` 를 섞지 않는다.** P0-1 이 이것을 게이트로 만들기 전까지는 손으로 지킨다.

## 7. 이 계획이 틀릴 수 있는 지점

1. **모순 24건이 전수가 아니다.** Rationale·Implementation Notes 약 38,000줄을 정독하지 않았다. (가)12 / (나)3 / (다)9 는 하한이며, Phase 2 의 우선순위가 이 비율에 걸려 있다.
2. **C1~C4 를 스위트로 재확인하지 않았다.** 옛 기준을 고정한 테스트가 있다면 Phase 1 이 그것도 함께 고쳐야 한다.
3. **표류 42쌍은 손으로 만든 표본이다.** 코퍼스 전체 비율이 아니다. Phase 2 완료 후 재측정하는 것이 게이트인 이유가 이것이다.
4. **`kiwi-orchestrator` 변종 비교의 절대 줄 수를 재현하지 못했다.** 정렬 후 `comm` 은 공통 731 / 고유 42·44 를, `Set` 차집합은 733 / 40·42 를 낸다. 두 방법이 중복 줄을 다르게 센다. **"약 89% 동일"만 쓰고 절대 수치는 쓰지 않는다.**
5. **산문·사이드카 포함률은 방법에 편향이 있다.** 자세한 것은 `04.phase-3-diet.md` P3-4 에 적었다. 편향의 방향이 결론에 유리한 쪽이었으므로 엄격 기준 수치를 쓴다.
