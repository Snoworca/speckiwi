## P1-1 — C1 에이전트 안내 블록의 버전·heading·마커

### 무엇이 어긋나 있는가

`FR-NODE-086` AC-3 [verified] 이 못박는다.

> The agent instruction block SHALL contain **no Hangul in any part, including its heading and its end marker**.

이와 동시에 참일 수 없는, 전부 `[x]` 인 기준들이다.

| 요구 | Stability | 못박은 heading |
|---|---|---|
| `IR-CLI-003` AC-7 | verified | `# SpecKiwi SRS 워크플로 v1.1` |

**일곱 요구가 다섯 버전(v1.1·v1.3·v1.4·v1.5·v1.6)을 못박고 어느 것도 상수와 일치하지 않으며, 전부 영문으로 바뀐 표기를 한글로 요구한다.** `FR-NODE-086` 이 verified 된 2026-07-30 이후 이 일곱 중 어느 것에도 Change Note 가 붙지 않았다.

`FR-FLOW-016` 은 앞의 여섯과 성격이 조금 다르나 **빼지 않는다.** AC 가 전부 `[ ]` 이고 Status 가 `implemented` 라 "검증된 거짓 주장"은 아니지만, AC-1 이 *"the current versioned heading (`# SpecKiwi SRS 워크플로 v1.4`)"* 로 **파생 문구 옆에 리터럴을 괄호로 달고 있고**, Requirement 본문도 한글 heading 을 규정한다. **파생 문구가 있다는 것이 리터럴이 없다는 뜻이 아니다** — 검사가 반드시 잡아야 할 형태이므로 표에 남긴다.

`docs/spec/90.appendix.md` §9 도 옛 형태(`v1.6`, 한글)를 담고 있다. **그것은 이력이 아니라 "이렇게 쓰라"는 참조 샘플이므로 낡으면 그대로 틀린다.**

### 수리 방향

**리터럴을 지우고 배포 상수 참조로 바꾼다.** `FR-NODE-051` 의 선례를 그대로 따른다. 버전 숫자를 최신으로 갈아 끼우는 수리는 하지 않는다 — 그러면 다음 버전 범프에 같은 일이 반복된다.

`Stability=stable` 인 둘(`FR-MCP-011`, `FR-NODE-009`)은 강등 후 개정하고 재verified 한다.

### 틀렸을 때

여섯 중 일부가 **의도적으로 옛 버전을 기술하는 역사 서술**일 수 있다. AC 는 현재 동작을 규정하는 자리이므로 그럴 가능성은 낮으나, 개정 전에 각 요구의 Rationale 을 읽어 확인한다.

### 검증

- P0-3 검사가 **이 일곱과 부록 §9 샘플**에 대해 0건을 낸다.
- 배포 상수를 바꾸는 뮤테이션을 넣으면 검사가 red 가 된다.

## P1-2 — C2 `force` 없는 덮어쓰기

### 무엇이 어긋나 있는가

`FR-NODE-085` AC-1 [verified]:

> **Init without the force flag SHALL overwrite** the installed rules documents … and SHALL report them as **refreshed rather than skipped**.

이와 어긋나는, 전부 `[x]` 인 기준:

| 요구 | Stability | 문안 |
|---|---|---|
| `FR-NODE-009` AC-9 (`50.nodejs-implementation.srs.md:827`) | **stable** | `force` 가 없으면 기존 파일을 덮어쓰지 않고 **skipped** path 로 보고 |
| `FR-MCP-011` AC-11 (`40.mcp-stdio-interface.srs.md:912`) | **stable** | `force` 없이 기존 파일을 덮어쓰지 않는다 |
| `FR-NODE-076` 본문 (`50.nodejs-implementation.srs.md:5287`) | verified | written via writeIfMissing (**a pre-existing file is never overwritten without force**) |

`FR-NODE-085` VE-1 이 조작된 SRS·SDS 규칙 파일이 **둘 다 바이트 단위로 복원됐다**고 실측을 기록하므로 `FR-NODE-076` 의 괄호절은 사실상 거짓이다.

**같은 줄에 낡은 못이 하나 더 있다.** 설치 대상을 `docs/rule/SDS-MD-Rules-v1.0.0.md` 로 못박는데 배포 상수는 `BUNDLED_SDS_RULES_VERSION = "2.5.0"` 이다.

### C2 는 둘로 갈린다 — 한쪽만 기계로 잡힌다

| | 대상 | 형태 | 판정 주체 |
|---|---|---|---|
| **C2a** | `FR-NODE-076` 의 파일명 리터럴 | `SDS-MD-Rules-v1.0.0.md` 대 `BUNDLED_SDS_RULES_FILENAME` | **P0-3 검사** |
| **C2b** | `FR-NODE-009` AC-9 · `FR-MCP-011` AC-11 | *"기존 파일"* 이라는 **무한정 범위** | **이 절의 검증** |

**C2b 에는 틀린 리터럴이 없다.** 진술의 범위가 틀린 것이라 대조할 SSOT 가 존재하지 않고, 따라서 어떤 리터럴 대조 검사로도 발화하지 않는다. 이 구분을 하지 않으면 Phase 0 게이트가 자기 작업으로 도달할 수 없는 것을 요구하게 된다(`00.index.md` §4.1).

**그리고 C2b 쪽이 더 조용하다.** C2a 는 `FR-NODE-085` 가 Trace Links 에 *"Supersedes the never-overwrite clause of FR-NODE-076 AC-2 only"* 라고 남겨 흔적이 있다. 반면 **`FR-NODE-009` 와 `FR-MCP-011` 의 블록 어디에도 `FR-NODE-085` 를 가리키는 supersede 기록이 없다**(두 블록 전수 확인). 두 요구는 흔적 없이 `[x]` 인 채 거짓이 됐고, 둘 다 `Stability=stable` 이다.

### 수리 방향

`FR-NODE-085` 가 규칙 문서에 한정한 예외라면, 나머지 셋의 문안을 **"규칙 문서를 제외한 기존 파일"** 로 좁힌다. 파일명 리터럴은 상수 참조로 바꾼다.

### 틀렸을 때

`FR-NODE-085` 가 규칙 문서 이외에도 적용되는 것이라면 좁히는 방향이 반대다. **`FR-NODE-085` 의 Requirement 본문과 VE-1 을 먼저 읽고 적용 범위를 확정한다.**

이 판정을 틀리면 `init` 이 사용자 파일을 덮어쓰는 경로가 열린다. **P4-0 의 파괴 경로와 같은 표면이므로 특히 주의한다.**

### 검증

- 규칙 문서와 그 밖의 파일에 대해 `force` 없는 `init` 의 동작이 각각 테스트로 고정된다.
- **이 저장소를 대상으로 `init` 을 실행하지 않는다.** 임시 저장소 픽스처로만 검증한다.

## P1-3 — C3 `--mini`

### 무엇이 어긋나 있는가

| 요구 | Status | AC-1 |
|---|---|---|
| `FR-FLOW-022` | verified `[x]` | **No** kiwi-* skill body or shared SSOT **references `--mini`**; … removed repo-wide |
| `FR-FLOW-034` | verified `[x]` | `--mini` … documented in the option table of **every** kiwi-* skill |

실측: `skills/**/*.md` 에서 `--mini` 가 **69개 파일에 296회** 출현.

`FR-FLOW-022` 는 supersede 를 Research 노트와 trace link 로만 기록했고 **AC 텍스트는 그대로 `[x]`, Change Notes 는 "Created" 한 행뿐**이다. 증거 테스트 `test/skills/kiwi-mini-removal-content.test.ts` 가 주석으로 밝힌다.

> "SUPERSEDED-SCOPE NOTE … This test is therefore NARROWED: it no longer asserts the `--mini` token is absent"

**증거가 더 이상 그 AC 를 단언하지 않는다.**

### 수리 방향

`FR-FLOW-023` 이 같은 상황을 **재개봉 → 개정 → 재verified** 로 처리한 선례가 있다. 그쪽으로 통일한다. `FR-FLOW-022` 를 강등하고 AC-1 을 supersede 사실이 반영된 문안으로 고친 뒤 재verified 한다.

### 틀렸을 때

`FR-FLOW-022` 를 통째로 discard 하면 그 요구가 담고 있던 다른 AC 도 함께 사라진다. **AC-1 만 개정한다.**

### P0-3 의 검사는 이것을 잡지 못한다 — 이 절의 검증이 Phase 1 게이트를 진다

C3 은 **배포 상수와 AC 리터럴의 불일치가 아니다.** 두 AC 사이의 수량자·부정 충돌이며(`No … references` 대 `every … skill`), **`--mini` 는 `src/**` 에 0회 출현한다**(실측). 대조할 SSOT 자체가 없으므로 P0-3 의 검사로는 어떤 구현이어도 발화하지 않는다.

초판은 Phase 0 게이트에 "검사가 C1~C4 를 전부 발화시킨다"를 넣어, **Phase 0 이 자기 작업으로 도달할 수 없는 것을 자기 게이트로 삼았다.** 그것을 바로잡아 C3 을 P0-3 범위에서 뺐고(`00.index.md` §4.1), 그 대신 **Phase 1 게이트가 이 절의 검증으로 C3 을 판정한다**(`00.index.md` §4 Phase 1 행).

### 검증

- 증거 테스트가 좁혀진 채로 남아 있지 않고, 개정된 AC 를 실제로 단언한다.
- 개정 후 AC 텍스트를 반대로 뒤집으면 테스트가 red 가 된다.
- **`FR-FLOW-022` AC-1 과 `FR-FLOW-034` AC-1 을 함께 읽었을 때 수량자가 충돌하지 않는다.** 판정은 두 AC 원문을 나란히 인용해 기록으로 남긴다 — 기계 판정 수단이 없으므로 인용이 증거다.

## P1-4 — C4 "설치본이 아직 옛 텍스트를 갖고 있다" 20건

### 무엇이 어긋나 있는가

`FR-FLOW-071` · `074~081` · `086` · `104` · `105` · `109~113` · `115` · `117` · `118` 의 기준 20개가 전부 `[x]` 로 `~/.claude/skills/` 설치본이 **변경 전 텍스트를 아직 갖고 있다**고 주장한다.

그런데 같은 요구들의 증거 셀이 자백한다.

> `FR-FLOW-086` VE-3 — AC-6 says the installed copy "still holds the pre-change text"; **it does not, because NO INSTALLED COPY EXISTS.**

그리고 `docs/next/2026-08-19.outstanding-work.md` §2 가 설치된 스킬 전 파일이 HEAD 소스와 **바이트 일치**한다고 실측을 기록한다.

### 수리 방향

**AC 에서 설치본 상태 주장을 제거한다.** 설치본은 이 저장소 바깥의 환경 상태이고 요구가 규정할 대상이 아니다. 규정할 것은 *도구가 무엇을 설치하는가*이지 *지금 설치되어 있는 것이 무엇인가*가 아니다.

`docs/next/2026-08-04.verification-integrity-handoff.md` §14.4·§15.8·§16.5 가 이것을 "다음 세션이 사용자에게 물어야 할 첫 항목"으로 세 번 연속 남겼다. **이 페이즈에서 닫는다.**

### 틀렸을 때

20개를 일괄로 고치는 것은 bulk mutation 에 가깝다. **요구마다 개별 증거와 사유를 붙인다.** `CLAUDE.md` 가 bulk-finalize 도구를 금지하는 이유가 이것이다.

### P0-3 의 검사는 이것을 잡지 못한다 — 이 절의 검증이 Phase 1 게이트를 진다

C4 는 **리터럴이 틀린 것이 아니라 대조 대상이 저장소 밖에 있는 것**이다. `~/.claude/skills/` 는 환경 상태이므로 **값을 대조하는 검사로는 발화하지 않는다** — 대조할 값이 존재하지 않기 때문이다. 개정 과정에서 저장소의 `.agents/skills/**` 미러와 대조하면 잡힌다고 적었던 자리가 있었으나 **서로 다른 산출물이다.**

**다만 아래 검증의 첫 항목은 기계 판정이 가능하다.** 그것은 값 대조가 아니라 **구조 규칙**이기 때문이다 — "AC 가 저장소 밖 경로의 상태를 주장하지 않는다"는 무엇과도 대조하지 않고 문장의 형태만 본다. 이 둘을 섞어 읽지 않는다.

### 검증

- **AC 본문에 홈 경로(`~/` 로 시작하는 경로)의 *상태* 를 주장하는 문장이 0건이다.** 이것은 기계 판정이 가능하다 — 경로 접두사와 상태 동사의 공기를 검사한다. 그 문장 하나를 되돌려 넣으면 red 가 된다(뮤테이션).
- 개정된 20개 각각이 **도구가 무엇을 설치하는가**를 규정하고, 지금 설치되어 있는 것이 무엇인지는 규정하지 않는다.
- 요구마다 개별 증거 행이 붙어 있다. 20개를 한 증거로 묶지 않는다.
- 요구 20개 각각에 개정 사유가 담긴 Change Note 가 붙는다.
- `validate --fail-on-warning --json` 이 errors 0 을 낸다.
