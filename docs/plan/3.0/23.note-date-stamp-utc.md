# 23. 요구 노트의 날짜 스탬프가 작성자의 날짜를 따르게 한다

| Field | Value |
|---|---|
| 우선순위 | MEDIUM — 정확도 |
| 근거 | 계획 [20번](20.shared-contract-tool-wiring.md) 검증 라운드 2 가 낸 LOW, 라운드 2 수정이 조사 |
| 선행 항목 | 없음 |
| 대상 | `src/core/mutation/append-section-note.ts` 와 같은 스탬프를 쓰는 자리들, `src/cli/commands/mutations.ts`, `src/mcp/tools/mutation-tools.ts` |

## 0. 이 항목이 생긴 경위

20 번 작업 중 한 요구 블록 안에서 **Implementation Notes 는 `2026-08-30`, Change Notes 는 `2026-08-31`** 로 갈렸다. 같은 사람이 같은 시각에 쓴 것인데 날짜가 하루 다르다.

`append-section-note.ts:42-43` 의 `todayIso()` 가 `toISOString().slice(0, 10)` 로 **UTC** 를 찍기 때문이다. KST 는 UTC+9 이므로 한국 시간 00:00~09:00 에 쓴 노트가 전날로 기록된다.

## 1. 무엇이 실제 문제인가

**"UTC 를 쓴다" 자체가 아니라 비대칭이다.** 날짜를 다루는 방식이 세 갈래로 갈려 있다.

| 갈래 | 해당 | 호출자가 날짜를 줄 수 있는가 |
|---|---|---|
| 안 받고 UTC 로 찍는다 | `toISOString().slice(0, 10)` 을 쓰는 `src/` **12 곳**(`append_section_note` 포함) | 없다 |
| 선택 `--date`, 기본값 UTC | `add-change-note`(CLI `mutations.ts:639` 등록 · `:645` 기본값) | 줄 수 있고 안 주면 UTC |
| 안 찍고 호출자가 반드시 준다 | `add-completed-work`(CLI `mutations.ts:431` 이 `requiredOption`) | 반드시 준다 |

셋째 갈래에는 `toISOString` 이 아예 없다. 코어가 `date is required` 와 `date must use YYYY-MM-DD` 로 거절하고(`add-completed-work.ts:290-292`), MCP 쪽은 그 필드를 `opt(...)` 로 등록하지만 핸들러가 `date: String(input.date)` 로 넘기므로 날짜를 뺀 호출은 UTC 로 채워지지 않고 거절된다. 저장소 전체에서 `--date` 를 받는 명령은 `add-change-note` 와 `add-completed-work` 둘뿐이다(MCP `schemas.ts:404` · `:478` 이 같은 둘을 비춘다).

`append_section_note` 는 CLI(`mutations.ts:287`)와 MCP(`mutation-tools.ts:236`)가 같은 코어를 부르고 **양쪽 등록 지점 어디에도 날짜 필드가 없다.** 그래서 한 사람이 한 세션에서 쓴 기록이, 호출자가 날짜를 대는 쪽은 로컬 날짜를 받고 대지 못하는 쪽은 UTC 로 남아 **같은 블록 안에서 갈린다.**

## 2. 실제로 갈린 자리

`docs/spec` 6 파일 · 요구 블록 598 을 훑어 같은 지문(노트 전부가 유일한 Change Note 날짜의 하루 전)을 가진 요구가 **셋** 있었다.

| 요구 | notes | change |
|---|---|---|
| `FR-FLOW-169` | 2026-08-30 | 2026-08-31 |
| `FR-NODE-174` | 2026-08-03 | 2026-08-04 |
| `FR-FLOW-120` | 2026-08-03 | 2026-08-04 |

뒤의 둘을 들여온 커밋 `25337f8` 의 로컬 시각이 **2026-08-04 17:40 +0900** 이므로, Change Note 쪽이 맞고 노트 스탬프만 어긋난다.

## 3. 왜 고쳐야 하는가

노트는 이 저장소에서 **요구의 이력**이다. 하루씩 어긋나면 두 가지가 무너진다.

- 같은 블록 안에서 노트와 Change Note 의 **선후가 뒤집혀 보인다.** 실제로는 노트가 먼저인데 날짜만 보면 나중이다.
- 날짜로 이력을 정렬하거나 대조하는 사람이 **없는 순서를 읽는다.** 셋 중 둘은 이미 3주 넘게 그 상태로 있었고 아무도 알아채지 못했다.

## 4. 목표 상태

한 사람이 한 세션에서 남긴 기록이 같은 날짜를 갖는다.

## 5. 작업 단계

1. **먼저 판정한다** — 옳은 기본값이 로컬 날짜인가, UTC 인가. 이 저장소는 KST 로 일하고 커밋 시각도 `+0900` 이므로 로컬이 유력하지만, **테스트가 날짜에 의존하는 자리가 있는지 먼저 세어야 한다.** UTC 를 기대하는 테스트가 있으면 그것부터 다룬다.
2. **12 곳을 전수로 읽고 갈래를 나눈다.** 전부 같은 성격인지, 로그·파일명처럼 UTC 가 맞는 자리가 섞여 있는지.
3. **요구를 등록한다.** scope 는 갈래에 따라 NODE 또는 CLI·MCP 를 함께 받는다.
4. **실패 테스트를 먼저 쓴다.** 시계를 함수 뒤로 밀어 넣어야 테스트가 시계를 필요로 하지 않는다 — 지금은 `todayIso()` 가 모듈 안에서 `Date` 를 직접 읽는다.
5. red 확인 → 구현 → green → 회귀.

## 6. 완료 조건

- KST 00:00~09:00 에 해당하는 시각을 주입했을 때, 노트와 Change Note 가 같은 날짜를 받는 것을 테스트가 잡는다.
- 그 배선을 되돌리면 붉어진다.
- 12 곳의 처분이 정해지고 그 근거가 요구에 적힌다 — 고친 자리와 UTC 로 남긴 자리를 갈라서.

## 7. 건드리지 말아야 할 것

- **이미 어긋난 노트 셋을 소급해 고치지 않는다.** 그것은 이력이고, 고치면 그때 무엇이 있었는지가 사라진다. 셋의 존재는 이 문서가 기록한다.
- **`--date` 를 받는 두 명령의 인터페이스를 없애지 않는다.** 소급 기록에 필요하다.
