# status enum 을 만드는 쓰기에서도 강제한다

| Field | Value |
|---|---|
| 우선순위 | CRITICAL — 정확도 |
| 근거 | `docs/research/28.skills-mcp-end-to-end-audit.md` §2.3, §5.1 |
| 선행 항목 | 없음 |
| 대상 | 코드 + 스킬 텍스트 |

## 1. 지금 무슨 일이 일어나는가

1. `kiwi-srs` 가 신규 요구의 status 를 `proposed` 로 지정하라고 지시한다.
2. `add_requirement` 가 그 값을 검사하지 않고 그대로 요구 블록에 기록한다. 같은 값이 레코드의 `status` 와 metadata 의 `Status` 행에 함께 실린다.
3. `validate` 를 돌리면 `SRS-E005` **error** 가 난다. `proposed` 는 `REQUIREMENT_STATUSES` 에 없기 때문이다.
4. 그런데 `kiwi-srs` 자신의 수렴 기준 첫 항목이 `validate_spec` PASS 다. 이 스킬은 자기 지시를 따르면 자기 종료 조건을 통과할 수 없다.
5. 그 요구는 `isNewWorkCandidate` 가 요구하는 세 status 어디에도 해당하지 않으므로 `newWorkCandidates` 에 영원히 오르지 않는다. `blocked` · `implementedNotVerified` · `missingEvidence` 목록도 각각 다른 status 를 요구하므로 전부 비켜간다. 남는 자리는 임의 문자열을 그대로 키로 받는 `countsByStatus` 딕셔너리뿐이다.
6. 이후 `kiwi-pm` 이 그 요구를 `implemented` 로 전이시키는 데 성공하면 무효한 값이 사라지고 `validate` 는 깨끗해진다. 그 값이 존재했다는 사실이 어디에도 남지 않는다.

재현하려면 격리된 임시 프로젝트를 만들어 그곳에서 `speckiwi add-requirement ... --status proposed` 를 실행한 뒤 `speckiwi validate --json` 을 본다. **이 저장소에서 재현하지 않는다.** 이 저장소의 `docs/spec/` 이 오염된다.

## 2. 근거

값을 **바꾸는** 쓰기는 enum 을 강제한다.

> `src/core/mutation/update-status.ts:106`
> `if (!isRequirementStatus(input.status)) return mutationFail("USAGE", ...);`

값을 **만드는** 쓰기는 검사하지 않는다.

> `src/core/mutation/add-requirement.ts:208`
> `status: input.status ?? "planned",`

같은 값이 metadata 에도 그대로 실린다.

> `src/core/mutation/add-requirement.ts:215`
> `Status: input.status ?? "planned",`

검증기는 그것을 error 로 판정한다.

> `src/core/validator/rules.ts:643-644`
> `if (!includes(REQUIREMENT_STATUSES, record.status)) {`
> `  diagnostics.push(diagnostic("SRS-E005", "error", ...));`

enum 은 여섯 값이다 — `src/core/types.ts:1-8` 의 `REQUIREMENT_STATUSES` 가 `planned` · `in_progress` · `blocked` · `implemented` · `verified` · `discarded` 를 담는다.

작업 후보 판정은 그중 세 값만 받는다.

> `src/core/query/summary.ts:39-40`
> `export function isNewWorkCandidate(record: RequirementRecord): boolean {`
> `  return (record.status === "planned" || record.status === "in_progress" || record.status === "blocked") && record.stability !== "draft" && record.stability !== "deprecated";`

스킬 계층은 일곱 값을 전제한다.

> `skills/claude/kiwi-srs/SKILL.md:485`
> 신규 REQ 기본 status: **`proposed`** (사용자 미승인).

> `skills/claude/kiwi-srs/SKILL.md:843`
> - `validate_spec` PASS

> `skills/claude/kiwi-pm/SKILL.md:949`
> `STATUS_ORDER = ["proposed", "planned", "in_progress", "implemented", "verified"]`

> `skills/claude/kiwi-review-fix-loop/SKILL.md:130`
> `| --close-reqs + 영향 REQ 중 현재 status 가 implemented 가 아닌 항목 (예: verified 이미 / proposed) | 해당 REQ skip + 보고, 나머지 진행 |`

> `skills/claude/kiwi-srs-feasibility/SKILL.md:64`
> `| feasibility=blocked + REQ.status ∈ {proposed, planned, blocked} | 정책에 따라 stability → deprecated 또는 keep |`

`src/mcp/` 와 `src/cli/` 가 그 enum 을 참조하는지는 다음 명령으로 잰다.

```
grep -rn "REQUIREMENT_STATUSES\|isRequirementStatus" src/mcp/ src/cli/
```

**같은 결함이 이미 한 번 일어났고 데이터만 수리되었다.** 이 항목의 근거는 이론이 아니라 이 저장소의 실적이다. `docs/spec/` 의 네 파일(`30` · `40` · `50` · `60`)에 `SRS-E005 fix: proposed is not a valid status` 라는 Change Notes 가 **11건** 남아 있다(2026-07-16, 근거 문서 §2.3 말미). 그때 요구 11개의 값을 `planned` 로 고쳤고, 그 값을 지시하는 스킬은 그대로 두었다. 그래서 같은 결함이 다시 발견되었다. 증상만 고치고 원인을 두면 어떻게 되는지를 이 저장소 자신이 기록해 두었으므로, 이 항목의 성립 조건은 "데이터를 고치는 것"이 아니라 "그 값이 다시 착지하지 못하게 하는 것"이다.

## 3. 목표 상태

`add_requirement` 가 enum 밖 status 를 `USAGE` 로 거부하고 파일을 쓰지 않는다. 스킬 텍스트에서 status 값 자리에 놓인 `proposed` 를 `planned` 로 정정하되, `kiwi-srs-feasibility` 의 status 분기가 `proposed` 를 잃고 죽은 조건이 되지 않도록 그 분기의 정의역을 다시 확정한다. **enum 에 `proposed` 를 추가하는 방향은 택하지 않는다.** 그 값을 만드는 코드 경로가 오늘 하나도 없고, 값을 늘리면 `isNewWorkCandidate` · `countsByStatus` · `STATUS_ORDER` 등 그 enum 을 소비하는 자리를 전부 다시 검토해야 한다.

## 4. 작업 단계

1. **요구를 먼저 등록한다.** `docs/spec/` 에 이 항목의 요구를 만들고 그 ID 를 이후 작업 요약에 적는다.
2. **실패하는 테스트를 쓴다.** `test/core/mutation/` 에 요구 ID 를 붙인 파일을 만들고, enum 밖 status 로 `addRequirement` 를 부르면 `USAGE` 로 실패하고 대상 파일 내용이 변하지 않는다고 단언한다. `npm test -- test/core/mutation` 으로 **red 를 확인한다.**
3. **최소 구현.** `src/core/mutation/add-requirement.ts` 에서 `input.status` 가 주어졌을 때만 `REQUIREMENT_STATUSES` 로 검사하고, 벗어나면 `mutationFail("USAGE", ...)` 를 반환한다. 미지정(`undefined`)은 거부 대상이 아니라 기본값 `planned` 로 간다. `:208` 과 `:215` 가 같은 식을 쓰므로 함수 진입부 한 곳에서 검사하면 두 자리가 함께 닫힌다. green 을 확인한다.
4. **전체 회귀.** `npm test` 를 돌린다. 픽스처나 `docs/spec/` 에 enum 밖 status 가 이미 있으면 여기서 드러난다.
5. **status 값이 놓이는 자리를 전수로 센다.** 감사가 지목한 네 스킬이 전부가 아니고, 어긋난 토큰도 `proposed` 하나가 아니다. 단일 토큰 grep 은 다른 토큰으로 난 같은 위반을 못 잡으므로, 토큰이 아니라 **자리**를 먼저 잡고 그 자리에 놓인 토큰을 뽑는다.
   ```
   grep -rhoE 'status *[:=∈] *\{[^}]*\}|status *[:=] *"?[a-z_-]+' skills/ .agents/skills/ \
     | grep -oE '[a-z_-]+' | sort | uniq -c | sort -rn
   ```
   출력은 status 자리에 등장하는 토큰 어휘 전체다.

   **⚠️ 정정 (2026-08-26, 실행해 확인) — 위 명령만으로는 대상을 전부 잡지 못한다.** 이 정규식은 `status:` 형태만 잡으므로 다음 네 형태를 놓치며, 그중에는 이 계획 §2 가 직접 지목한 자리도 있다.

   | 놓치는 형태 | 실례 (claude 렌더링) |
   |---|---|
   | 배열 리터럴 | `kiwi-pm/SKILL.md:949` — `STATUS_ORDER = ["proposed", "planned", ...]` |
   | 맵의 값 | `kiwi-pm/SKILL.md:316,318` — `"REQ-CORE-001": "proposed"` |
   | 표 안의 산문 서술 | `kiwi-review-fix-loop/SKILL.md:130` — `(예: verified 이미 / proposed)` |
   | 화살표 전이 서술 | `kiwi-srs/SKILL.md:785,788,805,813` — `proposed → planned 차단` |

   그러므로 **토큰을 전수로 훑은 뒤 자리를 사람이 분류하는 순서**로 간다. `grep -rn "proposed" skills/ --include=*.md` 가 139건을 내며, 그 가운데 요구 status 자리가 아닌 것이 다수다 — 식별자의 일부(`proposed_rung` · `proposed_scope` · `proposed_prefix` · `proposed_type` · `proposed_stability` · `current_status`), 경로와 파일명(`outputs/proposed-plan/` · `outputs/proposed-spec/` · `proposed-mutations.md`), 평범한 산문(`per-REQ proposed change 표`)이 전부 여기 해당하며 **건드리면 안 된다.**

   같은 이유로 `design-refuted` · `complete` · `running` · `skipped` · `sent` · `opened` · `emitted` 도 요구 status 가 아니다. 각각 lane manifest 의 status(`kiwi-orchestrator/SKILL.md:895`), 저널 result line 의 status(`:493`), 보고 채널의 status 다. 그 둘을 나눈 뒤 요구 status 자리만 고친다.
   **줄 단위로 거르지 않는다.** 한 줄이 유효한 값과 무효한 값을 함께 담으면 줄 필터가 그 줄을 통째로 놓친다. `kiwi-srs-feasibility/SKILL.md:243` 의 `status ∈ {discarded, draft} 제외` 가 그런 줄이고, 유효한 `discarded` 때문에 줄 필터에서 사라진다.
6. **세 렌더링을 함께 고친다.** `skills/claude` · `skills/codex` · `skills/etc` 이며, codex 와 etc 는 본문이 `SKILL.md` 와 `references/extended-workflow.md` 로 나뉘어 있으므로 두 파일을 모두 본다. `kiwi-srs-feasibility/SKILL.md:64` 의 분기는 `proposed` 를 뺀 뒤 남은 정의역이 `REQUIREMENT_STATUSES` 를 덮는지 확인한다. 오늘 그 표의 두 행을 합쳐도 `discarded` 는 다루지 않는다. 수정 대상에 다음 두 자리를 **명시적으로 포함한다.**
   - `skills/claude/kiwi-srs/SKILL.md:499` — `update_status { id: "REQ-X", status: "draft" }`. `draft` 는 Stability 값이고 `update-status.ts:106` 의 `isRequirementStatus` 가 오늘 이미 `USAGE` 로 거부하므로, 이 스킬은 **항상 실패하는 호출**을 지시하고 있다(근거 문서 §2.3.1). 단순 토큰 교체로 닫히지 않으므로 §7 의 항목을 먼저 읽는다.
   - `skills/claude/kiwi-srs-feasibility/SKILL.md:243` — `status ∈ {discarded, draft} 제외`. `draft` 를 status 필터에서 빼면 stability 필터 쪽으로 옮겨야 의미가 유지된다.
   - `skills/claude/kiwi-srs-sync/SKILL.md:470` — `update_stability — proposed→evolving 등 승급 시`. **이 자리는 방향이 반대인 같은 종류의 오류다** — `update_stability` 는 Stability 를 바꾸는 도구이고 Stability enum 에 `proposed` 는 없다. `kiwi-srs:499` 가 Stability 값을 Status 자리에 놓았다면 여기는 Status 토큰을 Stability 자리에 놓았다. 같은 문장이 codex·etc 의 `kiwi-srs-sync/references/extended-workflow.md:88` 에도 있다. `draft→evolving` 이 의도된 문장으로 보이나 **그 판정은 원문 맥락을 읽고 확정한다.** (2026-08-26 추가 — 이 계획이 원래 지목하지 않았던 자리다.)

   **3단계와 6단계는 같은 커밋에 착지한다.** 3단계만 먼저 들어가면 `kiwi-srs` 는 자기 지시를 그대로 따르는 동안 `add_requirement` 가 `USAGE` 로 거부해 **요구를 한 건도 등록하지 못한다.** 지금은 무효값이 착지하되 작업은 진행되므로, 코드만 먼저 착지한 중간 상태는 현재보다 나쁘다. 6단계만 먼저 들어가는 순서는 무해하지만 그 사이 원인이 열려 있으므로, 둘을 한 커밋으로 묶는다.
7. **스킬과 코드를 대조하는 테스트를 만든다.** `test/skills/` 에 세 렌더링을 순회하는 파일을 추가하고, 스킬 본문이 status 값으로 지목하는 토큰 집합이 `REQUIREMENT_STATUSES` 의 부분집합이라고 단언한다. `test/skills/kiwi-tdd-content.test.ts` 의 `VARIANTS` 순회가 기존 패턴이다. 6단계 수정 **전에** 이 테스트를 써서 red 를 확인한다.
8. **미러를 재생성한다.** `speckiwi skills mirror --write` 를 실행한 뒤 `speckiwi skills mirror --check` 가 divergence 0 을 보고하는지 확인한다. `.agents/skills/**` 를 손으로 고치지 않는다.
9. **검증을 서브에이전트에 맡긴다.** 원본 요구와 diff 만 주고 작성자의 결론은 주지 않는다.

## 5. 완료 조건

- enum 밖 status 로 `add_requirement` 를 부르면 `USAGE` 로 실패하고 대상 파일의 내용이 변하지 않는다. 그 사실을 단언하는 테스트가 스위트에 있다.
- 세 렌더링 어느 파일에도 status 값 자리에 enum 밖 값이 없고, 누가 그것을 다시 넣으면 `test/skills/` 의 대조 테스트가 실패한다.
- `speckiwi skills mirror --check` 가 divergence 0 을 보고한다.
- `kiwi-srs-feasibility` 의 status 분기가 `REQUIREMENT_STATUSES` 전체를 덮거나, 덮지 않는 값에 대해 무엇을 하는지 본문이 명시한다.

## 6. 틀렸을 때 무엇이 깨지는가

- **전제: 오늘 `proposed` 를 실제로 만드는 경로가 있다.** 만약 어떤 호출자도 status 를 넘기지 않아 항상 기본값 `planned` 만 쓰인다면 이것은 문서상 결함이고, 증상은 2단계 테스트가 red 로 가지 않는 것이다. 최소 구현 전에 red 를 반드시 확인해서 이 전제를 검사한다.
- **확인된 사실: 이 저장소에는 지금 중간 상태가 없다.** `node bin/speckiwi validate --json` 이 `SRS-E005` **0건**, error 급 진단 **0건**을 보고한다(2026-08-25 실행). 그러므로 4단계 전체 회귀가 기존 `docs/spec/` 데이터 때문에 실패할 일은 이 저장소에서는 없다. 픽스처는 별개이므로 4단계 결과로 확인한다.
- **남는 위험은 소비자 저장소다.** 전역 설치본으로 이 도구를 쓰는 다른 프로젝트에는 enum 밖 값이 이미 착지해 남아 있을 수 있고, `add_requirement` 에 검사를 넣는 것은 **새 쓰기만** 막는다. 이 항목이 착지해도 그 레코드는 그대로다. 사용자가 자기 저장소에서 발견하는 방법은 `speckiwi validate --json` 의 `SRS-E005` 진단이고, 수리 수단은 요구 하나씩 `update_status` 로 유효한 값에 옮기는 것뿐이다 — `update_status` 는 입력만 검사하므로 무효한 값에서 빠져나오는 전이는 막히지 않는다. 이 저장소가 금지하는 bulk 전이 도구를 이 수리를 이유로 만들지 않는다. **발견 방법과 수리 절차를 요구 문서와 릴리스 노트에 함께 적는다.** 적지 않으면 소비자는 자기 저장소가 이 상태인지 알 방법이 없다.
- **전제: `proposed` 를 `planned` 로 접는 것이 옳다.** 사용자 미승인 상태를 표현할 실제 필요가 있었다면 이 정정으로 그 구분이 사라진다. 증상은 `kiwi-srs` 종료 직후 승인되지 않은 요구가 `newWorkCandidates` 에 올라 작업 대상이 되는 것이다. 그 시점에 `speckiwi summary --json` 의 `newWorkCandidates` 를 보면 알아차린다. 그 구분이 실제로 필요하다고 판단되면 status 가 아니라 `Stability=draft` 로 표현한다.
- **이 결함은 자기은폐적이다.** `kiwi-pm` 이 전이에 성공하는 순간 무효한 값이 사라진다. 그러므로 "지금 `validate` 가 깨끗하다"는 관측은 이 결함의 반증이 아니다. 검증기가 그것을 볼 수 있는 창은 `kiwi-srs` 종료와 `kiwi-pm` 종료 사이뿐이다.

## 7. 주의할 점

- **세 렌더링을 함께 고친다.** 한 렌더링만 고치는 것이 이 저장소의 알려진 실패 형태다(근거 문서 §5.1). codex 와 etc 는 `references/extended-workflow.md` 에도 본문이 있다.
- **`.agents/skills/` 아래는 `skills/codex` 의 미러다**(`src/cli/commands/skills.ts` 의 mirror 액션). 손으로 고치지 말고 `mirror --write` 로만 갱신한다.

- **`kiwi-srs:499` — 이 계획의 원래 판단이 틀렸다. 2026-08-26 정정.**

  원래 이 자리에는 "토큰 교체로 닫히지 않으며 규칙 자체를 다시 설계해야 한다" 고 적혀 있었다. 근거는 그 지시문의 "status 만 변경, `stability` 필드 불변" 이라는 문구였다. **5인 결정 위원회가 원문으로 그 판단을 반증했고 만장일치로 Stability 축을 택했다.**

  같은 스킬이 세 자리에서 이미 Stability 를 뜻하고 있다. `SKILL.md:807`(§12 권고 표 B행)이 "기존 REQ {X} 는 `draft` 로 demote 됨. 폐기/재작성/수동 **stable** 복원 중 결정 필요" 라고 적고 근거란에 `§9.2 conflict` 를 달았는데 `stable` 은 Stability 값이다. `SKILL.md:855`(§15)도 "conflict 시 자동 discard 금지 — `draft` demote" 라고 적었다.

  그리고 문제의 꼬리 문구는 **바로 아래 `update` 분류 4단계에서 복사되며 따라온 것이다.** `update` 쪽은 `update_status { status: "discarded" }` 이고 `discarded` 가 실제 Status 값이므로 그 문구가 옳다. `conflict` 쪽은 같은 정형 문구를 복사하면서 값만 Stability 값을 넣었다. 이 계획은 그 복사된 꼬리 문구를 계약으로 읽었다.

  **확정된 처분**: `update_stability { id: "REQ-X", stability: "draft", reason: ... }` 로 갈아탄다. 대상은 **기존 REQ-X** 이며(`:807` 이 "기존 REQ {X}" 라고 명시한다), Status 는 건드리지 않는다. 새 status 값도 새 stability 값도 새 도구도 만들지 않는다.

  교체 문안은 다섯 요소를 모두 담아야 한다 — 도구 이름 `update_stability`, `Status` 불변, `status: "draft"` 가 `update_status` 에서 `USAGE` 로 거부된다는 사실, `reason` 이 §7 Change Notes 행을 자동 생성한다는 사실(`src/core/mutation/update-stability.ts:152-157`), 그리고 **verified 갈래**다. REQ-X 의 status 가 이미 `verified` 이면 이 호출은 `MUTATION_DENIED` 로 거부되므로(`update-stability.ts:123-124`) 그때는 demote 를 시도하지 않고 3단계의 `conflicts_with` trace link 만 남긴 뒤 6단계 보고에서 그 사실을 사용자에게 알린다.

  **같은 커밋에서 함께 고칠 부수 자리가 셋이다.** §13 MCP/CLI fallback 표에 `update_stability` 행이 **없고**(claude `SKILL.md:815-829` 대역, 직접 확인), §9.4 speckiwi 보장 목록에도 없다 — 그 목록이 "MCP mutation = line-patch 1회, 추가 `Edit` 금지" 를 성립시키므로 빠지면 에이전트가 수동 `Edit` 로 되돌아가 그 규칙을 깬다. 그리고 §12 권고 표 B행(`:807`)은 verified 갈래를 다루지 않는다.
