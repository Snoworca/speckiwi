# 31. 경로 인자를 조용히 버리는 대신 거절하게 한다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 정확도 |
| 근거 | SRS 경로 인자 결정위원회(2026-09-02) 위원 2·3·4 가 각각 독립으로 실서버 왕복 실측 |
| 선행 항목 | 없음 |
| 대상 | `src/mcp/server.ts` 의 SDK 배선, `src/mcp/adapter.ts` 의 게이트, `test/mcp/**` 의 게이트 테스트 |

## 0. 이 항목이 생긴 경위

사용자가 "SRS 계열 MCP 도구가 경로를 입력받는 인자를 갖게 하라" 고 지시해 위원회를 열었습니다. 위원회는 그 사안(읽기만 개방)에 만장일치로 답했지만, **조사 도중 사안보다 큰 것을 찾았습니다.**

**SRS 계열은 경로 인자를 거절하는 것이 아니라 조용히 버립니다.**

## 1. 무엇이 틀렸는가

`src/mcp/server.ts:652` 가 `toolSchemas[name]` 의 zod raw shape 을 SDK 에 넘기고, SDK 는 `safeParseAsync(z.object(shape), args)` 로 인자를 검증합니다. **zod object 는 기본이 strip 이므로 스키마에 없는 키가 파싱 단계에서 제거됩니다.** 그 뒤에야 `src/mcp/adapter.ts:127` 의 `"workspaceRoot" in input` 이 평가되므로, 그 조건은 **영영 참이 되지 않습니다.**

게이트는 없는 키를 볼 수 없고, 따라서 아무 말도 하지 않습니다.

## 2. 실측 — 세 위원이 각각 확인

이 세션에 붙은 실제 MCP 서버(3.0.0)와 SDK 클라이언트 왕복으로, 독립적으로 재현되었습니다.

- `list_requirements({workspaceRoot: <워크트리>})` → `ok:true`, **호스트의 답**, `rootSource: "server-cwd-discovery"`
- `update_status({id, dryRun:true, workspaceRoot: <워크트리>})` → 거절 문면 없이 **워크트리를 가리킨 채 호스트에 쓰러 감**
- `get_active_target({root: <워크트리>})` → `adapter.ts:130` 이 무조건 거절해야 하는 `root` 키인데 거절 없이 호스트 값
- 남의 저장소·없는 경로·상대경로·`docs/spec` 을 넘긴 경우도 전부 `ok:true`

**서버가 구버전이어서가 아닙니다** — 같은 서버에서 `workflow_workspace_info({workspaceRoot: <워크트리>})` 는 `per-call-workspace-root` 로 워크트리를 정확히 답합니다.

## 3. 왜 아무도 못 잡았는가

게이트를 검증하는 테스트 둘이 전부 `createTestMcpServer(...).callTool(...)` 즉 **어댑터 층만** 부릅니다. SDK 층을 통과하는 테스트는 설명문 검사 하나뿐입니다.

이 저장소가 반복해 잡은 형태 그대로입니다 — **소스 스캔은 실행을 단언하지 않습니다.** 선행 조사조차 `dist/` 를 직접 import 해 "8개 도구 전부 거절된다" 는 반대 결론을 냈고, 그 경로가 SDK 파싱을 건너뛴다는 것을 위원들이 밝혔습니다.

## 4. 무엇이 거짓이 되었는가

- `docs/spec/40.mcp-stdio-interface.srs.md` 의 `REL-MCP-005` VE-1 — "zero silently ignored"
- 같은 증거의 "49 refused / 51 accepted" — 실제 거절 관측은 **1건**뿐이고, 그 1건은 아래 §5 의 별개 결함 때문에 관측됩니다
- README 의 "도구가 돌기 전에 고유 사유로 거절된다"

**이 세 문장은 어댑터 층에서는 참이고 프로토콜 표면에서는 거짓입니다.** 요구가 어느 층을 약속했는지 먼저 판정해야 합니다.

## 5. 함께 나온 별개 결함

`preview_legacy_workflow_migration` 은 스키마(`src/mcp/server.ts:223`)가 `workspaceRoot` 를 광고하는데 등록(`src/mcp/tools/read-tools.ts:336`)에 `workspaceScope` 가 없어 **자기 startup root 를 넘겨도 거절**됩니다.

역설적으로 이 도구가 **거절이 실제로 관측되는 유일한 도구**입니다 — 스키마에 키가 있어 zod 가 지우지 않기 때문입니다. 그래서 이 결함이 위 결함을 가려 왔습니다.

`REL-MCP-005` VE-1 이 기록한 "47 SRS-facing" 도 실제 구성(SRS 계열 46 + 이 도구)과 1건 어긋납니다. **결함이 분류 안으로 흡수돼 아무도 눈치채지 못한 자리입니다.**

## 6. 확인해야 할 것

착수 시점에 먼저 재야 합니다.

- **분모.** 도구 100개 중 스키마가 광고하는 것과 게이트가 받는 것이 어긋나는 자리를 **전수로** 세십시오. 위원 4의 실측은 광고 52 / 받음 51 로 1건 초과였습니다. **하한을 두십시오.**
- **어느 층을 고칠 것인가.** 스키마에 키를 더해 게이트까지 도달시키는 방향과, SDK 배선에서 미지정 키를 보존하는 방향이 있습니다. 후자는 전 도구에 영향을 주므로 범위를 먼저 재십시오.
- **`orchestrate` 계열은 이미 스키마를 게이트 표에서 파생시킵니다**(`src/mcp/server.ts:67`, 어긋남 0건). `workflow_*` 는 게이트와 스키마를 따로 유지하고 그 결과가 §5 입니다. **새 계층을 만들지 말고 그 파생을 넓힐 수 있는지 먼저 보십시오.**
- **`root` 키의 무조건 거절**도 같은 이유로 도달하지 않습니다. 함께 처분해야 합니다.
- **요구가 어느 층을 약속했는지.** `REL-MCP-005` 의 SHALL 과 AC 를 읽고, 프로토콜 표면을 약속한 것이면 그 요구는 지금 거짓이며 하향 → AC 수정 → 재승격이 필요합니다.

## 7. 목표 상태

경로 인자를 받지 않는 도구에 그 인자를 넘기면 **호출자가 그 사실을 알게 됩니다.** 조용히 다른 저장소의 답이 돌아오지 않습니다.

## 8. 작업 단계

1. **§6 의 다섯을 재고 방향을 정한다.**
2. **요구를 등록한다.** scope 는 `MCP`(`docs/spec/40.mcp-stdio-interface.srs.md`).
3. **실패 테스트를 먼저 쓴다. 반드시 SDK 층을 지나는 테스트여야 한다** — 어댑터를 직접 부르는 테스트는 이 결함을 못 잡는다는 것이 이미 실측되었다. 실제 클라이언트-서버 왕복으로 재라.
4. red 확인 → 구현 → green → 회귀.

## 9. 완료 조건

- **경로 인자를 넘긴 호출이 실제 프로토콜 왕복에서 거절되는 것**을 실행으로 보인다.
- **어댑터 층만 부르는 테스트로는 잡히지 않고 SDK 층 테스트로만 잡히는 것**을 심어서 보인다 — 그것이 이 결함의 본질이다.
- 스키마와 게이트가 어긋나는 자리 전부의 처분이 정해진다.
- **거짓이 된 세 문장**(VE-1 둘, README 하나)의 처분이 정해진다.
- **검사가 못 잡는 형태가 요구에 실측과 함께 적힌다.**

## 10. 건드리지 말아야 할 것

- **SRS 계열에 경로 인자를 더하지 않는다.** 그것은 32번의 일이고, 이 항목은 **지금 거절해야 할 것이 거절되지 않는 것**만 다룬다.
- **`FR-MCP-058`·`FR-MCP-059` 가 정한 받는 계열의 동작을 바꾸지 않는다.**
