# 11. 진입점 이음매를 문서에 명시한다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 정확도 |
| 근거 | `docs/research/28.skills-mcp-end-to-end-audit.md` §2.5, §2.7 의 M1·M2·M3·M4·M6 |

## 1. 지금 무슨 일이 일어나는가

1. 사용자가 GitHub 이슈 번호 하나를 주고 파이프라인을 시작한다.
2. `kiwi-pipeline` 이 그 이슈를 감지하고, 저작 단계로 바로 가지 않고 먼저 `kiwi-srs-research` 를 돌리라고 규정한다(`skills/claude/kiwi-pipeline/SKILL.md:186`). 그런데 **이슈 본문을 어떻게 가져오는지는 적지 않는다.**
3. `kiwi-srs-research` 로 넘어간다. 그 파일에도 `gh issue` 는 0회다. 즉 연구자가 이슈 본문을 무엇으로 읽는지 문서에 없다.
4. 연구가 끝나면 `kiwi-srs` 로 넘어간다. `kiwi-srs` 의 필수 입력은 둘뿐이다(`:119-122`). `REQ_TEXT` 인 자연어 인라인과 `REQ_PATH` 인 파일 경로다.
5. **방금 만든 연구 보고서를 그 둘 중 무엇으로 승격하라는 문장이 없다.** `kiwi-srs` 전문에서 "이슈"와 "issue"의 등장 횟수는 0이다.
6. 결국 에이전트가 이음매를 스스로 채운다. 어떤 실행은 이슈 본문을 `REQ_TEXT` 로 넣고, 어떤 실행은 연구 보고서 경로를 `REQ_PATH` 로 넣고, 어떤 실행은 둘 다 넣지 않는다. 같은 이슈가 실행마다 다른 요구를 만든다.
7. 요구가 등록된 뒤에도 이슈 번호가 남지 않는다. `add_requirement` 에 `githubIssue` 필드가 실재하는데(`src/mcp/server.ts:333`) `skills/` 전체에서 그 이름의 등장 횟수는 0이다.

대조 사실이 중요하다. **같은 이음매를 명시한 자리가 이미 있다.** 오케스트레이터는 wave 위임에서 무엇이 넘어가는지를 인자로 적는다(`kiwi-orchestrator:512-513`). 명시가 가능한 자리인데 이슈 경로만 침묵한다.

## 2. 근거

파이프라인은 순서만 규정한다.

> `skills/claude/kiwi-pipeline/SKILL.md:186`
> 이슈 진입 큐와 `kiwi-srs` 시작 사이에는 오직 `kiwi-srs-research` 만 위치하고, 연구 없이 `kiwi-srs` 를 곧바로 시작하지 않는다.

`kiwi-srs` 의 필수 입력에는 이슈도 연구 문서도 없다.

> `skills/claude/kiwi-srs/SKILL.md:119-122`
> ### 1.1 필수 입력 (택1)
> - `REQ_TEXT` — 자연어 인라인 (positional)
> - `REQ_PATH` — 요구사항 파일 경로

## 3. 목표 상태

다섯 자리를 채운다. 전부 스킬 텍스트이고 코드는 건드리지 않는다.

- **M1 — 획득 명령.** `kiwi-pipeline` 의 이슈 진입 절과 `kiwi-srs-research` 의 입력 절에 이슈 본문을 가져오는 명령이 적힌다. `kiwi-hot-fix:200` 의 형식을 그대로 쓴다. 같은 저장소에서 같은 일을 하는 명령이 두 가지 형태로 적히지 않게 한다.
- **M2 — 산출물.** `kiwi-orchestrator` 의 `intake-issue` 동사가 무엇을 만드는지 적는다. 형제 동사(`:1010`)가 `01.intake.md` 를 적으므로 같은 형식으로 적는다.
- **M3 · §2.5 — 승격 이음매.** `kiwi-orchestrator:512-513` 의 `REQ_PATH=<경로>` 형식을 그대로 쓴다. 다만 **그 경로가 가리키는 것은 연구 보고서가 아니라 `kiwi-srs-research` 가 따로 쓴 요구 진술 발췌본이다.** 오케스트레이터가 `waves/wave-{n}/excerpt.md` 를 넘기는 것과 같은 모양이며, 그 스킬도 원본 문서가 아니라 자기가 쓴 발췌본을 넘긴다. 이유는 §7 에 적었다. `kiwi-pipeline` 쪽에도 같은 인자를 적는다. 한쪽만 적으면 다른 쪽을 읽은 에이전트가 여전히 스스로 채운다.
- **M4 — 에픽 진입.** `kiwi-wave-master` §8 에 에픽 이슈를 읽는 명령이 적힌다. 하위 이슈를 세는 방법은 오케스트레이터가 이미 정했으므로(`:356` 의 S8) 그것을 가리킨다. 다시 적지 않는다.
- **M6 — 추적 보존.** 이슈에서 출발한 요구는 `add_requirement` 의 `githubIssue` 필드에 그 이슈를 싣는다. 이슈와 요구의 연결이 요구 블록에 남는다.

## 4. 작업 단계

1. 요구를 먼저 등록한다. 다섯 자리를 한 요구로 묶어도 되고 M3 만 따로 떼어도 된다. M3 가 §2.5 의 본체이고 나머지 넷은 그 주변이다.
2. **§3 의 M3 가 확정한 형식을 요구의 AC 로 옮긴다.** 세 후보 중 무엇을 골랐고 왜 골랐는지가 AC 에 있어야 한다. 후보와 기각 사유는 이렇다.
   - **채택 — `REQ_PATH=<발췌본 경로>`.** `kiwi-srs-research` 가 이슈 본문과 연구 결과에서 요구 진술만 뽑아 파일 하나로 쓰고, 그 경로를 넘긴다. `kiwi-orchestrator:512-513` 과 같은 모양이므로 저장소에 같은 이음매가 두 형태로 존재하지 않는다.
   - 기각 — 연구 보고서 경로를 그대로 `REQ_PATH` 로 준다. `kiwi-srs:574` 가 "리서치 문서"에 이미 다른 의미를 부여했다. 같은 파일이 `REQ_PATH` 이면서 `--research-doc` 이면 두 절이 같은 입력에 다른 처리를 규정하게 된다.
   - 기각 — 이슈 본문을 `REQ_TEXT` 로 인라인한다. `REQ_TEXT` 는 positional 이므로 이슈 본문의 줄바꿈·따옴표·코드 블록이 그대로 인자 자리에 들어간다. 길이 제한도 문서에 없다.
   - **`--research-doc` 는 그대로 둔다.** 연구 보고서는 `--research-doc` 로 함께 넘겨 `:574` 의 A/B 루프를 돌린다. 즉 발췌본이 무엇을 만들지를 정하고, 보고서가 그것을 검증한다. 두 인자의 역할이 겹치지 않는다.
3. **실패 테스트를 먼저 쓴다.** `test/skills/` 관례를 따라 네 사본(`skills/claude` · `skills/codex` · `skills/etc` · `.agents/skills`)을 열거해 단언한다. 대상 파일이 넷이므로 테스트도 자리마다 나눈다.
   - `kiwi-pipeline/SKILL.md` 와 `kiwi-srs-research/SKILL.md` 에 `gh issue view` 가 있다.
   - `kiwi-srs/SKILL.md` 의 입력 절에 발췌본을 `REQ_PATH` 로 받는다는 문장이 있다.
   - `kiwi-srs-research/SKILL.md` 의 산출물 절에 그 발췌본을 쓴다는 문장과 그 파일 이름이 있다.
   - `kiwi-orchestrator/SKILL.md` 의 `intake-issue` 절에 산출물 이름이 있다.
   - `kiwi-wave-master/SKILL.md` 에 에픽 이슈 획득 명령이 있다.
   - 이슈 진입 경로를 다루는 스킬에 `githubIssue` 지시가 있다.
   - 테스트를 쓰기 전에 §2 의 측정을 다시 돌려 0임을 확인하고 테스트 상단 주석에 남긴다.
4. **실패를 확인한다.** `npx vitest run test/skills/<파일>` 로 red 를 본다.
5. **최소 구현으로 통과시킨다.** 해당 스킬들의 `skills/claude` · `skills/codex` · `skills/etc` 세 렌더링을 함께 고친다. 줄 번호는 렌더링마다 다르므로 문구로 찾는다.
6. `speckiwi skills mirror --write` 로 `.agents/skills/` 를 재생성한다.
7. `npx vitest run test/skills/` 로 green 과 회귀 없음을 확인한다. `test/skills/kiwi-pipeline-content.test.ts` 와 `test/skills/kiwi-wave-master-content.test.ts` 가 기존 문구를 고정하고 있을 수 있으므로 먼저 읽는다.
8. 이슈 하나로 실제 진입을 한 번 돌린다. `kiwi-srs` 가 받은 인자가 문서가 적은 것과 같은지 본다.
9. 검증 서브에이전트에게 원본 요구와 diff 만 준다.

## 5. 완료 조건

- **이음매 문장을 지우면 테스트가 실패한다.** 다섯 자리 각각에 대해 문장을 지운 상태에서 red 를 한 번 관찰한다.
- **`REQ_PATH` 를 다른 인자로 바꾸거나 발췌본 대신 연구 보고서를 가리키게 바꾸면 테스트가 실패한다.** §3 M3 이 확정한 형식이 단언에 들어 있어야 한다.
- **이슈 진입 경로 스킬의 `kiwi-srs` 호출 예시가 §3 M3 이 확정한 인자 형태를 리터럴로 담는다.** `kiwi-pipeline` 과 `kiwi-srs-research` 네 사본 각각에서 그 호출 예시를 읽어, `REQ_PATH=` 와 발췌본 파일 이름이 한 문자열 안에 있다고 단언한다. 두 스킬이 서로 다른 인자 형태를 적으면 실패하고, 예시를 다른 인자로 고치거나 발췌본 이름을 바꿔도 실패한다. 같은 이슈가 실행마다 다른 인자로 넘어가지 않는다는 것을 고정하는 것은 1회 실행이 아니라 이 단언이다.
- **이슈 진입 경로 스킬의 `add_requirement` 호출 지시에 `githubIssue` 인자가 있다.** 그 인자 이름을 지우면 실패한다. 인자가 넘어갔을 때 요구 블록의 GitHub Issue 행이 `-` 가 아닌 값으로 렌더링되는 것은 `src/core/mutation/render-requirement.ts:50` 과 `src/core/mutation/add-requirement.ts:221` 이 이미 보장하므로, 렌더링 결과를 따로 관찰하지 않는다.
- `speckiwi skills mirror --check` 가 divergence 0 을 보고한다.

## 6. 틀렸을 때 무엇이 깨지는가

- **발췌본을 쓰는 단계가 없으면 `REQ_PATH` 가 가리킬 파일이 없다.** M3 는 `kiwi-srs` 한 곳이 아니라 두 곳을 고친다. `kiwi-srs-research` 가 그 파일을 쓰지 않으면 이음매는 여전히 비어 있고, 에이전트가 연구 보고서 경로를 대신 넣는다. 알아차리는 방법은 실제 진입을 한 번 돌려 `REQ_PATH` 가 가리킨 파일을 열어 보는 것이다. 그것이 연구 보고서면 실패다.
- **발췌본이 요구 진술이 아니라 연구 요약이 되면 이 항목은 형식만 채운 것이 된다.** 증상은 `kiwi-srs` 가 만든 요구가 연구 문서의 목차를 닮는 것이다. 발췌본에 무엇을 담는지를 `kiwi-srs-research` 쪽에 규정한다.
- **`gh issue view` 의 `--json` 필드 목록이 두 곳에서 달라질 수 있다.** `kiwi-hot-fix:200` 은 `title,body,comments` 를 가져온다. 다른 자리에서 다른 필드를 적으면 같은 이슈가 스킬마다 다른 내용으로 읽힌다. 알아차리는 방법은 `grep -rn "gh issue view" skills/` 로 형태를 세는 것이다.
- **하위 이슈 세는 법을 다시 적으면 오케스트레이터와 어긋난다.** `:356` 이 네이티브 하위 이슈 API 가 추적 이슈에 0을 돌려준다는 사실을 이미 적었고, 그래서 본문의 `- [ ] #NNNN` 참조를 센다고 규정했다. `kiwi-wave-master` 에 이 규칙을 다시 쓰면 한쪽만 갱신되는 형태가 만들어진다. 가리키기만 한다.
- **`githubIssue` 를 필수로 만들면 이슈 없이 시작한 요구가 막힌다.** 증상은 자연어로 시작한 요구 등록이 거부되는 것이다. 이슈 진입 경로에서만 의무로 둔다.
- **전제가 틀렸다면**, 즉 어딘가에 이미 승격 문장이 있다면 이 항목의 M3 는 불필요하다. 재확인 명령은 `grep -rin "issue\|이슈" skills/claude/kiwi-srs/SKILL.md` 다. 0이 아니면 그 문장을 먼저 읽는다.

## 7. 주의할 점

- **`--research-doc` 의 의미를 바꾸지 않는다.** `:574` 가 그것을 A/B 검증 루프의 입력으로 규정한다. 신규 저작의 입력으로 재정의하면 그 절 전체의 의미가 바뀐다. 그래서 발췌본을 따로 두고 `REQ_PATH` 로 넘기는 것이며, 연구 보고서는 `--research-doc` 자리에 그대로 남는다.
- **다섯 자리는 서로 독립이다.** M3 가 막히면 나머지 넷을 먼저 끝낸다. 넷은 결정이 필요 없는 기술(記述) 작업이고, M3 만 두 스킬을 함께 고쳐야 한다.
- `kiwi-pipeline` 의 §2.7 은 요구 AC 를 그대로 옮겨 적은 절이다. 그 절의 문장을 고치면 대응하는 요구와 어긋날 수 있으므로, 고치기 전에 그 요구를 먼저 읽는다.
- `.agents/skills/**` 는 `skills/codex` 에서 생성된다(`src/core/skills/mirror-skills.ts:23-24`). 직접 편집하지 않는다.
