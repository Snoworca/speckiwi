# 25. CLI 전용 에이전트에게도 run lock 이 배타를 만들게 한다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 정확도 |
| 근거 | 계획 [22번](22.run-lock-owner-discrimination.md) 검증 라운드 1, 라운드 2 가 재현 |
| 선행 항목 | 없음 |
| 대상 | `src/cli/commands/orchestrate.ts` 의 run lock 계열, `src/core/orchestrator/run-lock.ts` |

## 0. 이 항목이 생긴 경위

`orchestrator-run-lock-held` 는 critical 게이트다. 두 run 이 같은 저장소에서 겹치는 것을 막는 자리다.

**그런데 CLI 전용 에이전트에게는 발화하지 않습니다.** MCP 서버는 프로세스가 살아 있어 sentinel 의 pid 가 유효하지만, CLI 는 `run lock` 이 반환하면 그 프로세스가 종료한다. 그래서 다음 `run lock` 이 그 lease 를 stale 로 보고 회수한다.

실측(2026-08-31, 두 측정자가 각각 재현):

```
A: speckiwi orchestrate run lock ...   → exit 0, pid 28884
B: speckiwi orchestrate run lock ...   → exit 0, pid 68712
게이트 없음
```

**두 run 이 같은 저장소를 동시에 잡습니다.** MCP 를 쓰는 에이전트는 보호받고 CLI 만 쓰는 에이전트는 보호받지 못한다.

## 1. 왜 이것이 중요한가

이 저장소의 스킬은 **MCP 를 우선하되 없으면 CLI 로 같은 판정을 받는다**고 적는다. 그 문장이 이 자리에서 거짓이다 — 같은 판정이 아니라 **게이트가 아예 없는 판정**을 받는다.

그리고 계획 [22번](22.run-lock-owner-discrimination.md)이 만든 판별 수단은 이 결함을 덮지 못한다. 판별은 "이 lease 가 내 것인가" 를 답할 뿐이고, **애초에 둘이 동시에 잡히는 것**은 막지 못한다.

## 2. 확인해야 할 것

- **회수를 결정하는 것이 무엇인가.** pid 생존 검사인지, mtime 유예인지, 둘 다인지. 22번 작업에서 `isReclaimable(holder, age)` 가 두 축을 쓰는 것이 관측됐다.
- **CLI 배치가 어떤 모양인지.** 한 에이전트가 `run lock` 을 부르고 여러 명령을 돌린 뒤 `run unlock` 을 부르는 것이 의도된 사용인가. 그렇다면 그 사이 프로세스가 없는 것이 정상이므로 pid 로 생존을 재는 것 자체가 이 배치에 맞지 않는다.
- **MCP 경로가 이 변경으로 어떻게 되는가.** 지금 MCP 는 서버 pid 로 보호받는데, 기준을 바꾸면 그 보호가 약해질 수 있다.
- **`FR-NODE-203` 이 정한 것과 충돌하지 않는가** — 읽을 수 없는 sentinel 을 경합으로 답하는 계약, 그리고 torn grace.

## 3. 목표 상태

CLI 만 쓰는 두 run 이 같은 저장소를 동시에 잡으면 뒤엣것이 `orchestrator-run-lock-held` 로 거절한다.

## 4. 작업 단계

1. **§2 의 넷을 재고 방향을 정한다.** 회수 기준을 바꾸는 것과 lease 에 만료를 두는 것 가운데 어느 쪽이 두 경로 모두에서 참인지.
2. **요구를 등록한다.** scope 는 NODE 가 유력하다.
3. **실패 테스트를 먼저 쓴다.** 두 프로세스가 연달아 `run lock` 을 부르는 것이 red 여야 한다.
4. red 확인 → 구현 → green → 회귀.

## 5. 완료 조건

- CLI 두 호출이 거절되는 것을 테스트가 잡고, 그 배타를 되돌리면 초록이 된다.
- **MCP 경로가 여전히 보호받는 것을 함께 잰다.** 한쪽을 고치며 다른 쪽을 잃지 않았음이 증거로 남아야 한다.
- **자기 run 의 재취득이 자기 lease 에 거절당하지 않는 것**을 잰다 — 22번이 그 경우를 실측했다(컴팩션된 같은 세션이 `exit 2` 로 거절당한다).

## 6. 건드리지 말아야 할 것

- **`FR-NODE-203` 의 torn grace 계약을 다시 열지 않는다.** 그것은 `FR-NODE-177 AC-7` 이 소유한다.
- **`unlock` 이 남의 lease 를 해제하는 거동을 바꾸지 않는다.** 계획 22번 §5 가 같은 이유로 그것을 뺐다.

## 7. 같은 명령 계열에서 함께 발견된 것

**착수하면 이것도 함께 보라.** 별도 항목을 만들지 않은 것은 LOW 이고 대상이 같은 명령이기 때문이다.

`orchestrate run lock --dry-run` 이 찢어진 sentinel 을 `ok` 로 답하는데, 같은 조건에서 실제 `lock` 은 torn grace 5 초 안에서 `exit 2` `orchestrator-run-lock-held` 로 거절한다(2026-08-31 실측, 두 측정자가 재현). **dry-run 이 "잡을 수 있다" 고 답한 뒤 실제 취득이 거절하는 자리다.**

`FR-NODE-204 AC-5` 가 그 어긋남을 재기만 하고 고치지는 않았다. 고치려면 dry-run 이 회수 판정을 복제해야 하므로 새 거동이고, 그것은 이 항목이 회수 기준을 다시 정할 때 함께 정하는 편이 싸다.
