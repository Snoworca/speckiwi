# 14. MCP 도구 100개에 설명을 부여한다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 정확도 |
| 근거 | `docs/research/28.skills-mcp-end-to-end-audit.md` §4.4 |
| 선행 항목 | 없음 (항목 12 가 이 항목을 선행으로 삼는다) |
| 대상 | 코드 |

---

## 1. 지금 무슨 일이 일어나는가

MCP 도구 등록부가 `description` 필드를 아예 전달하지 않는다.

> `src/mcp/server.ts:631-634`
> `sdk.registerTool(name, { title: name, inputSchema: toolSchemas[name] ?? {}, annotations: { readOnlyHint: isReadOnlyTool(name) } }, ...)`

넘기는 것은 이름과 입력 스키마와 읽기 전용 여부뿐이다. 근거 문서 §4.4 가 실제 `tools/list` 응답으로 확인한 결과, `description` 이 비어 있지 않은 도구가 하나도 없고 `title` 은 전부 `name` 과 같다.

**결과는 비용이 아니라 정확도다.** 도구를 고르는 에이전트에게 주어지는 것은 이름과 인자 목록뿐이다. 이름이 서로 가까운 도구가 여럿 있을 때 — `list_requirements` 와 `search_requirements`, `workflow_pipeline_status` 와 `workflow_pipeline_tail`, `get_active_target` 과 `summarize_target` — 어느 쪽이 이 질문에 답하는지를 도구 자신이 말하지 않는다. 그래서 그 의미론이 전부 스킬 산문으로 밀려났다. 각 스킬이 자기가 부를 도구를 문장으로 설명해야 하고, 그 문장은 도구를 부르든 부르지 않든 호출마다 적재된다.

**이것이 항목 12 의 근본 원인 하나다.** 근거 문서 §4.4 가 그렇게 판정했다. 도구가 자기를 설명하지 못하므로 스킬이 대신 설명하고, 그 설명이 본문을 키운다.

부수적으로, 페이로드의 상당 부분이 100개 도구 전부가 같은 값을 갖는 상용구다. 근거 문서 §4.4 의 표가 네 행으로 그것을 열거한다 — `title` 이 `name` 과 같은 것, 모든 도구에 붙는 동일한 `$schema` 문자열, 동일한 `execution` 객체, 그리고 `workspaceRoot` 인자를 받는 도구마다 반복되는 동일한 설명 문자열이다. 네 행의 처분은 §4-7 이 한 단계로 다룬다.

## 2. 근거

근거 문서 §4.4 가 실제 `tools/list` 호출과 소스 양쪽으로 확인했다. 이 계획을 쓰면서 `src/mcp/server.ts:631-634` 를 다시 읽어 `description` 이 없다는 것을 확인했다.

현재 상태를 재는 명령이다. MCP 서버를 띄우고 `tools/list` 를 호출해 `description` 이 비어 있지 않은 도구 수와 `title !== name` 인 도구 수를 세면 된다. 소스만으로 보려면 다음으로 충분하다.

```
grep -n "registerTool(name" src/mcp/server.ts
grep -n "description" src/mcp/schemas.ts
```

**설명을 붙이는 문법은 이미 이 저장소에서 쓰이고 있다.** `src/mcp/server.ts:40-43` 의 `WORKSPACE_ROOT_SCHEMA` 가 `.describe(...)` 로 인자 설명을 달고 있다. 인자에는 쓰면서 도구에는 쓰지 않은 상태다.

**설명을 둘 자리도 이미 있다.** `src/mcp/schemas.ts` 의 `toolSpecs` 레지스트리가 모든 명령의 SSOT 이며, 그 파일 머리말이 CLI 명령 집합과 MCP 도구 집합이 이 레지스트리에서 파생되어 어긋날 수 없다는 무드리프트 계약(REL-ARCH-002)을 선언한다. `ToolSpec` 인터페이스에는 아직 `description` 필드가 없다. 새 계층을 만들지 않고 이 레지스트리를 넓히는 것이 옳다.

**상용구 네 행 중 저장소가 직접 쓰는 것은 둘뿐이다.** 착수 시점에 확인했다.

| 상용구 | 저장소가 쓰는가 | 확인 |
|---|---|---|
| `title` 이 `name` 과 동일 | 쓴다 | `src/mcp/server.ts:632` 의 `title: name` |
| `workspaceRoot` 의 동일 설명 문자열 | 쓴다 | `src/mcp/server.ts:40-43` 의 `WORKSPACE_ROOT_SCHEMA` — 이미 한 상수를 공유한다 |
| `"$schema"` | 쓰지 않는다 | `grep -rn '\$schema' src/mcp/` 가 0건. 스키마 직렬화가 붙이는 값이다 |
| `"execution"` | 쓰지 않는다 | `grep -rn 'taskSupport\|"execution"' src/mcp/` 가 0건. SDK 가 붙이는 값이다 |

뒤의 둘은 저장소 코드에 자리가 없으므로, 처분하려면 SDK 나 직렬화 설정을 통해야 한다. §4-7 이 그 확인을 한 단계로 묶는다.

## 3. 목표 상태

**`mcpName` 을 가진 모든 `ToolSpec` 이 비어 있지 않은 `description` 을 갖고, 등록부가 그것을 SDK 에 전달한다.** 설명은 세 가지를 말한다. 이 도구가 무엇에 답하는가, 이름이 비슷한 이웃 도구 대신 이것을 골라야 하는 경우는 언제인가, 그리고 무엇을 바꾸는가(읽기 전용인지, 어떤 파일을 쓰는지).

레지스트리에 설명이 있으므로 무드리프트 계약이 그것까지 덮는다. 설명이 빠진 도구는 등록 시점이 아니라 테스트에서 걸린다.

**상용구 네 행은 각각 처분이 정해져 기록된다.** 생략할 수 있는 것은 생략하고, SDK 나 프로토콜이 요구해 생략할 수 없는 것은 그 사실이 §5 에 남는다. 판정 없이 비워 두지 않는다 — 그러면 다음 사람이 같은 조사를 처음부터 반복한다.

## 4. 작업 단계

1. 요구를 `docs/spec/` 에 등록한다. AC 에 "MCP 로 노출되는 모든 도구가 비어 있지 않은 설명을 갖는다"와 "설명이 이웃 도구와의 선택 기준을 포함한다"를 검사 가능한 형태로 적는다. 후자는 기계 검사가 어려우므로 서브에이전트 검토를 증거로 둔다.
2. **실패하는 테스트를 먼저 쓴다.** `toolSpecs` 를 순회해 `mcpName` 이 있는 모든 항목의 `description` 이 비어 있지 않을 것, 그리고 `tools/list` 응답의 모든 도구가 비어 있지 않은 `description` 을 가질 것을 단언한다. 이 시점에서 실패를 확인한다.
3. `ToolSpec` 에 `description: string` 을 필수 필드로 추가한다. 선택 필드로 두면 새 도구가 설명 없이 들어온다.
4. `readSpec` · `mutationSpec` 등 spec 빌더의 시그니처를 넓힌다. 컴파일이 깨지는 자리가 곧 설명을 써야 할 자리다.
5. 도구별 설명을 쓴다. 짝을 이루거나 이름이 가까운 도구는 **함께** 쓴다 — 어느 쪽을 고를지가 설명의 핵심이다. 대응하는 CLI 명령이 `.description(...)` 을 이미 갖고 있으면 그것을 출발점으로 삼되 그대로 복사하지 않는다. CLI 설명은 `--help` 한 줄용이라 선택 기준을 담지 않는다.
6. 등록부가 설명을 전달하게 한다. `src/mcp/server.ts:631-634` 에서 `description` 을 넘긴다.
7. **상용구 네 행을 한 단계로 처분한다.** 행마다 순서가 같다 — (a) 저장소 코드가 그 값을 쓰는지 확인하고, (b) SDK 나 프로토콜이 필수로 요구하는지 확인하고, (c) 생략 가능하면 생략하고 아니면 유지 사유를 §5 에 기록한다. **확인 없이 지우지 않는다.**

   | 행 | 지금 아는 것 | 이 단계에서 확인할 것 |
   |---|---|---|
   | `title` | `server.ts:632` 가 `title: name` 을 직접 쓴다 | `registerTool` 의 타입에서 `title` 이 선택인지, 생략했을 때 클라이언트 표시가 `name` 으로 떨어지는지 |
   | `"$schema"` | 저장소 코드에 없다. 스키마 직렬화가 붙인다 | 직렬화 설정으로 끌 수 있는지, 껐을 때 클라이언트가 입력 스키마를 계속 받아들이는지 |
   | `"execution"` | 저장소 코드에 없다. SDK 가 붙인다 | SDK 버전이 그 필드를 프로토콜 필수로 다루는지. 필수이면 그대로 두고 사유만 적는다 |
   | `workspaceRoot` 설명 | 이미 `WORKSPACE_ROOT_SCHEMA` 한 상수를 공유한다 | 중복 제거는 이미 되어 있으므로 **손대지 않는다.** 이 행을 다시 줄이려면 인자 설명 자체를 없애야 하고 그것은 §7 의 7번이 금지한다 |

   뒤의 두 행은 저장소 밖 설정에 달려 있으므로, 끌 수 없다는 것이 확인되면 그것으로 이 행의 처분은 끝난다. **끌 수 있더라도 클라이언트 호환이 확인되지 않으면 끄지 않는다** — 이 항목은 정확도 과제이고 상용구 정리는 부수적이다.
8. 전체 스위트를 돌려 회귀 0건을 확인한다. `tools/list` 의 크기 변화를 기록해 둔다. 설명을 붙이면 그 페이로드는 **커진다**(§6 참조).
9. 검증 서브에이전트에게 원본 요구와 diff 만 준다. 설명이 도구의 실제 동작과 일치하는지, 이웃 도구와의 선택 기준이 실제로 갈리는지를 소스와 대조하게 한다. 작성자의 결론은 주지 않는다.
10. 항목 12 를 시작하기 전에 이 항목을 닫는다. 도구가 자기를 설명하면 스킬 본문에서 뺄 수 있는 문장이 달라진다.

## 5. 완료 조건

- `mcpName` 을 가진 모든 `ToolSpec` 이 비어 있지 않은 `description` 을 갖고, 그 사실이 테스트로 단언된다.
- `tools/list` 응답의 모든 도구가 비어 있지 않은 `description` 을 갖는다.
- **이름이 가까운 도구 짝 목록이 테스트에 리터럴로 고정되어 있고, 짝마다 세 단언이 통과한다.** (가) 두 설명이 서로 다른 문자열이다. (나) 각 설명이 그 도구에만 나타나는 구분 어구를 하나 이상 포함한다. (다) 그 구분 어구가 짝의 다른 쪽 설명에는 없다. 목록의 최소 구성원은 §1 이 이름으로 든 셋이다 — (`list_requirements`, `search_requirements`) · (`workflow_pipeline_status`, `workflow_pipeline_tail`) · (`get_active_target`, `summarize_target`). 한 짝의 설명을 다른 쪽과 같게 만들거나 구분 어구를 빼면 실패한다. 그 상태를 만들어 실패하는 것을 한 번 확인한다.
- 위 단언이 잡는 것은 설명이 **비었거나 서로 같거나 구분 어구가 빠진 경우**이며, 설명이 도구의 실제 동작과 맞는지는 판정하지 않는다. 그 의미 판정은 §4-9 의 독립 서브에이전트가 소스와 대조해 맡고, 결과는 요구의 Verification Evidence 에 남는다. **서브에이전트 검토만으로는 이 항목의 완료 조건이 성립하지 않는다** — 검토는 한 시점의 판단이고 이후의 설명 수정을 다시 재지 않는다.
- **상용구 네 행이 각각 처분되었다.** 행마다 "생략했다" 또는 "유지한다 + 사유"가 요구의 Change Notes 에 한 줄씩 있다. 사유는 확인한 사실이어야 한다 — "SDK 가 요구하는 것으로 보인다"는 사유가 아니다.
- 대응 요구가 `verified` 이고 검증 증거가 붙어 있다.

## 6. 틀렸을 때 무엇이 깨지는가

**설명이 도구의 실제 동작과 어긋나면 지금보다 나빠진다.** 지금은 설명이 없으므로 에이전트가 이름과 스키마를 보고 판단한다. 틀린 설명이 붙으면 그 판단을 틀린 쪽으로 끌고 간다. 특히 뮤테이션 도구의 설명이 무엇을 바꾸는지 잘못 적으면 읽기인 줄 알고 부르는 일이 생긴다. 검증에서 소스와 대조해야 하는 이유가 이것이다.

**바이트를 줄이려고 설명을 짧게 쓰면 이 항목의 목적이 사라진다.** 설명을 붙이면 `tools/list` 페이로드는 커진다. 상용구 정리로 일부가 상쇄되지만 순증일 가능성이 높다. **그래도 이 작업은 옳다.** 회수는 항목 12 에서 일어난다 — 도구 의미론이 도구에 있으면 스킬 본문이 그것을 다시 쓰지 않아도 된다. 세션당 한 번 적재되는 도구 설명이, 스킬 호출마다 적재되는 산문보다 싸다. 이 항목을 바이트 절감 과제로 취급하면 쓸모없는 한 줄짜리 설명이 100개 생기고 항목 12 는 뺄 문장을 찾지 못한다.

**상용구를 확인 없이 끄면 클라이언트가 도구를 못 읽는다.** `$schema` 와 `execution` 은 저장소 코드가 쓰지 않으므로 끄려면 직렬화나 SDK 설정을 건드려야 하고, 그 설정은 이 도구 집합 전체에 한 번에 적용된다. 잘못 끄면 100개 도구가 동시에 영향을 받으며, 증상은 이 저장소의 테스트가 아니라 클라이언트 쪽에서 나타난다. **확인되지 않으면 그대로 둔다.**

**`description` 을 선택 필드로 두면 계약이 서지 않는다.** 이후 추가되는 도구가 설명 없이 들어오고, 그것이 발견되는 시점은 누군가 그 도구를 잘못 골랐을 때다.

**레지스트리 밖에 설명 표를 따로 만들면 무드리프트 계약이 깨진다.** `toolSpecs` 가 CLI 와 MCP 표면의 SSOT 인 이유가 두 표면이 조용히 어긋나지 않게 하기 위해서다. 설명만 다른 곳에 두면 도구는 지워졌는데 설명은 남는 상태가 만들어진다.

## 7. 건드리지 말아야 할 것

이 항목은 **도구가 자기를 설명하게 만드는 작업**이다. 도구 표면을 줄이는 작업이 아니다.

1. **도구를 목록에서 빼서 페이로드를 줄이지 않는다.** `orchestrate_*` 와 `workflow_*` 는 오케스트레이터·파이프라인 run 안에서만 쓰이지만 세션마다 적재된다. 조건부 노출은 별도의 요구가 필요한 사안이며, 목록에 없는 도구는 호출할 수 없으므로 잘못 좁히면 그 경로가 통째로 막힌다. 이 항목의 범위가 아니다.
2. **`list_requirements` 와 `search_requirements` 를 합치지 않는다.** 근거 문서 §4.7 이 제외 판정했다. 입력 스키마와 반환 규모가 달라 서로 다른 질문에 답한다. 이 항목이 할 일은 그 차이를 **설명에 적는 것**이다.
3. **`workflow_pipeline_tail` 과 `workflow_pipeline_status` 도 합치지 않는다.** 같은 이유로 §4.7 이 제외 판정했다.
4. **`orchestrate_*` 의 CLI·MCP 양면 존재를 없애지 않는다.** 단일 소스 파생이며 §4.7 이 제외 판정했다.
5. **스킬의 게이트 결정표를 도구 설명으로 옮기지 않는다.** 게이트 식별자와 발동 지점의 대응은 스킬마다 술어가 다르므로 도구 설명이 대신할 수 없다. §4.7 이 제외 판정했다.
6. **`_shared/kiwi/waves-event.md` 의 이벤트 스키마 산문을 도구 설명으로 대체하지 않는다.** `orchestrate_journal_append` 와 `orchestrate_card_write` 의 `payload` 스키마에 필수 필드가 없어 도구가 형식을 검사하지 않는다. 설명 문장은 검사를 대신하지 못한다. 형식 강제를 도구로 옮기는 것은 별도 요구다.
7. **`inputSchema` 의 인자 설명을 이 항목에서 함께 늘리지 않는다.** 도구 수준 설명이 먼저다. 인자 설명은 도구 설명이 자리를 잡은 뒤 어디가 여전히 모호한지 보고 정한다. 이미 있는 `workspaceRoot` 설명도 줄이지 않는다 — 그 반복은 한 상수를 공유한 결과이지 중복 기재가 아니다.
