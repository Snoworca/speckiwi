# 10. SDS 생략 판정을 기계 대조로 바꾼다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 정확도 |
| 근거 | `docs/research/28.skills-mcp-end-to-end-audit.md` §3.9 의 2번 |
| 선행 항목 | 없음 |
| 대상 | 둘 다 (스킬 텍스트 + 코드) |

## 1. 지금 무슨 일이 일어나는가

1. `kiwi-tdd` 가 Phase 2 에 들어간다. 이 Phase 의 제목은 "SDS 저작 (체크리스트 의무)"이고 본문이 그 체크리스트를 건너뛸 수 없다고 선언한다(`skills/claude/kiwi-tdd/SKILL.md:89-91`).
2. 그런데 체크리스트의 **첫 항목이 면제 조항**이다. `:93` 이 자명한 변경이면 SDS 를 생략하고 `intent.md` 에 EARS 스텁만 남긴 뒤 Phase 3 으로 가라고 지시한다.
3. 자명한지 여부를 판정하는 주체는 그 스킬을 실행 중인 에이전트다. 그 판정으로 SDS 저작 한 벌이 사라지므로, **판정자와 그 판정의 수혜자가 같다.**
4. 대조할 분모도 증거 요구도 없다. `:93` 은 "trade-off 없는 자명한(trivial) 변경인가"만 묻고, 그 답을 어디에 어떻게 기록하라는 지시가 없다.
5. 같은 체크리스트의 7번 항목이 `speckiwi step validate <task>` 로 SDS advisory 0건을 확인하라고 요구한다(`:99`). 그러나 1번에서 Phase 3 으로 빠지면 7번에 도달하지 않는다. **면제가 검사보다 앞에 있다.**
6. 결과적으로 §0.4 의 절대 규칙("SDS 없이 테스트를 먼저 작성하지 않는다")이 같은 파일 안에서 무효화되고, 테스트만이 스펙이 되는 상태가 만들어진다. §0.4 가 막으려던 것이 바로 그 상태다.

**확인 결과 (팀리드 지시 항목): `speckiwi step validate` 는 SDS 파일 부재 자체를 거부하지 않는다.** 근거는 §2 에 적었다. 진단은 나오지만 severity 가 `warning` 이고, 그 명령의 종료 코드는 error 에서만 1이 된다. 즉 **기계는 이미 부재를 감지하고 있으나 아무것도 막지 않는다.** 이 사실이 이 항목의 작업 범위를 결정한다.

## 2. 근거

규칙과 그 면제가 같은 파일에 있다.

> `skills/claude/kiwi-tdd/SKILL.md:21`
> | §0.4 | **SDS 선행**. SDS(design.md) 없이 테스트를 먼저 작성하지 않는다 — 테스트만이 스펙이 되는 순간 reward-hacking에 노출된다. |

> `skills/claude/kiwi-tdd/SKILL.md:93`
> 1. **skip-gate 판정 먼저**: trade-off 없는 자명한(trivial) 변경인가? 그렇다면 SDS를 생략(skip)하고 intent.md에 EARS 스텁(SDS-AC 1~3문장)만 기록 후 Phase 3으로.

> `skills/claude/kiwi-tdd/SKILL.md:99`
> 7. `speckiwi step validate <task>`로 SDS advisory(SDS-W050~W053) 0건 확인.

`step validate` 의 실제 동작이다.

```ts

  if (!design.present) {
    out.push(advisory("SDS-W050", `SDS design.md is absent for tdd step '${stepName}'`, { filePath }));
    return out;
  }
```

```ts
// src/core/validator/validate-scoped.ts:84-88 (발췌)
function advisory(code: string, message: string, location: DiagnosticLocation = {}): Diagnostic {
  ...
    severity: "warning",
```

소스 자신이 그 성격을 적어 두었다.

```ts
// src/core/validator/validate-scoped.ts:184-188
  // @req FR-PARSE-033 — SDS advisories, tdd work-mode only. All warning severity:
  // they inform the step gate without ever flipping it on their own.
  const mode = workspace.stateFile ? parseStepState(workspace.stateFile.lines).mode : "wait";
  if (mode === "tdd") {
    diagnostics.push(...sdsAdvisories(stepName, options.design ?? { present: false, lines: [] }));
  }
```

그리고 CLI 표면이 error 에서만 실패한다.

```ts
// src/cli/commands/read.ts:1019
      if (result.errors.length > 0) command.setOptionValue("exitCode", 1);
```

`speckiwi step validate` 에는 `--fail-on-warning` 옵션이 없다. 그 옵션은 워크스페이스 전역 `speckiwi validate` 에만 있고(`src/cli/commands/read.ts:404`), SDS advisory 는 step 스코프 통과에서만 나오므로 전역 명령으로는 얻을 수 없다.

## 3. 목표 상태

판정을 없애지 않는다. 자명한 변경에 SDS 한 벌을 강요하는 것은 비용이다. 바꿀 것은 **판정이 기록되지 않고 대조되지 않는다는 점**이다.

- **생략 판정이 아티팩트에 남는다.** 무엇을 생략했고 왜 자명하다고 보았는지가 `intent.md` 또는 step 상태에 기록된다. 기록이 없으면 생략이 성립하지 않는다.
- **체크리스트의 검사 항목이 면제 경로에서도 실행된다.** 즉 `:93` 이 Phase 3 으로 곧장 보내지 않고, 생략 경로 전용의 축소된 검사를 거치게 한다.
- **기계가 대조한다.** `SDS-W050` 이 이미 부재를 감지하므로, 그 신호를 소비하는 자리를 만든다. 선택지는 셋이다.
  - (A) `speckiwi step validate` 에 `--fail-on-warning` 을 추가한다. 전역 `validate` 와 옵션 이름이 같아지고 구현이 작다.
  - (B) 생략 결정이 기록되어 있지 않은 상태에서 `SDS-W050` 이 나오면 severity 를 error 로 올린다. 즉 기록된 생략만 warning 으로 남긴다.
  - (C) 스킬 텍스트만 고쳐 7번 항목을 면제 경로에도 적용하고 코드는 건드리지 않는다.
  - **권고는 (B) 다.** (A) 는 모든 advisory 를 함께 막으므로 W051~W053 까지 차단되어 생략 경로가 아예 불가능해진다. (C) 는 판정 주체를 그대로 두므로 이 항목이 고치려는 것을 고치지 못한다.
- **`kiwi-tdd` 의 §0.4 와 Phase 2 첫 항목이 서로 모순되지 않는다.** §0.4 가 예외를 인정하는 문장을 갖거나, `:93` 이 §0.4 의 하위 조건임을 명시한다.

## 4. 작업 단계

1. 요구를 먼저 등록한다. 범위는 "SDS 생략이 기록된 결정일 때만 성립하고 기계가 그것을 대조한다"이다. 위 (A)/(B)/(C) 중 무엇을 채택할지 요구의 결정 사항으로 적는다.
2. **실패 테스트를 먼저 쓴다. 코드 축과 스킬 축 둘 다.**
   - 코드: `test/core/` 또는 `test/cli/` 관례를 따라, tdd 모드에서 `design.md` 가 없고 생략 기록도 없는 step 에 대해 `validateWorkspaceScoped` 가 **error** 를 내는지 단언한다. 생략 기록이 있으면 warning 에 머무는지도 단언한다. 현재는 항상 warning 이므로 전자는 red 다.
   - CLI: 같은 상황에서 `speckiwi step validate <task>` 의 종료 코드가 1인지 단언한다.
   - 스킬: `test/skills/` 관례로 네 사본(`skills/claude` · `skills/codex` · `skills/etc` · `.agents/skills`)의 `kiwi-tdd/SKILL.md` 에 생략 기록 의무와 그 검사 문장이 있는지 단언한다.
3. **실패를 확인한다.** `npx vitest run test/core/ test/cli/ test/skills/` 로 세 축 모두 red 임을 본다.
4. **최소 구현으로 통과시킨다.** 코드는 `src/core/validator/validate-scoped.ts` 의 `sdsAdvisories` 분기와 그 위 `advisory` 헬퍼만 손댄다. severity 를 인자로 받게 하거나 error 전용 헬퍼를 하나 더 둔다. `:184-188` 의 주석이 "All warning severity" 라고 적혀 있으므로 그 주석도 함께 갱신한다.
5. 스킬은 `skills/claude` · `skills/codex` · `skills/etc` 세 렌더링을 함께 고친다. Phase 2 체크리스트 1번과 7번, 그리고 §0.4 행을 손댄다.
6. `speckiwi skills mirror --write` 로 `.agents/skills/` 를 재생성한다.
7. 전체 스위트로 회귀를 확인한다. `FR-PARSE-033` 을 고정한 기존 테스트가 warning severity 를 단언하고 있을 수 있으므로 그 테스트를 먼저 찾는다.
8. 검증 서브에이전트에게 원본 요구와 diff 만 준다.

## 5. 완료 조건

- **기록 없이 SDS 를 생략한 step 이 자동으로 실패가 된다.** `design.md` 를 지우고 생략 기록도 없는 상태에서 `speckiwi step validate <task>` 가 비영(非零)으로 끝나는 것을 한 번 관찰한다.
- **기록된 생략은 계속 통과한다.** 생략 결정을 기록한 뒤 같은 명령이 0으로 끝나는 것을 관찰한다. 이것을 확인하지 않으면 이 항목은 면제를 없앤 것이지 대조로 바꾼 것이 아니다.
- 코드에서 severity 를 warning 으로 되돌리면 테스트가 red 가 된다.
- `kiwi-tdd` 의 §0.4 와 Phase 2 첫 항목이 같은 판정을 말한다. 스킬 테스트가 그 일치를 고정한다.
- `speckiwi skills mirror --check` 가 divergence 0 을 보고한다.

## 6. 틀렸을 때 무엇이 깨지는가

- **work-mode 가 `tdd` 가 아니면 SDS advisory 자체가 나오지 않는다**(`validate-scoped.ts:186-188`). 따라서 mode 를 `vibe` 나 `sdd` 로 두고 step 을 돌리면 이 게이트가 통째로 침묵한다. 증상은 조용하다. 알아차리는 방법은 `speckiwi mode` 로 현재 모드를 먼저 확인하는 것이며, 스킬의 Phase 0 이 이미 모드를 확인하므로 그 자리에 이 의존을 적어 둔다.
- **(B) 를 골랐는데 "생략 기록"을 읽는 경로가 `ParsedWorkspace` 밖에 있으면 구현이 커진다.** `design.md` 도 `ParsedWorkspace` 밖이라 표면이 따로 로드한다(`read.ts:1016` 의 `loadStepDesign`). 생략 기록을 `intent.md` 에 두면 같은 문제가 반복되므로, step 상태 파일처럼 이미 파싱되는 자리에 두는 편이 작다.
- **생략 기록의 형식을 자유 서술로 두면 다시 자기선언이 된다.** 증상은 모든 step 이 "자명함"이라는 한 줄을 갖는 것이다. 형식을 정형화하고, 기록에 무엇을 대조할지를 넣는다.
- **전제가 틀렸다면**, 즉 `step validate` 가 실제로는 부재를 error 로 낸다면 이 항목의 코드 작업은 불필요하다. 재확인 명령은 `grep -n "severity" src/core/validator/validate-scoped.ts` 와 `sed -n '1015,1020p' src/cli/commands/read.ts` 다.
- **(A) 를 골랐다면** W051~W053 까지 함께 차단되므로 200줄 상한 초과 같은 조언성 진단이 진행을 막는다. 증상은 SDS 를 쓴 step 이 오히려 통과하지 못하는 것이다.

## 7. 주의할 점

- **면제를 없애는 것이 목표가 아니다.** 자명한 변경에 SDS 한 벌을 요구하면 이 스킬의 쓸모가 줄어든다. 목표는 면제가 기록되고 대조되게 만드는 것이다.
- 이 항목은 코드를 바꾸므로 `docs/spec/` 의 요구가 반드시 먼저 있어야 한다. `FR-PARSE-033` 이 현재 이 동작을 소유하고 있으므로, 새 요구를 만들지 그 요구를 개정할지를 먼저 정한다. 기존 요구의 개정은 sdd 모드 작업이다.
- `advisory` 헬퍼는 `validate-scoped.ts` 안의 다른 진단(SRS-W045, STEP_DIRECT_CONFLICT 등)도 함께 만든다. severity 를 통째로 바꾸지 말고 SDS 분기에서만 갈라야 한다.
- `.agents/skills/**` 는 `skills/codex` 에서 생성된다(`src/core/skills/mirror-skills.ts:23-24`). 직접 편집하지 않는다.
