# 15. 파이프라인 이벤트 기록을 단일 경로로 모은다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 비용 |
| 근거 | `docs/research/28.skills-mcp-end-to-end-audit.md` §4.6 의 H-5 |
| 선행 항목 | 없음 |
| 대상 | 둘 다 (스킬 텍스트 + 코드) |

---

## 1. 지금 무슨 일이 일어나는가

같은 파일에 같은 이벤트를 쓰는 경로가 둘이고, 공용 문서가 그 사실을 자기 입으로 밝힌다.

> `skills/claude/_shared/kiwi/pipeline-event.md:169`
> `kiwi-orchestrator` 는 §5.1 의 손으로 짠 append 블록을 쓰지 않고 **MCP `workflow_pipeline_emit` 도구**로 emit 한다 — 같은 append 로직을 스킬 본문에 한 번 더 복제하지 않기 위해서다. 다른 모든 스킬은 §5.1 을 그대로 쓴다.

`§5.1` 은 Bash 블록이다. `git rev-parse --show-toplevel` 로 디렉터리를 정하고, 실패하면 cwd 의 `kiwi/`, 그것도 없으면 `$HOME/.kiwi` 로 내려간 뒤 `echo "$EVENT" >> "$PIPE_DIR/pipeline.jsonl"` 로 한 줄을 덧붙인다. `§5.2` 의 멱등성 검사도 `grep -q` 한 줄이다.

MCP 도구는 같은 일을 하면서 가드를 갖고 있다. `workflow_pipeline_emit` 의 입력 스키마에 `idempotencyKey` · `expectedSha256` · `dryRun` 이 **이미 있다**(`src/mcp/server.ts:400-410`). 뮤테이션 구현은 그 키를 이벤트에 구조화된 필드로 기록한다(`src/core/workflow/mutation.ts:642`).

두 경로는 세 군데에서 다르다.

- **파일 위치.** MCP 도구는 해소된 워크스페이스 root 아래의 `kiwi/pipeline.jsonl` 을 기본값으로 쓴다(`src/mcp/tools/mutation-tools.ts:451-458`). shell 블록은 위의 3단계 해소를 거치며 마지막 단계에서 홈 디렉터리로 내려간다. git root 를 찾지 못하고 cwd 에 `kiwi/` 도 없는 실행에서 두 경로는 **서로 다른 파일**에 쓴다.
- **멱등성.** shell 은 파일 전체를 `run_id` 부분 문자열로 훑고, 도구는 구조화된 멱등 키를 기록한다.
- **동시 쓰기.** 도구에는 `expectedSha256` 이 있고 shell 의 `>>` 에는 그에 해당하는 것이 없다.

여기에 렌더링 사이의 어긋남이 하나 더 있다. `skills/codex/kiwi-pipeline/SKILL.md` 는 `workflow_pipeline_tail` · `workflow_pipeline_status` 를 정상 경로로 지시하지만(`:13`, `:21`, `:229`), `skills/claude/kiwi-pipeline/SKILL.md` 는 `workflow_pipeline_*` 도구를 **한 번도 이름으로 부르지 않는다.** 같은 스킬의 두 렌더링이 파이프라인 파일을 읽는 방법을 다르게 지시하고 있다.

## 2. 근거

근거 문서 §4.6 의 H-5 가 두 경로의 존재와 스킬 1회당 Bash 왕복 비용을 기록했다. 이 계획을 쓰면서 위에 인용한 공용 문서 줄과 도구 스키마·뮤테이션 구현·기본 경로를 소스에서 직접 확인했다.

재는 명령이다.

```
grep -rn "workflow_pipeline_emit" skills/
grep -rn "pipeline.jsonl" skills/claude/_shared/kiwi/pipeline-event.md
grep -rn "workflow_pipeline_" skills/claude/kiwi-pipeline/SKILL.md
```

**shell 경로가 폴백으로 필요한지에 대한 판단.** 필요하다. 그리고 그 판단은 이미 문서에 있다.

> `skills/claude/_shared/kiwi/pipeline-event.md:171`
> MCP 서버가 부재하면 §5.1 의 shell **fallback** 을 그대로 쓴다. emit 은 §5.5 대로 **best-effort** 이므로, 도구 부재가 run 의 실패가 되어서는 안 된다.

emit 은 실패해도 본 작업을 실패시키지 않는 best-effort 연산이다. MCP 가 없는 환경에서 이벤트를 아예 남기지 못하면 파이프라인 추적이 끊기고, 다음 스킬을 고르는 근거가 사라진다. **그러므로 shell 블록을 제거하지 않는다.** 이 항목이 바꾸는 것은 존재 여부가 아니라 **기본값**이다.

## 3. 목표 상태

**모든 `kiwi-*` 스킬의 정상 경로가 MCP `workflow_pipeline_emit` 이다.** `kiwi-orchestrator` 만의 예외가 아니라 공용 규정이 된다.

**shell 블록은 조건이 명시된 폴백으로 남는다.** 진입 조건은 하나다 — MCP 도구를 쓸 수 없는 경우. 조건이 문장으로 적혀 있고, 폴백을 쓴 실행은 그 사실이 이벤트나 보고에 드러난다.

**두 경로가 같은 파일에 쓴다.** 파일 위치 해소 규칙이 한 곳에서 정의되고 두 경로가 그것을 따른다.

**`kiwi-pipeline` 의 세 렌더링이 파이프라인 파일을 같은 방법으로 읽으라고 지시한다.**

## 4. 작업 단계

1. 요구를 `docs/spec/` 에 등록한다. 공용 계약(`_shared/kiwi/pipeline-event.md`)의 변경과 각 스킬의 emit 지시 변경을 같은 요구 아래 둔다.
2. **두 경로의 파일 위치가 실제로 갈리는 조건을 먼저 확정한다.** MCP 도구의 기본 경로와 `§1` 의 3단계 해소가 어떤 입력에서 다른 결과를 내는지 재현 테스트로 확인한다. 갈린다면 코드와 문서 중 어느 쪽을 맞출지 정한다. `§1` 의 홈 폴백은 git 저장소 밖에서 도는 실행을 위한 것이므로, 도구가 그 경우를 어떻게 다루는지 확인한 뒤에 판단한다.
3. 실패하는 테스트를 먼저 쓴다. 공용 문서가 MCP 경로를 정상 경로로 규정하고 shell 블록을 조건부 폴백으로 표시할 것, 그리고 emit 을 지시하는 모든 스킬이 그 규정을 가리킬 것을 `test/skills/` 아래에서 단언한다.
4. `_shared/kiwi/pipeline-event.md` 를 고친다. `§5.1` 을 폴백으로 재배치하고 `§5.6` 의 "다른 모든 스킬은 §5.1 을 그대로 쓴다"를 뒤집는다. `§5.2`~`§5.4` 의 멱등성·dry-run·재진입 키 규정은 두 경로 모두에 적용되도록 표현을 맞춘다 — 도구의 `idempotencyKey` 가 `§5.4` 의 `{run_id}#r{n}` 형태를 그대로 받는지 확인한다.
5. 파일 위치 규칙을 `§1` 한 곳에 두고, 도구 호출 시 `path` 인자로 그 결과를 넘길지 도구 기본값에 맡길지 명시한다. 두 방법을 섞지 않는다.
6. emit 을 지시하는 각 스킬의 종료 절을 고친다. 인라인 bash 를 담고 있는 스킬이 있으면 공용 문서 참조로 바꾼다.
7. `kiwi-pipeline` 의 claude 렌더링에 `workflow_pipeline_status` · `workflow_pipeline_tail` 읽기 지시를 넣어 codex 렌더링과 맞춘다. 이때 항목 13 이 `workflow_pipeline_next` 를 없애기로 했으므로 그 도구를 새로 지시하지 않는다.
8. **세 렌더링을 함께 고친다.** `skills/claude` · `skills/codex` · `skills/etc` 를 같은 커밋에서 수정한다. 공용 파일의 절 번호가 렌더링마다 다르므로(claude 와 codex 의 `§5.6` 줄 번호가 다르다) 줄 번호가 아니라 절 번호로 참조한다.
9. `speckiwi skills mirror --check` 로 발산을 확인하고 `speckiwi skills mirror --write` 로 `.agents/skills/` 를 재생성한다.
10. 전체 스위트를 돌려 회귀 0건을 확인한다. 검증 서브에이전트에게 원본 요구와 diff 만 준다.

## 5. 완료 조건

- 공용 문서가 MCP `workflow_pipeline_emit` 을 모든 스킬의 정상 경로로 규정한다.
- shell 블록이 남아 있고, 그 진입 조건이 "MCP 도구 사용 불가"로 문장에 적혀 있다.
- 두 경로가 같은 입력에서 같은 파일에 쓴다는 것이 테스트로 단언된다.
- 멱등성·dry-run·재진입 키 규정이 두 경로 모두에 적용되는 표현으로 되어 있다.
- `kiwi-pipeline` 세 렌더링이 파이프라인 파일을 같은 방법으로 읽으라고 지시한다.
- `speckiwi skills mirror --check` 가 발산 0건을 보고한다.
- 대응 요구가 `verified` 이고 검증 증거가 붙어 있다.

## 6. 틀렸을 때 무엇이 깨지는가

**shell 블록을 지우면 MCP 가 없는 환경에서 이벤트가 남지 않는다.** 그 환경은 `kiwi-pipeline` 이 다음 단계를 고르는 근거를 잃고, 재개하는 세션은 직전 실행이 무엇이었는지 알 방법이 없다. emit 이 best-effort 라는 규정 때문에 그 실패는 조용하다. **무조건 제거가 답이 아니라는 것이 이 항목의 핵심 판단이다.**

**두 경로가 다른 파일에 쓰면 저널이 갈린다.** 한 파이프라인의 이벤트가 두 파일로 나뉘면 어느 쪽도 완전하지 않고, 어느 쪽도 자기가 불완전하다는 것을 말하지 않는다. `§1` 의 run-root pin 규정이 있는 이유가 이것이며, 두 writer 가 그 규정을 각각 해석하면 pin 이 성립하지 않는다.

**멱등성 규정을 한쪽 경로에만 맞추면 재진입이 깨진다.** `§5.4` 는 재진입 실행이 `{run_id}#r{n}` 키를 쓰고 bare `run_id` 를 재사용하면 skip 되어 체인이 볼 새 `TASK_DONE` 이 생기지 않는다고 규정한다. 도구의 멱등 키가 이 형태를 받지 못하면 재진입이 조용히 누락된다.

**한 렌더링만 고치면 근거 문서 §5.1 이 기록한 실패 형태가 재발한다.** `kiwi-pipeline` 의 claude·codex 렌더링이 지금 이미 그 상태다.

## 7. 건드리지 말아야 할 것

1. **emit 의 best-effort 성격을 바꾸지 않는다.** `§5.5` 가 emit 실패를 본 작업의 실패로 이어지지 않게 규정한다. 단일 경로로 모으면서 emit 을 필수 성공으로 승격시키면, 도구 부재가 정상 종료한 run 을 실패로 뒤집는다.
2. **`kiwi-orchestrator` 의 run 수준 emit 키 규정을 건드리지 않는다.** `§5.6` 의 bare `{run_id}` 와 하위 unit·lane 의 `--no-pipeline-emit` 억제 규칙은 키 충돌을 막는 계약이다.
3. **`_shared/kiwi/waves-event.md` 의 이벤트 스키마 산문을 줄이지 않는다.** 근거 문서 §4.7 이 제외 판정했다. `orchestrate_journal_append` 의 `payload` 스키마에 필수 필드가 없어 도구가 형식을 검사하지 않으므로, 그 산문이 스키마를 강제하는 유일한 수단이다. 파이프라인 이벤트를 도구 경로로 모으는 것과 웨이브 저널의 형식 강제는 다른 문제다.
4. **`§5.2`~`§5.4` 의 멱등성·dry-run·재진입 규정 자체를 줄이지 않는다.** 표현을 두 경로에 맞추는 것이 이 항목의 일이고, 규정의 내용을 덜어내는 것은 아니다.
5. **각 스킬의 게이트 결정표를 emit 절과 함께 손보지 않는다.** §4.7 이 제외 판정했다. 이 항목의 편집 범위는 종료 시점의 emit 지시 문장이다.
