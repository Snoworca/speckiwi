## 1. 지금 무슨 일이 일어나는가

1. 에이전트가 `kiwi-orchestrator` 로 run 을 시작한다.
2. run 이 진행되는 동안 저널 `.kiwi/waves.jsonl` 에 줄이 쌓인다.
3. run 이 끝날 때 `§V.final-verify` 가 run 창 종료 리뷰를 1회 수행하고, run 종료 줄에 `terminal_review {skill, base, head, verdict}` 를 싣는다.
4. 그 종료 줄이 계약대로 쓰였는지 판정하는 검증기 `validateWavesJournal` 이 저장소에 실재하고 CLI 와 MCP 양쪽에 배선되어 있다.
5. **`kiwi-orchestrator` run 에서는 그 검증기가 이미 쓰기 경로 위에 있다.** `orchestrate_journal_append` 는 새 줄을 붙인 저널을 후보 파일로 만들어 `validateWavesJournal` 에 통과시키고, error 급 진단이 하나라도 나오면 쓰기를 거절한다. 그래서 `terminal_review` 가 빠졌거나 방면하지 않는 verdict 를 실은 완료 종료 줄은 **애초에 착지하지 못한다.** 이 계획의 초판은 그렇지 않다고 적었고, 그것은 틀렸다.
6. **`kiwi-wave-master` run 에서는 그 검사가 아무 줄도 보지 않는다.** 후보 저널을 파싱하는 호출이 엔진을 `kiwi-orchestrator` 로 고정하는데, 파서는 엔진이 다른 줄을 건너뛴다. wave-master 의 줄은 엔진이 다르므로 검사 대상 집합이 통째로 비고, 빈 집합에서는 진단이 나오지 않는다. 그 스킬 본문은 필수 두 필드가 빠진 종료 줄을 검증기가 거부한다고 적지만, 그 경로에서는 거부되지 않는다.
7. **종료 줄을 아예 쓰지 않은 run 은 어느 쪽에서도 걸리지 않는다.** `waves-validate.ts` 의 규칙은 전부 존재하는 줄을 보고 발화한다. 줄이 없으면 진단도 없다. 이것은 저장소가 이미 알고 기록해 둔 종류의 공백이다.
8. 같은 형태가 `orchestrate_*` 도구 여럿에 걸쳐 있다. 라운드 기록·라우팅 동결·handoff 검증·readiness 검사·이슈 원장을 수행할 도구가 등록되어 있으나 호명되지 않는다.
9. 그 자리를 대신하는 것은 에이전트의 산문 독해다. 게이트 이름은 코드에 등재되어 있지만 그 이름을 발화시키는 술어는 코드에 없다.
10. 별개로, validation ERROR 를 받아 진행을 중단하는 게이트 `validate-spec-error` 는 `kiwi-srs-sync` 만 선언한다. 구현·리뷰·승격 사슬의 일곱 스킬은 선언하지 않는다.

## 2. 근거

**검증기는 실재하고 배선되어 있다.**

> `src/core/orchestrator/waves-validate.ts:641`
> `export function validateWavesJournal(view: WavesJournalView): WavesDiagnostic[] {`

같은 함수의 `:647` 이 `checkTerminalReview(view, diagnostics);` 를 호출한다. CLI 는 `src/cli/commands/orchestrate.ts:1921` 의 `addCommonOptions(orchestrate.command("validate"))` 이고, MCP 도구 이름은 같은 파일 `:282` 에 있다.

> `src/cli/commands/orchestrate.ts:282`
> `{ tool: "orchestrate_validate", path: ["validate"], kind: "read", options: [RUN_ID_OPTION, JOURNAL_OPTION, o("--strict", "strict", "boolean")] },`

**그리고 그 검증기는 이미 저널 쓰기 경로 위에 있다.** 이 계획을 개정하면서 소스에서 확인했다. `orchestrate_journal_append`(`:252` 의 바인딩)가 부르는 함수는 `:949` 의 `appendWavesLine` 이고, 그 함수의 doc 주석 첫 줄이 의도를 밝힌다 — "Appends one stamped line, validating the **resulting** journal before the write lands." 실제 거절은 두 줄이다.

> `src/cli/commands/orchestrate.ts:980-981`
> `    const diagnostics = await validateProspectiveJournal(root, relativePath, runId, stamped);`
> `    if (diagnostics.some((entry) => entry.severity === "error")) {`

`validateProspectiveJournal`(`:1031`)은 후보 파일을 만들어 파싱한 뒤 `:1047` 에서 `validateWavesJournal(view)` 를 부른다. `terminal-review-loop-missing` 은 error 급이므로(`waves-validate.ts:477`) 그 줄은 쓰이지 않는다. 거절 시 후보 파일을 지우므로 저널은 바이트 단위로 그대로이며, 그 성질을 `test/cli/orchestrate-journal-outcome.fr-node-165.test.ts` 의 AC-5 블록이 단언한다. 스킬도 이 경로를 벗어나지 않는다 — `skills/claude/kiwi-orchestrator/SKILL.md:166` 이 직접 append 를 금지 행동의 닫힌 목록에 넣고, `:182` 가 "두 저널 쓰기는 모두 `orchestrate journal append` 도구를 통과"한다고 적는다.

**그러나 그 검사는 엔진 하나만 본다.**

> `src/cli/commands/orchestrate.ts:1046`
> `    const view = await parseWavesJournal(root, { runId, engine: "kiwi-orchestrator", relativePath: candidateRelative });`

엔진이 리터럴로 고정되어 있고, 파서는 다른 엔진의 줄을 건너뛴다.

> `src/core/orchestrator/waves-journal.ts:73`
> `    if (engineOf(event) !== options.engine) continue;`

`engineOf` 는 `engine` 필드가 `kiwi-orchestrator` 가 아닌 모든 줄을 `DEFAULT_ENGINE` 으로 읽고(`:36`), 그 기본값은 `kiwi-wave-master` 다(`journal-schema.ts:21`). 그리고 `orchestrate_journal_append` 바인딩에는 `--engine` 이 없다(`:252`). 따라서 wave-master run 이 이 도구로 종료 줄을 append 하면 후보 뷰가 비고, 빈 뷰에서 나오는 진단은 0건이며, 어떤 줄도 거절되지 않는다. `skills/claude/kiwi-wave-master/SKILL.md:325` 는 그 두 필드가 빠진 종료 줄을 "검증기가 거부한다"고 적는데, 이 경로에서 그 문장은 참이 아니다.

**부재는 어느 규칙도 진단하지 않는다.** `waves-validate.ts` 의 검사는 전부 `view.lines` 를 순회하며 조건에 맞는 **줄이 있을 때** 진단을 낸다(`checkCompletionGate` · `checkFinalVerify` · `checkTerminalReview` 모두 같은 형태다). 종료 줄이 없는 run 은 진단 0건으로 읽힌다. 이 종류의 공백은 저장소가 이미 알고 있다 — `checkTerminalReview` 의 주석이 "Closing it honestly means diagnosing the RUN … which is a separate rule about a different subject" 라고 적어 두었다.

**요구 자신이 이 위험을 문장으로 예견해 두었다.**

> `docs/spec/50.nodejs-implementation.srs.md:12099` (`FR-NODE-188`)
> The refusal SHALL be reached from the run-close path a caller actually executes, not only from a pure predicate, because a validator nothing invokes is the same absent guarantee in a better disguise.

**게이트 이름 목록은 술어가 아니다.**

> `src/core/orchestrator/auto-gate.ts:30`
> `export const GATE_IDS = [`

이 배열은 문자열 리터럴만 담으며 `:140` 에서 `export type GateId = (typeof GATE_IDS)[number];` 로 타입만 만든다. `"requirement-not-ready"`(`:56`) · `"post-merge-index-drift"`(`:70`) · `"plan-coverage-unclosed"`(`:71`) 는 이름으로만 존재하고, 무엇이 참일 때 발화하는지는 이 파일에 없다.

**스킬은 검증기의 존재를 알면서 실행을 지시하지 않는다.** `skills/claude/kiwi-orchestrator/SKILL.md:493` 은 R-PLAN rung 의 종료를 다루면서 "이 rung 의 종료는 검증기에 보이지 않고"라고 적는다. 같은 줄이 지시하는 명령은 SRS 쪽 `validate` → `sync-index` → `validate --fail-on-warning` 이며, 그 결과를 받는 게이트의 술어는 `:822` 가 정한 인덱스 드리프트다.

> `skills/claude/kiwi-orchestrator/SKILL.md:822`
> `sync_index` 가 실행된 뒤에도 `validate --fail-on-warning` 이 드리프트를 보고하면 `post-merge-index-drift` 로 run 을 중단한다.

**`validate-spec-error` 를 선언하는 스킬은 하나다.** `kiwi-srs-sync` 의 세 렌더링(`skills/claude/…:38`, `skills/codex/…:87`, `skills/etc/…:90`)과 그 미러뿐이며, 다른 스킬 파일에는 없다.

> `skills/claude/kiwi-srs-sync/SKILL.md:38` 중
> `{gate_id: "validate-spec-error", reason: "validate_spec ERROR 잔존 시 mutation 0건 종료 (§10.1 step 0)"}`

**반증 후보 둘은 확인되었고 무너졌다.** 이 계획을 세우면서 다시 측정했다.

| 반증 후보 | 측정 | 결과 |

**반증 후보 하나가 새로 확인되었고, 무너지지 않았다.** 근거 문서에 없는 사실이므로 여기에 적는다. `src/core/workflow/read.ts:393` 의 `wavesJournalDiagnostics` 가 `validateWavesJournal` 을 부르고, 이것이 `workflowDoctor` 에 들어간다. 그러나 세 조건이 붙는다 — (a) `runId` 가 주어질 때만 실행되고(`:390` 의 `if (!runId) return [];`), (b) 어떤 예외든 삼켜 빈 배열을 돌려주며(`:394` 의 `catch { return []; }`), (c) `workflow_doctor` 를 호명하는 스킬은 `kiwi-planner` 뿐이고 그것은 계획 무결성 용도이며 `runId` 를 넘기지 않는다. **따라서 §4 의 작업은 이 경로에 의존해서는 안 된다.**

## 3. 목표 상태

목표는 셋이고, 강제하는 힘이 서로 다르므로 나누어 적는다.

1. **엔진과 무관하게 계약을 어긴 종료 줄이 착지하지 못한다.** `validateProspectiveJournal` 이 후보 뷰를 만들 때 엔진을 리터럴로 고정하지 않고 **append 되는 줄 자신의 엔진**으로 파싱한다. 그러면 `kiwi-orchestrator` 에서 이미 성립하는 거절이 `kiwi-wave-master` run 에서도 성립하고, `kiwi-wave-master/SKILL.md:325` 의 문장이 그 경로에서도 참이 된다. **이것이 이 항목의 유일한 기계 보장이며 코드 변경이다.**
2. **run 종료 경로가 `orchestrate_validate --strict` 를 실행하고 그 결과로 분기하라는 지시가 네 사본에 존재한다.** 이 목표는 "지시가 존재한다"까지이고 그 이상이 아니다. 에이전트가 그 문장을 읽고도 도구를 부르지 않으면 run 은 정상 완료되고 계약 테스트는 초록이다. 이 지시가 남는 이유는 1번이 닫지 못하는 두 경우 — 종료 줄을 **아예 쓰지 않은** run, 그리고 이 항목이 착지하기 전 버전이 쓴 저널 — 을 사람에게 드러내기 위해서다. **실제 강제는 별도 요구로 분리하며 그 사실을 §7 에 적는다.**
3. **validation ERROR 를 받아 멈추는 게이트가 구현·리뷰 사슬에도 선언된다.** SRS 오류를 안은 채 승격이 진행되지 않는다.

목표 1과 목표 2의 강도 차이를 흐리지 않는다. 목표를 "실행하고 분기한다"로 적고 완료 조건을 "그 문장이 있다"로 두는 상태가 가장 나쁘다 — 이 저장소의 요구 자신이 그것을 금지한다(§2 의 `FR-NODE-188` 인용).

## 4. 작업 단계

0. **요구를 먼저 등록한다.** 이 항목에 대응하는 요구를 `docs/spec/` 에 만들고 AC 를 쓴다. AC 는 §3 의 세 목표에 각각 대응한다 — "wave-master 엔진의 계약 위반 종료 줄이 append 에서 거절된다", "네 사본 전부에 `orchestrate_validate --strict` 실행 지시가 있다", "구현 사슬 일곱 스킬이 `validate-spec-error` 를 선언한다". **"실행하지 않은 run 이 실패로 판정된다"를 AC 로 쓰지 않는다** — 이 항목이 그것을 보장하지 않기 때문이다(§3 목표 2, §7). 요구 ID 를 작업 요약에 적는다.

1. **현재 값을 측정해 기준선으로 남긴다.** 계획에 수치를 적지 않고 명령을 적는다.
   ```
   grep -rho "orchestrate_[a-z_]*" skills/ .agents/skills/ | sort | uniq -c | sort -rn
   grep -rn "orchestrate validate\|orchestrate_validate" skills/ .agents/skills/
   grep -rn "validate-spec-error" skills/ .agents/skills/
   ```
   세 명령의 출력을 요구의 Change Notes 에 붙인다. 착수 시점의 값이 무엇이었는지가 나중에 필요하다.

2. **엔진 고정을 먼저 닫는다 — 이 항목의 유일한 코드 변경이다.**
   - **실패하는 테스트를 먼저 쓴다.** `test/cli/` 에 요구 ID 를 붙인 파일을 만들고, `engine` 이 `kiwi-wave-master` 인 run 의 완료 종료 줄에서 `terminal_review` 를 뺀 payload 로 `orchestrate journal append` 를 부른다. 오늘은 `written: true` 로 통과하므로 **red 가 된다.** 같은 payload 를 `engine: "kiwi-orchestrator"` 로 바꾸면 오늘도 거절되는지 대조군으로 함께 단언해, 이 red 가 엔진 때문임을 고정한다.
   - **최소 구현.** `src/cli/commands/orchestrate.ts:1046` 이 `parseWavesJournal` 에 넘기는 `engine` 을 리터럴에서 **append 되는 payload 자신의 엔진**으로 바꾼다. 해소 규칙은 새로 만들지 않고 `waves-journal.ts:36` 의 `engineOf` 를 쓴다 — 그 함수가 이미 "`kiwi-orchestrator` 가 아니면 `kiwi-wave-master`" 를 정의한다. green 을 확인한다.
   - **회귀.** `test/cli/orchestrate-journal-outcome.fr-node-165.test.ts` 와 `test/core/orchestrator/terminal-review.fr-node-188.test.ts` 를 돌린다. 이 변경은 지금까지 검사 대상이 아니던 줄을 검사 대상으로 넣으므로, 기존 픽스처 중 엔진이 다른 줄이 섞인 것이 여기서 드러난다. 드러나면 픽스처가 틀린 것인지 이 변경이 틀린 것인지를 먼저 가른다.

3. **스킬 계약 테스트를 먼저 쓴다.** `test/skills/` 아래에 새 파일을 만든다. 관례는 이미 있다 — `test/skills/terminal-review-loop.fr-flow-131.test.ts` 가 `["skills/claude", "skills/codex", "skills/etc", ".agents/skills"]` 네 사본을 읽고 종료 리뷰 계약을 단언한다. 그 파일의 사본 목록과 `section()` 헬퍼를 그대로 쓴다. 단언은 이렇게 만든다.
   - 네 사본 각각의 `§V.final-verify` 절 안에 `orchestrate_validate` 또는 `orchestrate validate` 가 있다.
   - 같은 절 안에서 그 호출과 `terminal_review` 가 같은 창(예: 400자) 안에 함께 나온다. 이름만 스쳐 지나가는 문장으로 초록이 되지 않게 한다.
   - 검증기가 거부했을 때 무엇을 하는지를 지명하는 게이트 이름(`terminal-review-loop-missing`)이 그 창 안에 있다.
   - 이름 검색 하나로 초록이 되지 않는지 확인한다. `terminal-review-loop.fr-flow-131.test.ts:12-17` 이 같은 함정을 기록해 두었으니 그 방식대로, 새로 도입하는 문구가 착수 전 0회임을 먼저 세어 주석에 적는다.
   - **이 단언들이 무엇을 보장하고 무엇을 보장하지 않는지 테스트 주석에 적는다.** 보장하는 것은 "네 사본에 지시가 있다"이고, 보장하지 않는 것은 "에이전트가 그 도구를 실제로 부른다"이다. 주석이 없으면 다음 사람이 이 초록을 후자의 증거로 읽는다.

4. **red 를 확인한다.** `npx vitest run test/skills/<새 파일>` 을 돌려 네 사본 전부에서 실패하는지 본다. 하나라도 통과하면 단언이 약한 것이므로 3으로 돌아간다.

5. **세 렌더링을 함께 고친다.** `skills/claude/kiwi-orchestrator/SKILL.md` · `skills/codex/…` · `skills/etc/…` 의 `§V.final-verify` 절에 실행 지시를 넣는다. 넣을 내용은 세 가지다 — 언제 부르는가(종료 줄을 쓴 직후), 무엇으로 부르는가(MCP `orchestrate_validate` 를 `strict` 로, 실패 시 CLI `speckiwi orchestrate validate --run-id … --strict`, `kiwi-wave-master` 에서는 `--engine kiwi-wave-master` 를 함께 — §7), 거부되면 무엇을 하는가(`terminal-review-loop-missing` 으로 중단하고 종료 줄을 다시 쓰지 않는다). 한 렌더링만 고치지 않는다.

6. **미러를 재생성한다.** `speckiwi skills mirror --write` 를 실행한다. `.agents/skills/kiwi-orchestrator/SKILL.md` 가 갱신되는지 확인한다. `speckiwi init` · `skills install` · `upgrade` · `remove` 는 이 저장소에서 실행하지 않는다.

7. **green 을 확인한다.** 같은 vitest 파일을 다시 돌린다.

8. **`criticalGatesSection()` 을 먼저 일반화한다.** 9단계가 쓸 헬퍼가 오늘의 스킬 구조를 읽지 못하기 때문에 이 단계가 먼저다. `test/skills/kiwi-orchestrator-variants.ts:160-162` 의 `criticalGatesSection()` 은 `section(body, /^##\s*0\.G\b/)` 로 **레벨 2** `## 0.G` 헤딩을 찾는데, 그 헤딩을 가진 스킬은 일곱 중 둘뿐이다.

   | 스킬 | `critical_gates[]` 선언 자리 |
   |---|---|
   | `kiwi-orchestrator` | `## 0.G` (claude `:47`) |
   | `kiwi-wave-master` | `## 0.G` (claude `:34`) |
   | `kiwi-review-fix-loop` | `#### §0.G8` (claude `:134`) |
   | `kiwi-pm` | `#### §0.G7` (claude `:81`) |
   | `kiwi-coder` | `#### §0.G6` (claude `:106`) |
   | `kiwi-tdd` | `### §0.AG` (claude `:30`) |
   | `kiwi-planner` | `§1.5` (claude `:48` 이 그리로 넘긴다) |

   나머지 다섯에서 `criticalGateRows()` 는 빈 배열을 돌려주므로, 그대로 두면 9단계의 단언이 영구히 빨갛거나 구현자가 15개 파일의 절 구조를 재편하게 된다. 후자는 이 항목이 약속한 범위를 크게 넘는다. 그러므로 헬퍼를 **"`critical_gates[]` 문자열을 포함하는 가장 가까운 상위 절"** 로 일반화하고, 이것을 **별도의 red→green 으로 먼저 착지시킨다** — 일곱 스킬 전부에서 행이 하나 이상 나오는지를 red 로 확인한 뒤 일반화한다. 헬퍼가 일곱을 다 읽지 못하는 상태로 9단계에 들어가지 않는다.
   대안은 `validate-spec-error` 배선을 04 에서 떼어 별도 항목으로 옮기는 것이다. 그 경우 04 의 범위는 §3 목표 1과 2로 줄고, 색인의 `04 → 08` 의존은 그대로 유지된다.

9. **`validate-spec-error` 게이트를 사슬에 붙인다.** 별개의 실패하는 테스트를 먼저 쓴다 — 구현·리뷰 사슬 스킬(`kiwi-coder` · `kiwi-pm` · `kiwi-review-fix-loop` · `kiwi-orchestrator` · `kiwi-tdd` · `kiwi-wave-master` · `kiwi-planner`)의 `critical_gates[]` 표에 그 게이트 행이 있는지 8단계가 일반화한 `criticalGateRows()` 로 단언한다. red 확인 → 세 렌더링 수정 → `skills mirror --write` → green 확인 순서를 지킨다.

10. **회귀를 돌린다.** `npm test` 전체를 돌린다. 스킬 본문을 고쳤으므로 기존 스킬 계약 테스트가 위치·순서를 단언하고 있으면 함께 깨질 수 있다.

11. **검증을 서브에이전트에 맡긴다.** 원본 요구와 diff 만 주고 작성자의 결론은 주지 않는다.

## 5. 완료 조건

**목표 1 — 기계 보장.**

- `engine` 이 `kiwi-wave-master` 인 완료 종료 줄에서 `terminal_review` 를 빼고 `orchestrate journal append` 를 부르면 **쓰기가 거절되고 저널이 바이트 단위로 그대로다.** 오늘 이 호출은 성공한다.
- `src/cli/commands/orchestrate.ts:1046` 의 엔진 해소를 리터럴로 되돌리면 그 테스트가 실패한다.
- `engine` 이 `kiwi-orchestrator` 인 같은 payload 에 대한 기존 거절이 그대로 유지된다.

**목표 2 — 지시의 존재.** 이 세 조건은 도구가 실제로 호출된다는 것을 보장하지 않는다.

- `§V.final-verify` 에서 `orchestrate_validate` 실행 지시를 지우면 `npm test` 가 실패한다. 네 사본 중 **하나만** 지워도 실패한다.
- 그 실행 지시와 `terminal_review` 를 떼어놓아도(같은 절 안에 있지만 서로 다른 문단으로) 실패한다.
- `speckiwi skills mirror --write` 를 돌리지 않아 미러가 뒤처진 상태이면 실패한다.

**목표 3 — 게이트 선언.**

- 일반화한 `criticalGateRows()` 가 일곱 스킬 전부에서 행을 하나 이상 돌려준다. 하나라도 빈 배열이면 8단계가 끝나지 않은 것이다.
- 구현 사슬 일곱 스킬 중 하나의 `critical_gates[]` 표에서 `validate-spec-error` 행을 지우면 실패한다.

**공통.** 위 조건 각각에 대해, 실제로 그 상태를 만들어 실패하는 것을 한 번 확인한다. 확인하지 않은 완료 조건은 완료 조건이 아니다.

## 6. 틀렸을 때 무엇이 깨지는가

**전제 1 — 초판의 전제가 이미 한 번 틀렸다.** 초판은 "그 검증기를 실행하라는 문장이 없으므로 계약을 어긴 종료 줄이 그대로 남는다"고 적었고, 그것은 `kiwi-orchestrator` 경로에서 거짓이었다(§2). 같은 종류의 오류가 남아 있는지 재는 방법: `grep -rn "validateWavesJournal" src/` 로 호출자를 전수 조사한다. §2 에서 확인한 호출자는 셋이다 — `orchestrate.ts` 의 `validate` 명령, 같은 파일 `:1047` 의 append 선행 검사, 그리고 `src/core/workflow/read.ts:393`. 네 번째가 나오면 이 계획의 범위가 또 줄어든다. **호출자를 세기 전에 "배선되어 있지 않다"고 쓰지 않는다.**

**전제 2 — 스킬에 문장을 넣으면 에이전트가 실제로 그 도구를 부른다.** 이 전제는 §3 이 이미 참으로 가정하지 않는다. 목표 2 는 "지시가 존재한다"까지만 주장하고, §5 가 그 한계를 조건 문구에 박아 두었다. 그러므로 이 자리에서 물을 것은 전제의 참거짓이 아니라 **그 한계를 어떻게 관측하는가**이다. 알아차리는 방법: 실제 run 을 한 번 완주시킨 뒤 `.kiwi/waves.jsonl` 의 종료 줄 앞뒤에 검증 결과가 기록되었는지 본다. 기록되지 않으면 산문 지시로는 부족하다는 뜻이고, 그때 필요한 것은 "run 을 진단하는 규칙" — 종료 줄이 없는 run 자체를 결함으로 판정하는 별도 요구 — 이다. 줄 단위 규칙을 넓혀서는 닿지 않는다(§2 말미의 코드 주석이 같은 결론을 적어 두었다).

**전제 3 — 나머지 18종도 같은 처방이 듣는다.** 이것이 틀릴 가능성이 가장 높다. 어떤 도구는 호명되지 않는 것이 옳을 수 있다(phase 2 로 이연된 것, 다른 스킬이 소유한 것). 알아차리는 방법: 18종 각각에 대해 "이 도구가 없으면 어떤 판정이 산문 독해로 남는가"를 한 줄로 쓸 수 있는지 본다. 쓸 수 없으면 그 도구는 이 항목의 대상이 아니다. **이 항목은 `orchestrate_validate` 와 `validate-spec-error` 둘만 배선한다.** 나머지는 이 둘이 착지한 뒤 같은 방법으로 하나씩 판정한다.

## 7. 주의할 점

- **세 렌더링과 미러는 네 개다.** `.agents/skills/` 는 `codex` 렌더링에서 생성된다(`test/skills/kiwi-orchestrator-variants.ts:25`). `codex` 를 고치지 않고 미러만 손으로 고치면 다음 `skills mirror --write` 가 되돌린다.
- **`kiwi-wave-master` 는 미러에서 제외된다.** `terminal-review-loop.fr-flow-131.test.ts:29` 가 그 사실을 주석으로 남겼다. 이 스킬을 함께 고칠 때 사본 목록을 넷이 아니라 셋으로 잡는다.
- **`orchestrate validate` 는 `--engine` 을 받는다**(`src/cli/commands/orchestrate.ts:1929`). 기본값이 `kiwi-orchestrator` 이므로 `kiwi-wave-master` 의 저널을 검증하려면 그 값을 명시해야 한다. 스킬에 넣는 명령에 이 인자를 빠뜨리면 wave-master run 의 종료 줄은 검증되지 않은 채 통과한다. 같은 함정이 append 경로에서는 인자가 아니라 리터럴로 굳어 있고, 그것이 §4 2단계가 닫는 대상이다.
- **실제 강제는 이 항목이 아니라 후속 요구다.** §3 목표 2는 지시의 존재까지이고, 종료 줄을 아예 쓰지 않은 run 을 실패로 만드는 것은 줄이 아니라 **run 을 진단하는 규칙**이 필요하다. 그 규칙은 주체(무엇이 run 의 종결을 관측하는가)와 시점(언제 판정하는가)을 새로 정해야 하므로 별도 요구로 분리한다. 이 항목의 요구 문서에 그 후속 요구를 지목해 두고, 04 의 AC 에 그 보장을 쓰지 않는다.
- **`workflow_doctor` 를 우회 경로로 쓰지 않는다.** §2 가 기록한 세 조건 때문에 그것은 게이트가 될 수 없다. 특히 `catch { return []; }` 는 깨진 저널을 "진단 0건"과 구별할 수 없게 만든다.
- **이 항목은 독립 작업 둘을 담고 있으며, 분리를 제안한다.** 개정 뒤 §4 가 다루는 것은 넷이다 — (A) 엔진 해소 수정(코드 한 자리 + TDD), (B) `orchestrate_validate` 실행 지시(`kiwi-orchestrator` 네 사본), (C) `criticalGatesSection()` 일반화(테스트 헬퍼), (D) `validate-spec-error` 배선(일곱 스킬 × 세 렌더링 + 미러). **A 와 B 는 같은 대상을 공유한다** — run 종료 저널의 `terminal_review` 계약이며, 하나의 요구로 묶인다. **C 와 D 는 대상이 다르다** — SRS validation 이고, 공유하는 것은 "게이트 배선"이라는 라벨뿐이다. 파일도 겹치지 않고, 실패 형태도 다르며, D 는 C 없이 착지할 수 없다. §6 전제 3 이 이미 "이 항목은 둘만 배선한다"고 적어 계획 자신이 둘임을 말하고 있다.
  분리하면 04 는 A·B 만 갖고, C·D 는 새 항목이 된다. 색인의 의존 표는 그때 `04 → 08` 이 어느 쪽을 가리키는지 다시 정해야 한다 — 08 §1 과 §6 은 "대조 결과를 소비할 게이트"를 요구하므로 C·D 쪽에 걸린다. 색인 편집은 이 파일의 소유 범위 밖이므로 여기서는 제안만 적는다.
- **C 는 05 와 배타 관계에 걸린다.** 색인이 `04 ↔ 05` 를 동시 진행 금지로 두는 이유가 "같은 `## 0.G` 표를 만진다"인데, 8단계가 그 표를 찾는 헬퍼 자체를 일반화하므로 05 가 만지는 표의 인식 범위도 함께 바뀐다. 분리하든 아니든, C 를 착지시키기 전에 05 의 현재 상태를 확인한다.
- **08 항목이 이 배선을 전제한다.** 색인의 의존 표가 `04 → 08` 을 명시한다. 이 항목의 지시 문구가 바뀌면 08 의 분모 게이트 설계도 함께 봐야 한다.
- **`GATE_IDS` 에 새 이름을 추가하지 않는다.** 이 항목이 쓰는 게이트는 이미 등재된 `terminal-review-loop-missing`(`auto-gate.ts:133`)이다. 새 이름을 만들면 `critical_gates[]` 선언·`refuse()` 수용·부분집합 단언 세 곳을 동시에 손대야 하고, 그것은 이 항목의 범위가 아니다.
