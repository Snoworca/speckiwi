# 07. 문서가 사실과 다르게 말하는 세 자리를 정정한다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 정확도 |

## 1. 지금 무슨 일이 일어나는가

세 자리가 각각 독립적으로 사실과 어긋난다. 셋 다 스킬 텍스트만 고치면 되고 코드는 건드리지 않는다.

**(a) 실재하는 기능을 없다고 적고 사용을 금지한다.**

1. 에이전트가 `kiwi-coder` 의 `--defer-srs-mutation` 절을 읽는다.
2. `skills/claude/kiwi-coder/SKILL.md:603` 이 그 계획을 적용하는 쪽이 저장소에 없다고 알리고, 그러므로 그 플래그를 쓰면 mutation 이 소실된다고 경고한다.
3. 에이전트가 플래그 사용을 포기한다. 그 결과 워크트리 레인의 SRS mutation 이 host root 에 착지할 유일한 경로가 사라진다.
4. 실제로는 적용하는 쪽이 실재한다. `src/core/orchestrator/replay-apply.ts:72` 의 `applyReplayPlan` 이 그것이며, `src/cli/commands/orchestrate.ts:1899` 가 그 함수를 호출하고 `:1902` 가 `dispatch: hostRootDispatch(projectRoot(command))` 로 host root 를 지정한다.

**(b) 완료를 인정하는 판정값 집합을 반대로 적었다.**

1. 오케스트레이터가 run 종료 줄에 `terminal_review.verdict` 를 기록한다.
2. `skills/claude/kiwi-orchestrator/SKILL.md:1194` 가 네 값을 열거한 뒤 "뒤의 둘은 완료를 방면하지 않는다"라고 적는다. 열거 순서상 뒤의 둘은 `not-applicable-empty-window` 와 `skipped-run-halted` 다.
3. 실제 집합은 `src/core/orchestrator/journal-schema.ts:241-244` 의 `TERMINAL_REVIEW_DISCHARGING_VERDICTS` 이고, 그 배열에는 `pass` 와 `not-applicable-empty-window` 가 들어 있다. 즉 `not-applicable-empty-window` 는 완료를 인정하는 쪽에 있다.
4. 같은 스킬 `:428` 이 정반대를 적어 문서 내부에서도 어긋난다. 이 오기는 네 사본 전부에 동일하다.

**(c) Status cap 이 코드에 없는 필드에 걸려 있다.**

1. `skills/claude/kiwi-srs/SKILL.md:31` 의 §0.14 가 `trace_intent=addition_site` 가 잔존하면 그 요구의 status 를 `proposed` 상한으로 묶는다고 규정한다.
2. `grep -rn "trace_intent\|traceIntent" src/` 는 0건이다. `add_trace_link` 의 실제 스키마는 `src/mcp/server.ts:297` 이고 필드는 `id` · `type` · `reference` · `relation` · `notes` 다.
3. 같은 스킬 `:513` 이 `add_trace_link { id, type: "Code", reference, trace_intent: ... }` 를 지시하는데, 스키마가 필수로 요구하는 `relation` 이 빠져 있다.
4. 결과적으로 에이전트가 `:513` 을 그대로 실행하면 스키마 검증에서 거부되고, `:31` 의 상한은 아무 데이터도 참조하지 못한 채 임의 판단으로 남는다.

## 2. 근거

> `skills/claude/kiwi-coder/SKILL.md:603`
> **적용하는 소비자는 아직 없다.** 큐를 읽어 재생 계획을 세우는 쪽(`speckiwi orchestrate replay plan`)은 이 타깃에서 착지했지만, 그 계획을 host root 에서 실제 호출로 **적용하는 쪽은 아직 저장소에 없다**

```ts
// src/core/orchestrator/replay-apply.ts:72
export async function applyReplayPlan(plan: ReplayPlan, options: ApplyReplayOptions): Promise<ApplyReplayResult> {
```

> `skills/claude/kiwi-orchestrator/SKILL.md:1194`
> verdict 은 `pass` · `residual` · `not-applicable-empty-window` · `skipped-run-halted` 중 하나이고, 뒤의 둘은 완료를 방면하지 않는다(FR-NODE-188).

```ts
// src/core/orchestrator/journal-schema.ts:241-244
export const TERMINAL_REVIEW_DISCHARGING_VERDICTS: readonly TerminalReviewVerdict[] = [
  "pass",
  "not-applicable-empty-window"
];
```

> `skills/claude/kiwi-srs/SKILL.md:31`
> **Status cap**: 어느 trace 라도 `trace_intent=addition_site` 잔존 시 해당 REQ 의 status 는 `proposed` 상한.

```ts
// src/mcp/server.ts:297
add_trace_link: { id: z.string(), type: z.string(), reference: z.string(), relation: z.string(), notes: z.string().optional(), ... },
```

같은 스킬 `:498` 은 `re_stated_from` 에 대해 도구 미지원을 인지하고 `notes` 인라인 문법으로 우회한다. `trace_intent` 에는 그 우회가 없다.

## 3. 목표 상태

- (a) `kiwi-coder` 의 그 문단이 적용 경로의 실재를 적고, 사용 금지 대신 **수확 경로가 붙은 run 안에서만 쓴다**는 조건을 적는다. 형제 스킬이 이미 그 명령을 갖고 있다는 사실도 함께 적는다(`kiwi-orchestrator:1258`, `kiwi-wave-master:550`).
- (b) `kiwi-orchestrator:1194` 가 인정 집합을 **값 이름으로** 적는다. "뒤의 둘" 같은 순서 지칭을 쓰지 않는다. `:428` 과 표현이 일치한다.
- (c) `kiwi-srs` §0.14 의 Status cap 이 실재하는 표현 수단 위에 놓인다. `trace_intent` 를 `notes` 인라인으로 인코딩하거나(§`re_stated_from` 과 같은 방식) 그 규칙 자체를 철회한다. `:513` 의 호출 예시에 `relation` 이 들어간다.

## 4. 작업 단계

1. 요구를 먼저 등록한다. 세 자리는 원인이 다르므로 요구를 분리해도 되고 "스킬 텍스트가 코드 상수와 일치한다" 하나로 묶어도 된다. 06 의 요구와 중복되지 않게 범위를 나눈다.
2. **실패 테스트를 먼저 쓴다.** `test/skills/` 의 기존 관례를 따른다(`test/skills/review-loop-file-class.fr-flow-152.test.ts` 가 본보기다). 네 사본을 `["skills/claude", "skills/codex", "skills/etc", ".agents/skills"]` 로 열거하고 각각에 대해 단언한다.
   - (a) `kiwi-coder/SKILL.md` 에 "적용하는 쪽은 아직 저장소에 없다"가 **없고**, `replay-apply` 또는 `orchestrate replay apply` 를 지목하는 문장이 있다.
   - (b) `kiwi-orchestrator/SKILL.md` 의 그 문단이 `not-applicable-empty-window` 를 방면 목록에 두고, `residual` 과 `skipped-run-halted` 를 인정하지 않는 쪽에 둔다. 인정 목록을 코드에서 직접 읽어와(`TERMINAL_REVIEW_DISCHARGING_VERDICTS`) 대조하면 재발이 완전히 막힌다.
   - (c) `kiwi-srs/SKILL.md` 에 스키마 밖 필드명이 `add_trace_link` 호출 예시의 인자 자리에 나타나지 않고, 모든 `add_trace_link` 예시에 `relation` 이 있다.
3. **실패를 확인한다.** `npx vitest run test/skills/<파일>` 로 세 단언이 모두 red 임을 본다. red 가 아니면 단언이 이미 통과하는 문구를 고른 것이므로 단언을 고친다.
4. **최소 구현으로 통과시킨다.** `skills/claude` · `skills/codex` · `skills/etc` 세 렌더링의 같은 절을 **함께** 고친다. 줄 번호는 렌더링마다 다르므로 문구로 찾는다.
5. `speckiwi skills mirror --write` 로 `.agents/skills/` 를 재생성한다. 이 저장소에서 `.agents/skills/**` 를 직접 편집하는 것은 허용되지 않는다.
6. `npx vitest run test/skills/` 로 green 과 회귀 없음을 확인한다.
7. 검증 서브에이전트에게 원본 요구와 diff 만 준다. 어느 쪽이 사실인지 코드에서 직접 확인하게 한다.

## 5. 완료 조건

- 세 자리 각각에 대해, **그것을 다시 어긴 문구로 되돌리면 테스트가 실패한다.** 문구를 되돌려 red 를 한 번 관찰한 기록이 있어야 한다.
- (b) 의 테스트가 `journal-schema.ts` 의 상수를 읽어서 대조한다. 상수를 바꾸면 스킬 텍스트를 고치기 전까지 red 다.
- `speckiwi skills mirror --check` 가 divergence 0 을 보고한다.
- 네 사본 전부가 같은 문구를 갖는다. 한 사본만 고친 상태는 테스트가 잡는다.

## 6. 틀렸을 때 무엇이 깨지는가

- **(a) 의 전제가 틀렸다면**, 즉 `hostRootDispatch` 가 실제로는 host root 가 아닌 곳에 쓴다면, 이 정정은 소실되는 mutation 을 소실되지 않는다고 광고하는 문장으로 바꾼다. 알아차리는 방법은 `--defer-srs-mutation` 으로 큐를 만든 뒤 `orchestrate replay apply` 를 돌리고, host root 의 `docs/spec/` 파일이 실제로 바뀌었는지 `git diff` 로 보는 것이다.
- **(b) 의 전제가 틀렸다면**, 즉 `TERMINAL_REVIEW_DISCHARGING_VERDICTS` 가 게이트 판정에 쓰이지 않는다면, 문서를 코드에 맞추는 작업이 아무 동작도 바꾸지 않는다. 확인 지점은 `src/core/orchestrator/waves-validate.ts:474` 이며, 그 줄이 그 상수를 소비한다.
- **(c) 의 전제가 틀렸다면**, 즉 `trace_intent` 를 소비하는 코드가 어딘가에 있다면, 규칙을 철회하는 선택지가 잘못된다. 확인 방법은 `grep -rn "trace_intent\|traceIntent" src/` 를 다시 돌리는 것이다. 0 이 아니면 방향은 우회가 아니라 필드 추가다.
- **공통 증상**: 정정 후에도 에이전트가 옛 문구대로 행동한다면 다섯 번째 사본이 어딘가에 있다는 뜻이다. `grep -rn "<옛 문구>" --include=SKILL.md .` 로 찾는다.

## 7. 주의할 점

- **(c) 는 세 자리 중 유일하게 동작 결정이 필요하다.** 우회로 갈지 철회로 갈지가 갈리고, 그 선택이 `kiwi-planner` 에도 영향을 준다. `trace_intent` 는 `kiwi-planner` 에도 등장하므로(`skills/claude/kiwi-planner/SKILL.md`) 결정을 그 스킬에도 같이 적용한다.
- (a) 를 고칠 때 **경고 자체를 지우지 않는다.** 큐를 수확하지 않는 맥락에서 mutation 이 소실된다는 사실은 여전히 참이다. 바뀌는 것은 "적용하는 쪽이 없다"는 부분뿐이다.
- (b) 에서 `residual` 이 인정 목록에 없다는 사실이 현재 문장에서는 읽히지 않는다. 정정문에 그 사실을 명시한다.
- 스킬 텍스트는 계약이다. 세 렌더링 중 하나만 고치는 것은 근거 문서 §5.1 이 기록한 실패 형태 그 자체다.
