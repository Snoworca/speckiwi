## 0. 이 항목이 생긴 경위

사용자가 지시했습니다 — **"SRS 계열 MCP 도구가 경로를 입력받는 인자를 갖게 하라. 다른 도구들처럼."**

관찰은 사실이었습니다. 도구 100개 중 **51개가 `workspaceRoot` 를 받고**(`workflow_*` 26 + `orchestrate_*` 25) SRS 계열은 받지 않습니다. 그리고 **CLI 는 `--root` 를 무검사로 받습니다**(`src/core/project-root.ts:14`) — 같은 기능이 한쪽에서는 닫혀 있고 다른 쪽에서는 게이트 없이 열려 있습니다.

5인 위원회(계약·데이터 무결성·사용자 필요·API 설계·비용과 순서)가 **만장일치로 읽기 계열만 개방**하기로 결정했습니다.

## 1. 쓰기를 열지 않는 이유 — 실측

**위원 2가 6개 root 를 전수로 재어 ID 이중 발급을 재현했습니다.**

`src/core/mutation/add-requirement.ts:330~346` 에서 ID 후보가 나오는 자리는 넷이고 **넷 다 인자로 받은 단일 `root` 만** 봅니다. 캐시가 없든 낡았든 다른 root 를 참조하는 분기가 없습니다. 그리고 `kiwi/.status.json` 은 `.gitignore` 에 등재되어 있어 **카운터를 git 이 옮겨 주는 경로가 아예 없습니다.**

실측 결과 호스트는 다음 ID 로 `FR-MCP-062` 를, 두 워크트리는 각각 `FR-MCP-053`·`FR-MCP-057` 을 발급합니다. 병합하면 서로 다른 내용의 같은 ID 가 됩니다.

**위원 5가 락도 같은 성질임을 찾았습니다** — `src/core/mutation/srs-lock.ts:29` 가 `path.join(root.root, …)` 이므로 **두 accepted root 는 두 락 파일을 잡고 서로를 전혀 배제하지 않습니다.** 계획 25번이 지금 고치는 결함과 같은 형태를 SRS 계층에 새로 만드는 셈입니다.

**위원 4는 이름 축에서 반대했습니다** — `add_requirement(workspaceRoot)` 의 실제 의미는 "이 root 의 카운터로 ID 를 발급한다" 인데 이름 어디에도 그 말이 없고, **잘못 쓴 결과는 호출 시점에 성공으로 보이며 병합 때 처음 드러납니다.**

**위원 3은 배포된 스킬 계약을 찾았습니다** — `_shared/kiwi/worktree-lane.md` §1(네 렌더링에 배포)이 *"MCP 표면에는 레인을 가리킬 방법이 아예 없으므로, 레인이 MCP 핸들을 들고 있어도 그것으로 자기 워크트리를 건드릴 수 없다"* 고 적습니다. 쓰기 개방은 이 문장을 즉시 거짓으로 만듭니다.

**그러므로 이 항목은 사용자 지시의 절반만 이행합니다.** 쓰기 개방은 ID 발급 정책과 락 정책을 먼저 세워야 하는 별개의 일이며, 사용자 결정 사안으로 남깁니다.

## 2. 확인해야 할 것

착수 시점에 먼저 재야 합니다.

- **31번이 닫혔는지.** 31번이 남아 있으면 이 항목은 **개방 여부와 무관하게 조용히 틀립니다.** 반드시 선행되어야 합니다.
- **규모.** 위원 5의 실측은 **5파일 · 약 40자리**입니다(스키마를 게이트에서 파생시키면 24). 주입 지점이 **둘**임에 유의하십시오 — `workspace(deps)` 계열 10곳과 `projectRoot(deps)` 의 context 없는 SRS 호출 9곳입니다. 선행 조사는 후자를 놓쳐 약 4배 과소계상했습니다.
- **`validate_step` 은 헬퍼를 둘 다 씁니다**(`read-tools.ts:342` + `:347`). 한쪽만 배선하면 **한 도구가 서로 다른 두 root 를 읽습니다.**
- **스키마를 손으로 적지 마십시오.** SRS 스키마는 `server.ts` 에 손으로 적힌 표이고 `orchestrate` 만 `:67` 에서 파생시킵니다. 17개를 손으로 적으면 31번 §5 의 결함을 17배로 재현합니다.
- **`srsDestination` 오탐.** 입력 문자열 전부를 스캔하므로 `search_requirements({query:"docs/spec"})` 가 오탐 거절됩니다(실측). 함께 처분해야 합니다.

## 3. 무엇이 거짓이 되는가

**`REL-MCP-005`(verified, evolving) 한 건 안에서 닫힙니다.**

- **SHALL 의 한 구절** — 위원 1의 판정: AC-3 둘째 문장이 곧 판별식이고 코드가 그 문장 그대로입니다(`adapter.ts:130` 의 `workspaceScope !== "worktree-local"`). 새 scope 값을 하나라도 더하면 그 문장이 거짓이 됩니다.
- **AC-6** — `srsDestination` 예외를 두면 거짓이 되고, 안 두면 위 §2 의 오탐이 남습니다.
- **AC-8** 과 **VE-1 의 "49 refused / 51 accepted"**.

**주의**: 위원 1이 *"The boundary is authorship, not incidental reading"* 문장의 주어를 확인했습니다 — 그것은 **이미 수용된 worktree-local 도구가 envelope 을 채우려 인덱스를 읽는 행위**를 가리키는 수용 측 예외 조항이지, **SRS 조회 도구 개방 허가가 아닙니다.** 선행 조사가 이 문장을 근거로 "문면을 안 건드려도 된다" 고 적은 것은 틀렸습니다.

**하향 → AC 수정 → 재승격**이 필요합니다(선례 `FR-PARSE-033`·`FR-NODE-177`).

## 4. 산문 계약도 함께 깨집니다

위원 5가 찾은 셋입니다.

- `test/mcp/workspace-root-docs.rel-mcp-005.test.ts` 가 README 두 언어 절에 "SRS tools refuse it" 을 **정규식으로** 요구하고(`:37`), 4렌더링 × 2스킬에 그 기술을 요구합니다(`:52~65`). → README 2절 + `SKILL.md` 8 + 미러 재생성.
- `src/mcp/tools/read-tools.ts:229~231` 의 `@req REL-MCP-005 AC-2` 안전 주석이 거짓이 됩니다.
- `docs/spec/40.mcp-stdio-interface.srs.md` VE-1 의 수치.

**거절을 계약으로 고정한 테스트는 4파일 18단언이고, 이 항목은 그중 하나도 깨지 않습니다**(전부 쓰기 도구이거나 `root` 키 대상). 위원 5의 실측이며 선행 조사의 예상과 다릅니다.

## 5. 왜 29번·13번 뒤인가

- **13번**(`:117`)이 `workflow_workspace_info` 를 **삭제하지 않기로 한 근거**가 *"`mcp_workspace_info` 는 SRS-facing 이라 항상 startup root 에 답한다"* 입니다. 이 항목이 그 문장을 죽이면 그 도구는 진짜 중복이 되어 13번의 판단이 뒤집힙니다.
- **29번**은 `toolAxisAllows` 가 토큰을 소문자로 낮춰 조회하는데 집합은 스키마 키 원형을 담습니다. `workspaceRoot` 를 넣으면 **영원히 면제되지 않는 camelCase 인자가 하나 더** 생깁니다. 29번을 먼저 하면 무료로 흡수됩니다.

## 6. 되돌리기 비용

**스키마가 곧 인터페이스이므로 확산은 스킬 편집을 기다리지 않습니다.** 인자가 붙는 순간 스키마를 읽는 에이전트가 씁니다. 회수하려면 스키마까지 함께 걷어야 하고, 그러지 않으면 31번 §5 의 결함(광고하는데 거절)을 그대로 재현합니다.

## 7. 완료 조건

- **워크트리를 가리킨 조회가 그 워크트리의 답을 돌려주는 것**을 **실제 프로토콜 왕복**으로 보인다(어댑터 직접 호출이 아니라).
- 쓰기 계열은 여전히 거절되고, **거절 문면이 그 선을 설명한다** — "읽기는 받고 쓰기는 받지 않으며, 이유는 ID 가 root 별 카운터로 발급되기 때문".
- `REL-MCP-005` 의 하향 → AC 수정 → 재승격이 증거와 함께 끝난다.
- **산문 계약 셋의 처분이 정해진다.**
- `srsDestination` 오탐이 함께 처분된다.

## 8. 건드리지 말아야 할 것

- **쓰기 계열을 열지 않는다.** 위원회 만장일치이며, 열려면 ID 발급 정책과 락 정책이 선행되어야 한다.
- **CLI `--root` 에 게이트를 붙이지 않는다.** 위원 1의 판정으로 그것은 `FR-ARCH-002`(verified, **stable**) AC-2 가 명세한 의도이고, 조이면 기존 호출자를 깬다. **발견 사실로만 남긴다** — 다만 오타 난 root 에 `recovery: {"command":"init"}` 를 안내하는 것은 별개 결함이므로 따로 받아야 한다.

- **`src/core/bootstrap/templates.ts:518`** — `speckiwi init` 이 소비자 프로젝트에 기록하는 지시문이 "Every SRS-facing tool refuses workspaceRoot fail-closed" 라고 단정합니다. 가장 명백히 거짓이 되는 문장입니다.

| **D4** | **인덱스 부재를 게이트에서 구조화된 거절로 답합니다. 단 게이트 전역이 아니라 열셋에 한정합니다** | 만장 | 전역으로 걸면 인덱스를 요구하지 않는 `workflow_doctor` 가 `docs/` 없는 워크트리에서 **오늘 정상 응답하던 것이 거절로 바뀝니다**(회귀). 32번은 이 예외를 드문 가장자리에서 **그 기능의 기본 실패 모드**로 바꾸므로, 실패 모드를 말하지 않은 요구를 배포할 수 없습니다. 핸들러 ENOENT 를 잡는 안은 예외를 제어흐름으로 쓰는 것이고 한 게이트가 정할 일을 열세 자리에서 되풀이합니다 |
| **D5** | **요구 셋을 건드리고 새 요구는 하나입니다** | 만장 | 아래 §9.4 |

**새 scope 값을 도입합니다 — `workspaceScope: "srs-read-only"`.** 리터럴 `"worktree-local"` 을 재사용하면 이름이 거짓말을 하고, D4 의 인덱스 검사를 걸 자리가 없어 51개 전체에 걸게 되어 회귀가 됩니다. 게이트는 **닫힌 집합 소속 검사**로 써야 합니다 — 존재 검사로 바꾸면 오타 난 scope 값이 수용됩니다(지금의 `!== "worktree-local"` 은 오타에 fail-closed).

### 9.4 요구 구조

성격이 다른 약속 셋이 있고 그것이 요구의 경계입니다.

| 약속 | 누가 지는가 |
|---|---|
| 어떤 root 가 수용 가능하고 **누가 그것을 받을 자격이 있는가** | `REL-MCP-005` |
| 거절이 **프로토콜 표면까지 도달하는가**(seam) | `FR-MCP-063` |
| 수용된 root 로 **이 계열이 무엇을 하는가** | 계열별 — `FR-MCP-058` · `FR-MCP-059` · **신규(SRS 조회)** |

1. **`REL-MCP-005` 하향 → SHALL · AC-3 · AC-6 개정 → 재승격.** 선택이 아닙니다. SHALL 의 "only on tools whose subject is worktree-local run state" 가 배타 한정사이므로, 새 요구만 세우면 verified 두 건이 서로를 부정합니다. AC-3 개정은 리터럴 `worktree-local` 을 문면에서 걷어내 **구현이 두 scope 값을 정직하게 두는 길**을 열고, "선언이 없으면 거절"이라는 기본값은 그대로 둡니다. AC-8 은 개정 불필요합니다(계열 이름을 담지 않은 의무 조항).
2. **`FR-MCP-063` 하향 → AC-1 · AC-4 개정 → 재승격.** **숫자를 36으로 고치는 것이 아니라 원칙을 맞춥니다.** 같은 요구의 AC-4 가 이미 "held to a name rather than to a count" 라고 적으며 이름 원칙을 택했는데 AC-1 만 count 를 씁니다 — 한 요구가 자기 안에서 두 원칙을 씁니다. 거절 집합의 크기는 membership 에 대한 사실이고 그것은 `FR-MCP-063` 이 다스리지 않습니다. **다만 리터럴 49 가 하던 "누가 조용히 인자를 얻었다" 경보는 버리지 않고 새 요구로 옮깁니다.** AC-5·AC-6 은 도구 이름을 담지 않으므로 문면 수정이 필요 없고 테스트의 수단만 옮깁니다.
3. **새 요구 하나.** `FR-MCP-058`/`059` 와 같은 모양이고 `depends_on REL-MCP-005`. 지는 것 여섯: ① 열리는 열셋을 **이름으로** 고정하고 그 밖은 열리지 않는다(`FR-MCP-063` AC-1 에서 옮겨 온 가드의 자리) ② 인자를 생략하면 오늘 동작이 그대로다 ③ **워크트리를 가리킨 조회가 그 워크트리의 답을 돌려준다** — 두 root 의 내용을 다르게 만든 실제 프로토콜 왕복으로 ④ `validate_step` 이 **두 헬퍼 모두** 그 root 를 쓴다 ⑤ `mcp_workspace_info` 부정형 배제 ⑥ 인덱스 부재 시 구조화된 거절.

**`srsDestination` 처분은 새 요구로 가르지 않고 `REL-MCP-005` AC-6 에 남깁니다.** 규칙은 안전 요구 안에 있어야 독자가 찾고, 새 요구는 열셋이 그 선언을 단다는 membership 만 집니다. 그리고 개방만 착지하고 예외가 없는 중간 상태는 **가장 정상적인 사용이 거절되는 상태**이므로 절반이 착지한 것이 아니라 착지하지 않은 것입니다.

**건드리지 않는 것**: `FR-MCP-058`(D3 이 선언안이므로) · `FR-MCP-059` · `FR-MCP-062` · `FR-FLOW-042`(D1-a 로) · `FR-ARCH-002`.

### 9.5 순서와 중간 상태

**status 는 착수 전에 내리고, 문면은 코드 뒤에 고치고, 재승격은 마지막에** 합니다. `REMAINING.md` §4 의 "코드·테스트 → 요구 문면"은 **문면**의 순서이고 "하향 → AC 수정 → 재승격"은 **status 필드**의 순서이므로 충돌하지 않습니다. 먼저 내리는 이유는 실패 모드가 비대칭이기 때문입니다 — 나중에 내리면 그 사이 트리는 `verified` 라고 적힌 요구 둘이 자기 테스트를 붉히는 상태이고, 그때 세션이 끊기면 SSOT 가 조용히 거짓말을 합니다.

**이 작업의 핵심 위험은 red 와 우발적 파손을 가르는 것입니다.** 깨끗한 TDD red 는 **새 테스트만 추가한 상태 하나뿐**이고, 게이트만 열면 `FR-MCP-063` AC-4 가, 스키마까지 열고 배선을 안 하면 AC-1·AC-5·AC-6 과 새 테스트가 서로를 가리며 붉습니다. **가르는 방법은 숫자를 미리 등록하는 것입니다** — 오늘의 거절 49 는 SRS 조회 18 + SRS 쓰기 29 + orchestrate 2 이므로 열셋을 열면 **36** 입니다. 관측이 예측과 다르면 의도하지 않은 도구가 함께 움직인 것이고 그것이 우발적 파손입니다.

**게이트·스키마·배선·`FR-MCP-063` 갱신을 쪼개지 마십시오** — 사이 커밋이 전부 붉습니다.

### 9.6 새 거절 문면에 넣지 말아야 할 것

D4 의 recovery 문안에 **`speckiwi init --force` 를 넣지 마십시오.** `--force` 가 요구를 무증상으로 삭제하는 결함이 미해결로 기록되어 있고, `doctor` 가 그것을 안내하는 것이 이미 CRITICAL 로 잡혀 있습니다. recovery 는 **수리 명령이 아니라 검사한 체크아웃을 이름**해야 합니다.
