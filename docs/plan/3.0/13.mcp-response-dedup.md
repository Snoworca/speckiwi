# 13. 같은 사실을 두 번 실어 보내는 MCP 호출을 정리한다

| Field | Value |
|---|---|
| 우선순위 | HIGH — 비용 |
| 근거 | `docs/research/28.skills-mcp-end-to-end-audit.md` §4.3, §4.5, §4.6 의 M-1·M-2 |
| 선행 항목 | 없음 |
| 대상 | 둘 다 (코드 + 스킬 텍스트) |

---

## 1. 지금 무슨 일이 일어나는가

네 짝이 지목되었다. 넷 다 **한 소스에서 파생**되므로 계약이 갈리는 문제는 없다. 순수한 왕복 비용이다. 다만 짝마다 고쳐야 할 쪽이 다르고, 넷 중 하나는 조사 결과 짝이 아니었다.

**짝 1 — `get_active_target` + `summarize_target`.** 두 도구가 같은 `summarizeTarget` 함수를 부른다(`src/mcp/tools/read-tools.ts:277-286`). `get_active_target` 은 그 결과를 `{ activeTarget, summary, goal }` 로 감싸고, `summarize_target` 은 그 결과를 그대로 돌려준다. 근거 문서 §4.3 이 실제 호출로 확인한 바에 따르면 두 응답 사이에서 값이 갈리는 키는 `targetSource` 하나뿐이며, 그것은 프로젝트에 관한 사실이 아니라 호출 방식을 되비추는 값이다. 그런데 스킬들이 두 호출을 모두 지시한다 — `kiwi-review-fix-loop:510`, `kiwi-srs:252`/`:262`, `kiwi-planner:250`/`:257`, `kiwi-srs-feasibility:212`/`:810`.

**짝 2 — `workflow_resume_hint` + `workflow_next_plan_task`.** 전자가 후자를 호출하고 불린 하나를 덧붙여 같은 페이로드를 재전송한다(`src/core/workflow/read.ts:619-623`). 그 불린은 `blocking !== true && nextTask !== null` 이므로 응답 안의 두 필드에서 호출자가 직접 계산할 수 있다.

**짝 3 — `workflow_pipeline_status` + `workflow_pipeline_next`.** `workflowPipelineNext` 는 `workflowPipelineStatus` 를 호출한 뒤 `{ nextHint, latestEvent }` 를 돌려주며, `nextHint` 는 `latestEvent.event.next_hint` 다(`src/core/workflow/read.ts:604-607`). `latestEvent` 는 status 가 이미 돌려준 것과 같은 객체다.

**짝 4 — `workflow_workspace_info` + `mcp_workspace_info`.** 조사 결과 **짝이 아니다.** §7 에 근거를 적는다.

## 2. 근거

짝 1 과 짝 2 는 근거 문서 §4.3 과 §4.5 가 소스와 실제 호출로 확인했고, 이 계획을 쓰면서 해당 소스 줄을 다시 읽어 확인했다. 짝 3 은 근거 문서 §4.6 의 M-1 이 관측만 기록했으므로 소스로 확인했고, 위 인용이 그 결과다.

**짝 2 와 짝 3 의 파생 도구는 런타임 코드가 이름으로 지목한다.** 이 계획의 초판은 `skills/` 만 세어 "이름으로 부르는 스킬이 하나도 없으므로 아무도 쓰지 않는다"고 적었다. 그 측정 범위가 스킬 본문뿐이어서 실제 호출자를 놓쳤다.

> `src/core/workflow/work-order.ts:75-92` — `actionTool()`
> ```ts
>     case "execute-task":    return "workflow_next_plan_task";
>     case "resume-session":  return "workflow_resume_hint";
>     case "fix-artifact":    return "workflow_resume_hint";
>     case "blocked":         return "workflow_next_plan_task";
> ```

같은 파일 `:133-137` 의 `baseOrder()` 가 그 값을 `nextAction` 에 실어 내보낸다 — `:135` 가 `tool: actionTool(input.action)` 이다. 즉 `get_next_work_order` 는 `resume-session` 과 `fix-artifact` 두 action 에서 **`workflow_resume_hint` 를 다음에 부를 도구로 에이전트에게 지시한다.**

요구 계약 둘이 두 이름을 열거한다.

> `docs/spec/40.mcp-stdio-interface.srs.md:4114` (`FR-MCP-057` AC-5)
> … including workflow_next_plan_task, … workflow_pipeline_status, workflow_pipeline_tail, workflow_pipeline_next, … workflow_resume_hint, and get_next_work_order …

> `docs/spec/50.nodejs-implementation.srs.md:11420` (AC-9)
> … Every public JSONL consumer preserves that projection, including … workflowPipelineNext, … workflowResumeHint, and buildNextWorkOrder.

테스트도 그 이름을 단언한다 — `test/cli/workflow-record-reclassification.ir-cli-089.test.ts:1998`/`:2014`, `test/cli/workflow-work-order.test.ts:43`, `test/core/workflow/work-order.test.ts:40`, `test/core/workflow/record-reclassification.fr-node-177.test.ts:1129`/`:1149`, `test/mcp/workflow-read-tools.test.ts:86`/`:89`, `test/mcp/workflow-record-reclassification.fr-mcp-057.test.ts:494`/`:500`. `docs/spec/90.appendix.md:381`/`:384` 의 도구 목록에도 두 행이 있다.

**따라서 이 항목은 두 도구를 삭제하지 않는다.** 삭제하면 `get_next_work_order` 가 존재하지 않는 도구 이름을 다음 행동으로 돌려주게 된다. 그것은 근거 문서 §2.3 이 CRITICAL 로 판정한 형태 — 계약이 존재하지 않는 값을 지시하는 것 — 를 이 계획이 새로 만드는 일이다. 근거 문서 §4.5 도 이 짝을 "순수하게 네트워크 왕복 비용"으로만 판정했고 §6 처방에 도구 삭제가 없다.

**호출 지시가 어디에 있는지 재는 명령이다.** 스킬만이 아니라 코드·요구·테스트를 함께 훑는다.

```
grep -rn "workflow_resume_hint\|workflow_pipeline_next\|workflowResumeHint\|workflowPipelineNext" docs/spec/ test/ src/ skills/ .agents/skills/
grep -rn "get_active_target" skills/claude/ | grep "summarize_target"
```

## 3. 목표 상태

**짝 1 은 스킬의 호출 지시를 고친다. 도구는 둘 다 남긴다.** 두 도구는 호출자 입장에서 서로 다른 질문에 답한다. `get_active_target` 은 "활성 target 이 무엇이고 그 상태가 어떤가"에, `summarize_target` 은 "지명한 target 의 상태가 어떤가"에 답한다. 활성 target 을 요약하려는 스킬은 `get_active_target` 한 번으로 끝내고 `value.summary` 를 읽는다. `summarize_target` 은 활성이 아닌 target 을 요약할 때만 부른다.

**짝 2 와 짝 3 은 파생 필드를 원본 도구로 올린다. 파생 도구는 얇은 별칭으로 남긴다.** `workflow_next_plan_task` 가 `resume` 을, `workflow_pipeline_status` 가 `nextHint` 를 함께 돌려준다. 그러면 한 번의 왕복으로 같은 사실을 전부 얻는다. `workflow_resume_hint` 와 `workflow_pipeline_next` 는 등록부에 남되 원본 도구의 결과를 그대로 위임하는 별칭이 되어, 파생 계산이 두 벌이 되지 않는다. 이름이 유지되므로 `actionTool()` 의 반환값과 위 §2 의 두 요구 계약, 그리고 일곱 테스트 파일의 단언이 그대로 성립한다.

**짝 4 는 아무것도 고치지 않는다.** §7 에 사유를 적는다.

## 4. 작업 단계

1. 요구를 `docs/spec/` 에 등록한다. 짝 1(스킬 텍스트)과 짝 2·3(도구 반환 계약)은 대상 계층이 다르므로 요구를 나눈다.
2. **개정 대상 계약을 전수로 확정한다.** 도구를 지우지 않으므로 도구 집합 개수 단언은 그대로지만, 반환 필드가 늘어나므로 반환 형태를 단언하는 자리는 전부 본다. 다음 명령의 출력을 요구의 Change Notes 에 붙이고, 걸린 자리마다 개정이 필요한지 아닌지를 한 줄로 판정한다.
   ```
   grep -rn "workflow_resume_hint\|workflow_pipeline_next\|workflowResumeHint\|workflowPipelineNext" docs/spec/ test/ src/ skills/ .agents/skills/
   ```
   착수 시점에 걸리는 요구는 `FR-MCP-057`(`docs/spec/40.mcp-stdio-interface.srs.md:4114`)과 `docs/spec/50.nodejs-implementation.srs.md:11420` 의 AC-9, 그리고 `docs/spec/90.appendix.md` 의 도구 목록 두 행이다. 세 자리 모두 **이름을 유지하는 한 개정이 필요하지 않다.** 개정이 필요해졌다면 그것은 별칭 유지 결정이 지켜지지 않았다는 신호이므로, 개정을 쓰기 전에 §3 으로 돌아간다.
3. 짝 2·3 에 대해 실패하는 테스트를 먼저 쓴다. 단언은 넷이다.
   - `workflow_next_plan_task` 의 반환값에 `resume` 이 있고 그 값이 `blocking !== true && nextTask !== null` 과 일치한다.
   - `workflow_pipeline_status` 의 반환값에 `nextHint` 가 있고 그 값이 `latestEvent.event.next_hint` 와 일치한다.
   - `workflow_resume_hint` 가 여전히 등록되어 있고, 그 반환값이 `workflow_next_plan_task` 의 반환값과 **키 단위로 같다**.
   - `workflow_pipeline_next` 가 여전히 등록되어 있고, 그 `nextHint` 가 `workflow_pipeline_status` 의 `nextHint` 와 같다.
   뒤의 둘은 별칭이 조용히 사라지는 것을 막는 단언이다. 이것이 없으면 다음 사람이 "이제 파생 필드가 원본에 있으니 지워도 된다"고 판단해 §2 가 막으려는 일을 다시 한다.
4. 최소 구현으로 통과시킨다. `workflowResumeHint` 와 `workflowPipelineNext` 안에 있던 파생 계산을 각각 `workflowNextPlanTask` 와 `workflowPipelineStatus` 로 옮기고, 두 함수는 옮긴 원본을 그대로 위임한다. 계산 규칙이 한 곳에만 남는다.
5. **`actionTool()` 은 손대지 않는다.** `src/core/workflow/work-order.ts:82`·`:86` 이 돌려주는 이름이 계속 실재하는 도구를 가리키는지 테스트로 고정한다. 단언은 "`actionTool()` 이 돌려주는 모든 값이 등록된 MCP 도구 이름 집합의 원소다"이며, 항목 06 의 계약 3(스킬 산문과 코드의 도구 이름 대조)과 대상이 다르다 — 여기서는 코드가 코드를 가리킨다.
6. 짝 1 에 대해 실패하는 테스트를 먼저 쓴다. 네 스킬의 본문이 활성 target 요약을 위해 두 호출을 함께 지시하지 않을 것을 `test/skills/` 아래에서 단언한다.
7. 짝 1 의 스킬 문장을 고친다. `kiwi-review-fix-loop:510` 의 선결 호출 지시, `kiwi-srs:252`/`:262`, `kiwi-planner:250`/`:257`, `kiwi-srs-feasibility:212`/`:810` 이 대상이다. 활성이 아닌 target 을 다루는 경로에서는 `summarize_target` 지시를 그대로 둔다.
8. **세 렌더링을 함께 고친다.** `skills/claude` · `skills/codex` · `skills/etc` 를 같은 커밋에서 수정한다. 짝 1 의 호출 지시가 세 렌더링에서 문장 형태가 다르므로 각각 찾아 고친다.
9. `speckiwi skills mirror --check` 로 발산을 확인하고 `speckiwi skills mirror --write` 로 `.agents/skills/` 를 재생성한다.
10. 전체 스위트를 돌려 회귀 0건을 확인한다. 검증 서브에이전트에게 원본 요구와 diff 만 준다.

**도구를 지우는 쪽으로 결정을 뒤집는다면** 위 단계로는 부족하다. 그때는 `src/core/workflow/work-order.ts:82`·`:86` 을 작업 대상에 넣어 대체 도구 이름을 정하고, §2 가 열거한 두 요구(`FR-MCP-057` AC-5, `50.nodejs-implementation.srs.md` AC-9)와 `docs/spec/90.appendix.md` 의 두 행을 개정 대상으로 명시하며, 일곱 테스트 파일의 단언을 요구 개정과 함께 갱신해야 한다. 그 결정과 사유를 요구의 Change Notes 에 남긴다.

## 5. 완료 조건

- `workflow_next_plan_task` 가 `resume` 을, `workflow_pipeline_status` 가 `nextHint` 를 돌려주고 그 값이 종전 파생 도구의 값과 같다는 것이 테스트로 단언된다.
- 파생 계산이 코드에 한 벌만 있다. 원본 함수에서 지우면 별칭의 값이 달라져 테스트가 실패한다.
- `workflow_resume_hint` 와 `workflow_pipeline_next` 가 여전히 등록되어 있고, 둘 중 하나를 등록부에서 지우면 테스트가 실패한다.
- `actionTool()` 이 돌려주는 모든 이름이 등록된 도구 집합의 원소라는 것이 테스트로 단언된다. 그 집합에서 하나를 빼면 실패한다.
- 활성 target 요약을 위해 두 호출을 함께 지시하는 스킬 문장이 세 렌더링 어디에도 없다.
- `speckiwi skills mirror --check` 가 발산 0건을 보고한다.
- 대응 요구가 `verified` 이고 검증 증거가 붙어 있다.

## 6. 틀렸을 때 무엇이 깨지는가

**두 파생 도구를 지우면 `get_next_work_order` 가 존재하지 않는 이름을 지시한다.** `actionTool()` 이 `resume-session` 과 `fix-artifact` 에서 `workflow_resume_hint` 를 돌려주고 그 값이 `nextAction.tool` 로 나간다. 도구가 없으면 그 지시를 따르는 에이전트의 호출이 실패하며, 실패가 드러나는 시점은 도구를 지운 커밋이 아니라 그 두 action 이 처음 선택되는 실행이다. 증상이 늦게 나타나므로 이 항목에서 가장 위험한 오작동이다.

**짝 1 에서 `summarize_target` 지시를 전부 지우면 활성이 아닌 target 을 요약하는 경로가 끊긴다.** `get_active_target` 은 활성 target 만 요약한다. 명시적 target 을 다루는 자리에서 이 도구로 대체하면 **다른 target 의 요약이 활성 target 의 요약으로 조용히 바뀐다.** 응답 형태가 같으므로 실행 중에 드러나지 않는다.

**파생 필드를 옮기지 않고 원본에 추가만 하면 계산이 두 벌이 된다.** `resume` 불린과 `nextHint` 는 계산 가능하지만, 규칙이 두 곳에 있으면 한쪽만 고쳐지는 것이 근거 문서 §5.1 이 기록한 결함 형태다. 반드시 원본으로 옮기고 별칭은 위임만 하게 한다.

**도구 개수 단언을 요구 개정 없이 낮추면 계약 검사가 약해진다.** `test/mcp/workflow-workspace-root.fr-mcp-058.test.ts` 의 그 단언은 `workflow_*` 전부가 `workspaceRoot` 를 받는다는 검사를 통과시키는 분모다. 이 항목은 도구를 지우지 않으므로 그 수를 건드릴 이유가 없다. 건드리게 되었다면 별칭 유지 결정이 지켜지지 않은 것이다.

**한 렌더링만 고치면 근거 문서 §5.1 이 기록한 실패 형태가 재발한다.**

## 7. 건드리지 말아야 할 것

**`workflow_resume_hint` 와 `workflow_pipeline_next` 의 도구 이름은 지우지 않는다.** §2 와 §6 이 사유다. 이 항목이 옮기는 것은 파생 **계산**이지 도구 **표면**이 아니다.

**짝 4 — `workflow_workspace_info` 는 삭제하지 않는다.** 반환 필드만 보면 `mcp_workspace_info` 의 진부분집합이 맞다. 그러나 두 도구는 root 를 다르게 해소한다. `workflow_workspace_info` 는 `workspaceScope: "worktree-local"` 로 등록되어 호출자가 넘긴 `workspaceRoot` 에 대해 답하고(`src/mcp/tools/read-tools.ts:319`), `mcp_workspace_info` 는 SRS 를 향하는 도구라 항상 서버 시작 시점의 root 에 대해 답한다(같은 파일 `:233-234` 의 `@req REL-MCP-005 AC-2` 주석이 그렇게 밝힌다). 연결된 워크트리에서 호출하면 두 도구의 `workspaceRoot` 가 **서로 다르다.** 같은 질문에 두 번 답하는 것이 아니다. 게다가 FR-MCP-058 의 AC-1 이 이 도구를 검사 대상의 프로브로 쓴다.

**`meta.generatedAt` 은 이 항목에서 손대지 않는다.** 소비처를 직접 조사한 결과 `src/` · `skills/` · `.agents/` 어디에도 이 값을 읽는 곳이 없고, 유일하게 언급하는 테스트는 그것을 시계 값으로 규정해 비교에서 제외한 뒤 ISO 접두사만 확인한다. 다만 이 필드는 `workflow_workspace_info` 만의 것이 아니라 `src/core/workflow/read.ts:228` 의 공용 `envelope()` 가 모든 workflow 읽기 응답에 붙이는 필드다. 한 도구에서만 빼면 봉투가 도구마다 달라지고, 전부에서 빼면 요구 태그가 붙은 단언을 건드린다. 별도 요구로 다룰 사안이며 이 항목의 범위가 아니다.

**`workflow_pipeline_tail` 과 `workflow_pipeline_status` 는 중복이 아니다.** 근거 문서 §4.7 이 이미 제외 판정했고, 소스가 그것을 뒷받침한다. status 는 `latestEntries.at(-1)` 하나를 돌려주고, tail 은 `visibleWorkflowTail` 이 만든 목록을 돌려주는데 그 목록에는 `latestEntries` 가 배제하는 `audit_note` 와 `record_reclassification` 항목이 포함된다. 서로 다른 질문에 답한다.

**다만 `workflow_pipeline_tail` 자체에 별개의 결함이 있다 — 이 항목에서 고치지 않고 별도 요구로 넘긴다.** `workflowPipelineTail` 은 `cursor(tail, options.limit ?? 20, options.offset)` 로 자르는데, `cursor` 는 `items.slice(start, start + limit)` 로 배열의 **앞에서부터** 자른다(`src/core/workflow/read.ts:123-135`). `parsed.tail` 은 파일 순서 그대로이므로 가장 오래된 항목이 앞에 있다. 따라서 인자 없이 부른 `workflow_pipeline_tail` 은 **가장 오래된 N 건**을 돌려준다. 저널의 줄 수가 기본 상한보다 많으면 `latestEvent` 는 결과에 나타날 수 없다. 근거 문서가 관측한 현상의 원인이 이것이다. 이름과 동작이 어긋나 있으므로 중복 정리가 아니라 별도의 정확도 요구로 등록해야 한다.

**`list_requirements` 와 `search_requirements` 도 중복이 아니다.** §4.7 이 제외 판정했다. 입력 스키마와 반환 규모가 달라 서로 다른 질문에 답한다.

**`orchestrate_*` 의 CLI·MCP 양면 존재도 정리 대상이 아니다.** 단일 소스 파생이며 §4.7 이 제외 판정했다.
