## 0. 이 항목이 생긴 경위

22번이 소스 세 파일을 고쳤더니 `docs/spec` 의 `file:line` 참조 **스물**이 낡았다. 한 항목의 작업 하나가 낸 수다.

| 소유 요구 | 개수 | 자리 |

| `FR-NODE-203` | 7 | `50.nodejs-implementation.srs.md` 의 13175 · 13186 · 13189 · 13204 · 13205 · 13206(둘) |
| `FR-FLOW-168` | 3 | `60.workflow-release.srs.md` 의 11337 · 11348 · 11365 |

**다섯 다 verified 다.** 그래서 `edit_requirement_table_rows` 가 `MUTATION_DENIED: Granular edits cannot modify verified requirements` 로 거절한다(`src/core/mutation/edit-requirement.ts:90-91` 의 `assertEditable`). 그 거절은 결함이 아니라 계약이다.

22번은 자기가 원인이 된 셋(`FR-NODE-203`·`FR-FLOW-168`·`REL-MCP-005`)에만 정정 노트를 붙이고 나머지 아홉은 붙이지 않았다. **그 판단이 옳다** — 노트 스무 줄은 다음 소스 편집에서 다시 낡는다. 산문으로 메우는 것은 같은 일을 반복하는 것이다.

## 1. 왜 지금 고쳐야 하는가

**낡은 참조는 조용하다.** 아무도 붉히지 않고, 읽는 사람만 엉뚱한 줄로 간다. 그리고 이 저장소의 요구는 `file:line` 으로 코드를 지목하는 것이 관례라 참조가 계속 늘어난다.

**`FR-FLOW-167 AC-8` 은 "후속 항목을 번호로 지목한 채" 를 계약으로 담고 있다.** 그런데 그 요구 자신의 낡은 참조 일곱이 지목되지 않았다. 이 항목이 그 번호다.

## 2. 확인해야 할 것

착수 시점에 먼저 재야 한다. 아래는 2026-08-31 실측이고 그 뒤 움직였을 수 있다.

- **분모가 얼마인가.** 22번은 자기 편집이 낸 스물만 셌다. `docs/spec` 전체에서 낡은 `file:line` 참조가 몇인지 먼저 세어야 범위가 정해진다.
- **어떤 형태를 참조로 볼 것인가.** `path:line` · `path:line-line` · `path 의 :line` 처럼 표기가 갈린다. **표기를 세는 것이 아니라 지목을 세야 한다.**
- **무엇을 신선하다고 할 것인가.** 줄 번호가 가리키는 내용이 그대로인지 보려면 그 시점의 내용을 알아야 한다. 참조에 내용 지문을 함께 적게 할지, 아니면 줄 번호를 버리고 심볼 이름으로 옮길지가 갈린다.
- **verified 요구를 어떻게 고칠 것인가.** 검사가 잡아도 고칠 수단이 없으면 검사는 잔소리가 된다. `assertEditable` 의 계약을 건드리지 않고 고칠 길이 있는지 본다.

## 3. 목표 상태

소스가 움직여 `docs/spec` 의 지목이 어긋나면 기계가 붉힌다.

## 4. 작업 단계

1. **§2 의 넷을 재고 방향을 정한다.** 특히 넷째 — 잡아도 고칠 수 없으면 검사부터 만들 이유가 없다.
2. **요구를 등록한다.**
3. **실패 테스트를 먼저 쓴다.** 오늘 낡은 자리가 있으면 그것이 red 다. 없으면 하나를 심어 red 를 본다.
4. red 확인 → 구현 → green → 회귀.

## 5. 완료 조건

- 소스에서 줄이 밀렸을 때 그 지목이 붉어지는 것을 테스트가 잡는다. **밀림을 되돌리면 초록이다.**
- 오늘 낡은 자리 전부의 처분이 정해진다 — 고쳤는지, 못 고쳐 기록만 했는지.
- **검사가 잡는 표기와 못 잡는 표기가 요구에 실측과 함께 적힌다.** 이 계획에서 분모가 어휘에 걸려 다섯 번 새어 나갔다.

## 6. 건드리지 말아야 할 것

- **`assertEditable` 의 거절을 완화하지 않는다.** verified 요구를 도구가 함부로 고치지 못하는 것은 이 저장소의 계약이고, 그것을 푸는 것은 별개의 결정이다.
- **이미 붙은 정정 노트를 지우지 않는다.** 그것도 이력이다.

### 7.4 왜 자동 수리를 만들지 않는가 — 91%가 세 겹으로 무너집니다

수리 축은 `git blame` → 인용 시점 blob → 지문 → HEAD 재배치로 **148건(91%)이 유일 재배치**된다고 적었고 **손 검증은 1건**이었습니다. 위원 2가 그것을 재고 셋을 찾았습니다.

1. **분모 자체가 틀렸습니다.** 수리 축 스크립트의 `forEach` 콜백 안 `return` 이 콜백 전체를 끝내 **한 줄의 두 번째 지목부터 전부 버렸습니다.** 같은 정규식으로 다시 세면 435 가 아니라 **493** 입니다(다른 두 위원이 독립적으로 얻은 493·494 와 일치).
2. **91%는 시작 줄만 센 값입니다.** 재배치 대상 155 중 **112가 범위 지목**이고, 시작만 옮기면 **44건(39%)이 역전 범위**가 됩니다 — `read.ts:693-702 → 795-702`. 끝까지 옮기도록 고쳐도 지문이 `*`·`}`·`});` 같은 무정보 문자인 14건을 빼면 무인 가능은 **59.2%** 입니다.
3. **그 100건을 손으로 읽으면 절반만 옳습니다.** 표본 14건 중 **옳음 7 · 적극적으로 틀림 3 · 영역 지목이라 숫자를 옮겨도 뜻이 회복되지 않음 4.**

틀린 셋 중 하나가 이 결정을 굳혔습니다 — `60.workflow-release.srs.md:11078` 은 **verified 요구의 AC-3** 이고, 그 AC 는 *"`SKILL.md:526` 의 문장이 **사라졌다**"* 를 주장하는 회고적 지목입니다. 526→541 로 옮기면 AC 가 *"사라진 문장이 541 에 있었다"* 고 말하게 됩니다 — **원래 뜻의 반대**입니다.

**그리고 되돌릴 수 없습니다.** 격리된 임시 저장소에서 실행해 확인했습니다.

```
1) 수리 전:            AMBIGUOUS 5,9   (진실은 5)
2) 틀린 수리(:9) 뒤:   FRESH           ← 영구히
3) 소스가 또 밀린 뒤:  AMBIGUOUS 6,10  (진실은 6, 문서는 9)
```

신선도는 `git blame` 으로 인용 시점 지문을 뜯습니다. **수리가 그 줄을 다시 쓰면 blame 이 수리 커밋을 가리키고 지문이 수리가 쓴 값에서 뜯히므로, 어떤 숫자를 썼든 그 다음 순간부터 FRESH 입니다.** 검사가 자기 오류에 구조적으로 눈이 멉니다.

**아무도 세지 않은 것이 결정적입니다.** 수리는 요구마다 Change Note 를 삽입해 그 파일의 아래 줄 번호를 전부 밉니다. `docs/spec` 자신을 가리키는 지목이 22건이므로 **62개 요구를 수리하는 행위 자체가 40여 개 지목을 낡게 만듭니다. 수렴하지 않습니다.**

### 7.5 답은 줄 번호를 떼는 것입니다

**줄 번호를 잃어서 나빠지는 독자가 하나도 없고, 떼면 좋아지는 독자가 둘 있습니다.** (2026-09-06 정정 — 이전 문면은 *"읽는 도구가 하나도 없다"* 였고 그것은 거짓이었습니다.)

줄 번호를 **아예 보지 않는** 쪽 셋:

- `src/core/query/links.ts` 의 `links check` 는 `trace.type === "Requirement"` 만 봤습니다 — `Code`·`Test`·`Document` 행 210개는 한 번도 읽히지 않았습니다(이 항목이 그 분기를 넣습니다).
- `collectBrokenTraceLinks` 도 `Requirement` 행만 봅니다.
- `add-requirement.ts` 는 `Code` 행에 줄 범위를 강제하지 않습니다.

줄 번호를 **포함해서 통째로 비교하는** 쪽 둘 — 여기가 이전 문면이 놓친 자리입니다:

- `list_requirements({traceReference})` 의 필터. `records.ts` 의 `normalizeReferenceToken` 이 fragment·역슬래시·선행 `./` 만 손질하고 **접미는 남긴 채** `traceReferences` 를 채우고, `filter.ts` 의 `normalizeFilterReference` 도 접미를 남긴 채 **정확 일치**로 비교합니다.
- `route-probe.ts` 의 `deriveAnchoredRequirements`. 주석이 *"`list_requirements({traceReference})` 와 같은 정규화를 쓴다"* 고 못박고 있으므로 같은 성질을 그대로 물려받습니다.

**그래서 접미가 붙은 행은 자기 철자에만 답했습니다.** HEAD 대비 실측 — `--trace-reference src/cli/commands/read.ts` 가 **5건 → 14건**, 접미를 담은 조회 키 **210개가 사라졌는데 그중 오늘 자기 경로로 도달 못 하는 것은 0건**이고, 평범한 경로 키 **173개가 새로 생겨 요구 73개**가 새로 도달됩니다.

승격 게이트의 `localEvidencePath` 는 `candidate.replace(/:\d+(?::\d+)?$/, "")` 로 **줄 번호를 떼고** 경로만 해소하는데, 그것이 읽는 것은 **Verification Evidence 의 Reference** 이지 이 필드가 아닙니다 — 독자가 아니라 **선례**입니다.

그리고 **떼어도 잃을 것이 거의 없습니다.** trace Reference 210 중 **170(81%)이 범위이고 폭 중앙값이 36줄**입니다. 36줄짜리 범위는 애초에 위치를 지목하지 않으므로 옮길 심볼이 없고 잃을 정보도 없습니다. note 에 백틱 심볼을 담은 행도 드뭅니다(착수 당시 적었던 건수는 재현되지 않아 걷어냈습니다).

**빼면 그 아홉은 다시는 낡지 않습니다. 코드 0줄입니다.**

- **맨 `:N` 계열.** `docs/spec` 의 `:\d+` 출현 **1174** 에서 확장자 앵커 **495** 를 뺀 **679** 가 이 계열입니다(맨 `:N`·괄호 안·에이전트 변종·문서번호 약칭·이어 적기·영어 `line N`). 착수 당시 적었던 계열별 내역은 합계가 총계와 맞지 않아 걷어냈습니다 — 총계는 두 정규식의 차이로 언제든 재계수됩니다. 문맥 상속이 필요하고 그것이 판정이므로 이 항목의 분모 밖입니다.
- **`skills/**` 의 지목.** 네 건을 대조했고 전부 낡았습니다(`read.ts:100`=`}`, `summary.ts:42`=빈 줄, `mutations.ts:42`=무관, `add-requirement.ts:220-235`=AC 구성).

### 7.7 검사가 못 잡는 것 — 요구에 실측과 함께 적을 것

**막지 못하는 것**: 맨 `:N` 계열 **679**(§7.6 의 도출) · **산문 184건은 신선도 검사를 영영 받지 않음**(고칠 수도 면제할 수도 없음 — 500자 상한) · **같은 표의 Notes 셀에 적힌 지목 20건**(5 셀 — FR-FLOW-060 둘, 063, 064, 066) · basename 애매(건수는 어느 디렉터리를 세느냐에 따라 갈려 걷어냈습니다) · **범위의 뜻 170**(세 술어가 85건에서 갈림) · 빈 지문 9 · 처음부터 틀리게 적힌 지목(어떤 술어도 모름) · **`Requirement` 의 대소문자 변형 6행**(§7.10).

**범위 지목은 술어를 바꿔 다룹니다.** 세 술어를 같은 210건에 재어 **단일 줄 40건에서는 셋이 일치하고 범위 170 중 85건에서 답이 갈립니다.** 그러므로 요구에 이렇게 적습니다 — *"이 검사는 구간이 여전히 그 설명을 담는가를 판정하지 않는다. 텍스트가 인용 시점과 같은 자리에 있는가 하나만 판정한다."*

**basename 되짚기를 켜지 않습니다.** 두 위원이 독립적으로 같은 함정을 밟았습니다 — 켜면 `00.charter.md` 20건이 조용히 연구 문서로 해소되어 **"신선"으로 채점됩니다.** 규칙: **디렉터리를 담은 지목은 정확 경로로만 해소한다.** 그리고 상당수가 여러 후보에 걸리는데, 특히 `SKILL.md` 는 이 트리에 수십 개가 있고 그중 셋은 **일부러 깨뜨려 둔 픽스처 사본**입니다. 건수를 적지 않는 이유는 그 값이 **어느 디렉터리를 세느냐에 따라 갈리기 때문**입니다 — 착수 당시 값, 검증 축의 값, 재계수 값이 서로 달랐고 셋 다 자기 walk 안에서는 옳았습니다.

### 7.8 순서

1. **carrier 선을 요구에 못박는다** — 실측 수(493 / 254~258 / 검사 밖 660)가 **등호가 아니라 이름으로** 잡혔는가
2. **실패 테스트 먼저** — **정확히 10건**을 이름과 함께 보고하며 red 인가
3. **`links check` 에 `Code` 분기 구현**(약 40줄) — `checked` 가 늘고 `broken` 에 10건이 담기는가. **`release-readiness.ready` 에 배선하지 않는다**
4. **열 자리 처분** — 아홉은 Trace Links 에서 **줄 번호를 떼고**, 하나(AC)는 그 자리에서 판정. 여덟 verified 요구가 하향 → 수정 → 재승격되고 각각 Change Note 를 갖는가(`reason` 필수)
5. **형태 금지 게이트** — 앞으로 `docs/spec` 의 carrier 에 `path:line` 을 새로 쓰지 않는다
6. **회귀 + 밀림 되돌림 증거화** — 격리 사본에서 앵커 1회 매치, red → 되돌림 → green

### 7.9 건드리지 않는 것

- **`assertEditable` 의 거절을 완화하지 않는다**(§6 그대로).
- **`LIVE_SECTIONS` 정책을 고치지 않는다.** 정의역을 carrier 로 자르면 그 논쟁이 필요 없습니다. 그리고 위원 셋이 지적한 대로, `- [2026-08-29] 판정표 …` 형태의 **날짜 붙은 census bullet** 의 줄 번호를 오늘 값으로 고치면 **그 날짜에 참이 아니던 것을 참이라 적게 됩니다.**
- **`edit_acceptance_criteria` 가 게이트를 안 타는 것에 기대지 않는다.** 그것은 결함이고(요구 문면에 Status 언급이 없습니다), 닫는 날 이 절차가 무효가 됩니다.
- **`FR-FLOW-141` 을 넓히지 않는다.** 그 AC 하나가 *"착수일에 트리가 깨끗하다"* 를 `[x]` 로 담고 있어, `docs/spec` 을 주어에 넣으면 **참이었던 역사 서술을 지우게** 됩니다. 새 요구를 세우되 `@cite-lint: ignore` 어휘는 물려받습니다.

### 7.10 대소문자 비대칭 — 이 항목에서 고치지 않고 기록만 합니다 (2026-09-06)

`links.ts` 의 새 분기는 `trace.type === "Requirement"` 로 **정확 일치** 비교를 합니다. 그래서 소문자 `requirement` 로 적힌 Trace 행 **6개**가 id 검사를 건너뛰고 경로 분기로 내려가며, 거기서 후보가 0이므로 아무 말도 하지 않습니다.

| 요구 | 참조 |
|---|---|
| IR-CLI-091 | FR-NODE-182 |
| FR-NODE-182 | FR-FLOW-121 |
| FR-FLOW-152 | FR-FLOW-131 |
| FR-FLOW-153 | FR-FLOW-137 |
| FR-FLOW-171 | FR-FLOW-152, FR-FLOW-164 |

**고치지 않는 이유 넷.**

1. **소유가 다릅니다.** id 존재 검사는 `SRS-E012` 이고 그 진단의 `sourceRule` 은 **`FR-PARSE-009`** 입니다. 여기서 그 정의역을 넓히면 이 요구의 AC 가 담지 않은 동작을 구현하게 됩니다.
2. **비대칭이 사라지지 않고 자리만 옮깁니다.** `validator/rules.ts` 의 `SRS-E012` 도 같은 정확 일치를 씁니다. `links.ts` 만 대소문자를 무시하게 하면 이번엔 `links check` 와 `validate` 가 같은 6행을 두고 갈라집니다.
3. **정본 철자는 대문자 `Requirement`** 입니다(SRS-MD 규칙 §23.2). 독자를 비정본 철자에 맞추면 그 철자가 굳습니다. 고쳐야 할 것은 독자가 아니라 그 6행입니다.
4. **완전한 침묵은 아닙니다.** `release-readiness.ts` 의 `collectBrokenTraceLinks` 는 `type.trim().toLowerCase() === "requirement"` 로 비교하므로 **그 6행의 id 가 사라지면 `brokenTraceLinks` 에 담기고 `ready` 가 내려갑니다.** 실증: 소문자 행과 대문자 행에 각각 없는 id 를 넣어 호출하니 둘 다 보고됩니다.

**남는 노출**: `links check` 와 `validate` 는 그 6행의 dangling id 를 말하지 않습니다. 오늘 6개 id 는 전부 실재합니다.

### 7.11 두 검사가 "파일처럼 보이는 것"을 다르게 봅니다 — 기록만 합니다 (2026-09-06)

형태 금지(`citesALine`)와 경로 해소(`referencedPaths`)는 서로 다른 술어를 씁니다. 그래서 두 방향으로 어긋납니다.

**과다 — 버전 문자열을 경로로 봅니다.** `referencedPaths` 의 `REPOSITORY_PATH` 가 `[A-Za-z0-9_.@/-]+\.[A-Za-z0-9]+$` 라서 실측으로 이렇게 갈립니다.

| 값 | `citesALine` (AC-6 이 배제 선언) | `referencedPaths` (SRS-W074 대상) |
|---|---|---|
| `v2.5.0` | false | **`["v2.5.0"]`** |
| `1.2:34` | false | **`["1.2"]`** |
| `3.1.0` | false | **`["3.1.0"]`** |
| `5:0` · `12:48:33` | false | `[]` |
| `T-PH001-02` · `FR-NODE-206` | false | `[]` |

즉 Trace Link Reference 셀에 버전 문자열을 적으면 **SRS-W074 오탐**이 납니다. **오늘 실제 사례는 0건**입니다 — `links check` 가 broken 0 이고, 그 정의역에 그런 행이 없습니다. 고치려면 `REPOSITORY_PATH` 의 확장자에 `citesALine` 과 같은 "첫 글자는 letter" 규칙을 넣어야 하는데, 그것은 SRS-W074 의 정의역 변경이므로 이 항목의 AC 밖입니다.

**과소 — `#L30` 은 형태 금지를 빠져나갑니다.** `citesALine` 의 앵커가 `:\d+$` 라 GitHub 식 `path.ts#L30` 은 걸리지 않습니다. 경로 해소 쪽은 fragment 를 떼고 `path.ts` 로 정확히 해소하므로 **경로 검사는 정상**이고, 새어 나가는 것은 **형태 금지뿐**입니다. 같은 성질의 우회 철자가 몇 가지 더 있습니다(`#L30-L40` 등). 착수 당시 세어 둔 종류 수는 재현되지 않아 적지 않습니다.
