## 1. 작업 목적

이 계획은 사용자가 "다음 목표를 2.1.0으로 설정해줘"라고 요청했을 때 SpecKiwi가 Target Map 등록, Active Target 전환, 이후 SRS 작성 target 선택을 도구 수준에서 일관되게 처리하도록 구현하는 지침이다.

구현 목표는 네 가지다.

| Goal | Required Outcome |
|---|---|
| Target registration | `set-active-target` / `set_active_target`이 명시적 create flag로 미등록 target row를 생성한다. |
| Active Target assignment | Active Target metadata와 Target Map active row가 같은 target을 가리키고 active row는 하나만 남는다. |
| Default target resolution | `add-requirement` / `add_requirement`에서 target 생략 시 `00.index.md` Active Target을 사용한다. |
| Agent workflow | managed `AGENTS.md`와 `CLAUDE.md`가 next-target authoring workflow를 설명한다. |

## 2. 프로젝트 온보딩 컨텍스트

SpecKiwi는 Markdown SRS를 source of truth로 쓰는 Node.js TypeScript CLI와 stdio MCP server다. Parser가 `docs/spec/00.index.md`와 scope SRS 파일을 읽고, core mutation/query service를 CLI와 MCP adapter가 공유한다.

주요 디렉터리 맵:

| Path | Role |
|---|---|
| `src/core/mutation/set-active-target.ts` | Active Target metadata와 Target Map row를 수정하는 core mutation |
| `src/core/mutation/add-requirement.ts` | 새 Requirement Block을 scope SRS 문서에 추가하는 core mutation |
| `src/core/types.ts` | Target entry, Target source, mutation output type이 모이는 shared type 위치 |
| `src/cli/commands/mutations.ts` | mutation CLI surface |
| `src/mcp/tools/mutation-tools.ts` | MCP mutation tool adapter |
| `src/mcp/server.ts` | stdio MCP SDK schema registration |
| `src/core/bootstrap/templates.ts` | managed agent instruction block renderer |
| `test/core/mutation/` | core mutation unit tests |
| `test/cli/` | CLI command tests |
| `test/mcp/` | MCP adapter and stdio tests |
| `docs/spec/` | SRS source of truth |

핵심 규칙:

- `--create` 또는 `create=true` 없이는 미등록 target을 만들지 않는다.
- explicit target은 Active Target default보다 우선한다.
- Active Target이 비어 있고 explicit target도 없으면 파일을 변경하지 않는다.
- Target Map row의 table cell 값은 pipe, CR, LF 문자를 허용하지 않는다.
- CLI와 MCP는 같은 core mutation 결과와 error code를 사용한다.
- managed agent instruction text가 바뀌면 `AGENT_INSTRUCTION_VERSION`을 올리고 관련 테스트 기대값도 같이 갱신한다.

## 6. Phase P1 — Core Target Lifecycle and Default Resolution

### TASK-P1-001 — `setActiveTarget` create-mode core 계약 확장

| Field | Value |
|---|---|
| Related REQ-ID | `FR-NODE-014` AC-1, AC-2, AC-3, AC-4, AC-8 |
| Files | `src/core/mutation/set-active-target.ts`, `src/core/types.ts`, `test/core/mutation/set-active-target.test.ts` |
| Function signatures | `interface SetActiveTargetInput { target: string; create?: boolean; targetType?: string; description?: string; dryRun?: boolean }`; `function buildTargetEntry(input: SetActiveTargetInput): TargetEntry`; `function renderTargetRow(row: TargetEntry, status?: string): string` |
| source_anchors | `src/core/mutation/set-active-target.ts:9-80`; `src/core/types.ts:126-131`; `test/core/mutation/set-active-target.test.ts:8-50` |
| Feasibility | Medium |
| Idempotent | false |

Implementation guide:

1. Extend `SetActiveTargetInput` with `create`, `targetType`, and `description`.
2. Validate `target`, `targetType`, and `description` with the same markdown table-cell safety helper used by requirement mutations.
3. Keep existing unknown-target rejection when `create` is false.
4. When `create` is true and no row exists, append one Target Map row before the first row after the Target Map table or at table end.
5. Use deterministic defaults: `type = "version"` and `description = "Target ${target}"` unless caller provides values.
6. Build patch operations in one plan: Active Target metadata replacement or insertion, previous active row status downgrade, new row insertion when needed, target row active status.
7. Return `created: boolean`, `activeTarget`, `previousActiveTarget`, and `written`.

Rationale:

The create flag must be explicit to prevent a typo from silently expanding Target Map. Keeping row creation and active assignment in one patch prevents a transient mismatch between metadata and Target Map status.

Pitfalls:

- Do not change the current behavior for unknown targets without create.
- Do not allow pipe or newline in type or description.
- If a new row is inserted, compute active-row replacement line numbers from the original parsed table and apply operations through `createPatchPlan`; sorted patch application handles descending line order.
- Do not mark previous `released`, `completed`, `frozen`, or `archived` rows as `planned`; only previous `active` rows are downgraded.

Test guidance:

- Success: create missing `v2.1.0` with defaults and verify `| v2.1.0 | version | active | Target v2.1.0 |`.
- Success: create missing target with explicit type and description.
- Failure: missing target without create returns `NOT_FOUND` and index text is unchanged.
- Boundary: existing active target is downgraded, and no second `active` row remains.
- Boundary: dry-run create returns patch preview and leaves index unchanged.
- Boundary: convert `docs/spec/00.index.md` fixture text to CRLF before create-mode mutation and assert the resulting file still contains CRLF line endings.
- Failure: unsafe description containing `|` returns `MUTATION_DENIED`.

### TASK-P1-002 — `addRequirement` Active Target default resolution

| Field | Value |
|---|---|
| Related REQ-ID | `FR-NODE-014` AC-5, AC-6, AC-7, AC-8 |
| Files | `src/core/mutation/add-requirement.ts`, `src/core/types.ts`, `test/core/mutation/add-requirement.test.ts` |
| Function signatures | `interface AddRequirementInput extends Omit<RenderRequirementInput, "id" \| "type" \| "target"> { type: RequirementType; scope: string; target?: string; dryRun?: boolean }`; `function resolveRequirementTarget(workspace: ParsedWorkspace, input: AddRequirementInput): Result<{ target: string; targetSource: "explicit" \| "active-target" }>` |
| source_anchors | `src/core/mutation/add-requirement.ts:15-18`; `src/core/mutation/add-requirement.ts:209-265`; `src/core/query/summary.ts:17-23`; `test/core/mutation/add-requirement.test.ts:8-168` |
| Feasibility | Medium |
| Idempotent | false |

Implementation guide:

1. Change `AddRequirementInput` so `target` is optional.
2. Move table-cell validation that references target until after target resolution.
3. Parse workspace before target-required validation.
4. Resolve target:
   - If `input.target` is a non-empty string, use it with `targetSource = "explicit"`.
   - Otherwise use `workspace.index.activeTarget.trim()` with `targetSource = "active-target"`.
   - If resolved target is empty, return `MUTATION_DENIED` with a message that says Active Target must be set or target must be provided.
5. Build a resolved input object that has `target` filled and pass that object to `canBeVerified`, `assertSafeAddRequirementTableCells`, `renderRequirementBlock`, and `buildOutputRecord`.
6. Keep existing unknown-target rejection against the resolved target.
7. Add `targetSource` to `AddRequirementOutput` and include the resolved target in `record.target` and metadata.

Rationale:

Only the core service can make CLI and MCP defaulting identical. Adapter-level defaulting would duplicate behavior and create different error messages.

Pitfalls:

- Do not pass `String(undefined)` from MCP; that would create literal `"undefined"`.
- Do not call `assertSafeAddRequirementTableCells` before target resolution because it currently reads `input.target`.
- Do not change explicit target precedence.
- Do not let Active Target fallback bypass Target Map registration.

Test guidance:

- Success: fixture active target `v1.0.0`, call `addRequirement` without target, verify record target and metadata target are `v1.0.0` and output `targetSource` is `active-target`.
- Success: explicit target `v1.1.0` wins over active target `v1.0.0`.
- Failure: clear `| Active Target |  |`, omit target, verify `MUTATION_DENIED` and scope file unchanged.
- Failure: set Active Target to unknown value in index, omit target, verify unknown target error and no write.
- Boundary: dry-run omitted target returns `written: false`.
- Boundary: convert the target scope SRS fixture text to CRLF before omitted-target add and assert the resulting scope file preserves CRLF line endings.
