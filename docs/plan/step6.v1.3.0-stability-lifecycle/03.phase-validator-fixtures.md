## Goal

Add stability diagnostics and fixtures that prove `draft`, `volatile`, `verified`, active target, and released target semantics.

## TASK-P2-001 — Stability diagnostic registry and validator rules

| Related REQ-ID | `FR-PARSE-015` |
| Files | `src/core/diagnostic-registry.ts`, `src/core/validator/rules.ts`, `docs/rule/SRS-MD-Rules-v1.0.0.md`, `docs/spec/90.appendix.md` |
| Source Anchors | `src/core/diagnostic-registry.ts:80-110`, `src/core/diagnostic-registry.ts:320-390`, `src/core/validator/rules.ts:119-179`, `docs/rule/SRS-MD-Rules-v1.0.0.md:751-760`, `docs/rule/SRS-MD-Rules-v1.0.0.md:1450-1460`, `docs/rule/SRS-MD-Rules-v1.0.0.md:1476-1496` |
| Feasibility | Medium |
| Idempotent | true |

### Signature

```ts
function isRequirementInActiveOrReleasedTarget(workspace: ParsedWorkspace, record: RequirementRecord): boolean;
function isDraftImplementationContractBlocked(record: RequirementRecord): boolean;
```

Recommended diagnostic codes:

| Code | Severity | Meaning |
|---|---|---|
| `SRS-E033` | error | verified requirement has `Stability=draft` |
| `SRS-W022` | warning | requirement uses legacy `Stability=volatile` |
| `SRS-W023` | warning | non-discarded draft requirement is in active or released target |

### Reference Pattern

Use existing registry entries in `src/core/diagnostic-registry.ts` and validation push style in `src/core/validator/rules.ts:119-179`.

### Implementation Guide

1. Register new diagnostic definitions.
2. In validator, keep `SRS-E011` for unknown stability values.
3. Emit `SRS-W022` for `volatile`.
4. Emit `SRS-E033` for `record.status === "verified"` and `record.stability === "draft"`.
5. Emit `SRS-W023` when `record.stability === "draft"`, `record.status !== "discarded"`, and the record target is active target or target-map status `released`.
6. Update rules document stability table to document canonical values and legacy `volatile` migration policy.
7. Update diagnostic code table in rules and appendix.

### Rationale

Validator diagnostics make maturity problems visible before agents or release tooling make decisions.

### Pitfalls

- Do not flag `draft` in inactive planned future targets as active-work warning.
- Do not make every `draft` requirement an error, because new requirements default to draft.
- Keep legacy warning separate from invalid unknown-value error.

### Test Guide

Test file: `test/core/validator/validation-rules.test.ts`

Scenarios:

- Success: `draft` planned requirement in inactive target has no active/released warning.
- Failure: `verified` + `draft` emits `SRS-E033`.
- Boundary: `volatile` emits `SRS-W022`, while `unknown` emits `SRS-E011`.

## TASK-P2-003 — Frozen Change Notes parsing and validation

| Field | Value |
|---|---|
| Related REQ-ID | `FR-PARSE-015` |
| Files | `src/core/types.ts`, `src/core/query/records.ts`, `src/core/parser/table.ts`, `src/core/validator/rules.ts`, `test/core/parser/workspace-records.test.ts`, `test/core/validator/validation-rules.test.ts`, `test/fixtures/workspaces/stability-frozen-*` |
| Source Anchors | `src/core/types.ts:178-218`, `src/core/query/records.ts:1-136`, `src/core/parser/table.ts:1-90`, `src/core/validator/rules.ts:119-179`, `docs/rule/SRS-MD-Rules-v1.0.0.md:1484-1484`, `test/core/parser/workspace-records.test.ts:1-120` |
| Feasibility | Medium |
| Idempotent | true |

### Signature

```ts
export interface ChangeNoteRow {
  date: string;
  change: string;
  reason: string;
  line?: number;
}

export interface RequirementRecord {
  changeNotes: ChangeNoteRow[];
}
```

### Reference Pattern

Follow the existing evidence and trace table parsing pattern in `src/core/query/records.ts`. Reuse `parseSectionTable` for `#### Change Notes`.

### Implementation Guide

1. Add `ChangeNoteRow` and `changeNotes` to `RequirementRecord`.
2. Parse the `Change Notes` table into `record.changeNotes`.
3. Add fixture coverage for `Stability=frozen` with an empty Change Notes table and for `Stability=frozen` with at least one explicit non-placeholder row.
4. Emit existing `SRS-W009` when `record.stability === "frozen"`, `record.status !== "discarded"`, and no explicit Change Notes row exists.
5. Treat a generated placeholder row with empty cells as no explicit change history.

### Rationale

`FR-PARSE-015 AC-8` requires frozen requirements to be change-controlled. Parser-visible Change Notes are the enforceable source for that policy.

### Pitfalls

- Do not block parsing if Change Notes is missing; emit validation diagnostics instead.
- Do not count the table header separator as a change note.

### Test Guide

Test files: `test/core/parser/workspace-records.test.ts`, `test/core/validator/validation-rules.test.ts`

Scenarios:

- Success: frozen requirement with explicit Change Notes has no `SRS-W009`.
- Failure: frozen requirement without explicit Change Notes emits `SRS-W009`.
- Boundary: discarded frozen requirement does not emit the warning.
