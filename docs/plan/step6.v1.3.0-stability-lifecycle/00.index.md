## 1. 작업 목적

이 계획은 `FR-PARSE-015`와 `FR-FLOW-010`을 구현하기 위한 Phase별 작업 지침이다. 목표는 `Stability=draft`를 단순 문자열 옵션이 아니라 요구사항 성숙도 lifecycle로 정착시키는 것이다.

구현은 네 축을 함께 닫는다.

| Axis | Outcome |
|---|---|
| Taxonomy | canonical stability enum은 `draft`, `evolving`, `stable`, `frozen`, `deprecated`이며 `volatile`은 legacy compatibility로만 다룬다. |
| Validation | unknown stability는 error, legacy `volatile`과 active/release target의 `draft`는 diagnostic, `verified` + `draft`는 error로 보고한다. |
| Workflow | target summary, active-target, release readiness, CLI/MCP JSON이 stability counts와 blockers를 노출한다. |
| Agent guidance | managed `AGENTS.md` / `CLAUDE.md` block과 사용자 문서가 `Status`와 `Stability`를 구분한다. |

## 2. 프로젝트 온보딩 컨텍스트

SpecKiwi는 Git 저장소 내부의 Markdown SRS를 source of truth로 쓰는 Node.js TypeScript CLI와 stdio MCP server다. Parser가 `docs/spec/00.index.md`와 scope SRS 파일을 읽고, validator/query/mutation/workflow core service를 CLI와 MCP adapter가 공유한다.

주요 디렉터리 맵:

| Path | Role |
|---|---|
| `src/core/types.ts` | requirement enum, normalized record, target/release summary type |
| `src/core/schema.ts` | enum guard helper |
| `src/core/query/records.ts` | Requirement Block metadata를 normalized record로 변환 |
| `src/core/validator/rules.ts` | SRS-MD validation diagnostics |
| `src/core/diagnostic-registry.ts` | diagnostic code registry |
| `src/core/mutation/render-requirement.ts` | 새 Requirement Block Markdown renderer |
| `src/core/mutation/add-requirement.ts` | add-requirement core mutation service |
| `src/core/query/summary.ts` | active target과 target summary read contract |
| `src/core/workflow/release-readiness.ts` | release readiness blocker contract |
| `src/core/bootstrap/templates.ts` | init template과 managed agent instruction block |
| `src/cli/commands/` | CLI command surface |
| `src/mcp/` | MCP tools/resources surface |
| `test/fixtures/workspaces/` | parser, validator, workflow fixture workspaces |
| `docs/spec/` | 제품 SRS source of truth |
| `docs/rule/` | SRS-MD authoring rules |

핵심 규칙:

- `Status`는 구현과 검증 진행 상태만 뜻한다.
- `Stability`는 요구사항 문장과 Acceptance Criteria의 성숙도만 뜻한다.
- JSON read payload는 기존 필드를 제거하지 않고 새 필드를 추가한다.
- CLI와 MCP는 `summarizeTarget` 등 core payload를 공유한다.
- Diagnostic code는 `src/core/diagnostic-registry.ts`에 등록한 뒤 emit한다.
- `volatile`은 새 템플릿이나 add-requirement 기본값으로 출력하지 않는다.

빌드와 테스트 치트시트:

## 8. Feasibility 요약

| Area | Feasibility | Risk | Mitigation |
|---|---|---|---|
| Stability enum migration | Medium | Existing TypeScript `Stability` type currently includes only `stable/evolving/volatile`. | Add canonical and legacy helper constants in one pass, then update contract tests. |
| Validator diagnostics | Medium | New diagnostics must not make current SRS invalid unexpectedly. | Emit legacy and active draft as warnings; reserve error for unknown values and `verified` + `draft`. |
| Default `draft` | Medium | Existing add-requirement tests may assume `evolving`. | Update renderer, mutation output record, tests, README, and rule template together. |
| Summary payload expansion | Low | JSON clients may rely on old fields. | Add fields without removing existing fields. |
| Release readiness | Medium | `draft` blockers must affect `ready` without hiding status blockers. | Add separate `stabilityBlockers` and keep existing blocker arrays unchanged. |
| Frozen/deprecated workflow | Medium | `frozen` change detection is not currently parsed and default new-work recommendation is implicit. | Parse Change Notes rows, emit `SRS-W009` for frozen records without explicit change history, and add `newWorkCandidates` that includes only `planned`, `in_progress`, or `blocked` requirements whose stability is neither `draft` nor `deprecated`, while keeping deprecated list/show searchable. |
| Agent instruction update | Low | Managed block replacement depends on versioned heading and suffix marker. | Bump `AGENT_INSTRUCTION_VERSION` and extend existing bootstrap tests. |

## 9. 범위 고정

이번 구현 범위:

- `Stability` canonical enum과 legacy `volatile` policy
- add-requirement default `Stability=draft`
- stability validator diagnostics and registry entries
- frozen requirement Change Notes validation
- deprecated requirement explicit searchability plus exclusion from default new-work candidate lists
- stability-aware target summary and release readiness
- CLI/MCP read JSON parity through shared core fields
- managed agent instruction block version bump and text update
- SRS-MD rules, appendix, README update
- tests, fixtures, SRS evidence, Completed Work Log row after implementation

이번 구현에서 제외하는 범위:

- separate `update-stability` mutation command
- automatic migration command for `volatile`
- changing `Status` enum values
- YAML or generated JSON as canonical requirement source
- removing old JSON fields from target summary or release readiness
