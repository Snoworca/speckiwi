### Signature

```ts
export interface TargetSummary {
  countsByStability: Record<string, number>;
  draftRequirements: string[];
  deprecatedRequirements: string[];
  newWorkCandidates: string[];
  stabilityBlockers: string[];
  stabilityWarnings: string[];
}
```

### Reference Pattern

Extend `summarizeTarget` in `src/core/query/summary.ts:34-65`. CLI and MCP already use this core result.

### Implementation Guide

1. Extend `TargetSummary` with additive stability fields.
2. Count `record.stability ?? "unspecified"` in `countsByStability`.
3. Add non-discarded `draft` IDs to `draftRequirements` and `stabilityBlockers`.
4. Add non-discarded `deprecated` IDs to `deprecatedRequirements`.
5. Add every non-discarded `volatile` record to `stabilityWarnings` as a legacy migration warning.
6. Do not warn for `evolving` by default; it is implementable with caution and remains visible through `countsByStability`.
7. Add `newWorkCandidates` containing requirements whose `Status` is `planned`, `in_progress`, or `blocked` and whose `Stability` is neither `draft` nor `deprecated`.
8. Update CLI and MCP tests to assert the new fields appear in `summary`, `active-target`, `targets`, `summarize_target`, and active-target resource payloads.

### Rationale

Agents should answer current-work questions from JSON payloads without scanning raw Markdown.

### Pitfalls

- Do not remove existing `countsByStatus`, `countsByType`, `blocked`, `implementedNotVerified`, or `missingEvidence`.
- Do not include discarded requirements in blocker arrays.

### Test Guide

Test files: `test/core/query/query-summary-links.test.ts`, `test/cli/read-commands.test.ts`, `test/mcp/read-tools-resources.test.ts`

Scenarios:

- Success: target summary includes stability counts.
- Failure: draft requirement missing from blocker fields.
- Boundary: empty active target returns empty stability counts and empty blocker arrays.
- Boundary: deprecated and draft requirements remain listable and showable, but do not appear in `newWorkCandidates`.
- Boundary: implemented requirements do not appear in `newWorkCandidates`; they remain represented through `implementedNotVerified`.

## TASK-P3-003 — Deprecated explicit searchability and default new-work exclusion

| Feasibility | Low |
| Idempotent | true |

### Signature

```ts
export function isNewWorkCandidate(record: RequirementRecord): boolean;
```

### Reference Pattern

Keep `listRequirements` and `getRequirement` behavior searchable by default. Add recommendation behavior only to summary/new-work candidate fields.

### Implementation Guide

1. Implement `isNewWorkCandidate` as `status` in `planned`, `in_progress`, or `blocked`, and `stability` not in `draft` or `deprecated`.
2. Use it in `summarizeTarget` to populate `newWorkCandidates`.
3. Add tests proving `listRequirements` still returns deprecated records when filters match.
4. Add tests proving `getRequirement` still returns a deprecated requirement by ID.
5. Add tests proving deprecated, draft, and implemented IDs are excluded from `summary.newWorkCandidates`.

### Rationale

`deprecated` is a traceability state, not a deletion mechanism. It must remain searchable but should not guide default new implementation work.

### Pitfalls

- Do not hide deprecated records from explicit list/show APIs.
- Do not treat `deprecated` as `discarded`; the requirement remains part of traceability.

Scenarios:

- Boundary: discarded, verified, and implemented requirements are excluded from `newWorkCandidates`.

## TASK-P3-002 — Release readiness stability blockers

| Feasibility | Medium |
| Idempotent | true |

### Signature

```ts
export interface ReleaseReadinessSummary {
  draftRequirements: string[];
  deprecatedRequirements: string[];
  stabilityBlockers: string[];
  stabilityWarnings: string[];
}

export function collectStabilityBlockers(records: RequirementRecord[]): string[];
```

### Reference Pattern

Follow existing release-readiness collectors such as `collectAcCoverageGaps` and `collectCommandEvidencePolicyViolations` in `src/core/workflow/release-readiness.ts`.

### Implementation Guide

1. Add collector for non-discarded `draft` requirements.
2. Add collector for non-discarded `deprecated` requirements.
3. Add draft IDs to `stabilityBlockers`.
4. Add deprecated IDs or messages to `stabilityWarnings`.
5. Update `ready` so any draft stability blocker makes release readiness false.
6. Keep existing status, evidence, trace, and command policy blockers unchanged.
7. Ensure `baselineCommand` behavior does not change.

### Rationale

Release readiness should not accept a target whose requirements are still draft contracts.

### Pitfalls

- Do not use validation warnings alone to drive readiness; expose first-class stability fields.
- Do not block release on every `evolving` requirement unless SRS is updated to require that.

### Test Guide

Test file: `test/release/release-readiness.test.ts`

Scenarios:

- Success: stable verified target has no stability blocker.
- Failure: draft requirement in release target makes `ready=false`.
- Boundary: deprecated requirement appears in stability warnings but does not hide existing blockers.
