# Phase P1 — Taxonomy Defaults

## Goal

Introduce canonical stability constants and make new requirements default to `Stability=draft`.

### Signature

```ts
export const STABILITY_LEVELS = ["draft", "evolving", "stable", "frozen", "deprecated"] as const;
export const LEGACY_STABILITY_LEVELS = ["volatile"] as const;
export type Stability = (typeof STABILITY_LEVELS)[number] | (typeof LEGACY_STABILITY_LEVELS)[number];
export function isCanonicalStability(value: unknown): value is (typeof STABILITY_LEVELS)[number];
export function isLegacyStability(value: unknown): value is (typeof LEGACY_STABILITY_LEVELS)[number];
export function isKnownStability(value: unknown): value is Stability;
```

### Reference Pattern

Follow the current enum and `isOneOf` pattern in `src/core/types.ts:24-63` and `src/core/schema.ts:1-31`.

### Implementation Guide

1. Replace the current `STABILITY_LEVELS` with the canonical five values.
2. Add `LEGACY_STABILITY_LEVELS` for `volatile`.
3. Update `Stability` so parsed legacy records can still be represented.
4. Extend `src/core/schema.ts` with canonical, legacy, and known guards.
5. Update `test/core/types/contracts.test.ts` to assert canonical and legacy sets separately.

### Rationale

`volatile` must not remain a canonical value, but existing documents should receive a migration diagnostic rather than a surprise unknown-value error.

### Pitfalls

- Do not remove `volatile` from the representable TypeScript type until a migration command exists.
- Do not use `Status` values to model stability.

Scenarios:

- Success: canonical list is exactly `draft/evolving/stable/frozen/deprecated`.
- Failure: `volatile` appears in canonical list.

## TASK-P1-002 — add-requirement default draft stability

| Field | Value |
|---|---|
| Related REQ-ID | `FR-PARSE-015` |
| Files | `src/core/mutation/render-requirement.ts`, `src/core/mutation/add-requirement.ts`, `src/cli/commands/mutations.ts`, `src/mcp/tools/mutation-tools.ts`, `test/core/mutation/add-requirement.test.ts`, `test/cli/mutation-commands.test.ts`, `test/mcp/mutation-tools-errors.test.ts` |
| Source Anchors | `src/core/mutation/render-requirement.ts:32-45`, `src/core/mutation/add-requirement.ts:95-105`, `src/core/mutation/add-requirement.ts:146-195`, `src/cli/commands/mutations.ts:140-178`, `src/mcp/tools/mutation-tools.ts:66-80` |
| Feasibility | Medium |
| Idempotent | true |

### Signature

```ts
export const DEFAULT_REQUIREMENT_STABILITY = "draft";
function assertKnownStabilityInput(input: AddRequirementInput): MutationResult<AddRequirementOutput> | undefined;
```

### Reference Pattern

Use the existing metadata default path in `renderRequirementBlock` and `buildOutputRecord`. Add validation before write in the same style as `isRequirementType` and table-cell guards.

### Implementation Guide

1. Add `DEFAULT_REQUIREMENT_STABILITY` near stability constants or mutation renderer.
2. Change renderer default from `evolving` to `draft`.
3. Change `add-requirement` metadata output record default from `evolving` to `draft`.
4. Reject unknown stability input before file write in core mutation service.
5. Allow explicit canonical stability input.
6. Reject explicit `volatile` input for new add-requirement writes across core, CLI, and MCP before mutation. Parser compatibility keeps existing `volatile` records readable and validator emits the legacy diagnostic.
7. Update CLI and MCP tests so omitted stability renders `draft`.

### Rationale

New requirements start as uncertain text by default. A human or agent should promote them to `evolving`, `stable`, or `frozen` after review.

### Pitfalls

- Do not rely on post-write validation to reject bad input.
- Do not silently rewrite user-provided `volatile` into another value; reject it as legacy-only input for new writes.

### Test Guide

Test files: `test/core/mutation/add-requirement.test.ts`, `test/cli/mutation-commands.test.ts`, `test/mcp/mutation-tools-errors.test.ts`

Scenarios:

- Success: omitted `--stability` writes `| Stability | draft |`.
- Failure: unknown stability is rejected before file mutation.
- Boundary: explicit `stable`, `frozen`, and `deprecated` are accepted when provided.
