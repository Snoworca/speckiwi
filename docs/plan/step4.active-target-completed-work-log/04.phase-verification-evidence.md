#### 구현 가이드

1. `npm run typecheck`를 실행한다.
2. `npm run lint`를 실행한다.
3. `npm test`를 실행한다.
4. `npm run release:check`를 실행한다.
5. release acceptance SRS evidence 갱신 전 `npm run release:acceptance`를 실행한다.
6. 실패가 나오면 output에서 첫 실패 suite와 file path를 기록하고 해당 Phase TASK로 되돌아간다.
7. 성공한 명령과 날짜를 P4-002 evidence에 사용한다.

#### Rationale

이 기능은 parser, bootstrap, CLI, MCP, docs를 동시에 건드리므로 focused tests만으로는 충분하지 않다. full gate가 통과한 뒤에만 verified evidence를 기록한다.

#### 함정 / 주의사항

- test가 실패한 상태로 SRS `Status`를 verified로 바꾸지 않는다.
- release readiness는 Completed Work Log warning을 error로 승격하지 않는다.
- MCP stdio tests는 build output을 요구하므로 typecheck/build 관련 실패를 먼저 해결한다.

#### 테스트 작성 지침

- 성공: 모든 pre_commit_gate 명령 exit code가 0이다.
- 실패: 어떤 명령이 실패했는지 final report에 기록한다.
- 경계: `npm run release:acceptance`가 SRS evidence와 traceability를 함께 검증한다.

#### 구현 가이드

1. P4-001에서 통과한 명령만 evidence reference에 쓴다.
2. 새로 추가된 Requirement Block은 구현 완료 후 `Status`를 `verified`로 바꾸고 AC를 체크한다.
3. 기존 Requirement Block을 수정한 경우 Change Notes에 2026-05-10 row를 추가한다.
4. `docs/spec/00.index.md`의 Status Summary와 Requirement Type Summary count를 갱신한다.
5. `docs/spec/00.index.md`의 Completed Work Log에 이번 기능 완료 row를 추가한다.
6. Completed Work Log row의 Requirement IDs는 이 TASK의 관련 SRS 참조 목록 중 핵심 IDs만 넣는다.
7. `docs/spec/90.appendix.md`의 command/tool/resource tables가 구현 결과와 일치하는지 다시 확인한다.
8. 마지막으로 `npm run release:acceptance`를 한 번 더 실행한다.

#### Rationale

SRS는 구현의 source of truth이면서 evidence ledger다. 구현 전 evidence를 쓰면 실제 동작과 문서가 어긋나므로 full gate 이후에만 갱신한다.

#### 함정 / 주의사항

- Completed Work Log에는 한 줄 summary만 넣고 상세 test output을 넣지 않는다.
- Requirement Block evidence에는 실제 실행한 명령과 test file path만 넣는다.
- count 갱신이 누락되면 release traceability나 validation tests가 실패할 수 있다.
- evidence table의 pipe cell에 `|` 문자를 넣지 않는다.

#### 테스트 작성 지침

- 성공: `npm run release:acceptance`가 updated SRS와 traceability를 통과한다.
- 성공: Completed Work Log row가 `YYYY-MM-DD` date와 one-line summary를 가진다.
- 실패: unknown Requirement ID warning이 새 completed row에서 발생하지 않는다.
- 경계: Active Target이 비어 있어도 validation error가 없다.
