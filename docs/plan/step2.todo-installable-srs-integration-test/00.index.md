## 1. 작업 목적

이 계획은 설치형 Todo 리스트 관리 웹서비스라는 가상 프로젝트를 테스트 중 임시 디렉토리에 만들고, Server와 Web Page 두 SRS scope를 통해 SpecKiwi의 core, CLI, MCP read, MCP mutation 흐름을 통합 검증하기 위한 TDD 계획이다.

완료 후에는 동적으로 생성한 Markdown SRS 세트가 SpecKiwi의 실제 사용 흐름과 가까운 방식으로 파싱, 검증, 조회, 변경되는지 확인할 수 있어야 한다.

## 3. 프로젝트 온보딩 컨텍스트

SpecKiwi는 Git 저장소의 Markdown SRS 문서를 요구사항 원본으로 사용하는 Node.js TypeScript 도구다. 이 작업은 제품 기능을 새로 추가하지 않고, 실제 사용자 워크플로우에 가까운 통합 테스트를 추가한다.

주요 디렉토리 맵:

| Path | Role |
|---|---|
| `test/integration/` | end-to-end style integration tests |
| `src/core/parser/` | SRS discovery and Markdown parsing |
| `src/core/validator/` | SRS validation rules |
| `src/core/query/` | requirement lookup and summary |
| `src/core/mutation/` | add-requirement and status/evidence mutation services |
| `src/cli/` | CLI command entrypoint and JSON output |
| `src/mcp/` | MCP test adapter, tools, resources, structured errors |

핵심 규칙:

- 테스트 파일 쓰기는 모두 UTF-8로 수행한다.
- SRS heading은 `### {ID} — {Title}` 형식을 사용한다.
- `Scope Map`의 `Prefix`와 Requirement ID의 scope segment를 일치시킨다.
- 이번 계획은 full CLI/MCP response parity를 요구하지 않는다.
- MCP mutation 결과는 domain value와 Markdown side effect를 중심으로 검증한다.

빌드와 테스트 치트시트:

| Purpose | Command |
|---|---|
| Build | `npm run build` |
| Typecheck | `npm run typecheck` |
| Integration target | `npx vitest run test/integration/todo-installable-workflow.test.ts --hookTimeout 60000 --testTimeout 60000 --no-file-parallelism` |
| Full integration suite | `npm run test:integration` |
| Lint | `npm run lint` |

도움 요청 경로: SRS 구조 판단이 막히면 `docs/rule/SRS-MD-Rules-v1.0.0.md`의 Requirement Block 규칙과 `src/core/parser/*` parser 계약을 먼저 확인한다. CLI/MCP 결과 차이가 생기면 `src/mcp/errors.ts`의 MCP response boundary를 확인한다.

## 8. TDD 수행 원칙

이 계획은 테스트 추가 작업이므로 Red 단계는 `test/integration/todo-installable-workflow.test.ts`를 먼저 작성하고 같은 파일만 실행해 실패를 확인한다. Green 단계는 production code 변경 없이 기존 surface를 호출하도록 assertion과 helper를 완성한다. production code 결함이 드러나면 별도 요구사항 또는 후속 계획으로 분리하고, 이 계획의 검증 범위를 넓히지 않는다.

## 9. 계획 리뷰 절차

계획 리뷰어는 다음을 확인한다.

| Reviewer | Required Checks |
|---|---|
| SRS Coverage Reviewer | 추적표의 요구사항이 테스트 의도와 연결되는지 확인한다. |
| Integration Feasibility Reviewer | temp workspace, CLI, MCP 호출 순서가 실행 가능한지 확인한다. |
| Junior/Agent Determinism Reviewer | TASK 필수 필드, source_anchors, acceptance_tests, rollback, 금지 표현을 확인한다. |

CRITICAL 또는 HIGH finding이 있으면 계획 파일을 수정하고 다시 리뷰한다.

## 10. 코드 리뷰 절차

구현 후 코드 리뷰어는 다음을 확인한다.

- 테스트가 production code 변경보다 먼저 작성됐는가.
- Red 실패가 새 테스트 파일 부재 또는 기대 assertion 미충족에서 발생했는가.
- 동적 SRS 문서는 SRS-MD Requirement Block 구조를 보존하는가.
- CLI/MCP 전체 response parity를 요구하지 않았는가.
- mutation 후 validation을 다시 실행하는가.
- 검증 명령이 통과하는가.

## 13. 용어집

| Term | Meaning |
|---|---|
| SRS | Software Requirements Specification. 이 저장소에서는 `docs/spec` Markdown 요구사항 문서를 뜻한다. |
| Scope | 요구사항을 묶는 기능 영역이다. 이 계획의 가상 프로젝트 scope는 `SRV`와 `WEB`이다. |
| Target Map | SRS index의 목표 버전 표다. 이 계획은 `todo-installable-v1`을 사용한다. |
| Scope Map | SRS index의 scope 문서 등록 표다. parser는 이 표에서 prefix와 문서 경로를 읽는다. |
| Requirement Block | `### {ID} — {Title}` heading으로 시작하는 단일 요구사항 Markdown block이다. |
| CLI | `speckiwi` command interface다. 테스트는 `main(argv, io)`로 직접 호출한다. |
| MCP | Model Context Protocol interface다. 테스트는 repo test adapter로 tool handler를 직접 호출한다. |
| TDD | 실패 테스트를 먼저 작성하고, 최소 구현으로 통과시킨 뒤, 동작을 유지하며 정리하는 절차다. |
| DoD | Definition of Done. TASK 완료를 판단하는 측정 가능한 기준이다. |
