## 1. 작업 목적

이 계획은 v1.2.0 hardening target에 추가된 15개 planned requirement를 구현하기 위한 Phase별 작업 지침이다. 목표는 SpecKiwi의 `verified`와 release readiness가 실제 parser, validator, evidence, CLI, MCP, init, package, CI 동작으로 증명되도록 만드는 것이다.

구현 순서는 연구 문서의 권고를 따른다. Diagnostic registry를 먼저 세우고, parser/index hardening과 mutation safety를 core에 넣은 뒤 release readiness와 CLI/MCP surface를 확장한다. 마지막 Phase에서 CI, coverage, SRS evidence, Completed Work Log를 갱신한다.

## 2. 프로젝트 온보딩 컨텍스트

SpecKiwi는 Git 저장소 내부의 Markdown SRS를 source of truth로 쓰는 Node.js TypeScript CLI와 stdio MCP server다. Parser가 `docs/spec/00.index.md`와 scope SRS 파일을 읽고, validator/query/mutation/workflow core service를 CLI와 MCP adapter가 공유한다.

주요 디렉터리 맵:

| Path | Role |
|---|---|
| `src/core/types.ts` | parser, query, mutation, workflow가 공유하는 normalized type |
| `src/core/diagnostic.ts` | diagnostic 생성과 summary helper의 진입점 |
| `src/core/parser/` | index, Requirement Block, table, AC, evidence, trace parser |
| `src/core/validator/` | workspace validation rules와 rule registry |
| `src/core/query/` | target summary, lookup, completed work read contract |
| `src/core/mutation/` | requirement, evidence, trace, active target, completed work mutation |
| `src/core/patch/` | line patch plan과 atomic write layer |
| `src/core/bootstrap/` | init template, bundled rules, AGENTS/CLAUDE managed block |
| `src/core/workflow/` | release readiness, evidence workflow |
| `src/cli/commands/` | Commander 기반 read/mutation command |
| `src/mcp/` | MCP tool, resource, schema, stdio SDK bridge |
| `test/fixtures/workspaces/` | parser, validator, CLI, MCP fixture |
| `docs/spec/` | 제품 SRS source of truth |

핵심 규칙:

- 새 behavior는 v1.2.0 SRS requirement ID에 매핑한다.
- Diagnostic code는 registry에 등록하지 않고 emit하지 않는다.
- CLI와 MCP는 core payload builder와 mutation service를 공유한다.
- Markdown table cell mutation은 공통 helper로 pipe와 newline을 거부한다.
- Release readiness는 script wrapper가 아니라 core workflow contract다.
- SRS evidence는 명령이 통과한 뒤에만 추가한다.

## 7. Feasibility 요약

| Area | Feasibility | Risk | Mitigation |
|---|---|---|---|
| Diagnostic registry | Medium | Existing code calls `diagnostic()` with free-form code strings. | Add registry first, then convert parser/validator call sites with contract tests. |
| Parser hardening | High | Block boundary changes can alter `record.markdown` and downstream snapshots. | Add fixtures before behavior change, then update only assertions tied to accidental trailing sections. |
| Index consistency | Medium | Current fixture rollups may drift from new rules. | Treat historical rows as warning where SRS allows it, and update fixtures intentionally. |
| Table safety | Medium | Multiple mutation paths interpolate table cells directly. | Centralize helper and test every mutation surface. |
| Optimistic concurrency | High | Patch layer currently checks only replace-line original text. | Add snapshot token to `TextFile` and pre-write freshness check before broad retry policy. |
| Release readiness | High | It spans validation, evidence, trace, local files, URLs, and command evidence. | Implement core collectors with focused tests before script/CLI/MCP exposure. |
| CLI/MCP parity | Medium | Existing MCP resource completed-work stdio shape is raw in tests. | Apply envelope-all with compatibility window documented in Appendix and tests. |
| CI/coverage | Medium | Coverage tooling is not configured. | Add Vitest coverage provider and thresholds in the same Phase as CI. |

## 8. TDD 수행 원칙

각 TASK는 Red 단계에서 현재 누락이나 drift를 재현하는 테스트를 먼저 작성한다. Green 단계는 core service를 먼저 구현하고 CLI/MCP adapter를 얇게 연결한다. Refactor 단계는 payload shape, diagnostic code, tests가 같은 contract를 쓰는지 확인한다.
