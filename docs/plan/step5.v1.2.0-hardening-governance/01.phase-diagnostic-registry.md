## 1. 목표

Diagnostic code 의미를 code-level registry로 고정한다. Parser, validator, index, release readiness가 새 diagnostic을 emit하기 전에 registry entry를 먼저 추가하도록 만든다.

## 2. TASK 목록

#### 구현 가이드

1. `src/core/diagnostic-registry.ts`를 만들고 `DiagnosticDefinition` 배열을 export한다.
2. 기존 `SRS-E001`부터 `SRS-W015`까지 현재 emit되는 code를 모두 등록한다.
3. v1.2.0에서 추가될 parser/index/release code를 placeholder 없이 실제 title과 source rule로 등록한다.
4. `diagnostic()`은 unknown code를 받으면 developer error를 던지도록 만든다. 기존 테스트에서 의도하지 않은 unknown code가 있다면 registry를 보강한다.
5. `summarizeDiagnostics()`를 `src/core/diagnostic.ts`에 두어 CLI/MCP/release가 같은 summary shape를 쓰게 한다.
6. rules doc diagnostic table과 registry가 code, severity, title 수준에서 일치하는 contract test를 작성한다.

#### Rationale

Registry가 먼저 없으면 P2와 P4에서 새 diagnostic code가 다시 흩어진다. 이 TASK가 끝나야 이후 Phase에서 새 diagnostics를 추가할 때 code meaning이 안정된다.

#### 함정 / 주의사항

- Registry entry의 `severity`와 emit call의 severity가 다르면 테스트가 실패해야 한다.
- Message text는 context를 포함할 수 있으므로 exact full message보다 code와 title contract를 우선 검증한다.
- Rules document를 생성기로 전환하지 않는다면 contract test가 drift를 잡아야 한다.

#### 테스트 작성 지침

- 성공: 모든 current diagnostics가 registry에 있다.
- 실패: unknown diagnostic code를 emit하면 테스트가 실패한다.
- 성공: rules doc diagnostic table code set이 registry subset과 일치한다.
- 경계: warning code는 `warnings` count에, error code는 `errors` count에 들어간다.

| 예상 소요 | 4시간 |

#### 구현 가이드

1. Code fence heading, malformed heading inside code fence, final block boundary fixture를 만든다.
2. Duplicate section, nested AC, forbidden heading content, malformed metadata/evidence/trace table fixture를 만든다.
3. Duplicate target, duplicate scope prefix, missing scope document, unregistered `.srs.md`, stale Status Summary, stale Requirement Type Summary fixture를 만든다.
4. Red assertions는 P2 구현 전 실패하도록 code expectations를 registry code names로 작성한다.
5. Fixture text는 minimal valid index와 one scope document를 기준으로 유지한다.

#### Rationale

Parser behavior 변경은 regression surface가 넓다. Red fixture를 먼저 만들면 P2가 accidental parser behavior를 보존하는 방향으로 흐르지 않는다.

#### 함정 / 주의사항

- Fixture가 여러 diagnostics를 동시에 만들면 assertion이 불안정해진다. 한 fixture가 한 primary behavior를 드러내게 나눈다.
- Code fence 안 heading은 record도 diagnostic도 만들지 않아야 한다.

#### 테스트 작성 지침

- 성공: valid-basic fixture는 계속 errors 0이다.
- 실패: hardening fixture는 P2 구현 전 expected code가 없어서 Red가 된다.
- 경계: CRLF fixture는 계속 parser line number를 보존한다.
