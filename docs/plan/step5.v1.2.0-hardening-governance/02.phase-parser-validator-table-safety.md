### TASK-P2-001 — Fenced-code-aware block scanner and documented block boundary

| Field | Value |
|---|---|
| 관련 SRS 참조 | `FR-PARSE-011` |
| 파일 경로 | 수정: `src/core/parser/block-scanner.ts`, `src/core/parser/workspace-parser.ts`, `test/core/parser/workspace-records.test.ts`, parser hardening fixtures |
| 메서드/함수 시그니처 | `function scanRequirementBlocks(lines: string[], filePath?: string): { blocks: RequirementBlockRange[]; diagnostics: Diagnostic[] }`; `function parseRequirementHeading(line: string): RequirementHeading | undefined` |
| 참고 패턴 | `src/core/parser/block-scanner.ts:23-42`의 linear scan을 fenced-code state machine으로 확장한다. |
| source_anchors | `["src/core/parser/block-scanner.ts:15-42", "src/core/parser/workspace-parser.ts:7-27", "test/core/parser/workspace-records.test.ts:8-70", "docs/spec/20.parser-validation.srs.md:622-678"]` |
| 예상 소요 | 5시간 |

#### 구현 가이드

1. Backtick fence와 tilde fence를 감지하는 `inFence` state를 scanner 내부에 둔다.
2. `inFence` 상태에서는 `### ` heading-like text와 malformed heading diagnostic을 모두 무시한다.
3. Requirement extraction은 `## 4. Requirements` 이후에서 시작하고, 다음 top-level `## ` heading 또는 EOF에서 종료한다.
4. Requirement block end는 다음 valid requirement heading, top-level boundary, EOF 중 가장 가까운 줄로 계산한다.

#### Rationale

현재 scanner는 code fence 내부 예시도 requirement 후보로 본다. Release readiness가 모든 SRS file을 신뢰하려면 parser boundary가 먼저 고정되어야 한다.

#### 함정 / 주의사항

- 마지막 requirement markdown에 후속 top-level section이 포함되던 기존 accidental behavior를 유지하지 않는다.
- Malformed heading inside fence는 diagnostic을 만들지 않는다.

#### 테스트 작성 지침

- 성공: fenced code 내부 `### FR-...`는 record를 만들지 않는다.
- 성공: fenced code 내부 malformed heading-like text는 diagnostic을 만들지 않는다.
- 경계: 마지막 Requirement Block은 다음 top-level section 앞에서 끝난다.

### TASK-P2-002 — Duplicate section, nested AC, heading content, and malformed table diagnostics

| Field | Value |

| 파일 경로 | 수정: `src/core/parser/section-parser.ts`, `src/core/parser/ac-parser.ts`, `src/core/parser/table.ts`, `src/core/query/records.ts`, `test/core/parser/workspace-records.test.ts`, parser hardening fixtures |
| 메서드/함수 시그니처 | `function parseRequirementSections(block: RequirementBlockRange, lines: string[]): { sections: Record<string, SectionRange>; diagnostics: Diagnostic[] }`; `function parseAcceptanceCriteria(section?: SectionRange): { criteria: AcceptanceCriterion[]; diagnostics: Diagnostic[] }`; `function parseMarkdownTable(lines: string[], startLine: number, options?: TableParseOptions): ParsedTableResult` |
| 참고 패턴 | `src/core/parser/section-parser.ts:11-30`, `src/core/parser/ac-parser.ts:4-19`, `src/core/parser/table.ts:21-52`의 pure parser shape를 diagnostics-aware result로 확장한다. |
| source_anchors | `["src/core/parser/section-parser.ts:11-30", "src/core/parser/ac-parser.ts:4-19", "src/core/parser/table.ts:21-52", "src/core/query/records.ts:1-58", "docs/spec/20.parser-validation.srs.md:680-739"]` |
| 예상 소요 | 7시간 |

#### 구현 가이드

1. Duplicate canonical section은 first section을 유지하고 duplicate line diagnostic을 반환한다.
2. AC parser는 top-level task와 nested task를 구분하고 nested AC를 criteria에 넣지 않는다.
3. Requirement heading title validation은 link, emphasis, inline code, emoji를 error diagnostic으로 보고한다.
4. Table parser는 header count와 row cell count mismatch를 table type별 diagnostic으로 반환한다.
5. `toRequirementRecord()`와 workspace parser가 parser diagnostics를 workspace diagnostics에 합친다.

#### Rationale

Duplicate section overwrite, nested AC counting, table width mismatch는 SRS-MD source를 조용히 오염시킨다. Structural violation은 release 전에 diagnostic으로 드러나야 한다.

#### 함정 / 주의사항

- Public parser return type 변경이 넓게 퍼진다. Parser call site를 한 Phase에서 같이 수정한다.
- Nested AC line number는 문서 수정 위치를 찾을 수 있을 만큼 정확해야 한다.

#### 테스트 작성 지침

- 성공: duplicate `#### Requirement`는 diagnostic line을 포함한다.
- 성공: nested `- [ ] AC-2`는 top-level AC count에 들어가지 않는다.
- 성공: heading title의 Markdown link, emphasis, inline code, emoji는 각각 error diagnostic이다.
- 성공: malformed metadata/evidence/trace table row는 registered diagnostic을 낸다.

### TASK-P2-003 — Shared Markdown table cell safety for every table-writing mutation

| Field | Value |
|---|---|
| 관련 SRS 참조 | `FR-NODE-011` |
| 파일 경로 | 수정: `src/core/mutation/render-requirement.ts`, `src/core/mutation/add-evidence.ts`, `src/core/mutation/add-trace.ts`, `src/core/mutation/add-completed-work.ts`, mutation tests; 신규: `src/core/mutation/table-cell.ts`, `test/core/mutation/table-cell-safety.test.ts` |
| 메서드/함수 시그니처 | `function assertSafeMarkdownTableCell(label: string, value: string): MutationResult<void> | undefined`; `function assertSafeMarkdownTableCells(cells: Record<string, string>): MutationResult<void> | undefined` |
| 참고 패턴 | `src/core/mutation/add-completed-work.ts:118-123`의 pipe rejection을 generalized helper로 옮긴다. |
| source_anchors | `["src/core/mutation/render-requirement.ts:32-100", "src/core/mutation/add-evidence.ts:16-24", "src/core/mutation/add-trace.ts:17-27", "src/core/mutation/add-completed-work.ts:111-128", "test/core/mutation/add-requirement.test.ts:8-108", "test/core/mutation/add-completed-work.test.ts:85-107"]` |
| 예상 소요 | 5시간 |

#### 구현 가이드

1. `table-cell.ts` helper를 만들고 pipe `|`, LF, CR을 모두 reject한다.
2. `addCompletedWork()`는 local `includesPipe()`를 제거하고 shared helper를 쓴다.
3. `addVerificationEvidence()`와 `addTraceLink()`는 row 생성 전 table cells를 검증한다.
4. `addRequirement()` 또는 `renderRequirementBlock()` 진입 전에 metadata/evidence/trace/change note table cells를 검증한다.
5. Failure는 structured `MUTATION_DENIED`를 반환하고 target file은 변경하지 않는다.

#### Rationale

Table parser는 escaped pipe round-trip을 지원하지 않는다. Mutation이 unsafe cell을 쓰면 SRS source가 깨지므로 한 helper가 모든 writer를 막아야 한다.

#### 함정 / 주의사항

- Statement와 rationale 본문은 table cell이 아니다. Table row에 들어가는 field만 검증한다.
- Existing completed-work pipe rejection message가 바뀌면 CLI/MCP tests를 함께 조정한다.

#### 테스트 작성 지침

- 성공: add-requirement metadata/evidence/trace table cells에서 pipe/newline을 reject한다.
- 성공: add-evidence, add-trace, add-completed-work가 같은 error code를 쓴다.
- 실패: reject 후 file content가 byte-for-byte 동일하다.
