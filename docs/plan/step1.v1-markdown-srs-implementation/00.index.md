## 1. 작업 목적

이 계획은 삭제된 기존 구현을 기준으로 하지 않고, 현재 `docs/spec`의 Markdown SRS를 원본으로 삼아 SpecKiwi v1.0.0을 새로 구현하기 위한 TDD 실행 계획이다.

완료된 구현은 Git 저장소 내부의 Markdown SRS 문서를 파싱, 검증, 조회, 변경하고 같은 core service를 CLI와 stdio MCP server에서 공유해야 한다. YAML 요구사항 파일, YAML front matter, 별도 요구사항 DB, 대체 source-of-truth는 만들지 않는다.

## 3. 프로젝트 온보딩 컨텍스트

SpecKiwi는 Git 저장소 안의 `docs/spec` Markdown 문서를 요구사항의 원본으로 다루는 Node.js TypeScript 도구다. 사용자는 `speckiwi` CLI로 요구사항을 읽고 검증하며, AI agent는 stdio MCP server를 통해 같은 기능을 호출한다.

주요 디렉토리 맵:

| Path | Role |
|---|---|
| `docs/spec/` | canonical SRS Markdown documents |
| `docs/rule/` | SRS-MD authoring rules |
| `docs/research/` | implementation research input |
| `docs/plan/step1.v1-markdown-srs-implementation/` | this plan and review outputs |
| `src/core/` | parser, validator, query, mutation, patch service |
| `src/cli/` | thin CLI adapter |
| `src/mcp/` | thin MCP adapter and resources |
| `test/` | fixtures, unit tests, integration tests, release checks |

핵심 규칙:

- SRS source-of-truth는 Markdown 본문뿐이다.
- CLI와 MCP는 Markdown을 직접 파싱하거나 직접 파일을 수정하지 않는다.
- 모든 의미 있는 동작은 `src/core` service를 통해 실행한다.
- 변경 command는 line-based patch와 no-write-on-failure를 보장한다.
- `verified`는 모든 AC checked와 non-empty evidence reference가 함께 있을 때만 허용한다.
- stdout purity를 깨뜨리지 않는다. CLI `--json` stdout은 valid JSON만, MCP stdout은 JSON-RPC만 담는다.

빌드와 테스트 치트시트:

| Purpose | Command |
|---|---|
| Install dependencies | `npm install` |
| Build | `npm run build` |
| Typecheck | `npm run typecheck` |
| Unit tests | `npm test` |
| CLI/MCP integration tests | `npm run test:integration` |
| Lint | `npm run lint` |
| Release acceptance | `npm run release:check` |
| Parser performance | `npm run perf:srs` |

도움 요청 경로: SRS 해석이 막히면 `docs/spec/00.index.md`의 scope map에서 대상 문서를 찾고, 해당 Requirement Block의 `Open Questions`, `Trace Links`, `Rationale`를 먼저 확인한다. 여전히 결정이 불가능하면 계획 문서에 `needs_clarification` 항목을 남기고 사용자에게 묻는다.

## 8. TDD 수행 원칙

각 TASK는 다음 순서만 허용한다.

1. Red: 해당 TASK의 실패 테스트를 먼저 작성한다.
2. Red 확인: 새 테스트가 요구한 이유로 실패하는지 확인한다.
3. Green: 테스트 통과에 필요한 최소 구현을 작성한다.
4. Green 확인: TASK별 acceptance_tests를 실행한다.
5. Refactor: 공개 동작을 유지하면서 중복과 경계를 정리한다.
6. Regression 확인: Phase 전체 검증 명령과 pre_commit_gate 관련 명령을 실행한다.

Red 확인 기록은 phase 문서의 TASK 완료 체크리스트에 남긴다. TDD 순서가 깨지면 해당 TASK 변경을 폐기하고 Red부터 다시 시작한다.

## 9. 계획 리뷰 절차

계획 리뷰는 서브에이전트가 수행한다.

| Reviewer | Required Checks |
|---|---|
| SRS Coverage Reviewer | 75개 Requirement ID가 task에 매핑됐는지, AC 핵심 동작이 빠지지 않았는지 검증한다. |
| Implementation Feasibility Reviewer | phase 순서, 파일 경계, TDD 가능성, stdout purity, path safety 리스크를 검증한다. |
| Junior/Agent Determinism Reviewer | TASK 필수 필드, source_anchors, acceptance_tests, rollback, 금지 표현, Windows command를 검증한다. |

CRITICAL 또는 HIGH finding이 있으면 계획 문서를 수정하고 같은 리뷰를 다시 수행한다. MEDIUM finding은 구현 오류를 만들 수 있으면 수정한다. LOW finding은 명확성 개선 항목으로 처리한다.

## 10. 코드 리뷰 절차

각 Phase 구현 후 코드 리뷰어 서브에이전트가 먼저 TDD 준수를 확인한다. 검토 기준은 다음이다.

- 테스트가 구현보다 먼저 작성됐는가.
- Red 실패가 기대한 이유였는가.
- 구현이 SRS 요구사항과 trace table을 만족하는가.
- CLI/MCP adapter가 core service를 우회하지 않는가.
- mutation 실패에서 파일 변경이 없는가.
- 관련 테스트, typecheck, lint, release gate가 통과했는가.

TDD 위반 또는 요구사항 누락이 있으면 해당 TASK 구현을 폐기하고 Red 단계부터 다시 진행한다.
