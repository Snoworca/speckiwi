### U-2 — 2026-11-05 issue #1151 (gh issue view 1151 -R hancomins/orchestrationgrid-server-java --json title,body,comments)

> Issue: https://github.com/hancomins/orchestrationgrid-server-java/issues/1151
> Title: [tooling] SpecKiwi mutation 2종이 성공을 보고하며 SRS 본문을 조용히 파괴한다
>
> ## 무슨 문제인가
>
> SpecKiwi CLI 의 mutation 두 개가 **성공을 보고하면서 SRS 본문을 조용히 파괴한다.** 둘 다 이번 세션에서 **실제로 데이터를 잃었고**, `speckiwi validate` 는 errors 0 으로 통과시켰다.
>
> ## 결함 1 — `append-note --mode replace` 가 섹션 전체를 갈아치운다
>
> ### 증상
>
> ```
> speckiwi append-note FR-PREF-005 --section implementation_notes --mode replace --text "<한 문단>"
> ```
>
> 이름은 "note 를 replace" 로 읽히지만, 실제 동작은 **그 섹션에 있던 모든 항목을 지우고 텍스트 하나로 대체**다. 첫 문단만 고치려던 호출이 `[2026-08-04]` 로 시작하는 항목 3건을 통째로 날렸다.
>
> `--text` 가 **500자 상한**이라는 점이 이 결함을 키운다 — 섹션 전문이 500자를 넘으면 애초에 "전체를 다시 써서 보존" 하는 것이 불가능하므로, replace 를 쓰는 순간 손실이 확정된다.
>
> ### 왜 위험한가
>
> - **`--dry-run` 을 붙여도 무엇이 사라지는지 보이지 않는다.** 미리보기는 넣을 텍스트만 보여준다.
> - **`speckiwi validate` 가 errors 0 으로 통과한다.** 섹션이 비어도 스키마상 유효하기 때문이다.
> - 따라서 **손실이 무증상이다.** 이번에는 우연히 `git diff` 를 읽다가 발견했다. 커밋 후였다면 아무도 몰랐을 것이다.
>
> ### 기대 동작
>
> `--mode replace` 가 섹션 전체를 대체하는 것이 의도라면, 최소한 (a) `--dry-run` 이 **제거될 내용을 함께** 보여주고, (b) 제거 대상이 있으면 확인 플래그를 요구해야 한다. 의도가 "첫 문단만 교체" 라면 그런 모드가 따로 필요하다.
>
> ## 결함 2 — `edit-requirement --statement` 가 `--dry-run` 을 무시하고 다중행을 truncate 한다
>
> ```
> speckiwi edit-requirement <ID> --statement "<여러 줄 텍스트>" --dry-run
> ```
>
> - **`--dry-run` 이 무시되고 실제로 파일이 쓰인다.**
> - 다중행 statement 가 **첫 줄만 남고 잘린다.**
>
> 즉 "미리 보기만 하려던" 호출이 실데이터 손실을 일으킨다. 이 둘이 겹치면 되돌릴 근거조차 화면에 남지 않는다.
>
> ## 재현
>
> 두 결함 모두 SRS 를 실제로 변형하므로, **재현은 임시 브랜치나 복사본에서** 해야 한다. 이번 세션의 손실은 `git diff` 로 확인됐다 — 섹션에서 항목 3건이 사라지고 빈 줄만 남았다.
>
> ## 해야 할 일
>
> 1. `--dry-run` 이 **모든 mutation 에서 실제로 쓰기를 막는지** 확인한다. 한 곳이 무시하면 다른 곳도 의심해야 한다.
> 2. `--mode replace` 의 미리보기에 **제거될 내용**을 포함시킨다.
> 3. 다중행 입력이 조용히 잘리지 않게 한다 — 지원하거나, 지원하지 않으면 **거부**한다. 조용한 truncate 가 최악이다.
> 4. 가능하면 mutation 이 **손실성인지 여부**를 결과에 표시한다(`removedItems` 같은 필드).
>
> ## 왜 지금 올리나
>
> 이 저장소는 SRS 를 요구사항의 정본으로 삼는다. 정본을 고치는 도구가 **성공을 보고하면서 내용을 지우고, 검증기가 그것을 통과시키면**, 요구사항이 조용히 비어도 아무도 모른다. 손실을 발견한 경로가 "사람이 diff 를 읽다가" 하나뿐인 상태다.
>

>

> - 직접 만든 사례(요구 A 가 `[DISCARDED → see B]` 이고 다른 요구가 `Requirement | A | extends` 행을 가짐)와 이 저장소의 실제 사례(`docs/spec/41.server-credential-management.srs.md` 의 `FR-CREDMGMT-005` 를 가리키는 `extends` 행 두 개) 모두 `links check --json`·`validate --json` 진단이 0건입니다.

> **처리 계획:** SpecKiwi 다음 도구 개선 판(5.3.2)에서 `links check`(와 validate)에 "discarded 요구를 가리키는 trace 엣지" 진단을 더하고, 진단 메시지가 폐기 표식의 후속 요구(`see B`)를 함께 안내하게 합니다. 폐기 관계 자체를 기록하는 `supersedes` 행은 진단하지 않습니다. 말씀대로 기존 링크 정리는 이 저장소 쪽 몫으로 두겠습니다. 고친 버전이 나오면 이 이슈에 다시 적겠습니다.
