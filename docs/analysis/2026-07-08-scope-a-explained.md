# 스코프 A란 무엇인가? (주니어 개발자용 설명)

> 한 줄 요약: **"나머지 스킬 2개(kiwi-spec-merge, kiwi-vibe)를 만들려면, 그 스킬이 쓰는 '도구'부터 먼저 제대로 만들어야 한다"** — 그 선행 작업 묶음이 스코프 A입니다.

---

## 1. 먼저, "스킬"이 뭐예요?

SpecKiwi에서 **스킬(SKILL.md)** 은 *실행 코드가 아니라* **AI 에이전트에게 주는 사용설명서(레시피 카드)** 입니다.

> 비유: 스킬은 **요리 레시피 카드**입니다.
> "① 냄비를 꺼내고 ② 물을 끓이고 ③ 면을 넣어라" 처럼,
> AI에게 "이미 있는 도구를 어떤 순서로 쓰라"고 알려줄 뿐입니다.

레시피 카드 자체는 냄비도 가스레인지도 아닙니다. **도구(냄비·가스레인지)는 따로 존재해야** 레시피가 작동합니다.

SpecKiwi에서 그 "도구"에 해당하는 것이 **런타임 오퍼레이션**입니다 — 예: `claim_step`, `validate_step`, `diff_steps`, `start_vibe_task`. 이들은 실제 코드(`src/`)로 구현되고, MCP 도구나 CLI 명령으로 "호출 가능하게 등록"되어 있어야 합니다.

---

## 2. 방금 우리가 성공한 것 (kiwi-step)

`kiwi-step` 레시피는 **잘 만들었습니다.** 이유는 간단합니다 — 그 레시피가 쓰는 도구가 이미 다 있었거든요.

| kiwi-step이 쓰는 도구 | 상태 |
|---|---|
| `claim_step` (step 선점) | ✅ 코드 있음 + MCP 도구로 등록됨 |
| `validate_step` (검증) | ✅ 코드 있음 + MCP·CLI 둘 다 등록됨 |

→ 도구가 다 있으니 레시피(SKILL.md)만 쓰면 끝. 그래서 kiwi-step은 **verified(검증 완료)** 로 닫혔습니다.

---

## 3. 왜 나머지 2개는 보류됐나 (핵심)

`kiwi-spec-merge`와 `kiwi-vibe` 레시피는 **도구가 없어서** 못 만들었습니다.

> 비유:
> - **`diff_steps`** = **전원이 안 꽂힌 전자레인지.** 물건(코드)은 부엌에 있는데, 콘센트(MCP/CLI 등록)에 연결이 안 돼 있어서 버튼을 눌러도 안 켜집니다.
>   - 실제: 코드는 `src/core/query/diff-steps.ts`에 있지만, MCP 도구/CLI 명령으로 등록이 안 됨 → 레시피가 호출할 방법이 없음.
> - **`start_vibe_task`** = **아예 안 산 오븐.** 부엌에 없습니다.
>   - 실제: `src/` 어디에도 코드가 없음.

여기에 **더 나쁜 문제**가 하나 있습니다:

> 부엌 **재고 장부(SRS 명세)** 에는 이 두 도구가 **"보유 중(implemented)"** 이라고 잘못 적혀 있습니다.
> - `FR-MCP-044`(diff_steps 도구) → 장부: 보유중 / 실제: 전원 미연결
> - `FR-MCP-046`(start_vibe_task 도구) → 장부: 보유중 / 실제: 없음
>
> 이걸 **phantom-implemented(유령 구현)** 라고 부릅니다. 예전 대규모 "살베지" 작업이 *"파일이 있으면 구현된 걸로 친다"* 는 대충한 기준으로 장부를 채운 탓입니다.

**요점**: 레시피(스킬)가 문제가 아니라, 레시피가 부르는 **도구 자체가 없거나 안 켜져 있고, 장부는 거짓말을 하고 있다**는 것.

---

## 4. 그래서 "스코프 A" = 무슨 일을 하는 것?

나머지 2개 스킬을 진짜로 완성하기 위한 **선행 작업 3묶음**입니다:

### 1단계. 재고 장부부터 진실로 고치기 (거버넌스)
- `FR-MCP-044`, `FR-MCP-046`의 상태를 `implemented`(거짓) → `planned`/`in_progress`(진실)로 되돌린다.
- **왜 먼저?** "없는 도구를 있다고 적힌 장부" 위에 뭔가를 쌓으면, 나중에 아무도 뭐가 진짜인지 모르게 됩니다. 거짓 장부 위에 짓지 않는다 — 이게 규칙입니다.

### 2단계. 없는 도구를 실제로 만들기 (TDD로)
- **`diff_steps`**: 이미 있는 코드를 MCP 도구 + CLI 명령으로 **"콘센트에 연결"**(등록)하고, 연관된 merge-journal(중단 후 이어하기 기록)도 연결한다.
- **`start_vibe_task`**: **처음부터 구현**한다. 순서가 중요함 — 먼저 `intent.md`(작업 의도 기록)를 쓰고, *그다음* Active Task를 설정(중간에 죽어도 의도 없는 작업이 안 생기게). MCP 도구로 노출.
- 각 도구마다 **실패하는 테스트 먼저 → 구현 → 통과**(TDD) 순서로.

### 3단계. 그제서야 스킬 2개 만들기 (kiwi-step과 똑같은 방식)
- `kiwi-spec-merge`(step→body 병합 오케스트레이터), `kiwi-vibe`(vibe 모드 진입) SKILL.md + 테스트 작성.
- 4단계 파이프라인(feasibility→planner→pm→review-fix-loop)으로 검증까지.

---

## 5. 한눈에 비교

| | kiwi-step (완료 ✅) | kiwi-spec-merge / kiwi-vibe (스코프 A) |
|---|---|---|
| 필요한 도구 | 이미 다 있었음 | 없거나 안 켜져 있음 |
| 장부(SRS) | 정확 | **거짓(유령 구현)** |
| 할 일 | 레시피만 작성 | 장부 수정 + 도구 제작 + 레시피 작성 |
| 규모 | 작음 (파일 몇 개) | **큼** (런타임 신규 개발 포함) |

---

## 6. 왜 지금 자동으로 안 하고 물어봤나?

- 원래 요청은 *"스킬(레시피) 3개 만들기"* 였는데,
- 실제로는 *"도구를 새로 개발 + 명세 정정"* 이라는 **훨씬 크고 성격이 다른 일**로 밝혀졌습니다.
- 무인(--auto)으로 이만큼 범위를 마음대로 키우는 건 위험해서, **방향만 확인**받으려고 멈춘 것입니다.

> **스코프 A를 하겠다고 하시면**: 위 1→2→3 순서로 (명세 정정 → 런타임 TDD 구현 → 스킬 구현) 진행합니다.
